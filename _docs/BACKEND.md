## 1. Auth, sessions & roles

**What it is.** Supabase Auth (email+password, Google/Apple OAuth, email confirmation link, phone OTP) provides identity; a `profiles` row per user carries the app-level role (`customer` / `salon_owner` / `staff` / `admin`) and ban/suspension state. Every server-side identity check goes through `supabase.auth.getUser()`, never `getSession()`, enforced by a pre-commit hook.

**How it works.**

*Identity verification, the getUser()-not-getSession() rule.* `lib/supabase.ts:68-72` (`getSessionUser()`) and `lib/auth/require.ts:51-63` (`requireAuth()`) both call `supabase.auth.getUser()`, which round-trips to the Supabase Auth server to verify the JWT signature and returns `null` on any failure (fails closed). `supabase.auth.getSession()` instead trusts the client-supplied cookie's claims without verifying them, so a forged cookie could set any `user.id`. The whole backend was migrated off `getSession()` for authz on 2026-07-10 (commit `9783e5711`), and `.claude/hooks/no-getsession-authz-gate.py` now blocks any new `Write`/`Edit` that introduces a real (non-comment) `auth.getSession()` call in `app/**` or `lib/**`, except files starting with `"use client"` (client components legitimately read their own session for UI redirects, e.g. `components-legacy/auth/SignIn.tsx:48`, `app/[locale]/auth/register/page.tsx:240`, both call `getSession()` for a "already logged in, bounce away" check, which is not a security boundary).

*Middleware.* `middleware.ts:101-146` runs a Supabase SSR client on every request, calls `getUser()` with a 4-second timeout race (`middleware.ts:142-146`) so a hung Auth-server call can't hang the whole app, and treats a rejected promise the same as a timeout (both resolve to `user: null`) so a transient error can't silently fall through to the unauthenticated pass-through path. For any path under `/{locale}/dashboard`: no user → redirect to `/auth/login?redirect=<path>` (`middleware.ts:154-163`); user present → loads `profiles.role` (`middleware.ts:165-169`); if role is neither `salon_owner` nor `admin`, it checks whether the user owns any row in `salons` and self-heals the role to `salon_owner` if so (`middleware.ts:175-191`, a stale-role safety net for onboarding failures); otherwise redirects home. A fixed list of admin-only subpaths (`all-salons`, `all-users`, `platform-analytics`, `badge-manager`, `content-editor`, `segments`, `revenue`, `review-moderation`, `approvals`, `editor`, `discovery-admin`, `nail-admin`, `cases`) additionally requires `role === "admin"` (`middleware.ts:203-221`). Any exception thrown inside this whole block fails CLOSED for dashboard paths (redirects to login) rather than falling through to the plain pass-through response (`middleware.ts:223-240`, an explicitly documented fix for a prior auth-bypass-on-DB-blip bug).

*Shared auth helpers exist but are barely adopted.* `lib/auth/require.ts` defines the "canonical" return-or-`NextResponse` helpers `requireAuth`, `requireAdmin`, `requireSalonOwner`, `requireRole`, re-exported from `lib/auth/index.ts:1`. In practice, **zero files under `app/` or `lib/` import from `@/lib/auth` or `@/lib/auth/require`** (verified by grep across the whole tree). Instead, 244 files call `supabase.auth.getUser()` directly and re-implement the pattern inline: 84 files inline an admin check shaped like `profile?.role !== "admin"` (e.g. `app/api/admin/users/route.ts:18-23`, `app/api/admin/users/route.ts:46-52`), 50 files inline an owner check shaped like `salon.owner_id !== user.id`. The clearest evidence of non-adoption: `app/api/admin/seed-test-salons/route.ts:18-30` defines its own local async function literally named `requireAdmin()` that duplicates the shared helper's logic instead of importing it. `getSessionUser()` (`lib/supabase.ts:68`) fares slightly better with 4 real call sites outside its own file. Net effect: `lib/auth/require.ts` is effectively dead code today, and the actual "canonical" pattern to follow when reading or writing a new route is the inline `getUser()` + `.from("profiles").select("role")` shape seen in the 244 direct callers, not the helpers in `lib/auth/`.

*Roles: where stored, where checked, how they get set.* `profiles.role` is a plain `text` column (see `lib/database.types.ts:4431`) gated by a Postgres CHECK constraint, most recently `role IN ('customer', 'salon_owner', 'staff', 'admin')` (`supabase/migrations/075_compliance_roles_schema.sql:11-12`, superseding the earlier 3-value constraint in `supabase/migrations/014_new_schema.sql:29`). New users get a `profiles` row via the `on_auth_user_created` trigger → `handle_new_user()` (`supabase/migrations/014_new_schema.sql:60-63`, function body in `supabase/migrations/076_update_handle_new_user.sql:6-20`), which inserts `display_name`/`avatar_url`/`locale`/`birthday` from `auth.users.raw_user_meta_data` but never sets `role`, so every new profile gets the column default (`'customer'`). A user becomes `salon_owner` later (during salon creation/onboarding, not in this trigger) or via the middleware self-heal described above. `staff` is a valid DB value but **nothing in `app/` or `lib/` ever writes `role = 'staff'`**: `app/api/staff/accept-invite/route.ts:107-111` only sets `profiles.staff_salon_id` and inserts/links a `staff_members` row, it never touches `role`. Since `middleware.ts`'s dashboard gate only admits `role === "salon_owner" || role === "admin"`, a staff member who accepts an invite (their `role` stays `customer`) will be bounced by the middleware's `/dashboard` gate the moment they follow the "Go to Dashboard" link the accept-invite success screen shows them (`app/[locale]/staff-invite/page.tsx:97`). Nothing in `app/[locale]/dashboard/**` or `middleware.ts` checks `staff_salon_id`. Multi-salon owner scoping is resolved separately by `lib/active-salon.ts` (`getActiveSalonId`/`getActiveSalon`, `owner_id`-only, cookie-based salon switcher), which is unrelated to and not used by `requireSalonOwner` in `lib/auth/require.ts`.

*Privilege-escalation guard on `profiles`.* The RLS policy `profiles_update_own` (`supabase/migrations/014_new_schema.sql:74-75`) lets any authenticated user `UPDATE` every column of their own row with no column restriction (`FOR UPDATE USING (auth.uid() = id)`). The only thing stopping a user from self-promoting via a direct client-side `.update({role:"admin"})` call is a `BEFORE UPDATE` trigger added 2026-07-11, `guard_profile_privilege_columns()` (`supabase/migrations/20260707095749_security_phase1_profiles_privilege_guard.sql:4-19`): unless `auth.role() = 'service_role'`, it force-resets `role`, `is_admin`, `is_suspended`, and `account_status` back to their `OLD` values on every update. This means privileged-column writes only take effect through routes using `createAdminSupabaseClient()` (service role), e.g. `app/api/admin/users/route.ts:59-69`.

*OAuth (Google, Apple).* Both providers are wired client-side, not server-side: `components-legacy/auth/SignIn.tsx:54-74` calls `supabase.auth.signInWithOAuth({ provider: "google" | "apple", options: { redirectTo: "/api/auth/callback?redirect=..." } })` directly on the browser client (`lib/supabase-browser.ts`). There is also a server-side Google-only path at `app/api/auth/login/route.ts:35-46` (`oauthSchema` only accepts `provider: z.literal("google")`) that returns the provider redirect `url` to the caller, but it is not the path `SignIn.tsx` actually uses. Both flows land on `app/api/auth/callback/route.ts:8-72`, which validates the `redirect`/`next` query param is a safe internal relative path (blocks `//`, backslash-based protocol-relative tricks per the WHATWG URL-parsing quirk noted in the comment), then calls `supabase.auth.exchangeCodeForSession(code)` (`app/api/auth/callback/route.ts:44`) on an SSR client whose cookie `setAll` writes onto the redirect response, so the session cookies survive the redirect. On success, if the destination isn't `/onboarding/salon` and the profile's `onboarding_completed` is falsy, it rewrites the redirect `Location` to `/{locale}/onboarding` (`app/api/auth/callback/route.ts:50-66`). Apple's OAuth client-secret is a signed JWT with a hard Apple-imposed max lifetime and must be periodically re-minted in the Supabase Auth provider dashboard; this is an external Apple Developer / Supabase-project config concern, not something in this repo's code (no file in this worktree references it; noted here per project memory, un-groundable in a file, flagged as an operational reminder only).

*Email + password, and email confirmation link.* `app/api/auth/signup/route.ts:34-75` validates with `signupSchema` (password needs 8+ chars, one uppercase, one digit; either `birthday` with age ≥16 or a `salon_name`), then calls `supabase.auth.signUp()` with `emailRedirectTo: /api/auth/callback?redirect=<onboarding path>` (`app/api/auth/signup/route.ts:52-59`). It deliberately returns the same generic 200 response whether the email is new or already registered, to avoid an email-enumeration oracle (`app/api/auth/signup/route.ts:70-74`, checking `data.user.identities.length`). Login is `app/api/auth/login/route.ts:58-67` via `signInWithPassword`, but the UI (`components-legacy/auth/SignIn.tsx:81-84`) actually calls `signInWithPassword` directly on the browser client rather than hitting this route, so cookies are set client-side. Password reset is `resetPasswordForEmail` (`app/api/auth/login/route.ts:50-56`) landing on `app/[locale]/auth/reset-password/page.tsx`, which exchanges the `code` query param for a session client-side (`page.tsx:34`) before allowing `supabase.auth.updateUser({ password })`.

*Email/phone OTP.* `app/api/auth/verify-otp/route.ts:14-39` wraps `supabase.auth.verifyOtp({ email, token, type })` for a 6-digit code against `type: "signup" | "email"`; no file in `app/` or `components-legacy/` calls this route (grepped, zero hits), so it currently has no discoverable web caller, it may be intended for the mobile app or is dead. Phone OTP is bespoke (not Supabase's phone auth): `app/api/auth/verify-phone/send/route.ts` generates a 6-digit code with `crypto.randomInt` (`send/route.ts:42`), stores it in Upstash Redis under `phone_otp:{phone}` for 10 minutes (`send/route.ts:45`), and sends it via seven.io SMS (`send/route.ts:57-68`, `X-Api-Key` header, silently no-ops to a "simulated" success if `SEVEN_API_KEY` is unset). `app/api/auth/verify-phone/check/route.ts:43-63` reads the stored code back from Redis and compares. Both routes double rate-limit: once on caller IP, once on the normalized target phone number (`send/route.ts:33-35`, `check/route.ts:31-33`), specifically to stop an attacker from SMS-bombing or brute-forcing one victim's number by rotating IPs. Neither route creates a Supabase Auth session; the verified state is just handed back to the caller for the client to use later (comment in `check/route.ts:56-61` notes the salon-creation flow is expected to persist `salons.phone_verified` itself).

*Dev-only session minting.* `app/api/dev/login/route.ts:18-60` is hard-gated to `NODE_ENV === "development"` (returns 404 otherwise, so it 404s on the real Netlify production build) and mints a magic-link for a fixture salon-owner account (`hiroseseiju@proton.me`) via `admin.auth.admin.generateLink()`, then verifies it server-side and writes the session cookies onto a redirect response, honoring a relative `to` query param so it survives being accessed through a tunnel.

*Ban/suspend gate.* `lib/feature-flags.ts:149-183` (`checkUserBanned(userId)`) is the live enforcement gate, called at the top of roughly 100 route handlers right after `getUser()` (pattern: `getUser()` → `checkUserBanned(user.id)` → proceed, e.g. `app/api/nail-discovery/publish/route.ts:16-23`). It reads `profiles.banned_at`/`ban_reason` via the admin (service-role) client, returns 403 `USER_BANNED` if `banned_at` is set, and fails CLOSED on any DB error other than "no rows" (PGRST116), returning 503 rather than letting a banned user through on a transient failure. A clean read is cached in-process for 10 seconds (`BAN_TTL_MS`, `lib/feature-flags.ts:119`) so a freshly-banned user stops slipping through on a warm serverless instance within ~10s; a query error is never cached. **However, there is currently no write path anywhere in `app/` or `lib/` that sets `banned_at`/`ban_reason`** (a `adminUserUpdateSchema` zod schema for it exists at `lib/validations.ts:766-770` but is imported nowhere else in the codebase; the only route that references `banned_at` besides the check itself is a read in `app/api/cron/review-prompt/route.ts:73,234` to skip review-prompt emails to banned users). Banning a user today can only happen via a direct DB write (Supabase Studio / SQL), not through any app-level admin action. Separately, `profiles.is_suspended` (boolean) DOES have a working write path, `PATCH /api/admin/users` (`app/api/admin/users/route.ts:44-72`, admin-role-gated, uses the service-role client so it passes the privilege guard trigger), and a working read/display path in the admin UI (`app/[locale]/dashboard/all-users/page.tsx`), **but `is_suspended` is never read by `checkUserBanned()` or by any other gate** (grepped across `app/`, `lib/`, `middleware.ts`). A third, distinct field, `profiles.account_status` (`'active' | 'warned' | 'suspended' | 'banned'`, added by the same migration that added `staff` to the role enum, `supabase/migrations/075_compliance_roles_schema.sql:15-18`), is only referenced by the GDPR deletion-request routes (`app/api/profile/request-deletion/route.ts`, `app/api/profile/delete/route.ts`), not by any ban enforcement. Net: three separate "is this account restricted" fields exist in the schema (`banned_at`/`ban_reason`, `is_suspended`, `account_status`), only one (`banned_at`) is actually enforced on API traffic, and that one has no UI/API way to set it.

**Gotchas + invariants.**
- Never use `supabase.auth.getSession()` server-side for an identity/authz decision. It trusts the cookie's claims without verifying the JWT signature; a forged cookie can set any `user.id`. Always use `getUser()`. Hook-enforced (`.claude/hooks/no-getsession-authz-gate.py`), historical fix at commit `9783e5711` (2026-07-10).
- `lib/auth/require.ts`'s `requireAuth`/`requireAdmin`/`requireSalonOwner`/`requireRole` are effectively dead code (zero real importers found by grep). Don't assume new routes use them just because the file calls itself "canonical" in its docblock; check the actual route before assuming a shared-helper pattern is in effect. If you're refactoring auth checks, importing the real helper into new code is an improvement, but it is not what the existing 244 routes do.
- `profiles.role` can be `'staff'` per the DB CHECK constraint, but nothing in the codebase ever writes it. A staff member who accepts an invite keeps `role = 'customer'` and gets salon-scoped access purely via `staff_salon_id` + a `staff_members` row. `middleware.ts`'s `/dashboard` gate only admits `salon_owner`/`admin`, so as the code stands today, a staff member following the "Go to Dashboard" link after accepting an invite will be redirected away by the middleware. If you touch staff-dashboard access, this needs either a middleware exception for `staff_salon_id`, or the accept-invite route needs to set `role = 'staff'` (and every downstream role check needs to accept it).
- Three separate "restricted account" fields exist on `profiles` (`banned_at`/`ban_reason`, `is_suspended`, `account_status`), but only `banned_at` is read by the live enforcement gate (`checkUserBanned` in `lib/feature-flags.ts`), and `banned_at` currently has no write path anywhere in the app (only a direct DB write can set it). `is_suspended` has an admin UI + API write path (`PATCH /api/admin/users`) but is never checked by anything. Don't assume flipping `is_suspended` in the admin panel actually blocks the user, it doesn't, today.
- The `profiles_update_own` RLS policy (`FOR UPDATE USING (auth.uid() = id)`) has no column restriction; the only thing preventing a user from self-promoting to admin via a direct client update is the `guard_profile_privilege_columns()` trigger (added 2026-07-11), which silently resets `role`/`is_admin`/`is_suspended`/`account_status` back to their old values unless the request comes from `service_role`. If this trigger is ever dropped or a new migration recreates the `profiles_update_own` policy without re-checking the trigger exists, this is a live privilege-escalation hole, not a theoretical one, verify it's still attached before touching `profiles` RLS.
- Every auth/OTP route is rate-limited by `authLimiter` (5/min per IP via `applyRateLimit`), and phone OTP additionally rate-limits per normalized target phone number, not just IP, specifically because IP-only limiting lets an attacker SMS-bomb or brute-force one victim's number by rotating IPs.
- `app/api/auth/signup/route.ts` always returns the same generic success response whether the email is new or already registered (email-enumeration defense); don't "fix" this to return a more specific error without re-adding that defense.
- `app/api/auth/callback/route.ts` validates the `redirect`/`next` param against `startsWith("/")`, `!startsWith("//")`, and no backslash, specifically because `new URL()` treats `\` as `/` per the WHATWG spec, so a naive `startsWith("/")` check alone is bypassable with `/\evil.com`. Preserve all three checks if this logic is ever touched.
- `getUser()` calls in `middleware.ts` race against a 4-second timeout and treat both the timeout and a rejected promise identically as "no user" (`middleware.ts:142-146`); a prior version let a rejected (not just slow) `getUser()` fall through to the outer `catch`, which then returned the plain pass-through response, an auth bypass on a transient error. Any future edit to this block must keep the reject-and-timeout paths equivalent.
- The Apple OAuth provider secret is a signed JWT with an Apple-imposed expiry and needs periodic re-minting in the Supabase Auth dashboard; per project memory this is due before 2026-12-30. This is pure ops/config, not code in this repo, there is nothing to grep for it here.

**Where to look when changing it.**
- New protected API route: start from an existing route in the same family (e.g. `app/api/nail-discovery/publish/route.ts` for the `getUser()` → `checkFeatureEnabled()` → `checkUserBanned()` → rate-limit shape) rather than `lib/auth/require.ts`, since that's the pattern actually in force across the codebase today.
- Changing the dashboard role gate or adding a role: `middleware.ts:148-222`.
- Changing what counts as "banned": `lib/feature-flags.ts` (`checkUserBanned`) plus deciding whether to also wire in `is_suspended`/`account_status`, and adding an actual write path for `banned_at` if one is wanted.
- Changing OAuth providers or redirect handling: `components-legacy/auth/SignIn.tsx` (client-side kickoff) and `app/api/auth/callback/route.ts` (code exchange + redirect safety + onboarding rewrite).
- Changing signup/login validation or password rules: `app/api/auth/signup/route.ts` and `app/api/auth/login/route.ts` (zod schemas at the top of each file).
- Changing phone OTP: `app/api/auth/verify-phone/send/route.ts` + `check/route.ts`, both keyed off Upstash Redis and seven.io.
- Changing the profile-creation defaults or the role enum: `supabase/migrations/076_update_handle_new_user.sql` (trigger function) and the latest `profiles_role_check` constraint (currently `075_compliance_roles_schema.sql`), remembering DB migrations here are additive/idempotent only, never `db push`/`db reset` (project-wide rule).

## 2. Database, RLS & the two-client model

**What it is.** Postgres on Supabase (146 live tables, captured `_inventory/_db-snapshot.json:736` `capturedAt: "2026-07-12"`) with Row Level Security enabled on every table (`rlsDisabled: []` in the same snapshot) as the floor. Every query in the app runs through one of two Supabase client factories in `lib/supabase.ts`, and which one you pick determines whether Postgres's row-level policies are enforced or bypassed.

**How it works.**

*The two clients.* `lib/supabase.ts:15-58` defines `createServerSupabaseClient()`: an `@supabase/ssr` server client built with the **anon key**, reading the caller's session from cookies via `next/headers`. Every query issued through it runs as whatever Postgres role the session resolves to (`authenticated` with `auth.uid()` set, or `anon` with none), so RLS policies are evaluated on every read and write. `lib/supabase.ts:75-90` defines `createAdminSupabaseClient()`: the same `@supabase/ssr` wrapper but built with **`SUPABASE_SERVICE_ROLE_KEY`**, no cookie plumbing, `autoRefreshToken: false`. The `service_role` Postgres role bypasses RLS entirely, so this client sees and can write every row in every table regardless of ownership. `lib/supabase.ts:6-13` documents that `lib/database.types.ts` (the generated `Database` type) is applied to both clients as a compile-time guard: `SupabaseClient<Database>`, so a phantom column or table is now a `tsc` error instead of a silent `null` (per the 2026-07-11 types sprint memory note).

Because the admin client bypasses RLS completely, **every route that uses it is responsible for doing its own ownership/authorization check in application code first** (verify `salon.owner_id === user.id`, verify an HMAC/access token, verify `role === 'admin'`) before issuing the privileged write. RLS is not a backstop for admin-client code; it simply does not apply.

*The RLS-CLIENT TRAP.* The `availability_slots` table has exactly two policies (`supabase/migrations/014_new_schema.sql:207-217`): `slots_select_available` (`FOR SELECT USING (true)`, public read) and `slots_manage_owner` (`FOR ALL USING (EXISTS (SELECT 1 FROM salons s WHERE s.id = salon_id AND s.owner_id = auth.uid()))`). The second is the only write-capable policy, and it requires the caller to be the **salon owner**. A logged-in customer's session client is never the salon owner, so any UPDATE or DELETE it attempts against `availability_slots` (freeing a slot, claiming a slot) matches **zero rows** under RLS. PostgREST does not surface this as an error: the request returns success with an empty result set, so code that doesn't check the affected-row count believes the write happened. `lib/bookings/claim-slot.ts:12-14` states this explicitly: "MUST be called with a SERVICE-ROLE client. `availability_slots` UPDATE is owner-only under RLS (`slots_manage_owner`), so a booking customer's own session client silently matches 0 rows on this write... (Council 2026-07-07)." `app/api/bookings/[id]/reschedule/route.ts:62-66` carries the same reasoning inline and correctly instantiates `const admin = createAdminSupabaseClient()` before touching any slot row, using the session client only for the `bookings` table write (which the `bookings_update_own` policy does permit for the owning customer).

The `bookings` table (`014_new_schema.sql:253-267`, tightened by the guest-RLS migration `supabase/migrations/20260601_sp1_bookings_guest_rls.sql`) has SELECT, INSERT, and UPDATE policies but **no DELETE policy at all**. Under RLS default-deny, that means nobody except `service_role` can DELETE a `bookings` row through the session client, including the row's own owner. Every delete call I found is routed through an admin/service-role client (`app/api/bookings/express-rebook/confirm/route.ts:106`, `app/api/admin/test-salon/route.ts:148`, `app/api/admin/test-salon/seed/route.ts:154`), **except** the rollback deletes inside the main booking-creation route: `app/api/bookings/route.ts:127` sets `const db = isGuest ? createAdminSupabaseClient() : supabase` (the session client for a logged-in customer), and the three rollback deletes at `app/api/bookings/route.ts:541,549,554` (`await db.from("bookings").delete().eq("id", booking.id)`) run through `db`. For a guest that is the admin client and the delete works; for a logged-in customer it is the session client, which has no DELETE policy to satisfy, so the rollback silently no-ops and the loser of a slot-claim race is left with an orphaned booking row instead of being cleaned up. The same route's slot claim at `app/api/bookings/route.ts:531` (`await db.from("availability_slots").update(slotUpdate)...`) has the identical shape: for a logged-in user this is the session client hitting `slots_manage_owner`, the exact pattern `claim-slot.ts` says "MUST be called with a SERVICE-ROLE client," and this call site does not go through the `claimSlot()` helper (that helper is only wired into `reschedule/route.ts:116`). I could not verify live behavior (no authenticated Supabase MCP session in this environment), and the repo's own `scripts/e2e-booking.ts:15-33` explains it can only exercise the **guest** path end-to-end ("no real logged-in session can be synthesized at function level"), so this exact logged-in code path is not covered by the existing e2e test either. Flagging this as a contradiction between the documented invariant and the code at those three line numbers, worth a live check before relying on it.

A precedent for the correct fix already exists in this codebase: `group_bookings` had the identical class of bug (audit finding at `_plans/BOOKING_BACKEND_AUDIT.md:187`, "the RLS-bound server client group_bookings UPDATE... has no UPDATE policy... matches zero rows... PostgREST reports success with an empty result, not an error, so this failure is invisible") and was closed by two migrations, `audit_fix_group_bookings_rls` and `audit_fix_create_group_booking_rpc_2`, verified live per `_plans/BACKEND_FIX_TRACKER.md:27`.

*Key triggers.* `guard_profile_privilege_columns()` (`supabase/migrations/20260707095749_security_phase1_profiles_privilege_guard.sql`, `SECURITY DEFINER`, `BEFORE UPDATE ON profiles`) resets `role`, `is_admin`, `is_suspended`, `account_status` back to their `OLD` value on any UPDATE where `auth.role()` is not `service_role`, closing the direct-REST privilege-escalation vector (a customer PATCHing their own `profiles` row through PostgREST can no longer grant themselves `role='admin'`). `guard_booking_status_escalation()` (`supabase/migrations/20260709184246_audit_fix_bookings_status_escalation_guard.sql`, `SECURITY DEFINER`, `BEFORE UPDATE ON bookings`) lets `service_role` writes through unconditionally, but rejects (raises `42501`) any non-service-role transition of `status` to `completed` or `no_show` unless the caller is the salon owner or an admin; a customer setting `status='cancelled'` is untouched. This closes the exact vector described in its own comment: a customer PATCHing their own booking to `completed` to farm Solen Status tier + member discount.

*Constraints that prevent double-booking.* `prevent_double_booking` (`supabase/migrations/20260328_prevent_double_booking_gist.sql`) is a `btree_gist` EXCLUDE constraint on `availability_slots`: `EXCLUDE USING gist (staff_member_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (status IN ('booked','blocked'))`, mathematically preventing two overlapping booked/blocked ranges for the same staff member. It fires only when a slot row is newly flipped into an overlapping range for the *same staff member*; it does not stop two different bookings from both referencing the same existing `slot_id` (per `_plans/BOOKING_BACKEND_AUDIT.md:223`, `bookings.slot_id` has no unique constraint). `bookings_one_active_per_slot` (`supabase/migrations/20260707155609_bookings_one_active_per_slot.sql`) closes that second gap: a UNIQUE INDEX on `bookings(slot_id)` filtered `WHERE slot_id IS NOT NULL AND group_booking_id IS NULL AND status IN ('pending','pending_approval','confirmed')`, so two live (non-cancelled, non-group) bookings can never point at the same slot.

*Migration model.* Schema changes go through the Supabase MCP `apply_migration` tool only, additive and idempotent (`create table if not exists`, `add column if not exists`, `create or replace function`, `drop policy if exists` + `create policy`), never `supabase db push` or `supabase db reset` against the live project (`_rules/DB_SCHEMA.md:87-93`). This applies live and records the SQL in `supabase_migrations.schema_migrations`, but does not automatically write a local file under `supabase/migrations/`, so local and live can drift; `_rules/DB_SCHEMA.md:95-119` documents the backfill recipe (query `schema_migrations` for missing versions, write the file verbatim, regenerate `lib/database.types.ts`, confirm `tsc` error count is unchanged). Several files already carry the `"backfilled 2026-07-11 from supabase_migrations.schema_migrations"` header from this recipe (`20260707095749_security_phase1_profiles_privilege_guard.sql`, `20260709184246_audit_fix_bookings_status_escalation_guard.sql`, `20260707155609_bookings_one_active_per_slot.sql`, all read above). The live DB is canonical; migration files are a re-appliable record, not the source of truth.

**Gotchas + invariants.**
- **The RLS-client trap is real and only partially fixed.** `availability_slots` writes (UPDATE/DELETE) require the salon-owner policy `slots_manage_owner`; a customer's session client silently matches 0 rows. `reschedule/route.ts` and `quick-action/route.ts` route slot writes through `createAdminSupabaseClient()` correctly. The main `bookings/route.ts` creation route's own inline slot-claim (`:531`) and its rollback deletes on `bookings` (`:541,549,554`) use `db`, which is the session client for a logged-in (non-guest) user, not the admin client, and does not go through the documented `claimSlot()` helper. `app/api/bookings/[id]/cancel/route.ts:240-243` frees the slot back to `available` using `supabase` (session client), also not admin, for both the customer-cancel and salon-owner-cancel branches. Any route that flips `availability_slots.status` MUST use `createAdminSupabaseClient()` (or the `claimSlot()` helper) and check the affected-row count; never trust a 0-error response as proof the write happened.
- **`bookings` has no DELETE policy for anyone but `service_role`.** Any code path that needs to delete a `bookings` row (rollback on slot-claim failure, admin test-data cleanup) must use the admin client. A session-client delete silently no-ops.
- **RLS silently returns success on a 0-row match.** This is the single biggest documented failure class across the audits (`_plans/PAYMENTS_BACKEND_AUDIT.md`, `_plans/BOOKING_BACKEND_AUDIT.md`, `_plans/DASHBOARD_CRM_BACKEND_AUDIT.md` each cite multiple instances): a filtered UPDATE whose WHERE/RLS clause doesn't match returns `error: null` and an empty result, identical to what a genuine 0-match legitimately looks like. Every write that matters for correctness (a CAS claim, a status transition, a refund ledger update) must check `.select()` row count or `{count:'exact'}`, not just the `error` field.
- **The admin client does no authorization by itself.** Every route using `createAdminSupabaseClient()` must independently verify the caller owns the resource (salon ownership check, HMAC/access-token verification via `resolveBookingActor()`, or `role==='admin'`) before issuing the write; RLS provides zero protection once you're on the service-role client.
- **Never `supabase db push` / `db reset` against live.** Only additive, idempotent `apply_migration` calls via the Supabase MCP tool; a bare `DROP TABLE` or destructive rewrite is not permitted through that path either. `_rules/DB_SCHEMA.md` section 7 has the exact backfill recipe when a live-applied migration has no local file.
- **Trust the live snapshot over migration files or TS types for schema existence.** `_inventory/_db-snapshot.json` / `_db-columns.json` are regenerated by `npm run inventory`; a column can exist in `database.types.ts` (stale generation) or be referenced in a migration file that was never actually applied, and PostgREST silently returns `null` for a `.select()` on a genuinely nonexistent column rather than erroring.
- **`opening_hours` (on `salons`, not this table, but adjacent) is short-day-keyed** (`mon`…`sun`); flagged here because it's the canonical example this codebase uses for "a convention mismatch that returns an empty/constant result instead of an error," the same shape as the RLS traps above.

**Where to look when changing it.**
- Adding or changing a table/policy: use the Supabase MCP `apply_migration` tool (never edit a migration file and expect it to apply itself), then regenerate `lib/database.types.ts` via `generate_typescript_types` and refresh `_inventory/_db-snapshot.json` / `_db-columns.json` via `npm run inventory`.
- Adding a new customer-facing write to `availability_slots` or `bookings`: use `lib/bookings/claim-slot.ts`'s `claimSlot()` for any slot-status flip, and `createAdminSupabaseClient()` for any `bookings` DELETE; check the affected-row count on every write that gates money or availability, never just the `error` field.
- Investigating "a filter/control does nothing": treat it as the RLS-silent-0-rows pattern first (grep the table's policies in `supabase/migrations/`, cross-check which client the route uses) before assuming the bug is elsewhere.
- Understanding what's actually live: `_inventory/_db-snapshot.json`, `_inventory/_db-columns.json`, and `_rules/DB_SCHEMA.md` section 6, in that order of trust.

*TikTok/discovery thumbnail proxy* (`app/api/discovery/thumb/[id]/route.ts`): three-tier cache in front of TikTok's expiring signed CDN URLs.
1. In-memory `imageCache` (per server-process Map, 1h TTL) — fast path, no DB/network hit (`:76-87`).
2. **Durable Storage tier** — on a memory-cache miss, download `discovery-images/tiktok-cache/{id}.jpg` from Storage (`:96`); if present, serve it and populate the memory cache with header `X-Cache: STORAGE` (`:97-109`). This is what makes a thumbnail survive forever once persisted, independent of TikTok's CDN staying reachable.
3. **Cold path** — look up `discovery_items.tiktok_url` (`:113-117`, stable, non-expiring), call TikTok's oEmbed endpoint on the hardcoded `OEMBED_BASE = "https://www.tiktok.com/oembed"` (`:35,133-136`) to get a freshly-signed thumbnail URL (cached in-memory 1h, `:128-148`), fetch those bytes, then **await** (not fire-and-forget — comment at `:169-171` explains Fluid Compute can freeze post-response work, so a fire-and-forget write would silently stop persisting in prod) an `upload(..., { upsert: true })` back into `discovery-images/tiktok-cache/{id}.jpg` before returning the bytes with `X-Cache: MISS` (`:159-189`).

SSRF safety on this specific route comes from construction, not an explicit guard call: the oEmbed host is a hardcoded string literal and the only attacker-influenceable input is the discovery-item `id`, which maps through a DB lookup to a stored `tiktok_url`, never a raw fetch target. This was reviewed and marked REFUTED (not a bug) in `_plans/CROSSCUTTING_BACKEND_AUDIT.md:50`. **Gotchas + invariants.**
1. **`review-photos` has zero INSERT policy on `storage.objects` right now** — confirmed live (`select count(*) from pg_policies where schemaname='storage' and tablename='objects'` = 19 rows total, only one of them, `public_read_review_photos`, mentions this bucket, and it's `SELECT`-only). `supabase/migrations/005_reviews_trust.sql:45-47` created an `"Anyone can upload review photos"` INSERT policy, but it does not exist in the live database anymore — it was presumably dropped during a later hardening pass and never replaced. Since `app/api/reviews/[id]/photos/route.ts:63-65` uploads with the **user-session** client (not admin, unlike every sibling route), every real upload attempt gets an RLS violation; the route's error handling (`:67-70`, `if (uploadErr) { console.error(...); continue; }`) swallows it and moves to the next file. The endpoint currently returns `200 { success: true, photos: [] }` for every request — a live silent no-op, the exact failure mode this codebase's rules call out as the #1 risk. Needs either a real ownership-scoped INSERT policy (matching the `salon_owners_upload_*` pattern used for the other buckets) or switching the route to the admin client.
2. **`client-photos` and `formula-photos` are private buckets, but both upload routes call `.getPublicUrl()` and the frontend renders that URL directly.** Live bucket flags confirm both are `public: false`. `app/api/clients/[id]/photos/route.ts:70` and `app/api/dashboard/coiffeur/formula-photo/route.ts:82-86` both call `getPublicUrl()` and persist the result (`client_photos.photo_url`, `client_formulas.before_photo_url`/`after_photo_url`). `components-legacy/dashboard/ClientPhotosTab.tsx:111,122,140` and `components-legacy/dashboard/coiffeur/FormulaBook.tsx:330-333` render those values straight into `<Image src>`. Supabase Storage's `/object/public/...` endpoint checks `buckets.public` before anything else and rejects the request when the bucket is private, independent of RLS. There is no `createSignedUrl` call anywhere in the repo (grepped `app/`, `lib/`, `components-legacy/`) to compensate. The RLS `SELECT` policies that do exist (`salon_owners_read_client_photos`, `salon_owners_read_formula_photos`, both scoped to `storage.foldername(name)[1]` being a salon the caller owns) imply the intended access model is authenticated/signed access, not a public link — this needs a fix (signed URLs, or flip the buckets to public + accept that tradeoff), not just documentation.
3. **`clients/[id]/photos` has no app-layer MIME/size validation**, unlike its 4 sibling upload routes which all check `file.type` against an allowlist and `file.size` against a cap. Line 45-58 of `app/api/clients/[id]/photos/route.ts` checks only that `file` exists and `photo_type` is one of `before/after/progress` — `file.type` is passed straight through as `contentType` with no allowlist. This is currently masked by the fact that the live `client-photos` bucket itself has `file_size_limit: 5242880` and `allowed_mime_types: [jpeg,png,webp]` set at the Storage layer, so an oversized or wrong-MIME upload is rejected by Supabase, not by the app. That is bucket-level luck, not designed defense-in-depth — if the bucket config ever gets reset (e.g. bucket recreated without the allowlist, which is plausible given point 4 below), this route has no fallback.
4. **Most buckets are not tracked in migration files at all.** Only 5 of 14 live buckets appear in `supabase/migrations/*.sql`; the rest (`client-photos`, `formula-photos`, `salon-gallery`, `staff-portfolio-images`, `barber-portfolio-images`, `chat-media`, `gift-card-assets`, `nail-inspo-images`, `nail-portfolio-images`) were created directly against the project (dashboard or MCP `apply_migration` without a matching committed file). `supabase/migrations/004_salon_photos.sql:37-39` even shows the create-bucket statement commented out with "run via Supabase dashboard or API". Per project convention: always verify bucket config (public flag, size limit, MIME allowlist, RLS policies) against the live project, never assume the migrations directory is complete.
5. **Five buckets are orphaned** (zero references anywhere in `app/`, `lib/`, `supabase/functions/`, `scripts/`): `barber-portfolio-images`, `chat-media`, `gift-card-assets`, `nail-inspo-images`. These trace to killed features — chat messaging is fully OFF (memory `project_killed_features`), gift-card purchase/redeem routes were deleted 2026-07-11 (`_design-system/REMOVED.md:59`), nail features are disabled behind a flag. `staff-portfolio-images` is the opposite case: bucket + RLS policies (`public_read_staff_portfolio_images`, `salon_owners_upload_staff_portfolio_images`) were provisioned 2026-07-13 but no route writes to it yet — forward-provisioned, not currently reachable.
6. **`discovery-images` write access is now admin-gated at both layers.** Before `supabase/migrations/20260710210708_audit_fix_discovery_images_write_policies_admin_only.sql`, the live RLS policy named `discovery_admin_delete` only checked `bucket_id`, not role, so any authenticated user could upload or wipe discovery images despite the name implying an admin check. All current app-layer discovery write routes also independently check `profiles.role === 'admin'`, so this is now genuinely defense-in-depth, not the app's only gate.
7. **`service-photos` got a retroactive Storage-layer MIME allowlist** (`supabase/migrations/20260710155420_...sql`) after a finding that the public bucket had none, meaning `file.type` (client-controlled) was passed straight through as the object's `Content-Type`, which could let arbitrary HTML/SVG get hosted on the trusted `*.supabase.co` domain. The app-layer check at `app/api/services/[id]/photos/route.ts:41-43` was added at the same time, with a comment naming the exact risk. Any bucket that serves user-controlled `file.type` as `contentType` on a public bucket without a MIME allowlist (Storage-layer or app-layer) has this same exposure — worth checking `salon-gallery` and `salon-documents`, which only have app-layer checks (`app/api/salons/[slug]/gallery/route.ts:50-56`, `app/api/salon/documents/route.ts:49-50`) and no Storage-layer `allowed_mime_types` set live.
8. **The discovery-staging approve flow's image re-fetch does not use the SSRF guard.** `app/api/admin/discovery/staging/route.ts:81` does `fetch(item.image_url)` directly, where `item.image_url` on a `discovery_staging` row can originate from an admin-supplied value (`app/api/admin/discovery/analyze/route.ts:28-30` takes `image_url` straight from the request body). This is inconsistent with `lib/ai-vision.ts`, which explicitly wraps the equivalent fetch in `assertSafeFetchUrl()` (`:211-220`, `:263-266`) specifically because "image_url is attacker-reachable." Lower severity here because the route requires `profiles.role === 'admin'` first, but it is the one media-adjacent fetch in this system that skips the guard other fetches of the same shape use.
9. **`salon-gallery`'s upload route bypasses RLS entirely and is the only gate.** `app/api/salons/[slug]/gallery/route.ts:6-9` builds its own `createClient(url, SUPABASE_SERVICE_ROLE_KEY)` instead of using `lib/supabase.ts`'s shared helpers, so every Storage call runs with the service role and RLS on `storage.objects` never applies. The only thing preventing a cross-salon gallery write is the app-layer `salon.owner_id !== user.id` check (`:38`) — unlike `client-photos`/`formula-photos`/`salon-documents`/`service-photos`, which all also have a matching `salon_owners_upload_*` RLS policy as a second gate.
10. **The thumb proxy's Storage persist is deliberately `await`ed, not fire-and-forget** (`app/api/discovery/thumb/[id]/route.ts:169-172`), because Netlify/Vercel-style Fluid Compute can freeze background work after the response is sent. Converting this to fire-and-forget "for latency" will silently stop the durable-cache write from ever completing in production, even though the response itself will look fine.

**Where to look when changing it.**
- New upload surface → copy the pattern in `app/api/services/[id]/photos/route.ts` (ownership join + MIME allowlist + size cap + `contentType` passthrough) rather than `app/api/clients/[id]/photos/route.ts` (missing app-layer validation) or `app/api/salons/[slug]/gallery/route.ts` (bespoke service-role client, no RLS backstop).
- Changing bucket public/private status, size limits, or MIME allowlists → do it against the live project (`storage.buckets`) and add a migration file for it; do not assume the existing migrations directory reflects current bucket config.
- Adding/checking RLS on `storage.objects` → query `pg_policies where schemaname='storage' and tablename='objects'` live rather than trusting migration files; several buckets' policies (e.g. `discovery-images`'s admin gate, `client-photos`'s salon-scoped read/write) were created or altered directly, outside any committed migration.
- Discovery thumbnail behavior → `app/api/discovery/thumb/[id]/route.ts`, keep the three-tier order (memory → Storage → oEmbed/TikTok) and the `await` on the persist step.
- Backup/retention behavior → `lib/backup/export.ts` plus `app/api/cron/db-backup/route.ts`; `scripts/db-backup-kill-test.ts` exists for testing the export logic directly without going through the cron route.

## 4. Payments, Stripe Connect & payouts

**What it is.** Solen prepays salons for services through Stripe Connect destination charges: the customer's card is charged the full price (or a deposit, depending on the salon's configured `payment_mode`), the money is routed to the salon's own Stripe Connect account, and Solen keeps a commission as a Stripe `application_fee_amount` on the same charge. A single webhook (`app/api/stripe/webhook/route.ts`) is the only place that advances booking/purchase state on payment success, and two chokepoint files (`lib/bookings/issue-refund.ts`, `lib/purchases/issue-purchase-refund.ts`) are the only code allowed to call `stripe.refunds.create`.

**How it works.**

*Two live payment-creation paths, not one.* `app/api/stripe/create-payment-intent/route.ts` is the older **deposit-hold** model: it creates a `capture_method:"manual"` PaymentIntent (a hold, not a capture) for `salons.deposit_percent`% of the service price when `payment_mode === "deposit"`, else the full price. `app/api/stripe/booking-pay-intent/route.ts` is the newer **full-prepay ("the Fresha model")** path used by the current booking flow: `capture_method:"automatic"` (captured immediately), `setup_future_usage:"off_session"` (saves the card for later off-session charges), keyed off an already-created `bookings` row (`booking_id`), works for both logged-in users and guests (`booking.user_id IS NULL`). Both derive the charge amount **server-side from the `services.price` row**, never from the client (create-payment-intent.ts:46-90 explicitly rejects a client `deposit_amount` that doesn't match the server-derived figure; booking-pay-intent.ts:123-198 derives `priceChf` from `services.price` + `extras_addons` + an optional bundle re-price via `loadPricedBundle`, lib/pricing/bundle.ts).

*booking-pay-intent's full pricing stack, in order (app/api/stripe/booking-pay-intent/route.ts):*
1. Resolve `priceChf` from the service row + extras (+ bundle re-price if `booking.bundle_id` is set, refusing rather than falling back to a full-sum charge on a stale/mismatched bundle, lines 154-178).
2. Apply the salon's `payment_mode` (deposit % or full price, lines 183-198).
3. Re-validate a persisted `promo_code` live against `promo_codes` (active, date window, `min_booking_amount`, salon match, `min_tier`) and reserve one use atomically via the `reserve_promo_use` RPC (lines 219-301). The client-sent discount is never trusted.
4. Resolve/create a Stripe Customer (one per logged-in user, persisted on `profiles.stripe_customer_id`; a fresh one per guest booking, lines 321-356).
5. Compute the platform commission from `platform_settings.commission.rate_percent` (fallback `DEFAULT_COMMISSION_RATE_PERCENT = 15`, lib/constants/billing.ts:9), then apply an optional Solen Plus member commission-waiver (`resolveMemberDiscount` + the atomic `reserve_member_discount` RPC, lines 365-419). Promo discount and member-discount waiver are independent: promo lowers the gross (salon bears it), the member waiver only lowers Solen's `application_fee_amount` (salon payout unchanged).
6. Create the PaymentIntent with a **deterministic idempotency key** keyed on `(booking_id, baseAmountRappen)` — the pre-discount amount, not the post-discount one, specifically so a re-attempt with a since-changed discount replays the same PI instead of forking a second capturable one (lines 467-480).
7. **Credits + voucher spend** (owner-approved 2026-07-11), applied *after* the PI already exists: redeems via `redeem_user_credits` / `redeem_voucher` RPCs against the real Stripe PI id, then **shrinks** the just-created PI with `paymentIntents.update` (legal pre-confirmation, status `requires_payment_method`). A failed shrink restores the just-applied redemption immediately (lines 554-692).
8. Every discount reconciliation reads back from the **actually-returned PaymentIntent**, not the in-memory calculation, because Stripe may have replayed an earlier PI via the idempotency key (lines 506-553).

*Stripe Connect.* `app/api/stripe/connect/create-account/route.ts` creates an Express account (`type:"express"`, country `CH`, `card_payments` + `transfers` capabilities) and returns an onboarding link. `app/api/stripe/connect/status/route.ts` live-retrieves the account and reports `connected` only when **both** `charges_enabled` AND `payouts_enabled` are true. Every charge-creation path sets `application_fee_amount` + `transfer_data.destination` only when `salons.stripe_account_id` is present (a **destination charge**); without it, money would land on the platform account, not the salon's, so booking-pay-intent hard-blocks in production (`NOT_CONNECTED`, lines 104-121) and only falls back to an un-routed platform charge in `NODE_ENV !== "production"` for local testing.

*The webhook (`app/api/stripe/webhook/route.ts`) is the single state-advancing entry point.* Every event is verified (`stripe.webhooks.constructEvent`) then **atomically claimed** by inserting into `processed_webhook_events` (`event_id` PRIMARY KEY, Postgres `23505` = already processed = no-op; route.ts:50-62). On any handler throw the claim row is deleted so Stripe's retry re-runs the event with a clean slate (route.ts:849-857). Events handled:
- `payment_intent.succeeded` — the big one. Dispatches through a chain of early-return guards (`handleVoucherPurchase`, `handleSalonVoucherPaid`, `handlePurchasePaid`, `handleGiftCardPurchase`) before falling into the booking branch. For `type:"booking"` PIs: flips the booking to `status:"confirmed"`/`payment_status:"paid"` **only from a pre-payment state** (`.in("status", ["pending","pending_approval","confirmed"])`, an ADVANCE-ONLY guard against Stripe's non-guaranteed event ordering, line 161), splits `paid_amount` into net/VAT via `computeVat` (lib/vat.ts), completes any pending referral, and CAS-marks `promo_counted_at`. Then, for any PI carrying a `salon_id`, upserts a `salon_payouts` row keyed on `stripe_payment_intent_id` (lines 217-259).
- `payment_intent.payment_failed` — releases the slot and reverses any promo reservation / credit / voucher redemption, again only from a pre-payment state.
- `charge.refunded` — the canonical `salon_payouts` reconciler: recomputes `gross_amount` from the **charge's own** `charge.amount - charge.amount_refunded` (cumulative), never from the already-mutated row, so repeated/partial refund deliveries converge instead of double-subtracting (lines 771-796).
- `charge.dispute.created` / `charge.dispute.closed` — emails `ADMIN_EMAIL`, writes an `audit_log` breadcrumb, and on a **lost** dispute decrements the `salon_payouts` row via a CAS write gated on `lost_dispute_id IS NULL` (see Gotchas).
- `setup_intent.succeeded` — persists a saved card (`payment_status:"card_saved"`) for the deposit-hold flow's later off-session recharge.
- `account.updated` — flips `salons.accepts_online_payment = true` once `charges_enabled` (see Gotchas: does not check `payouts_enabled`).
- `account.application.deauthorized` — flips `accepts_online_payment = false` and emails the admin.
- `payout.paid` / `payout.failed` — notifies the salon owner (email + in-app) via `lib/notifications`.
- `payment_intent.amount_capturable_updated` — a walk-in backstop: issues the walk-in ticket if the customer's own confirm request never landed.
- An **additive** block (lines 330-430, outside the `bookingId` branch's booking-only logic but still inside `if (bookingId)`) writes a `salon_payouts` row for `type:"upcharge"` / `"cancellation_fee"` / `"no_show_fee"` off-session charges too, and for upcharges CAS-advances `booking_disputes.status` from `salon_approved` to `charged` if the synchronous path (dispute-engine.ts's `chargeUpcharge`) lost the race to 3-D Secure.

*Refunds.* `lib/bookings/issue-refund.ts` is the only chokepoint for `stripe.refunds.create` on a booking. It reads `bookings.paid_amount` (integer Rappen — **never** `price_paid`, which is CHF and was a live 100x bug), computes `remaining = paid_amount - refunded_amount`, then **claims the accounting BEFORE calling Stripe** with a compare-and-set (`.eq("refunded_amount", staleRefunded)`, lines 150-171) so two concurrent different-amount refunds can't both reach Stripe. Only after winning the CAS does it call `refunds.create` with a deterministic idempotency key; on a Stripe throw it rolls the CAS back (guarded so a later legitimate refund isn't clobbered) and pages an admin via `alertAdmin`. `salon_payouts` is deliberately **not** touched here — `charge.refunded` is the single canonical reconciler, to avoid double-decrementing. On a **full** refund it also restores any spent credits/vouchers via `restore_user_credits`/`restore_voucher` (never on a partial refund — the redeemed amount still backs the unrefunded remainder). `lib/purchases/issue-purchase-refund.ts` is the sibling for `package_purchases`/`retail_purchases` (same CAS + idempotency-key + Connect-aware mechanics, plus an optional Redis (Upstash) short-lived lock that fails open when Redis isn't configured, and a retail-only stock re-increment on a full refund). `lib/bookings/customer-cancel-money.ts` is the money-outcome wrapper both cancel entry points (`/api/bookings/[id]/cancel`, the HMAC quick-action link) call: if the booking was prepaid, the cancellation fee is **netted out of the refund** (`issueRefund` called for `remaining - fee`); if not prepaid, the fee (if any, inside the free-cancel window) is charged **off-session** against the saved card via `lib/bookings/charge-fee.ts`.

**Gotchas + invariants.**
- **The webhook's generic booking-branch `else` silently overwrites `payment_status` back to `"deposit_held"` for non-booking money events that carry a `booking_id`.** `app/api/stripe/webhook/route.ts:211-215` was written for the original deposit-hold PI (which never sets `metadata.type` at all), but `payment_intent.succeeded` also fires for `type:"pre_charge"` (`app/api/cron/pre-charge/route.ts:78`), `type:"cancellation_fee"`/`"no_show_fee"` (`lib/bookings/charge-fee.ts:231`), and `type:"upcharge"` (`lib/bookings/dispute-engine.ts:344`) — all of which set `metadata.booking_id` but never `metadata.type === "booking"`. Since the `bookingId` gate (route.ts:114-115) fires for all of them and the `else` branch has **no CAS/status guard at all**, a successful cancellation-fee, no-show-fee, upcharge, or pre-charge capture unconditionally resets an already-`"paid"`/`"refunded"`/`"partially_refunded"` booking's `payment_status` back to `"deposit_held"`. In practice this mostly manifests as a wrong reported status plus noisy failed-capture errors in `app/api/cron/release-payments/route.ts` (it re-queries `status:"completed" AND payment_status:"deposit_held"` and calls `paymentIntents.capture()` on an already-captured automatic PI, which Stripe rejects and the cron logs as `failed`) rather than a double-charge, but it is a real state-integrity bug worth fixing before it's relied on anywhere.
- **`account.updated` only checks `charges_enabled`, not `payouts_enabled`, to flip `accepts_online_payment`** (route.ts:761-769). A salon can start accepting customer payments before its bank payout details are actually verified. `app/api/stripe/connect/status/route.ts` and `app/api/salon/go-live/route.ts` both correctly require both flags for their own readiness signal — only the webhook's auto-flip is looser.
- **TWINT is structurally excluded, not just flag-gated.** The `feature_flags` row `twint` exists (`enabled:false`, live-verified 2026-07-14) but nothing in the codebase reads that key (`grep '"twint"'` across `app/` and `lib/` returns zero hits). Both money-charging PI paths that matter (`booking-pay-intent.ts:433`, `walkin/pay-intent/route.ts:131`) set `automatic_payment_methods: { enabled: true, allow_redirects: "never" }`, which excludes TWINT (a redirect method) from the Payment Element regardless of any flag, because a redirect method can't be saved via `setup_future_usage:"off_session"` for later no-show/upcharge recharges. There is also no Karte/TWINT chooser component anywhere in the current tree (`components-legacy/booking/PayConfirmStep.tsx` has zero TWINT references) — the two remaining TWINT mentions in `app/[locale]/checkout/page.tsx:740` and `terms/components/TermsContent.tsx:124` are a decorative trust-badge and a Terms list item, not functional UI. **This contradicts `project_money_features_shipped` memory's claim of a "card|twint PI branch in booking-pay-intent + Karte/TWINT chooser in PayConfirmStep"** — that branch/chooser is not present in the code as of this read; either it was reverted or the memory describes an unmerged/different state. Re-enabling TWINT needs both a Stripe platform-level review (per the flag's own description) and new PI/UI branching code, not just a flag flip.
- **Gift cards are purchase-only; redemption is not built, not just hidden.** `app/api/bookings/route.ts:151-157` explicitly accepts `gift_card_code` in the schema (so the field isn't a 400) then logs a warning and drops it — there is no `redeem_gift_card` RPC anywhere in `supabase/migrations/`, unlike vouchers/credits which have full redeem+restore RPC pairs. The backend (`gift_cards` table, `gift-card-handler.ts`, `/api/gift-cards/balance`) stays intact per owner decision (2026-06-14, "in favour of the Solen-wide loyalty card"), but wiring redemption back in would need new RPCs, not just un-hiding UI. `_plans/PAYMENTS_BACKEND_AUDIT.md` documents an optimistic-lock race in a `gift-cards/redeem` route that no longer exists in the tree (`app/api/gift-cards/` only has `balance/` today) — that finding is moot, the route was removed.
- **`_plans/OPS_RUNBOOK.md:49` is stale.** It says the 4 voucher/credit RPCs are "built + live but wired to NOTHING; user credits can be earned but never spent." As of the code read here (comments dated 2026-07-11, "owner-approved"), they ARE wired: `booking-pay-intent.ts:554-692` calls `redeem_user_credits`/`redeem_voucher`, and `issue-refund.ts:250-291` / `issue-purchase-refund.ts:476-521` call the matching restores on a full refund. Don't trust that runbook line without re-checking the code, per rule 18.
- **Two structurally different "voucher" systems share the word "voucher".** `vouchers` (table) = a salon GIFT voucher bought via `/api/vouchers`, redeemed via the `redeem_voucher` RPC keyed on `(code, salon_id)`. `promo_codes` with `is_purchased_voucher:true` = a **discount code** minted via `/api/vouchers/create` (Stripe Coupon + Promotion Code), redeemed through the ordinary `promo_code` re-validation path in booking-pay-intent, not `redeem_voucher`. The "Gutschein oder Rabattcode" unified checkout input feeds both namespaces into different code paths; don't assume one RPC covers both.
- **`refund_application_fee` is hardcoded to `false` (keep the commission) unless `REFUND_APP_FEE_DEFAULT=true` in env.** `lib/bookings/refund-config.ts:29-40` documents `platform_settings.'refund_policy'` as the intended future source but that table row doesn't exist live yet — this is a real, deliberate business default (D7), not a bug, but it means every refund keeps Solen's commission by default regardless of why the refund happened.
- **Commission VAT is deferred, not automatic.** `DEFAULT_COMMISSION_RATE_PERCENT = 15` (`lib/constants/billing.ts:9`) is a flat platform fee; nothing in the commission math itself applies VAT to Solen's own commission revenue (only the customer-facing `bookings.vat_amount`/`net_amount` split via `computeVat` is implemented). Per `project_commission_vat_deferred` memory this is intentionally deferred until platform revenue exceeds CHF 100k — there is no code-level TODO marker for it, it's a business decision tracked outside the codebase.
- **Idempotency keys are the load-bearing safety net everywhere money moves twice.** `issue-refund.ts`/`issue-purchase-refund.ts` key on `refund:{source}:{id}:{staleRefunded}:{amountCents}`; `booking-pay-intent.ts` keys the PI create on `(booking_id, baseAmountRappen)` (pre-discount, deliberately); `charge-fee.ts` keys on `(source, id, kind, amountCents)`. Never call `stripe.paymentIntents.create` / `refunds.create` outside these chokepoints, or a retry collapses to nothing and a double-charge/double-refund becomes possible.
- **CAS-before-Stripe is the pattern, everywhere.** `issue-refund.ts` claims `refunded_amount` via `.eq("refunded_amount", staleRefunded)` BEFORE calling Stripe, not read-then-write, specifically to close a race where two concurrent different-amount refunds could both reach Stripe. The `charge.dispute.closed` handler uses the identical shape for `lost_dispute_id` (route.ts:658-669) — decrementing `salon_payouts.gross_amount` is only safe on the delivery that wins the `IS NULL` CAS guard; a naive re-decrement on Stripe's webhook retry would silently underpay the salon a second time.
- **Money unit discipline: integer Rappen end-to-end, never `bookings.price_paid` (CHF, numeric) in a refund/fee computation.** Every refund/fee file has an explicit comment warning against this exact 100x bug; it happened live before these chokepoints existed.

**Where to look when changing it.**
- New charge type or amount logic → `app/api/stripe/booking-pay-intent/route.ts` (current model) or `app/api/stripe/create-payment-intent/route.ts` (deposit-hold model); never construct a `stripe.paymentIntents.create` call outside these + `lib/bookings/off-session-charge.ts`.
- New webhook event or a fix to existing event handling → `app/api/stripe/webhook/route.ts` (plus its `*-handler.ts` siblings in the same directory for purchase-type-specific finalization).
- Any refund → `lib/bookings/issue-refund.ts` (bookings) or `lib/purchases/issue-purchase-refund.ts` (packages/retail); never call `stripe.refunds.create` elsewhere.
- Commission rate or VAT behavior → `lib/constants/billing.ts` (fallback), `platform_settings` table (`commission` key, live override), `lib/vat.ts` (the VAT split math).
- Voucher/credit spend rules → `lib/credits/redeem.ts` (the cap math + flag reads) and the RPCs in `supabase/migrations/20260703103322_voucher_redemption_ledger_and_rpcs.sql` / `20260703150856_credit_redemption_ledger_and_rpcs.sql` / `20260703161101_fix_redeem_idempotency.sql`.
- Connect onboarding/readiness → `app/api/stripe/connect/create-account/route.ts`, `app/api/stripe/connect/status/route.ts`, `app/api/salon/go-live/route.ts`.
- salon_payouts ledger drift → `app/api/cron/reconcile/route.ts` (detection) and the `charge.refunded` / `charge.dispute.closed` handlers in the webhook (the actual reconcilers).

## 5. Booking engine & availability

**What it is.** The system that turns a staff member's working hours into bookable inventory (`availability_slots`), lets a customer atomically claim one slot into a `bookings` row, and manages that booking's lifecycle (reschedule, cancel with a full-prepay refund, group/recurring/express-rebook variants, waitlist, and the separate pay-then-queue walk-in flow). Everything runs in Europe/Zurich wall-clock for the salon but stores true UTC instants in Postgres `timestamptz` columns.

**How it works.**

*Supply — nightly slot generation.* `app/api/cron/generate-slots/route.ts` runs daily at 02:00 UTC (`.github/workflows/cron-jobs.yml:96-105`), Bearer-`CRON_SECRET`-gated. For every active salon it reads `staff_schedules` (wall-clock `start_time`/`end_time` per `day_of_week`), skips `salon_closures`, `staff_time_off`, and `salons.vacation_start/end` (route.ts:135), and walks the day in `slotDuration`-minute steps converting each Zurich wall-clock instant to true UTC via `zurichWallClockToUtc` (`lib/time/zurich.ts:10-18`, DST-safe: diffs the same instant rendered in UTC vs `Europe/Zurich`). It inserts **one row per service the staff member is mapped to** (route.ts:184-217) because the booking API resolves slots by `salon_id + service_id + starts_at`, and each row's `ends_at` is derived from that specific service's own `duration_minutes + buffer_minutes` (route.ts:206, fixed from an earlier bug where every service on a staff member shared slot 0's duration — HIGH #7 in the audit). After generation it re-evaluates capacity limiting for nail salons (`nail_stations.station_count`) and barbershops (`barber_chairs.chair_count`) using `classifyOverlapBlocks` (`lib/slots/overlap.ts`, an O(n log n) sweep that replaced an O(n²) all-pairs scan, RING 3b), flipping over-capacity rows to `status='blocked', block_reason='capacity'` and reverting only its own prior capacity blocks first (never touching `block_reason='manual'`/`'vacation'` blocks or booked slots) so the pass is idempotent per run.

*Demand — the CAS slot-claim pattern.* `lib/bookings/claim-slot.ts` is meant to be THE one place the compare-and-swap lives: `UPDATE availability_slots SET status='booked', ... WHERE id=? AND status='available'`, checking `data.length > 0` to know if this caller actually won. Its own doc comment states the hard rule: it **must be called with the service-role (admin) client**, because `availability_slots` has exactly one write RLS policy, `slots_manage_owner` (`supabase/migrations/014_new_schema.sql:212-215`, `FOR ALL USING (salons.owner_id = auth.uid())`), and a logged-in customer's session client is not the salon owner, so its UPDATE silently matches 0 rows under RLS (no error, just an empty result). `app/api/bookings/[id]/reschedule/route.ts:62-66` documents this exact trap and fixes it ("Council 2026-07-07"): it uses the RLS session client for the `bookings` row (`bookings_update_own` policy permits the owner) but the **admin** client for every `availability_slots` write. `app/api/bookings/[id]/quick-action/route.ts` and `app/api/walkin/*` also correctly use the admin client for slot writes.

*Main booking create.* `app/api/bookings/route.ts` `POST` (668 lines) is the canonical create path: rate-limited by user/IP (§10b.12), resolves guest vs logged-in (`isGuest = !user`, `db = isGuest ? admin : supabase` at route.ts:127), resolves the target slot by either an explicit `slot_id` or `salon_id+service_id+starts_at` (route.ts:181-202), runs staff auto-assignment (`lib/bookings/auto-assign.ts`: `least_busy`/`round_robin`/manual, honoring a per-stylist daily cap, always via the **admin** client since it aggregates across all customers), checks `online_booking_enabled`, `vacation_start/end`, and `payment_mode` (deposit/prepay salons reject non-online payment), prices the booking server-side (primary + `extra_service_ids` + optional priced bundle via `lib/pricing/bundle.ts`, which also pre-checks the widened bundle window against booked/blocked slots for the same staff), freezes the salon's cancellation/no-show terms into `booking.policy_snapshot` (the legal basis `chargeFee` requires), runs a duplicate-booking guard keyed on `user_id`/`guest_phone` + `salon_id`+`starts_at` (statuses `pending`/`pending_approval`/`confirmed`), inserts the `bookings` row, then claims the slot inline with the same CAS shape as `claimSlot` (`.update({status:'booked',...}).eq('id',resolvedSlotId).eq('status','available').select('id')`, route.ts:531-536) and rolls back the just-inserted booking on any 0-row match, `23P01` GIST collision, or other write error (route.ts:537-556, fixed post-audit finding #2/#14). **This final slot-claim write still goes through `db`, which for a logged-in customer is the RLS session client**, not the admin client the sibling reschedule/quick-action routes were fixed to use for the identical write. Grounded only in migrations (I could not query live `pg_policies` here — auth-gated MCP), but the reschedule route's own comment proves this exact RLS silent-no-op class is real and unfixed in this file today; verify live before trusting logged-in booking works end to end. A DB backstop exists regardless: `bookings_one_active_per_slot` (`supabase/migrations/20260707155609_...sql`) is a partial UNIQUE index on `bookings(slot_id) WHERE group_booking_id IS NULL AND status IN ('pending','pending_approval','confirmed')`, so even a broken app-level CAS cannot leave two live bookings on one slot; a second INSERT gets a `23505` instead.

*Cancel — full-prepay refund model.* `app/api/bookings/[id]/cancel/route.ts` `POST`: only `status='confirmed'` bookings, only the customer or salon owner. Salon-owner cancel is a full remaining-balance refund via the single chokepoint `lib/bookings/issue-refund.ts` (Stripe idempotency key + CAS on `refunded_amount`). Customer cancel routes through `lib/bookings/customer-cancel-money.ts`'s `applyCustomerCancelMoney` (extracted from an earlier no-refund bug, audit CRITICAL #1): if the booking was prepaid (`paid_amount>0` and `payment_intent_id` set), the cancellation fee is **netted out of the refund** (`refund = remaining − fee`, one Stripe call, never a separate charge on top); if it was pay-at-salon, the fee (if inside the paid window) is charged off-session against the saved card via `chargeFee`. The booking status UPDATE carries a CAS on both `status` and `slot_id` (guards against a concurrent reschedule moving `slot_id` out from under the cancel) using `.maybeSingle()` to distinguish a lost race from a real DB error. The slot free-up at cancel/route.ts:240-243 uses `supabase` (the RLS session client), the same client the admin client is already imported and used elsewhere in this same file for — this is the identical RLS-owner-only trap described above, on the highest-traffic customer-cancel path, and its result is never checked (no rowcount, no error branch), so if it does silently no-op the slot stays `booked` forever with a stale `booking_id` pointing at a cancelled booking. After freeing the slot, up to 3 oldest unnotified `waitlist` rows matching `salon_id+service_id+preferred_date` get an email and are stamped `notified_at` (unconditionally, even if the email never sent — audit HIGH finding).

*Reschedule.* Guarded to `status IN ('confirmed','pending')` only, 24h minimum lead time, and claims the **new** slot before freeing the **old** one (claim-then-free ordering, so there's never a window where the old slot is bookable while the new one isn't secured yet). Both the new-slot claim and the old-slot free use `claimSlot`/admin writes; the booking-row move is CAS'd on the booking's own prior `slot_id`+`status` so a concurrent second reschedule or cancel loses cleanly (409) instead of clobbering.

*Group / recurring / express-rebook / waitlist sub-flows.* `app/api/bookings/group/route.ts` calls the `create_group_booking` RPC (`supabase/migrations/20260709184658_...sql`, `SECURITY DEFINER`, takes a real `FOR UPDATE` row lock per member slot, checks `status='available'`, inserts each member's booking with `user_id=auth.uid()` and flips the slot to `booked`) — this is the one place in the codebase that already does the atomic pattern correctly (the `FOR UPDATE` + status-check the audit's "root-cause theme #1" holds up as the model). `app/api/bookings/recurring/route.ts` and its cron twin (`supabase/functions/recurring-booking-processor/index.ts`) insert the first/each occurrence with `status:'confirmed'` unconditionally and no Stripe flow at all — a real gap on any salon with `payment_mode` `deposit`/`prepay` (audit HIGH), and the slot claim there is a plain unconditional UPDATE with no CAS. `app/api/bookings/express-rebook/confirm/route.ts` has since been hardened past the audit's CRITICAL finding: it now branches `bookingStatus` on the salon's `payment_mode` the same way the main create route does, and its slot claim uses the admin client with the same CAS+rollback shape as the main route. Two parallel waitlist systems exist: the live one is `waitlist` (1 row live per `_inventory/SURFACE.md:690`) via `/api/waitlist`, wired into `WaitlistModal.tsx` and the cancel route's notifier; `booking_waitlist` (0 rows live, `_inventory/SURFACE.md:562`) via `/api/bookings/waitlist` is dead code with no reader anywhere (confirmed by `npm run exists waitlist` per the audit) — do not wire new UI to it.

*Concurrency backstop.* `prevent_double_booking` (`supabase/migrations/20260328_prevent_double_booking_gist.sql`) is a Postgres `EXCLUDE USING gist (staff_member_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE status IN ('booked','blocked')`. This is the hard DB-level guard against two overlapping bookings for the same staff member, but it keys on `staff_member_id`, so it does **not** fire for any pair of slots where `staff_member_id IS NULL` (unstaffed/"any staff" salons) — those rely entirely on the app-level CAS.

*availability_slots hygiene.* The table is dedup-guarded by a unique index `availability_slots_dedup_uniq (salon_id, service_id, staff_member_id, starts_at) NULLS NOT DISTINCT` (`20260703200921_gap_hunt_d3_d5_d8_hardening.sql`), added after a one-time cleanup that deleted 56k exact-duplicate rows the generator had been producing. Live row count today is 9,365 (`_inventory/SURFACE.md:554`). A `purge_past_available_slots(p_days, p_limit)` `SECURITY DEFINER` RPC exists (`supabase/migrations/20260707161019_purge_past_available_slots_lockdown.sql`, `service_role`-only execute, clamps `p_days>=1` so it can never target future rows) to delete old unbooked `available` rows — **but nothing in the codebase calls it**: no route, no script, no cron job in `.github/workflows/cron-jobs.yml` references `purge_past_available_slots`. It is a dormant capability; past-dated `available` slots accumulate indefinitely unless someone runs this manually via the Supabase SQL editor or MCP.

*Zurich timezone handling.* `lib/time/zurich.ts`'s `zurichWallClockToUtc` is the one shared, DST-safe wall-clock→UTC converter (used by the cron). The audit's HIGH finding #8 states several **manual** dashboard slot-create/edit paths (`POST /api/slots`, `/api/slots/bulk`, `PATCH /api/slots/[id]`) instead stored the owner's picked wall-clock time as if it were already UTC (a naive `YYYY-MM-DDTHH:MM:SS` with no `Z`), so a 09:00 CH pick landed on the DB as 09:00 UTC (11:00 CH in summer) — verify these paths' current state before trusting manually-created slots' displayed time.

*Walk-in queue — pay-then-number.* This is a separate flow from the appointment booking above, no `availability_slots` row involved. Free join: `app/api/walkin/queue/route.ts` `POST` inserts via `lib/walkin/join.ts`'s `joinWalkinQueue`, which pre-issues a per-salon daily ticket code (`nextWalkinTicketCode`) and retries the position assignment on a `23505` collision against two partial unique indexes on `barber_walkin_queue`: `(salon_id, position) WHERE status IN ('waiting','in_chair')` and `(salon_id, ticket_code)`. Pay-first shops (`walkin_mode='pay_first'`) block the free-join route (402) and require `POST /api/walkin/pay-intent` (manual-capture Stripe hold, server-trusted price from `services.price`, Connect `transfer_data`/`application_fee_amount` when the salon has `stripe_account_id`, dev-only platform-charge fallback otherwise) → `POST /api/walkin/confirm`, which retrieves the PI (`requires_capture` or `succeeded`), resolves salon/service either from the PI's server-set metadata (tokenless self-serve) or from a linked booking via an HMAC token (salon-SMS payment-link flow, with a cross-tenant `salon_id` metadata check), then calls `lib/barber/walkin-ticket.ts`'s `createWalkinTicket` (shared with the webhook backstop, idempotent). The customer's tracker is `app/[locale]/queue/[token]/page.tsx`, which polls `GET /api/walkin/queue/status?token=` on an adaptive interval (faster near the front, paused when the tab is hidden). Per the audit, `resequence_walkin_queue` (`supabase/migrations/20260531_walkin_resequence_fn.sql`) can no-op whenever a chair is occupied: it only renumbers `status='waiting'` rows to 1..N, but the partial unique index spans `('waiting','in_chair')`, so a departure can try to renumber a waiting row into the in-chair customer's position and hit `23505`, aborting the whole resequence (caught + logged, but positions stay stale) — worth re-verifying live. `GET /api/walkin/queue` is public and unauthenticated and returns each waiting entry's `customer_name` (route.ts:34,66), a PII leak the audit flags as HIGH.

**Gotchas + invariants.**
- **`availability_slots` UPDATE is owner-only under RLS** (`slots_manage_owner`, `salons.owner_id = auth.uid()`). This is grounded in migrations only (I could not query live `pg_policies`); verify live before relying on either path working for a logged-in customer. If it does silently no-op: the create path treats a 0-row match as "someone else took the slot" and rolls back the whole booking (customer sees a false `SLOT_TAKEN` 409); the cancel path never checks the result at all, so the booking cancels successfully but the slot stays `booked` forever, permanently leaking that inventory slot.
- **`purge_past_available_slots` is a dead capability.** It exists, is locked down correctly (service-role only, `p_days` clamped positive), but nothing calls it — not a cron, not a script. Past-dated `available` rows will keep accumulating in `availability_slots` until someone wires it into a cron or runs it manually.
- **Full-prepay refund model.** Bookings paid online capture in full. Any cancel/fee code must net the cancellation fee out of the refund, never issue a second charge on top of a captured prepayment (this was the CRITICAL #1 audit bug, now fixed via `applyCustomerCancelMoney`, but a new cancel/refund code path that bypasses that shared function will reintroduce the same class of bug).
- **`booking.policy_snapshot` is the source of truth for cancellation/no-show terms**, not the salon's live `cancellation_fee_type`/`value`/`free_cancel_hours` columns — a salon can change its fee terms after a customer already booked and consented to different ones; always read the frozen snapshot for money decisions on an existing booking.
- **The GIST `prevent_double_booking` constraint ignores `NULL staff_member_id`.** Salons that book without staff assignment get zero DB-level double-booking protection beyond the app-level CAS and `bookings_one_active_per_slot`.
- **Two parallel waitlist systems exist; only `waitlist` (via `/api/waitlist`) is live.** `booking_waitlist` (via `/api/bookings/waitlist`) has 0 live rows and no reader anywhere — do not wire new UI to it; if it's ever going to be deleted, log it to `_design-system/REMOVED.md` first per the graveyard protocol.
- **Manual dashboard slot-create paths may store the wrong instant.** Only the cron (`generate-slots`) and `lib/time/zurich.ts` are proven DST-safe; the audit found `POST /api/slots`, `/api/slots/bulk`, and `PATCH /api/slots/[id]` storing the owner's picked wall-clock time as if it were UTC. Re-check these before trusting a manually-created slot's displayed time.
- **`scripts/e2e-booking.ts` only ever exercises the guest booking path.** Calling a route handler directly outside a real Next.js request means `cookies()`/session always resolves anonymous, so there is no automated test coverage today for the logged-in-customer create/cancel/reschedule paths — exactly the paths flagged above as carrying the unresolved RLS risk.
- **The daily per-stylist limit has both an app-level pre-check (`auto-assign.ts`) and a DB-level backstop** (`enforce_staff_daily_limit` BEFORE INSERT trigger, advisory-xact-locked per `staff_member_id:day` so concurrent inserts serialize correctly). The trigger fires a `staff_daily_limit_reached` exception that `bookings/route.ts:497` maps to a clean 409; if you add a new booking-insert path, remember the trigger covers you automatically (it's `BEFORE INSERT ON bookings`), but only for `staff_member_id IS NOT NULL` rows with a matching salon `daily_limit_enabled`.
- **The walk-in queue's `resequence_walkin_queue` can silently no-op** whenever a chair is occupied (position collision between a renumbered `waiting` row and the fixed `in_chair` row), inflating the customer-visible queue position after every departure while someone is being served. Live status: re-verify (fix listed in the audit, not confirmed applied).
- **`GET /api/walkin/queue` is public and returns customer names** for everyone currently waiting at a salon, unauthenticated — a live PII exposure per the audit, not confirmed fixed.
- **`pay_at_counter` is the default `walkin_mode`**, and per the audit all 5 live walk-in salons use it — meaning the "pay gates the number" invariant this system was designed around (§ task scope: "pay upfront → number → show up") is enforced on zero live salons today; free-join issues a real queue number with no payment anywhere in that path.

## 6. Background jobs & crons

**What it is.** Solen's scheduled work (payment lifecycle, reminders, retention emails, GDPR erasure, nightly backup, search/loyalty recomputes) runs as 26 Next.js route handlers under `app/api/cron/*`, pinged on a schedule by a GitHub Actions workflow with a shared-secret bearer token. A separate, much smaller layer of 3 native Postgres `pg_cron` jobs handles pure-SQL maintenance (materialized view refresh, PII retention, dead-row purge) inside Supabase itself. A third layer, 7 Supabase Edge Functions, is dead: their source was deleted from the repo 2026-07-11 and the deployed artifacts were neutered to 410 stubs, but nothing has actually called `supabase functions delete` yet.

**How it works.**
1. `.github/workflows/cron-jobs.yml` fires on 14 distinct `on.schedule` cron expressions (all UTC). Each `jobs.<name>` block has an `if: github.event.schedule == '<expr>'` guard so only the matching job body runs on a given trigger (`.github/workflows/cron-jobs.yml:9-23` for the schedule list, `:26-49` for the first job). Every job step calls the reusable composite action `.github/actions/ping-cron/action.yml`, passing a comma-separated list of `/api/cron/*` paths plus `secrets.CRON_SECRET`.
2. `ping-cron` (`.github/actions/ping-cron/action.yml:24-63`) sends `Authorization: Bearer $CRON_SECRET` to each path, defaults to GET (a few jobs pass `method: POST`), and **hard-asserts** the JSON body has `"ok":true` (via `jq -e '.ok == true'`, falling back to a regex if `jq` is unavailable). Any non-2xx status OR a missing/false `ok` field increments a failure counter; if any endpoint fails, the composite action `exit 1`s, which turns that GitHub Actions run red. A red run is what GitHub's own default notification (email to repo watchers, i.e. the owner) surfaces on. There is no separate alerting service, the "alert" IS a failing CI run.
3. The `every-15-min` job also piggybacks a live-site health check (`curl https://solen.ch/api/health`, 2 retries) so the same cadence covers uptime, "costs zero extra Actions minutes" per the inline comment (`.github/workflows/cron-jobs.yml:33-42`).
4. Every route handler does its own auth check before touching anything: `const cronSecret = getServerEnv().CRON_SECRET; if (!cronSecret) return 503; if (req.headers.get("authorization") !== \`Bearer ${cronSecret}\`) return 401;` (this exact 4-line shape is repeated verbatim in all 26 route files, e.g. `app/api/cron/auto-complete/route.ts:10-15`). `CRON_SECRET` is validated as `.min(16 chars).optional()` in `lib/env.ts:65`, and is one of the vars whose absence is called out explicitly in `lib/env.ts:212-218` ("every transactional email silently no-ops... without CRON_SECRET, cron routes are [unreachable]"). This is a plain `!==` string compare, not a constant-time comparison, same as every other bearer check in this codebase.
5. Past the auth gate, the handler body is wrapped in `withCronRun(name, handler)` (`lib/cron-run.ts:38-92`). This times the call, catches any thrown error, and **best-effort** inserts one row into `cron_runs` (`{ name, ok, processed, duration_ms, errors }`, service-role client, RLS enabled with zero policies so only service-role can touch it) via `supabase/migrations/20260711082619_backend_loop_cron_runs_log.sql`. It NEVER throws itself and never blocks the HTTP response on the insert failing (only `console.error`s). It shapes the final JSON body's `ok` flag as `!threw && result.ok !== false && errors.length === 0`, where `errors` is the union of any thrown error's message and whatever the handler itself put in `result.errors` **as an array** (a plain number in `errors` is accepted for backward compat but does NOT flip `ok` to false, see `lib/cron-run.ts:23-27`).
6. A thrown exception also calls `reportError("cron:<name>", err)` (`lib/cron-run.ts:65`), which `console.error`s AND fires `alertAdmin` (`lib/alert-admin.ts`), a one-shot email to `ADMIN_EMAIL` via `sendEmail`/Resend, throttled to one email per `scope` per 15 minutes via an **in-memory `Map`** (`lib/error-report.ts:26,38-44`, only correct for a single running instance).
7. Separately from the per-failure alert, `/api/cron/daily-digest` (`app/api/cron/daily-digest/route.ts`, scheduled 05:15 UTC, after the 02:00-04:00 UTC batch of daily crons has had time to run) reads `cron_runs` directly: `SELECT name, ran_at, errors FROM cron_runs WHERE ok=false AND ran_at >= now()-24h` (`:94-101`) and folds that into one summary email to `ADMIN_EMAIL` alongside yesterday's booking counts and the pending-reviews backlog. Each of its 4 sections is independently try/caught, a query failure omits that section rather than rendering a fabricated 0 (`:60-135`).
8. `/api/cron/reconcile` is the dedicated Stripe↔DB money safety net (daily, `app/api/cron/reconcile/route.ts`). It is read-only (SELECT + compare, never auto-fixes), pulls the last 48h of Stripe charges/refunds, and diffs them against `bookings`/`retail_purchases`/`package_purchases`/`gift_cards`. Found mismatches are emailed straight to `ADMIN_EMAIL` in their **own** dedicated email (`:397-421`), completely separate from both `cron_runs` and the daily digest, because `mismatches` is never copied into the `errors` field of the returned result (`:424-430`), so `cron_runs.ok` stays `true` even on a night with real drift; only a thrown exception (e.g. the Stripe API call itself failing) would turn this cron red.
9. Idempotency is handled per-cron, not by the wrapper: state-machine crons (`auto-complete`, `pending-timeout`, `no-show`) gate on a status column plus, for `no-show`, an explicit `fee_charge_status IS NULL` filter so a re-run never re-targets an already-handled booking. `abandon-sweep` re-checks the live Stripe PaymentIntent status before cancelling and re-asserts `.eq("status","pending").eq("payment_status","none")` in the UPDATE's WHERE clause so a webhook that confirmed the booking mid-sweep can't be clobbered (`app/api/cron/abandon-sweep/route.ts:71-138`). `pre-charge` uses a deterministic Stripe idempotency key `pre-charge:<bookingId>:<amountRappen>` so an overlapping retry collapses to one charge (`app/api/cron/pre-charge/route.ts:77`). Email-drip crons (`welcome-series`, `salon-onboarding`, `birthday-messages`, `rebooking-nudge`) dedupe by querying the `notifications` table for an existing row of that `type` for the target user before sending, then insert a new row after (e.g. `app/api/cron/rebooking-nudge/route.ts:63,135`).
10. Bounded batches: almost every cron caps its query with `.limit(50)` (or `PER_RUN=10` for the AI-vision one) so a large backlog spreads itself across multiple runs instead of timing out one run. Per-item error arrays are capped at 20 with a `capErrors()` helper duplicated in ~10 route files (`...and N more` suffix) so a bad batch can't bloat the `cron_runs.errors` jsonb column.
11. Three `pg_cron` jobs run entirely inside Postgres, scheduled via SQL migrations, invisible to `cron_runs`/GitHub Actions/the daily digest: `search-popularity-refresh` (`0 3 * * *`, refreshes the `search_popularity` materialized view), `search-events-retention` (`30 3 * * *`, nulls `query`/`session_id`/`user_id` on `search_events` rows older than 90 days for nFADP/GDPR compliance), both from `supabase/migrations/20260606204021_search_phase6_learning_loop.sql:67-70`; and `purge-past-available-slots` (`15 4 * * 0`, weekly, calls `purge_past_available_slots(7, 100000)`) from `supabase/migrations/20260711161352_backend_loop_schedule_slot_purge.sql`. Their only observability is Supabase's own `cron.job_run_details` table, not anything covered above.
12. Supabase Edge Functions: 7 directories exist under `supabase/functions/` (`booking-reminder`, `compute-analytics`, `post-booking-preferences`, `recurring-booking-processor`, `salon-verification`, `slot-auto-release`, `smart-nudges`) but every one is **empty** (`index.ts` deleted in commit `71d1c2522`, "ring4c dead-code" sweep, 2026-07-11). Before that, a security sweep found 6 of the 7 (all but `smart-nudges`) were live-deployed on Supabase with no committed `supabase/config.toml`, meaning `verify_jwt` sat at Supabase's default of `true`, satisfied by the public anon key, and none of them had any in-code request-authorization check, i.e. anyone holding the anon key could invoke privileged service-role logic (fire reminder emails, release slots, drive the recurring-booking processor) on demand. They were neutered to inert 410 stubs via `deploy_edge_function` on 2026-07-10 (`_plans/BACKEND_SWEEP_2026-07-10.md`, "Reserve-at-checkout refactor" section) rather than deleted, because the available MCP tooling had no deletion call. `_plans/OPS_RUNBOOK.md:50` still lists "6 dead functions still deployed on Supabase... delete via `supabase functions delete <name>` when convenient" as an open owner action.

**Gotchas + invariants.**
- **`errors[]` is opt-in, and most money-adjacent crons don't populate it.** `withCronRun` only flips `cron_runs.ok` to `false` (and thus fails the GH Actions run + shows up in the daily digest) when the handler throws, or when the handler's returned `result.errors` is a non-empty **array**. Several crons track per-item failures under a *different* field name that never gets copied into `errors`: `no-show` returns `{ processed, charged }` with no errors field at all (`app/api/cron/no-show/route.ts:137`), `release-payments` returns `{ released, failed, processed }` (`app/api/cron/release-payments/route.ts:63`), `pre-charge` returns `{ charged, declined, processed }` (`app/api/cron/pre-charge/route.ts:123`), `discovery-ai-backfill` returns `{ analyzed, failed, ... }` (`:74`), `generate-slots` swallows every per-salon try/catch into a bare `console.error` with no failure counter surfaced at all (`app/api/cron/generate-slots/route.ts:295-297,355-357`), `process-deletions` returns a per-user `results[]` with `success:false` entries that never reach `errors` (`app/api/cron/process-deletions/route.ts:126-136,156`), and `reconcile`'s entire `mismatches[]` array is never copied into `errors` either (`:424-430`, it has its own separate email instead). Concretely: a night where Stripe declines or errors on every single no-show/pre-charge/release-payments attempt still reports `cron_runs.ok:true`, the GitHub Action stays green, and the daily digest's "cron failures" section shows 0, because nothing threw. The only visibility into that failure mode is grepping Netlify function logs for the per-item `console.error` lines. If you touch any of these routes, decide deliberately whether a batch of item-level failures should flip `ok:false` and wire it into `errors[]` if so, don't assume `withCronRun` catches it for you.
- **`late-cancel` is intentionally retired to a no-op but is still pinged every 30 minutes.** `app/api/cron/late-cancel/route.ts` is a 200 stub (`return withCronRun("late-cancel", async () => ({ processed: 0, retired: true }))`) kept alive only so the GH Actions ping doesn't 404. The real late-cancellation fee logic moved to the on-cancel hook inside `app/api/bookings/[id]/cancel/route.ts`. Re-implementing logic in this file would risk a double-charge race against that hook (the file's own comment says the `fee_charge_status` CAS in `chargeFee` is the backstop even if both ever ran).
- **`app/api/cron/reminders/route.ts` is a dead, deprecated stub, not the SMS reminder cron.** It was superseded by `sms-reminders` on 2026-06-03 (it used to double-mark bookings sent under a too-wide time window, silently starving the real sender's narrower window) and removed from `cron-jobs.yml`, but the folder still exists returning a 410. A grep for "reminder cron" will surface this file first; the live one is `app/api/cron/sms-reminders/route.ts`.
- **Dead source is not the same as a dead endpoint.** The 7 `supabase/functions/*` directories are empty (source deleted 2026-07-11), but 6 of them were still deployed and callable on Supabase's live infrastructure as of the 2026-07-10 sweep, with default `verify_jwt=true` (any anon-key holder) and zero in-code auth. They've since been neutered to 410 stubs, but the underlying deployed function was never actually deleted (`supabase functions delete` needs an owner/MCP action not yet taken, per `_plans/OPS_RUNBOOK.md:50`). Don't assume "no `index.ts` in the repo" means "no live surface."
- **`nail-infill-reminders` and `barber-smart-reminders` don't check their feature flags.** `lib/feature-flags.ts` defines `nail_features`/`barber_features` and ~35 other routes gate on them, but neither of these two cron routes references `feature_flags` at all (confirmed by grep across the codebase). They act on every booking matching their category (`services.category = 'nails'` / `salons.categories @> ['barbershop']`) regardless of whether that salon has the corresponding feature toggled on.
- **`cron_runs` has no purge scheduled yet.** `_plans/OPS_RUNBOOK.md:31` flags it growing ~30 rows/day with a "FOLLOW-UP: add a 90-day purge clause" that has not been wired into any of the 3 pg_cron jobs or a 4th cron route as of this writing.
- **The 15-minute alert throttle is per-process, not global.** `lib/error-report.ts`'s `lastAlertAt` is an in-memory `Map`; if Netlify spins up more than one function instance under load, each instance keeps its own throttle window, so the admin can receive more than one alert email per scope per 15 minutes across instances.
- **Runtime is mixed and matters if you add a Stripe call.** Most cron routes are `runtime="nodejs"` (needed for the Stripe SDK / admin Supabase client), but `rebooking-nudge`, `release-deposits`, `salon-onboarding`, `welcome-series`, and the dead `reminders` stub run `runtime="edge"`. All the edge-runtime crons currently only touch Supabase + email, never Stripe directly; adding a Stripe call to one of them needs an edge-compatibility check first.
- **`/api/admin/solen-score/recalculate` is cron-triggered via `CRON_SECRET` too**, even though it lives outside `app/api/cron/`. It's pinged (POST) in the same `daily-03-utc` job as `process-deletions`/`reconcile`/`style-affinity-recompute`, and its own auth check accepts either the `CRON_SECRET` bearer or an authenticated admin session (`app/api/admin/solen-score/recalculate/route.ts:10,14`). A search scoped to `app/api/cron/*` alone will miss this one.
- **`db-backup` retention is conditional on a clean export.** `pruneOldBackups()` only runs `if (exportResult.errors.length === 0)` (`app/api/cron/db-backup/route.ts:36-39`), so a partially failed night never deletes an older complete backup out from under itself, but it also means a chronically-failing single table silently prevents ALL retention pruning indefinitely until that table's export succeeds.

**Where to look when changing it.**
- Add/change a cron's schedule: `.github/workflows/cron-jobs.yml` (add a new `on.schedule` cron expression + a guarded `jobs.*` block, or add a path to an existing job's `paths:` list if the cadence already exists).
- Add a new cron endpoint: copy the auth-guard + `withCronRun(name, ...)` shape from a simple existing route (`app/api/cron/loyalty-recompute/route.ts` is the shortest clean example), remember to actually wire failures into `errors: capErrors(errorMsgs)` if per-item failures should be visible.
- Change what counts as a cron failure / what the owner gets alerted on: `lib/cron-run.ts` (the `ok` derivation) and `app/api/cron/daily-digest/route.ts` (what the daily summary reads).
- Change backup scope/retention: `lib/backup/export.ts` (`BACKUP_TABLES`, `RETENTION_DAYS`), test with `scripts/db-backup-kill-test.ts` before trusting a change.
- Change the money reconciliation logic: `app/api/cron/reconcile/route.ts`, re-read its own "UNIT CONTRACT" comment block (`:20-58`) before touching amount comparisons, Rappen vs CHF units are load-bearing here.
- Decide the fate of the dead Edge Functions: `_plans/OPS_RUNBOOK.md` open decision #5, actually run `supabase functions delete <name>` for the 6 still-deployed-but-neutered ones (owner-gated, destructive infra op).

## 7. Notifications (email, SMS, edge)

**What it is.** All outbound customer/salon messaging: transactional email via Resend (`lib/email.ts`), transactional SMS via seven.io (`lib/sms.ts`), an in-app `notifications` table feed, and a set of `/api/cron/*` routes that batch-send reminders, drip sequences, and a founder ops digest. A previously-planned Supabase Edge Function (`booking-reminder`) that would have sent 24h-before email reminders was deleted from the repo entirely; that job does not exist anymore in any form.

**How it works.**

*Transactional send primitives.*
- `sendEmail()` (`lib/email.ts:28-53`) POSTs to `https://api.resend.com/emails` from `noreply@solen.ch`, using `RESEND_API_KEY`. If the key is unset or still the placeholder `PASTE_RESEND_KEY_HERE`, it logs a warning and silently returns (`:30-33`), never throwing. `lib/email.ts` then defines ~35 template-builder functions (`bookingConfirmation`, `bookingCancellation`, `bookingReminder`, `recurringConfirmation`, `recurringFailed`, `salonNewBooking`, `salonVerificationRequest/Warning`, `salonFrozen`, `customerBookingSuspended`, `salonApproved/Rejected`, `adminNewSalonNotification`, `salonOutreachInvitation`, `newMessageNotification`, `rebookingNudge`, `reviewPrompt`, `welcomeEmail`, `walkInPaymentEmail`, `tipPromptEmail`, `birthdayEmail`, `giftCardDeliveryEmail`, `nailInfillReminderEmail`, `nailAllergyAlertEmail`, `barberSmartReminderEmail`, `barberLoyaltyRewardEmail`, `tosUpdateNotification`, plus two SMS-text builders `barberQueuePositionSMS`/`barberYoureNextSMS`), each returning `{ to, subject, html }` in de/en/fr/it.
- `sendSMS()` (`lib/sms.ts:18-80`) POSTs to `https://gateway.seven.io/api/sms`. It hard-requires the number to start with `+41` (`:29-32`, Swiss-only) and rate-limits to **3 SMS per phone number per 24h** via Upstash Redis (`sms:daily:<phone>` INCR + 24h EXPIRE, `:35-51`); if Redis is down it logs and lets the send through rather than blocking. If `SEVEN_IO_API_KEY` is unset it warns and returns `false` (`:23-26`).
- `lib/notifications.ts:sendNotification()` does two things per call: inserts a row into the `notifications` table (`user_id, type, title, body, data`) for the in-app bell, then, if `emailParams` is passed, switches on `NotificationType` to pick one of the `lib/email-templates/audit-notifications.ts` builders (`bookingPendingApprovalEmail`, `bookingApprovedEmail`, `bookingRejectedEmail`, `bookingModifiedEmail`, `noShowChargeEmail`, `lateCancellationFeeEmail`, `refundProcessedEmail`, `upchargeChargedEmail`, `newReviewEmail`, `reviewResponseEmail`, `reviewFlaggedEmail`, `accountWarningEmail`, `accountSuspensionEmail`, `payoutCompletedEmail`, `payoutFailedEmail`, `termsChangedEmail`, `salonStrikeEmail`, `salonRejected`) and calls `sendEmail`. Both steps are individually try/caught: a DB insert failure or an email failure only `console.error`s, it never throws back to the caller. Called from `app/api/stripe/webhook/route.ts` (`booking_confirmed` at `:316`, `payout_completed`/`payout_failed` at `:808`/`:834`), `voucher-handler.ts`, `bookings/[id]/cancel`, `bookings/[id]/confirm`, `admin/salons/[id]/reject`, `profile/notifications`, and `app/api/cron/review-prompt/route.ts` (`review_prompt` type).

*Internal notify routes (`app/api/notify/*`).* Both `review-posted/route.ts` and `review-replied/route.ts` are server-to-server only: they check `x-internal-secret === CRON_SECRET` (`review-posted/route.ts:22-25`, `review-replied/route.ts:23-26`) and 401 otherwise. `review-posted` is invoked by `app/api/reviews/route.ts:113-117` right after a customer submits a review, looks up the salon owner's email via `salons(owner_id) → profiles(email)`, and sends a "new review" email. `review-replied` is invoked by `app/api/reviews/[id]/respond/route.ts:73` after a salon owner replies to a review, looks up the review author's email, and sends the reply. Both now HTML-escape the user-supplied text (`escapeHtml` at the top of each file) before interpolating it into the email body.

*`app/api/notifications/route.ts`* is the dashboard bell endpoint (session-authed, not internal-only). `GET` assembles a synthetic feed by querying three live tables directly (not the `notifications` table): recent `bookings` with `status = cancelled_by_customer` (`:33-40`), `reviews` with `salon_response IS NULL` (`:55-62`), and `barber_walkin_queue` rows waiting > 30 min (`:80-87`), sorts them client-side, and returns the top 15. `PATCH` (mark-all-read) is a documented no-op that just returns `{ success: true }` (`:110-120`) — it does not write anything.

*Cron-driven sends, actual live schedule (`.github/workflows/cron-jobs.yml`):*
- **`/api/cron/sms-reminders`** (every 30 min, `sms-reminders,late-cancel,no-show` batch): the real SMS reminder sender. Queries `bookings` where `status='confirmed' AND sms_sent_24h=false` in a 23.5-24.5h `starts_at` window, and separately `sms_sent_1h=false` in a 0.5-1.5h window, honoring the per-salon `salons.sms_reminder_24h` / `sms_reminder_1h` toggles before sending. Marks `sms_sent_24h`/`sms_sent_1h = true` on the booking whether the send succeeded or failed (deliberate, "avoid retry loops when phone is invalid", `:87-94`), so a failed send is a permanent skip, not a retry.
- **`/api/cron/reminders`** (not scheduled at all anymore) is a **410 deprecated no-op**. Its own doc comment (`route.ts:6-17`) explains why: its original 24h-before window overlapped the real sender's tighter window and raced it, so it claimed and stamped bookings before the real sender could reach them, silently suppressing SMS reminders. It is kept only as a harmless stub for any stale scheduler still pointed at it.
- **`/api/cron/review-prompt`** (hourly): for bookings `completed` 23-25h ago with `review_prompt_sent=false`, sends either a "leave a Google review" email (if the customer already left 4-5 stars on Solen and the salon has `google_place_id`) or a "review on Solen" email, batches an optional tip-prompt email (only if the salon has `stripe_account_id` and a named stylist), and creates an in-app `review_prompt` notification. Marks `review_prompt_sent=true` in one batched update after send.
- **`/api/cron/welcome-series`** (daily 10:00 UTC): for `profiles` created exactly 0/3/7 days ago with `role='customer'`, sends `welcomeDay0/3/7` (`lib/email-templates/welcome-series.ts`), gated on `notification_preferences.deals_enabled !== false`. Send-once guard: queries `notifications` for an existing row of `type = welcome_series_day{N}` for that user before sending, then inserts one after (`route.ts:62-67, 76-79, 121-124`).
- **`/api/cron/rebooking-nudge`** (daily 11:00 UTC): users whose most recent `completed` booking was 28+ days ago get `rebookingNudge`. Gated on `notification_preferences.rebooking_enabled` and a send-once guard against `notifications` (`type='rebooking_nudge'`) within the same 28-day window.
- **`/api/cron/barber-smart-reminders`** (daily 08:00 UTC): for barbershop salons, computes a per-customer visit cycle (`lib/barber/visit-cycle-algorithm.ts`) from `barber_cut_history`, and where overdue, both writes a `client_notes` row AND sends an SMS via `sendSMS` (the one live non-reminder-cron SMS use besides `sms-reminders`).
- **`/api/cron/nail-infill-reminders`** (daily 10:00 UTC): finds `completed` bookings in the `nails` service category whose `reminder_cycle_days` puts them due within 2 days, and writes a `client_notes` row (dashboard-facing) for the salon. It does **not** email or SMS the customer directly.
- **`/api/cron/birthday-messages`** (daily 09:00 UTC) and **`/api/cron/salon-onboarding`** (daily 09:00 UTC, 5-email adaptive drip via `lib/email-templates/salon-onboarding.ts`) follow the same shape.
- **`/api/cron/daily-digest`** (daily 05:15 UTC, after the 03:00-04:00 UTC batch): the founder ops email. Composes yesterday's Europe/Zurich day (bookings created, bookings completed, `cron_runs` failures in the last 24h, pending-review backlog) into one email to `ADMIN_EMAIL`. Each of the 4 sections is queried independently; a query failure omits that section rather than rendering a fabricated 0 (`route.ts:60-135` comment at `:29`).

All of the above crons are wrapped in `withCronRun()` (`lib/cron-run.ts`), which times the handler, best-effort-inserts one row into `cron_runs` (`name, ok, processed, duration_ms, errors`), and shapes the JSON response to `{ ok, processed, errors }`. GitHub Actions' `.github/actions/ping-cron` composite action then hard-asserts `ok:true` on the response body (not just HTTP 2xx), so a cron that silently no-ops without throwing still surfaces as a red check.

*The dead `booking-reminder` edge function.* `supabase/functions/booking-reminder/index.ts` was a Deno edge function meant to run daily at 09:00, select `bookings` where `status='confirmed' AND reminder_sent=false` in a 23-25h window, send a 24h-before email per booking, and set `reminder_sent=true`. Its source was **deleted from the repo** in commit `71d1c2522` (2026-07-11, "ring4c dead-code" sweep) alongside 6 other unused edge functions (`compute-analytics`, `post-booking-preferences`, `recurring-booking-processor`, `salon-verification`, `slot-auto-release`, `smart-nudges`). Per `_design-system/REMOVED.md:65`, the deployed artifacts were already neutered to inert 410 stubs in an earlier sweep (ring 3, 2026-07-10); removing the actually-deployed Supabase function stays an owner-memo, no `supabase functions delete` was run. **No live code path calls it.** The `bookingReminder` email template in `lib/email.ts:150-168` that this function used to call is also dead: zero callers anywhere in the app besides its own definition.

**Gotchas + invariants.**
- **There is currently no automated 24h-before EMAIL reminder.** The only "reminder" template not dead is `bookingReminder` in `lib/email.ts:150` and it is never called. The only live 24h/1h reminder channel is SMS via `/api/cron/sms-reminders`, gated per-salon by `sms_reminder_24h`/`sms_reminder_1h`. Don't assume booking confirmation implies a later reminder email goes out, it doesn't.
- **Several email/SMS template functions are dead code**: `bookingReminder`, `walkInPaymentEmail`, `barberQueuePositionSMS`, `barberYoureNextSMS`, `newMessageNotification`, `salonCancelledBooking`, `customerCancelledNotification` all exist in `lib/email.ts` / `lib/email-templates/booking-notifications.ts` but have zero callers anywhere in `app/`. If you're asked to "add a queue-position SMS" or "wire the walk-in payment email", check first whether the template already exists unwired before writing a new one (`npm run exists`).
- **Walk-in queue has no live SMS at all**, despite a comment referencing a "salon-SMS booking link" (`app/api/bookings/walk-in-verify/route.ts:12,34`). `app/api/walkin/queue/[id]/route.ts:178` states directly: "SMS is a logged future epic. Never blocks the capture." The HMAC-token payment-link flow (`walk-in-verify`, `walkin/pay-intent`, `walkin/confirm`) is real and live, but nothing in that flow calls `sendSMS`.
- **`booking-reminder` (Supabase Edge Function) does not exist as deployable code anymore.** If a future task references it (a stale doc, a memory, a plan), treat that as a graveyard hit, not something to extend, per `_design-system/REMOVED.md:65`. Its historical send-once guard was also a known non-atomic read-then-write bug (`_plans/CROSSCUTTING_BACKEND_AUDIT.md` finding #5): two concurrent invocations could both read `reminder_sent=false` and both send, duplicating reminders. That finding is now moot only because the function itself is gone, not because the pattern was fixed; the live crons (`sms-reminders`, `welcome-series`, `rebooking-nudge`, `review-prompt`) use the same non-atomic select-then-update-after-send shape, so the same race is theoretically possible if two cron invocations ever overlapped. In practice the 30-min-to-daily cadence and single GH Actions runner make overlap unlikely, but it is not lock-protected.
- **The `/api/notify/review-posted` and `/api/notify/review-replied` open-relay + HTML-injection bug is FIXED**, not theoretical. Before commit `0af9a2930` (2026-07-09 audit, fixed same day per `_plans/BACKEND_FIX_TRACKER.md:6`), both routes had no auth at all: any caller could POST an arbitrary `review_id` to email-bomb a salon owner's inbox (`review-posted`), and `review-replied` additionally interpolated attacker-controlled `reply_text` UNESCAPED into an email sent from Solen's trusted sender to the review author, a phishing vector. Both now require `x-internal-secret === CRON_SECRET` and HTML-escape user text. If you ever see a `/api/notify/*` route without a `CRON_SECRET`/`x-internal-secret` check, that is a regression of this exact bug, treat it as CRITICAL.
- **Supabase Edge Functions in general have no in-code request-auth gate** (`_plans/CROSSCUTTING_BACKEND_AUDIT.md` finding #3): none of the 7 functions (dead or not) check `req.headers` for any shared secret, and there is no `supabase/config.toml` setting `verify_jwt`, so the default (`true`) means the public anon key is sufficient to invoke any deployed one. This was flagged but the fix (add a shared-secret header check per function, or pin `verify_jwt`) was not applied as part of the source-deletion sweep, since the deletion only removed the repo source, not the live deployed artifacts (which were separately neutered to 410 stubs in an earlier ring). Don't assume "we deleted the source" means "the deployed function is gone" for the 6 still-alive-elsewhere functions if any get redeployed later.
- **SMS rate limiting is per-phone via Redis (3/day), and fails open.** `lib/sms.ts:47-50`: if the Upstash Redis call throws, the code logs and lets the send through rather than blocking. This is deliberate (don't let an infra outage silently kill all reminders) but means the 3/day cap is not a hard guarantee during a Redis outage.
- **Marking a booking `sms_sent_24h=true`/`sms_sent_1h=true` happens even when `sendSMS` returns `false`** (invalid phone, provider error), specifically to avoid an infinite retry loop on a permanently-bad number (`app/api/cron/sms-reminders/route.ts:87-94, 132-136`). This means a transient seven.io outage during one 30-min tick permanently skips that booking's reminder for that window, it will not be retried on the next tick.
- **`PATCH /api/notifications` (mark-all-read) does nothing.** It returns `{ success: true }` unconditionally without touching any row (`route.ts:110-120`, explicit "no-op for now" comment). The dashboard bell's "unread" state is not actually persisted anywhere; `GET` always recomputes `unread_count` from scratch off live cancellations/reviews/walk-in-queue queries, there is no `read` flag being set.
- **`notification_preferences` only has two opt-out columns** (`deals_enabled`, `rebooking_enabled`). Welcome-series and rebooking-nudge check these; review-prompt, birthday-messages, nail-infill, and the SMS reminders do not check any user-level preference at all (only the salon-level `sms_reminder_24h`/`sms_reminder_1h` toggles for SMS). If a task requires a new opt-out category, this table needs a new column, don't assume one exists.

**Where to look when changing it.**
- New transactional email/type: add a template function to `lib/email.ts` or the relevant `lib/email-templates/*.ts` file, then either call `sendEmail()` directly from the triggering route, or add a case to the `NotificationType` union + switch in `lib/notifications.ts` if it should also produce an in-app bell entry.
- New scheduled send: add a route under `app/api/cron/<name>/route.ts` following the existing shape (CRON_SECRET check outside `withCronRun`, business logic inside, use `runWithConcurrency` for any batch of sends), then add it to `.github/workflows/cron-jobs.yml`'s existing schedule buckets (reuse a bucket, don't add a new `cron:` entry unless the timing genuinely differs) and to the matching `ping-cron` `paths:` list.
- SMS behavior/limits: `lib/sms.ts` (validation, Redis rate limit, seven.io call).
- Internal-only relay pattern (server-to-server, not session-authed): `app/api/notify/review-posted/route.ts` is the canonical example of the `x-internal-secret === CRON_SECRET` gate, copy this pattern for any new internal-only notify endpoint rather than leaving it public.
- Cron observability: `lib/cron-run.ts` (the `cron_runs` contract) and `.github/actions/ping-cron/action.yml` (the hard `ok:true` assertion) together define what "the cron actually ran" means; changing one without the other breaks the guarantee.

## 8. Search & discovery

**What it is.** Two coupled systems that both search the same underlying content: (1) salon/service search (`/api/salons`, `/api/salons/search`, `/api/search/*`) that blends full-text, trigram-fuzzy, exact-match, pgvector semantic, Bayesian rating, click-popularity and a per-user "DNA" affinity term into one ranking RPC, plus a large AND-combining structured-filter engine (city, price, gender, amenities, date/time availability, distance); and (2) the "Inspo" discovery feed (`/api/discovery/feed` and friends), a TikTok-style content grid with its own category taxonomy, progressive tag drill-down, and a separate DNA-scored for-you ranking. The two systems share the same embeddings table and the same user-affinity table, and the category taxonomies must be explicitly bridged because they are not the same vocabulary.

**How it works.**

*Embeddings.* `lib/search/embeddings.ts:16` `generateEmbedding(text, taskType)` calls Gemini's REST `embedContent` with model `gemini-embedding-001` (`text-embedding-004` is retired, 404s) and `outputDimensionality: 768`, matching the `search_embeddings.embedding vector(768)` column and its HNSW cosine index (`supabase/migrations/074_search_embeddings.sql:5-20`). `taskType` defaults to `RETRIEVAL_QUERY` (query-time callers). Two paths write embeddings into `search_embeddings`: the admin route `app/api/admin/search/generate-embeddings/route.ts:51` (calls `generateEmbedding(text)` with **no** `taskType` argument, so it silently uses `RETRIEVAL_QUERY` even though it is writing documents) and the standalone script `_tasks/backfill-search-embeddings.ts:34-51` (a separate, hand-rolled REST call that correctly passes `RETRIEVAL_DOCUMENT`). See Gotchas.

*Query-time salon search (`app/api/salons/route.ts`, the main filter engine).* When `q.length >= 2` (line 133), the route races `generateEmbedding(q)` against a 500ms timeout (line 140) and, whatever happens, calls the `search_salons_ranked` RPC (line 152) with `p_query_embedding` set or `undefined` (lexical-only fallback, never blocks the request). The returned `salon_id`s become `rankIndex`, a rank-order `Map`; `semanticMode = rankIndex !== null` (line 162) skips the DB `.order()/.range()` entirely, fetches the whole matched set via `.in("id", ids)`, and sorts + paginates in JS at the very end (lines 625-633). Structured filters (category `.contains`, "search this area" lat/lng bounds that *replace* the city filter, `ids`, `min_rating`, `accepts_payment`, `deals`, `walk_in`, nine amenity booleans) are applied directly as `.eq()`/`.contains()` predicates on the same query builder (lines 178-227). Filters that cannot be expressed as a direct predicate (city name/slug resolution, service-name substring match, gender via `suitable_gender` array, price range via joined `services`, time-of-day `period`, `instant_bookable`, single-day `date`, `open_now`) are each resolved as an **independent salon_id set first**, fired concurrently with `Promise.all` (lines 361-367, replacing what used to be N sequential round-trips), then AND-combined onto the main query with `.in("id", ids)` **before** `.range()` is applied (lines 370-427). Any filter that resolves to zero ids short-circuits to `emptyResult()` rather than falling through. This resolve-ids-then-`.in()`-before-`.range()` shape is the codebase's canonical "computed filter" pattern (see `_rules/LESSONS_LEARNED.md:342-347`) and every new filter here follows it.

*Availability RPCs.* `salons_with_slot_in_hours(start_hour, end_hour, from, to)` (`supabase/migrations/20260607182403_add_salons_with_slot_in_hours_rpc.sql:6`) returns `DISTINCT` `salon_id`s with an available slot whose local hour falls in the window, computed server-side with `EXTRACT(hour ...)`, so it never hits PostgREST's ~1000-row cap or requires a JS dedupe pass. It backs `period` (a `PERIOD_HOURS` lookup: morning 9-12, noon 12-15, afternoon 15-18, evening 18-24), `instant_bookable` (0-24h window, next 48h), and the `date` narrow-filter (0-24h window, single day). `next_available_dates(salon_ids[], after)` (`20260711094114_backend_loop_next_available_dates_rpc.sql`) is a `DISTINCT ON (salon_id)` query returning the earliest future slot bucketed as an Europe/Zurich calendar day (`to_char(... at time zone 'Europe/Zurich', 'YYYY-MM-DD')`); it replaced a per-salon fetch-every-future-slot approach that silently truncated at PostgREST's row cap (1,470 rows fetched to keep 6). `earliest_slots_by_service(service_ids[], from, to, per)` (`20260703095144_perf_earliest_slots_by_service_rpc.sql`) is a `LATERAL`-join RPC returning the earliest N slots per service in one round trip, replacing ~60 parallel per-service queries; it powers the `?with_slots=1` Fresha-style booking card (top 3 services per salon, each annotated with `.slots`, `app/api/salons/route.ts:534-583`).

*Open-now filtering.* `open_now=true` cannot be a PostgREST predicate: it depends on Zurich-local time-of-day evaluated against a free-form `opening_hours` jsonb column, including overnight wrap (e.g. 20:00-02:00). The route fetches a light `id, opening_hours` candidate set, evaluates `isOpenNow()` (`lib/salon-hours.ts:50`) in JS, and only then applies `.in("id", openIds)` before `.range()` (`app/api/salons/route.ts:352-359, 420-427`) — the same computed-filter shape as above.

*Semantic + lexical ranking (`search_salons_ranked`).* This RPC has been rewritten through a chain of migrations (phase1 → phase4 → phase4b → phase5 → phase5b → DNA-affinity); the live definition is `supabase/migrations/20260701120000_search_dna_affinity.sql:21`. It builds a `websearch_to_tsquery('german', ...)` over an `f_unaccent`-normalized query, expands it through a one-way `search_synonyms` table (including fr/it terms), unions FTS matches across `services`, `salons`, and `staff_members`, unions in a `word_similarity` (trigram) fuzzy path and an exact-substring boost, unions in a pgvector cosine path over `search_embeddings` (candidates above `vec_threshold`, top `vec_topk`, both tunable columns on `search_ranking_weights`), and blends all of it with a Bayesian-shrunk rating term (`bayes_prior_m`/`bayes_global_c`) and a `search_popularity` term, weighted by the single tunable row `search_ranking_weights` (`id=1`, live-adjustable without redeploy). A final `uaff` CTE adds a **signed-in-only** category-affinity boost read from `user_style_affinity` via `auth.uid()` (never a caller-supplied user id, so it cannot be spoofed for another user) — this is where the discovery-category-to-salon-category bridge (`hair→coiffeur`, `beard→barbershop`, else identity) is re-implemented a second time, in SQL, independently of `lib/discovery-categories.ts`. `search_suggest` (typeahead) carries the same synonym/FTS/fuzzy/affinity machinery at smaller limits (5 services, 3 salons, 5 stylists).

*Learning loop.* `app/api/search/event/route.ts` is the only writer to `search_events` (impressions + clicks). It is deliberately a hardened Next route rather than a public RPC: IP rate-limited, a server-minted httpOnly session cookie (never client-supplied), click-membership proof (the clicked id must actually appear in what `search_suggest`/`search_salons_ranked` would return for that query), owner self-click exclusion, and an explicit client-side consent flag that gates whether the row carries a session/user id at all (anonymous aggregate rows are still logged when consent is refused). A nightly `pg_cron` job (`supabase/migrations/20260606204021_search_phase6_learning_loop.sql:67-68`) refreshes the **materialized view** `search_popularity` (per-salon, per-session, time-decayed, position-debiased, Bayesian-shrunk click popularity) that `search_salons_ranked` joins in.

*Discovery / Inspo feed (`app/api/discovery/feed/route.ts`).* Three mutually exclusive branches: (1) `filters.search` set → `search_discovery` RPC, FTS `ts_rank` over an `IMMUTABLE` wrapper `discovery_fts_doc()` (an earlier GIN index built directly on `to_tsvector(...)` never actually applied because Postgres rejects non-`IMMUTABLE` index expressions — `20260531_discovery_search_rpc.sql:1-9` documents the fix), logs the search to `discovery_search_events` on page 1 only, and is the one branch that never personalizes so it is always CDN-cacheable. (2) A logged-in "pure browse" (no category/gender/texture/style/creator/tag filter) → `discovery_feed_for_you` RPC, which ranks every published item by `sum(user_style_affinity.score)` matched against the item's gender/texture/vibe/length/occasion/tags; a cold user (no affinity rows) scores 0 across the board, which sorts identically to the neutral feed. Falls back to branch (3) on RPC error. (3) Everything else → `discovery_feed` RPC: hard filters on category/gender/texture/style/creator, a tag-overlap filter (`di.tags && p_tags_any`, the progressive drill-down mechanism — see `lib/discovery/hair-cuts.ts`'s `HAIR_CUTS` texture→cut-chip→tag map), and a **soft** gender bias (`p_user_gender`, read from the viewer's `profiles.disc_gender`) that sorts matching-or-unisex items first without ever excluding anything. Response caching (`lib/discovery/feed-cache-headers.ts`) is asymmetric: the search branch is always cacheable; the for-you/general branches are cacheable **only** when no `sb-`-prefixed auth cookie was present at all (so a personalized payload can never be written into a shared CDN slot keyed only by URL).

*DNA / affinity scoring (`user_style_affinity`).* `recompute_user_style_affinity()` (`supabase/migrations/20260623124500_user_style_affinity.sql:29`, `SECURITY DEFINER`) is invoked daily by `app/api/cron/style-affinity-recompute/route.ts` (wired in `.github/workflows/cron-jobs.yml:132`). It aggregates `discovery_saves` (weight 0.5), `discovery_likes` (0.4), `discovery_interactions` of type share/click/view (0.5/0.25/0.15), and `discovery_search_events` (0.35) over a 365-day window with exponential recency decay (60-day half-life-ish constant), exploding each interacted item into per-attribute rows (`gender`, `texture`, `vibe`, `length`, `occasion`, one row per `tag`) and upserting summed, decayed scores per `(user_id, attr_type, attr_value)`. This single table feeds two consumers: `discovery_feed_for_you` (fully live, drives the Inspo for-you order) and `search_salons_ranked`'s `w_affinity` term (salon search personalization) — see Gotchas for why the latter currently does nothing.

*Category taxonomy bridge.* `lib/discovery-categories.ts:24` `DISCOVERY_TO_MARKETPLACE_CATEGORY` maps the discovery/Inspo taxonomy (`hair | beard | nails | lashes | brows`, plus `makeup`/`waxing` which fall back to `coiffeur`) onto the marketplace taxonomy (`coiffeur | barbershop | nails | spa` — the four-value `salonCategory` enum in `lib/validations.ts:255`). Only `nails` spells the same in both namespaces; every other discovery category needs the bridge. It's consumed by `app/api/discovery/salons-for-style/route.ts:27` ("shop this look" salon suggestions under an Inspo item, joining `salons` to `services!inner` on the bridged category) and is re-implemented independently (in SQL, via a `CASE` expression) inside `search_salons_ranked`'s and `search_suggest`'s `uaff` CTEs for the DNA-affinity boost.

*Other salon-adjacent surfaces.* `app/api/salons/search/route.ts` is a second, older salon-search endpoint that calls the same `search_salons_ranked` RPC and is explicitly commented as "queued for deletion... once its 3 consumers are repointed" (line 57). `app/api/salons/similar/route.ts` (same quartier + exact category match, ordered by `solen_score`) and `app/api/salons/recommendations/route.ts?salon_id=` (category `.overlaps`, ordered by `explore_score`) are two independently-implemented "similar salons" endpoints with different matching logic. `app/api/recommendations/route.ts` (Gemini-ranked, booking-history-aware, cold-start-fallback-to-Basel-trending) and `app/api/salons/recommendations/route.ts` (no LLM call, `user_preferences.favorite_quartier_ids`/`favorite_service_slugs`-based, falls back to highest `explore_score`) are two independently-implemented "recommendations" endpoints.

**Gotchas + invariants.**
- **The open-now short-day-key bug is fixed but the trap is structural.** `opening_hours` is short-day-keyed (`mon`/`tue`/…, missing key = closed) in every real row; `isOpenNow()` used to look up only long names and silently returned `isOpen:false` for every salon (`_rules/LESSONS_LEARNED.md:336-338`). It now checks both conventions, but any *new* opening-hours consumer must do the same or repeat the bug.
- **Computed filters must resolve ids before `.range()`, never filter client-side over one page.** This is proven history, not style preference: `open_now` was previously a dead filter that counted as "active" in the UI while doing nothing (`_rules/LESSONS_LEARNED.md:342-347`). Every filter in `/api/salons/route.ts` that can't be a direct PostgREST predicate (period, instant_bookable, date, open_now) follows the resolve-ids-then-`.in()`-before-`.range()` shape; a new one that doesn't will silently break count/pagination.
- **The admin embedding-backfill route likely writes embeddings in the wrong vector space.** `app/api/admin/search/generate-embeddings/route.ts:51` calls `generateEmbedding(text)` with no `taskType`, so it defaults to `RETRIEVAL_QUERY` even though it is embedding *documents* (services). `lib/search/embeddings.ts:12-14`'s own doc comment says backfill callers should pass `RETRIEVAL_DOCUMENT`. The separate script `_tasks/backfill-search-embeddings.ts` gets this right (bypasses `lib/search/embeddings.ts` entirely with its own REST call). If salon/service search feels asymmetrically bad for query-vs-document matching, check which backfill path actually populated the live `search_embeddings` rows.
- **`w_popularity` and `w_affinity` default to `0.0` and no migration in this repo flips them.** `search_popularity` (click-derived) and `user_style_affinity` (DNA-derived) are both fully wired into `search_salons_ranked`'s scoring formula, but unless someone updated the single `search_ranking_weights` row live (outside migration history), both terms currently contribute nothing to salon search ranking. `w_vector` *was* flipped to `0.35` in `20260606204921_search_phase5_hybrid_vector_fusion.sql:120`, so semantic vector search is live; do not assume popularity/affinity are, without reading the live row.
- **Two independent copies of the discovery→marketplace category bridge exist**: `lib/discovery-categories.ts` (TypeScript, used by API routes) and an inline SQL `CASE` inside `search_salons_ranked`/`search_suggest`'s `uaff` CTE. They currently agree (`hair→coiffeur`, `beard→barbershop`) but nothing enforces that they stay in sync; a change to one without the other is a silent divergence, not an error.
- **A direct join of `discovery_items.category` into `services.category` is a silent no-op for every category except `nails`.** Any new discovery→salon join must go through `DISCOVERY_TO_MARKETPLACE_CATEGORY`.
- **The Inspo feed's personalization/caching split depends on cookie presence, not auth success.** `feedCacheHeaders()` treats "no `sb-` cookie" as safe-to-cache and any cookie presence as no-store, even if `auth.getUser()` would have failed. This is intentionally conservative (correctness over caching), but it means a visitor with a stale/expired session cookie always gets the uncached path.
- **Discovery search RPC used to silently not use its index.** `search_discovery`'s GIN index was originally built directly on `to_tsvector(...)`, which Postgres rejects for non-`IMMUTABLE` expressions; the fix wraps it in an explicit `IMMUTABLE` function (`discovery_fts_doc`) that both the index and the RPC now share. Any future FTS index on a computed expression needs the same `IMMUTABLE` wrapper or it will "apply" without erroring and just never be used.
- **`/api/salons/search/route.ts` is explicitly marked for deletion** once its three consumers are repointed at `/api/salons`. Don't build new features on it.
- **Multiple overlapping "similar"/"recommendations" endpoints** (`/api/salons/similar` vs `/api/salons/recommendations?salon_id=`; `/api/recommendations` vs `/api/salons/recommendations`) implement different matching logic with no shared source of truth. Check which one a given UI surface actually calls before "fixing" the wrong one.
- **`open_now`, `deals`, and `gender` filters are three different maturity levels of the same problem** (a filter that must actually discriminate, not just render): `open_now` is always shown and computed correctly; `deals`/`gender` are hidden by `getFilterAvailability()` until live data can discriminate on them, then reappear automatically. Don't assume a visible filter control implies live discriminating data, or a hidden one implies broken code — check `lib/search/filter-availability.ts`'s two head-counts.
- **`search_events` writes can be rate-limit-bypassed when Upstash env vars are missing** (`applyRateLimit` fails open, explicitly documented in the route itself). Treat `search_popularity` as a soft signal, not ground truth, until that's closed.

## 9. Security infrastructure (the S1 stack)

**What it is.** A mandatory, ordered set of layers (feature flag/kill-switch, auth, ban check, rate limit, input validation, audit log) that every `app/api/**/route.ts` handler is supposed to compose before touching business logic, plus the surrounding infrastructure (env schema, secrets model, SSRF guard) that backs it. It exists because a 2026-03-17 audit found zero rate limiting, zero input validation, exposed credentials in git, and disabled RLS (`_rules/SECURITY_RULES.md:7`).

**How it works.**

1. **Feature flag / kill-switch** (`lib/feature-flags.ts:39` `checkFeatureEnabled(featureKey)`). Reads two rows from `feature_flags` (`maintenance_mode` + the route's own key) through a single `.in("key", keys)` call, behind a 30s in-process `Map` TTL cache (`lib/feature-flags.ts:24-26`, added "Ring 2a" 2026-07-11 to cut the DB round-trips most mutation routes were paying every request). Both checks **fail open**: a missing row or a query error leaves `maintenance_mode` false and the feature `enabled` true (`lib/feature-flags.ts:74-83`), and any thrown exception (e.g. the admin client can't even be constructed) also returns `null` i.e. "proceed" (`lib/feature-flags.ts:104-107`). Returns a `503` `NextResponse` with `MAINTENANCE_MODE` or `FEATURE_DISABLED` when blocked, or `null` to continue. `checkUserBanned(userId)` (`lib/feature-flags.ts:149`) is the companion ban check: it has its own, much shorter, 10s TTL cache (`lib/feature-flags.ts:119`, deliberately shorter than the flag cache so a freshly banned user is cut off fast) and it is the opposite risk posture, it **fails closed**: any DB error other than "no row" (`PGRST116`) returns a `503` `BAN_CHECK_FAILED` rather than letting the request through (`lib/feature-flags.ts:167-173`).

2. **Auth** (`lib/auth/require.ts`). `requireAuth()` calls `createServerSupabaseClient()` then `supabase.auth.getUser()`, which round-trips to the Supabase Auth server to verify the JWT signature and **fails closed** (`user: null` on any verification failure) (`lib/auth/require.ts:51-63`). This is the mandated replacement for `supabase.auth.getSession()`, which only reads the client-supplied cookie without checking its signature, so a forged cookie could set any `user.id` (`_rules/SECURITY_RULES.md:13`). The migration happened 2026-07-10 in commit `9783e5711`. `requireAdmin()` layers a DB read of `profiles.role` on top and only proceeds if `role === "admin"` (`lib/auth/require.ts:72-101`); `requireSalonOwner(salonId)` checks `salons.owner_id === user.id` (`lib/auth/require.ts:109-144`); `requireRole(roles)` checks `profiles.role` against an allow-list (`lib/auth/require.ts:151-183`). **Gotcha:** despite being documented as the canonical import in `_rules/SECURITY_RULES.md:25` and re-exported from `lib/auth/index.ts:1`, these four helpers are essentially unused in the live route tree, see Gotchas below.

3. **Rate limit** (`lib/ratelimit.ts`). `applyRateLimit(limiter, { userId } | { ip })` calls Upstash's sliding-window `Ratelimit.limit(key)` and returns a `429` `NextResponse` (with `X-RateLimit-*`/`Retry-After` headers) on a hit, or `null` to continue (`lib/ratelimit.ts:151-191`). A dozen+ named limiters are pre-declared with route-specific windows (`generalLimiter` 30/min, `bookingLimiter` 5/hour, `paymentLimiter` 3/hour, `authLimiter` 5/min, `guestLookupLimiter` 10/10min for the guest-token enumeration surface, `resendAccessLimiter` 3/hour, etc., `lib/ratelimit.ts:15-102`). **Fail-open/closed split**: if `UPSTASH_REDIS_REST_URL`/`TOKEN` are unset, every limiter normally fails open (`return null`), **except** a hardcoded `ABUSE_PRONE_LIMITERS` set (auth, payment, booking, guestLookup, referral, referralValidate, resendAccess), which fails **closed** with a synthetic `429` **only on a real production boot** (`process.env.CONTEXT === "production" && process.env.NODE_ENV === "production"`, `lib/ratelimit.ts:160-169`). On any other misconfigured-prod limiter it pages `ADMIN_EMAIL` once per process via `alertAdmin()` (`lib/ratelimit.ts:136-147`). A genuine Redis error at request time (not "unconfigured") always fails open with a `console.error` (`lib/ratelimit.ts:186-189`). `getClientIp(req)` (`lib/ratelimit.ts:216-229`) is XFF-hardening: it trusts Netlify's edge-set `x-nf-client-connection-ip` first, then `x-real-ip`, and only falls back to the client-spoofable `x-forwarded-for` leftmost entry as a last resort (local/dev only) — because an attacker can prepend any value to XFF and trivially bypass an IP-keyed limiter that trusts it alone.

4. **Input validation** (`lib/validations.ts`). `validateBody(schema, body)` runs a Zod `.safeParse` and returns `{ data, error: null }` or `{ data: null, error: { message } }`, where `message` is every issue's `path: message` joined with `; ` (`lib/validations.ts:5-12`). There is one schema per mutation shape (100+ exported schemas covering bookings, reviews, payments, admin actions, discovery, nail/barber verticals, guest access, etc.). Money fields are consistently typed as integer Rappen with `.max()` bounds (e.g. `tipSchema.amount: z.number().int().min(100).max(10000)`, `lib/validations.ts:386-389`); server-trusted values a client sends only as a *display* hint are commented as such (e.g. `createBookingSchema.total_price`, `lib/validations.ts:69-70`: "the server ALWAYS recomputes the real price… never trusts it"). `validateQuery(schema, params)` (`lib/validations.ts:1248-1252`) reuses the same helper for `URLSearchParams`.

5. **Business logic**, which itself must never trust client-supplied prices/totals/roles — every price is recomputed server-side from the live `services`/`bundles`/`vouchers` rows (see `app/api/bookings/route.ts:294-385` for the canonical example: primary price + extras + optional bundle recompute, promo/voucher re-validated at charge time, never at booking-create time).

6. **Audit logging** (`lib/audit.ts`). `logAuditEvent(req, actorId, action, targetType, targetId?, metadata?)` inserts one row into `audit_log` (`actor_id, action, target_type, target_id, metadata, ip_address`) using the **service-role admin client** (`lib/audit.ts:17`, so it bypasses RLS entirely) and stamps `ip_address` via the same `getClientIp()` used for rate limiting. It never throws: a failure is logged with `console.error` and additionally pages `ADMIN_EMAIL` through `alertAdmin()` (`lib/audit.ts:27-39`), because the dispute engine treats `audit_log` as the redundant money-trail, so a silent failure there means a money move with no record. `action`/`target_type` are free-text strings, not an enum, validated only by convention (grep existing call sites before inventing a new action name).

**S6, the admin double-role-check rule.** Every route under `app/api/admin/**` must re-derive the caller's role from the `profiles` table on the server, never trust a client header or a JWT claim (`_rules/SECURITY_RULES.md:129-141`). In practice this is done two ways in the live codebase: (a) via `requireAdmin()` from `lib/auth/require.ts` (used by exactly one route today, see Gotchas), or (b) inlined, e.g. `app/api/admin/commission/route.ts:23-25`: `supabase.from("profiles").select("role").eq("id", user.id).single()` then `if (profile?.role !== "admin") return 403`. Both patterns hit the DB every time (no role caching), which is the point: a role change or ban takes effect on the very next request.

**The secrets/env model** (`lib/env.ts`). One Zod schema per boundary: `serverEnvSchema` (server-only vars, read via `getServerEnv()`) and `publicEnvSchema` (only `NEXT_PUBLIC_*` vars, safe to ship to the browser, read via `getPublicEnv()`). Only `SUPABASE_SERVICE_ROLE_KEY` is truly required at first access (`lib/env.ts:32`); everything else is `.optional()` with format validation where relevant (`sk_live_`/`sk_test_` for Stripe, `whsec_` for the webhook secret, `re_` for Resend, URL/email format). `getServerEnv()`/`getPublicEnv()` throw on first access if the schema fails, by design ("crash-loud at boot, not silent fallback at runtime", `lib/env.ts:143`), and cache the parsed result in a module-level variable so validation only runs once per process. A separate list, `PROD_REQUIRED_VARS` (`lib/env.ts:215-223`: Upstash pair, `CRON_SECRET`, Stripe secret+webhook, Resend key, `ADMIN_EMAIL`), is enforced only by `assertProdRequiredEnv()`, called once at boot from `instrumentation.ts`, and only actually throws when **both** `CONTEXT === "production"` and `NODE_ENV === "production"` (this double-check, repeated in `lib/ratelimit.ts:160` and `:201`, exists because Netlify also sets `CONTEXT` on deploy previews and branch deploys, which must never be blocked by a missing prod-only secret).

**The CANONICAL S1 route skeleton** (`_rules/SECURITY_RULES.md:17-44`, mirrored by the money routes that follow it most closely, e.g. `app/api/admin/commission/route.ts`):

```typescript
export async function POST(req: NextRequest) {
  // 1. Feature flag check
  const disabled = await checkFeatureEnabled("bookings");
  if (disabled) return disabled;

  // 2. Auth (verifies JWT, fails closed)
  const auth = await requireAuth(); // or manual getUser() pattern, see Gotchas
  if (auth instanceof NextResponse) return auth;
  const { user, supabase } = auth;

  // 3. Ban check
  const banned = await checkUserBanned(user.id);
  if (banned) return banned;

  // 4. Rate limit
  const rateLimited = await applyRateLimit(bookingLimiter, { userId: user.id });
  if (rateLimited) return rateLimited;

  // 5. Input validation (zod)
  const body = await req.json();
  const { data, error } = validateBody(createBookingSchema, body);
  if (error) return NextResponse.json({ message: error.message, code: "VALIDATION_ERROR" }, { status: 400 });

  // 6. Business logic, never trust client prices/roles/totals
  // 7. (money/admin routes) logAuditEvent(...)
}
```

For public/unauthenticated `GET` routes, swap step 2-4 for IP-keyed rate limiting only: `applyRateLimit(generalLimiter, { ip: getClientIp(req) })` (`_rules/SECURITY_RULES.md:60-69`, live example `app/api/salons/route.ts:56`).

**Gotchas + invariants.**
- **The documented canonical helpers are effectively dead code in the live route tree.** `_rules/SECURITY_RULES.md:25` tells you to import `requireAuth()`/`requireAdmin()` from `lib/auth/require.ts`. A repo-wide grep found **zero** `app/api/**/route.ts` files importing `requireAuth` and exactly **one** (`app/api/admin/seed-test-salons/route.ts`) importing `requireAdmin` from that module (verified: `grep -rln "requireAuth\b" app/ lib/` returns only `lib/auth/require.ts` and `lib/auth/index.ts` themselves). Every real route (`app/api/bookings/route.ts:19-20`, `app/api/admin/commission/route.ts:16-25`, 232 routes total per grep of `auth.getUser()` in `app/api`) instead inlines `createServerSupabaseClient()` + `supabase.auth.getUser()` + a manual `profiles.role` read. Worse: `app/api/admin/seed-test-salons/route.ts:18-30` defines its **own local function also named `requireAdmin`**, shadowing the imported name rather than calling the shared helper, so even that one "usage" is not actually the shared implementation. This is not a security bug per se (the inline pattern does the same `getUser()`-then-DB-role-check work correctly), but it means the shared helper file is aspirational documentation, not the enforced pattern; do not assume a grep for `requireAuth(` will find every auth-checked route, and do not be surprised the helper's edge cases (e.g. its `503 ROLE_CHECK_FAILED` on a DB error) are not what most routes actually return.
- **Fail-open vs fail-closed is deliberately inconsistent, know which is which before you add a new limiter/flag.** Feature flags fail OPEN on any error (`lib/feature-flags.ts:74-83`, `104-107`). Ban checks fail CLOSED on a DB error (`lib/feature-flags.ts:167-173`). Rate limiting fails OPEN everywhere except the hardcoded `ABUSE_PRONE_LIMITERS` set on a *real production* boot with Redis unconfigured (`lib/ratelimit.ts:114-122`, `160-169`). If you add a new limiter for an abuse-prone surface (auth, payment, booking, any enumeration oracle), you must add it to `ABUSE_PRONE_LIMITERS` yourself, the default for a new `Ratelimit` instance is fail-open.
- **The `CONTEXT === "production" && NODE_ENV === "production"` double-check appears three times** (`lib/env.ts:236`, `lib/ratelimit.ts:160`, `lib/ratelimit.ts:201`) and must stay in sync: Netlify sets `CONTEXT` to `deploy-preview`/`branch-deploy` too, so `CONTEXT` alone is not a safe "is this really prod" test.
- **`logAuditEvent` never blocking the caller** means a caller cannot rely on it to guarantee a record exists; it is deliberately fire-and-forget (`await`ed, but its own internal errors are swallowed after alerting). If a route needs a hard guarantee an action was recorded before responding success, `logAuditEvent` alone does not provide that.
- **`audit_log.action`/`target_type` have no DB-level enum/CHECK constraint** (migration `031_audit_log.sql:6-8` is plain `text NOT NULL`); action names are whatever string a caller chose (e.g. `"cancellation_fee_charged"`, `"feature_flag.toggle"` even when the actual event was a commission-rate change, `app/api/admin/commission/route.ts:88` , the comment there literally says "using closest available action type"). Grep existing call sites before inventing a new action string, there is no source of truth other than convention.
- **Rate limiting only engages if `UPSTASH_REDIS_REST_URL`/`TOKEN` are both set.** In any non-production context (local dev, preview, branch deploy) with Redis unconfigured, every limiter, including auth/payment/booking, is a silent no-op. Do not test "does my new rate limit work" against a preview deploy without confirming Upstash env vars are actually set there.
- **The feature-flag and ban caches are per-process, in-memory `Map`s** (`lib/feature-flags.ts:26`, `:128`), not shared across serverless instances. A cold instance always reads fresh; a warm instance can serve a stale flag/ban state for up to its TTL (30s flags, 10s bans). An owner toggling `maintenance_mode` or banning a user is not instantaneous across the fleet.

**Where to look when changing it.**
- Adding a new mutation route: `_rules/SECURITY_RULES.md` for the checklist, then copy the layer-ordering from `app/api/bookings/route.ts` (guest-tolerant, userId-or-IP rate limiting) or `app/api/admin/commission/route.ts` (admin double-role-check + audit log) depending on whether the route is customer-facing or admin.
- Adding a new rate limiter: `lib/ratelimit.ts`, decide immediately whether the surface is abuse-prone (enumeration oracle, money, credential-adjacent) and add it to `ABUSE_PRONE_LIMITERS` if so.
- Adding a new request-body shape: `lib/validations.ts`, add one Zod schema near its sibling schemas (grouped by feature area with section comment headers), never inline a schema in the route file.
- Adding a new env var: `lib/env.ts` schema, then `.env.example`, then `.env.local` + Netlify dashboard (server) per the file's own header comment (`lib/env.ts:21-25`); add to `PROD_REQUIRED_VARS` only if a real production boot must hard-fail without it.
- Auditing what actually enforces auth today: do not trust a grep for `requireAuth(`, grep for `auth.getUser()` in `app/api/**/route.ts` instead (the manual pattern is what is actually live).

## 10. Observability, ops & disaster recovery

**What it is.** How the backend detects that something is broken (health probe, error alerting, cron-run logging, a founder daily digest), how it protects data (nightly export to Storage since Supabase PITR is off), how schema state gets reproduced from files, and how it satisfies Swiss nFADP/GDPR retention duties. This is a self-built stack, no Sentry, no external uptime service wired in yet (that step is explicitly left to the owner).

**How it works.**

1. **Liveness/dependency probe.** `GET /api/health` (`app/api/health/route.ts:15-19`) calls `runHealthProbes(admin)` in `lib/health.ts:117-122`, which runs three checks in parallel: `probeDb` does a HEAD count against the tiny `cities` table via the service-role client (`lib/health.ts:47-59`, chosen specifically because `.select("*", {count:"exact", head:true})` can't silently no-op on a renamed column, the project's own "silent no-ops" failure class); `probeRedis` PINGs Upstash if `UPSTASH_REDIS_REST_URL`/`TOKEN` are set, else reports `"unconfigured"` (not a failure) (`lib/health.ts:67-83`); `probeEnv` checks `PROD_REQUIRED_VARS` are present, but only during a real production boot (`CONTEXT=production && NODE_ENV=production`), so dev/preview never trips it (`lib/health.ts:91-100`, `lib/env.ts:235-246`). Each probe has a 2s timeout via `Promise.race` (`lib/health.ts:31-38`). The route returns `200` if every probe is `ok`/`unconfigured`, `503` if any hard-fails (`app/api/health/route.ts:18`, `lib/health.ts:120`). `.github/workflows/cron-jobs.yml:37-44` piggybacks a curl-and-retry-once health check onto the existing every-15-min Actions job (zero extra Actions minutes), failing that job red on a down site (which triggers GitHub's default failed-workflow email).

2. **Central error alerting.** `reportError(scope, err, context)` in `lib/error-report.ts:42-65` is the one call a top-level catch should make: it always `console.error`s, then fires `alertAdmin(scope, {...})` (`lib/alert-admin.ts:35-69`), which emails `ADMIN_EMAIL` via the existing Resend pipe (`lib/email.ts:35`, subject `[Solen money-alert] {subject}`). Throttled per `scope` to once per 15 minutes via an in-memory `Map` (`lib/error-report.ts:25-28,51-56`) — the file's own header flags this throttle is per-process, so a multi-instance Netlify deploy under load can emit more than one alert per scope per window (`lib/error-report.ts:15-21`). Both `reportError` and `alertAdmin` are contractually non-throwing (`lib/error-report.ts:60-64`, `lib/alert-admin.ts:64-68`) so a broken alert path can never mask or crash the original error. `reportError` is called directly from money-path catches (`app/api/stripe/webhook/route.ts`, `app/api/bookings/[id]/refund/route.ts`, `app/api/bookings/[id]/dispute/route.ts`, `app/api/admin/purchase-refund/route.ts`, etc., found via grep) and once centrally from `withCronRun` on any thrown cron error (`lib/cron-run.ts:56-63`).

3. **Cron observability.** `withCronRun(name, handler)` (`lib/cron-run.ts:43-102`) wraps a cron route's body: times it, catches a throw (calling `reportError` per above), inserts one best-effort row into `cron_runs` (`name, ok, processed, duration_ms, errors`, `lib/cron-run.ts:79-91`), and shapes the response as `{...result, ok, processed?, errors?}` with HTTP `200` when `ok` else `500` (`lib/cron-run.ts:94-101`). `ok` is `true` only when nothing threw, `result.ok !== false`, and `errors.length === 0` (`lib/cron-run.ts:74`). Every route under `app/api/cron/*` uses this wrapper (verified: 24 of 24 route files grep for `withCronRun`) — **except** `app/api/admin/solen-score/recalculate/route.ts`, which lives outside `app/api/cron/` (see Gotchas, this is load-bearing). `.github/actions/ping-cron/action.yml:48-71` then hard-asserts `jq -e '.ok == true'` on the JSON body and `exit 1`s the step if any pinged path fails that assert, so a dead cron turns the GitHub Actions run red (introduced in commit `7f057ede3`, 2026-07-11; before that it only emitted a warning and always exited 0, see Gotchas).

4. **Founder daily digest.** `GET /api/cron/daily-digest` (`app/api/cron/daily-digest/route.ts`), scheduled 05:15 UTC (`.github/workflows/cron-jobs.yml:212-221`, deliberately after the 03:00-04:00 UTC batch so the cron-health section reflects that night). Computes yesterday's Europe/Zurich calendar day via `zurichWallClockToUtc` (DST-safe, `app/api/cron/daily-digest/route.ts:47-53`) and queries four independent sections: bookings created (`:61-74`), bookings completed (`:77-91`), `cron_runs` rows with `ok=false` in the last 24h (`:94-120`), and pending reviews with no `salon_response` (`:123-135`). Each section is wrapped in its own try/query; a failed query is pushed to `errors[]` and simply **omitted** from the email rather than rendered as a fabricated `0` (`:67-73` etc., matches the project's no-fabricated-data rule). One email to `ADMIN_EMAIL` via `sendEmail` if any section succeeded (`:137-153`). The whole handler is itself wrapped in `withCronRun("daily-digest", ...)` so its own failure is logged too (`:38`).

5. **Backups / disaster recovery.** Supabase PITR is `false` and the platform backup list is empty on the live project (per `_plans/OPS_RUNBOOK.md:14,18`, stated as verified 2026-07-11 via the Supabase MCP `get_project` call; not independently re-verified in this pass, no Supabase MCP auth available in this session). The in-house nightly export is therefore the only restorable backup today. `GET /api/cron/db-backup` (`app/api/cron/db-backup/route.ts`), scheduled 03:45 UTC (`.github/workflows/cron-jobs.yml:135-144`), calls `runDbBackupExport(prefix)` (`lib/backup/export.ts:76-116`) which pages every table in `BACKUP_TABLES` (24 tables, `lib/backup/export.ts:26-51`) in 1000-row chunks via `.range()`, JSON-stringifies each table to one array, and uploads to the private `db-backups` Storage bucket at `backups/<YYYY-MM-DD>/<table>.json` with `upsert:true` (idempotent re-run). A single table's failure is pushed to `errors[]` and does **not** abort the loop (`lib/backup/export.ts:105-109`). Retention (`pruneOldBackups`, `lib/backup/export.ts:130-172`) deletes date-folders older than `RETENTION_DAYS = 14` — but only runs when the export was fully clean (`app/api/cron/db-backup/route.ts:34-39`), so a partial night never prunes an older complete backup. `availability_slots` (regenerable via `generate-slots`) and `discovery_items` (media-heavy, regenerable from source feeds) are deliberately excluded (`lib/backup/export.ts:24-25`). Restore is manual: download the date folder, apply `supabase/migrations/*` to provision schema first, upsert rows table-by-table in the FK order documented in `_plans/OPS_RUNBOOK.md:24`, then verify with `npm run smoke` before repointing anything live. `scripts/db-backup-kill-test.ts` exercises the real export against a throwaway `backups-test/` prefix and asserts row counts + byte counts + zero leftovers after cleanup (does not exercise restore).

6. **Schema reproducibility.** `_plans/OPS_RUNBOOK.md:15` states all 260 applied migrations now have committed `.sql` files under `supabase/migrations/` (59 were backfilled from `supabase_migrations.schema_migrations` on 2026-07-11), so a fresh environment can be provisioned from files. Both migrations this section depends on carry that same backfill header (`supabase/migrations/20260711082619_backend_loop_cron_runs_log.sql:1-3`, `supabase/migrations/20260711161553_backend_loop_db_backups_bucket.sql:1-2`).

7. **Data retention (Swiss nFADP).** `search_events` (`supabase/migrations/20260606204021_search_phase6_learning_loop.sql:8-23`) is written only by the rate-limited `/api/search/event` service-role endpoint. A `pg_cron` job `search-events-retention` (`:69-73`) nulls `query`, `session_id`, `user_id` (not the row itself) for events older than 90 days — anonymization, not deletion, so aggregate stats keep working. `user_id` also carries `on delete set null` so a profile delete de-links immediately regardless of the 90-day job (`:11`). GDPR/revDSG account deletion runs via `GET /api/cron/process-deletions` (`app/api/cron/process-deletions/route.ts`), scheduled daily 03:00 UTC as the second step of the `daily-03-utc` job (`.github/workflows/cron-jobs.yml:119-123`, but see Gotchas — this step may not currently execute). It finds `profiles` with `deletion_requested_at` more than 30 days old (`:22-31`), batch-clears 17 dependent tables via one IN-list op per table across all due users (`:90-117`, FK-order preserved: `credit_redemptions` before `user_credits`), then calls `admin.auth.admin.deleteUser(id)` per user (`:128-136`), which cascades to `profiles` and fires a `BEFORE DELETE` trigger (`supabase/migrations/20260602083300_financial_retention_on_delete.sql:196-267`) that **anonymizes rather than deletes** `bookings`, `booking_disputes`, and `case_events` in place — stripping identity while keeping `paid_amount`/`refunded_amount`/`payment_intent_id` intact, because Swiss OR Art. 958f mandates 10-year accounting retention and GDPR Art. 17(3)(b) carves out exactly this case. A `data_deletion_log` row is written per batch of users actually deleted, listing every table touched (`app/api/cron/process-deletions/route.ts:142-154`; live snapshot shows this table at 0 rows, so no real deletion has run yet).

8. **Cost snapshot.** `_plans/OPS_RUNBOOK.md:35-44` is a manually-filled table (Supabase, Netlify, Upstash, Resend, GitHub Actions, Stripe) with CHF amounts left as `OWNER` placeholders — this is not code-derived and needs a monthly manual refresh, not something a future session can re-verify from files alone.

- Redis: Upstash (`@upstash/redis`), PING-only for the health probe; also backs `lib/ratelimit.ts` elsewhere.
- Email: Resend, via `lib/email.ts`, used for `alertAdmin` money/ops alerts and the daily digest.
- GitHub Actions: schedules every cron, pings with a `CRON_SECRET` bearer, and is itself part of the monitoring story (a red run + GitHub's default email is the outer alert layer).

**Gotchas + invariants.**
- **The `daily-03-utc` job almost certainly hasn't run `process-deletions`, `reconcile`, or `style-affinity-recompute` since 2026-07-11.** The job runs four ping-cron steps in sequence with no `continue-on-error` / `if: always()` (`.github/workflows/cron-jobs.yml:107-134`): solen-score recalc, then process-deletions, then reconcile, then style-affinity-recompute. `app/api/admin/solen-score/recalculate/route.ts:148` returns `NextResponse.json({ success: true, updated })` — there is no `ok` field. The ping-cron action hard-asserts `jq -e '.ok == true'` and `exit 1`s on failure (`.github/actions/ping-cron/action.yml:52-56,69-71`), a change introduced in commit `7f057ede3` (2026-07-11); before that commit the same action only emitted `::warning::` and always `exit 0`'d (verified via `git show 7f057ede3`), so this exact route has silently gone from "logged a harmless warning" to "kills the rest of the job" the moment that commit landed, and the route itself was never updated to match. Since GitHub Actions stops a job's remaining steps on a failed step by default, this means the solen-score step's guaranteed-missing `ok` field blocks the three steps after it, every night, until either the route is fixed to return `ok:true` or the steps are reordered/split into independent jobs. This is invisible to the founder daily digest too: `app/api/admin/solen-score/recalculate/route.ts` is not wrapped in `withCronRun`, so it never writes a `cron_runs` row (success or failure), and the three blocked routes never even start, so they also write nothing — the digest's "cron failures in the last 24h" section (`app/api/cron/daily-digest/route.ts:94-120`) will read `0` even while GDPR deletions and Stripe reconciliation are not running. `_tasks/INCOMPLETE_FEATURES.md:13` still says "the workflow soft-fails on individual endpoint errors so a single bad endpoint doesn't suppress the others" — that claim was true before commit `7f057ede3` and is false now. `_plans/OPS_RUNBOOK.md` does not mention this gap at all. Fix options: add `ok: true` to the solen-score route's response (simplest), wrap it in `withCronRun`, or split the four steps into independent jobs/`continue-on-error: true`.
- **`_plans/OPS_RUNBOOK.md:31`'s "`cron_runs` grows ~30 rows/day" looks understated by roughly an order of magnitude**, assuming the scheduled workflow actually fires on cadence. Reading the schedule directly off `cron-jobs.yml`: every-15-min job × 3 routes ≈ 288 rows/day, every-30-min × 3 routes ≈ 144/day, hourly × 2 ≈ 48/day, every-6h × 2 ≈ 8/day, the ai-backfill every-30-min ≈ 48/day, plus the various once-daily jobs ≈ 10/day — roughly 540+ rows/day, not 30. At that rate the "revisit at ~10k rows" follow-up in the same line would trigger in under three weeks, not months. (Caveat: this is schedule math, not an observed count — the live snapshot shows `cron_runs` at only 1 row as of 2026-07-12, one day after the table was created, so there's no multi-day observed rate yet, and if the repo is private and near the Actions free-minutes cap per the runbook's own open decision #4, some scheduled runs may simply not fire.)
- **The `/api/health` DB-probe retry follow-up from `_plans/OPS_RUNBOOK.md:8` is still not implemented.** `lib/health.ts:47-59` (`probeDb`) makes exactly one attempt with a 2s timeout, no retry loop — a single timeout blip still produces a full `503`, same as the runbook flagged on 2026-07-11.
- **`reportError`'s admin-alert throttle is per-process, not global** (`lib/error-report.ts:15-21`). Netlify functions can spin up more than one instance under load, so ADMIN_EMAIL can receive more than one alert for the same `scope` inside a 15-minute window. Accepted risk per the file's own header, not a bug to "fix" without adding a shared store (Redis).
- **`alertAdmin` and `sendEmail` both silently no-op, not throw, when their env var is missing** (`lib/alert-admin.ts:41-49` on missing `ADMIN_EMAIL`, `lib/email.ts:29-32` on missing `RESEND_API_KEY`) — they `console.error`/`console.warn` and return. In a misconfigured prod boot this means the entire alerting story goes silent without any error appearing anywhere except server logs. `assertProdRequiredEnv` (`lib/env.ts:235-246`) is the only thing that would catch a missing `ADMIN_EMAIL`/`RESEND_API_KEY` before boot, and only in a real `CONTEXT=production && NODE_ENV=production` boot.
- **`db-backup`'s retention prune only runs after a fully clean export** (`app/api/cron/db-backup/route.ts:34-39`), by design, so a partially-failed table never causes an older complete backup to be pruned out from under you — but it also means a persistently-failing single table (e.g. an RLS/schema drift on one table) silently prevents retention pruning indefinitely, growing the bucket, without surfacing as anything beyond an `errors[]` entry in that day's `cron_runs` row.
- **The restore procedure is FK-order-sensitive and the runbook is explicit that `process-deletions`'s `TABLES_CLEARED` list is NOT the right order to follow** (`_plans/OPS_RUNBOOK.md:24`) — that list is a GDPR-anonymization order covering ~21 tables, not a topological insert order for the 24-table backup set. Anyone restoring from a backup must derive FK order from `lib/database.types.ts` Relationships or the live schema, not from that route.
- **PITR/backup platform-status claims in `_plans/OPS_RUNBOOK.md:14,18` are dated 2026-07-11 and were not re-verified in this pass** (no Supabase MCP session auth available here). Treat as "documented, last independently confirmed 2026-07-11" rather than live-verified today.
- Anonymize-not-delete is intentional, not a bug: a customer deletion request does **not** remove their `bookings`/`booking_disputes`/`case_events` rows, only their identity on those rows (`supabase/migrations/20260602083300_financial_retention_on_delete.sql:17-29`), per Swiss OR Art. 958f 10-year accounting retention. Don't "fix" this into a hard delete without checking that legal basis again.

**Where to look when changing it.**
- Adding a new cron: create the route under `app/api/cron/<name>/route.ts`, wrap its body in `withCronRun("<name>", ...)` (`lib/cron-run.ts`), add it to a `.github/workflows/cron-jobs.yml` job with the right `if: github.event.schedule` (reuse an existing cadence's job where possible so it doesn't cost an extra Actions job), and keep the `CRON_SECRET` bearer guard outside the wrapper.
- Changing alert behavior: `lib/error-report.ts` (routing/throttle) and `lib/alert-admin.ts` (the email itself); both must stay non-throwing.
- Changing what counts as healthy: `lib/health.ts`, keep `app/api/health/route.ts` a thin pass-through so `scripts/ring1c-kill-test.ts` can still exercise the probes directly.
- Changing backup scope/retention: `lib/backup/export.ts` (`BACKUP_TABLES`, `RETENTION_DAYS`), then re-run `scripts/db-backup-kill-test.ts` against the live throwaway prefix before trusting it.
- Fixing the daily-03-utc chain-blocking gap: either patch `app/api/admin/solen-score/recalculate/route.ts` to include `ok: true` in its response (and ideally move it under `withCronRun` for parity with every other cron), or restructure `.github/workflows/cron-jobs.yml:107-134` so the three downstream steps don't share fate with the first.
- Data retention changes: the `search-events-retention` `pg_cron` job lives in the DB (`supabase/migrations/20260606204021_search_phase6_learning_loop.sql:69-73`), not in app code — changing its cadence or window means a new migration plus an `apply_migration` call, and updating the file to match (this project never runs `supabase db push`/`reset`).

## 11. API surface & request conventions

**What it is.** `app/api/` is the entire server-side surface of Solen: 351 `route.ts` files across 48 top-level groups, all Next.js App Router route handlers. It is the one layer every browser fetch, dashboard action, Stripe webhook, and GitHub Actions cron job goes through to reach Postgres, Stripe, email/SMS, and the other external services.

**How it works.**

1. **Every request hits `middleware.ts` first** (project root, matcher excludes `_next/static`, `_next/image`, favicon, and static file extensions, `middleware.ts:245-249`). For `/api/*` paths it only does CORS: it echoes `Access-Control-Allow-Origin` back for `https://solen.ch`, `https://www.solen.ch`, and (dev only) `http://localhost:3000`, and short-circuits `OPTIONS` preflights with a 204 (`middleware.ts:46-73`). API routes get **no locale rewrite and no auth gate from middleware** — auth is each route's own job. Only page routes under `/{locale}/dashboard/**` get the auth/role redirect logic in the same file (`middleware.ts:148-222`): it calls `supabase.auth.getUser()` with a defensive 4s timeout (`middleware.ts:142-146`), and on any thrown error inside that block it now fails **closed** for dashboard paths (redirects to login) rather than falling through to a pass-through response (`middleware.ts:223-240`, a fix noted inline as a prior auth-bypass bug).
2. **Locale redirect** happens for non-API, non-locale-prefixed paths: `getLocaleFromRequest` checks the URL, then the `NEXT_LOCALE` cookie, then `Accept-Language`, then falls back to `defaultLocale` (`middleware.ts:6-32, 75-85`). This is why API routes are **locale-agnostic**: there is no `app/api/[locale]/...` anywhere, only `app/[locale]/...` for pages. A route handler never needs to know which of de/en/fr/it the caller is on unless it explicitly reads a `locale` query param or `Accept-Language` itself (e.g. email templates do this at the call site, not in middleware).
3. **Inside the route handler**, the standard shape is: `export const dynamic = "force-dynamic"` (290 of 351 files) plus `export const runtime = "nodejs"` or `"edge"` (248 files declare one explicitly; nodejs for anything touching Stripe SDK, Gemini SDK, or needing longer execution, edge for lightweight reads). The handler then builds a Supabase client:
   - `createServerSupabaseClient()` (`lib/supabase.ts:21-59`) for anything acting **as the calling user** — reads cookies via `next/headers`, wraps a `cookies()` call in try/catch because a malformed `Cookie` header can throw (`lib/supabase.ts:26-32`), and is RLS-scoped.
   - `createAdminSupabaseClient()` (`lib/supabase.ts:78-95`) for service-role work that must bypass RLS (webhooks, cron, admin aggregate reads). Both clients are typed against the generated `Database` type (`lib/database.types.ts`), so a phantom column/table is a compile error, not a silent `null` (`lib/supabase.ts:6-15`).
4. **Auth is centralized in `lib/auth/require.ts`**, a "return-or-response" pattern: `requireAuth()`, `requireAdmin()`, `requireSalonOwner(salonId)`, `requireRole(roles)` each either return `{ user, supabase, ... }` or a ready-made `NextResponse` (401/403/503) the caller returns directly (`lib/auth/require.ts:17-31, 51-63`). All of them call `supabase.auth.getUser()`, never `getSession()` — `getSession()` trusts the client-supplied cookie without verifying the JWT signature and is now hard-blocked in `app/**`/`lib/**` by the `no-getsession-authz-gate.py` PreToolUse hook (`_rules/SECURITY_RULES.md:13`, `_rules/CODE_SAFETY.md:193-197`). Many older routes still inline the same `supabase.auth.getUser()` + 401 check rather than calling `requireAuth()` (e.g. `app/api/bookings/route.ts:19-21`, `app/api/conversations/route.ts:8-10`) — both patterns are correct, `requireAuth()` is just the DRY version introduced after ~230 duplicated inline checks.
5. **The full security stack for a mutating route**, in order, per `_rules/SECURITY_RULES.md` Rule S1: feature-flag check (`checkFeatureEnabled`, `lib/feature-flags.ts`) → auth (`requireAuth`/inline `getUser()`) → ban check (`checkUserBanned`) → rate limit (`applyRateLimit` with a named `Ratelimit` instance from `lib/ratelimit.ts`: `generalLimiter` 30/min, `bookingLimiter` 5/hour, `messageLimiter` 10/min, `paymentLimiter` 3/hour, `adminLimiter` 20/min, all Upstash-Redis-backed and no-op if Upstash env vars are unset) → zod validation (`validateBody(schema, body)` from `lib/validations.ts`) → business logic. `app/api/bookings/route.ts:1-16` is the canonical example: it imports all of `applyRateLimit`/`bookingLimiter`/`getClientIp`, `checkFeatureEnabled`/`checkUserBanned`, `validateBody`/`createBookingSchema` before touching Postgres. Public unauthenticated GETs use IP-based rate limiting instead of a user id (`getClientIp(req)`, e.g. `app/api/analytics/track-view/route.ts:12-13`).
6. **Response shape is not fully standardized.** Success responses are always `NextResponse.json(...)`. Error responses lean on two competing conventions: `{ error, code }` (1356 occurrences across `app/api`) and `{ message, code }` (223 occurrences, e.g. `app/api/bookings/route.ts:21`, `app/api/conversations/route.ts:10`) — both are live in production simultaneously, so a frontend fetch helper cannot assume one key name project-wide; check the specific route or the shared `requireAuth`/`requireAdmin` helpers (which use `error`) versus older inline checks (which often use `message`). `_rules/CODE_SAFETY.md` Rule 11 documents this exact split and recommends returning both keys when changing an existing route's shape rather than picking one.
7. **Stripe webhooks** (`app/api/stripe/webhook/route.ts`) read the raw body with `req.text()` (never `req.json()`, needed for signature verification), verify `stripe.webhooks.constructEvent(body, sig, webhookSecret)` inside a try/catch that returns 400 on failure (`app/api/stripe/webhook/route.ts:18-35`), then use `createAdminSupabaseClient()` and an atomic idempotency claim against a `processed_webhook_events` table (unique-constraint insert, not check-then-insert, to close a race where a mid-handler throw could mark an event processed without actually completing it, documented inline at `app/api/stripe/webhook/route.ts:37-44`).
8. **Cron routes** (`app/api/cron/*`, 26 routes) are triggered by `.github/workflows/cron-jobs.yml`, not Vercel cron (migrated off Vercel; the workflow file's own header says so). Each scheduled job pings one or more `/api/cron/*` paths via a shared composite action `.github/actions/ping-cron` with a `Bearer ${CRON_SECRET}` header (`.github/workflows/cron-jobs.yml:41-45`); the route checks `authHeader !== \`Bearer ${env.CRON_SECRET}\`` and 401s otherwise (`app/api/cron/reminders/route.ts:19-22`, itself a deprecated 410-stub example that documents a real incident: a prior version's wide time window stole bookings from the real sender). The every-15-minute job also piggybacks a live-site health check (`curl .../api/health`) so a down site fails the GitHub Actions run and emails the owner (`.github/workflows/cron-jobs.yml:33-41`), avoiding a separate paid uptime job.
9. **Error handling convention** (`CLAUDE.md` "Error handling" + `_rules/CODE_SAFETY.md:133-147`): never `.catch(() => {})` — grep across `app/api` and `lib` confirms zero live occurrences, so this is actually enforced, not just aspirational. Log with `console.error("[Component] description:", err)` (150 of 351 route files call `console.error` directly; more via shared helpers). Payment flows must log + surface a user-visible error + retry option; auth flows log + redirect to login. `lib/error-report.ts`'s `reportError(scope, err, context)` is the shared top-level-catch call: it always `console.error`s, then fires a throttled (15 min per scope, in-memory per process) admin email via `lib/alert-admin.ts` so a real production failure reaches a human without flooding the inbox; it never throws itself (`lib/error-report.ts:22-33`). **Not every route follows this**: `app/api/metrics/global/route.ts:56-65` catches the whole Promise.all block and silently returns hardcoded fallback stats (`salons: 500, bookings_this_week: 10000, ...`) with no `console.error` call at all — a genuine violation of the "never swallow" rule found by reading the file, worth fixing if this route is touched again.
10. **Dev-only auth bypass**: `GET /api/dev/login?to=<path>` (`app/api/dev/login/route.ts`) mints a session for a seed test salon-owner fixture (`hiroseseiju@proton.me`, not the owner's real account) via `admin.auth.admin.generateLink({ type: "magiclink" })` then `supabase.auth.verifyOtp(...)`, writing session cookies onto a 307 redirect. Hard-gated to `process.env.NODE_ENV === "development"` — returns a bare 404 otherwise, so it cannot exist on the Netlify production build (`next build` sets `NODE_ENV=production`) (`app/api/dev/login/route.ts:11-21`). It uses a **relative** `Location` header on purpose so it still works behind a cloudflared tunnel where `req.url`'s host is `localhost` (`app/api/dev/login/route.ts:37-39`).
11. **Health/metrics/analytics** are three different things, not one system: `GET /api/health` (`app/api/health/route.ts`) is a dependency probe (`lib/health.ts`'s `runHealthProbes`) checking DB, Redis if configured, and required prod env vars, returning 200 only if every probe is ok-or-unconfigured and 503 if any hard-fails; it runs on `nodejs` explicitly because it needs the service-role client and `@upstash/redis` (`app/api/health/route.ts:8-9`). `GET /api/metrics/global` (`app/api/metrics/global/route.ts`) is the public homepage stat-strip (salon count, bookings, reviews, avg rating), cached 24h via `export const revalidate = 86400`, with silent fallback defaults on any query failure (see gotcha above). `app/api/analytics/*` (8 routes) is business analytics (platform, salon-level, staff-level, referrals, benchmarks, gift-card revenue) plus one public write endpoint, `POST /api/analytics/track-view`, which is unauthenticated, IP-rate-limited, and zod-validated (`app/api/analytics/track-view/route.ts:8-13`).

**Gotchas + invariants.**
- **Response error-key inconsistency is real and live**, not a stale worry: `{ error, code }` and `{ message, code }` both occur hundreds of times across current routes. A frontend consumer must check the specific route (or trust the shared `require*` helpers, which standardize on `error`) rather than assuming one shape project-wide. `_rules/CODE_SAFETY.md` Rule 11 recommends returning both keys when changing a live route's response shape, to avoid the DM Chat incident it documents (one route returned `{ data: profile }`, the frontend expected `profile` directly).
- **`app/api/metrics/global/route.ts` silently swallows its Promise.all failure** and returns hardcoded fallback numbers with no `console.error`, contradicting the project's own "never swallow" rule. Anyone touching this route should add the missing log.
- **`getSession()` is banned server-side** and hook-enforced (`no-getsession-authz-gate.py` blocks new `auth.getSession()` calls in `app/**`/`lib/**`). Only `auth.getUser()` (directly or via `lib/auth/require.ts`) is a valid identity check, because `getSession()` trusts an unverified, forgeable client cookie.
- **Middleware does not gate API routes**, only page routes under `/{locale}/dashboard/**`. Every route handler under `app/api/` is individually responsible for its own auth check; there is no global "you must be logged in to hit `/api/*`" backstop. A new route that forgets `requireAuth()` (or the inline equivalent) is silently public.
- **CORS in middleware only allows `solen.ch` / `www.solen.ch` (+ localhost in dev)** — any other origin gets a response with no `Access-Control-Allow-Origin` header, which the browser then blocks client-side; this is enforced per-request, not a build-time allowlist, so testing from a new preview domain requires updating `middleware.ts:48-51`.
- **Cron routes trust a shared secret, not user auth** — `CRON_SECRET` as a `Bearer` header, checked per-route (`env.CRON_SECRET` must be set or the route always 401s, `app/api/cron/reminders/route.ts:19-22`). A cron route with a badly-scoped query (as the deprecated `reminders` route's incident shows: a too-wide time window claimed bookings before the real handler could) can silently break a feature without ever erroring, because the route still returns 200.
- **Runtime choice matters for specific SDKs**: Gemini and Stripe SDK calls are pinned to `runtime = "nodejs"` with an inline comment explaining why ("crashes on Edge" / "Use Node runtime for Stripe") , don't move those routes to edge without checking the SDK's edge-compatibility first.
- **`.catch(() => {})` is a hard zero** across the codebase right now (verified by grep, not just documented as a rule) , if you ever find one while editing, it is new and should be treated as a regression, not a pre-existing pattern to match.
- **Rate limiters are no-ops if Upstash env vars are missing** (`lib/ratelimit.ts:8-13` casts `null as any` when `UPSTASH_REDIS_REST_URL`/`TOKEN` are unset) , don't assume rate limiting is active in every environment just because the code calls `applyRateLimit`.
- **`checkFeatureEnabled` caches for 30s per process** (`lib/feature-flags.ts:14-26`) , flipping a feature flag (including `maintenance_mode`) takes up to 30s to reach a warm serverless instance, not instant.

**Where to look when changing it.** For a brand-new route: read `_rules/SECURITY_RULES.md` Rule S1 first (the mandatory layer order: feature flag → auth → ban check → rate limit → zod validation → business logic) and `_rules/STRUCTURAL_RULES.md` Rule 42 (file-tree template: `app/api/[feature]/route.ts` alongside the page, component, types, and all 4 locale files). Run `npm run exists <keyword>` before creating the route at all (project `CLAUDE.md` exists-check protocol) , a hit means extend, not duplicate. Reuse `lib/auth/require.ts`, `lib/ratelimit.ts`, `lib/feature-flags.ts`, `lib/validations.ts` rather than reinventing any of them. For editing an existing route: read the whole file (these are frequently 100+ lines with inline incident comments explaining non-obvious ordering, like the Stripe webhook's idempotency claim or the cron `reminders` deprecation) before changing anything, per the project's "surgical edits only" rule.
