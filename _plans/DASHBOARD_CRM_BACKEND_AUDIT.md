## [CRITICAL] salon-crud-authz — spa/treatment-outcomes POST has zero ownership check, writing arbitrary data to any salon/client  (3/3, CONFIRMED)
`app/api/dashboard/spa/treatment-outcomes/route.ts:35`
- Defect: POST /api/dashboard/spa/treatment-outcomes only checks `session?.user` exists (any authenticated user, not necessarily a salon owner). It then takes `salon_id` and `client_id` directly from the request body with NO ownership verification (no getActiveSalon, no owner_id/admin-role check, no rate limit, no ban check), and inserts via the admin (RLS-bypassing) client. The sibling GET on the same file does the correct owner_id/admin check right above it, so the omission on POST is a copy/paste-style gap, not an intentional design.
- Scenario: Any logged-in user (including an ordinary customer account, not a salon owner) can POST { salon_id: '<any other salon's UUID>', client_id: '<any UUID>', satisfaction_rating, skin_before, skin_after, follow_up_notes, next_visit_date } to /api/dashboard/spa/treatment-outcomes and it is inserted verbatim into spa_treatment_outcomes for a salon/client they have no relationship to. Confirmed reachable: components-legacy/dashboard/spa/TreatmentOutcome.tsx (wired into app/[locale]/dashboard/spa-admin/page.tsx) posts exactly this shape with salon_id/client_id taken from client-side props, so the endpoint is live, not dead code. Impact: an attacker can inject fabricated skin-condition/medical-adjacent notes and satisfaction ratings into another salon's client records, or spam fake outcome rows against a competitor's clients.
- Fix: Resolve the caller's own salon via getActiveSalon(admin, user.id, 'id') (as the neighboring GET and the spa/rooms and spa/wellness-journal routes in the same directory already do) and use that resolved salon.id for the insert instead of trusting body.salon_id; also add checkUserBanned + applyRateLimit to match the GET/sibling routes.

## [HIGH] salon-crud-authz — nail/ai-history PATCH lets any authenticated user toggle is_saved on any salon's AI image, no ownership check  (3/3, CONFIRMED)
`app/api/dashboard/nail/ai-history/route.ts:36`
- Defect: The GET handler in this file verifies salon.owner_id === session.user.id or admin role before reading nail_ai_staging. The PATCH handler (toggle is_saved) in the same file only checks `session?.user` exists, then updates nail_ai_staging by `id` with the admin client and no ownership check at all linking that row's salon_id back to the caller.
- Scenario: Any authenticated user who has seen or can guess a nail_ai_staging row id (e.g. one shown in their own salon's history, or leaked in a support ticket / screenshot) can PATCH { id, is_saved: true|false } and flip the saved flag on another salon's staged AI nail-design image, corrupting that salon's saved-image gallery.
- Fix: Before the update, fetch the row's salon_id (admin.from('nail_ai_staging').select('salon_id').eq('id', id).single()) and verify it matches the caller's own salon via getActiveSalon (or owner_id/admin check), mirroring the GET handler directly above it in the same file.

## [HIGH] salon-crud-authz — GET /api/staff has no auth or ownership check at all, leaking commission_rate and permissions for any salon  (3/3, CONFIRMED)
`app/api/staff/route.ts:6`
- Defect: GET /api/staff?salon_id=xxx has no session check and no ownership check whatsoever, unlike every other salon-management route in this sweep. It returns `commission_rate` and `permissions` (both sensitive business/privilege data) for every staff member of the given salon_id.
- Scenario: An unauthenticated caller (or a competing salon owner) can call /api/staff?salon_id=<any-salon-uuid> for every salon on the platform and scrape each staff member's commission_rate and permissions array. Confirmed as the live/only backing endpoint for the dashboard staff list (called from app/[locale]/dashboard/settings/page.tsx, app/[locale]/dashboard/calendar/page.tsx, app/[locale]/dashboard/staff/page.tsx), so the UI assumes this is owner-scoped but the API enforces nothing.
- Fix: Add the same session + ownership pattern used by every sibling salon/staff route: require session.user, then verify salon.owner_id === user.id (or admin) for the requested salon_id before returning staff rows; alternatively drop commission_rate/permissions from the public shape and only include them once ownership is confirmed.

## [HIGH] staff-permissions — Staff-invite acceptance silently fails to link the new hire's account (RLS grant missing for the invited user)  (3/3, )
`app/api/staff/accept-invite/route.ts:85`
- Defect: accept-invite runs its staff_members writes through the RLS-bound `supabase` client (session-scoped, not admin). Live RLS on staff_members (verified via Supabase MCP execute_sql against project tocfnsmxmdxkrcmjzzdw) has exactly one INSERT policy (`staff_members_insert_4c9184_m`) and one UPDATE policy (`staff_members_update_4c9184_m`), and BOTH require `salons.owner_id = auth.uid()`. The person accepting an invite is never the owner, so: (a) the 'create new staff member' branch's INSERT (line ~92) is rejected by RLS and surfaces a 500; (b) the 'link existing named-placeholder staff member' branch's UPDATE (line ~85-88, `update({ user_id: user.id }).eq('id', namedStaff.id)`) has no error/row-count check at all -- under RLS an UPDATE whose USING clause doesn't match simply affects 0 rows with no error, so the call succeeds silently while staff_members.user_id is NEVER actually set.
- Scenario: Owner invites 'Anna' by name, and the dashboard had already created a placeholder staff_members row named 'Anna' (user_id NULL, is_active true, no permissions). Anna signs up, opens the invite link, and the API responds 200 with `{ staff_member_id, salon_id }` -- looks like success, and `profiles.staff_salon_id` really does get set (that write goes through the `admin`/service-role-adjacent success paths). But the staff_members.user_id linking UPDATE silently no-op'd under RLS, so Anna's staff_members row is still unlinked. Every staff self-service endpoint that resolves 'who am I' via `.eq('user_id', user.id)` (my-schedule GET/PUT, staff/services GET's staffSelf branch, staff/breaks, staff/time-off) now returns 403 'Not a staff member' for her forever, even though the invite flow told her she'd joined. For the no-existing-placeholder case (brand-new hire), the flow doesn't silently fail -- it hard-errors (500) on the INSERT, so staff onboarding via invite is broken for that path too.
- Fix: Either move the staff_members insert/update in accept-invite onto the admin (service-role) client -- the code already imports/uses `admin` elsewhere in the same file for the invite lookup and status update, so this is a small, scoped change -- or add a permissive RLS policy letting an authenticated user update/insert their OWN staff_members row (`user_id = auth.uid()` for update, or a narrower invite-token-gated insert policy). Also add explicit error/row-count checking on the linking UPDATE so a genuine RLS denial surfaces as an error instead of a silent no-op.

## [HIGH] dashboard-reads-logic — Booking reschedule has no atomic guard on the final slot-booking write — TOCTOU double-booking  (3/3, )
`app/api/bookings/[id]/reschedule/route.ts:120`
- Defect: The reschedule flow is check-then-act across four separate round trips with no transaction/lock: (1) SELECT availability_slots WHERE status='available' (line 58-65), (2) UPDATE old slot to available (74-78), (3) UPDATE bookings to point at the new slot (88-99), (4) UPDATE new slot to status='booked' (120-127) — and step 4's UPDATE has NO `.eq("status","available")` re-check, so it blindly overwrites the slot row regardless of what happened to it in between. The DB-level `prevent_double_booking` EXCLUDE USING gist constraint (supabase/migrations/20260328_prevent_double_booking_gist.sql) only fires on inserting a NEW overlapping row for the same staff_member_id; it does nothing here because the slot row already exists and is only having its status/booking_id columns flipped, not being inserted with an overlapping range.
- Scenario: Customer A reschedules into freed-up slot X (passes the availability check at line 58). Before A's flow reaches step 4, slot X gets legitimately booked by another path (a new customer booking it, or a second concurrent reschedule by customer B also targeting X after passing its own step-58 check). A's step-4 update at line 120-127 still runs unconditionally and overwrites slot X's booking_id back to A's booking, silently detaching whichever booking got there first from its slot (that customer's `bookings` row still shows slot_id=X, but availability_slots.booking_id no longer points back to them) — two customers now believe they hold the same appointment with the same staff member at the same time, and there is no server-side signal that anything went wrong (all responses return 200/success).
- Fix: Make the final slot claim conditional and verify it took effect, e.g. `.update({status:'booked', booking_id, booked_by}).eq('id', newSlot.id).eq('status','available').select()` and treat a zero-row result as a 409 conflict (roll back steps 2/3), mirroring the guard the initial booking-creation flow presumably already has.

## [MEDIUM] salon-crud-authz — services/import CSV endpoint accepts negative prices (bypasses the Zod min(0) enforced on the JSON create/update endpoints)  (3/3, CONFIRMED)
`app/api/services/import/route.ts:63`
- Defect: serviceCreateSchema/serviceUpdateSchema enforce price.min(0) on POST/PATCH /api/services, but the CSV import path parses price with `parseFloat(cols[priceIdx])` and only rejects it if `isNaN(price)`, a negative value like "-50" parses cleanly and is inserted as-is, with no min-0 check unlike its sibling create endpoint.
- Scenario: A salon owner (accidentally or otherwise) uploads a CSV with a negative price column value; the row is inserted into `services` with `price: -50`, bypassing the validation the rest of the write surface enforces. Downstream booking/payment code that assumes price >= 0 (deposit/commission calculations, Stripe amount conversion) can then be fed a negative amount.
- Fix: Reuse serviceCreateSchema (or at minimum add `if (price < 0) errors.push(...)`) on the parsed CSV price before pushing to servicesToInsert, matching the JSON create endpoint's validation.

## [MEDIUM] salon-crud-authz — staff/services POST does not verify service_ids belong to the caller's own salon before creating the assignment  (2/3, PLAUSIBLE)
`app/api/staff/services/route.ts:83`
- Defect: POST verifies the staff_member_id's salon is owned by the caller, but the service_ids array in the body is inserted into staff_services with no check that each service_id's salon_id matches staffMember.salon_id.
- Scenario: A salon owner can pass a service_id belonging to a different salon in the `service_ids` array; the resulting staff_services row cross-references another salon's service. Because /api/staff/[id]/profile's public GET joins `staff_services -> services(name_de, name_en, duration_minutes, price)`, this can surface another salon's service name/price/duration on this salon's staff public profile, a data-integrity/minor cross-tenant leak (not a data-modifying attack on the other salon's row, but incorrect/leaked pricing data displayed under the wrong salon).
- Fix: When building `rows`, first fetch services for the given service_ids and filter/reject any whose salon_id !== staffMember.salon_id (400 on mismatch), the same pattern services/reorder already uses (`.eq('salon_id', salon_id)` on every row touched).

## [MEDIUM] staff-permissions — staff_member_id is never validated against the target salon when creating availability slots -- lets an owner reference another salon's staff and pollute that salon's analytics  (3/3, )
`app/api/availability/manage/route.ts:23`
- Defect: All three slot-creation surfaces (`/api/availability/manage` POST line 23-30, `/api/slots` POST line 148-157, `/api/slots/bulk` POST line 93-124) verify `service_id` belongs to the caller's own salon before inserting, but none of them verify `staff_member_id` belongs to that same salon -- it's taken straight from the request body/validated schema and inserted as-is. The DB foreign key on availability_slots.staff_member_id only requires the id to exist in staff_members somewhere, not that it belongs to the slot's salon_id. `GET /api/staff?salon_id=<id>` (app/api/staff/route.ts) requires no authentication at all and returns every staff member's id for any salon_id, so any salon owner can trivially enumerate another salon's staff_member ids.
- Scenario: Owner of Salon A calls `GET /api/staff?salon_id=<Salon B's id>` (unauthenticated, works for anyone) to get Salon B's staff_member ids, then POSTs to `/api/slots` (or `/api/slots/bulk`, or `/api/availability/manage`) with their OWN salon_id but Salon B's staff_member_id. The insert succeeds. When a customer books that slot, `/api/bookings` copies `staff_member_id` from the slot into the new booking (app/api/bookings/route.ts line 420: `staff_member_id: staff_member_id ?? slot.staff_member_id`) without re-checking it belongs to the booking's salon. Salon B's owner then opens `/api/analytics/staff/[id]` for their own employee -- that endpoint sums `bookings` and `reviews` filtered ONLY by `staff_member_id` (no salon_id join/filter, app/api/analytics/staff/[id]/route.ts lines 57-74) -- and sees phantom bookings, revenue, and review counts that actually happened at a completely different, unrelated business. This is a cross-tenant data-integrity break with real 'wrong money' consequences for the analytics/reporting a salon owner relies on.
- Fix: In all three slot-creation routes, when staff_member_id is provided, look it up and assert `staff_members.salon_id === salon_id` (the same pattern already used for service_id in /api/slots and /api/slots/bulk), returning 400/403 on mismatch. Consider also scoping the analytics/staff/[id] booking and review queries by `salon_id` (derived from the staff member's own salon) as defense in depth, so even a legacy bad row can't cross-contaminate another salon's reported numbers.

## [MEDIUM] dashboard-reads-logic — nail/ai-history PATCH has no salon-ownership check — cross-salon write IDOR  (2/3, )
`app/api/dashboard/nail/ai-history/route.ts:36`
- Defect: GET on this route verifies salon ownership (lines 17-22, same pattern as the rest of the nail dashboard routes). PATCH, in the same file, only checks `session?.user` exists, then does `admin.from('nail_ai_staging').update({is_saved}).eq('id', id)` with no salon_id/ownership filter or check at all — any authenticated user can flip is_saved on any row in the table by guessing/enumerating its id.

## [LOW] salon-crud-authz — salon/last-minute-settings checks a phantom column (salons.user_id) and phantom table (salon_admins), permanently failing closed  (3/3, CONFIRMED)
`app/api/salon/last-minute-settings/route.ts:29`
- Defect: Both GET and POST authorize via `salon.user_id !== session.user.id`, but the live `salons` table has no `user_id` column (verified against _inventory/_db-columns.json: the ownership column is `owner_id`). GET additionally queries a `salon_admins` table that does not exist in the live DB snapshot at all. Every other salon-management route in this codebase uses `owner_id`.
- Scenario: Because the referenced column/table don't exist, the ownership check can never evaluate true for a legitimate owner, so every call fails closed (403/404) regardless of caller. This is not currently exploitable as an authz bypass (fails closed, not open) and the endpoint is not wired into any current page (no callers found in app/ outside this route file itself), so today it is dead/broken code rather than a live vulnerability, but it demonstrates the project's known phantom-column/phantom-table drift pattern and would silently break the feature the moment it's wired into a UI.
- Fix: Replace `salon.user_id` with `salon.owner_id` and drop (or replace with a real table) the `salon_admins` lookup, matching the owner_id + profiles.role=='admin' pattern used by every other salon route.

## [LOW] staff-permissions — Staff analytics 'view own stats' check compares the wrong ID space, so it can never actually grant self-access  (3/3, )
`app/api/analytics/staff/[id]/route.ts:45`
- Defect: `const isSelf = user.id === staffId;` compares the authenticated user's auth UID to `staffId`, which is the `staff_members.id` primary key -- a different ID space entirely (the correct join is `staff_members.user_id === user.id`, as done correctly in every other staff self-service route, e.g. my-schedule, staff/services). Since staff_members.id and auth.users.id are independently generated UUIDs, this condition is true only by astronomical coincidence.
- Scenario: A staff member (correctly linked, user_id set) tries to view their own analytics at `/api/analytics/staff/[staffMemberId]`. `isOwner` is false (they're not the salon owner) and `isAdmin` is false, and `isSelf` is also false because it's comparing `user.id` (their auth UID) to `staffId` (the staff_members row id, a different value) -- so they always get 403 'Forbidden' even though the intent of the `isSelf` branch is clearly to let staff view their own stats. This fails safe (denies access rather than granting it improperly), so it's a functional defect rather than an exploitable vulnerability, but it means the 'staff can view their own earnings/stats' feature is currently dead code.
- Fix: Replace with a lookup: fetch the staff_members row for `staffId`, and set `isSelf = staff.user_id === user.id` (the row is already being fetched at line 23-27 for the salon_id, just also select user_id and compare).

## [LOW] dashboard-reads-logic — barber-reminders/send does not verify client_id is actually a customer of the calling salon  (3/3, )
`app/api/dashboard/barber-reminders/send/route.ts:38`
- Defect: The route verifies the caller owns salon_id (lines 33-36), but never checks that client_id is a customer who has ever booked with that salon. It then calls `admin.auth.admin.getUserById(client_id)` (line 39) to resolve ANY registered user's email and sends them a marketing/reminder email branded with the salon's name, returning 404 'Client email not found' only when the id does not resolve to a real user.
- Scenario: A salon owner (or a compromised/malicious dashboard session) can pass an arbitrary user UUID as client_id and (a) spam that unrelated user with an unsolicited 'time for a new haircut' email via the platform's transactional sender, and (b) use the 200-vs-404 response difference to enumerate whether a given UUID corresponds to a real Solen account, all without that person ever having been a client of the salon.
- Fix: Before sending, verify a booking exists for (salon_id, client_id) — e.g. `bookings` with `user_id = client_id AND salon_id = salon.id` — and 403/404 otherwise, the same relationship the barber-reminders GET list already implies these targets come from.
