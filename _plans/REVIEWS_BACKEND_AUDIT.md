# Reviews / ratings backend — bug & gap audit (2026-07-09)

3 finders (submission-gating / rating-integrity / moderation-replies-google) x 3-skeptic verify. Several confirmed against the LIVE DB (pg_policies + information_schema + rolled-back-txn probes). 10 confirmed, 0 refuted.

## [CRITICAL] review-submit — Review-authenticity gate exists only in app code; live RLS lets anyone post unlimited fake reviews for any salon  (3/3, CONFIRMED)
`app/api/reviews/route.ts:38`
- Defect: The completed-booking check, automod (checkReview), rate limit, and banned-user check in app/api/reviews/route.ts (lines 16-58) are the ONLY defense against fake reviews. The live database's Row Level Security INSERT policy on `reviews` is `reviews_insert_own`: WITH CHECK (auth.uid() = user_id) -- verified via `select policyname, cmd, with_check from pg_policies where tablename='reviews'` against the live project (tocfnsmxmdxkrcmjzzdw). It does NOT require a completed booking, unlike the restrictive policy migrations 009_verified_reviews_rls.sql and 061_fix_review_inserts.sql intended to ship (their EXISTS-a-completed-booking WITH CHECK clause is not what is live today -- classic migration-file-vs-live-DB drift). Because `booking_id` is nullable (20260610_walkin_review.sql dropped NOT NULL) and Postgres treats NULL as distinct in the UNIQUE index, an account can insert an unlimited number of reviews with booking_id=null for the same salon.
- Scenario: Any authenticated user (a free signup, zero bookings) calls the Supabase REST endpoint directly with their own session JWT: `POST /rest/v1/reviews {salon_id: <any salon>, user_id: <self>, booking_id: null, rating: 1, comment: 'trash'}`. I reproduced this live (in a rolled-back transaction, no data left behind) by setting `role authenticated` + `request.jwt.claims.sub` to a real profile id and inserting a 1-star review for a salon that profile has zero relationship to: the INSERT succeeded and returned the new row. Since `is_hidden` defaults to `false` (confirmed via information_schema.columns) and the recompute trigger `reviews_update_salon_rating` fires on every INSERT and only filters `is_hidden=false`, the fake row is immediately public (app/api/reviews/salon/[salon_id]/route.ts also just filters is_hidden=false) and immediately counted into salons.average_rating/review_count. A competitor or bot can therefore tank or inflate any salon's rating at will, completely bypassing the booking-ownership check, automod, rate limiting, and the banned-user gate -- none of which exist at the DB layer.
- Fix: Restore a restrictive INSERT policy on public.reviews requiring EXISTS a bookings row with matching user_id/salon_id and status IN ('confirmed','completed') OR the caller is service_role (for Google-sourced/admin inserts), matching what 061_fix_review_inserts.sql already wrote but is evidently not the live policy. Re-apply via idempotent migration and verify live with the same pg_policies query used here, not by re-reading the migration file.

## [CRITICAL] rating-integrity — Review moderation is completely broken live: writes to a column that does not exist in production  (3/3, CONFIRMED)
`app/api/admin/reviews/[id]/route.ts:30`
- Defect: supabase/migrations/060_review_moderation_status.sql adds reviews.moderation_status and reviews.removal_reason, but its own comment flags it as a MANUAL step ('Run this in Supabase SQL Editor before deploying Phase 2 code'). I queried the LIVE production schema directly (Supabase MCP execute_sql, project tocfnsmxmdxkrcmjzzdw, information_schema.columns for table reviews) and confirmed neither column exists on the live reviews table. Every admin moderation action (PATCH /api/admin/reviews/[id] with a moderation_status value) builds one .update() call containing moderation_status (and often removal_reason) alongside is_hidden/is_flagged. Because PostgREST issues this as a single SQL UPDATE with all keys in one SET clause, the nonexistent column makes Postgres reject the WHOLE statement (42703 undefined column) -- so is_hidden never gets set either. The same applies to POST /api/reviews/[id]/flag (app/api/reviews/[id]/flag/route.ts:62-71), which bundles is_flagged + flag_reason + moderation_status:'under_review' into one .update(). Both routes 500 every time they're invoked.
- Scenario: A salon owner clicks 'Flag this review' on an abusive 1-star review -> POST /api/reviews/[id]/flag -> the .update({is_flagged:true, flag_reason, moderation_status:'under_review'}) call errors with 'column reviews.moderation_status does not exist' -> updateErr is truthy -> route returns 500 -> is_flagged is NEVER set (the whole statement rolled back), so the review never even reaches an admin queue. Same failure mode when an admin tries to approve/remove a flagged review via PATCH /api/admin/reviews/[id]: the entire update (including is_hidden) fails, so a fake or abusive review can never be soft-hidden via the intended moderation flow. The only moderation action that still works is the admin's hard DELETE, which has its own aggregate-drift bug (see next finding).
- Fix: Apply the missing migration (add moderation_status + removal_reason to the live reviews table, matching 060_review_moderation_status.sql) before these two routes can function at all. Also add integration coverage that actually exercises a real PATCH/POST against a dev DB so a phantom-column regression like this surfaces immediately instead of only in production logs.

## [CRITICAL] review-moderation — Phantom moderation_status column silently breaks review flagging AND admin moderation end-to-end  (3/3, CONFIRMED)
`app/api/reviews/[id]/flag/route.ts:62`
- Defect: The reviews table in the LIVE database does not have a moderation_status (or removal_reason) column. Migration 060_review_moderation_status.sql (dated 2026-03-23) was apparently never applied to production: (1) app/[locale]/reviews/page.tsx:12-15 contains a first-party code comment explicitly stating 'The live DB lacks the moderation_status column (migration 060 unapplied, schema drift)'; (2) the live column snapshot _inventory/_db-columns.json lists only 16 columns for reviews (admin_response, admin_response_at, booking_id, comment, created_at, flag_reason, id, is_flagged, is_hidden, rating, salon_id, salon_response, salon_response_at, staff_member_id, user_id, walkin_queue_id), no moderation_status/removal_reason; snapshot was refreshed 2026-07-06, well after the migration file's date. Despite this, app/api/reviews/[id]/flag/route.ts (line 62-68) bundles moderation_status:'under_review' into the SAME .update() call as is_flagged/flag_reason, and app/api/admin/reviews/[id]/route.ts PATCH (lines 31-51) bundles moderation_status/removal_reason into the SAME .update() call as is_hidden/is_flagged. A single Postgres UPDATE statement referencing a nonexistent column fails atomically (PostgREST returns a schema-cache error), so NONE of the fields in that call persist, not just the phantom one.
- Scenario: A salon owner clicks 'Flag' on a negative review of their own salon (app/[locale]/dashboard/reviews/page.tsx handleFlag, calls POST /api/reviews/[id]/flag). The update() call errors on the missing moderation_status column; is_flagged and flag_reason never persist either, since it's one atomic statement. The client never checks response.ok, so the owner sees no error and believes the review was reported. The admin's flagged-reviews queue (GET /api/admin/reviews?flagged=true, filtered on is_flagged=true) never receives it. Separately, even if a review WERE somehow flagged, the admin's 'Approve' and 'Hide' buttons in app/[locale]/dashboard/review-moderation/page.tsx (handleAction) PATCH /api/admin/reviews/[id] with moderation_status set, which also errors for the same reason: is_hidden is never actually set to true on 'Hide', and is_flagged is never cleared on 'Approve'. The admin dashboard's own client code (handleAction) also never checks response.ok, so no error is surfaced there either. Net effect: the entire review-flag-and-moderate safety mechanism the codebase explicitly built for 'ToS §7.2 legal defensibility' (per migration 060's own comment) is completely non-functional in production, silently, with no error visible to any user. The only working way to remove a bad review is the separate hard DELETE endpoint, which does not go through this code path.
- Fix: Apply migration 060_review_moderation_status.sql to the live DB (adding moderation_status + removal_reason with backfill default 'active'), or until it's applied, strip moderation_status/removal_reason out of both .update() payloads so is_flagged/flag_reason/is_hidden continue to work on the columns that do exist. Also add response.ok checks (with a visible error toast) to handleFlag and handleAction on both dashboard pages so a future silent DB error is never invisible to the operator again.

## [HIGH] review-submit — Review moderation removal is fully broken in production: writes to a phantom `moderation_status` column  (3/3, CONFIRMED)
`app/api/reviews/[id]/flag/route.ts:62`
- Defect: app/api/reviews/[id]/flag/route.ts (lines 62-71) and app/api/admin/reviews/[id]/route.ts PATCH (lines 30-51) both write a `moderation_status` field to the `reviews` table. That column does not exist on the live database: `select column_name from information_schema.columns where table_name='reviews'` (live project) lists no `moderation_status` and no `removal_reason`. Migration 060_review_moderation_status.sql, which would add both columns, contains an explicit unactioned instruction: '⚠️ MANUAL STEP: Run this in Supabase SQL Editor before deploying Phase 2 code.' -- it was checked into the repo but never actually applied to the live database.
- Scenario: A salon owner flags a defamatory/fake review -> POST /api/reviews/[id]/flag executes `.update({ is_flagged: true, flag_reason, moderation_status: 'under_review' })`; Postgres rejects the whole statement with 'column "moderation_status" of relation "reviews" does not exist' before any row is touched, so the route returns a 500 and NOTHING is flagged (not even is_flagged). Separately, an admin trying to mark a review 'removed' via PATCH /api/admin/reviews/[id] hits the same phantom column and the update fails outright -- `is_hidden` (the only thing that would actually hide the review from the public listing/average, per is_hidden=false filters everywhere and the reviews_update_salon_rating trigger) can never be set to true through this path. The only working moderation action left is the admin hard-DELETE endpoint, which permanently destroys the review with no removal_reason/audit trail -- the very thing migration 060's own comment says is needed 'for ToS §7.2 legal defensibility'. Net effect: no fake, defamatory, or competitor-planted review can ever be hidden (only permanently deleted, losing the record), and the salon-owner report flow is dead on arrival.
- Fix: Apply migration 060_review_moderation_status.sql's ALTER TABLE against the live database (idempotent apply_migration), then verify with information_schema that moderation_status/removal_reason exist before relying on either route again.

## [HIGH] rating-integrity — average_rating/review_count are never recomputed on review UPDATE or DELETE -- only on new-review INSERT  (3/3, CONFIRMED)
`supabase/migrations/014_new_schema.sql:414`
- Defect: The only DB-level aggregate trigger, reviews_update_salon_rating (014_new_schema.sql:414-417), fires 'AFTER INSERT' only and was never extended to UPDATE or DELETE in any later migration (grepped every migration referencing update_salon_rating/CREATE OR REPLACE FUNCTION; 014 is the sole definition). The only other writers of salons.average_rating/review_count are inline recompute blocks inside the two 'submit a new review' POST handlers (app/api/reviews/route.ts:123-144 and app/api/walkin/review/route.ts:92-108) -- both only run as a side effect of a brand-new review being created. Meanwhile RLS grants real UPDATE/DELETE capability on reviews directly to end users (reviews_update_own_48h and reviews_delete_own, supabase/migrations/029_review_policies.sql:4-11, callable straight from the Supabase client, not gated behind any Next.js route) and to admins (reviews_delete_admin, same file, plus the hard DELETE in app/api/admin/reviews/[id]/route.ts:58-80).
- Scenario: Admin hard-deletes an abusive review via DELETE /api/admin/reviews/[id] (the one moderation action that actually works given the CRITICAL finding above). The row is gone from the reviews table, but salons.average_rating and review_count are untouched -- the storefront keeps showing the polluted rating/count computed before the deletion, indefinitely, until pure chance brings a new legitimate review for that same salon (which finally triggers a fresh recompute). Equally, a customer can directly call supabase.from('reviews').update({rating:1}).eq('id', reviewId) within 48h of posting a 5-star review (RLS permits it, no API route required) -- the salon's public average_rating stays frozen at the value baked in when the 5-star was originally inserted.
- Fix: Extend the trigger to AAFTER INSERT OR UPDATE OR DELETE and use a statement-level or FOR EACH ROW form that handles OLD.salon_id on delete, or add an explicit recompute call to every route that can mutate/delete a review (the two admin routes at minimum). Recompute logic should live in one place, not be duplicated ad hoc inside each 'create review' handler.

## [HIGH] review-moderation — salons.average_rating / review_count never recomputed after an admin deletes or hides a review  (3/3, CONFIRMED)
`app/api/admin/reviews/[id]/route.ts:51`
- Defect: The only DB trigger that recomputes salons.average_rating/review_count (migration 014, reviews_update_salon_rating) fires AFTER INSERT only and is unfiltered by is_hidden; it only ends up correct because the two app-level insert paths (app/api/reviews/route.ts lines 123-143, app/api/walkin/review/route.ts lines 92-108) immediately re-run the computation filtered on is_hidden=false, overwriting the trigger's naive value. Neither app/api/admin/reviews/[id]/route.ts's DELETE handler (line 76) nor its PATCH handler (lines 30-52, which sets is_hidden via moderation_status, once Finding 1 is fixed) calls any recompute. No cron job backstops this (checked .github/workflows/cron-jobs.yml and every app/api/cron/* route; none touches average_rating).
- Scenario: A salon has 10 reviews averaging 4.5 stars, one of which is a fake/fraudulent 5-star review an admin discovers and permanently DELETEs via DELETE /api/admin/reviews/[id]. The delete succeeds (this endpoint doesn't reference the phantom moderation_status column), but salons.average_rating and review_count are never recalculated: the public-facing rating stays at the old value computed with 10 reviews, including the deleted one, indefinitely, until some unrelated new customer completes a booking and submits a fresh review (which triggers the only recompute code path that exists and happens to also fix the historical drift as a side effect). For a low-traffic salon this can mean the salon's average_rating and review_count shown on search results, salon cards, and the salon page are silently wrong for weeks or months after every admin moderation action, in either direction (understating an unfairly-removed bad review's negative pull, or overstating review_count after any hide/delete).
- Fix: After both the DELETE and the PATCH (is_hidden change) branches in app/api/admin/reviews/[id]/route.ts, re-run the same is_hidden=false-filtered average/count recompute already used in app/api/reviews/route.ts (factor it into a shared helper, e.g. lib/reviews/recompute-salon-rating.ts, and call it from all three write paths: POST /api/reviews, POST /api/walkin/review, and PATCH/DELETE /api/admin/reviews/[id]).

## [MEDIUM] rating-integrity — Aggregate recompute silently skips resetting to zero when a salon's visible review set becomes empty  (3/3, CONFIRMED)
`app/api/reviews/route.ts:131`
- Defect: Both recompute call sites guard the salons/staff_members UPDATE with `if (stats.length > 0)` (app/api/reviews/route.ts:131) and `if (salonRows.length > 0)` (app/api/walkin/review/route.ts:94), so when the visible (is_hidden=false) review set for a salon is empty, the UPDATE is skipped entirely -- average_rating/review_count are left at whatever stale value they held before, instead of being reset to 0.
- Scenario: A salon has exactly one review (5 stars, avg=5.0, count=1). That review turns out to be spam and gets hidden (is_hidden=true) via whatever moderation path is working. If no new review for that salon is ever submitted afterward, the recompute code that would run inside the next insert never fires, so the salon keeps displaying '5.0 (1)' to every visitor forever, even though zero visible reviews actually exist.
- Fix: Remove the length>0 guard, or explicitly set average_rating:null/0 and review_count:0 in the else branch so an empty visible-review set is reflected honestly.

## [MEDIUM] rating-integrity — DB trigger computes the aggregate over ALL rows, with no is_hidden filter, unlike the app-level recompute  (3/3, CONFIRMED)
`supabase/migrations/014_new_schema.sql:405`
- Defect: update_salon_rating() (014_new_schema.sql:402-412) runs `SELECT AVG(rating)... FROM reviews WHERE salon_id=NEW.salon_id` with no WHERE is_hidden=false clause. is_hidden was added later in 021_review_moderation.sql, but the trigger function was never redefined to account for it. It is currently masked in practice because the app code in app/api/reviews/route.ts and app/api/walkin/review/route.ts always overwrites the trigger's result immediately after, using the correct is_hidden=false filter -- but the trigger itself, taken alone, is wrong, and any future write path that inserts into reviews without going through those two specific routes (a script, a seed, a new feature, an admin bulk-import) will have hidden/spam reviews baked straight into the public-facing average_rating/review_count via the trigger, with no app-level correction to catch it.
- Scenario: A future bulk-import or admin tool inserts reviews directly (bypassing app/api/reviews and app/api/walkin/review) -- the trigger fires and computes the aggregate including any is_hidden=true rows for that salon, and nothing subsequently corrects it since only those two specific POST handlers apply the is_hidden filter.
- Fix: Redefine update_salon_rating() to filter `WHERE salon_id = NEW.salon_id AND is_hidden = false`, and extend it to fire on UPDATE/DELETE too (folds into the HIGH finding above), so the DB-level trigger is the actual single source of truth instead of being silently patched over by duplicated app code in two places.

## [LOW] review-submit — Duplicate, lower-precision average_rating recompute races the DB trigger that already does it correctly  (3/3, CONFIRMED)
`app/api/reviews/route.ts:123`
- Defect: POST /api/reviews (lines 123-143) and POST /api/walkin/review (lines 92-104) both manually re-select all is_hidden=false reviews for the salon and re-write salons.average_rating/review_count (plus staff_members.average_rating in the walkin route) via the admin client immediately after insert. The live DB trigger `reviews_update_salon_rating` (confirmed via pg_trigger/pg_get_functiondef: `AFTER INSERT OR DELETE OR UPDATE ... FOR EACH ROW`) already does exactly this, atomically, inside the same transaction as the write, filtering is_hidden=false and rounding to 2 decimals via ROUND(avg,2). The app-side recompute runs afterward in a separate transaction and rounds to 1 decimal (Math.round(avg*10)/10), so it always overwrites the trigger's more precise value with a coarser one and performs 2 extra round-trip queries per review submission for no benefit.
- Scenario: Two reviews for the same salon land with ratings that average to e.g. 4.26: the trigger correctly stores 4.26, then the app code's manual recompute (same transaction set, just after commit) overwrites it with 4.3 -- a small but avoidable precision loss, plus wasted DB round-trips on every single review write.
- Fix: Delete the manual recompute blocks in both routes now that the trigger is confirmed correct and covers INSERT/UPDATE/DELETE; rely on the trigger as the single source of truth for average_rating/review_count (and add an equivalent trigger for staff_members if per-staff recompute needs to stay out of the API layer).

## [LOW] rating-integrity — average_rating precision is truncated to 1 decimal despite a numeric(3,2) column  (3/3, CONFIRMED)
`app/api/reviews/route.ts:136`
- Defect: salons.average_rating is numeric(3,2) (014_new_schema.sql:98, 2 decimal places), but both write sites round to 1 decimal place: `Math.round(avg * 10) / 10` (app/api/reviews/route.ts:136 and app/api/walkin/review/route.ts:96,103). A true average like 4.34 is stored/displayed as 4.3.
- Scenario: A salon with ratings [5,5,5,4] has a true average of 4.75 -> stored correctly either way in this example, but a salon with [5,5,5,5,4,4,4] (true avg 4.4286) is stored as 4.4 instead of the schema-supported 4.43 -- not a security bug, just an avoidable precision loss versus what the column was designed to hold.
- Fix: Round to 2 decimals (Math.round(avg * 100) / 100) to match the column's numeric(3,2) precision, or move this rounding into the DB trigger so it's computed once, consistently.
