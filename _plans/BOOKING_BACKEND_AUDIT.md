# Booking flow backend — bug & gap audit (2026-07-09)

Method: 1 orchestrator pass over the core write path (personally verified against live DB + code) + 4 parallel adversarial read-only backend agents (payment/webhook, mutations/state, availability/slots/cron, walk-in/queue) + a running sub-flow verification workflow (recurring/group/waitlist/guest/express-rebook/admin-disputes — results appended when it lands). Every CRITICAL and the top HIGHs were re-verified by the orchestrator against the actual code. Confidence tags: **CONFIRMED** = traced in code; **PLAUSIBLE** = needs a runtime/concurrency trigger.

Line numbers are as-read on 2026-07-09; re-confirm before editing (post-audit drift).

---

## Root-cause themes (fix the theme, not just the instance)

1. **Check-then-act with no DB guard** (the single biggest cluster). The repo already HAS the correct pattern — the group-booking RPC does `SELECT … FOR UPDATE` + status check + `RAISE` (migration `071:145-158`). The single-booking create, reschedule, and the Stripe webhook do NOT use it. Instances: #2, #4, #6, #10, #17, #23.
2. **Full-prepay model mismatch.** Booking PIs capture in full (`webhook:143-153`, `payment_status='paid'`), but the cancel/fee code was written for a save-card-no-prepay world → customers lose their prepayment on cancel. Instances: #1, #15, #19.
3. **Frozen policy_snapshot ignored.** Booking freezes the consented cancellation/no-show terms in `policy_snapshot`; the cancel route reads the salon's LIVE columns instead. Instance: #4.
4. **Timezone convention split.** Cron stores true UTC instants; every manual dashboard slot-create stores wall-clock-as-UTC. Instances: #8, #34.
5. **GIST double-booking gaps.** The exclusion constraint can't catch a same-row re-flip (#2) or NULL staff_member_id (#9).

## CRITICAL

### 1. Customer cancellation refunds NOTHING and charges a fee on top (full money loss) — CONFIRMED
`app/api/bookings/[id]/cancel/route.ts:143-210`. Bookings are full-prepay. The `isCustomer` branch computes `feeCents`, sets `status='cancelled'`, and calls `chargeFee(...)` (an *additional* off-session debit, :183) but never calls `issueRefund` — `refundResult` stays `{refundAmount:0}` (:115, overwritten only in the salon-owner branch :116-141). The route's own GET preview (:42-66) promises "you'll get back CHF X".
- Free-cancel window (fee=0): booking cancelled, no refund → customer loses 100% of prepaid.
- Late (fee>0): extra fee debited on top, still no refund → customer out prepaid + fee.
Fix: on the customer branch, `issueRefund(paid_amount − feeCents)` and NET the fee out of the prepayment (don't re-charge the card).

### 2. Non-atomic single-booking slot flip → double-booking / double-charge on one slot — CONFIRMED (orchestrator-verified)
`app/api/bookings/route.ts:156` reads slot `.eq("status","available")`; INSERT `:409`; flip `:471-474` `update({status:'booked'}).eq("id",resolvedSlotId)` with NO `status='available'` guard, no row-count check, no `FOR UPDATE`. `bookings.slot_id` has NO unique (migration `014:230`, ON DELETE RESTRICT). GIST `prevent_double_booking` can't catch a same-row re-flip. Duplicate guard (:389-405) only keys on user_id/guest_phone → two DIFFERENT customers race through.
- In-person path (`status='confirmed'` instant): two real confirmed bookings, one chair.
- Online-pay path: partially saved by `booking-pay-intent:275` (rejects if `slot.booking_id !== booking.id`) → loser gets a payment error + an orphaned pending row.
Fix: `UPDATE … SET status='booked' WHERE id=? AND status='available'`, treat `rowCount===0` as 409 + delete the just-inserted booking; or route through a `FOR UPDATE` RPC like the group path.

## HIGH

### 3. Webhook `payment_failed` frees a PAID slot on out-of-order Stripe events → double-booking — CONFIRMED (orchestrator-verified)
`app/api/stripe/webhook/route.ts:429-433` guards the booking update advance-only (`.in("payment_status",["pending","none","card_saved"])`) but `:435-436` frees the slot unconditionally (`.update({status:'available'}).eq("id",slot_id)`). Stripe doesn't guarantee order; one PI can emit failed+succeeded (decline→retry). If `succeeded` lands first (slot→booked, booking→paid), a late `payment_failed` no-ops the booking but forces the slot back to available → paid booking + free slot → 2nd customer books it. Fix: only free the slot when this handler actually cancelled the booking.

### 4. Cancellation fee read from LIVE salon columns, not the frozen `policy_snapshot` — CONFIRMED
`cancel/route.ts:148-153` reads `salon?.cancellation_fee_type/value/free_cancel_hours`. Booking froze these in `policy_snapshot` (`bookings/route.ts:376-383`); the no-show cron correctly uses the snapshot, the cancel route ignores it. `chargeFee`'s consent gate only checks `policy_accepted_at` EXISTS, not that the amount matches. Salon flips fee from free→CHF50 after booking → customer charged terms they never agreed to. Fix: read fee terms from `booking.policy_snapshot` (fallback to live only when null).

### 5. Reschedule has NO booking-status guard → cancelled/completed booking re-occupies inventory — CONFIRMED
`app/api/bookings/[id]/reschedule/route.ts` (POST). Only actor + 24h-lead checks; nothing checks `booking.status`. A cancelled booking (slot already freed) rescheduled → marks a fresh slot `booked` with a cancelled booking's id = dead inventory. Completed bookings can be pushed to the future. Fix: `if (status !== 'confirmed' && status !== 'pending') return 400`.

### 6. Reschedule new-slot claim is TOCTOU (no `status='available'` guard) → double-book — CONFIRMED
`reschedule:58-65` SELECTs available slot; `:120-127` marks booked `.eq("id",newSlot.id)` only. Two concurrent reschedules both pass the SELECT → both write the slot; second overwrites `booking_id`, first customer silently displaced. Fix: compare-and-set on status, 0 rows → 409.

### 7. Cron computes one duration per staff → wrong `ends_at` for every non-first service → physical overlap — CONFIRMED
`app/api/cron/generate-slots/route.ts:114-116` takes `slotDuration` from `staffServices[0]` only; `:164-189` inserts every service row with `ends_at = slotStart + firstServiceDuration`. Staff-service order is nondeterministic. A 90-min colour behind a 30-min cut gets `ends_at` 30 min out → non-bundle booking copies `slot.ends_at` (`bookings:425`) → GIST reserves only 30 min → next slot bookable → real overlap. Fix: set each row's `ends_at` from its own service's duration+buffer.

### 8. Timezone split: dashboard-created slots stored at the wrong instant — CONFIRMED
Cron stores true UTC (`generate-slots:15-23` `zurichWallClockToUtc`); manual paths store naive wall-clock-as-UTC: `POST /api/slots:137-145`, `/api/slots/bulk:28-30,120-121`, `PATCH /api/slots/[id]:54-57`. `starts_at` is timestamptz; consumers format in Europe/Zurich assuming true UTC. Owner adds a 09:00 slot → customers see 11:00, can bucket to the wrong day. Fix: convert owner-picked Zurich wall-clock to a true UTC instant in the manual paths (reuse `zurichWallClockToUtc`).

### 9. GIST double-booking constraint ignores NULL staff_member_id → no DB backstop for null-staff salons — CONFIRMED (reachability PLAUSIBLE)
`20260328_prevent_double_booking_gist.sql:7-10` (`staff_member_id WITH =`); GIST ignores NULL keys. Null-staff slots are creatable via `/api/slots`, `/bulk`, `/availability/manage`, and bookings resolve `staff_member_id ?? slot.staff_member_id` (can stay null). For salons listing availability without staff assignment, overlapping booked null-staff slots never conflict → only the racy app check (#2) protects. Fix: require not-null staff (or a synthetic resource id) on booked slots.

### 10. Concurrent different-amount refunds both fire at Stripe, only one recorded → silent over-refund — PLAUSIBLE
`lib/bookings/issue-refund.ts:134,151,176-210`. Stripe idempotency key + CAS are both keyed on `staleRefunded`; two callers reading `staleRefunded=0` with different `amountCents` → different keys → BOTH `refunds.create` fire, only one CAS commits. 4+ call sites (salon refund, admin dispute-action, PATCH cancel, salon-cancel). Fix: serialize per-booking (row lock/RPC), or make the key+CAS independent of amount.

### 11. `resequence_walkin_queue` no-ops whenever a chair is occupied → queue positions never compact — CONFIRMED
Live fn ranks only `status='waiting'` rows to 1..N, but partial unique index `uq_walkin_queue_salon_position` spans `status IN ('waiting','in_chair')`. With A in_chair pos 1 + waiting rows, a departure renumbers a waiting row to pos 1 = collides with A → `23505` → whole UPDATE aborts, caught + logged "resequence failed". Fires on essentially every departure while someone is served. Customer-visible `position` stays inflated. Fix: rank over `status IN ('waiting','in_chair')` (in-chair first) OR drop in_chair from the index predicate — the two must match.

### 12. Referral reward + credits issued at booking CREATE, before payment (online-pay) → credit farming — CONFIRMED
`bookings/route.ts:560-631` runs at creation, guarded `if (referral_code && user)`, counts `.eq("status","confirmed")`. Online-pay booking is `pending` → not counted → first-booking check passes → referral completed + `user_credits` issued to referrer + referee BEFORE payment. Webhook does NOT handle referrals (no paid-gating, no reversal on abandon). Real spendable credit for a booking that may never be paid. Fix: move referral completion to the webhook payment_succeeded path.

## MEDIUM

### 13. Duplicate-booking guard misses `pending_approval` → manual-approval salons get duplicates — CONFIRMED
`bookings/route.ts:395` dup guard `.in("status",["pending","confirmed"])`; manual-approval bookings are `pending_approval` (:360). Guard never fires there → clicking back repeatedly creates multiple bookings (auto-assign grabs another stylist's slot at the same time) — the exact scenario the guard was built for. Fix: add `pending_approval` (+ arguably `deposit_held`).

### 14. Non-23P01 slot-flip error swallowed → confirmed booking with an unbooked, re-bookable slot — CONFIRMED
`bookings/route.ts:475-483` rolls back only on `23P01`; any other error → `console.error` + returns 201 with booking created but slot still `available` (and `booking_id`/`booked_by` never set, which also disarms the delete-cancel branch of #20). Fix: roll back the booking on any slot-flip error.

### 15. Two divergent customer-cancel paths with opposite money behavior — CONFIRMED
PATCH `bookings/[id]/route.ts:149-177` issues a ToS 50%/100% REFUND and charges no fee (and ignores the salon's configured fee); `/cancel` charges a fee and refunds nothing (#1). Customer outcome differs by the full booking value depending on which the client wired. Fix: collapse to one canonical customer-cancel path; retire the PATCH `cancelled` branch (its own comment calls it "legacy fallback").

### 16. PATCH lets booking owner self-set completed/no_show/cancelled, no transition guard — CONFIRMED
`bookings/[id]/route.ts:57-116`. Schema enum `["completed","no_show","cancelled"]`, gate only requires owner. Customer can PATCH own booking to `completed` (opens the salon-upcharge window) or `no_show`. Re-cancelling an already-cancelled booking hits the `else` (:183-185), clobbering `payment_status` refunded→none and re-running strike evaluation. Fix: per-status role checks (only salon sets completed/no_show) + a current-status guard.

### 17. Reschedule `bookError` rollback leaves booking pointing at an `available` slot → double-book — CONFIRMED
`reschedule:129-150`. On bookError the rollback repoints the booking to the old slot and frees newSlot but never re-marks the OLD slot `booked` (freed at :75-78). The `updateError` rollback (:101-110) does; this branch doesn't. Net: booking → an available, booking_id=null slot another customer can book. Fix: re-book the old slot in this rollback too.

### 18. Reschedule slot lookup ignores service_id/staff + `.single()` → wrong service / spurious 409 — CONFIRMED
`reschedule:58-72` matches ANY available slot in the window for the salon; booking keeps its original service/staff. `.single()` errors (→ 409) whenever >1 staff has an open slot in the window → reschedule fails at busy salons. Fix: filter by the booking's service_id/staff (or duration), use `.limit(1).maybeSingle()`.

### 19. `quick-action` public cancel: no refund/fee + silent RLS no-op + no token-minting site — CONFIRMED (latent)
`bookings/[id]/quick-action/route.ts:57-76` cancels + frees slot with no refund/fee (strands prepaid money). Uses RLS client; anon has no bookings policy → SELECT null → 404, or UPDATE matches 0 rows yet still responds `{result:"cancelled"}`. No site mints the `bookingId:action:expiry:hmac` token anywhere → latent/likely-dead public mutation. Fix: route through canonical cancel + service-role after HMAC verify, or delete.

### 20. Deleting a BOOKED slot 500s and half-completes (FK RESTRICT) — CONFIRMED (schema); runtime PLAUSIBLE
`app/api/slots/[id]/route.ts:18-27` and `availability/manage/[slot_id]/route.ts:28-49` cancel the booking (keeps `slot_id`) then DELETE the slot; `bookings.slot_id` is ON DELETE RESTRICT → `23503` → 500. Booking cancelled + email sent, then delete throws; slot stays `booked` pointing at a cancelled booking. Fix: null/re-point the booking's slot_id first, or flip the slot to available instead of deleting; wrap in a transaction.

### 21. Cron ignores `salons.vacation_start/end` → phantom availability during vacation — CONFIRMED
`generate-slots:46-59` reads only `salon_closures` + `staff_time_off`. Vacation Mode writes `salons.vacation_start/end`, honored only by the booking guard + `unavailable-dates`. Cron still generates `available` slots across the vacation → phantom calendar slots (blocked only at commit). Fix: add `salons.vacation_start/end` to the cron skip set.

### 22. `last-minute` feed leaks inactive / unlisted / test salons — CONFIRMED
`app/api/slots/last-minute/route.ts:24-28` filters only status/time/`last_minute_discount_percent>0`; missing `is_active`/`listed_on_marketplace`/`is_test` (which `lib/search/filter-availability.ts:68-74` applies). Fix: add those predicates to the `salons!inner` filter.

### 23. Promo `max_uses` TOCTOU (discount at charge, counter at webhook) → single-use code over-redeemed — CONFIRMED
`booking-pay-intent:227` gates on `current_uses<max_uses`; `webhook:169-172` increments only on success. Concurrent pays inside the webhook-latency window all pass a `max_uses:1` gate → multiple discounts granted (counter capped after). Fix: atomically reserve the use at charge time (increment-and-check RPC), roll back on failure.

### 24. Deposit mode + promo clamp → customer overcharged vs advertised discount — PLAUSIBLE
`booking-pay-intent:247` clamps the promo to the deposit; `:460` `remaining_at_salon` uses the clamped value → total = price − clampedPromo, not price − fullPromo. Only when `payment_mode='deposit'` and promo > deposit. CHF100/20% deposit/30% promo → pays 80.50 not 70. Fix: apply promo to full price, then take deposit% of the discounted total.

### 25. `walkin/pay-intent` has no Stripe idempotencyKey → double card hold — CONFIRMED
`app/api/walkin/pay-intent/route.ts:154` `create()` lacks `{idempotencyKey}` (booking-pay-intent:416 has one). Double-tap → two `requires_capture` holds; unique payment_intent_id index means only one becomes a ticket, the other strands ~7d. Fix: deterministic idempotency key.

### 26. Public queue GET leaks waiting customers' names (PII), unauthenticated — CONFIRMED
`app/api/walkin/queue/route.ts:34` → `:46-71` returns `customer_name` + row id for all active entries; endpoint is only feature-flag + IP-rate-limited. Anyone with a salon_id enumerates who's in line. Fix: drop names/ids from the public payload (counts + ticket_codes only) or gate behind owner/staff auth.

### 27. Booking SMS pay link → second hold + second queue entry → double charge / orphan hold — PLAUSIBLE
`walkin/pay-intent` accepts `booking_id` (:31) but never checks booking state; `lib/barber/walkin-ticket.ts:260-266` re-links the booking to the newest entry. Re-opening the pay link mints hold #2 + entry #2, orphaning hold #1; on completion both capture. `walk-in-verify:59` only 409s on `payment_status='paid'` (a `requires_capture` hold isn't). Fix: reject/reuse when the booking already has a walkin_queue_id or a live hold.

## Booking sub-flows (verified workflow — 3 skeptics/finding; 32 of 36 survived)

Coverage: recurring / group / waitlist / guest-access / express-rebook / admin-disputes.

### [CRITICAL] recurring — preferred_day type mismatch crashes rule creation whenever the field is supplied  (3/3, )
`lib/validations.ts:892`
- Defect: recurringBookingSchema validates preferred_day as z.number().int().min(0).max(6) (an integer 0-6), but the DB column is `preferred_day text CHECK (preferred_day IN ('mon','tue','wed','thu','fri','sat','sun'))` (supabase/migrations/014_new_schema.sql:281). app/api/bookings/recurring/route.ts:48 inserts the raw validated number straight into that column.
- Scenario: Client sends POST /api/bookings/recurring with preferred_day: 3 (any value the Zod schema explicitly accepts). The insert into recurring_booking_rules violates the CHECK constraint (integer isn't one of the mon..sun strings), Postgres rejects the row, ruleError is set, and the route returns 500 { code: 'DB_ERROR' }. Any customer who actually uses the preferred-day feature (the entire reason the field exists) gets a hard failure creating the series, not just a wrong value.
- Fix: Either change the Zod schema to accept the short day-key strings ('mon'..'sun', matching opening_hours convention) and map correctly, or change the column to an integer/smallint 0-6 and drop the text CHECK, then verify the cron processor's date math against the corrected representation.

### [CRITICAL] group — Group-booking RPC's own INSERT is blocked by RLS (no INSERT policy on group_bookings) — feature never completes a single call  (3/3, )
`supabase/migrations/071_megabuild_booking_crm_payments.sql:151`
- Defect: create_group_booking() is a plain plpgsql function with no SECURITY DEFINER (confirmed live via pg_get_functiondef: no 'SECURITY DEFINER' in the definition, only 'SET search_path'), so it executes as the caller's authenticated role and is subject to RLS. group_bookings has ENABLE ROW LEVEL SECURITY with exactly one policy, 'group_organizer_read', SELECT only (confirmed live via pg_policies: a single row, cmd='SELECT'). No INSERT policy exists anywhere in the migrations or live DB, so Postgres default-denies the INSERT.
- Scenario: Any authenticated, non-banned user POSTs /api/bookings/group with 2+ valid members and slot_ids. The RPC reaches 'INSERT INTO group_bookings (...) VALUES (...) RETURNING id INTO v_group_id' and Postgres raises 'new row violates row-level security policy for table group_bookings'. route.ts (line 61) catches this as rpcError and returns HTTP 409 to the caller. This happens on every single invocation, for every user, with no way around it from the client side — the group booking feature is completely non-functional in production today.
- Fix: Either mark the function SECURITY DEFINER (with an explicit search_path and no reliance on caller RLS bypass elsewhere), or add an INSERT policy on group_bookings scoped to authenticated users creating their own group (and a matching UPDATE policy, see next finding).

### [CRITICAL] group — Even past the RLS block, the bookings INSERT violates NOT NULL constraints (starts_at, ends_at, price_paid) on every call  (3/3, )
`supabase/migrations/071_megabuild_booking_crm_payments.sql:155`
- Defect: INSERT INTO bookings (salon_id, slot_id, service_id, staff_member_id, group_booking_id, status, payment_status) omits starts_at, ends_at and price_paid. Live schema query confirms all three are is_nullable='NO' with column_default=null, and the only trigger on bookings is 'bookings_updated_at' (BEFORE UPDATE only) — nothing backfills these columns on INSERT.
- Scenario: If the RLS block above were fixed, the very next statement in the loop would raise 'null value in column "starts_at" violates not-null constraint' for the first member, aborting the whole function call. Per Postgres function-call transaction semantics this rolls back everything done so far (the group_bookings row and any prior members' booking rows + slot updates in the same call), so no group booking can ever be persisted regardless of input.
- Fix: Populate starts_at/ends_at from the locked availability_slots row (already read via FOR UPDATE) and price_paid from services.price (converted to the correct unit) before the INSERT.

### [CRITICAL] guest-access — walk-in-verify (and its sibling quick-action) read `bookings` through the RLS-bound session client, so the entire guest audience the endpoint is built for gets silently 404'd regardless of a valid token  (3/3, )
`app/api/bookings/walk-in-verify/route.ts:49`
- Defect: verifyHmacToken() correctly validates the HMAC token, but the subsequent booking lookup uses `createServerSupabaseClient()` (line 49-55: `const supabase = await createServerSupabaseClient(); ... .from("bookings").select(...).eq("id", bookingId)...`), which is the anon-key + cookie-session client subject to RLS. The project's own SP-1 guest-RLS migration (supabase/migrations/20260601_sp1_bookings_guest_rls.sql, comment at lines 9-11) states explicitly: 'Guests NEVER touch the table through RLS -- guest rows (user_id IS NULL) are reachable only via the token-gated SERVICE-ROLE path'. `bookings_select_own` (same migration, lines 30-38) requires `(user_id IS NOT NULL AND auth.uid() = user_id) OR <salon owner>` -- both false for an unauthenticated caller with no session. So for any guest (the entire intended audience of an SMS/email link opened on a phone with no Solen account), the SELECT returns 0 rows, `data` is null, and the route returns the generic `{ error: "Booking not found" }` 404 (line 57) -- masking that the token was cryptographically valid. The sibling GET route app/api/bookings/[id]/quick-action/route.ts has the identical defect (its `createServerSupabaseClient()` SELECT at lines 57-62 and UPDATEs at lines 67/72/74). Proof this is a genuine oversight, not an intentional design: the SAME walk-in-verify handler correctly uses `createAdminSupabaseClient()` a few lines later (line 75) for the `barber_walkin_queue` lookup, and the sibling POST /api/walkin/confirm/route.ts correctly uses `createAdminSupabaseClient()` (line 61) for its own token-gated booking lookup -- the pattern for 'token is the authorization, use the admin client' is established and used correctly elsewhere in the very same feature area, just missing on this GET path.
- Scenario: A salon creates a walk-in booking for a guest (user_id NULL) and texts them `/walk-in-pay?token=<valid-hmac>`. The guest opens the link on their phone with no account/session. `GET /api/bookings/walk-in-verify?token=...` verifies the HMAC as valid, then the RLS-gated SELECT matches zero rows, so the route responds 404 'Booking not found'. The frontend (app/[locale]/walk-in-pay/page.tsx line 101-104) shows 'invalid/expired token' and the guest cannot pay or see their booking, even though their token was completely valid -- the core walk-in-pay self-service flow is broken for its actual guest users. The identical failure applies to the one-click email 'cancel my booking' link via /api/bookings/[id]/quick-action for any guest booking or any customer who isn't currently logged in on that browser.
- Fix: Swap `createServerSupabaseClient()` for `createAdminSupabaseClient()` in both walk-in-verify/route.ts and quick-action/route.ts for the token-gated lookups/updates, mirroring the pattern already used correctly in guest-lookup, resend-access, and walkin/confirm -- the HMAC/token check IS the authorization here, RLS should not additionally gate it.

### [CRITICAL] express-rebook — Express-rebook confirm bypasses full-prepay payment entirely, unconditional status='confirmed'  (3/3, )
`app/api/bookings/express-rebook/confirm/route.ts:59`
- Defect: Unlike app/api/bookings/route.ts (which computes bookingStatus = isOnlinePay ? ### Refuted / not-a-bug
- group: Individual member bookings never get user_id set and no other endpoint anywhere reads/manages group bookings (1/3) — The scenario does not reproduce, because a group booking can never reach the state the finding assumes ("a group booking is created" and the organizer paid for it). The live DB has a CHECK constraint `bookings_owner_or_guest_chk` (added later in supabase/migrations/20260601_sp1_bookings_guest_rls.sql, confirmed live via pg_constraint on project tocfnsmxmdxkrcmjzzdw): `CHECK (user_id IS NOT NULL OR (guest_name IS NOT NULL AND guest_phone IS NOT NULL) OR anonymized_at IS NOT NULL)`. The `create_group_booking` RPC's per-member INSERT (confirmed live via pg_proc, matches the migration source verbatim) only sets `(salon_id, slot_id, service_id, staff_member_id, group_booking_id, status, payment_status)` — user_id, guest_name, guest_phone, and anonymized_at are all left NULL (confirmed no column defaults). That row violates the CHECK constraint immediately on the first member insert, so Postgres raises a constraint-violation error inside the PL/pgSQL function body. The function has no EXCEPTION handler, so the error propagates out and aborts the entire implicit transaction for that RPC call, rolling back the earlier `group_bookings` insert and any prior member inserts in the loop too. Net effect: attempting to create a group booking today always fails outright with a hard error (surfaced to the client as the route's 409 `rpcError` branch) — no group_bookings row and no member bookings rows ever persist. So there is no scenario where an organizer has already paid for a group booking that then becomes unreadable/unmanageable through RLS or a missing endpoint, because the booking never exists in the first place. The RLS analysis in the finding (bookings_select_own requiring auth.uid()=user_id, and no other group-booking endpoint existing) is accurate as written and would matter if the INSERT column list were ever fixed to include user_id, but as currently deployed the missing user_id column is exactly what trips the CHECK constraint and blocks creation before any of the claimed downstream consequences can occur. This is a different, arguably more severe defect (the whole group-booking feature is non-functional / silently errors on the very first attempt) but it is not the "created-but-unmanageable paid booking" scenario the finding describes, so the specific claim as written does not reproduce.
- group: NULL-vs-'available' comparison lets a nonexistent slot_id silently skip the availability guard (1/3) — The NULL-vs-'available' PL/pgSQL logic bug is real (SELECT INTO on zero rows sets v_slot_status to NULL, and `NULL != 'available'` evaluates to NULL/false, so the RAISE EXCEPTION is skipped) but the claimed exploit scenario does not reproduce, exactly as the finding itself admits.

Confirmed in supabase/migrations/014_new_schema.sql: `bookings.slot_id uuid NOT NULL REFERENCES public.availability_slots(id) ON DELETE RESTRICT`. For a syntactically valid but nonexistent slot_id, the guard's silent no-raise lets the loop fall through to `INSERT INTO bookings (...)` at 071_megabuild_booking_crm_payments.sql:155-157, but that INSERT's slot_id value has no matching row in availability_slots, so Postgres itself raises a foreign-key-violation error there. In plpgsql, an unhandled exception inside the function body aborts the whole function's implicit transaction, so the earlier `INSERT INTO group_bookings` (line 151-153) is rolled back too. Net effect: the RPC call still fails and no booking or group_booking row is ever persisted for a phantom slot_id, identical in outcome (rejection) to what the intended `RAISE EXCEPTION 'Slot % is not available'` would have produced, just with a generic FK-violation message instead of the friendly one.

Checked the only caller (app/api/bookings/group/route.ts): it requires an authenticated, non-banned user and rate-limits, but does not pre-validate slot_id against availability_slots before calling the RPC, so this DB-level constraint is the only thing that would matter here, and it does cover the phantom-slot case.

So there is no authz/data-exposure gap and no path today where a nonexistent slot_id lets a booking or group_booking actually get created: the NOT NULL + FK on bookings.slot_id (ON DELETE RESTRICT, requires an existing row) closes the gap the guard's NULL-comparison bug opens. This is a legitimate code-quality defect (wrong PL/pgSQL comparison, misleading error message, and it would become exploitable if a future change ever made slot_id nullable or removed the FK) but it does not currently reproduce as a security bug, matching the finding's own "masked" caveat.
- waitlist: Waitlist entries joined without pinning a specific service can never be matched (NULL never equals anything in SQL) (0/3) — The SQL fact cited (NULL never satisfies `.eq("service_id", <uuid>)`) is correct, and the schema/DB path (waitlist.service_id nullable, cancel route's promotion query at app/api/bookings/[id]/cancel/route.ts:225 doing `.eq("service_id", booking.service_id)`) is real. But the reproduction scenario does not occur through the current live UI, because the only caller of POST /api/waitlist is components-legacy/booking/WaitlistModal.tsx:71 (`service_id: service?.id`), which is only rendered from components-legacy/booking/DateTimeStep.tsx:271 inside the booking wizard, with `service={formData.services[0] ?? null}`.

Reaching DateTimeStep requires having already passed through ServicesStaffStep, which double-guards against an empty service cart:
1. The Continue button is `disabled={formData.services.length === 0 || isChecking}` (ServicesStaffStep.tsx:480).
2. `handleContinue` itself early-returns with a validation error if `formData.services.length === 0` (ServicesStaffStep.tsx:159-162), before ever calling `goToStep`.

BookingWizard's step machine is a strict linear sequence (`STEPS = ['services-staff', ...maybe 'staff', 'datetime', ...]`, BookingWizard.tsx:127-133) with no localStorage/session persistence (booking-context.tsx always initializes `currentStep: 'services-staff'` on mount, and only the reducer's own goToStep calls change it), and every `goToStep('datetime')` call site (ServicesStaffStep.tsx:164, StaffStep.tsx:158) is downstream of that guard. There is no deep link, query param, or alternate entry point that seeds `currentStep` past `services-staff` while leaving `formData.services` empty.

So `formData.services[0]` is guaranteed non-null whenever WaitlistModal renders, `service_id` sent to the API is always a real UUID, and the waitlist row can never actually be written with `service_id = NULL` through the reachable customer flow today. The optional `service_id` in `waitlistSchema` and the NULL-join hazard in the cancel route are latent/defensive-code concerns (e.g. if a future UI surface or direct API call omits it), not a currently reproducible silent no-op.
- express-rebook: service_id is optional in expressRebookConfirmSchema; omitting it silently produces a free (price_paid=0) confirmed booking (0/3) — Traced the full path in app/api/bookings/express-rebook/confirm/route.ts and verified the live DB schema (Supabase execute_sql on project tocfnsmxmdxkrcmjzzdw). The claimed exploit does not reproduce.

When service_id is omitted: `.eq("id", service_id)` in postgrest-js does `searchParams.append(column, \`eq.${value}\`)` (node_modules/@supabase/postgrest-js/src/PostgrestFilterBuilder.ts:114), so with value=undefined this literally sends `id=eq.undefined`. Postgres fails to cast the string "undefined" to uuid, the services query errors, and (as the finding says) that error is discarded so `service` is null and `price_paid: service?.price ?? 0` computes 0.

BUT the finding stops there and is wrong about what happens next. The insert body is built with `service_id` (line 53), and `service_id` is JS `undefined` in this scenario. PostgrestBuilder.ts:128 does `body: JSON.stringify(this.body)`, and JSON.stringify drops object keys whose value is `undefined` — so the "service_id" field is not sent to PostgREST at all, not sent as null.

Live schema check confirms `bookings.service_id` is `is_nullable: NO`, `column_default: null`, plus an active FK `bookings_service_id_fkey FOREIGN KEY (service_id) REFERENCES services(id) ON DELETE CASCADE` (migrations/014_new_schema.sql:228, reconfirmed live via execute_sql). With no service_id key sent and no default, the INSERT hits a NOT NULL violation. That Postgres error IS checked in this route (`if (error) return NextResponse.json({ error: error.message }, { status: 500 })`, route.ts:66), so the request returns a 500, no booking row is created, and the slot is never marked booked.

So omitting service_id does not produce a free confirmed booking — it produces a 500 error and no side effects. The same NOT NULL + FK guard also blocks a nonexistent/deleted service_id (FK violation on insert). The only way price_paid could land at 0 is submitting a valid, existing service_id that legitimately has price 0, which is not the scenario described (and is a distinct, lower-severity price/slot-service mismatch concern, not a "free booking via omission" bug). The unchecked error on the services lookup is sloppy but has no exploitable effect because the downstream DB constraint independently blocks the insert.
