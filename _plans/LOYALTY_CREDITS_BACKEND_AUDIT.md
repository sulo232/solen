3 finders (credits-ledger / loyalty-rank / credit-promo-stacking) x 3-skeptic verify; several confirmed vs LIVE DB (pg_policies). 6 confirmed, 0 refuted. (Already-known referral/promo findings not repeated.)

## [CRITICAL] loyalty-rank — bookings RLS write policies have no WITH CHECK — customer can self-fabricate 'completed' bookings to game Solen Status tier and unlock the member discount  (3/3, CONFIRMED)
`supabase/migrations/20260601_sp1_bookings_guest_rls.sql:44`
- Defect: The live RLS policies on public.bookings have no column/value restriction on customer-initiated writes. Verified live against the production DB (project tocfnsmxmdxkrcmjzzdw): `bookings_update_own` (cmd UPDATE) has `qual = ((user_id IS NOT NULL AND auth.uid() = user_id) OR salon-owner)` and `with_check = null`; `bookings_insert_auth` (cmd INSERT) has `with_check = (auth.uid() = user_id)` only — neither restricts which OTHER columns/values may be set. The `authenticated` role holds a live UPDATE grant on the table. The only trigger on bookings is `bookings_updated_at` (timestamp bookkeeping); `bookings_status_check` merely enumerates valid status strings, it does not gate WHO may set them. This means any logged-in customer can call the Supabase REST API directly (bypassing every app route, salon-dashboard completion flow, and Stripe) with their own session JWT and PATCH/INSERT their own booking row to `status: "completed", price_paid: 25, refunded_amount: 0` — which is EXACTLY the predicate `current_user_tier()`, `recompute_loyalty_status()`, and `lib/loyalty/status.ts getLoyaltyStatus()` all use to count 'qualifying completed visits' (status='completed' AND refunded_amount<=0 AND gross price >= CHF25 AND within the 12-month window). Because `bookings_insert_auth`'s WITH CHECK only checks `user_id`, the attacker does not even need a genuine booking/slot flow: they can INSERT a fully fabricated row directly (any existing salon_id/service_id/slot_id satisfies the FK constraints; slot_id need not be their own or actually available) with status already 'completed'.
- Scenario: A customer logs in normally (gets a real Supabase auth JWT), then from any HTTP client sends: `PATCH https://<project>.supabase.co/rest/v1/bookings?id=eq.<own_booking_id>` with body `{"status":"completed","price_paid":25,"refunded_amount":0}` (or an outright `POST` insert of a new row with the same fields plus any real salon_id/service_id/slot_id). Repeating this 6 times instantly gives them Platinum tier per `LOYALTY.thresholds` in lib/loyalty/status.ts, with zero real visits, zero payment, and zero salon involvement. On their next real booking, `resolveMemberDiscount` (lib/loyalty/perks.ts, wired into app/api/stripe/booking-pay-intent/route.ts) reads `current_user_tier()` live and grants the Platinum discount_pct (10% placeholder), which comes directly out of Solen's own Stripe Connect application_fee per §12.1 of LOYALTY_STRUCTURE.md — i.e. this is a direct real-money leak from Solen's margin, not just a vanity-tier gaming issue. It also unlocks member-only promo codes (`min_tier` gate in app/api/promo/validate/route.ts), prime-time early access, and walk-in queue priority, all keyed off the same self-inflatable tier.
- Fix: Add a `WITH CHECK` to bookings_update_own that pins unauthorized-role updates to a safe column set (or explicitly disallows the customer branch from touching `status`, `price_paid`, `final_price`, `refunded_amount`, `payment_status`, `applied_tier`, `tier_discount_amount`), and tighten `bookings_insert_auth`'s WITH CHECK to require `status` be the default pending/unpaid value on customer-initiated inserts. Most robust: revoke direct UPDATE/INSERT of the status and money columns from `authenticated` entirely and route all completion/payment-status writes through a SECURITY DEFINER function callable only by the salon owner or service_role, mirroring the pattern already used correctly for `current_user_tier()` and `recompute_loyalty_status()`.

## [CRITICAL] credit-promo-stacking — Customer can self-mark their own booking 'completed' with zero verification, gaming Solen Status tier and unlocking the member discount  (3/3, CONFIRMED)
`app/api/bookings/[id]/route.ts:106`
- Defect: PATCH /api/bookings/[id] validates status against z.enum(['completed','no_show','cancelled']) (lib/validations.ts:768) and authorizes the write as `!isSalonOwner && !isBookingOwner -> 403` (line 106), i.e. isBookingOwner (the CUSTOMER) is allowed through for ANY status value including 'completed'. The 'completed' branch (line 111) only stamps completed_at = now(); unlike the salon-side cron (app/api/cron/auto-complete/route.ts, which requires status='confirmed', payment_status != 'pending', ends_at < 48h ago, and salon.auto_complete_enabled), this endpoint applies NO guard: no requirement that the prior status be 'confirmed', no requirement that starts_at/ends_at is in the past, no requirement that payment_status='paid'. current_user_tier() (supabase/migrations/20260614010000_solen_plus_phase1_perks.sql:88-94) and recompute_loyalty_status() count visits purely as `status='completed' AND coalesce(refunded_amount,0)<=0 AND coalesce(final_price,price_paid,estimated_price,0)>=25 AND starts_at within 12 months` -- there is no payment_status check at all.
- Scenario: A customer creates 3 real at_salon (pay-in-person) bookings for services priced >= CHF 25 (no payment required upfront for at_salon mode). Immediately after creating each booking (booking.status is 'pending' or 'confirmed', payment_status is 'none'/'pending', starts_at can be in the future), the customer calls `PATCH /api/bookings/{id}` with `{"status":"completed"}` on their own booking id. isBookingOwner=true passes the 403 gate, the row is updated to status='completed' with no other checks. current_user_tier(uid) on next read now counts 3 completed >=CHF25 bookings within the window and returns 'gold' (threshold 3) instantly -- without the customer ever attending an appointment, ever paying, or the salon ever confirming anything. As Gold, resolveMemberDiscount() in lib/loyalty/perks.ts then grants a real 5% (Gold) or 10% (Platinum, 6 self-completions) discount on the customer's NEXT real booking charge in /api/stripe/booking-pay-intent (funded by Solen's own commission waiver, so Solen's margin is directly reduced by a self-manufactured tier), plus other tier_perks (cancel_grace_per_month, reschedule_free, prime_time_early_access, walkin_priority) and eligibility for min_tier-gated promo codes.
- Fix: In the PATCH handler, split the authorization by target status: only isSalonOwner (or an admin/cron/service actor) may set status='completed'; isBookingOwner should only be able to reach 'cancelled' (existing behavior) and never 'completed' directly. Additionally mirror the cron's invariants server-side before allowing any 'completed' write: require the prior status to be 'confirmed', require starts_at/ends_at to already be in the past, and require payment_status to be 'paid' (or 'none' only for genuinely-free services), matching the guards already enforced in app/api/cron/auto-complete/route.ts.

## [HIGH] credits-ledger — user_credits has no spend/redemption path anywhere in the codebase; earned referral credit can never be applied to a charge  (3/3, )
`app/[locale]/checkout/page.tsx:575`
- Defect: Exhaustive search (`grep -rl "user_credits"` over app/, lib/, and the mobile repo) turns up exactly 5 hits, all in: the migration (supabase/migrations/050_user_credits.sql, table+RLS only), app/api/referral/complete/route.ts:78-95 (INSERT only), app/api/bookings/route.ts:609-626 (duplicate INSERT-only path on first booking), app/api/referral/route.ts (reads nothing from the table), and app/[locale]/checkout/page.tsx (display only). There is no RPC, no conditional UPDATE, no `.eq("remaining", ...)` guard, nothing in app/api/stripe/create-payment-intent, app/api/stripe/booking-pay-intent, or app/api/bookings/route.ts's own charge-amount computation that ever reads a user's `user_credits.remaining` and subtracts it from a charge. No route named /api/credits exists at all. The `remaining` column, the `expires_at` column, and the `source: 'promo' | 'birthday' | 'manual'` enum values are all write-only decoration: nothing ever filters on expiry, nothing ever decrements remaining, and nothing besides the referral flow ever inserts a row.
- Scenario: A user refers a friend, both get 'CHF 10 Guthaben gutgeschrieben' (app/api/referral/complete/route.ts:110), and that CHF 10 can never be spent by any code path in production today, not through a race, not through normal use, not through any means, because the spend logic simply does not exist. This makes every one of the requested ledger-integrity questions (double-spend, negative remaining, expired-credit-still-spendable, Rappen/CHF mixup at redemption) currently moot: there is no spend code for those bugs to live in. The real defect is that the product promises spendable credit it structurally cannot deliver.
- Fix: Either build the redemption path (a single atomic RPC that does `UPDATE user_credits SET remaining = remaining - $amount WHERE id = $id AND remaining >= $amount AND (expires_at IS NULL OR expires_at > now())`, wired into the payment-intent/booking-charge amount server-side, never trusting a client-supplied credit amount) or, if credits are intentionally dormant like the nail-retention and other feature-flagged systems in this repo, gate the referral 'Guthaben gutgeschrieben' copy/UI behind the same flag so users are not told they earned spendable money that does not exist yet.

## [MEDIUM] credits-ledger — GET /api/referral hardcodes total_earned = 0, so even the credit BALANCE display is dead code  (3/3, )
`app/api/referral/route.ts:31`
- Defect: `let total_earned = 0;` is declared and returned in the JSON response but is never reassigned anywhere in the function; `user_credits` is never queried. The only computed field is `friends_invited` (from the `referrals` table). Checkout's `useEffect` at app/[locale]/checkout/page.tsx:187-197 does `if (data.total_earned) setUserCredits(data.total_earned)`, and since 0 is falsy this branch never fires, so the 'Guthaben verfügbar' banner at lines 575-586 never renders regardless of how much a user has actually accrued in user_credits.
- Scenario: A user who earned CHF 10 (or CHF 20 across two referrals) opens checkout expecting to see and use that balance; the API always reports total_earned: 0, so the balance is invisible, on top of being unspendable per the finding above. Two independent bugs compound into a credit feature that is completely non-functional end-to-end (issue -> is never truthfully displayed -> can never be spent).
- Fix: Compute total_earned/remaining by summing `user_credits.remaining` for the session user, filtered to `expires_at IS NULL OR expires_at > now()`, and wire that real number into the checkout display, then build the redemption path described above.

## [MEDIUM] credit-promo-stacking — /api/stripe/create-payment-intent trusts a fully client-supplied deposit_amount with no server-side promo/voucher re-validation  (3/3, PLAUSIBLE)
`app/api/stripe/create-payment-intent/route.ts:74`
- Defect: This endpoint only bounds-checks the client-supplied `deposit_amount` against the live service price (>= CHF 0.50 and <= truePriceChf, line 74-79) and checks `estimated_price` matches truePriceChf within 1 Rappen (line 80-82). It never re-validates a promo code, voucher, or any other discount server-side -- unlike app/api/stripe/booking-pay-intent/route.ts, which re-validates promo_codes against the live row (constraints, expiry, max_uses, min_tier) before computing the charge. The caller (app/[locale]/checkout/page.tsx line 141-159) builds `deposit_amount` entirely from a client-controlled `booking_intent` JSON blob read out of the URL query string (`searchParams.get('booking_intent')`), with no server-issued signature. NOTE: this /checkout page appears to be dead/orphaned code (grep found zero in-app navigation to /checkout anywhere in app/ or components/, and its own Stripe return_url points at /{locale}/checkout/success, a route that does not exist in the repo), so this is not confirmed to be reachable via the live UI. The API route itself, however, is deployed and callable directly by any authenticated, non-banned user regardless of UI reachability.
- Scenario: Any authenticated user can POST directly to /api/stripe/create-payment-intent with `{salon_id, service_id, service_name, estimated_price: <real price>, deposit_amount: 0.5}` for a real CHF 200 service. estimated_price matches so that check passes; deposit_amount 0.5 clears only the floor/ceiling checks (>=0.5, <= truePriceChf) with no requirement that 0.5 correspond to any real discount, promo code, or the salon's actual deposit_percent setting. A manual-capture (hold) PaymentIntent for CHF 0.50 is created instead of the real deposit amount the salon configured (e.g. 20-50% of price), undermining the no-show deposit's purpose. Actual monetary harm depends on whatever downstream flow (if any) captures/relies on this PI; the orphaned success-redirect suggests nothing currently does, but the trust boundary itself is broken and would misfire if this endpoint is ever wired back up or hit via a stale link.

## [LOW] credit-promo-stacking — Audit-premise contradiction: user_credits, last-minute discount, and off-peak discount are NOT wired into any live charge computation, so they cannot currently stack with promo/loyalty  (2/3, CONFIRMED)
`app/api/stripe/booking-pay-intent/route.ts:?`
- Defect: Grepped the whole repo (excluding worktrees) for user_credits: only app/api/bookings/route.ts (issues referral credits on completion), app/api/referral/complete/route.ts (issues), and app/api/referral/route.ts (reads total_earned for display) reference it -- there is no app/api/credits/* endpoint and no code anywhere that decrements user_credits.remaining or subtracts it from a charge amount. The one place credits are shown at checkout (app/[locale]/checkout/page.tsx line 575-586, 'Guthaben verfügbar') is purely a display block; the actual `chargeAmount` calc at line 349 only subtracts promoResult.discount_amount + voucherResult.remaining_amount, never userCredits. Likewise last_minute_discount_percent / off-peak discount_percent are read only in search/filter/badge code (app/api/salons/*, app/api/slots/last-minute, lib/search/filter-availability.ts) -- never in app/api/bookings/route.ts or app/api/stripe/booking-pay-intent/route.ts, which derive the charge solely from `services.price` (+ optional bundle price) with promo and Solen Plus member-tier discount as the only two reductions, both explicitly floored at 50 Rappen (booking-pay-intent lines 244-247, lib/loyalty/perks.ts computeMemberDiscount clamp). So the specific 'credit + promo + last-minute + loyalty stacking to zero/negative' scenario cannot occur today because two of the four levers never touch the charge amount at all on main.
- Scenario: Not an exploit path today. Flagging per the reasoning discipline: the audit brief assumed 4 reductions combine at charge time; only 2 (promo, Solen Plus tier) actually do, and both are already correctly floored/capped/re-validated server-side (order: promo first defines the post-promo gross, member waiver reduces the resulting commission and, in lockstep, the customer charge, floored at max(0, amountRappen-50) so the combination can never go below 50 Rappen or negative). If credits or last-minute/off-peak discounts are later wired into a real redemption path, the floor/cap/re-validation pattern already used for promo + member-tier in booking-pay-intent should be reused rather than re-invented.
- Fix: No code fix needed today. When user_credits redemption or last-minute/off-peak discounts are actually implemented at checkout, apply the same pattern already proven in booking-pay-intent: re-derive server-side, cap each reduction so the running total never drops the charge below 50 Rappen, and re-validate expiry/eligibility from the live row, not the client.
