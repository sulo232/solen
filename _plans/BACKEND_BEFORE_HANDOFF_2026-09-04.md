### Walk-in refund bypasses chokepoint, no idempotency key (route.ts:248, :351)

**How it was proved:** Confirmed for the PATCH handler (line 248): the CAS at lines 83-93 is self-referential (`.eq('status', entry.status)`, using the freshly-read current status as its own comparison value), so once a queue row is already 'cancelled', a repeat PATCH with {status:'cancelled'} re-reads entry.status='cancelled', the CAS trivially matches (cancelled->cancelled no-op), and execution falls through to the Stripe refund block, which calls `stripe.refunds.create` with no `idempotencyKey` and no monetary-column CAS (confirmed barber_walkin_queue has no refunded_amount-type column in _inventory/_db-columns.json). This is a genuine deviation from the documented architecture: _docs/BACKEND.md and lib/bookings/issue-refund.ts both establish that only issue-refund.ts/issue-purchase-refund.ts may call stripe.refunds.create, using a deterministic idempotencyKey plus a pre-Stripe CAS on a monetary column, a pattern this walk-in code doesn't follow. HOWEVER, the claim's inclusion of the DELETE endpoint (line 351) as equally vulnerable is WRONG: DELETE has an explicit `if (entry.status !== 'waiting') return 400` check (line 318) on a freshly-read status, executed before the CAS and before any Stripe call. Any second call (sequential retry or a request landing after the first's CAS already committed) reads status='cancelled' and is rejected at line 318, never reaching Stripe; a truly simultaneous pair both reading 'waiting' still resolves safely because Postgres serializes the two competing UPDATE...WHERE status='waiting' statements, so only one can win the CAS. So DELETE cannot double-refund under any timing. For PATCH, the realistic risk is also narrower than 'a retried cancel': a simple sequential retry (waited, response lost, tapped again after the first call fully finished) is caught by Stripe's own charge_already_refunded rejection on a second full-refund call with no amount specified (all three call sites omit `amount`, so they're always full refunds) — that error is swallowed by the local try/catch, so no real double-refund results. A genuine double-refund needs the second request's Stripe call to fire concurrently with the first's still-in-flight Stripe call (sub-second double-tap), which is a real but narrow window, not the everyday 'slow request, taps again' scenario. Net: real defect, but severity is MEDIUM not HIGH given the DELETE citation is incorrect and the exploit window on PATCH is a tight concurrency race rather than an ordinary retry.
