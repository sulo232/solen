## [CRITICAL] payout-ledger — Pre-charge cron's PaymentIntent metadata omits salon_id, so pre-charged bookings never get a salon_payouts ledger row  (3/3, )
`app/api/cron/pre-charge/route.ts:65`
- Defect: app/api/cron/pre-charge/route.ts creates the off-session PaymentIntent via chargeOffSession() with metadata `{ type: "pre_charge", booking_id: booking.id }` only (no salon_id). chargeOffSession (lib/bookings/off-session-charge.ts) passes that metadata straight to Stripe unmodified. In app/api/stripe/webhook/route.ts, the payment_intent.succeeded handler's ledger write is gated on `if (grossAmount > 0 && pi.metadata?.salon_id)` (line 187) with no fallback that resolves salon_id from the `bookings` table for this branch. Contrast with the off-session upcharge/cancellation-fee branch added later in the same file (lines ~309-350), which explicitly resolves `chargeSalonId` from `bookings.salon_id` when metadata lacks it -- that resolution was never applied to the plain booking branch, and `type: "pre_charge"` also doesn't match `isUpchargeCharge`/`isFeeCharge`, so it falls through both code paths untouched.
- Scenario: A booking with payment_status='card_saved' (SP-3 deferred-payment flow) sits within 5 days of starts_at with a saved card. The daily pre-charge cron fires, chargeOffSession() successfully charges the customer's card via Stripe Connect (money actually moves: application_fee to the platform, net to the salon's connected account). The webhook's payment_intent.succeeded handler runs: bookingId is present so it takes the booking branch, but pi.metadata.salon_id is undefined, so the `admin.from("salon_payouts").upsert(...)` call is skipped entirely -- no row is ever created for this real, captured charge. Consequences: (1) app/api/salon/earnings and app/api/salon/invoices/[payoutId] never show this booking's revenue/commission to the salon, permanently under-reporting real earnings; (2) app/api/admin/revenue's `total_commission`/`total_net_to_salons` (derived from salon_payouts) silently exclude this charge from platform-wide totals; (3) if this booking is later refunded, the charge.refunded webhook's reconciler (`.select("*").eq("stripe_payment_intent_id",...).maybeSingle()`) finds no payout row and no-ops, so the refund is never reflected in the ledger either, compounding the drift. cron/reconcile/route.ts would eventually flag this PI as `missing_payout` in its daily admin-email digest, but that is detection only (48h lookback, email-only, no auto-fix) -- the ledger stays wrong until a human manually backfills it.
- Fix: Add `salon_id: booking.salon_id` to the metadata object passed to chargeOffSession() in app/api/cron/pre-charge/route.ts (mirrors what release-payments' original booking-time metadata already carries). As defense in depth, also extend the webhook's plain-booking branch (around line 185-226) to resolve salon_id from the `bookings` table when metadata omits it, the same pattern already used for the upcharge/fee branch just below it.

## [CRITICAL] connect-onboarding — Retail purchase, tips, and gift-card checkout route customer money to a salon's Connect account based only on stripe_account_id being non-null — no onboarding-status check at all  (3/3, )
`app/api/salon/retail/purchase/route.ts:40`
- Defect: app/api/salon/retail/purchase/route.ts:40 (`if (!salon?.stripe_account_id)`), app/api/tips/route.ts:46, app/api/walkin/tip/route.ts:53, and app/api/gift-cards/purchase/route.ts:51 all gate `transfer_data.destination` purely on `stripe_account_id` being non-null. They never check `accepts_online_payment`, `charges_enabled`, or `payouts_enabled`. `stripe_account_id` is written to the `salons` row the instant a salon clicks Connect, at the top of app/api/stripe/connect/create-account/route.ts:37-48, before ANY Stripe onboarding step (KYC, bank account, TOS) has been completed and before any capability is active. This is stricter than the booking flow, which at least checks the DB-cached `accepts_online_payment` flag (app/api/stripe/create-payment-intent/route.ts:43, app/api/walkin/pay-intent/route.ts:52) — these four routes skip that check entirely.
- Scenario: A salon owner clicks 'Connect Stripe' but abandons onboarding before submitting any KYC/bank info (a very common drop-off point). `salons.stripe_account_id` is now set to `acct_XXX` with charges_enabled=false, payouts_enabled=false, details_submitted=false. A customer immediately buys a retail product, or tips a staff member, or buys a gift card, from that salon. The route reads `stripe_account_id`, finds it truthy, and creates a PaymentIntent with `transfer_data: { destination: acct_XXX }` and (for retail) `application_fee_amount`. Depending on Stripe's handling of an account still missing required capabilities, this either fails at Stripe's API (customer sees a payment error with no clear cause, or the charge succeeds and funds land in an account the salon cannot yet withdraw from because payouts_enabled is false) — either way, money is routed toward an unverified account with zero code-level guard, unlike every other payment path in the app.
- Fix: Add the same `accepts_online_payment` (or better, a live/cached `charges_enabled && payouts_enabled`) check used by create-payment-intent/walkin-pay-intent to retail/purchase, tips, walkin/tip, and gift-cards/purchase before setting transfer_data.

## [CRITICAL] money-crons — abandon-sweep never cancels/voids the Stripe PaymentIntent for abandoned bookings  (3/3, CONFIRMED)
`app/api/cron/abandon-sweep/route.ts:32`
- Defect: The route retrieves the PI status (line 69) and, for anything not succeeded/processing/requires_capture, falls through to cancel the booking row and free the slot (lines 92-123). It never calls stripe.paymentIntents.cancel(...) on the abandoned PI (grep confirms zero .cancel( calls in this file). The PI is left dangling in requires_payment_method / requires_confirmation / requires_action state, still completable by Stripe.
- Scenario: Customer opens the booking-pay-intent flow, closes the tab before confirming, cron marks the booking cancelled and frees availability_slots row S123 after 30 min. A second customer books S123 for the same time. The first customer's browser tab (still holding the original PaymentIntent client secret) is reopened or auto-retried and successfully confirms the SAME old PI. Stripe fires payment_intent.succeeded; the webhook looks the booking up (by payment_intent_id, per its own logic) and finds a row that this cron already flipped to status:cancelled, cancellation_reason:abandoned_payment_timeout, while the slot now belongs to a different, second booking. Money moves for the first customer against a slot no longer theirs, and no code path in this cron prevented it because the PI was never voided.
- Fix: Before or instead of just freeing the slot, call stripe.paymentIntents.cancel(booking.payment_intent_id) (guarded by try/catch, since a PI that already transitioned can legitimately error on cancel) whenever the booking is being auto-cancelled, so the PI can no longer be confirmed after the slot is released.

## [CRITICAL] money-crons — abandon-sweep frees the slot even when the guarded cancel update matched zero rows  (3/3, CONFIRMED)
`app/api/cron/abandon-sweep/route.ts:106`
- Defect: The cancel update re-asserts .eq("status","pending").eq("payment_status","none") in the WHERE clause (lines 99-104) with a comment claiming 'this matches 0 rows and we don't clobber a paid booking'. But the code only branches on updErr (a Supabase client/network error), never on whether any row was actually matched/updated (no .select() or {count:'exact'} is used, so a 0-row UPDATE returns the same error:null as a 1-row UPDATE). Step 2 (slot release, lines 112-123) runs unconditionally whenever updErr is falsy, regardless of whether the guard actually blocked anything.
- Scenario: Cron SELECTs a stale booking (status=pending, payment_status=none, payment_intent_id=null because the FE hadn't stamped it yet at SELECT time, per the file's own documented case of an abandoned booking with no PI). Before the cron's sequential per-row loop reaches this booking's UPDATE (the loop processes up to 50 rows with an awaited Stripe retrieve() per PI-bearing row, so this can take many seconds), the customer actually finishes checkout: booking-pay-intent stamps the PI, it succeeds, and the webhook flips the row to status=confirmed, payment_status=paid. Because booking.payment_intent_id was null in the cron's in-memory snapshot, the live-PI-status guard at line 66 (`if (booking.payment_intent_id)`) is skipped entirely, so the cron proceeds straight to the cancel UPDATE, which now matches 0 rows (booking is confirmed/paid), returns updErr=null, and the code treats that as success. Step 2 then unconditionally sets availability_slots for that slot to status=available/booked_by=null/booking_id=null, freeing a slot that a paying, confirmed customer actually holds -> a second customer can book the same slot, producing a real double-booking for a paid appointment.
- Fix: Chain .select("id") (or use { count: "exact" }) on the cancel UPDATE and only proceed to free the slot when a row was actually returned/counted; otherwise skip the slot release entirely for that iteration (matching the comment's stated intent).

## [HIGH] payout-ledger — charge.dispute.closed ('lost') decrements salon_payouts via a non-atomic read-then-write with no CAS guard, unlike the sibling charge.refunded handler  (3/3, )
`app/api/stripe/webhook/route.ts:566`
- Defect: The charge.refunded handler (lines 666-691) deliberately derives the new gross from the CHARGE's own absolute, cumulative fields (`charge.amount - charge.amount_refunded`), specifically so repeated/concurrent deliveries converge to the same value regardless of the payout row's current state (the code comment even explains this was a bug fix for exactly this class of issue). The charge.dispute.closed 'lost' branch (lines 561-582) does the opposite: it SELECTs the current `salon_payouts` row, computes `newGross = payout.gross_amount - dispute.amount/100` from that just-read value, then UPDATEs by `id` with no compare-and-set / version check tying the write to the value it read. This is a classic read-modify-write race: two ledger-touching webhook events on the SAME payment_intent (e.g. an admin-issued partial refund arriving close in time to this chargeback resolving 'lost', or two disputes closing near-simultaneously) can both read the same stale gross_amount and each write back a result that overwrites the other's adjustment -- one of the two deductions is silently lost.
- Scenario: salon_payouts row for PI pi_123 starts at gross_amount=100 (commission_percent=15). An admin issues a 30 CHF partial refund via issueRefund at nearly the same moment a separate chargeback for 20 CHF on the same charge resolves as 'lost'. Both webhook handlers read the row before either writes: charge.refunded computes newGross = (charge.amount 100 - charge.amount_refunded 30)/... = 70 (correct, absolute). charge.dispute.closed reads payout.gross_amount = 100 (stale, pre-refund) and computes newGross = 100 - 20 = 80. Whichever UPDATE commits last wins and clobbers the other: if the dispute write lands last, the 30 CHF refund deduction is erased from the ledger (gross_amount reverts to 80 instead of the correct 50); if the refund write lands last, the 20 CHF chargeback clawback is erased (gross_amount stays at 70 instead of 50). Either way the salon_payouts row diverges from the true remaining balance and nothing else catches it (cron/reconcile only compares bookings.paid_amount/refunded_amount against Stripe, it does not re-derive salon_payouts CHF values, per its own header comment at lines 23-26).
- Fix: Replace the read-then-subtract-then-write with either (a) a single atomic SQL UPDATE that decrements in the database (e.g. `UPDATE salon_payouts SET gross_amount = GREATEST(0, gross_amount - $1), ... WHERE id = $2`, run via an RPC so the arithmetic happens server-side in one statement), or (b) a compare-and-set update keyed on the value just read (`.eq("gross_amount", payout.gross_amount)`) with a retry-on-no-op loop, mirroring the CAS pattern already used for `refunded_amount` in lib/bookings/issue-refund.ts and lib/purchases/issue-purchase-refund.ts.

## [HIGH] retail-packages — Concurrent last-unit purchases both succeed: customer charged for stock that no longer exists, no automatic refund  (3/3, CONFIRMED)
`app/api/salon/retail/purchase/route.ts:70`
- Defect: The out-of-stock gate at PaymentIntent-creation time (route.ts:70-76, reading nail_retail_products.stock_count) is check-then-act, not atomic. The only atomic guard is the webhook's decrement_retail_stock RPC (app/api/stripe/webhook/purchase-handler.ts:130-145), which prevents the STOCK COUNTER from going negative, but does nothing to prevent the PAYMENT from succeeding for a unit that is no longer available. When the decrement RPC returns no row (out of stock), purchase-handler.ts only does `console.error(...)` — it never triggers an automatic refund, never alerts an admin (no alertAdmin call, unlike other money paths in this codebase), and the retail_purchases row is still flipped to status:'paid' with the customer's card already captured.
- Scenario: A salon has exactly 1 unit of product X (stock_count=1). Two customers A and B both open the product page and both POST /api/salon/retail/purchase within the same second, before either has confirmed payment. Both requests independently read stock_count=1 at lines 46-51/70-76 and both pass the OUT_OF_STOCK check, so both get a real Stripe PaymentIntent and a pending retail_purchases row. Both then confirm card details client-side and both PaymentIntents succeed (Stripe has no concept of the salon's stock, so nothing there blocks the second charge). Both webhooks fire: the first decrement_retail_stock call for product X succeeds (1->0); the second call's guarded UPDATE (`stock_count >= 1`) matches zero rows, so it silently logs and returns, but the second retail_purchases row is still marked 'paid' with paid_amount set and a salon_payouts row written. Customer B has now paid full price for a product that does not exist, with the system's only trace being a server log line; no code path refunds B or notifies the salon/ops.
- Fix: Move the authoritative stock check to be resolved atomically at the SAME point money is committed, e.g. reserve stock (a guarded decrement, or a `SELECT ... FOR UPDATE` / advisory lock keyed on product id) at PaymentIntent-creation time rather than only at webhook settle, and release the reservation if the PI is later canceled/fails. Alternatively, when the webhook's decrement RPC returns no row for a SETTLED purchase, treat it as a hard failure path: call alertAdmin and (if the refund policy allows) auto-issue a full refund via issuePurchaseRefund instead of a bare console.error.

## [HIGH] retail-packages — Duplicate product_ids in one purchase decrement stock more times than the customer is charged for  (3/3, CONFIRMED)
`app/api/salon/retail/purchase/route.ts:78`
- Defect: The charged amount (line 78, `totalAmount = products.reduce(...)`) is computed over `products`, the result of `.in("id", product_ids)` (retail/purchase/route.ts:46-51), which naturally returns at most ONE row per distinct id no matter how many times that id appears in the client-supplied `product_ids` array. The 'never charge a subset' guard (lines 55-64) also compares against `requestedIds = [...new Set(product_ids)]`, i.e. it is dedup-aware and does NOT reject duplicates. But the row actually inserted into retail_purchases (line 99-105) stores the RAW, non-deduped `product_ids` array. The webhook (purchase-handler.ts:127-146) then loops `for (const productId of settledRow.product_ids)` and calls `decrement_retail_stock` once per array ENTRY, including duplicates. So the amount charged reflects one unit while the stock decrement reflects however many times the id was repeated.
- Scenario: A customer (or a scripted client, since this is a client-supplied JSON array with no uniqueness validation in retailPurchaseSchema) POSTs product_ids: ["X","X"] for a single-stock-tracked product X (price 1000 Rappen, stock_count=5). The products query returns exactly one row for X, so `requestedIds.length === products.length` (1 === 1) passes the anti-subset guard, and `totalAmount` = 1000 Rappen (one unit's price) — the customer is charged for exactly one unit. retail_purchases.product_ids is inserted as ["X","X"]. On webhook settle, the loop calls decrement_retail_stock("X") twice, dropping stock_count from 5 to 3 for a single-unit payment. Depending on whether staff/dashboard fulfillment reads retail_purchases.product_ids as the pick list, this is either an inventory-count desync (stock_count silently drifts below physical reality, eventually causing false OUT_OF_STOCK on units the salon still has) or outright free extra stock handed to the customer for the price of one.
- Fix: Deduplicate product_ids once (e.g. use the same `requestedIds` array) before it is ever persisted to retail_purchases or used for stock accounting, and reject or explicitly quantity-aggregate duplicate ids in retailPurchaseSchema so the charged amount and the stock impact are always derived from the same set.

## [HIGH] vouchers-giftcards — POST /api/vouchers/create has zero auth/authz — anyone can mint real Stripe coupons and spoof a customer identity  (3/3, )
`app/api/vouchers/create/route.ts:?`
- Defect: Unlike every sibling money route (gift-cards/purchase, vouchers POST, gift-cards/redeem — all of which call checkFeatureEnabled + supabase.auth.getSession()), this route has NO session check, NO checkFeatureEnabled call, and NO rate limit. It reads `customerId` straight from the request body as a bare `z.string().uuid()` and never verifies it against any authenticated session. It then creates a real Stripe Coupon + PromotionCode (max_redemptions:1), inserts a promo_codes row with `created_by: customerId`, and creates a real PaymentIntent whose metadata.customer_id is that same client-supplied value. The middleware (middleware.ts:46) only adds CORS headers to /api/* — it enforces no auth. Additionally, for percent-off vouchers the 'purchase price' is computed as `purchaseAmount = discountValue` (the raw percent number treated directly as a CHF amount, per the route's own comment 'you may want to set a fixed purchase price') — a 5%-off voucher costs CHF 5, a 90%-off voucher costs CHF 90, an arbitrary/unvalidated mapping.
- Scenario: Any unauthenticated caller POSTs {discountType:'fixed', discountValue:100, customerId: '<a real victim profile UUID>'} to /api/vouchers/create. The route creates a real Stripe Coupon/PromotionCode and a promo_codes row attributed to the victim's UUID with no ownership check, and a PaymentIntent tagged with the victim's customer_id. If the attacker pays the PI (or spams it unpaid to burn Stripe API quota — no rate limit gates coupon/promotion-code creation), the webhook's voucher-handler.ts inserts a voucher_purchases row under the victim's customer_id and emails the promo code to the victim's real address (looked up via admin.auth.admin.getUserById(customerId)) unless the attacker also supplies a different recipientEmail, in which case the code is sent to the attacker's own address while the purchase is attributed to the victim in the audit trail.
- Fix: Add the same auth + feature-flag + rate-limit gate used by every other money route: require a session, derive customerId from session.user.id (never trust the body), and validate the percent-voucher purchase price against a real, bounded price list instead of reusing discountValue as CHF.

## [HIGH] connect-onboarding — account.updated webhook only ever turns accepts_online_payment ON, never back OFF when Stripe later restricts the account  (3/3, )
`app/api/stripe/webhook/route.ts:656`
- Defect: app/api/stripe/webhook/route.ts:656-664: `case "account.updated"` only has `if (account.charges_enabled) { update accepts_online_payment: true }` — there is no `else` branch to set it back to `false` when a later `account.updated` event reports `charges_enabled: false` (e.g. Stripe places the account under review, restricts it for compliance/risk, or requires additional verification, all of which fire additional account.updated events with charges_enabled flipped back to false). The only path that ever sets `accepts_online_payment: false` is the full `account.application.deauthorized` event (line 638-643), which only fires on a complete disconnect, not a partial restriction. No reconciliation cron re-syncs this flag against live Stripe state either (checked app/api/cron/*, only salon-onboarding exists and it's an unrelated email drip).
- Scenario: Salon completes onboarding, charges_enabled flips true, `accepts_online_payment` becomes true in the DB. Three months later Stripe flags the account for a risk review (common for Express accounts, e.g. unusual volume or a filed dispute) and sets charges_enabled=false, firing a new account.updated event. The webhook handler's `if` is false, so it does nothing — `accepts_online_payment` stays `true` in Postgres. Every payment route that reads this flag (create-payment-intent, walkin/pay-intent) keeps creating PaymentIntents with `transfer_data.destination` pointed at that now-restricted account, so customer charges keep getting attempted/captured against an account Stripe has told the platform can no longer process them, with the DB never reflecting reality until someone manually checks Stripe's dashboard.
- Fix: Add an else branch (or explicit boolean assignment `accepts_online_payment: !!account.charges_enabled`) so the flag tracks the CURRENT charges_enabled state on every account.updated event, not just the true transition.

## [HIGH] connect-onboarding — payouts_enabled is never checked anywhere in the codebase — only charges_enabled gates payment routing  (3/3, )
`app/api/stripe/webhook/route.ts:658`
- Defect: Grepped the whole `app/api` tree for `payouts_enabled`: it only appears as a read-only field in the GET /api/stripe/connect/status response (app/api/stripe/connect/status/route.ts:26-42) shown to the dashboard UI. No route or webhook handler ever uses `payouts_enabled` to gate money routing. The only server-side gate (`accepts_online_payment`) is driven exclusively by `charges_enabled` (app/api/stripe/webhook/route.ts:658). Stripe Express accounts routinely have `charges_enabled: true, payouts_enabled: false` for a period (pending identity verification, minimum-balance holds, first-payout review) — this is an independent, well-documented Stripe state, not an edge case.
- Scenario: A newly onboarded salon reaches `charges_enabled: true` (can accept card charges) while `payouts_enabled` is still `false` (Stripe is holding first payouts pending additional verification, common in Stripe's own onboarding flow). The webhook sets `accepts_online_payment: true` on `charges_enabled` alone. Customers begin booking and paying deposits/retail purchases that route via `transfer_data.destination` to that account. The money lands in the connected account's Stripe balance but cannot be paid out to the salon's bank until payouts_enabled flips true — and if it never does (KYC rejected), the funds are stuck in a Connect account the salon can't withdraw from, with the platform having no visibility into or gate against that state.
- Fix: Change the webhook (and ideally the payment-route-time check) to require `account.charges_enabled && account.payouts_enabled` before treating a salon as payment-ready, and re-check payouts_enabled specifically since it's the field that actually gates money reaching the salon's bank.

## [HIGH] money-crons — no-show cron flips booking status to no_show with no re-assert guard, racing any concurrent status change  (3/3, CONFIRMED)
`app/api/cron/no-show/route.ts:43`
- Defect: Step 1 (`await admin.from("bookings").update({ status: "no_show", ... }).eq("id", booking.id)`) has no WHERE guard on the booking's current status at all (not even the ineffective pattern seen in abandon-sweep) despite the SELECT above having required status='confirmed' AND fee_charge_status IS NULL. Whatever the booking's live status is at UPDATE time, this write unconditionally forces it to no_show, and the subsequent no-show fee charge (guarded only by fee_charge_status IS NULL / policy_accepted_at, not by the booking actually being a genuine no-show) will fire.
- Scenario: A booking ends; within the 24h-7day window a customer or salon legitimately cancels it through a different flow (e.g. a goodwill/free cancellation with no fee owed, so fee_charge_status is never set), just before or concurrently with this cron's SELECT (status was still 'confirmed' when read). The cron's step 1 then clobbers that cancellation, overwriting status back to 'no_show', and because fee_charge_status is still null and policy_accepted_at is present, chargeFee proceeds to charge the customer's saved card an off-session no-show fee for an appointment that was properly cancelled with no fee due -- an unauthorized charge plus an incorrect permanent booking status.
- Fix: Add the same current-status re-assert to the UPDATE WHERE clause (.eq("status","confirmed")) and, per the abandon-sweep bug above, actually check whether the update matched a row (via .select() or count) before continuing on to the fee-charge step; skip the fee charge entirely if the guard didn't match.

## [MEDIUM] payout-ledger — salon_payouts.status is written as 'recorded' but never transitioned to 'paid' anywhere, so the earnings dashboard's total_earnings is permanently zero  (3/3, )
`app/api/salon/earnings/route.ts:33`

## [MEDIUM] retail-packages — Concurrent refunds for different amounts on the same purchase bypass the idempotency-key collapse, understating retail_purchases.refunded_amount  (3/3, PLAUSIBLE)
`lib/purchases/issue-purchase-refund.ts:271`
- Defect: The double-refund guard relies on a deterministic Stripe idempotency key `refund:${source}:${id}:${staleRefunded}:${amountCents}` (line 271) plus a CAS on refunded_amount (lines 309-342). The code's own comment (lines 323-334) explicitly assumes 'the Stripe idempotency key is keyed on the SAME staleRefunded' for any concurrent call, which only holds when two requests submit the IDENTICAL amount (a true double-click / retry). If two requests read the same stale refunded_amount but submit DIFFERENT amountCents (e.g. salon route and admin route both acting on the same purchase near-simultaneously, or a UI double-submit with an edited amount field), each computes a distinct idempotency key, so Stripe issues TWO separate real refunds. Only the first request's CAS (eq('refunded_amount', staleRefunded)) succeeds; the second's CAS matches zero rows and the code just re-reads and returns the current (first-refund-only) total — the second, real Stripe refund's amount is never added to refunded_amount.
- Scenario: retail_purchases row has paid_amount=2000, refunded_amount=0. Request A (salon, amount=1000) and Request B (admin, amount=500) both call resolvePurchase within the same read window (both see staleRefunded=0), both pass the EXCEEDS_REMAINING check against remaining=2000, and both call stripe.refunds.create with different idempotency keys (`refund:retail:ID:0:1000` and `refund:retail:ID:0:500`), so Stripe genuinely refunds 1500 Rappen total. Request A's CAS runs first (0->1000, status partially_refunded). Request B's CAS (`eq('refunded_amount', 0)`) matches zero rows since the DB now shows 1000; B falls into the 'concurrent refund' branch and returns totalRefundedCents=1000 (not 1500). retail_purchases.refunded_amount is now permanently stuck at 1000 even though 1500 Rappen has actually left the connected account. A subsequent refund attempt computes remaining = 2000-1000 = 1000 and would try to refund up to that amount; since real remaining on Stripe's charge is actually only 500, Stripe's own API would reject anything above 500 with an error surfaced to the caller as STRIPE_FAILED, and the purchase's refunded_amount/status can never reconcile to reflect reality through this code path.
- Fix: Serialize refund attempts per purchase id (e.g. a short-lived advisory lock or a `SELECT ... FOR UPDATE` on the purchase row spanning the read-through-CAS window) so two refund calls for the same purchase cannot both observe the same staleRefunded before either commits, or fold the Stripe refund itself into the CAS transaction (create the refund only after acquiring the row lock) rather than doing read -> Stripe call -> CAS write with the DB uncontended in between. Note: the salon_payouts ledger is unaffected by this bug since app/api/stripe/webhook/route.ts's charge.refunded handler (line 680) recomputes gross/commission/net from the charge's own cumulative amount_refunded rather than from this CAS total, so payouts stay correct even when retail_purchases.refunded_amount drifts.

## [MEDIUM] vouchers-giftcards — Gift-card redeem race: concurrent redemptions can double-spend a card's balance (currently dormant, no live caller)  (2/3, )
`app/api/gift-cards/redeem/route.ts:?`

Supabase/PostgREST returns NO error when a filtered update matches zero rows — it just returns an empty result set successfully. ## Refuted / not-a-bug
- vouchers-giftcards: vouchers/confirm never binds payment_intent_id to voucher_id before refilling a voucher's balance (dormant, no live caller) (1/3) — The code-level defect is accurately described (no binding check between payment_intent_id and voucher_id, unconditional refill to voucher.amount), but the claimed exploit scenario does not reproduce as stated: "any caller who owns their own succeeded PaymentIntent can reset a STRANGER's voucher."

The route uses createServerSupabaseClient() (app/api/vouchers/confirm/route.ts:25), which is built with the ANON key (lib/supabase.ts:16-29) — so it runs under the caller's own session, RLS-scoped, not service-role. The `vouchers` table has RLS enabled (confirmed live: _inventory/_db-snapshot.json shows rls:true for `vouchers`), and its UPDATE policy is:

CREATE POLICY "vouchers_update_redemption" ON public.vouchers
  FOR UPDATE USING (
    EXISTS (SELECT 1 FROM public.profiles WHERE id = auth.uid() AND role = 'admin')
    OR salon_id IN (SELECT id FROM public.salons WHERE owner_id = auth.uid())
  );
(supabase/migrations/20260401_gift_vouchers.sql:60-64, not modified by any later migration touching this table's UPDATE policy)

This USING clause is evaluated against the voucher row's own salon_id, independent of whatever payment_intent_id the caller supplies. So an arbitrary customer/stranger cannot update someone else's voucher through this endpoint at all — the .update() call would simply match 0 rows for them (RLS silently filters, no error). The only actors who CAN successfully invoke the update are: (a) admins, who already have unrestricted FOR ALL access to vouchers via the dashboard/other paths, or (b) the owner of the specific salon that voucher belongs to, who already has legitimate authority to manage redemption state for their own salon's vouchers (that's literally what "vouchers_update_redemption" was created to allow). A salon owner refilling their own salon's voucher back to full value doesn't gain them anything (they'd be giving away free stored value against their own salon, not extracting money), so there's no plausible attacker incentive.

So the actual missing check (PI not bound to voucher) is real as a code smell, but it is not exploitable by the "stranger with their own payment" scenario the finding describes, because the RLS UPDATE policy already restricts execution to the voucher's own salon owner or an admin — actors who don't need this loophole to have that level of access. Combined with the already-confirmed dormancy (zero live callers per grep across app/ and components/, and the salon-voucher-handler.ts header comment noting the onSuccess callback that would call this route never fires), the practical risk is effectively nil: not reachable by any live caller, and even a direct curl only grants capability to actors who already have it.
