# DEEP AUDIT , ROUND 2 (live-DB-verified) , 2026-07-12

A 12-agent fleet (6 finder agents each paired with a read-only verifier) re-audited the backend across storage, auth, cache/perf, external-facing edges, and a live database census. Of the raw findings produced, 26 survived independent re-verification against the live Supabase project (`tocfnsmxmdxkrcmjzzdw`) and are kept here: **2 CRITICAL, 11 HIGH, 6 MEDIUM, 7 LOW** (one additional CSP finding was REFUTED as a duplicate of a Round 1 item and is dropped). Unlike Round 1, which read the merged tree statically, this round queried live RLS policies, grants, and storage-bucket state directly and traced which routes are actually reachable from the UI, so these findings carry direct proof (curl against the live REST API, `pg_policies`/`information_schema` rows, live row counts) rather than static-code inference alone.

## CRITICAL

### 1. `availability_slots` RLS SELECT policy is fully public, leaking booking PII to anon

**Where**: live policy `availability_slots_select_4c9184_m` on `public.availability_slots` (not present in any migration file in the repo; the original app-owned migration is `supabase/migrations/014_new_schema.sql:209-210`).

**What**: The live SELECT policy's qual is `((EXISTS (SELECT 1 FROM salons s WHERE s.id = availability_slots.salon_id AND s.owner_id = auth.uid())) OR true)`. The trailing `OR true` makes the owner-check dead code: the policy is always true for the `public` role (covers both `anon` and `authenticated`). This was proven live, not just read from policy text: pulling the project's own public anon key and curling the Supabase REST endpoint directly (`/rest/v1/availability_slots?select=id,salon_id,booking_id,client_id,booked_by,price_override,block_reason,status,last_minute_discount_percent`) with zero authentication returned real rows, including `status=booked` rows and non-null `booking_id` values, and a count request confirmed all 9365 rows in the table are dumpable this way.

**Why**: Anyone who copies the anon key out of the page source (trivial, it is meant to be public) can bulk-dump the platform's entire booking-slot table straight through Supabase's own REST API, completely outside the app's auth, rate-limit, and ownership layers. Exposed columns include `booking_id` (links a slot to a real booking), `client_id`/`booked_by` (customer references when populated), `price_override` and `last_minute_discount_percent` (individual pricing/discount data), and `block_reason` (internal owner notes). The original migration intentionally made slot availability public for booking UX, but never intended to expose booking linkage, PII, or internal notes.

**Fix + status**: This is NOT a blind migration fix. Customer-facing availability routes read via the session client (`createServerSupabaseClient`), so the `OR true` is currently load-bearing for public slot display, and the owner's dashboard calendar (also on the session client) needs the PII columns (`booking_id`, `client_id`, `price_override`, `block_reason`) for its own view. A correct fix requires a redesign, one of:
- a security-barrier view that exposes only the safe columns (`id, salon_id, service_id, staff_member_id, starts_at, ends_at, status`) for public reads, with owner-only RLS restored on the base table, or
- moving public availability reads onto the admin client (bypassing RLS deliberately, with the safe column set hardcoded into the query) and keeping owner-only RLS on the base table.

This needs an explicit owner design decision, plus a test-as-non-owner-customer pass (confirm public slot search/booking still works) before applying anything. Do not ship a bare `REVOKE`/policy-tighten without that verification, it will break public availability display.

**Effort**: M (redesign + owner decision required, not a quick patch)

### 2. `profile_summaries` and `public_profiles` views are writable by anon/authenticated

**Where**: `supabase/migrations/027_rls_hardening.sql:44-48` (creates `public_profiles`) and `supabase/migrations/20260712010500_audit_fix_profile_summaries_missing_migration.sql:22-26` (creates the sibling view `profile_summaries`). Live objects: `public.profile_summaries`, `public.public_profiles`.

**What**: Both are simple single-table pass-through views (`SELECT id, display_name, avatar_url FROM profiles`), which Postgres auto-generates as directly writable. Live grants show `anon`/`authenticated` hold INSERT, UPDATE, DELETE, and TRUNCATE on both views, not just the SELECT both migration files intended. Neither view has `security_invoker` set, both are owned by `postgres` (which has `rolbypassrls = true`), so any DML issued against the view runs with RLS bypassed on the underlying `profiles` table. `profiles`' own RLS restricts UPDATE/DELETE to `auth.uid() = id`, and its one relevant trigger only resets privilege columns on UPDATE and does not fire on DELETE at all. `profiles.id` has 15 foreign keys, several with `ON DELETE CASCADE` (including `salons_owner_id_fkey`), so deleting a stranger's profile row cascades into deleting their entire salon plus conversations, messages, waitlist entries, and more.

**Why**: This is exploitable right now with nothing but the public anon API key embedded in every browser bundle, no login required for `profile_summaries`, and only a free signup for `public_profiles`. A caller can `PATCH /rest/v1/public_profiles?id=eq.<any-uuid>` to overwrite a stranger's display name/avatar, or `DELETE` it outright to cascade-delete their salon, straight through PostgREST's auto-exposed REST endpoint, bypassing every app-level check entirely.

**Fix + status**: Fix ALREADY WRITTEN as migration `supabase/migrations/20260712140000_audit_fix_profile_views_writable_critical.sql`. It revokes INSERT/UPDATE/DELETE/TRUNCATE on both views from `anon`/`authenticated` (leaving SELECT intact) and sets `security_invoker = true` on both, so each view runs under the querying user's own RLS instead of the owner's. This has been live-verified as non-breaking: a grep across the app confirms these views are only ever read, never written to, by any current route. Pending owner apply (via the Supabase MCP `apply_migration`, or the normal deploy path).

**Effort**: S (migration already written, just needs applying)

## HIGH

### 1. Upstash/Redis runtime error silently disables rate limiting on abuse-prone surfaces
**Where**: `lib/ratelimit.ts:179` and `lib/ratelimit.ts:217-220`.
**What**: `ABUSE_PRONE_LIMITERS` (auth, payment, booking, guest-lookup, referral, resend-access, walk-in-anon-join) correctly fail CLOSED when Upstash is unconfigured. But the separate catch block for a live runtime error from `limiter.limit(key)` itself (timeout, 5xx, network blip, an actual outage) does not check `ABUSE_PRONE_LIMITERS` at all: it logs to `console.error` and then lets the request through for every limiter, including the abuse-prone ones. No alert is fired either.
**Why**: A live Upstash incident is at least as likely in production as the config being unset. During any such incident, credential stuffing on auth, payment-attempt abuse, booking spam, and the enumeration oracles (guest lookup, referral validation, resend-access) all run completely unthrottled, with nothing but a console log nobody watches in real time to notice it happened.
**Fix**: In both catch blocks, check `ABUSE_PRONE_LIMITERS.has(limiter)` the same way the unconfigured-Redis branch does (return 429/false for those), and call an alert function (e.g. `alertMisconfiguredRedisOnce()` or a sibling) so a live outage pages someone instead of only logging.
**Effort**: S

### 2. Non-httpOnly Supabase session cookie removes the main defense against session theft
**Where**: `lib/supabase.ts:27` (`createServerSupabaseClient`) and `:72` (`createAdminSupabaseClient`), plus `middleware.ts:116`, `app/api/dev/login/route.ts:42`, `app/api/auth/callback/route.ts:28`.
**What**: None of these calls to `@supabase/ssr`'s `createServerClient()` pass a `cookieOptions` override. The pinned version (0.5.2) defaults to `httpOnly: false`. A grep across the whole repo for `cookieOptions` returns zero hits, no override exists anywhere. By contrast, the app's own hand-rolled guest-access cookie (`lib/bookings/guest-access.ts:117-124`) explicitly sets `httpOnly: true`, proving the team applies this correctly elsewhere but missed the primary Supabase-managed session cookie.
**Why**: This does not create XSS on its own, but it removes the single biggest mitigation against session theft once any XSS exists anywhere on the site (a stored XSS in a salon description, review, or chat message would be enough). With `httpOnly: false`, injected script can read the raw session cookie directly, turning any future XSS bug into full account takeover instead of a contained UI bug. There is currently no CSP header either, so there is no compensating control.
**Fix**: This is an architectural tradeoff, 11 client components read the session via `document.cookie`/`getSession()` for instant UI state, so `httpOnly` cannot simply be flipped without reworking those call sites. Two real paths: (a) accept the tradeoff but add a CSP header to sharply cut off the realistic XSS vector, or (b) migrate client components off direct cookie reads onto `onAuthStateChange` or a small server-state endpoint, then set `httpOnly: true`. Needs an explicit owner call, not a pure bugfix.
**Effort**: M

### 3. One-click email cancel/confirm link fires the destructive action automatically on page load
**Where**: `app/[locale]/booking-action/page.tsx:20-38` (the landing page), calling `app/api/bookings/[id]/quick-action/route.ts:38`.
**What**: The quick-action route is a public GET gated only by a self-contained HMAC token in the query string (so classic cookie-based CSRF does not apply). Its only caller fires the state-changing fetch unconditionally inside a `useEffect` the instant the page mounts, with no "click to confirm" step, and the token has no server-side single-use/consumed marker, so it stays valid and replayable until its expiry timestamp passes.
**Why**: Corporate email link-scanners (Microsoft Defender for Office 365 Safe Links, Proofpoint, Mimecast) commonly prefetch and headlessly render linked pages before the recipient opens the email, and Swiss business email runs largely on Microsoft 365. If a cancel/confirm link is emailed and a scanner renders the landing page, the fetch fires automatically and silently cancels a real, paid booking (running the refund-minus-fee logic) or auto-confirms one, before the actual customer or salon has seen or clicked anything.
**Fix**: Require an explicit user click before firing the mutating request (render "Cancel this booking?" with a real Confirm button), and make the token single-use by writing a `consumed_at` marker checked/set atomically in the same query.
**Effort**: S

### 4. Review-photo, salon-document, and formula-photo uploads all target storage buckets that do not exist live
**Where**: `app/api/reviews/[id]/photos/route.ts:63` (uploads to `review-photos`), `app/api/salon/documents/route.ts:55,91` (uploads to `salon-documents`), `app/api/dashboard/coiffeur/formula-photo/route.ts:72,83` (uploads to `formula-photos`).
**What**: The live project has exactly 10 storage buckets and none is named `review-photos`, `salon-documents`, or `formula-photos`. For review-photos, the root cause was traced: `supabase/migrations/005_reviews_trust.sql:42` would create the bucket, but that migration was never applied (confirmed via the live migrations table and via the absence of the columns that same migration would add to `reviews`). The other two buckets have no creation migration in the repo at all.
**Why**: All three upload endpoints are completely broken in production, `storage.upload()` fails with a bucket-not-found error. Salon-documents fails loudly (a 500), but review-photos fails silently: its per-file upload loop swallows errors with `continue` and unconditionally returns `{success: true, photos: uploadedRecords}` even when every file failed and `uploadedRecords` is empty. A customer attaching photos to a review sees a 200 success response with zero photos actually saved, the exact silent-no-op failure class this project already treats as its top recurring bug pattern.
**Fix**: Create the three missing buckets live (mirroring `005_reviews_trust.sql`'s bucket + policy pattern for review-photos, plus new equivalents for the other two with appropriate mime/size limits and RLS). Separately, fix the review-photos route so a per-file upload failure surfaces in the response instead of unconditionally reporting success.
**Effort**: M

### 5. Client-photo uploads store a `getPublicUrl()` link for a bucket that is actually private
**Where**: `app/api/clients/[id]/photos/route.ts:93`.
**What**: The live `client-photos` bucket has `public: false`, but the route calls `.getPublicUrl(path)` anyway and saves that constructed URL into `client_photos.photo_url`. `getPublicUrl()` builds the URL string client-side without checking the bucket's real public flag, so against a private bucket the resulting URL always 400s/403s for any viewer, including the rightful salon owner.
**Why**: Currently latent, a repo-wide grep found zero frontend consumers of `client_photos` and zero uses of `createSignedUrl` anywhere in the codebase, so no UI renders these photos yet. But the moment a client-photo gallery is wired up (a natural next step for this feature), every photo will render as a broken image, because the URL the API itself returns and stores can never resolve.
**Fix**: Since the bucket is intentionally private (salon-scoped), switch to `createSignedUrl(path, expirySeconds)` generated on read, or store just the raw storage path and mint a signed URL per request. Do not persist a `getPublicUrl()` result for a non-public bucket.
**Effort**: S

### 6. `chat-media` storage INSERT policy has no folder-ownership check
**Where**: live storage policy on `storage.objects` for bucket `chat-media` (not present in any tracked migration, grep across `supabase/migrations` for `chat-media` returns zero files).
**What**: The INSERT policy's `with_check` is only `bucket_id = 'chat-media'`, no restriction on which folder is targeted. The sibling DELETE policy on the same bucket correctly restricts to `auth.uid()::text = (storage.foldername(name))[1]`, so the write path was never given the same ownership scoping the delete path already has.
**Why**: Any authenticated user can write into any other user's chat-media storage path directly against the Supabase Storage REST API, no app code required, since a repo-wide grep found zero frontend references to `chat-media` at all. The chat/messaging feature is recorded as fully OFF at the product level, but the RLS gap is a database-level hole that exists regardless of the current UI, and would allow storage abuse or spoofed-attachment planting the moment the feature is re-enabled without someone separately noticing this policy.
**Fix**: Add the same folder-ownership predicate the DELETE policy already uses to the INSERT policy (`with_check: bucket_id = 'chat-media' AND auth.uid()::text = (storage.foldername(name))[1]`), and land it as a migration so it is reproducible instead of live-only.
**Effort**: S

### 7. Staff/staff-earnings commission is computed from the service's list price, not what the customer actually paid
**Where**: `app/api/earnings/staff/route.ts:41`.
**What**: The route selects the joined `services(price)` (current list price) as the gross basis for every completed booking, and never reads `bookings.price_paid` (the amount actually charged after promo/member discounts, manual overrides, or edits to the service's price since the booking happened). A live join proved 5 real bookings currently diverge, e.g. one booking has `price_paid = 80.00` against a `services.price` of `180.00`, a 100 CHF gap.
**Why**: This is the same root-cause family Round 1 already flagged for the admin revenue route (summing quoted price instead of captured amount), but it was never checked against this sibling route. A salon owner viewing the staff earnings/commission dashboard sees a wrong gross, and therefore a wrong staff share and house share, for any booking whose price was discounted, overridden, or edited after the fact, a real money-calculation bug on a page owners use to decide payouts.
**Fix**: Select `price_paid` on the bookings query instead of the joined service price, and use it as the per-booking gross before applying `commission_rate`.
**Effort**: S

### 8. Admin seed/test-data routes have zero production guard
**Where**: `app/api/admin/seed-test-salons/route.ts:111`, `app/api/admin/test-salon/route.ts`, `app/api/admin/test-salon/seed/route.ts`.

**Fix**: Add the same `NODE_ENV`/`CONTEXT` production check `app/api/dev/login/route.ts` already uses (404 on a real production boot) to all three routes.
**Effort**: S

### 9. Live intake-AI-recommendation button is still prompt-injectable; Round 1's fix landed on a dead route
**Where**: `app/api/ai/recommend/route.ts:39-50` (live, called from `components-legacy/dashboard/IntakeFormTab.tsx:94-101`); the fixed sibling `app/api/ai/intake-recommendation/route.ts` has zero callers anywhere in the frontend.
**What**: Round 1 reported the intake-text-into-AI-prompt injection risk and applied a `sanitizeAnswer()` + delimiter guard, but to `intake-recommendation/route.ts`, which nothing in the app calls. The actual live button calls `/api/ai/recommend` instead, which interpolates free-text intake answers directly into the Gemini prompt with zero sanitization, no delimiters, and no length guard beyond a 5000-char zod max.
**Why**: This is the real live attack surface for the exact bug class Round 1 thought it had closed. **Fix**: Apply the exact same `sanitizeAnswer()` + delimiter pattern already written for the sibling route to `app/api/ai/recommend/route.ts`'s `intake_summary` before interpolating it. Separately, decide whether `intake-recommendation/route.ts` should replace `recommend/route.ts` (then retire the dead one per the project's `REMOVED.md` convention) or whether both need the guard.
**Effort**: S

### 10. `create_group_booking` does not verify the client-supplied `salon_id` against the slot/service/staff actually being booked
**Where**: live SECURITY DEFINER function `public.create_group_booking`, called from `app/api/bookings/group/route.ts:29-51`.
**What**: The function's only authorization check is that the caller is logged in. For each group member it checks the slot is available and reads the service's price, then inserts the booking using the client-supplied `p_salon_id` verbatim, never checking that the slot's, service's, or staff member's actual `salon_id` matches `p_salon_id`. The route handler passes `salonId` straight from the request body with only a presence check, no cross-salon validation either.
**Why**: Any authenticated user can submit a group booking whose `slot_id` is a real available slot at Salon A but whose `salon_id` in the payload is Salon B: the function marks Salon A's slot booked (blocking it from real customers) while writing a booking attributed to Salon B, corrupting Salon B's calendar with a booking it never received and desyncing Salon A's slot inventory. This is the same bug class already known and flagged for the express-rebook confirm route, in a completely different code path Round 1's booking audit never inspected.
**Fix**: Inside `create_group_booking`, before the member loop, resolve each `availability_slots.salon_id` (and `staff_members.salon_id`/`services.salon_id` if supplied) and raise an exception if any differ from `p_salon_id`, mirroring whatever fix ships for the express-rebook finding.
**Effort**: S

### 11. `slots/last-minute`'s `revalidate = 60` is a silent no-op
**Where**: `app/api/slots/last-minute/route.ts:4` (the `revalidate` directive) and `:12` (the client call that defeats it).
**What**: The route sets `export const revalidate = 60` but calls `createServerSupabaseClient()`, which calls Next.js's `cookies()` internally. Calling `cookies()` anywhere in a route handler forces that route into dynamic rendering, opting it out of ISR entirely, per Next.js's documented Dynamic APIs behavior. This route never reads any session or personalization data, it is a plain public browse query, so the cookie read serves no purpose except to accidentally kill the caching. Two sibling routes in the same codebase (`app/api/salons/trending/route.ts`, `app/api/analytics/platform/route.ts`) explicitly document this exact gotcha and deliberately use `createAdminSupabaseClient()` instead so their `revalidate` directives actually work.
**Why**: This is exactly the "control that looks wired but does nothing" pattern this codebase calls out as its top silent-failure mode. Someone reading this file reasonably assumes the route is cached for 60 seconds, but every request re-runs the full 3-way join query with zero caching, on a public unauthenticated endpoint that also has no rate limit.
**Fix**: Swap `createServerSupabaseClient()` for `createAdminSupabaseClient()`, identical to the pattern already used in `trending/route.ts` and `analytics/platform/route.ts`. One-line import + call swap.
**Effort**: S

## Cross-reference to Round 1

Round 1 was a static, read-only pass over the merged tree and its own advisor output, so it caught the generic Supabase-advisor lint for `profile_summaries`/`public_profiles` ("security_definer_view... enforces the creator's RLS") but never queried `information_schema.role_table_grants` or `is_updatable`, so it never found that both views are actually writable and cascade-deletable. It never opened `availability_slots`' live policy at all (a zero-hit grep against both Round 1 reports confirms this), since that policy exists only live and not in any migration file, invisible to a tree-only read. Round 1 also correctly diagnosed and fixed the intake-text prompt-injection bug, but fixed it on `intake-recommendation/route.ts` without tracing which of the two near-identical routes the UI actually calls, so the live `recommend/route.ts` path stayed exposed. Round 2 closed all three gaps by querying live grants and policies directly and by grepping the frontend for actual callers before trusting a route's presence as proof it is used.
