# Onboarding / registration backend — bug & gap audit (2026-07-09)

3 finders (salon-registration / customer-onboarding / onboarding-edges) x 3-skeptic verify; several confirmed vs LIVE DB. 9 confirmed (deduped), 0 refuted. (Known go-live/Connect findings not repeated.)


---

## [CRITICAL] customer-onboarding — Unrated OTP brute-force lets an attacker claim ANY unclaimed salon_directory listing (business impersonation, permanent lockout of the real owner)  (3/3, )
`app/api/directory/[id]/claim/route.ts:39`
- Defect: POST /api/directory/[id]/claim is fully unauthenticated and has zero rate limiting on either step (no applyRateLimit import/call anywhere in the file). Step 2 verifies a 6-digit numeric code (1,000,000 possibilities) against the stored hash with no attempt counter, no lockout, no CAPTCHA, and a 15-minute expiry window. An attacker who does not control the listing's real email can simply POST guesses of `{code}` in a tight loop; at any meaningful concurrency the full keyspace is exhaustible well inside the 15-minute window. On a correct guess the route immediately sets `is_claimed = true` and hands back the real business's name/address/phone/website/categories for pre-fill into registration.
- Scenario: Attacker enumerates public /api/directory listings, picks a real, reputable, unclaimed salon (name, address, phone, categories all real). They call POST /api/directory/<id>/claim (no body) to trigger code generation (this alone can also be spammed to email-bomb the real owner, since there's no rate limit on step 1 either), then brute-force POST /api/directory/<id>/claim with `{code}` guesses in a loop. Once a guess lands, `is_claimed` flips true (permanently blocking the legitimate owner from ever claiming their own listing through this flow) and the attacker receives the real business's identity data, which they feed into POST /api/salons to register a salon under their own account using that business's real name/address/phone. Combined with the already-known go-live self-activation gap, the attacker's impostor salon can then go live and take real customer payments while impersonating an established business.
- Fix: Add per-listing and per-IP rate limiting (applyRateLimit) on both the code-generation and code-verification steps, cap verification attempts per code (e.g. 5, then invalidate and require a fresh send), and use a cryptographically random code generator with constant-time comparison instead of a plain hash equality check.

## [CRITICAL] onboarding-edges — IDOR in salon re-verification endpoint lets any authenticated user reset ANY salon's verification/freeze status  (3/3, CONFIRMED)
`app/api/salons/verify/route.ts:22`
- Defect: The monthly `salon-verification` cron (supabase/functions/salon-verification/index.ts) escalates warnings on stale salons and auto-freezes (`is_active:false` + cancels bookings) after 3 unanswered warnings over ~2 months. The 'confirm' link it emails encodes an UNSIGNED token: `btoa(JSON.stringify({salon_id, owner_id, exp}))` (index.ts line 43). But the confirm route treats that string as if it were a real Supabase access-token JWT: `admin.auth.getUser(token)` (line 22). This call only succeeds for an actual signed Supabase JWT, so (a) the real cron-generated links can never work (they are base64 JSON, not a JWT, so `admin.auth.getUser` always errors -> 'invalid_token', a dead/broken feature), and (b) if the caller instead supplies THEIR OWN ordinary login access token as `token`, `admin.auth.getUser` succeeds and returns their own (unrelated) user object. The code then does `const salonId = user.app_metadata?.salon_id ?? searchParams.get('salon_id')` (line 29) - for any normal user, `app_metadata.salon_id` is unset, so `salonId` falls back to the attacker-supplied query parameter with NO check that this user owns, works at, or has any relationship to that salon. It then unconditionally does `admin.from('salons').update({ last_verified_at: now, verification_warnings: 0 }).eq('id', salonId)` (lines 34-37).
- Scenario: Any logged-in user (a brand-new customer signup is enough) grabs their own Supabase access token (from the browser session/cookies) and calls `GET /api/salons/verify?token=<their own access token>&salon_id=<any target salon UUID>`. The response redirects to `/de/dashboard?verify=success`, and the target salon's `verification_warnings` is reset to 0 and `last_verified_at` bumped to now - permanently defeating the abandonment/inactivity-freeze safety net for ANY salon on the platform (including salons the caller has zero relationship to), regardless of whether that salon's actual owner ever re-confirms anything.
- Fix: Stop parsing this custom token through `admin.auth.getUser()` (it isn't a Supabase JWT). Verify it as a signed, server-issued token (HMAC-signed JWT or a random opaque token stored server-side with an expiry), decode salon_id/owner_id only from the verified payload, and never fall back to a client-supplied `salon_id` query parameter. Also re-check that the resolved salon_id actually matches the row being updated before writing.

## [HIGH] salon-registration — Directory-listing claim code has no rate limit, brute-forceable in minutes  (3/3, )
`app/api/directory/[id]/claim/route.ts:39`
- Defect: The claim flow (POST /api/directory/:id/claim) sends a 6-digit numeric verification code to the listing's email and, in the same route, accepts { code } to verify it (lines 39-77). Neither the code-request step nor the code-verify step calls applyRateLimit / any limiter (grep for generalLimiter/authLimiter/adminLimiter/applyRateLimit in this file returns nothing), and middleware.ts has no global rate limiting either (confirmed no ratelimit reference in middleware.ts). The code space is only 1,000,000 combinations and is valid for 15 minutes (line 88: Date.now() + 15*60*1000).
- Scenario: Attacker looks up a competitor's salon_directory id (the directory listing list is itself publicly readable via GET /api/directory), triggers step 1 to mint a code for that listing's email, then scripts step 2 with body.code cycling 000000..999999 against POST /api/directory/<id>/claim with no throttling. At even a modest 200 req/s (trivial for an unthrottled Next.js route) the full keyspace is exhausted in under 90 minutes and the correct code is expected to be found well inside the 15-minute expiry window on repeat attempts (request a new code, keep guessing). Once a guess hits, is_claimed flips to true for that listing without the attacker ever receiving the real owner's email, letting them take over the pre-fill data (name, address, phone, email) for onboarding a real salon under that identity.
- Fix: Add applyRateLimit(authLimiter, {...}) (or a dedicated tight limiter) to both the code-request and code-verify branches, keyed by directory id + IP, and add a server-side attempt counter that invalidates the code after e.g. 5 wrong guesses (not just a 15-minute TTL).

## [HIGH] customer-onboarding — Admin salon-approval is fully bypassable: an owner can self-flip is_active (the marketplace-listing gate) via /api/salon/go-live without any admin review ever happening  (3/3, )
`app/api/salon/go-live/route.ts:57`
- Defect: The `is_active` column is the actual gate GET /api/salons uses for public marketplace listing (`.eq('is_active', true).eq('listed_on_marketplace', true)`, and `listed_on_marketplace` defaults to `true` at the DB level per supabase/migrations/20260602120000_walkin_foundations.sql:43). Both /api/admin/salons/[id]/approve (admin-only, role check present) and /api/salon/go-live (owner-only, no admin involvement) write to this SAME column with the SAME effect. The admin approve/reject endpoints therefore are not the gate they appear to be: any salon owner can independently set is_active=true themselves the moment they satisfy 3 lightweight, self-controlled criteria (stripe_account_id present, 1 cover photo URL, 1 active service) with zero human vetting of the business. This is a distinct authorization-model gap from the already-confirmed narrower issue (that the stripe check only looks at account existence, not charges_enabled/payouts_enabled/details_submitted) -- even if that stripe check were fixed to be fully rigorous, the admin-approval workflow would still be entirely optional/dead-letter for any owner who uses the self-serve path instead of waiting for admin review.
- Scenario: A salon owner completes onboarding (POST /api/salons, is_active defaults false), connects Stripe (creating an Express account without finishing KYC/bank details per the already-confirmed finding), uploads any cover photo, and adds one CHF 1 service. They call POST /api/salon/go-live directly (or via the dashboard's normal go-live button) and their salon goes live and publicly bookable/searchable immediately, with no admin ever reviewing the listing, no fraud check, no manual approval step exercised at all -- despite the admin approve/reject endpoints existing and implying that human review is the intended gate.
- Fix: Decide the intended model explicitly: either (a) require an admin-set flag (e.g. approved_at IS NOT NULL) as an additional precondition inside POST /api/salon/go-live before it will set is_active=true, making self-serve go-live and admin approval work together rather than as two independent full-bypass paths, or (b) if self-serve go-live is the intended product design, remove/repurpose the admin approve/reject endpoints so they aren't misleadingly implying a mandatory review step that never actually gates anything.

## [HIGH] onboarding-edges — Salon categories are never validated against the canonical service_categories taxonomy on create or update  (3/3, CONFIRMED)
`app/api/salons/[slug]/route.ts:64`
- Defect: `createSalonSchema.categories` in lib/validations.ts (line 230) is `z.array(z.string()).min(1)` with no enum/whitelist against the 67-row `service_categories` canonical taxonomy, so registration accepts arbitrary strings. Separately, the owner-facing `PATCH /api/salons/[slug]` handler includes `categories` in its generic `allowed` passthrough list (line 66) and assigns `updates[key] = body[key]` directly (line 105) with zero schema validation (only the money-adjacent POLICY_KEYS subset gets Zod-validated, categories is not one of them).
- Scenario: A salon owner (or admin acting on any salon) calls `PATCH /api/salons/<their-salon-slug>` with `{ categories: ["nails", "massage", "spa"] }` for a barbershop that only does haircuts, or with garbage/oversized/malformed values (arbitrary strings, huge arrays, even non-string JSON since there's no type re-check beyond what JSON.parse produced). The salon then surfaces in discovery/search category filters it has no legitimate business being in, or silently breaks downstream taxonomy-bridge logic (hair->coiffeur, beard->barbershop) that assumes categories come from the known 67-row set.
- Fix: Validate `categories` against the live `service_categories` slugs (a proper zod enum/refine backed by that table, or a DB check constraint) at both the registration (`POST /api/salons`) and settings-update (`PATCH /api/salons/[slug]`) paths.

## [MEDIUM] customer-onboarding — createSalonSchema.categories accepts arbitrary strings, no server-side taxonomy whitelist  (3/3, )
`lib/validations.ts:230`
- Defect: `categories: z.array(z.string()).min(1)` has no enum/whitelist constraint against the canonical category set (lib/constants/categories.ts CATEGORY_OPTIONS, or the 67-row service_categories taxonomy). The onboarding UI (app/[locale]/onboarding/salon/page.tsx) only offers the whitelisted CATEGORY_OPTIONS client-side, but POST /api/salons has no matching server-side check, so any direct API caller can set salons.categories to arbitrary/garbage strings.
- Scenario: A caller POSTs directly to /api/salons with `categories: ["<script>", "totally-not-a-real-category", "coiffeur"]`. The insert succeeds. The salon is then invisible to every legitimate `.contains('categories', [category])` search filter for real categories it should logically belong to (a self-inflicted but customer-facing silent no-op), and any downstream code that assumes categories are always one of the canonical taxonomy values (discovery bridging logic, category-specific dashboards) can behave unpredictably on the garbage value.
- Fix: Add `z.enum([...VALID_CATEGORY_SLUGS])` (sourced from lib/constants/categories.ts, the same list the UI already uses) to the categories field in createSalonSchema.

## [MEDIUM] onboarding-edges — Directory-listing claim OTP has no rate limiting or lockout, and the endpoint requires no authentication at all  (3/3, CONFIRMED)
`app/api/directory/[id]/claim/route.ts:39`
- Defect: This route has no session/auth check whatsoever (fully anonymous, no `createServerSupabaseClient`/session lookup anywhere in the file) and imports no rate limiter (confirmed: no `applyRateLimit`/`ratelimit` import in the file, unlike its sibling `app/api/directory/route.ts` which does use `generalLimiter`). The step-2 code check (lines 39-57) compares a client-supplied 6-digit code against a stored hash with no per-IP/per-listing attempt counter or lockout, and the project-wide `middleware.ts` only adds CORS headers to `/api` routes, no rate limiting. The 6-digit code space (900,000 values) combined with a 15-minute TTL and zero throttling means it is brute-forceable by an unauthenticated caller. A successful (or lucky) guess sets `is_claimed:true` permanently with no linkage to any real account, and the verified response also returns the listing's full unmasked email (line 74) versus the masked version shown at step 1 (line 108).
- Scenario: An anonymous caller (no login required) hammers `POST /api/directory/<id>/claim` with `{code: "000000"}` through `{code:"999999"}` in parallel within the 15-minute window; nothing in the route or platform layer throttles or locks them out. On a hit, the listing becomes permanently `is_claimed=true` with no owner tie, which (since the code's own guard at line 32-34 rejects any further claim attempt on an already-claimed entry) can lock the real business out of ever completing this claim flow, and leaks the full business email.
- Fix: Add `applyRateLimit` (per-IP and per-listing-id) to both steps of this route, add a stored failed-attempt counter that invalidates the code after e.g. 5 wrong guesses, and require the caller to be authenticated (bind the resulting claim to `user.id` rather than leaving it anonymous) so a successful claim can't be disconnected from any account.

## [LOW] salon-registration — Salon registration accepts arbitrary category strings, not the canonical taxonomy  (3/3, )
`lib/validations.ts:230`
- Defect: createSalonSchema validates categories as z.array(z.string()).min(1) (line 230), not z.array(salonCategory) even though the canonical enum salonCategory = z.enum(["coiffeur","barbershop","nails","spa"]) is defined two lines above (line 223) and exported as SALON_CATEGORY_SLUGS. The same laxness applies to each service's category field in the services array (line 248: category: z.string().optional()). /api/salons POST (app/api/salons/route.ts line 711) inserts validated.categories directly into salons.categories with no server-side re-check against the enum.
- Scenario: A salon owner submits categories: ["totally-made-up-category"] during onboarding. The insert succeeds (categories is just a text array/jsonb column with no DB-level check constraint reference confirmed), the salon can still complete go-live, but it will never match any .contains("categories",[category]) search/category-page filter used across app/api/salons/route.ts, by-category, similar, quartier-counts, etc., silently vanishing from all category-based discovery even though it is_active=true and listed_on_marketplace.
- Fix: Change categories to z.array(salonCategory).min(1) (and the per-service category field to salonCategory.optional()) in createSalonSchema so registration rejects invalid taxonomy values instead of silently admitting salons that can never be found by category.

## [LOW] customer-onboarding — customer_preferences accepts unbounded, unvalidated JSON (z.any()) on the session user's own profile  (3/3, )
`lib/validations.ts:125`
- Defect: updateProfileSchema's `customer_preferences: z.any().optional()` places no shape, key-count, or size constraint on the JSONB blob PATCH /api/profile writes. The write is correctly scoped to the session user (`.eq('id', user.id)` using user.id from the server-derived session, and the schema's `.strict()` top-level check does block privileged fields like role/is_admin/staff_salon_id/tier from being smuggled in, so no cross-user or privilege-escalation path was found here). The residual risk is data-integrity/DoS-on-own-account scoped: a caller can store an arbitrarily large or arbitrarily-shaped object (megabytes of nested junk, wrong types for `persona`/`interests`/`categories`) that other code assumes has a specific small shape (e.g. app/api/persona/hair-dna/route.ts reads `prefs.persona` and casts it to PersonaSelection with no runtime validation).
- Scenario: A caller PATCHes their own profile with `customer_preferences` set to a several-MB nested object, or with `interests` as a deeply nested object instead of a string array. Nothing rejects it; it stores as-is in their own profiles row. Later reads (hair-dna derivation, ForYouSalonRows, useCustomerPrefs) that assume `interests` is a flat string array or `persona` is a small selection object receive whatever shape was stored, with only loose `as` casts and no runtime guards, so malformed data can silently produce wrong personalization output for that one user (self-contained blast radius, not cross-user).
- Fix: Give customer_preferences a real zod shape (or at minimum a size cap and key/array-length caps) instead of z.any(), covering the known sub-keys (persona, interests, categories, skinType) actually read elsewhere in the codebase.
