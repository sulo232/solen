### [HIGH] auth-routes — Auth rate limiting keyed on a client-spoofable X-Forwarded-For header  (3/3, CONFIRMED)
`lib/ratelimit.ts:139`
- Defect: `getClientIp()` takes `req.headers.get("x-forwarded-for")?.split(",")[0]` - the FIRST (leftmost) entry of the XFF chain - which by the XFF convention is the value the ORIGINAL requester supplied, not a value guaranteed to be added by a trusted proxy. The code performs no validation that the request actually came through the expected number of trusted hops, and doesn't fall back to a platform-verified header (e.g. Netlify's `x-nf-client-connection-ip`) or `request.ip`. Every consumer of `applyRateLimit`/`authLimiter` (login, signup, password reset, verify-otp, the callback route, verify-phone send/check) keys its 5-req/min bucket off this same spoofable value.
- Scenario: An attacker sends repeated POST /api/auth/login (or /signup, /verify-otp, /verify-phone/check) requests each with a different, self-chosen `X-Forwarded-For: <random-ip>` header. Each request is bucketed under a fresh identifier in Upstash, so the 5-per-minute sliding window never trips, defeating the only brute-force/spam defense on every credential-guessing, OTP-guessing, and password-reset-spam surface in the auth system.
- Fix: Use the platform-trusted client-IP source only (on Netlify, prefer `x-nf-client-connection-ip`, or configure/verify the exact number of trusted proxy hops before trusting XFF), and never let client-supplied headers alone determine the rate-limit key for a security control.

### [HIGH] authz-escalation — Referral-completion endpoint grants CHF 10 credit to any two accounts with no real qualifying action (booking/purchase) required  (3/3, )
`app/api/referral/complete/route.ts:26`
- Defect: POST /api/referral/complete uses createAdminSupabaseClient (bypasses RLS) and credits CHF 10 to both the referrer and the calling user based solely on a client-supplied referral_code, with no verification that the calling (referred) user has completed any qualifying action such as a paid booking. It only checks: (1) the code exists and is still 'pending', (2) the caller isn't the exact same user_id as the referrer, (3) the caller has never redeemed a code before. The intended/canonical referral-completion flow (app/api/bookings/route.ts lines ~557-630) DOES gate completion on an actual booking being created, but this standalone endpoint is a second, live, reachable code path that completely bypasses that gate. Every completion also auto-generates a fresh pending code for the referrer (via the same insert at the end of the handler), so the referrer's code supply never runs out.
- Scenario: Attacker controls account A (any real signup, gets a referral code for free from /profile/referral, which every user has). Attacker creates burner account B (disposable email), logs in, and calls POST /api/referral/complete with body {"referral_code": "<A's code>"}. No booking, no payment, nothing beyond signup is required. Response: both A and B are credited CHF 10 via user_credits inserts, and a fresh pending code is generated for A. Attacker repeats with burner accounts C, D, E... Each burner account can call this once (existingReferral check blocks a second use per account) but is otherwise rate-limited only at 10 calls per 30 days PER CALLING ACCOUNT (referralLimiter keyed on the redeemer's own user.id, not the referrer) -- so the limiter does nothing to cap how many different burner accounts can drain value into a single referrer account A. This is a direct path to manufacture spendable CHF credits at zero cost, exploitable by anyone who can create disposable email accounts.
- Fix: Require server-side proof of a qualifying event (e.g. the referred user's first completed/paid booking) before crediting, mirroring the logic already correctly implemented in app/api/bookings/route.ts. Either remove this standalone endpoint entirely (the booking-time completion path already exists and is the one actually wired into the frontend -- no .tsx file calls /api/referral/complete) or gate it behind the same booking-completion check. Also fix the rate limiter to key on the referrer_id in addition to (or instead of) the redeemer's user.id, since the current limiter caps the wrong party.

### [HIGH] admin-get-idor-sweep — IDOR: /api/dashboard/barber-leaderboard leaks any salon's staff revenue/bookings to any authenticated user  (3/3, CONFIRMED)
`app/api/dashboard/barber-leaderboard/route.ts:?`
- Defect: The GET handler only checks that a Supabase session exists (`authError || !userData?.user`) and never verifies that the caller owns (or is admin for) the `salon_id` passed in the query string. It then uses `createAdminSupabaseClient()` (bypasses RLS) to read `staff_members`, `bookings` (including `price_paid`), and `barber_walkin_queue` filtered only by the attacker-supplied `salon_id`, and returns per-staff-member revenue, booking counts, and walk-in conversion rates.
- Scenario: Any logged-in Solen user (customer account is enough) calls `GET /api/dashboard/barber-leaderboard?salon_id=<victim-salon-uuid>&period=month` with their own valid session cookie. The response returns the victim salon's staff names, booking counts, and total revenue per staff member for any period, with no ownership check at any point in the handler.
- Fix: Add the same ownership/admin check every sibling dashboard route uses: resolve `salons.owner_id` for the given `salon_id` (or use `getActiveSalon`) and 403 if `owner_id !== user.id` and the caller is not `profiles.role === 'admin'`, before running the queries.

`app/api/dashboard/walkin-analytics/route.ts:?`

### [MEDIUM] auth-routes — Open redirect in OAuth/magic-link callback via backslash URL normalization  (2/3, CONFIRMED)
`app/api/auth/callback/route.ts:14`
- Defect: The redirect-target sanitizer only blocks paths starting with `/` followed by `//` (protocol-relative URLs): `redirect = rawRedirect.startsWith("/") && !rawRedirect.startsWith("//") ? rawRedirect : "/de"`. It does not account for the fact that `new URL(redirect, origin)` (line 20) treats backslashes as forward-slash separators per the WHATWG URL spec. I verified with `new URL("/\\evil.com", "https://solen.ch")` -> `https://evil.com/`. A value like `/\evil.com` (or `/\/evil.com`, `/	/evil.com`) passes the `startsWith("/") && !startsWith("//")` check yet resolves to an external origin.
- Scenario: GET /api/auth/callback?code=<a valid, self-obtained PKCE code>&redirect=%2F%5Cevil.com . `code` must be one legitimately issued to the requesting browser (PKCE code_verifier cookie must match), so this cannot hijack an arbitrary victim's session in isolation, but it lets anyone mint a genuine solen.ch-hosted link (own or via a real confirmation/magic-link email whose `redirect` query is otherwise never attacker-influenced from the two current call sites) that authenticates normally and then 302-redirects the browser to an attacker-controlled domain. That is a classic open-redirect abused for phishing (a link that visibly starts with https://solen.ch/... to defeat spam/link-preview filters, then bounces to a fake login/payment page) and for laundering trust in outbound campaigns.
- Fix: Reject any redirect value containing a backslash before the startsWith checks (or, more robustly, parse with `new URL(redirect, origin)` and assert `result.origin === origin` before using it, rather than pattern-matching the raw string).

### [MEDIUM] auth-routes — Account/email enumeration on signup  (3/3, CONFIRMED)
`app/api/auth/signup/route.ts:72`
- Defect: The signup handler explicitly branches on Supabase's `identities.length === 0` signal (which GoTrue returns when the email is already registered and confirmed) and returns a distinct, unambiguous response: HTTP 409 with message "Ein Konto mit dieser E-Mail existiert bereits..." for an existing account vs HTTP 200 "Verification code sent" for a new one.
- Scenario: POST /api/auth/signup with `{email:"victim@example.com", password:"Aaaaaaa1", salon_name:"x"}` (satisfies the zod refine so it's accepted for validation). The response status/body deterministically reveals whether victim@example.com already has a solen.ch account, letting an attacker enumerate registered emails at up to 5 req/min (the auth rate limit) per source identifier for account-targeting, credential-stuffing list-building, or user-privacy exposure (e.g. confirming someone uses this beauty-booking service).
- Fix: Return the same 200 response and generic message ("Falls diese E-Mail neu ist, wurde ein Bestätigungscode gesendet") regardless of whether the identities array is empty; do not surface the 409 existing-account branch to the client (log it server-side only if needed for support).

### [MEDIUM] auth-routes — Unauthenticated phone-OTP endpoints let anyone target arbitrary phone numbers (SMS-bombing / brute-forceable verification)  (3/3, CONFIRMED)
`app/api/auth/verify-phone/send/route.ts:22`
- Defect: `POST /api/auth/verify-phone/send` and `POST /api/auth/verify-phone/check` require no authentication and no binding between the calling session/user and the `phone` value: any caller can request an OTP SMS to any phone number, and any caller can attempt to check any `{phone, code}` pair. The only defense is the same IP-keyed `authLimiter` shown above.
- Scenario: (a) SMS-bombing/cost-abuse: repeated `POST /api/auth/verify-phone/send {"phone":"<victim's number>"}` from spoofed-XFF requests (see finding above) sends unlimited real SMS via seven.io to a number the attacker doesn't own, at solen.ch's expense and as harassment of the victim. (b) OTP brute force: because the rate limiter is bypassable, an attacker can attempt far more than 5/min against the 6-digit code space (1,000,000 values) for `phone_verified`-style verification of a number they don't control, eventually succeeding and having it accepted as "Erfolgreich verifiziert" for a phone they never received the code on.
- Fix: Require an authenticated session and tie the phone-verification attempt to that user's id (not just an IP-derived rate-limit key); add a strict per-phone-number attempt cap (not just per-IP) and a max-attempts lockout with exponential backoff in Redis, independent of the spoofable IP key.
