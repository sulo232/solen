## [CRITICAL] discovery-inspo — discovery_items has no RLS INSERT policy — the entire "Post from Discover" user-generated-content feature is permanently broken  (3/3, CONFIRMED)
`app/api/discovery/post/route.ts:81`
- Defect: The route inserts into discovery_items using the user's own session-scoped Supabase client (createServerSupabaseClient, not the admin/service-role client). Live-DB inspection shows discovery_items has exactly ONE RLS policy: `discovery_items_public_read` (SELECT, roles={public}, qual=true). There is no INSERT (or ALL) policy for the `authenticated` role. Postgres RLS defaults to deny for any command with no matching policy, so every insert from a real logged-in user is rejected with `new row violates row-level security policy for table "discovery_items"`. I proved this empirically: running `SET LOCAL role authenticated; ... INSERT INTO discovery_items (...) VALUES (...)` inside a rolled-back transaction on the live project (tocfnsmxmdxkrcmjzzdw) returned exactly that RLS error. The feature is not a stub: it's fully wired (ban check, rate limit, content-flag auto-moderation, salon-owner detection) and the `PostFromDiscover` component is live-rendered in app/[locale]/inspo/page.tsx:615, and the `discovery` feature flag is enabled=true in the live feature_flags table. The original migration (supabase/migrations/067_discovery.sql:174-179) DID define the missing policies (`items_insert_own`, `items_update_own`, `items_delete_own`, scoped to owner_user_id = auth.uid()), but the live database no longer has them — they were dropped/replaced at some point outside the committed migration history (schema drift), leaving only the single permissive read policy.
- Scenario: Any logged-in customer opens Inspo, taps 'Post from Discover', fills in a look and submits. The insert always fails server-side; the route logs the error and returns HTTP 500 'Failed to create post'. This happens for 100% of submissions, for every user, right now, in production — a fully-built feature that silently never works.
- Fix: Add (or restore) an owner-scoped INSERT policy on discovery_items for authenticated users, e.g. `CREATE POLICY "items_insert_own" ON discovery_items FOR INSERT TO authenticated WITH CHECK (auth.uid() = owner_user_id);` (mirroring the original 067_discovery.sql intent), and commit it as a proper migration so it isn't lost to drift again. Verify with the same rolled-back-transaction technique before considering it fixed.

## [CRITICAL] search-geo-semantic — Public /api/recommendations returns full unredacted salon rows (select("*")), leaking stripe_account_id and owner_id  (3/3, )
`app/api/recommendations/route.ts:206`
- Defect: The final enrichment query does `.from("salons").select("*")` and the response spreads the raw row (`{...salon, ai_reason, ai_score}`) straight into the JSON response. `salons` has ~98 columns including `stripe_account_id` and `owner_id` (confirmed present in _inventory/_db-columns.json). This route requires no auth (`session` may be `null`; anonymous callers are rate-limited by IP, not blocked) so it is reachable by anyone. This is the exact anti-pattern the codebase already fixed in sibling endpoints: app/api/salons/search/route.ts and app/api/salons/similar/route.ts both carry an explicit comment ('Replaces select(\'*\') which shipped all ~98 salon columns to anonymous clients, including owner/payment internals. Never select search_doc, score_details, stripe_account_id, owner_id here.') and use an explicit column allowlist instead. /api/recommendations was missed.
- Scenario: curl -s 'https://solen.ch/api/recommendations' (no cookie/session) with any `viewedSalonIds` -> the JSON body's `recommendations[]` items contain `stripe_account_id` and `owner_id` for every recommended salon, exposed to an anonymous caller.
- Fix: Replace `select("*")` at line 206-209 with the same explicit public column allowlist used in app/api/salons/search/route.ts and app/api/salons/similar/route.ts (id, slug, name, cover_photo_url, gallery_urls, categories, address, postal_code, quartier, latitude, longitude, opening_hours, average_rating, review_count, last_minute_discount_percent, walkin_enabled, accepts_online_payment, solen_score, created_at), never stripe_account_id/owner_id/search_doc/score_details.

## [HIGH] search-salons — Time-of-day (period) search filter silently returns the wrong salons: hour extracted in UTC, not Zurich local time  (3/3, CONFIRMED)
`supabase/migrations/20260607182403_add_salons_with_slot_in_hours_rpc.sql:20`
- Defect: salons_with_slot_in_hours() does `extract(hour from s.starts_at) >= p_start_hour and extract(hour from s.starts_at) < p_end_hour` directly on the timestamptz column. Postgres extract(hour from timestamptz) evaluates in the SESSION's default timezone, which I confirmed live is UTC (`SHOW timezone` -> UTC) on this Supabase project. availability_slots.starts_at is stored as a genuinely correct UTC instant (the nightly cron app/api/cron/generate-slots/route.ts explicitly converts Zurich wall-clock -> UTC via `zurichWallClockToUtc`, with a code comment describing a prior real incident from exactly this class of bug). So the RPC's raw `extract(hour from starts_at)` reads the UTC hour, not the Zurich local hour the PERIOD_HOURS bands (morning 9-12, noon 12-15, afternoon 15-18, evening 18-24) in app/api/salons/route.ts are documented and intended to mean ('Time-of-day windows (local hour ranges)', route.ts line 16-22, and route.ts line 338-341 explicitly says open_now 'depends on Zurich-local day/time' implying the same intent applies to period). I verified this live: querying real availability_slots rows shows e.g. starts_at='2026-03-08 10:55:01+00' where extract(hour from starts_at)=10 but the true Zurich-local hour (`starts_at at time zone 'Europe/Zurich'`) is 11 -- a systematic 1-hour offset in that CET sample, and today (CEST, UTC+2) the live offset is 2 hours.
- Scenario: A customer in July (CEST, UTC+2) picks the 'morning' (9-12) time-of-day pill in search. The RPC matches slots whose UTC hour is 9-12, which is actually Zurich local 11:00-14:00 (late morning through early afternoon) -- salons whose only real morning slots (Zurich 09:00-11:00, i.e. UTC 07:00-09:00) get WRONGLY EXCLUDED from the 'morning' result set, while salons whose only slots are Zurich 13:00-14:00 get WRONGLY INCLUDED. The filter still discriminates (returns a different, non-trivial subset) so it isn't a total no-op, but the subset is the wrong one relative to what the UI label promises, and this also silently distorts any date+period combined query since period supersedes the date-narrow path (route.ts line 220, 296-308).
- Fix: Convert to Zurich local time before extracting the hour: `extract(hour from s.starts_at at time zone 'Europe/Zurich')`, matching the pattern already used correctly by zurichWallClockToUtc (cron/generate-slots), isOpenNow (lib/salon-hours.ts), and lib/format.ts elsewhere in this codebase. instant_bookable and the plain date-narrow filter are NOT affected since they call the same RPC with p_start_hour=0/p_end_hour=24, which passes regardless of timezone -- only the period-specific bands need the fix.

## [HIGH] discovery-inspo — discovery_items RLS SELECT policy is unrestricted (qual=true) — staging/flagged/archived/inactive content is world-readable via direct REST, bypassing every app-level status filter  (3/3, CONFIRMED)
`supabase/migrations/067_discovery.sql:158`
- Defect: Every API route/RPC in the app (discovery_feed, discovery_feed_for_you, search_discovery, discovery_chip_terms, discovery_trending_terms, /api/discovery/similar) carefully filters `status = 'published' AND is_active = true` before returning rows. But that filtering is application-layer only. The live RLS policy on discovery_items (`discovery_items_public_read`, roles={public}, qual: true) has no such predicate at all — it grants unrestricted SELECT to anyone, including the public `anon` key that ships in every page load. The table's own CHECK constraint (`discovery_items_status_check`) proves `status` legitimately takes the values `staging`, `published`, `flagged`, `archived` — i.e. this table holds pre-moderation AI/TikTok-imported content and moderated-out (reported/rejected) content, not just published looks. The original migration (067_discovery.sql:158) correctly scoped the read policy to `USING (status = 'published' AND is_active = true)`; the live database has since replaced it with the unrestricted version, again outside any committed migration (schema drift). Today there happens to be only one is_active=false row and zero non-published rows, but any future staging import (bulk-import/import-tiktok/smart-import all write into this same table before an admin flips status to 'published') or any flagged/reported post is immediately readable by anyone who queries `<project>.supabase.co/rest/v1/discovery_items?select=*` with the public anon key — full row contents (owner_user_id, flag_reason, raw AI fields, etc.), not just the narrow field set the app routes expose.
- Scenario: An admin bulk-imports a batch of TikTok content for review (status='staging') or a user's post gets auto-flagged (status='flagged', flag_reason populated). Before any moderator acts, anyone (no auth, no cookie) hits the Supabase REST endpoint directly with the anon key and reads that unmoderated/flagged content in full, plus who posted it (owner_user_id) — completely invisible to and unblockable by the app's own status/is_active checks.
- Fix: Replace `discovery_items_public_read` with a policy scoped to `USING (status = 'published' AND is_active = true)` (restoring 067_discovery.sql's original `items_read`), and add a separate admin-only (or owner-only) SELECT policy for staging/flagged/archived rows so moderation tooling still works. Commit the corrected policy as a migration.

## [HIGH] search-geo-semantic — Salon-detail "nearby" recommendations have no geographic bound and skip the marketplace-visibility gate  (3/3, )
`app/api/salons/[slug]/nearby/route.ts:31`
- Defect: The candidate query only filters `is_active` + `neq(id, salon.id)` + `categories overlap`, with NO city/quartier/radius predicate and NO `ORDER BY` before `.limit(4)`. Distance is computed only AFTER the 4 rows are already picked, purely for display, not for selection. It also omits `listed_on_marketplace`, which every sibling salon-listing endpoint (app/api/salons/similar/route.ts line 34, app/api/salons/nearby/route.ts line 57, app/api/salons/route.ts) enforces, and which the search_salons_ranked/search_suggest RPCs treat as mandatory (walk-in-only opt-out salons must not surface in discovery contexts, per the 20260602140000_smart_search_marketplace_filter.sql comment).
- Scenario: A Basel salon with categories=['coiffeur'] requests /api/salons/basel-slug/nearby. If Postgres's default (unordered) scan happens to return 4 same-category salons located in Zurich or Geneva before any Basel one, those become the 'nearby' recommendations, each labeled with a real but large distance_km (hundreds of km), because nothing in the query constrains them to be geographically close. Separately, a walk-in-only salon that opted out of the marketplace (`listed_on_marketplace=false`) can still appear as a 'nearby' recommendation on another salon's page, contradicting the documented opt-out contract enforced everywhere else.
- Fix: Add `.eq("listed_on_marketplace", true)` to match sibling endpoints, and constrain candidates geographically before limiting (e.g. filter by `city_id`/`quartier` match, or widen the fetch and sort by real distance before truncating to 4, the way app/api/salons/nearby/route.ts does).

## [MEDIUM] search-salons — Several customer-facing salon-discovery surfaces omit the is_test (and one omits listed_on_marketplace) filter that the main search route enforces  (3/3, CONFIRMED)

But six other salon-listing surfaces only apply is_active + listed_on_marketplace and never check is_test: app/api/salons/nearby/route.ts (lines 56-57), app/api/salons/by-category/route.ts (lines 58-59), app/api/salons/similar/route.ts (lines 33-34), app/api/salons/recommendations/route.ts (lines 29-30, 60-61, 80-81, service-role client bypassing RLS so the app code IS the only gate), app/api/salons/quartier-featured/route.ts (lines 11-12), and app/api/salons/quartier-counts/route.ts (lines 12-13). Worse, the Postgres function get_last_minute_slots() backing app/api/salons/last-minute/route.ts (supabase/migrations/014_new_schema.sql line 508) checks ONLY `sal.is_active = true` -- it has no listed_on_marketplace or is_test predicate at all, and no later migration redefines it (verified: 014_new_schema.sql is the only CREATE for this function). ## [MEDIUM] discovery-inspo — salons-for-style route joins the discovery category straight into services.category with no bridge — a live, reachable, silent no-op for 6 of 7 categories  (3/3, CONFIRMED)
`app/api/discovery/salons-for-style/route.ts:32`
- Defect: The route reads `category` straight from the query string and does `.eq("services.category", category)`. Discovery taxonomy (discovery_items.category, per its CHECK constraint) is `hair|beard|nails|makeup|waxing|lashes|brows`; the marketplace taxonomy (services.category, verified live) is `coiffeur|nails|barbershop|spa`. Only `nails` happens to spell the same in both taxonomies — every other discovery category (hair, beard, makeup, waxing, lashes, brows) will never match any services.category value, so the query always returns an empty salons array with a 200 status: a textbook silent no-op, the exact discovery-vs-salon-category trap this codebase has already been bitten by once. The correct bridge exists elsewhere in the codebase: app/[locale]/inspo/[id]/page.tsx:153 defines `CATEGORY_ROUTES = { hair: "coiffeur", beard: "barbershop", nails: "nails", lashes: "spa", brows: "spa" }` and its own comment explicitly documents this as the fix for "the bug the audit flagged in the old salons-for-style stub." That page no longer calls this API route at all (it queries salons directly with the mapped category) — but the route itself was left live, unfixed, and reachable (no auth, only feature-flag + rate-limit gating), so a future re-wire (mobile client, a stale bookmark, a new caller added without re-reading the old audit note) would silently ship the same broken behavior again.
- Scenario: Any client calls GET /api/discovery/salons-for-style?category=hair&style=Textured%20Crop (hair is by far the largest discovery category, ~majority of content). The `.eq("services.category","hair")` filter matches zero services (no such category value exists), so `salons: []` comes back for every hair look, with no error and no indication anything is wrong.
- Fix: Either delete the route (it has no live caller — flag it in _design-system/REMOVED.md per the graveyard protocol) or apply the same CATEGORY_ROUTES bridge used in app/[locale]/inspo/[id]/page.tsx:153 before filtering on services.category.

## [MEDIUM] search-geo-semantic — Geo "nearby" endpoint sorts distance only within an arbitrary, unordered DB-fetch window that will silently exclude the true nearest salons at scale  (3/3, )
`app/api/salons/nearby/route.ts:63`
- Defect: When lat/lng are supplied, the query has no `.order()` before `.limit(limit * 4)` (e.g. 24 rows for the default limit=6). Whatever Postgres's default row order returns for that city (or globally, if no city filter) is the entire candidate pool; haversine distance is computed and sorted only inside that pool. There is no PostGIS/earthdistance index to pre-select genuinely close rows, and the comment in the file acknowledges this is a stopgap ('postgis isn't installed') but the pool-selection step itself has no relevance signal at all (not even a rating pre-sort), just whatever order the table happens to return rows in.
- Scenario: Today _inventory/_db-snapshot.json shows only 25 total salon rows, so the bug is currently masked (the *4 window covers most/all of a city's inventory). Once a served city grows past `limit*4` active+listed salons (e.g. Zurich reaching 30+ salons, a stated growth goal), a user near a salon that happens to fall outside that arbitrary first-N window will never see it in /api/salons/nearby's results, regardless of how close it actually is, while a farther salon that happened to be in the window shows up ranked as nearer. The endpoint's own JSDoc claims it 'returns salons sorted by Haversine distance,' but that's only true within an unordered, unrelated-to-distance subset.
- Fix: Either pre-order the candidate query by something distance-correlated (e.g., require a city match first, or bucket by lat/lng range with a WHERE clause before LIMIT) or widen the multiplier and monitor city-level salon counts so the window always exceeds real inventory; the durable fix is a PostGIS/earthdistance-backed nearest-neighbor query instead of the JS haversine-over-an-arbitrary-slice approach.

## [LOW] search-salons — Dead 'auto-hide test salons' computation in the main search route: the DB round-trip runs but can never change the result  (3/3, CONFIRMED)
`app/api/salons/route.ts:363`
- Defect: The cityTask closure (lines 249-260) runs an extra COUNT query to decide `hideTest` ('Auto-hide test salons when real salons already exist for this city+category'), and line 363 conditionally re-applies `.eq('is_test', false)` when hideTest is true. But the base query already unconditionally applies `.eq('is_test', false)` at line 151, before any of this runs. Since is_test=false is already enforced regardless of hideTest's value, the conditional re-application at line 363 is a literal no-op (adding an identical predicate a second time changes nothing), and the realCount query that computes it (lines 252-260) is pure wasted latency on every city+category search -- it discriminates nothing, matching the project's own definition of a silent no-op ('a control that renders/returns 200 and does nothing').
- Scenario: Any request with both `city` and `category` params triggers the extra realCount query (an additional DB round-trip on the request's critical path) purely to compute a boolean that is then applied through a predicate the query already has unconditionally -- the query results and count are byte-for-byte identical whether hideTest resolves true or false.
- Fix: Either remove the dead hideTest computation and its extra query entirely (since is_test is already hard-excluded), or -- if the actual product intent was 'show test salons only when a city+category has zero real salons yet (e.g. onboarding demos)' -- that requires making the base .eq('is_test', false) at line 151 CONDITIONAL instead of unconditional, which is a product/behavior change that should go back to the owner rather than being silently 'fixed' either way.
