# Cross-Surface Mismatch Doctrine (Round 1)

**Date: 2026-07-23. Status: research complete (11 of 12 streams delivered + adversarially verified; stream S7 failed, see section 8). No code shipped by this doc; detection method + extension plan are build-ready specs, not scripts.**

This is the doctrine for a mismatch class Solen's existing drift infrastructure cannot see: **cross-surface, same-role, divergent-treatment**. It was produced by 12 parallel research streams (S1-S12), each independently adversarially verified against the live repo and against its own cited sources. This document synthesizes the surviving, corrected findings. Every empirical claim below carries a named source and an evidence tier (T1 = peer-reviewed/primary, T2 = applied research org or secondary academic, CONV = house convention or industry practice with no controlled study behind it, T3 = single-observation or directional). A claim that was downgraded during verification is marked as such; a CONV is never presented as if it were T1.

## Delta vs. existing infrastructure

Solen already has three layers that catch drift. This doc does not replace or duplicate any of them:

1. **`solen-drift-check` / `.claude/skills/solen-drift-check/scripts/check.py`** (mechanical layer). Confirmed by direct read: every rule (A1 hex, A2 arbitrary Tailwind, A3 duration, A4 easing, A5 retired token, A6 emoji, A7-A13 type/imagery registry, A14 control elevation, A15 raw palette, A16 decorative dot, A17 opacity hairline, A18 flip-flop guard, A19 sub-12px text, A20 middle-dot separator, A21 tracked-uppercase eyebrow, B1/B2 dead-click, B5 category branches) is a **single-file, single-line regex/AST check against a fixed literal allowlist**. A real precedent for this exact mismatch class, but a ONE-TIME, HUMAN-RUN, single-pass manual scan (two read-only agents, 2026-06-07, 370 files) along five metric axes (radius, type-size, spacing, widths, icon size) and several treatment axes. **The net-new delta this document is about**: none of the three layers above group call sites BY SEMANTIC ROLE across the whole codebase and diff them against each other. `RATIONALE.md` already contains an unbuilt spec for exactly this (S16, "Cross-surface consistency diff / D7 role-registry gate spec," lines ~1242-1279, plus S17 for spacing at lines ~1281-1298, S19 for severity scoring at lines ~1336-1358). This document supplies the missing WHY layer (the cognitive/perceptual evidence grounding the class), the full taxonomy of concrete Solen shapes the class takes, a deepened detection method (S11 extends S16's spec), and the extension plan naming exactly which files and seams a build phase touches. It does not re-decide anything CONSISTENCY_AUDIT.md or LOCKFILE.md already settled, and it is cross-linked to both rather than edited into them.

## 1. The mismatch class

**SAME-ROLE, DIVERGENT-TREATMENT**: an identical semantic role (an icon standing for one meaning, the selected-state fill on a single-choice control, one step of the type scale, a spacing tier between structurally-equivalent siblings, an elevation recipe for a card, a component's own visual grammar, a color-role mapping, a copy term or verb for one concept, the state-treatment for loading/empty/error) is implemented differently depending on which file or screen renders it, **even though every individual instance independently passes every existing per-file rule** (legal token, legal hex, legal Tailwind class, legal component).

The defect is **relational, not local**. No single file is "wrong": each call site is independently legal. The mismatch exists only in the relationship between what file A renders for role R and what file B renders for the same role R, and it only becomes visible once call sites are **grouped by role across the codebase** and compared to each other, not against a fixed allowlist. A per-file linter is structurally blind to it by construction, the same way a spell-checker cannot catch a word that is spelled correctly but means the wrong thing in context.

Concrete Solen shapes of this class (full taxonomy in section 4): two icon rendering systems in one view, a selected state that is gray fill on one screen and blue border on another, a type-scale one-off or role-swap, a spacing gap that plays the wrong structural role even though the number itself is on the locked scale, a card with a different border+shadow recipe than its sibling cards, a component hand-rolled instead of imported from the shared primitive, an accent hue applied to a non-interactive element on one surface while an equivalent element stays ink elsewhere, two words for one concept across nav/confirmation/button copy, and a hand-rolled spinner where a sibling screen uses `<Skeleton>`.

## 2. Why it matters (mechanics)

The evidence below is what SURVIVED the adversarial verify pass for stream S1 (the dedicated mechanics stream), corrected where the verifier found a citation error. Every claim is tiered on the corrected basis, not the original claim.

- **Gestalt similarity (T1 for the base mechanism).** Elements sharing visual properties (shape, rendering technique, stroke treatment) are perceived by the viewer as belonging to one category. Source: Wertheimer 1923, codified in Lidwell/Holden/Butler, *Universal Principles of Design*; already the same T1 citation Solen's own `RATIONALE.md` uses for proximity and closure. **Verify correction**: the base same-screen grouping effect is solid T1. The extension used to justify cross-surface, non-simultaneous grouping (two icons never seen side by side still read as "differently sourced") is this stream's own inferential bridge into memory/schema theory, not something the 1923 source itself measured. That extension is T2, not T1.

- **Recognition vs. recall (T1 for the recall half, T2 corrected for the recognition half).** A control the user already learned is processed as cheap RECOGNITION only if the next instance matches exactly; any divergence forces expensive RECALL. Source for the recall/span-limit half: Cowan 2001, "The Magical Number 4 in Short-Term Memory" (working-memory chunk capacity, ~4 chunks), already T1 in `RATIONALE.md:73`. **Verify correction**: Cowan 2001 says nothing about recognition memory cost. The "recognition is near-zero-cost" half of the claim actually belongs to Mandler 1980, *Psychological Review* (recollection-vs-familiarity dual-process theory): a real citation mismatch, and one `RATIONALE.md:73` itself already carries. Recommendation logged in section 8: add Mandler 1980 as co-citation wherever this pairing is used.

- **Cognitive Load Theory / schema automation (T1 core, softened claim).** A schema learned on one screen ("gray fill + check = selected") is retrieved as one low-cost chunk only when the next instance matches it exactly; a divergent instance cannot reuse the schema and must be processed as new information. Source: Sweller 1988 (schema acquisition/automation); Paas & van Merrienboer 2020, *Current Directions in Psychological Science* 29:394-398 (meta-review), both independently verified real. **Verify correction**: the word "measurable" in the original claim overstates what these sources demonstrate for a UI-specific divergence. Neither paper measured an icon-family or selected-state mismatch directly; applying CLT's mechanism to that exact scenario is a reasoned, plausible extrapolation. Correct framing: "theoretically predicted increase in extraneous load," not "a measurable spike."

- **Nielsen's Consistency and Standards heuristic (T1/T2 split).** "Consistency and standards" was one of the heuristics with the highest explanatory power when Nielsen factor-analyzed 249 logged usability problems to derive the current heuristic set (Nielsen 1994, "Enhancing the Explanatory Power of Usability Heuristics," CHI '94, pp.152-158; already cited in `RATIONALE.md:1372` and `:1269`). The heuristic itself, and its origin in a real factor analysis of real logged problems, is T1. The specific downstream claim "violations are directly measurable, not a matter of taste" is the project's own gloss, not something the 1990/1994 papers assert (heuristic evaluation is famously subject to evaluator variance, per Nielsen's own later recommendation of 3-5 evaluators). Keep the heuristic citation at T1; the measurability claim is T2 (true only once a role is narrowed to a literal CSS/Tailwind value, i.e. after mechanization, which is a Solen-specific operationalization).

- **Mendel and Pak 2009, consistency's benefit concentrates under high cognitive load (T2, citation corrected).** A controlled study found the performance benefit of interface consistency is significant specifically under high extraneous cognitive load, not uniform across all use. This is the empirical answer to WHERE a mismatch costs the most: dense, decision-heavy Solen surfaces (booking flow, checkout, filters) pay the highest price for a mismatch; a low-density static page pays comparatively little. Source: Mendel and Pak, *Proceedings of the Human Factors and Ergonomics Society Annual Meeting* 53(22). **Verify correction**: the originally-cited page range (1786-1790) is wrong; the correct range is **1684-1688**. The claimed sample specifics (48 participants, 4 websites, 24 search tasks) were not independently re-confirmed this pass and should be checked against the primary paper before being repeated as fact.

- **Nielsen's five usability quality components (T2 for the taxonomy, CONV for the narrative link).** Learnability and errors are two of five independent usability attributes (with efficiency, memorability, satisfaction); a cross-surface mismatch degrades both simultaneously, learnability because the user must relearn the role per screen, errors because a schema learned elsewhere gets misapplied (a Norman "slip"). Source: Nielsen 1993, *Usability Engineering*. The five-attribute taxonomy is real and correctly T2; the narrative stitching it to Norman's slip concept is this stream's own synthesis and should carry CONV confidence, not the same T2 weight as the taxonomy itself.

- **Jakob's Law and its internal-consistency mirror (CONV, honestly self-labeled).** External consistency: users import expectations from other products (Jakob's Law, Nielsen Norman Group convention). This is the axis Solen's own dual-axis rule (STRUCTURE = Fresha) already operationalizes and is NOT the gap this document targets. Internal consistency is Jakob's Law turned inward: after a handful of screens, a user's model of THIS product's own conventions becomes their reference set. Nielsen folds this into the same heuristic with no separate name; this document names it explicitly for Solen because it is otherwise left implicit in both the literature and Solen's own docs. Correctly tiered CONV in both directions, not dressed up as an independent empirical finding.

- **Norman's conceptual-model-transfer framing (CONV).** "Mixed systems are confusing to everyone... lessons learned with one system transfer readily to others" (Donald Norman, *The Design of Everyday Things*, substantively verified as real Norman text). A role-registry divergence breaks a transfer the user already paid attention-cost to build. Correctly CONV, not T1.

### The Grudin boundary (necessary counterweight, its own subsection because a detector without it produces false positives)

Consistency is **not monolithic**. Jonathan Grudin, "The Case Against User Interface Consistency," *Communications of the ACM* 32(10):1164-1173, 1989 (page range verified exact) argues that matching the CONTROL TYPE and its task context matters more than forcing every superficially-similar element toward one literal treatment. Two distinct canonical dialects can both be legitimately correct simultaneously if each stays internally consistent within its own type. Source, T2.

**This is the false-positive guard the detector MUST respect.** A same-role divergence is only a real finding when the underlying SITUATION is genuinely the same (same control type, same decision, same user goal) across the compared call sites. Comparing two visually similar elements serving different situations and flagging their difference as drift is exactly the false positive Grudin's critique predicts. Concrete Solen instance of this guard actually firing correctly during research: the S3 verify pass initially flagged `SearchOverlay.tsx:894`'s blue "period chip" selected state as an unauthorized third dialect outside the four owner-named exceptions (primary CTA / booking date-slot / booking category pill / avatar badge). On closer read the same verify pass downgraded this: the chip sits in the same `footerInner` function as two explicitly-blessed blue booking-time exceptions and renders a time-of-day selector, i.e. it plausibly IS the "booking date/time-slot stays blue" exception, just documented with a lazier comment than its siblings. It is more likely a mislabeled legitimate exception than a genuine new dialect (see section 8). A detector that fires on visual similarity alone, without checking whether the underlying situation matches, would have shipped this as a false positive.

A second real over-consistency counter-example, from the icon research (S2, verified): Nielsen Norman Group's own consistency article documents a case where Google made Mail/Calendar/Drive icons MORE stylistically consistent and made them HARDER to tell apart at small mobile sizes. Consistency and distinguishability trade off; "more consistency is always better" is not an unqualified law (T3, single documented example, cited honestly at that tier).

## 3. The mismatch taxonomy

One subsection per class. Each states the concrete Solen shape (with file:line where a live instance was confirmed during research), the survived grounding principle with its tier, and the detection signal. Streams are matched S2-S10; **S7 (component re-implementation) failed to deliver usable research** (see section 8) and is covered here only via what S1, S3, and S12 independently surfaced about it.

### 3.1 Icon-system-per-view (S2)

Two or more icon glyphs sitting in the same visual zone (both row-leading, both meta-line, both on one card) render from different SYSTEMS: (a) rendering-technique mismatch, a Lucide SVG line-icon next to a raster/3D asset or hand-drawn inline path; (b) library mismatch, two different SVG icon packages both live in the codebase and land in one view via files built at different times; (c) stroke/weight mismatch inside the same nominal library (strokeWidth 1.9 next to 2.8-3, or filled vs. outlined) with no semantic reason for the difference.

Grounding: Gestalt similarity (T1, base mechanism) predicts the viewer reads mismatched icons as differently-sourced or differently-important. Apple HIG requires consistent size/detail/stroke/perspective within an icon set (CONV, vendor guide). NN/g applies Nielsen heuristic 4 specifically to icons (T2). Solen's own `LOCKFILE.md §13.7-13.8` already rules on this (owner-approved 2026-06-11): different icon styles may coexist ONLY in visually separate zones (3D category tiles vs. Lucide UI chrome is sanctioned; mixing within one zone is drift). `RATIONALE.md`'s own retrofit queue (section 13, item 8) already separately flags the stroke-width-1.9-vs-2/1.75 inconsistency between LOCKFILE §13.1 and §13.7 as an unretrofitted, still-open gap, confirming this is a known live problem, not a hypothetical.

Detection signal: resolve the view's real render graph (route + every contributing component file via import resolution, not one file), extract an "icon fingerprint" per call site (source-kind: lucide-react / other icon lib / inline path / raster asset, plus strokeWidth and size for Lucide), group by ZONE per LOCKFILE's own taxonomy, flag more than one distinct source-kind or stroke-width inside the same zone type without a documented semantic license.

### 3.2 Cross-screen selected-state (S3)

The same control-type family (pill/chip/segmented-control/filter-tab) renders a functionally-identical "selected" state with a different className recipe on different screens, with no owner-named exception covering the difference. Confirmed live: `SalonServicesSheet.tsx:265` uses `bg-s-bg-sunken/60` (an opacity-suffixed notation fork of the canonical plain `bg-s-bg-sunken`), though the S3 verify pass found this specific file has been dead code with zero live importers since 2026-07-19, so it is a documentation/graveyard risk, not a live rendering bug today. `COMPONENT_REGISTRY.md`'s PillToggle row still documents "active = ink fill + white text," directly contradicting the 2026-06-29 gray-sunken supersession; it has 0 live call sites but is a live trap for whoever next copies it as a reference.

Grounding: WCAG 2.2 SC 3.2.4 "Consistent Identification" is a real Level AA conformance requirement (T1, not merely taste) that same-functionality components must be identified consistently across pages. NN/g Consistency and Standards (T1). Gestalt similarity (T1, same source Solen already cites for closure/repetition). Grudin's boundary (T2, section 2 above) is the required false-positive guard here specifically, because "selected" is the highest-traffic role in this taxonomy and the one most likely to have legitimate per-context dialects. Solen's own binding law and its exactly four named exceptions are CONV, verified verbatim against `CONSISTENCY_AUDIT.md` section B1, `.claude/hooks/no-black-selected-gate.py`, and `TASTE_LOG.md:358`.

Detection signal: reuse `no-black-selected-gate.py`'s existing selection-condition detector (confirmed regex/text-pattern based, not AST, contrary to an earlier overclaim caught in verify), extract the TRUE-branch class set per match, tag by control-type family (from an explicit `selected-ok:` comment or COMPONENT_REGISTRY.md's control-type rows), diff each family's class-sets against ONE canonical set per family, and separately validate every `selected-ok:` escape's stated reason against the four owner-named exceptions instead of trusting any comment string at face value (the gate today does the latter: it checks only that a comment exists, never that its content is valid).

### 3.3 Type-scale one-off / role divergence (S4)

Two flavors: (1) ROLE DIVERGENCE, the same semantic role renders at two different literal sizes depending on the file. Confirmed live: `app/[locale]/_components/salon/SalonHeader.tsx:83` renders the salon-name H1 as `text-[clamp(22px,2.8vw,26px)]`, which is exactly LOCKFILE's locked "Page H2" value, not its OWN locked "Salon-PDP H1" value of 30px/34px. The file's own inline comment (line 79-81) names a THIRD, also-unapplied intended value (`clamp(28,3.5vw,40)`), meaning the drift is worse than a single mismatch, three different numbers are in play for one element. (2) OFF-SCALE ONE-OFF, a font-size literal matching none of the locked roles at all.

Grounding: NN/g Consistency and Standards (T1, live-fetched and confirmed verbatim). NN/g's "2-3 sizes per screen" ceiling (T1, live-fetched, exact quote confirmed). Material Design 3's bounded 5-role x 3-size system as evidence the correct consistency unit is the ROLE, not the raw pixel (CONV). W3C Design Tokens Community Group's single-source-of-truth convention (CONV).

Detection signal, two-tier: TIER 1 (static) normalizes every font-size declaration to a canonical px value and tests set-membership against the closed whitelist LOCKFILE §2/§2.5 publish. **Verify correction, must be fixed before this whitelist ships**: LOCKFILE §2 and §2.5 currently DISAGREE with each other on Hero H1 (§2.5 locks `clamp(28,7vw,64)` at line 291; §2's own role table and its "common clamp() patterns" block both give `clamp(40px,10vw,64px)` at lines 223/246, a 28-vs-40 contradiction for the identical role name in the same file), and the whitelist as drafted omits the Tag/Status role's documented 10px floor. The whitelist is not yet a genuinely closed canonical set; §2.5 is explicitly marked "ENFORCED" and is the better candidate ground truth, but the two sections need reconciling first (logged to section 8). TIER 2 (DOM-measured) builds a role-to-selector map off COMPONENT_REGISTRY.md primitives, visits live routes via the existing site-tester Playwright MCP, reads `getComputedStyle` font-size, and groups BY ROLE across surfaces instead of counting sizes on one screen; a role-swap (one component silently borrowing another role's exact literal, as SalonHeader.tsx does) is ranked more severe than a stray custom number.

### 3.4 Spacing-rhythm mismatch (S5)

Two forms: (a) a vertical-rhythm value off Solen's locked 3-tier scale (Section 32px / Card 12px / Group 16px, `LOCKFILE.md §3` lines 444-455) and not the documented home-feed exception; (b) the true cross-surface case, two elements playing the IDENTICAL structural role (two consecutive page sections, two consecutive cards in the same list, the same kind of section across different routes) carry different spacing-tier values even when each individual value is itself canonical. LOCKFILE's own home-feed exception (lines 457-463) is direct proof this class is real: it had to be carved out explicitly because the homepage's internally-consistent ~24/12/4 rhythm would otherwise read as drift against the 32/12/16 rule everywhere else.

Grounding: Gestalt proximity (T1, Wertheimer/Koffka, the same source already grounding Solen's 32/12/16 rhythm at `RATIONALE.md:55-56`), space itself encodes grouping, so an inconsistent gap between structurally-equivalent siblings actively communicates a FALSE grouping. NN/g Consistency and Standards (T1). The 8pt/4pt grid convention (CONV, industry design-ops practice, not a controlled study).

**Verify correction, important**: this stream's detection method was presented as net-new but is largely already specced, in more rigorous form, at `RATIONALE.md` S16 (line 1242) and **S17** (line 1281, "Spacing-rhythm audit... ladder conformance, ratio-distinctness, within/between grouping"), which already has real formulas (distinct_count, mode, divergence_rate, outliers) this stream's draft lacked, and which commits to measuring the RENDERED DOM (`getBoundingClientRect` on live siblings) rather than statically grepping Tailwind class names, sidestepping a real ambiguity a static approach cannot resolve (`gap-N` is ambiguous between a horizontal row and a vertical column; a static regex over the class name alone cannot tell which). **A build phase should target S17, not rebuild this stream's weaker static-parse variant**: building it as originally drafted would create a second, weaker parallel spec for the same gap-register item, which is exactly the duplication the project's exists-check rule warns against.

Detection signal: use S17's already-verified rendered-DOM method (see `RATIONALE.md` S17 directly), not a JSX-AST sibling walk.

### 3.5 Elevation recipe divergence (S6)

Divergent elevation recipe for the same semantic card/surface role, in two forms: (a) WITHIN one page, `dashboard/cases/page.tsx:287` and `dashboard/refunds/page.tsx:197` apply the exact hand-rolled arbitrary shadow `shadow-[0_1px_2px_rgba(0,0,0,.04),0_10px_28px_rgba(10,10,10,.07)]` only to the escalated/open branch of a ternary while the sibling branch gets border-only, confirmed real; (b) ACROSS surfaces, roughly 8 dashboard admin pages (analytics, approvals, cities-admin, commission-admin, ai-limits-admin, help-editor, revenue, all-salons) consistently pair `border border-s-border` + `shadow-warm-md` for their content-card family, confirmed on all 8, a combination `CONSISTENCY_AUDIT.md:98` already flags as a retired-alias problem codebase-wide but never checked per-role, and which sits outside every documented allow-list exception without ever being logged as an intentional dashboard-skin deviation.

Grounding: Gestalt figure-ground (T1, Wertheimer/Koffka, the same citation `RATIONALE.md:55` and `:405/:429` already use for why a shadow signals lift at all): a shadow only functions as a depth signal if a given recipe reliably maps to a given perceived lift; two recipes for one role break that mapping. NN/g Consistency and Standards (T2, correctly downgraded from T1 here since the cited claim is the applied-practice framing, not the raw heuristic). Design-token single-source-of-truth debt is self-verified: `shadow-warm-md` and `shadow-warm-lg` are byte-identical rgba stacks in `tailwind.config.js:270-271`, so two names for one value already signals unmerged history before any page even uses them inconsistently (CONV).

**Verify correction**: the flagship illustrative "within one page" example (mixing `shadow-elevation-1`/`shadow-warm-lg`/`shadow-elevation-3`/`shadow-warm-md` "in the same render tree" on `dashboard/settings/page.tsx`) does not survive the stream's own proposed detection method on inspection: one cited element is a 20x20px toggle thumb (a control, not a card, would not cluster on radius/padding), one is a blue toast pill (fails the bg-white/bg-s-bg-sunken card filter outright), and the elements are mutually-exclusive conditional branches, not simultaneous siblings. The genuinely comparable pair in that file (`warm-lg` vs `warm-md`) is a RENAME-ONLY case (byte-identical rgba), not the REAL DIVERGENCE the example claimed to illustrate. **Use the dashboard admin-page cross-surface finding (8 pages, border+warm-md) as the load-bearing example instead**; it held up under verification. Also downgraded: Material Design's current elevation guidance was checked live and does NOT support pairing border+shadow on one card (M3 treats Outlined and Elevated as mutually exclusive variants), which if anything supports Solen's existing "one depth cue" house rule rather than undermining it as the original claim implied. `RATIONALE.md:429` already self-labels that house rule CONV ("no perceptual formula backs the word dated"); it should stay CONV, not be reframed as backed-then-unbacked.

Detection signal: role-signature clustering by (radius bucket, padding bucket, background) as a proxy for "same card family" (report-only, human-reviewed, false-positive-prone by the tool's own honest admission), diff shadow-identity within a cluster after resolving to rgba (not class name), split findings into RENAME-ONLY (auto-fixable alias collapse) vs REAL DIVERGENCE (owner call).

### 3.6 Component re-implementation (S7, re-run 2026-07-23)

A UI element sharing a ROLE with a locked registry primitive (the modal, the from-price line, the avatar, the selected pill) is hand-authored as a second JSX tree instead of importing the primitive, so its radius, elevation, selected-state, and motion drift independently on every future edit to either copy. This is invisible to per-file token gates because each hand-rolled instance can be built entirely out of legal tokens; the defect is that a shared primitive already exists for the role and the call site silently reimplements it instead of importing it.

Confirmed live, four instances (three individual files plus one repeated pattern):
- `app/[locale]/profile/settings/page.tsx:169-176` (the `IdentityBlock` function, avatar rendered at line 174): hand-rolls a circular avatar (`h-16 w-16 rounded-full`, image-or-initial fallback) instead of importing `Avatar` from `_components/primitives/Avatar`, the same primitive the codebase's own `SettingsForm.tsx:10` imports and uses for the identical role elsewhere. **Citation correction made during this write-up**: the file:line first supplied for this instance (`profile/page.tsx:235`) does not exist, that file is 195 lines total and contains no avatar markup at all; the confirmed live instance is the sibling settings file and line above, verified by direct read.
- `components-legacy/discovery/DetailPage.tsx:409`: hand-rolls `ab CHF {s.priceFrom}` as a bare span, bypassing the `PriceFrom` primitive at `_components/primitives/PriceFrom.tsx` (confirmed to exist; confirmed not imported anywhere in this file). File:line verified exact by direct read.
- `app/[locale]/_components/search/CategoryHeroCarousel.tsx:162` (**corrected from the originally supplied line 150**, which is the unrelated name heading; the price render is 12 lines further down): hand-rolls `` `${pick(FROM, locale)} ${price} CHF` `` as a template string instead of importing `PriceFrom`. The file's own inline comment at lines 160-161 admits the string is manually kept in sync with "the PriceFrom primitive" convention and was itself the one deviation from it until a manual fix, direct proof the drift risk here is not hypothetical: this exact file already drifted once and was patched by hand rather than by importing the shared component.
- Dashboard modals: confirmed zero files under `app/[locale]/dashboard/` import `primitives/Modal.tsx`, while at least a dozen dashboard pages carry a hand-rolled `fixed inset-0` backdrop-plus-panel pattern; the re-run stream counted 8 of these as genuine modal reimplementations (the remainder being other full-screen overlay uses), each maintaining its own backdrop, close affordance, and panel radius independently instead of the one shared primitive.

Grounding:
- **P1, single authoritative representation, the DRY principle** (Hunt & Thomas, *The Pragmatic Programmer*, 1999). **Tier correction for consistency with the rest of this document**: this document reserves T1 for peer-reviewed or primary empirical sources; a widely-adopted but empirically-unstudied SE convention like DRY is tiered CONV here, the same tier this document already gives Norman's *Design of Everyday Things* (section 2) and Podmajersky's *Strategic Writing for UX* (section 3.8), not the T1 the source stream proposed.
- **P2, internal consistency is a property of the whole element's behavior, not any single legal value** (Nielsen heuristic 4, consistency and standards; live-verified at nngroup.com during this research round, T1). The same heuristic already grounds sections 3.2-3.5 and 3.7-3.9; a hand-rolled reimplementation is simply the mechanism by which a role's treatment first forks into two.
- **P3, duplicated UI logic is a correctness liability, clones diverge silently on the next edit** (Juergens, Deissenboeck, Hummel, Wagner, "Do Code Clones Matter?", ICSE 2009, T2). The specific "52% of clones changed inconsistently / 15% caused faults" figures could not be confirmed against the primary source and are rejected as unsourced (see section 6); the qualitative finding, that clones diverge silently over subsequent edits, is what survives at T2.
- **P4, the false-positive guard for this class specifically** (Fowler, *Refactoring*, "Rule of Three"; Sandi Metz, "The Wrong Abstraction," 2016, CONV): forced abstraction from a coincidental shape match is itself a real cost. Two components that happen to share JSX shape but serve genuinely different roles should not be merged; this is the same discipline as the Grudin boundary in section 2, applied to structural similarity instead of visual similarity.

Detection signal, three signals on the TS/ESLint parser already in the repo, zero new dependencies:
- **Signal A**: className token-set Jaccard similarity between JSX-returning components.
- **Signal B**: normalize each JSX subtree to a tag-plus-prop-name sequence with values stripped, then compare; this catches a same-shape/different-legal-token reimplementation Signal A alone would miss.
- **Signal C, the sharpest and cheapest**: fingerprint each LOCKED registry primitive once, then compare every OTHER candidate component against that fixed corpus only (O(n), not O(n^2) pairwise), which directly answers the operational question, "should this call site have imported X."

False-positive controls, all P4-driven: composition-exclusion first (a component that imports and renders the primitive is reuse, not a duplicate, exclude it before scoring anything); a minimum JSX-size floor calibrated to this repo (below it, shape overlap is coincidence, not drift); Rule-of-Three occurrence gating (2 instances of a shape = review, 3-plus = high severity, matching the 8-instance Modal fork above); a boilerplate stoplist (a shape recurring 15-plus times across the codebase is layout noise, not a role, exclude it); a matching name root (e.g. two components both named `*Modal`) is a confidence BOOSTER, never a gate on its own, since name similarity without shape similarity proves nothing and shape similarity without name similarity is still a real finding. The similarity threshold (e.g. Jaccard 0.6) is explicitly a tunable to be CALIBRATED against this repo's own known true positives (Avatar, PriceFrom, the 8-way Modal fork), not an externally sourced constant.

Extends infra: a new `scripts/detect-near-duplicates.mjs`, sibling to the existing `exists.mjs`, exposed as `npm run dupe-check`; it parses `COMPONENT_REGISTRY.md`'s File column to build the Signal-C fixed corpus (reusing the registry as data rather than re-declaring a component list, the same "read the doc, don't duplicate it" principle used elsewhere in this document, section 5); outputs to `_design-system/_dupe-report.md` in REPORT mode by default, mirroring solen-drift-check's logger-not-gate default; extends `~/.claude/agents/council-dedup.md` to shell out to `dupe-check` and treat a HIGH-severity structural hit the same way it already treats a keyword hit; a staged gate comes later, report-first, then wired into the `--gate-stdin` pattern per rule 12.5 (build, self-test, then integrate, never register-and-hope); logs as a new Enforcement row under `CONSISTENCY_AUDIT.md` section D once built (cross-link only, not edited here).

### 3.7 Color-role / hue-role binding drift (S8)

The same semantic role (interactive-accent, success, error, price-emphasis, rating-star) resolves to different literal tokens/hexes depending on the file, OR the interactive-blue accent (`s-accent #276EF1`, reserved per LOCKFILE §1.5 to read as "an `<a href>` inside prose") appears on non-interactive elements on some surfaces while equivalent elements elsewhere correctly stay ink. Confirmed live and independently re-verified byte-for-byte: `app/[locale]/_components/search/SalonResultCard.tsx:541` hand-rolls `<span className="shrink-0 font-semibold tabular-nums text-s-ink">{s.price} CHF</span>` (amount-then-CHF), while the SAME FILE's other price instances (lines 296/341/413/431/571/657) call the shared `<PriceFrom>` primitive, whose own source comment states "owner 2026-07-23: unify to CHF-first prefix... supersedes the earlier card=prefix/row=suffix split" and renders `CHF {amount}`. One file, one role, two literal formats and two implementation paths, invisible to any single-line check.

Grounding: Nielsen's consistency heuristic applied to hue-as-signifier (T1, accurately quoted, a reasonable non-overreaching extension per verify). Feature Integration Theory, color-to-meaning mappings act as pre-attentive visual-search cues that only pop out when the mapping is stable (Treisman & Gelade, *Cognitive Psychology*, 1980, T1 for the qualitative mechanism). **Verify correction**: the specific "~200-300ms pop-out latency" figure attached to this citation does NOT trace to the paper (which reports reaction-time SLOPES across set size, not an absolute latency number); this is an unsourced number riding on a legitimate citation and belongs in the myth table (section 7), not cited as fact. WCAG 2.1 SC 1.4.1 "Use of Color" (T1): color must never be the sole channel carrying state; if role X is redundantly coded on surface A but color-only on surface B, the accessibility guarantee itself becomes surface-dependent. Blue-as-hyperlink is correctly CONV (learned web convention, not inherent to the hue). Red/green as danger/success is correctly T3 with an explicit cultural-reversal caveat (East Asian finance conventions invert it), never asserted as universal or biological.

Detection signal: role-tagged token-usage index across the tree, tag each color-bearing occurrence with an inferred role via local context heuristics (interactive-affordance if an onClick/href/Link ancestor exists within N JSX levels; price if the text matches a CHF/amount pattern; success/error if adjacent to status copy or a check/x icon), resolve every token alias to its literal hex first (so `s-accent.DEFAULT` and `s-accent.bright` both collapse to `#276EF1` but a stray `#2563EB` does not), group by (role, surface), flag any role where the resolved-value set has more than one member. This generalizes check.py's existing A9 rule (currently a flat per-line INFO list a human must mentally cross-reference) into one grouped finding per role/surface.

## 4. Detection method

This is S11's deepened method, built directly on top of the already-written `RATIONALE.md` S16 spec (role registry, distinct_count/mode/divergence_rate formula, HARD/SOFT threshold split), not a replacement for it. Corroborated independently by S12's parallel design.

**1. Role registry.** Each role = (call-site glob/regex) x (the Tailwind class family / CSS property / JSX prop carrying its value) x (a LOCKFILE-named canonical literal, or the sentinel `"CONV: mode-wins"`). Seed set already exists at `RATIONALE.md:1250-1254` (card-radius, tabpill-selected-fill, price-string-format, icon-stroke-width): reuse it, do not re-seed. Add the concrete new roles this document's taxonomy surfaced: icon-fingerprint-per-zone, selected-state-per-control-family, type-role, spacing-role-per-structural-position, elevation-recipe-per-card-family, color-role, i18n-concept-term, i18n-button-verb, state-treatment-primitive.

**2. Extraction.** AST-walk (not line-regex) for the cross-surface mode specifically, extending check.py's existing extraction primitives rather than reinventing them. Regex is fine for a single fixed literal (what A1-A21 already do) but cannot resolve a role's value across a spread prop, a template literal, or a component-boundary branch, the exact mechanism that let the real TabPill ink-fill regression (commit `c21c6cd91`) through every existing per-file rule. **Verify correction on scope**: resolving a value threaded through a spread prop or across a component boundary is genuinely an interprocedural, type-aware problem (would need the TypeScript language service, not a plain syntax walk), and template-literal resolution only works when every interpolated segment is statically known. The method holds cleanly for the seed roles named (direct Tailwind classes, direct hex, direct format strings); "handles spread props and component boundaries" oversells what a lightweight AST-walk alone can do, and should be scoped down accordingly for a first build.

**3. Normalize before counting.** Collapse resolved values that mean the same literal (`rounded-2xl` and `rounded-[16px]` both resolve to 16px) into one bucket before comparing. Skipping this step false-positives on Fresha's own `LocationCard` pattern (a hardcoded-but-internally-consistent literal, independently re-verified live via `getComputedStyle` on fresha.com twice during this research, `RATIONALE.md:1255/1267`): a production design system can legitimately satisfy zero within-role divergence either through a named registry modifier (Fresha's `Card_--radius-m`, resolving to exactly 8px on every instance sampled) OR through a hardcoded-but-identical literal at every call site. Both patterns pass; only the value needs to match, not the notation.

**4. Cross-file compare.** Group the multiset V of resolved values by role. `distinct_count(R)`, `mode(R)` (ties favor the LOCKFILE canonical), `divergence_rate(R) = count(vi != mode(R)) / N` (S16's existing formula, reused not replaced).

**5. Severity (this document's net-new contribution to S16's existing HARD/SOFT split).** For roles with no LOCKFILE canonical (`CONV: mode-wins`) and three or more legitimate variants, add Shannon entropy `H(R) = -sum(p_i * log2(p_i))` over the value-frequency distribution alongside divergence_rate. `divergence_rate` alone cannot distinguish "one stray outlier among many correct sites" from "the convention is genuinely split, no value dominates": these need different responses (fix the outlier vs. escalate to an owner decision). Near-zero entropy signals a dominant convention plus noise (stays SOFT/logged); entropy above roughly half the theoretical maximum signals no dominant convention exists (escalate to a HARD "owner decision needed" finding instead of a fix-the-outlier note). **Honestly tiered CONV**: this is a net-new methodological proposal for this stream, no external source was found applying entropy specifically to design-token drift scoring, and the ~0.5 threshold is provisional, not validated (logged to section 8 as an owner-taste question for the taste-lab probe pattern `RATIONALE.md` already uses elsewhere).

**False-positive controls, all required, not optional:**
- The Grudin same-situation check (section 2): a role's call-site set must be verified to represent the same underlying situation before its divergence counts as drift.
- The normalization step (point 3 above).
- **Liveness/import-reachability filter.** A real gap the S3 verify pass caught directly: the `SalonServicesSheet.tsx:265` finding was flagged as live cross-screen drift, but the file has zero live importers (removed 2026-07-19 per its own doc comment). Without a reachability filter on the role's call-site set, the detector generates false positives from orphaned files. Any build must resolve reachability before scoring a role.
- **Minimum call-site floor.** Require at least 3 instances before scoring a role at all (loosely grounded by analogy to size/token-filtering thresholds in large-scale code-clone-detection tooling, e.g. SourcererCC's pruning heuristics, **a loose analogy, not a direct statistical precedent**, per verify; SourcererCC's filters are scalability optimizations, not a claim that fewer than 3 instances of anything is statistically indistinguishable from noise). Below the floor, "drift" and "these are legitimately two different roles that happen to look similar" cannot be told apart.
- **Scope each role to one rendering context.** A component with an intentional design-axis prop (e.g. list-view vs. grid-view card sizing) is two roles sharing a name, not one role in disagreement; the registry entry must split, not merge, those call sites.

**Correction on cited technique**: an earlier draft of this method described the extraction technique as "AST-subtree-hashing... the established technique, per SourcererCC." Verified false: SourcererCC (Sajnani et al., ICSE 2016, arXiv:1512.06448, real paper, confirmed) is explicitly TOKEN-based (bag-of-tokens + inverted index), built specifically to AVOID AST parsing so it scales to 250+ MLOC on one workstation. AST-subtree-hashing is a real, separate technique family (e.g. Deckard, CloneDR) but is not what SourcererCC does. The Type-1/2/3/4 clone taxonomy this method borrows (exact / renamed-reformatted / near-miss / semantic) is real and correctly T1-grounded literature; the specific tool attribution needed this fix.

No stream in this round proposed a concrete mechanical test for this beyond the Grudin same-situation guard and the owner-exception escape hatch; it remains a human judgment call at review time, not something the detector resolves on its own.

## 8. The built system + self-improve loop (2026-07-23)

The doctrine above became running tooling this session. This section is the operational map + the repeatable pattern for extending it (the owner's "self improve... catch fix bfr me even knowing").

### What exists now (`npm run consistency` runs all detectors)
| check | class | catches | status |
|---|---|---|---|
| `npm run dupe-check` | S7 | a component re-implementing a locked primitive | report-only (60% precision, role-fuzzy) |
| `npm run icon-check` | S2 | 3D-icon used outside blessed surfaces (owner trigger) | report + **LIVE GATE** |
| `npm run type-check-scale` | S4 | off-scale `text-[Npx]` font sizes | report + **LIVE GATE** |
| `npm run selected-check` | S3 | selected-state diverging from the gray-sunken canonical | report-only (role-fuzzy) |

Live PreToolUse gates (block a net-new violation at write time; net-new-count comparison, fail-open, escape hatches): `scripts/hooks/icon-blessed-context-gate.mjs`, `scripts/hooks/type-scale-gate.mjs`. Each shares its classifier with its detector via `scripts/lib/*.mjs` so the report and the gate can never diverge.

### The rule for gate-eligibility (learned this round)
A class is GATE-eligible only when its role is machine-unambiguous in one file's text: an icon path IS an icon, a `text-[Npx]` IS a font size. Fuzzy-role classes (selected-state collides with press-pseudos + status badges; color-role needs "is this a big CTA or a small link"; spacing/elevation are relational) are REPORT-ONLY, not gates. Forcing a gate on a fuzzy class reproduces the dupe-detector's 60%-precision failure and the gate gets disabled.

### Classes intentionally NOT built (covered or low-signal, rule 12)
- color-role: `blue-sparse-gate.py` already gates blue-overuse in mockups; production measured largely compliant (~3 real violations). Extend that gate to production only if drift grows.
- spacing: `_spacing-drift.md` + `_geometry-report.md` exist. elevation/copy-voice/state-treatment: relational/semantic, low-signal, no clean gate.

### Self-improve loop: adding a new consistency check (the harden-mandate, generalized)
When the owner catches a NEW mismatch class (the way the icon-mixing case started this whole system), turn it into tooling with this proven pattern, do not just add advice:
1. Write `scripts/detect-<class>.mjs` modeled on an existing detector (report-mode, grouped output, `_design-system/_<class>-report.md`, zero new deps). Ground the canonical value + the exceptions from LOCKFILE/CLAUDE.md, and GROUND the false-positive classes by grepping the real code first.
2. Self-test it (rule 12.5): a fixture that SHOULD flag + real cases that should NOT.
3. If the role is machine-unambiguous: factor the classifier into `scripts/lib/<class>.mjs`, build `scripts/hooks/<class>-gate.mjs` importing it (net-new-count, fail-open, `<class>-ok:` + skip-flag + env escape hatches), self-test should-block + should-pass, wire into `.claude/settings.json` PreToolUse Edit/Write. If role-fuzzy: stay report-only.
4. Add the `npm run <class>-check` line + register it in `scripts/consistency-check.mjs` so `npm run consistency` includes it.
5. Park any surfaced rule contradiction in `QUESTIONS.md` for the owner; the gate waits on the ruling (as the icon rule did).

The DRIFT these detectors surface (76 dupe, 0 icon, 422 type-scale, 90 selected) is a separate remediation workstream, not part of building the system: customer-facing fixes go through mockup-first + owner sign-off.
