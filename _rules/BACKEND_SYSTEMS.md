# Solen Backend , How It All Works

This doc is the how-it-works map of every backend system on Solen: what it does, how the flow runs end to end, and what its current health/security state is. Read it before touching backend code.

For WHAT exists (routes/tables/components inventory), see `_inventory/SURFACE.md`. For the security checklist every new route must pass, see `_rules/SECURITY_RULES.md`. For the do/don't patterns (the recurring mistake classes), see `_rules/BACKEND_DOS_AND_DONTS.md`.

## Stack in one paragraph

Solen runs on Next.js App Router (API routes under `app/api/**`, server components for pages) talking to a Supabase Postgres database. Every table has Row Level Security (RLS) turned on, so the database itself decides who can read/write each row, not just the app code. There are two ways to talk to the database: the "session" client, which carries the caller's cookie and is subject to RLS as that user, and the "admin" client, which uses the service-role key and bypasses RLS entirely (used only in trusted server code after an explicit ownership check). Stripe handles all money movement (card charges, Connect payouts to salons, refunds), arriving back via one webhook. The app deploys to Netlify automatically from `main`. Recurring jobs (charging cards, sending reminders, nightly backups) are not self-triggering; GitHub Actions pings around 25 `/api/cron/*` routes on a schedule, each guarded by a shared secret.

## Systems

### Auth & Identity
**In one line (plain):** This is the system that knows who you are on solen.ch, logs you in and out, decides whether you're a customer, a salon owner, or an admin, and handles "delete my account" requests.

**What it does:** It signs people up and logs them in (email+password, Google, and a phone-number OTP step for salon onboarding), keeps them logged in across page loads via a cookie, and checks on every request whether that cookie really belongs to a real, currently-valid session (not just a cookie someone typed in). It also decides what each logged-in person is allowed to see: a normal customer, a salon owner (their own dashboard), or a site admin (everything). Finally, it runs the "download my data" and "delete my account" flows required by Swiss/EU privacy law (revDSG/GDPR).

**How it works (the flow):**
1. **Sign up**: The browser posts to `app/api/auth/signup/route.ts`, which validates the password (8+ chars, one uppercase, one digit), calls Supabase's `auth.signUp()`, and always returns the same generic "verification code sent" message whether the email is new or already registered (this is deliberate, so an attacker can't use the signup form to find out which emails already have accounts).
2. **Email confirm / OAuth / magic link**: Whatever link Supabase emails (or the Google OAuth redirect) lands on `app/api/auth/callback/route.ts`. It exchanges the one-time `code` for a real session, writes the session cookies onto the redirect response, and then checks `profiles.onboarding_completed` , if it's false, it silently reroutes a freshly-verified customer into `/{locale}/onboarding` instead of wherever they were headed (salon-owner onboarding is left alone). The redirect target is validated against `/`-only relative paths so this can't be used as an open redirect.
3. **Password login**: `app/api/auth/login/route.ts` handles three request shapes in one POST: Google OAuth kickoff, password-reset email, and email+password sign-in via `supabase.auth.signInWithPassword()`. The session lands entirely via `Set-Cookie` , the JSON response body only ever says `{ message: "Logged in" }`, it does not echo the access/refresh tokens (this used to leak them; see Current health below).
4. **The cookie itself**: `lib/supabase.ts` (`createServerSupabaseClient`) and `lib/supabase-browser.ts` (`createBrowserSupabaseClient`) both go through `@supabase/ssr`. The session cookie is intentionally NOT `httpOnly` , the browser-side client reads it straight off `document.cookie` for instant client-component UI state, so making it `httpOnly` would silently log everyone out client-side. This is a documented tradeoff (see gotchas).
5. **Every request, is this a real person?** Any route that needs to know who's calling does `const { data: { user} } = await supabase.auth.getUser()`. `getUser()` makes a network round-trip to Supabase's Auth server and cryptographically verifies the JWT; it fails CLOSED (returns `user: null`) if verification fails. The codebase used to call `getSession()` instead, which just trusts whatever the cookie claims without checking it against the server , that was a real, fixed security bug (see below). `middleware.ts` does the same `getUser()` check on every non-static request (with a defensive 4-second timeout so a slow Supabase Auth server can't hang the whole site), and the shared helpers in `lib/auth/require.ts` (`requireAuth`, `requireAdmin`, `requireSalonOwner`, `requireRole`) do it for individual API routes.
6. **Roles**: `profiles.role` is a plain string column (`customer` / `salon_owner` / `admin` in practice; there's also a `staff_salon_id` column and an `is_admin` boolean that look like older/parallel signals, not the canonical one , `role` is what every RLS policy and every `require*()` helper actually checks). `requireAdmin()` and `requireRole()` in `lib/auth/require.ts` look up `profiles.role` for the current `user.id` and return a 403 `NextResponse` if it doesn't match; `requireSalonOwner(salonId)` instead checks `salons.owner_id === user.id` for a specific salon.
7. **Middleware gating dashboard routes**: `middleware.ts` redirects anyone hitting `/{locale}/dashboard/**` without a session to `/auth/login`. If they have a session but `profiles.role` isn't `salon_owner`/`admin`, it does one extra fallback check , does this user own a salon anyway (`salons.owner_id = user.id`)? If yes, it auto-heals the stale role by writing `role = 'salon_owner'` back onto the profile (a self-repair for onboarding flows that failed to set the role). A fixed list of admin-only subpaths (`adminOnlyPaths` in `middleware.ts`) gets an extra `role === 'admin'` check on top of the owner check. If anything in this whole block throws (a DB blip, a cookie parse error), the `catch` now fails CLOSED for dashboard paths , it redirects to login rather than letting the request through unauthenticated (this used to fail OPEN; fixed, see below).
8. **The RLS identity model**: Postgres Row Level Security policies key off `auth.uid()` (Supabase's built-in function returning the current JWT's subject) compared against `profiles.id`, since `profiles.id` IS the `auth.users.id` (one-to-one). A typical admin-only policy looks like `EXISTS (SELECT 1 FROM profiles WHERE id = auth.uid() AND role = 'admin')` (see e.g. `supabase/migrations/020_site_content.sql:20`, `027_rls_hardening.sql:18`). There are two different Supabase clients in play: the "session" client (`createServerSupabaseClient()`) carries the caller's cookie, so every query it runs is subject to RLS as that user; the "admin" client (`createAdminSupabaseClient()`) uses the `service_role` key and bypasses RLS entirely , it's used server-side, after an explicit `require*()` check has already established who's allowed to do what (e.g. in `app/api/profile/delete/route.ts`, `app/api/profile/export/route.ts`).
9. **Phone OTP** (used during salon-owner onboarding, not customer login): `app/api/auth/verify-phone/send/route.ts` requires a logged-in session, generates a 6-digit code with `crypto.randomInt`, stores it in Upstash Redis for 10 minutes, and sends it via the seven.io SMS API (falls back to a "simulated" success if the SMS API key is missing, i.e. local dev). `app/api/auth/verify-phone/check/route.ts` compares the submitted code against Redis and deletes it on success.
10. **Local dev shortcut**: `app/api/dev/login/route.ts` mints a magic-link session for one hardcoded seed test-owner email (`hiroseseiju@proton.me`) using the service-role client, then verifies it against a session client so the redirect response carries real cookies. It 404s outright unless `NODE_ENV === "development"`, so it cannot run against the Netlify production build.
11. **GDPR deletion/export**: There are actually TWO deletion endpoints doing overlapping work for a logged-in user , `app/api/profile/delete/route.ts` and the newer `app/api/profile/request-deletion/route.ts`. Both: block deletion if the user owns a salon with active (`confirmed`/`pending`) bookings, then stamp `profiles.deletion_requested_at = now()` and `account_status = 'suspended'`, write an `account.delete_requested` row via `lib/audit.ts`'s `logAuditEvent`, and return "deleted in 30 days." A cron (`app/api/cron/process-deletions/route.ts`, outside this section's scope) later hard-deletes the auth user after 30 days, which cascades and fires a DB trigger that anonymizes financial rows. `request-deletion` additionally handles a GUEST erasure path (no session, proven via `reference_code` + matching `guest_email`) that anonymizes PII immediately via `lib/gdpr/anonymize-guest.ts`, with SQL-LIKE wildcard escaping and a uniform 200 response regardless of match (anti-enumeration). `app/api/profile/export/route.ts` (self-service "download my data") pulls the user's rows from ~18 tables via the admin client and streams them back as a downloadable JSON file, logging an `account.data_export` audit event.

**Gotchas / traps:**
- **`getUser()` not `getSession()`, always.** This project had a real production security bug from trusting `getSession()` (an unverified, client-suppliable cookie claim) for auth decisions; it was fully migrated to `getUser()` (commit `9783e5711`, "security(auth): verify JWT via getUser() platform-wide"). `lib/auth/require.ts` and `lib/supabase.ts` both carry long comments explaining why. Round 1 of this session's audit found the codebase's own AI "roadmap generator" prompt still told future code to use `getSession()` , flagged as finding #5, fix is a one-line prompt-text change.
- **The session cookie is NOT `httpOnly`, on purpose.** `lib/supabase.ts:27` documents this at length: `@supabase/ssr`'s browser client reads the session via `document.cookie`, so flipping `httpOnly: true` would silently blank out every client component's session. The compensating control is the CSP header in `next.config.mjs` (added specifically for this, per `_plans/WORKLOG.md:15`), not an actual cookie flag fix. This is a deliberate, documented tradeoff, not an oversight , but it means an XSS bug anywhere on the site (a stored payload in a salon description, review, or chat message) could still steal a live session.
- **Two GDPR deletion endpoints exist and do almost the same thing for logged-in users** (`app/api/profile/delete/route.ts` and `app/api/profile/request-deletion/route.ts`). The newer one additionally handles guest erasure , but per the audit, nothing in the UI actually calls `request-deletion` (open item, see below).
- **`app/api/auth/verify-phone/check/route.ts` imports `createServerSupabaseClient` but never calls it** , it does not check for a logged-in session at all, unlike its sibling `send/route.ts` which does (fixed to require login). The two-factor protection here is really just "know the phone number + guess the right 6-digit code within a rate limit," not an auth check.
- **`dev/login` is real and unlockable in dev**, but hard-locked to `NODE_ENV === "development"` and one hardcoded seed email , it cannot be pointed at an arbitrary account, and 404s outright on the Netlify production build (`NODE_ENV=production` at build time).
- **`profiles.role` is a plain `string` column, not a Postgres enum** (`lib/database.types.ts:4431`) , nothing in the type system stops a typo like `'admn'` from silently granting nobody any access; the actual constraint is only whatever `require*()` and RLS policies compare against.
- **Middleware's admin-route gate is defense-in-depth, not the only gate** , every admin route also re-checks role itself server-side (via `requireAdmin()`), so a route missing from `middleware.ts`'s `adminOnlyPaths` list is not, by itself, an open door.

### Storage & Files

**In one line (plain):** This is where every uploaded picture and document lives (review photos, salon licenses, staff portfolios, client before/after shots, discovery videos' thumbnails), organized into 13 separate "buckets" (think: 13 separate folders with their own lock-or-no-lock setting).

**What it does:** Any time a user or salon owner uploads a photo or file, the app puts the raw bytes into a Supabase Storage bucket and keeps a small database row pointing at it (a path or a URL). Some buckets are public (anyone with the link can view, e.g. review photos, discovery images), others are private (only the owner/salon can see them, e.g. client photos, salon compliance documents, hair-formula before/after shots). Uploads always go through the server, never straight from the browser to storage, so the server can check file type, size, and ownership first.

**How it works (the flow):**
1. A route like `app/api/reviews/[id]/photos/route.ts`, `app/api/salon/documents/route.ts`, `app/api/dashboard/coiffeur/formula-photo/route.ts`, `app/api/clients/[id]/photos/route.ts`, or `app/api/staff/portfolio/route.ts` receives a `multipart/form-data` POST with a file.
2. The route authenticates the caller (`createServerSupabaseClient()` + `auth.getUser()`), checks ownership (does this review/salon/client/staff member belong to this user), validates MIME type and file size (this is inconsistent, see Gotchas), then rate-limits.
3. The actual write to Supabase Storage goes through `createAdminSupabaseClient()` (the service-role client from `lib/supabase.ts:88`, which **bypasses RLS** entirely) calling `.storage.from("<bucket>").upload(path, file)`. The admin client is used for uploads because the storage RLS write policies are keyed on the folder name matching the owner's ID, and using the admin client sidesteps any RLS edge case while the route itself has already done the real authorization check in application code.
4. The upload path is built by the route, not the client, e.g. `${salonId}/${Date.now()}-....ext` (salon-documents) or `${salon.id}/${customerId}/${Date.now()}.ext` (client-photos). The leading folder segment is always the owner ID (salon_id, customer_id, staff/salon_id) because the storage.objects RLS SELECT/INSERT policies pattern-match on `(storage.foldername(name))[1]`.
5. A row is written to a companion table (`review_photos`, `salon_documents`, `client_photos`, `staff_portfolio_images`, `coiffeur_formula_photos`) holding either the public URL (public buckets) or the raw storage path (private buckets, never a URL, since a signed URL would go stale sitting in the database).
6. On read, public buckets are served via `admin.storage.from(bucket).getPublicUrl(path)` (a pure string-builder, does not check the bucket is actually public), private buckets are served via `admin.storage.from(bucket).createSignedUrl(path, expirySeconds)` minted fresh on every GET (e.g. `client-photos` at a 1-hour expiry, `salon-documents` at 1 hour).
7. `app/api/discovery/thumb/[id]/route.ts` is a special case: it is not a user-upload route at all, it is a caching proxy. TikTok's thumbnail URLs expire, so the route re-fetches from TikTok's oEmbed API, pipes the bytes back to the caller, and persists its own permanent copy into the `discovery-images` bucket under a `tiktok-cache/` prefix (`STORAGE_PREFIX`) so subsequent requests skip TikTok entirely (`X-Cache: STORAGE` header signals a hit from Storage; `X-Cache: HIT` signals the in-memory cache; `X-Cache: MISS` means it just fetched fresh from TikTok).
8. `.claude/hooks/no-phantom-bucket-gate.py` is a PreToolUse hook that runs whenever Claude edits/writes a `.ts`/`.tsx` file whose new text calls `.storage.from("<bucket>")` with an upload/download/getPublicUrl/createSignedUrl chain. It cross-checks the bucket name against `_inventory/_storage-buckets.json` (the 13-bucket manifest) and BLOCKS the edit if the bucket is not in that manifest, because a route writing to a bucket that was never created fails at runtime (see the Round-2 audit finding below, which is exactly what this hook was built to prevent from happening again). It only fires on new edits, so it cannot catch phantom-bucket bugs already sitting in unedited files (see Gotchas).

**Gotchas / traps:**
- **`getPublicUrl()` never checks the bucket is actually public.** It is a pure string-builder; call it against a private bucket and you get a URL that always 403s. This was a real bug (client-photos, fixed, see health below), and it is a trap any new route can reintroduce. Rule of thumb: public bucket -> `getPublicUrl()`, private bucket -> `createSignedUrl()`, always. Never persist a signed URL to the database (it expires); persist the raw storage path and mint the signed URL fresh on every read, as `app/api/clients/[id]/photos/route.ts` and `app/api/salon/documents/route.ts` both correctly do.
- **Folder-scoped RLS convention**: every private bucket's storage.objects policy pattern-matches `(storage.foldername(name))[1]` against the caller's own ID (or the salon ID they own). The upload path MUST start with that folder segment or the RLS insert will reject it (irrelevant when using the admin client, which bypasses RLS, but still the convention every route follows so a future RLS-respecting client keeps working). See `supabase/migrations/20260712160000_create_missing_storage_buckets.sql` for the exact pattern (`(storage.foldername(name))[1] in (select id::text from salons where owner_id = auth.uid())`).
- **`app/api/staff/portfolio/route.ts` uploads to a bucket that does not exist.** It calls `.storage.from("staff-portfolio-images")` (route.ts:73,81), but the 13-bucket manifest only has `barber-portfolio-images` and `nail-portfolio-images` , there is no `staff-portfolio-images` bucket, live or in any migration. This route currently 500s on every upload attempt at the `.upload()` call, before it even reaches the next bug.
- **Same route also inserts the wrong column name.** It writes `staff_member_id` and `caption` into `staff_portfolio_images` (route.ts:85,87), but the live table (confirmed in `lib/database.types.ts:7395-7425` and migration `032_staff_portfolio_images.sql`) only has a `staff_id` column and no `caption` column at all. PostgREST rejects unknown insert columns loudly (not a silent no-op), so even if the bucket existed, this insert would 500. ### Bookings & Availability

**In one line (plain):** This is the calendar-and-checkout engine: it turns an open time slot into a confirmed appointment, and undoes that safely if the customer cancels, reschedules, or rebooks.

**What it does:** It tracks every bookable time slot per salon/staff/service (`available` -> `booked` -> freed again), and creates/cancels/reschedules the actual appointment (`bookings` row) that a customer holds against one of those slots. It supports both logged-in customers and anonymous guests (name+phone only, no account), auto-assigns "any available" staff, prices multi-service and bundle bookings, freezes the salon's cancellation/no-show policy onto the booking at creation time so refund math never depends on a policy the salon changed later, and drives recurring, group, and "book again" (express-rebook) variants of the same core flow.

**How it works (the flow):**
1. **Browse (read-only, public):** the customer's device asks `GET app/api/availability/[salon_id]/route.ts` or `GET app/api/slots/route.ts` for open times. Both now read from the view `availability_slots_public` (migration `supabase/migrations/20260712160500_c1_availability_slots_public_view.sql`), a safe-columns projection of the base table `availability_slots` that hides `client_id`, `booked_by`, `booking_id`, `price_override`, `block_reason`. `slots/route.ts` re-attaches `price_override` afterwards via the admin client (needed for the "last-minute discount" badge) rather than exposing it through the view.
2. **Create a booking:** `POST app/api/bookings/route.ts` is the main entry point. It resolves the slot two ways: an explicit `slot_id` (dashboard/legacy) or `salon_id + service_id + starts_at` (consumer pay-confirm), matched against `availability_slots.status = 'available'`. If staff is "any", `lib/bookings/auto-assign.ts` (`pickSlotForAnyStaff`, `countStaffBookingsOnDay`) picks one per the salon's `auto_assign_method` and optional daily cap, always via the admin client so the count sees the salon's real load, not just the caller's own rows under RLS. It then runs a stack of server-side guards (online-booking-enabled toggle, salon-vacation-range block, deposit/prepay-requires-online-payment), prices the booking (primary service + extra services + optional bundle via `lib/pricing/bundle.ts`'s `loadPricedBundle`, which also widens `ends_at` for a bundle's summed duration and pre-checks for an overlap on the same staff), snapshots the salon's cancellation/no-show policy onto the row (`policy_snapshot`, `policy_accepted_at` , this is the legal basis every later fee-charge path checks), inserts the `bookings` row, then flips the slot to `booked` with a compare-and-swap (`.eq("status","available")` on the UPDATE) so two simultaneous requests can't both win the same slot; a lost race rolls back the just-inserted booking and returns `409 SLOT_TAKEN`.
3. **Guest vs logged-in, and the RLS-CLIENT-TRAP:** a logged-in user's booking insert runs on the normal session client (RLS policy `bookings_insert_auth` allows `user_id = auth.uid()`). A guest has no `user_id`, so that same RLS policy would reject the insert , the route therefore switches its DB handle (`const db = isGuest ? createAdminSupabaseClient() : supabase`) so every guest write goes through the service-role client that bypasses RLS. The identical trap applies to `availability_slots` writes: that table's UPDATE policy is owner-only, so a customer's own session client silently matches 0 rows when trying to flip a slot to `booked` (it looks like "the slot was already taken" when really the write was never permitted). The dedicated fix is `lib/bookings/claim-slot.ts` (`claimSlot()`), the one shared CAS-claim helper documented to require an admin client, used by reschedule/express-rebook/recurring; the main create route inlines the same admin-client CAS pattern directly.
4. **Guest identity after booking:** `lib/bookings/guest-access.ts` mints a random access token (`issueAccessToken()`) before the insert; only its hash + expiry is persisted on the booking row, the raw token is returned once in the API response and exchanged for an httpOnly cookie. Later guest actions (cancel/reschedule/view) go through `lib/bookings/authorize.ts`'s `resolveBookingActor()`, the single resolver for "who is allowed to touch this booking" (customer by `user_id`, admin by `profiles.role`, salon by `salons.owner_id`, or guest by cookie + `verifyAccessToken` against the booking's stored hash). `lib/bookings/reference.ts` stamps a human-readable order/reference code after insert.
5. **Cancel:** `POST app/api/bookings/[id]/cancel/route.ts` (a `GET` on the same route gives a refund-preview without mutating anything). Computes the fee via `lib/cancellation-policy.ts` (`calculateCancellationFee`/`calculateNoShowFee`, integer Rappen, capped at what the customer actually paid, using the booking's frozen `policy_snapshot`, not the salon's live settings). Flips the booking to `cancelled` with a CAS that re-checks both `status` and `slot_id` (guards against a concurrent reschedule silently moving the slot mid-cancel), frees the slot back to `available`, and notifies the first 3 waitlisted customers for that salon/service/date (only stamping `notified_at` once the email actually sent). Money movement for a customer cancel goes through `lib/bookings/customer-cancel-money.ts`; refunds themselves go through the single chokepoint `lib/bookings/issue-refund.ts`.
6. **Reschedule:** `POST app/api/bookings/[id]/reschedule/route.ts`. Only `confirmed`/`pending` bookings, only more than 24h out (`RESCHEDULE_MIN_LEAD_HOURS`), same service/staff. Order matters: claim the NEW slot first (CAS via `claimSlot`, admin client), then move the booking (CAS on old `slot_id`+`status`), then free the OLD slot last, so there's never a window where the old slot is bookable while the reschedule is half-finished, and a failed step rolls back cleanly.
7. **Recurring / group / express-rebook / walk-in:** `app/api/bookings/recurring/route.ts` creates a `recurring_booking_rules` row plus an immediate first booking if a matching slot exists (mirrors the deposit/prepay payment-mode gate of the main route). `app/api/bookings/group/route.ts` calls the Postgres RPC `create_group_booking` for atomic multi-member slot reservation. `app/api/bookings/express-rebook/route.ts` (suggest) + `express-rebook/confirm/route.ts` (create) let a customer one-tap rebook a past salon/service; the confirm route now verifies the client-supplied `service_id`/`staff_id` actually belong to the resolved slot's salon before using them. `app/api/bookings/walk-in/route.ts` + `walk-in-verify/route.ts` handle the pay-to-queue walk-in flow (separate from the appointment slot lifecycle).
8. **Status transitions:** a booking is created as `confirmed` (instant, in-person), `pending_approval` (salon set to `manual_approval`), or `pending` (online prepay/deposit, awaiting the Stripe webhook to flip it `confirmed`+`paid`). From there it moves to `cancelled` (customer or salon), `completed` (post-appointment cron), or `no_show`. `availability_slots.status` moves `available` -> `booked` -> back to `available` on cancel/reschedule, or `blocked` (owner-managed via `app/api/availability/manage/**`).

**Gotchas / traps:**
- **The RLS-CLIENT-TRAP is the #1 must-know here.** Both `bookings` INSERT (for a guest, no `user_id`) and `availability_slots` UPDATE (for any customer, the policy is owner-only) will silently match 0 rows under the session/anon client, not error, just no-op. Every write path in this system has to consciously reach for the admin client (`createAdminSupabaseClient()`) for these two operations. `app/api/bookings/route.ts:126` picks the client once (`db = isGuest ? admin : supabase`) for the booking insert; `lib/bookings/claim-slot.ts` is the shared, documented CAS helper for the slot flip, used by reschedule/express-rebook/recurring. When adding a new booking-write path, grep for how the existing ones pick their client before assuming the session client "should" work.
- **The C1 barrier view is HALF-applied, on purpose (parked).** `availability_slots_public` (migration `20260712160500`) is live and both browse routes use it. The companion "flip" migration that actually closes the leak on the base table (`20260712161000_c1_flip_availability_slots_owner_only.sql`) is written but explicitly **NOT applied** , its own header says "NOT APPLIED, do NOT run this migration yet." Until it's applied, the base `availability_slots` table's live RLS SELECT policy still has an `OR true` clause, meaning ANY caller (no auth needed) can still `select * from availability_slots` and get every column including `client_id`/`booked_by`/`booking_id`/`price_override`/`block_reason` for all ~9,365 rows, proven live via a direct anon-key REST curl in the Round-2 audit. The flip is held back because several logged-in-customer write paths (`app/api/bookings/route.ts:181`'s slot-resolution query, plus reschedule/express-rebook/recurring/group's own slot reads) still read the base table on the session client during a booking-write transaction, and flipping to owner-only RLS before those are repointed to the view or the admin client would break booking for real customers with a silent empty-result, not an error. This needs a follow-up pass + a live non-owner customer test before the flip can ship.
- **CAS everywhere, not soft locks.** Slot claims, booking cancels, and reschedules all re-assert the exact row state they read (`.eq("status", ...)`, sometimes `.eq("slot_id", ...)` too) on the write, and treat "0 rows updated" as a lost race, not success. If you add a new booking mutation, follow this pattern rather than a plain UPDATE.
- **`policy_snapshot` is the legal basis for every later fee charge.** It's frozen onto the booking at create time (`policy_accepted_at`) precisely so a later cancel/no-show fee calculation never depends on whatever the salon's cancellation policy happens to say today. `chargeFee`'s callers refuse to charge a booking with no `policy_accepted_at`.
- **`opening_hours` is short-day-keyed** (`mon`...`sun`) in live data; `lib/salon-hours.ts` checks both short and long keys defensively because a past bug (long-key-only lookup) made `isOpenNow` return false for every salon.
- **Recurring bookings previously skipped payment entirely** on deposit/prepay salons (a "known" finding in `_plans/DEEP_AUDIT_REPORT.md`). The current code at `app/api/bookings/recurring/route.ts:83-97` already branches on `payment_mode` and mirrors the main route's `pending`/payment_status contract, so this reads as fixed in the live tree even though the audit doc still lists it; no corresponding fix-migration or commit hash was found to cite, so treat this as "fixed in code, not independently re-verified this pass."

### Payments & Money

**In one line (plain):** This is everything that moves real Swiss francs on Solen: charging a customer's card for a booking, splitting that charge between the salon and Solen's commission, refunding money, and the side-currencies (gift vouchers, referral credit, promo codes) customers can spend instead of a card.

**What it does:** A customer's card is charged through Stripe, and the money is split at the moment of charge so the salon's share lands directly in the salon's own Stripe account (a "Connect destination charge") while Solen's commission is skimmed off automatically as an `application_fee`. Solen never holds the salon's money in between. On top of a plain card charge, a booking can also be paid down with a promo code, a Solen Plus member discount, referral credit, or a purchased gift voucher, all stacked in a fixed order so the salon and Solen never double-discount each other. Refunds, disputes (chargebacks), and Swiss VAT/MWST splitting all flow back through the same webhook that confirms a successful charge.

**How it works (the flow):**
1. **Booking created unpaid** by `app/api/bookings` (out of scope here), then the customer hits pay.
2. **Charge created** by `app/api/stripe/booking-pay-intent/route.ts`. This is the real engine room: it re-derives the price server-side (never trusts the client), re-validates any promo code against the live `promo_codes` row, applies the Solen Plus member commission-waiver via `lib/loyalty/perks.ts` (`resolveMemberDiscount`), then atomically "reserves" both the promo use and the member-discount use with the SECURITY DEFINER RPCs `reserve_promo_use` / `reserve_member_discount` (this stops two concurrent checkouts from both winning a limited-use promo). It creates a Stripe PaymentIntent as a **Connect destination charge**: `amount` = what the customer pays, `application_fee_amount` = Solen's cut, `transfer_data.destination` = the salon's Stripe account. After the PI exists, it optionally shrinks the charge further using referral credit (`lib/credits/redeem.ts`) or a spendable voucher code, via the RPCs `redeem_user_credits` / `redeem_voucher`.
3. **Stripe confirms the charge** client-side, then Stripe fires webhooks at `app/api/stripe/webhook/route.ts`. This is the single most important file in this system. Every event is claimed atomically first via an INSERT into `processed_webhook_events` (primary key = Stripe event id), which is the idempotency gate: a duplicate delivery hits a unique-violation and no-ops. If a handler throws, the claim is deleted so Stripe's retry can re-run it cleanly.
4. On `payment_intent.succeeded` for a real booking, the webhook flips the booking to `confirmed`/`paid`, splits the paid amount into net + VAT (`lib/vat.ts`), completes a pending referral if this was the referred user's first booking, and writes a `salon_payouts` ledger row (gross/commission/net) keyed on the PaymentIntent id.
5. **Money leaves Solen's control on `payout.paid`**: Stripe pays the salon's connected account out to their bank on its own schedule; the webhook listens for `payout.paid` and flips the matching `salon_payouts` rows from `recorded` to `transferred` (by walking the payout's own Stripe balance transactions), which is what makes `app/api/salon/earnings/route.ts`'s "total earnings" number real instead of permanently zero.
6. **Refunds** for bookings go through `lib/bookings/issue-refund.ts` (not in this scope file but the sibling of); **package/retail purchase refunds** go through `lib/purchases/issue-purchase-refund.ts`, called by `app/api/salon/retail/[id]/refund/route.ts`. Both reverse the Connect transfer and (by policy) the application fee, claim the refund amount in the DB with a compare-and-swap BEFORE calling Stripe (so two concurrent refund clicks can't double-refund), and the webhook's `charge.refunded` case is the single canonical place that re-syncs the `salon_payouts` row afterward (recomputed from the Stripe charge's own cumulative `amount_refunded`, never by subtracting twice).
7. **Non-card money**: gift vouchers (`vouchers` table, bought via `app/api/vouchers`, finalized by `salon-voucher-handler.ts`), discount/promo vouchers (`promo_codes` rows with `is_purchased_voucher:true`, minted by `app/api/vouchers/create`, finalized by `voucher-handler.ts`), gift cards (`gift_cards` table, finalized by `gift-card-handler.ts`, feature is owner-KILLED/HIDDEN on the frontend per memory but the backend still exists), referral credit (`user_credits`, earned via `app/api/referral/complete`), and walk-in payments (`app/api/walkin/pay-intent`, a manual-capture "hold" charged later when the barber marks the customer served) are all separate small systems that ultimately either become a discount inside `booking-pay-intent` or their own standalone Stripe charge.
8. **Commission rate**: a single platform-wide default lives in `platform_settings` (key `commission`), readable/writable by an admin only via `app/api/admin/commission/route.ts`. Every charge computes its own commission from the ACTUAL `application_fee_amount` Stripe returns (never re-derived from the rate after the fact), so a Solen Plus member discount that shrank the fee is always reflected correctly downstream.

**Gotchas / traps:**
- **Two unrelated "voucher" systems share one word.** A "salon gift voucher" (`vouchers` table, bought at `app/api/vouchers`, e.g. buy CHF 100 for someone) is a completely different thing from a "purchased discount voucher" (a `promo_codes` row with `is_purchased_voucher:true`, minted at `app/api/vouchers/create`, e.g. buy a CHF 20-off code). They use different webhook handlers (`salon-voucher-handler.ts` vs `voucher-handler.ts`) keyed on different `pi.metadata.type` values (`"voucher"` vs `"voucher_purchase"`). Read the file header comments before touching either.
- **`app/api/vouchers/confirm/route.ts` is now mostly dead weight.** Its own webhook sibling's comment says this used to be the only finalizer, fired from a client `onSuccess` callback that never actually ran (Elements confirm lacked `redirect:"if_required"`), so paid vouchers were created but never usable. The webhook (`salon-voucher-handler.ts`) is now the reliable finalizer; `confirm/route.ts` still exists and still works (it independently re-verifies the PI with Stripe) but is redundant, not load-bearing.
- **`app/api/promo/validate/route.ts` has a stale code comment.** It says "promo discounts are not yet applied to the booking Stripe charge (booking-pay-intent ignores promos)" , that was true once but is no longer accurate: `booking-pay-intent/route.ts` has applied promos server-side since the 2026-06-30 fix. The comment was never updated; don't trust it when reading that file.
- **Commission is always read from the real Stripe `application_fee_amount` on the PaymentIntent, never re-derived from `commission_rate x gross`.** This matters because a Solen Plus member discount reduces the fee Stripe actually charged; re-deriving from the rate would silently over-report Solen's commission and disagree with what `bookings.platform_fee` already recorded. This same discipline repeats in the off-session-charge branch (upcharges, cancellation/no-show fees) and in `purchase-handler.ts`.
- **`salon_payouts.status` only has three legal values**: `recorded` | `transferred` | `failed` (DB-constrained). Nothing ever sets `'paid'` or `'pending'` , a filter on those values silently returns nothing (this was exactly the Round 1 bug that made `total_earnings` always show CHF 0, see health section).
- **`opening_hours`/day-key traps don't apply here, but the equivalent trap in this system is metadata `type` tags on PaymentIntents.** The webhook's generic booking-status write is explicitly guarded to skip `pre_charge` / `upcharge` / `cancellation_fee` / `no_show_fee` PIs (`app/api/stripe/webhook/route.ts` around line 211) because those flows already set the correct `payment_status` themselves; forgetting to add a new off-session charge type to that exclusion list will silently downgrade an already-paid booking back to `deposit_held` (this was Round 1's headline critical bug, now fixed, see below).
- **Refund order matters for idempotency**: both refund chokepoints (`issue-purchase-refund.ts` and its booking sibling) CLAIM the DB update (compare-and-swap on `refunded_amount`) BEFORE calling Stripe, not after. If Stripe's call then fails, the claim is rolled back. This is deliberate: it closes a race where two different-amount refund requests (e.g. salon + admin acting near-simultaneously) could both reach Stripe before either wrote the DB.
- **Gift cards are a real, working backend system that the owner has hidden/killed on the customer-facing frontend** (per project memory `project_killed_features`). Don't be surprised the routes and webhook handler still exist and work; don't resurface the UI without an explicit owner yes.
- **Retail stock and payment are two separate near-simultaneous races**, both handled: the purchase route blocks an already-sold-out product before charging, and `purchase-handler.ts` (the webhook settle step) additionally detects a genuine oversell race (two buyers both passed the pre-check) and auto-refunds + alerts an admin rather than silently leaving a charged, undelivered sale.

### Crons & Background Jobs

**In one line (plain):** A robot alarm clock (GitHub Actions) rings on a schedule and pokes about 25 different "do this now" web addresses on solen.ch, each of which does one small housekeeping job (charge a card, cancel a stale booking, send a reminder, back up the database), and every job writes down whether it succeeded so a human gets emailed if something breaks.

**What it does:** Nothing on Solen runs itself just because time passes. Every recurring task, from "capture money 24h after a haircut" to "email the founder a daily summary", is a plain API route that some outside scheduler has to call. GitHub Actions is that scheduler: it fires HTTP requests into these routes on a cron timetable, carrying a shared secret so randoms on the internet can't trigger them. Every route logs its own outcome (success/fail, how many rows it touched, how long it took) to one database table, and a failure is surfaced two ways: immediately by email (throttled) and again the next morning in a digest email.

**How it works (the flow):**
1. **Trigger.** `.github/workflows/cron-jobs.yml` runs on 14 different GitHub Actions cron schedules (every 15 min, every 30 min, hourly, every 6h, several fixed daily UTC times, monthly, weekly). Each schedule block is gated by `if: github.event.schedule == '...'` and calls the composite action `.github/actions/ping-cron` with a comma-separated list of `/api/cron/...` paths and the `CRON_SECRET` GitHub secret.
2. **Ping.** `.github/actions/ping-cron/action.yml` curls each path with `Authorization: Bearer <CRON_SECRET>`, a 280s timeout, and now HARD-asserts the response: it must be 2xx AND the JSON body must contain `"ok":true` (parsed with `jq`, or a `grep` fallback if `jq` is missing). If any endpoint fails that check the whole job step exits 1, so it shows red on the Actions dashboard. The comment in the action file explicitly says the old behavior (a soft `::warning::` + exit 0) let a dead cron go invisible, this was fixed.
3. **Auth guard.** Every route repeats (inline, not shared, see Gotchas) the same check at the top: read `CRON_SECRET` from `getServerEnv()`, 503 if it isn't configured, compare the incoming bearer header, 401 on mismatch. This guard sits OUTSIDE the logging wrapper by design (`lib/cron-run.ts` comment), so an unauthorized call never even gets logged as a run.
4. **Business logic + logging spine.** Once authorized, almost every route (23 of 25 active routes, plus `db-backup` and `daily-digest`) wraps its actual work in `withCronRun(name, handler)` from `lib/cron-run.ts`. That wrapper: times the handler, catches any thrown error, calls `reportError("cron:<name>", err)` (from `lib/error-report.ts`, throttled admin email via `lib/alert-admin.ts` -> `lib/email.ts` -> Resend) on a throw, best-effort inserts one row into the `cron_runs` table (service-role client, RLS enabled with **no policies** so only the server-role admin client can write/read it), and finally returns `NextResponse.json({...result, ok, processed?, errors?})` with HTTP 200 if `ok` else 500. `ok` is `false` if the handler threw, returned `ok:false` itself, or returned a non-empty `errors` array (a per-item failure COUNT as a plain number is tolerated for legacy routes but does NOT flip `ok:false`, only an array does).
5. **Human visibility.** `app/api/cron/daily-digest/route.ts` runs once a day at 05:15 UTC (after the 02:00-04:00 UTC batch of daily crons), queries yesterday's bookings created/completed, the last 24h of `cron_runs` failures, and the pending-review backlog, and emails ONE summary to `ADMIN_EMAIL` via `sendEmail`. It only renders a section if that section's own query succeeded (never fabricates a 0). Separately, any single cron that throws fires an immediate (but 15-minute-throttled per scope) admin alert email through `reportError` -> `alertAdmin`.
6. **Money-safety crons run their own logic on top of the same spine**: `pre-charge` (charge saved cards 5 days out via the shared `chargeOffSession` primitive with a deterministic Stripe idempotency key), `release-payments` (capture held deposits 24h after completion, CAS-claims the row first), `release-deposits` (cancel + refund stale pending deposits after 72h, re-checks `status='pending'` in the UPDATE's WHERE clause before touching Stripe), and `reconcile` (read-only: pulls the last 48h of Stripe charges/refunds and diffs them against `bookings`, `retail_purchases`, `gift_cards` etc., emails a mismatch digest, never auto-fixes).

### Search & Discovery (Inspo)

**In one line (plain):** This is the engine behind two different screens that both feel like "search": the salon search/results list (find a coiffeur in Basel that's open now and under 80 CHF), and the Inspo feed (a Pinterest-style scroll of hairstyle/nail/lash photos and TikTok clips you can save or filter by look).

**What it does:** Salon search (`/api/salons`) lets a customer filter salons by city, category, price, gender, amenities, "open now", a specific date/time, or a free-text query, and returns a ranked, paginated list. Inspo (`/api/discovery/feed`) is a separate content feed of user- and salon-posted looks (photos/TikToks) that can be filtered by beauty category, gender, hair texture/style, or searched by term, and personalizes the order for logged-in users based on what they've liked/saved before. A thumbnail proxy keeps TikTok-sourced images alive after TikTok's signed URLs expire. A third, smaller piece (`/api/recommendations`) uses Gemini to hand-pick 3-4 salons for the homepage based on booking history or trending fallback.

**How it works (the flow):**
1. **Salon search** , `app/api/salons/route.ts` (`GET`). The client sends query params (category, city, price range, dates, `q` free-text, lat/lng, sort). If `q` is present, the route first calls `generateEmbedding()` (`lib/search/embeddings.ts`, Gemini `gemini-embedding-001`, 768 dims, 500ms timeout with lexical-only fallback) and passes the vector into the `search_salons_ranked` Postgres RPC to get a relevance-ranked set of salon ids (capped at 60), which becomes the base id filter (`semanticMode`). All the structured filters (city lookup, service-name match, gender, price band, "open now" via `lib/salon-hours.ts`'s `isOpenNow`, time-of-day `period`, `instant_bookable`, a specific `date`) each resolve their own matching salon-id set independently and concurrently (`Promise.all`), then get AND-combined onto the main `salons` query via repeated `.in("id", ids)` calls , this is the "resolve ids, then `.in()`" pattern the project's convention rules require, so pagination/count stay correct even for filters that can't be expressed as a single PostgREST predicate. A missing date/period/instant candidate set short-circuits to an empty result (`emptyResult()`) rather than silently ignoring the filter. Price and distance sorts are the one exception to DB-side sorting: because `min_price` and `distance_meters` are computed after the fetch (from joined `services` rows / the `get_nearby_salon_ids` RPC), the route skips `.range()`, pulls the *whole* matching set, sorts in JS, and only then slices the page , this was a fixed bug (see Current health below).
2. **Inspo / discovery feed** , `app/api/discovery/feed/route.ts` (`GET`). Three branches, tried in order: (a) if `search` is set, it calls the `search_discovery` RPC (full-text rank over name/author/style/tags/description) and logs the term to `discovery_search_events` for trending; (b) if the visitor is logged in AND browsing with no category/gender/texture/style/creator filter ("pure browse"), it calls `discovery_feed_for_you`, which ranks the whole feed by the visitor's derived `user_style_affinity` row (built from their saves/likes/views/searches , cold users score 0 everywhere so the order is unchanged); (c) otherwise it calls the general `discovery_feed` RPC, which takes the structured filters plus a soft gender bias (`profiles.disc_gender`, never a hard filter) and an optional `tags_any` array for the progressive drill-down filter UI. All three RPCs return a `total_count` column on every row (window function) so pagination doesn't need a second query, and all three strip the raw `tiktok_embed_html` blob before returning (kept the feed light).
3. **Discovery category to marketplace category bridge** , `lib/discovery-categories.ts`. The Inspo feed's own categories (`hair, nails, lashes, brows`, plus `beard`/`makeup`/`waxing` in the DB) are a *different taxonomy* from the salon-booking categories (`coiffeur, barbershop, nails, spa`). Anywhere that needs to jump from "I like this Inspo look" to "book a salon that does this," it must go through `DISCOVERY_TO_MARKETPLACE_CATEGORY` (e.g. `app/api/discovery/salons-for-style/route.ts` likely consumes this) rather than passing the discovery category straight into a `salons.categories` filter.
4. **Thumbnail proxy** , `app/api/discovery/thumb/[id]/route.ts` (`GET`). TikTok's thumbnail CDN URLs are cryptographically signed and expire. This route: looks up the item's stable `tiktok_url`, calls TikTok's public oEmbed endpoint to get a freshly-signed thumbnail URL, fetches those image bytes, and **persists a permanent copy to Supabase Storage** (`discovery-images/tiktok-cache/<id>.jpg`) so the card survives forever even after the video itself is deleted or embedding is disabled. Three cache tiers on the way in: in-memory image bytes (1h TTL, capped at 5000 entries) -> Storage (permanent, `X-Cache: STORAGE`) -> live TikTok fetch (`X-Cache: MISS`, then persisted).
5. **Recommendations** , `app/api/recommendations/route.ts` (`GET`). Pulls the visitor's last 5 bookings' categories (if logged in), matches candidate salons on category, falls back to trending-in-Basel if fewer than 3 candidates, then asks Gemini 2.0 Flash to rank the top 3-4 and write a one-sentence reason per pick in the visitor's locale. `app/api/recommendations/chips/route.ts` is a lighter sibling (not read in depth here). There is no `app/api/persona/**` directory or `lib/persona/` module in this repo today , that piece named in scope does not exist server-side (a `lib/persona/deriv.ts` "Hair DNA" reference exists only in the iOS mobile project per project memory, not this backend).

**Gotchas / traps:**
- **Discovery categories are NOT salon categories.** `lib/discovery-categories.ts` explicitly documents this: Inspo uses `hair|beard|nails|makeup|waxing|lashes|brows`, salons use `coiffeur|barbershop|nails|spa`. Only `"nails"` happens to spell the same in both , every other pairing needs `DISCOVERY_TO_MARKETPLACE_CATEGORY` or it silently no-ops (a filter that looks wired but matches nothing, or matches the wrong salons). `makeup`/`waxing` have no direct marketplace equivalent and fall back to `coiffeur`.
- **Computed filters resolve ids first, then `.in()`, never client-side pagination.** `app/api/salons/route.ts` comments this out explicitly (lines ~230-241): city, service, gender, price, period, instant-bookable, and date filters each run as an independent concurrent query/RPC, and the "open now" filter in particular has to be evaluated in JS (`isOpenNow` against the `opening_hours` jsonb) because it can't be a PostgREST predicate , so it fetches candidate ids first and narrows with `.in()` **before** `.range()`, never after.
- **`opening_hours` is short-day-keyed** (`mon...sun`), per the project's own lessons-learned convention , any new code touching it must match that key convention or it silently returns "closed" for every salon.
- **Price/distance sort skip the DB `.range()` entirely.** Because `min_price` and `distance_meters` are post-fetch computed values, sorting by them requires pulling the *full* matching set and paginating in JS after the sort , a DB pre-sort-then-cutoff would have silently dropped the actual cheapest/nearest salon once a city had more than one page of results. This was a real, fixed bug (see health below).
- **The Inspo feed cache is deliberately conservative about personalization.** `app/api/discovery/feed/route.ts` only marks a response cacheable when `userId` is positively null (no session cookie present at all) , any request that resolves a session, even one that ends up in the same "neutral" branch, gets `no-store`, because there's no verified way here to add a cookie-aware `Vary` split against current Netlify CDN behavior.
- **The thumbnail proxy fails closed, not silently.** Any of (item not found / oEmbed down / image fetch failed) returns a 502 with no body; card components need their own gradient fallback under the image (documented in the route's own comment), not an assumption the proxy always returns something.
- **`app/api/persona/**` does not exist in this repo.** It was named in scope but a repo-wide grep found no `app/api/persona` directory and no `lib/persona/` module; the only "persona"/DNA-style personalization here is `user_style_affinity` (Inspo for-you) and the mobile-only `lib/persona/deriv.ts` referenced in project memory, which lives in the separate `solen-mobile` repo, not this backend.

### Salon Dashboard & CRM

**In one line (plain):** This is the salon owner's back-office: the "how's business today" screen, the client record book (notes, photos, allergy/formula history), and the staff roster, and only the salon's own owner (or a Solen admin) can ever open it for a given salon.

**What it does:** A logged-in salon owner sees a live "today" strip (current booking, today's revenue, walk-in queue, rating), a client list built from real booking history (not a separate customer database), and category-specific tools (barber leaderboard/reminders, coiffeur formula photos, nail AI history/retail, spa treatment outcomes). Owners invite staff by email, staff accept and get linked to a `staff_members` row, and staff get a small self-service slice (their own schedule, their own service assignments) completely separate from the owner dashboard. There is no in-between role: a person either owns the salon (or is a platform admin) and sees everything, or is staff and only sees their own small self-service corner.

**How it works (the flow):**
1. **Who am I looking at?** Every dashboard route resolves "the caller's salon" one of two ways: `getActiveSalon()` / `getActiveSalonId()` in `lib/active-salon.ts` (honors the `solen_active_salon` cookie set by the multi-salon switcher, falls back to the owner's oldest salon, and only ever matches rows where `salons.owner_id = userId`), or an explicit `salon_id` in the request that the route then checks against `salons.owner_id === user.id` or `profiles.role === 'admin'`. Both patterns show up across the scope; there is no third path for staff.
2. **There is no `salon_clients` table.** A "client" is just a distinct `bookings.user_id` (or `barber_walkin_queue.customer_id`) that has ever interacted with the salon. `GET /api/dashboard/clients` builds the client list by grouping completed bookings by customer, then joins `public_profiles` for name/avatar and `barber_loyalty_cards` for stamp counts (barbershop only). Any write that attaches data to a specific client (a note, an allergy record, a formula photo, a tag) must first prove the relationship using the shared helper `clientBelongsToSalon()` in `lib/verify-salon-client.ts`, which checks `bookings` (any status) OR `barber_walkin_queue` for that salon_id + client_id pair. Skipping this check was Round-1 finding HIGH-3 (see Health below), and it is now the standard pattern almost everywhere in this scope.
3. **CRM writes go through the admin (service-role) client** because they need to read/write across the RLS boundary (e.g. writing a note about a customer who isn't the one making the request). Routes still do their own explicit ownership + `clientBelongsToSalon` checks before touching the admin client, since the admin client itself has no idea who's asking.
4. **The dashboard "batch" endpoint** (`app/api/dashboard/batch/route.ts`) lets the frontend ask for up to 5 named sub-queries (`bookings_today`, `revenue_month`, `reviews_pending`, `walkin_queue`, `activity_feed`) in one POST instead of 5 waterfalled requests. It checks ownership once (`salons.owner_id` + `profiles.role` in parallel), then runs the requested sub-queries in `Promise.all`, catching each sub-query's own error so one failing key doesn't 500 the whole batch.
5. **Staff invites**: owner calls `POST /api/staff/invite` (session client, RLS-gated by `staff_invites`' owner-only policy), which mints a random token and emails an accept link. The invitee calls `POST /api/staff/accept-invite` with the token; because the accepter is never the salon owner, the RLS-bound session client can't write `staff_members`/`profiles`/`staff_invites`, so that route deliberately uses the admin client for the token lookup, the email-match check, the staff_members insert/link, the `profiles.staff_salon_id` update, and the invite status flip. Email must match the invited address exactly (case-insensitive) before any link happens.
6. **Staff self-service is a separate, narrower surface**: `GET/PUT /api/staff/my-schedule`, `staff/breaks`, `staff/time-off`, and the `staffSelf` branch of `GET /api/staff/services` all resolve "who is this" by `staff_members.user_id = auth.uid()` (never by salon ownership), so a staff member can see and edit only their own rows. `staff_members.permissions` is a text array with (today) exactly two meaningful strings actually checked in code, `edit_own_schedule` and `manage_all`, enforced only in `PUT /api/staff/my-schedule`. Nothing else in the scope reads `.permissions`.
7. **Category-aware nav** (`lib/dashboard/category-nav.ts`) is pure UI config: it maps each `SalonCategory` (barbershop/nails/coiffeur/spa) to a list of sidebar nav groups. It carries no auth or data logic; multi-category salons just get multiple nav groups.

### Loyalty, Rewards & Referral

**In one line (plain):** This is Solen's "keep coming back" system: a frequency rank that unlocks small discounts, a per-salon punch-card the barber stamps by QR when you visit, and a friend-referral code that gives both people CHF credit once the invited friend actually books.

**What it does:** It tracks how often a customer books (Solen Status: Base, Gold, Platinum) and gives Gold/Platinum members a small automatic discount on future bookings, funded by Solen giving up part of its own commission rather than the salon losing money. Separately, individual salons (mainly barbershops) can run their own "10 stamps = free cut" punch card that staff stamp by scanning a QR code the customer shows at checkout. Separately again, every user has a shareable referral code; when someone they invite completes their first real booking, both people get CHF store credit. A fourth, older stamp-card mechanism exists in the code but is dormant (see Gotchas).

**How it works (the flow):**

1. **Solen Status (frequency rank).**
   - Computed on read, not stored live: `GET /api/loyalty/status` calls `getLoyaltyStatus()` in `lib/loyalty/status.ts`, which counts the user's `completed` bookings in a rolling 12-month window from the `bookings` table, where the charged value (from `paid_amount` in Rappen if paid online, else `price_paid`/`estimated_price`) is at least CHF 25 and the booking wasn't refunded. 3+ qualifying visits = Gold, 6+ = Platinum.
   - A monthly cron (`app/api/cron/loyalty-recompute/route.ts`, scheduled 1st of month 04:00 UTC per `.github/workflows/cron-jobs.yml:180`) calls the Postgres function `recompute_loyalty_status()` (added in `supabase/migrations/20260614000000_loyalty_status_rank_phase2.sql`) which writes a snapshot row per user into the `loyalty_status` table, including a `valid_through` date and a "soft drop" (tier falls at most one level at a time even if visits drop off a cliff). The on-read status and the snapshot are blended: tier/visits are always freshly computed, `valid_through` comes from the snapshot.
   - The **money-relevant** tier lookup at checkout does NOT use this route at all. `lib/loyalty/perks.ts`'s `getCurrentTier()` calls a separate SECURITY DEFINER SQL function `current_user_tier(uid)` (same math, mirrored in SQL) so a payment-path decision never depends on anything the browser could influence.

2. **Member discount (the money perk).**
   - `tier_perks` table (`supabase/migrations/20260614010000_solen_plus_phase1_perks.sql`) holds per-tier knobs: Base 0%, Gold 5% (max 2 uses per window), Platinum 10% (max 4 uses). All PLACEHOLDER values, not yet calibrated against real usage.
   - At checkout (`app/api/stripe/booking-pay-intent/route.ts`), `resolveMemberDiscount()` in `lib/loyalty/perks.ts` reads the live tier, the tier's perk row, and how many discounted bookings the user already used this window (`countDiscountUsesInWindow`), then `computeMemberDiscount()` does the actual Rappen math: the customer's charge AND Solen's own `application_fee` both drop by the same amount, so the salon's payout is untouched, only Solen's margin absorbs the discount (capped per salon by `salons.member_commission_waiver_rate`, default 2%).
   - The "reservation" (so a use can't be double-counted across two concurrent checkouts by the same user) is a Postgres RPC pair, `reserve_member_discount` / `release_member_discount`, called from `booking-pay-intent/route.ts:398` and `:496`/`:526`.

3. **Barber loyalty stamp cards (the live QR punch-card).**
   - Tables: `barber_loyalty_programs` (salon's program config: stamps required, reward type/value), `barber_loyalty_cards` (one row per customer per program, `stamps_collected`, `status`: active/completed/redeemed, plus a `qr_token` column), `barber_loyalty_history` (audit trail of stamp/redeem actions).
   - Customer requests their QR: `GET /api/loyalty/qr/[cardId]` generates an HMAC-signed token (`lib/barber/loyalty-qr.ts`, format `salonId:customerId:cardId:issuedAt:hmac`, 5-minute TTL) and persists it as the card's current `qr_token`, then renders it as an SVG QR pointing at `/loyalty/stamp?token=...`.
   - Staff scans it: `POST /api/loyalty/stamp` verifies the HMAC + TTL (`verifyLoyaltyQRToken`), checks the scanning user owns the salon, then atomically consumes the token with a compare-and-swap update (`UPDATE ... WHERE qr_token = <this token>`) before incrementing `stamps_collected`. A second scan of the same QR (screenshot replay) fails because the row's `qr_token` has already changed.
   - When a card completes, staff redeems it: `POST /api/loyalty/redeem` also does a compare-and-swap (`.eq("status","completed")` on the update) so two concurrent redeem clicks can't both succeed, then logs to `barber_loyalty_history` and auto-creates the customer's next active card.
   - Customer reads: `GET /api/loyalty/cards` (list) and `GET /api/loyalty/cards/[cardId]` (single + history). This whole surface is gated behind the `barber_features` flag (`checkFeatureEnabled("barber_features")` in every route).

4. **General loyalty stamp cards (DORMANT).**
   - A separate, older schema: `loyalty_cards` (salon program: `stamps_needed`, `reward_text`) + `loyalty_stamps` (one row per stamp, linked by `loyalty_card_id` + `customer_id`). Read paths exist and are live: `GET /api/loyalty` (customer's cards with progress), `app/[locale]/profile/stamps/page.tsx`, and `app/api/profile/live-state/route.ts` all query these tables.
   - The only place a stamp could ever be inserted is `POST /api/loyalty/award` (`app/api/loyalty/award/route.ts`), which is cron-secret-gated and meant to be called after a booking completes. Nothing calls it: not `app/api/bookings/route.ts`, not the Stripe webhook, not any cron in `.github/workflows/cron-jobs.yml`. So every customer who has a `loyalty_cards` row can only ever see 0 stamps, permanently.

5. **Referrals + credits.**
   - Every user gets a pending `referrals` row (CSPRNG code, format `SOLEN-XXXXXXXXXXXX`) minted automatically by a DB trigger (`trg_generate_referral_code`, migration 049) on `profiles` INSERT. `GET /api/referral` reads that pending code (or mints a fresh one via `insertPendingReferralCode()` in `lib/referral/code.ts` if somehow missing) plus the user's stats (friends invited, unexpired `user_credits` balance).
   - A prospective referred user can pre-check a code via the public `GET /api/referral/validate` (rate-limited separately, `referralValidateLimiter`, because it's a public valid/invalid oracle for a guessable-shaped code).
   - The actual completion and dual CHF-credit is done by ONE shared function, `completeReferralForFirstBooking()` in `lib/referral/complete-referral.ts`, called from three places: `app/api/bookings/route.ts` (instant-confirm/in-person bookings), `app/api/stripe/webhook/route.ts` (online-pay bookings, on `payment_intent.succeeded`), and `app/api/referral/complete/route.ts` (a direct endpoint, which also requires the referred user to already have at least one confirmed/completed booking before it'll pay out). It only fires on the user's genuinely first confirmed booking, uses a compare-and-swap update on the `referrals` row (`.eq("status","pending")`) so a retry or a race can't double-credit, and a partial-unique index (`referrals_one_completed_per_referred_uidx`) is the DB-level backstop against a second code being used by the same person. On success it inserts two `user_credits` rows (referrer + referred, each with a 6-month expiry) and mints the referrer's next pending code.
   - Credits are spent at checkout through `lib/credits/redeem.ts` (`capStoredValueRappen`, `getAvailableCreditRappen`), feeding into the same `booking-pay-intent` flow, gated by the `credits` feature flag (fails CLOSED on any read error, unlike the general feature-flag helper).

6. **Off-peak deals (adjacent, not core loyalty).** `app/api/off-peak/route.ts` lets a salon owner define discounted time-slot rules (`off_peak_slots` table) and, on creating a new rule, emails everyone who favorited that salon. This is a salon-configured promotional discount, not part of the Solen Status/referral system, but is in this system's file scope.

### Walk-in Queue

**In one line (plain):** A shop that takes walk-ins can put customers into a real-time numbered line (pay upfront or cash at the counter), and each customer tracks their own spot from a phone link, no app or login needed.

**What it does:** A customer either walks in and pays with a card (or Apple/Google Pay) to get a queue number, or a staff member types a cash walk-in straight into the same line, or a customer joins remotely (QR code / SMS link) before they arrive. Every ticket gets a short A-number ("A47") and a private, unguessable tracking link (`/queue/[token]`) that shows live position, estimated wait, and lets the customer cancel, tip, or leave a review. Staff run the line from a dashboard board: call the next person, mark them in the chair, complete (captures the held card payment), or no-show (captures a policy fee from the same hold).

**How it works (the flow):**
1. **Getting a number (three entry paths, all funnel into the same table `barber_walkin_queue`):**
   - **Pay-first / online (`walkin_mode = 'pay_first'`):** customer calls `POST /api/walkin/pay-intent` which trusts only the server-side `services.price` (never the client), creates a Stripe PaymentIntent with `capture_method: "manual"` (an authorization hold, not a charge yet), and routes the money via Stripe Connect (`transfer_data.destination` = the salon's connected account, `application_fee_amount` = platform commission). The client then confirms the card with Stripe Elements and calls `POST /api/walkin/confirm`, which retrieves the PaymentIntent, checks it is `requires_capture` or `succeeded`, and calls the shared `createWalkinTicket()` (`lib/barber/walkin-ticket.ts`) to actually insert the queue row and mint the ticket number.
   - **Free join (any other `walkin_mode`):** `POST /api/walkin/queue` or `POST /api/walkin/queue/remote-join` call the shared `joinWalkinQueue()` (`lib/walkin/join.ts`) directly, no payment.
   - **Cash / staff-entered:** the salon owner/staff (logged in) calls `POST /api/bookings/walk-in`, which calls `createCashWalkinTicket()` (`lib/barber/walkin-ticket.ts`) , same table, same position/ticket-number sequence, `payment_intent_id = null`.
   - **SMS payment-link flow:** a salon can text a customer a link to pay for a pre-created `bookings` row (`paid_via = 'walk_in'`). `GET /api/bookings/walk-in-verify` validates an HMAC token (`BOOKING_HMAC_SECRET`) and returns the booking + salon + service context; the customer then pays through the same `/api/walkin/pay-intent` -> `/api/walkin/confirm` path, passing `booking_id` in the PaymentIntent metadata so `confirm` can link the resulting queue ticket back to the booking row.
2. **The number itself** comes from `next_walkin_ticket_seq()` (a per-salon Postgres RPC, migration `20260602150000_walkin_ticket_seq.sql`), an atomic `UPDATE ... RETURNING seq` so concurrent joins can never mint the same "A" number, no daily reset, no timezone math.
3. **Position** is `max(position)+1` among `waiting`/`in_chair` rows for that salon, recomputed and retried (up to 6 attempts) on a unique-index collision (`(salon_id, position)` partial index) , see `insertWalkinEntry()` in `lib/barber/walkin-ticket.ts` and the retry loop in `lib/walkin/join.ts`.
4. **Tracking:** every row gets a `tracking_token` (`nanoid(12)`). This token is the customer's *only* proof of identity (`barber_walkin_queue` has no anonymous RLS policy at all, see `lib/walkin/authz.ts`). The public ticket page polls `GET /api/walkin/queue/status?token=...` every ~30s for live position/wait; the wait re-derives from the salon's **actual recent measured service durations** (`recentAvgServiceMinutes()`, an EWMA over the last 20 completed visits, weighted newest-first, falling back to a flat 30 min until there are 3+ samples), not the frozen estimate from join time.
5. **Staff side:** `PATCH /api/walkin/queue/[id]` (owner/staff auth) moves a ticket through `waiting -> in_chair -> completed | no_show | cancelled`. This is where the money actually moves: `completed` captures the manual-capture hold in full; `no_show` does a *partial* capture of just the salon's no-show-fee policy amount (`lib/cancellation-policy.ts`) and releases the rest; salon-initiated `cancelled` releases the hold or refunds-and-reverses-the-Connect-transfer if it was already captured. `DELETE /api/walkin/queue/[id]?token=...` is the customer's own self-cancel, gated by the same tracking token, and does the equivalent release/refund.
6. **Queue re-sequencing:** whenever someone leaves the active queue (completed/no_show/cancelled/self-cancel), `resequence_walkin_queue()` (a Postgres RPC, migration `20260531_walkin_resequence_fn.sql`) closes the position gap for everyone behind them in one atomic statement.
7. **Live counts / discovery surfaces:** `GET /api/walkin/queue-stats`, `GET /api/walkin/availability` (via `lib/barber/walkin-availability.ts`), and `GET /api/walkin/nearby` all read the same `barber_walkin_queue` + `staff_members` + `services` tables to show "X ahead, ~Y min" on search cards and the homepage walk-in band, always restricted to salons that are `is_active`, `listed_on_marketplace`, and `walkin_enabled`.
8. **After the visit:** `POST /api/walkin/tip` (token-gated, 7-day expiry window from `completed_at`) creates a second, separate PaymentIntent that goes 100% to the salon's Connect account (no `application_fee_amount`, i.e. no platform commission on tips). `POST /api/walkin/review` lets the same tracked customer leave a review once served.

**Gotchas / traps:**
- **`app/api/waitlist/route.ts` is a DIFFERENT, unrelated system** from the walk-in queue: it writes to a `waitlist` table (customers wanting a *future date/time slot* to open up), not `barber_walkin_queue`. Don't confuse the two just because both use "queue/waitlist" vocabulary; Round 1 audit even flagged (`_plans/DEEP_AUDIT_REPORT.md:409`) that there is a *second*, dead waitlist mechanism elsewhere in the booking system, on top of this one, so "waitlist" appears at least twice in this codebase with different meanings.
- **No anonymous RLS policy on `barber_walkin_queue` at all** (`lib/walkin/authz.ts` header comment). Every guest-facing route runs on the admin (service-role) client and must gate manually on `tracking_token`. Any new guest route that skips `findQueueEntryByToken()` and hand-rolls its own `.eq("tracking_token", ...)` check reopens the exact leak class the shared helper exists to prevent (this happened once, see health section).
- **The dual write paths for ticket creation** (`joinWalkinQueue()` for free/public, `createWalkinTicket()`/`createCashWalkinTicket()` for paid/cash) both hand-roll the same position-retry and ticket-number logic independently; they are kept in sync by convention/comments, not by one shared function, so a future change to one must be mirrored in the other (both files cross-reference each other in comments, e.g. `lib/walkin/join.ts:12`).
- **The webhook backstop race:** Stripe's webhook can also call `createWalkinTicket()` as a backstop the instant a hold is authorized, racing the client's own `/confirm` call. Both sides must run `linkBookingToQueue()` regardless of who wins the race (`lib/barber/walkin-ticket.ts:266-269`), or the booking-to-ticket link silently drops. This is now handled correctly, see health.
- **`estimateWaitMinutes()` uses `|| 1`, not `?? 1`,** for the active-barber divisor everywhere it's called, deliberately, so a salon with 0 currently-active staff still estimates against 1 chair instead of showing a false "0 min" wait. Don't "clean up" that operator without checking the comment (e.g. `lib/barber/walkin-ticket.ts:60-61`).
- **Anonymous guests with no phone number have no DB identity to dedupe on** , the free-join dedupe (unique indexes on `customer_id`/`customer_phone`) simply doesn't apply to them, so that specific case falls back to an IP+salon rate limit (`walkinAnonJoinLimiter`) instead of a hard uniqueness guarantee (`lib/walkin/join.ts:99-109`).
- **Tips carry zero platform commission** by design (`transfer_data` with no `application_fee_amount`, `app/api/walkin/tip/route.ts:86`) , don't "fix" this to match the main booking commission logic, it's intentional.
- **The SMS payment-link HMAC token (`walk-in-verify` + `walkin/confirm`) has no `consumed_at` single-use marker of its own** , unlike the general booking `quick-action` link (see health), this token stays valid until its embedded expiry passes. In practice it's lower risk here because the downstream state change (`createWalkinTicket`) is itself idempotent on `payment_intent_id`, but it is not the same double-layered protection the regular booking link now has.

### Notifications & Communications

**In one line (plain):** the system that sends emails, texts, and in-app alerts to customers and salon owners whenever something happens (a booking, a review, a payout, a birthday, a marketing nudge).

**What it does:** Every "something happened, tell someone" moment in the app (booking confirmed/cancelled, review posted or replied to, payout completed/failed, account warning, birthday, off-peak deal, walk-in queue update) routes through a small set of shared helpers instead of each route building its own email. Emails go out through Resend (a third-party email API), a handful of SMS messages go out through seven.io (Swiss SMS gateway), and some events also write a row into an in-app `notifications` table that a user can see inside the product. Marketing-flavored sends (birthday, rebooking nudge, off-peak deal) check a `notification_preferences` opt-out table first; pure signup forms (newsletter, "notify me when this launches", neighbourhood/quartier alerts) just upsert an email into a subscriber table with no confirmation email of their own.

**How it works (the flow):**
1. **The single send funnel**: `lib/notifications.ts` exports `sendNotification({ userId, type, title, body, emailParams })`. It (a) always inserts a row into the `notifications` table via the admin Supabase client (bypasses RLS, so any server code can write a notification for any user), then (b) if `emailParams` was passed, switches on `type` to pick one of ~19 email-template builder functions (from `lib/email-templates/audit-notifications.ts` plus a couple from `lib/email.ts`) and calls `sendEmail()`. Both steps are wrapped in their own try/catch so a DB failure never blocks the email and vice versa (see Gotchas).
2. **The actual email transport**: `lib/email.ts`'s `sendEmail(payload)` is the only place that talks to Resend. It reads `RESEND_API_KEY` via `getServerEnv()`; if the key is missing or still the placeholder string, it logs a warning and returns silently (no email, no error) rather than throwing. If the key is set, it POSTs to `https://api.resend.com/emails` from a hardcoded `noreply@solen.ch` sender; a non-2xx response throws (caller decides whether to swallow it).
3. **Template builders are plain functions, not stored templates**: `lib/email.ts` (subject+HTML builders for booking confirmations, salon lifecycle emails, gift cards, tips, birthdays, nail infill reminders, etc.) plus four sibling files under `lib/email-templates/` (`audit-notifications.ts` for the `sendNotification` switch, `booking-notifications.ts` for booking cancel/reschedule variants, `off-peak.ts` for the favorited-salon deal alert, `salon-onboarding.ts` + `welcome-series.ts` for cron-driven drip campaigns). Each function returns `{ to, subject, html }` in all four locales (de/en/fr/it) and the caller passes it straight to `sendEmail`.
4. **Two review-notification routes bypass `sendNotification` entirely**: `app/api/notify/review-posted/route.ts` and `app/api/notify/review-replied/route.ts` are internal-only routes (gated by a shared `CRON_SECRET` header, not a user session) that `app/api/reviews/route.ts` and `app/api/reviews/[id]/respond/route.ts` call server-to-server to email the salon owner or the reviewer directly, building their own HTML inline with a local `escapeHtml`.
5. **SMS is real, not a stub**: `lib/sms.ts`'s `sendSMS(to, message)` calls seven.io's REST API, gated by `SEVEN_IO_API_KEY`. It also rate-limits to 3 SMS per phone number per day via Upstash Redis (`sms:daily:<phone>` key, 24h TTL) and requires the number to start with `+41` (Swiss numbers only). Two crons use it: `app/api/cron/sms-reminders/route.ts` and `app/api/cron/barber-smart-reminders/route.ts` (which also calls `barberQueuePositionSMS` / `barberYoureNextSMS` string builders in `lib/email.ts`, oddly named alongside the email templates).
6. **The in-app "notifications" the salon dashboard shows are NOT the `notifications` table**: `app/api/notifications/route.ts` (GET) does not read anything `sendNotification` wrote. It computes an ad-hoc list on every request by querying `bookings` (recent cancellations), `reviews` (unreplied ones, via the `review_replies` join), and `barber_walkin_queue` (waiting >30 min) for the salon the logged-in owner is currently viewing, and merges them into a synthetic feed. The `notifications` DB table (written by `sendNotification`) is a separate, customer-facing concept never surfaced by this route. PATCH on this route ("mark all as read") is a documented no-op that just returns success.
7. **Signup/subscribe paths** (no confirmation email is sent for any of these): `app/api/newsletter/route.ts` upserts `{ email }` into `newsletter_subscribers`; `app/api/coming-soon-notify/route.ts` upserts `{ email, feature }` into `coming_soon_signups`; `app/api/quartier/subscribe/route.ts` validates + upserts `{ email, quartier }` into `quartier_subscriptions` via the admin client.

### Reviews, Moderation & Admin Tooling

**In one line (plain):** This is the trust-and-safety layer: customers leave star ratings and comments on completed bookings, a set of automatic filters quietly catch abusive or fake ones, salon owners reply, and a handful of admin-only screens let staff approve/reject/freeze salons, manage badges and audience segments, and review flagged content.

**What it does:** After a booking is marked completed, the customer can leave a rating (1-5, optionally three sub-scores blended into one) plus a comment. Every new review is run through a word-filter and pattern-detector before it is ever shown publicly; anything suspicious is hidden or flagged for a human. Salon owners can publicly reply to a review once. Separately, a family of `/api/admin/*` routes gives staff (role = `admin`) tools to approve or reject a new salon, freeze (suspend) a salon and auto-refund its open bookings, warn a salon (3 warnings = auto-freeze), assign "badges" to top salons, group customers into segments, and resolve booking disputes. Most of these admin actions write an entry to a shared `audit_log` table so there is a record of who did what.

**How it works (the flow):**
1. **Leaving a review.** `POST /api/reviews` (`app/api/reviews/route.ts`) checks the booking belongs to the caller and is `completed`, blocks a second review on the same booking, then calls `checkReview()` in `lib/automod.ts`. That function runs six checks in order: slur/profanity word-list match (hides the review outright), comment under 10 characters (flags but keeps visible), an exact duplicate comment from the same user, a burst of 3+ five-star reviews in 24h where 3+ of the reviewers are brand-new accounts (fake-positive ring), and the mirror check for 1-star review-bombing. The result (`flagged`, `hidden`, `reason`) is written straight onto the new `reviews` row (`is_flagged`, `is_hidden`, `flag_reason`). The route then recalculates the salon's `average_rating`/`review_count` from all non-hidden reviews and fires a fire-and-forget notification to the salon.
2. **Reading reviews.** `GET /api/reviews/salon/[salon_id]` is the public listing: it explicitly selects only safe columns (never `user_id`), joins `review_replies` for any salon reply, and computes `is_verified` from whether the review has a `booking_id`, then strips `booking_id` before responding. `GET /api/reviews/featured` is the homepage carousel: admin client, 4+ star reviews only, not flagged/hidden, filtered again in-route to customer-visible salons.
3. **Salon replies to a review.** There are TWO reply endpoints doing the same job with a real historical scar between them. `reviews.salon_response` (added by migration `021_review_moderation.sql`) was the original inline column. Migration `076_migrate_salon_responses.sql` later copied every non-null `salon_response` into the newer `review_replies` table (one row per review, `reply_text` + `is_public`) and that table is now the live source of truth. `POST /api/reviews/reply` (`app/api/reviews/reply/route.ts`) is the "clean" implementation: it expects `reply_text` in the body and inserts into `review_replies`. `PATCH /api/reviews/[id]/respond` (`app/api/reviews/[id]/respond/route.ts`) is what the actual dashboard UI calls, and the dashboard sends the field as `salon_response`, not `reply_text` , the route has an explicit shim (`if (!body.reply_text && body.salon_response) body.reply_text = body.salon_response;`) added to bridge that mismatch, then upserts into `review_replies` keyed on `review_id`.
4. **Flagging.** `POST /api/reviews/[id]/flag` lets the salon owner (only) mark a review as needing admin attention: sets `is_flagged=true`, `flag_reason`, and `moderation_status='under_review'` on the `reviews` row.
5. **Admin review queue.** `GET /api/admin/reviews?flagged=true` (admin role only) lists reviews, optionally filtered to flagged ones. `PATCH /api/admin/reviews/[id]` lets an admin set `moderation_status` (`active`/`removed`/etc, which also flips `is_hidden`), attach a `removal_reason`, or write an `admin_response`. `DELETE` hard-deletes a review row.
6. **Salon lifecycle.** Each action is its own route under `app/api/admin/salons/[id]/`: `approve` (PATCH) sets `is_active=true` + `approved_at`/`approved_by`, clears any rejection reason, emails the owner, and logs `salon.approve` to `audit_log` via `logAuditEvent()` (`lib/audit.ts`). `reject` (PATCH) sets `is_active=false` + `rejection_reason`, notifies the owner, logs `salon.reject`. `freeze` (POST) sets `frozen_at`/`frozen_reason`, then walks every `pending_approval`/`confirmed` booking for that salon, cancels it, refunds the remaining paid balance through the single refund chokepoint (`lib/bookings/issue-refund.ts`), frees the booked slot, writes an `account_actions` row (`action_type: 'suspension'`), and logs `salon.freeze`. `warn` (POST) increments `salons.warning_count`; hitting 3 auto-freezes the salon (reuses the same `frozen_at`/`frozen_reason` fields) and also writes an `account_actions` row + `salon.warn` audit entry.
7. **Booking-level penalties (separate from the salon lifecycle above).** `lib/strikes.ts`'s `evaluateBookingPenalties()` is called from `app/api/bookings/[id]/route.ts` when a booking is cancelled or marked no-show. It counts a salon's cancellations in the last 30 days (via `audit_log` entries it writes itself) and issues an `account_warnings` row at 3+ (ToS §3.3 "strike"); it counts a customer's no-shows in 6 months and issues an `account_warnings` row at exactly 3 (`warning`) and again at 5+ (`suspension`).
8. **Badges, segments, disputes.** `app/api/admin/badges/*` manages `salon_badges` (definitions) and `salon_badge_assignments` (who has one); `POST /api/admin/badges/auto-assign` can be called by cron (`x-cron-secret`) or an admin and auto-grants system badges whose `auto_rule` (e.g. `rating_and_reviews`) matches. `app/api/admin/segments/*` groups customers into `customer_segments` with pre-computed `customer_segment_members`. `app/api/admin/booking-disputes/*` is the admin side of the refund-dispute engine (`lib/bookings/dispute-engine.ts`, out of this section's direct scope but wired in via `writeCaseEvent`): admin actions are gated by a compare-and-swap on `booking_disputes.status` so two admins (or a retry) can't double-process the same case, and refunds run through the same `issueRefund()` chokepoint as the salon-freeze flow.
9. **Content moderation for non-review content.** `lib/content-flags.ts`'s `checkContentFlags()`/`checkCommentFlags()` is the equivalent auto-filter for Discovery posts/comments (used by `app/api/discovery/post/route.ts`, `app/api/discovery/comments/route.ts`, `app/api/nail-discovery/publish/route.ts`), separate word-lists (DE/EN/FR) from `automod.ts`'s reviews list, plus spam heuristics (repeated characters, too many URLs) and an image-too-small / missing-gender / daily-rate-exceeded check. `app/api/admin/discovery/moderation/route.ts` (GET/PUT) is the admin queue for items this flags (`discovery_items.status = 'flagged'`), approve sets `status='published'`, reject sets `status='archived'`. Note: `lib/discovery-moderation.ts` named in this system's original scope does not exist in the repo; the logic actually lives in `lib/content-flags.ts` + the route above.
10. **Audit log.** `lib/audit.ts`'s `logAuditEvent()` is the single writer to `audit_log`: actor, action string, target type/id, arbitrary metadata, caller IP. Non-uuid actor ids (e.g. `"system"`, `"guest"` used by cron/anonymous flows) are coerced to `null` rather than breaking the insert. A failed audit write never blocks the calling operation, but it does call `alertAdmin()` so a broken audit trail itself gets surfaced.

### Database, Infra & Security Posture

**In one line (plain):** This is the vault and the lock system underneath Solen: the Postgres database that holds every table (146 of them), the rules that decide who is allowed to read or write each row, and the safety nets (rate limits, input checks, security headers) that keep the app from being abused.

**What it does:** Supabase Postgres stores everything (salons, bookings, users, payments, reviews...) and every table has Row Level Security (RLS) turned on, meaning the database itself, not just the app code, decides whether a given request is allowed to see or touch a row. Two different ways of talking to the database exist: a normal "session" client that respects RLS (used for anything a logged-in customer or salon owner does), and a privileged "admin" client that bypasses RLS entirely (used only inside trusted server code, e.g. crons, webhooks, and a handful of writes that must succeed regardless of who's asking). Around the database sits a layer of infra plumbing: environment-variable validation, rate limiting, input validation (zod schemas), a security-header policy (CSP), and Netlify/GitHub Actions automation that deploys the app and runs nightly jobs.

**How it works (the flow):**
1. **Schema and migrations.** The database's shape lives in `supabase/migrations/**` (273 files as of this audit). Each migration is a one-way, additive SQL file; nothing is ever edited in place once it has shipped (enforced by a hook, see Gotchas). Applying a migration to the LIVE database goes through the Supabase MCP's `apply_migration` tool, which is gated by `~/.claude/hooks/mcp-prod-write-guard.py` (a PreToolUse hook that blocks genuinely catastrophic SQL like `DROP TABLE`, `TRUNCATE`, disabling RLS, or granting privileges to `anon`/`public`, but lets routine and REVOKE-only statements through).
2. **Who can touch what (RLS).** Every one of the 146 public tables has RLS enabled (live-verified 2026-07-12, see `_inventory/STATUS.md`). A policy on each table says, in SQL, exactly which rows a given `auth.uid()` may SELECT/INSERT/UPDATE/DELETE. The session client (`createServerSupabaseClient()` in `lib/supabase.ts`) always goes through these policies. The admin client (`createAdminSupabaseClient()`, same file) uses the service-role key and skips RLS completely, so every route that uses it is personally responsible for re-implementing the ownership check RLS would otherwise do (this is the single biggest recurring bug class in both audit rounds, see Gotchas #2).
3. **Identity.** Every server route that needs to know "who is asking" must call `getUser()` (verifies the session cookie's JWT against Supabase's own auth server) never the old `getSession()` (trusts the cookie's claims blindly, forgeable). This is enforced by a live PreToolUse gate, `.claude/hooks/no-getsession-authz-gate.py`, that blocks new `auth.getSession()` calls in `app/**`/`lib/**`. Full checklist: `_rules/SECURITY_RULES.md` Rule S1 (feature-flag check -> `getUser()` auth -> ban check -> rate limit -> zod validation -> business logic, in that exact order for every new route).
4. **Abuse control.** `lib/ratelimit.ts` wraps Upstash Redis. A named set of "abuse-prone" limiters (auth, payment, booking, guest-lookup, referral, resend-access, walk-in-anon-join) fail CLOSED (return 429) both when Redis is unconfigured in production AND when a live Redis call itself errors mid-request (this second case was a real gap found and fixed in Round 2, see Health section). Every other limiter fails open so a Redis blip never takes down the product.
5. **Input shape.** `lib/validations.ts` (1338 lines) is the single place every API route's zod schema lives; routes call `validateBody(schema, body)` before touching the database.
6. **Config safety.** `lib/env.ts` is the one place every `process.env.*` read is supposed to go through: required vars throw at first access (a boot-time failure, not a silent runtime one), optional vars are explicit, and format is validated (e.g. Stripe keys must start with `sk_live_`/`sk_test_`). One known drift: `lib/stripe.ts:8` reads the Stripe secret key directly instead of through this schema (Round 1 finding, still open, low effort).
7. **Edge/network hardening.** `next.config.mjs` sets a Content-Security-Policy header on every response (shipped 2026-07-12, see Health) plus Netlify (`netlify.toml`) layers on `X-Content-Type-Options`, `X-Frame-Options`, `Strict-Transport-Security`, and `no-store` caching on `/api/*`.
8. **Automation.** GitHub Actions (`.github/workflows/`) runs `quality.yml` (tsc, lint, vitest, each ratcheted against a known baseline of pre-existing errors, on every push/PR), `invariants.yml` (repo-only structural checks), `inventory-freshness.yml` (checks the DB snapshot isn't stale, though this check itself was found to only look at the calendar date not real content drift, an open Round 1 finding), `db-migrate.yml`, and `cron-jobs.yml` (the nightly/periodic jobs, since Vercel cron was migrated off in favor of GitHub Actions on 2026-05-06).
9. **What Claude/future sessions read for DB shape.** `_inventory/_db-snapshot.json` (a JSON dump of the live table list, currently dated `2026-07-06`, 145 tables recorded there, one table behind the live-verified 146; treat migration files as the append log and the snapshot as a sometimes-stale cache, never the other way round) and `lib/database.types.ts` (the generated TypeScript types, currently 190 top-level table/view entries). `_inventory/STATUS.md` is the hand-kept "what's actually true right now" layer on top of both, and it was itself caught being wrong once this audit cycle (see Health).

**Gotchas / traps:**
- **The admin client bypasses RLS and does NOT check ownership for you.** Every route using `createAdminSupabaseClient()` must manually verify the customer/resource actually belongs to the caller's salon (the `clientBelongsToSalon` helper pattern). Skipping this was a real HIGH finding (Round 1 #3: `client-notes` and `nail-preferences` routes let any salon owner attach a note or fake medical record to a stranger's account). Documented as mistake #2 in `_rules/BACKEND_DOS_AND_DONTS.md`.
- **Session-client writes to owner-only tables silently do nothing, not error.** `availability_slots` UPDATE is owner-only under RLS; a customer's session client matches 0 rows and PostgREST returns success with an empty result. This shipped more than once (reschedule, express-rebook, abandon-sweep cron). Fix pattern: `claimSlot()` in `lib/bookings/claim-slot.ts`, an atomic compare-and-swap via the admin client. Full writeup: `_rules/BACKEND_DOS_AND_DONTS.md` #1.
- **Migrations are append-only.** Never edit a committed `supabase/migrations/*.sql` file, write a new dated migration instead. The deep-audit fix fleet violated this twice in Round 1 (editing already-applied migrations in place, which silently never reaches the live DB); the `no-edit-applied-migration.py` gate now blocks it, though wiring it into `.claude/settings.json` is still owner-side (the sandbox write-protects that file).
- **Live DB, not migration files, is the source of truth for current shape.** `_inventory/STATUS.md` says this explicitly: "Live DB is not equal to migration files (schema drift). Trust `_db-snapshot.json` for the backend, not `supabase/migrations/`." But the snapshot itself can go stale (see Health).
- **Live-only RLS policies exist that no migration file created.** The C1 `availability_slots` leak (see below) is a policy that exists only on the live database with no corresponding migration in the repo; Round 1's tree-only read never saw it because it isn't text anyone committed. This means a pure code/migration read is not sufficient to know the real security posture, live probing (`execute_sql`/`get_advisors`) is required periodically.
- **REVOKE is not catastrophic, but the guard used to treat it as such.** The prod-write guard's regex matched the literal word `TRUNCATE` even inside a harmless `REVOKE ... TRUNCATE ...` privilege-removal statement, false-positive-blocking the exact migration meant to fix the C2 critical. Fixed 2026-07-12 (commit `691c2bf0f`): any statement starting with `REVOKE` is now skipped by the catastrophic check; self-tested 10/10 (real `DROP`/`TRUNCATE`/`GRANT ... TO anon`/unscoped `DELETE` still block).
- **The inventory-freshness CI check only looks at the calendar date, not real content drift**, so it can report "fresh" even when the snapshot is demonstrably stale (Round 1 finding, `scripts/inventory.mjs:147`, still open).

## How to use this doc

When you're adding or changing anything backend, find your system in the table of contents above first and read its section before writing code. When a system changes (a bug gets fixed, a new route lands, a migration applies), come back and update that system's section in the same turn, don't let this doc drift into a snapshot of a past state. The `backend-systems-pointer` hook nudges you to this file on backend edits, treat that nudge as a reminder to both read AND write, not just read.
