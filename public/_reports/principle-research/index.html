Principle research, run 1

Taking the rules we already wrote and grading each one against evidence from outside this building.

2026-07-29 Measured against the live production database and the main working tree. Detail in _plans/PRINCIPLE_RESEARCH.md, commits 1571c72b2 and 6e21f3341.

Most of our engineering law was written from reasoning, not from evidence. This run tested the non-design half. Four rules survived, four need changing, and looking at the live database found two security holes that no rule would have caught, because no rule covers the place they live.

First, the brief I was given was partly wrong

The handoff told me to read RESEARCH_METHOD.md before starting. It is not on main. It sits on branch claude/principles-security-audit-0ae738 with 38 other commits and 660 changed files, none of which have ever merged. That is the second time in three days a file our law cites by name turned out to live on a branch nobody merged.

The same branch holds the migration for yesterday's security fix. The fix itself is live, I checked the database directly and availability_slots_public carries security_invoker=true in production. So nothing is exposed. What is missing is the file that records why, which means rebuilding the database from migrations would quietly reopen the hole.

The two live findings

LIVE, anon-readable

A second view leaks past row-level security, the same way the first one did

Yesterday's fix closed one view. I swept all six. staff_ratings_view still runs as its owner, so it ignores the rule on staff_members that says the public may only see active staff.

Proven rather than assumed: the view hands out 70 rows. There are 70 staff members, of whom 67 are active. So 3 inactive staff are visible to anyone with the public key who could not read them directly. Small, and it only exposes an id and an average rating, but it is the identical defect, and Supabase's own security advisor does not flag it, so the linter is not covering us here either.

LIVE, unauthenticated write

Our security rule assumes the API route is the only door. It is not.

Rule S1 lists five layers every API route must carry: feature flag, auth, ban check, rate limit, validation. All of that guards /api/*. But we also expose the database directly through PostgREST with the public key, and create_group_booking is a write function that anyone can call at /rest/v1/rpc/create_group_booking without signing in. The app reaches it through a properly guarded route. An attacker does not have to.

Two more read functions sit in the same position: search_salons_ranked and search_suggest.

Verdicts

KEEP

Never trust getSession() for a server-side identity decision

Right, and actually followed. I opened every one of the 11 remaining getSession calls against 361 getUser calls, and all 11 sit in browser components where it is legitimate. Zero server-side authorization decisions.

One staleness note: Supabase's current Next.js docs refresh the token with getClaims, not getUser. We are running supabase-js 2.110.2 and ssr 0.12.0, both of which have it. Not a vulnerability, just a network round trip per request we no longer need to pay.

REVISE

"RLS is non-negotiable" says nothing about views, which is exactly where both holes were

PostgreSQL's own documentation, quoted directly:

"If any of the underlying base relations has row-level security enabled, then by default, the row-level security policies of the view owner are applied ... However, if the view has security_invoker set to true, then the policies and permissions of the invoking user are used instead."

So a view is invisible to row-level security by default. Every bullet in our rule can be satisfied while a view over the same table hands out everything. The rule needs a views clause.

GAP

Breached-password checking is switched off, and this is the rare case where two standards agree

NIST SP 800-63B section 3.1.1.2: verifiers "SHALL compare the prospective secret against a blocklist that contains known commonly used, expected, or compromised passwords."

OWASP ASVS 5.0, requirement 6.2.12: "Verify that passwords submitted during account registration or password changes are checked against a set of breached passwords."

Supabase reports it disabled on our project. When two independent standards converge, our own method file says that is the strongest evidence available. Cost to close: one toggle, no code. It is a production auth setting, so it is yours to flip.

REVISE

"Money is stored as integer minor units, never float"

The float ban holds perfectly. I swept all 78 money-shaped columns and there is not one double precision anywhere. Nobody should "fix" that.

But bookings runs two unit conventions side by side, and the one our principle prescribes is the one almost nothing uses:

I could not find a live error, and I looked. On all 9 rows where both are set, paid_amount is exactly price_paid times 100. Zero rows carry final_price, so that pair cannot be tested at all. The code that reads them is correct and even says so in a comment: "Fee base in Rappen: paid_amount (Rappen) ?? toRappen(price_paid CHF). NEVER mix units."

The problem is that this comment is the only place the convention is written. No rule file, no database constraint, no gate. A 100x money error is one autocomplete away, on a product that has not taken a real payment yet.

KEEP, SHARPEN

"Prove behaviour, not existence", and the handoff's prediction was wrong

I was told to expect a negative result, that nobody else has a name for this. Half wrong. Mutation testing is the external cousin and it uses our vocabulary almost word for word: an assertion-free test is a control that runs without validating anything, a surviving mutant is a fault the suite failed to notice.

What does not transfer is the tooling, because those tools grade a test suite and we are grading runtime behaviour. What transfers is the move: perturb the input, demand the output change. That is exactly what "booked went 833 to 0 while available stayed at 1281" was, and what "the view emits 70 where the rule allows 67" is above.

REVISE

The motion gate is not "proven", and I was told not to check

The handoff said the enforcement is already proven, so do not re-test it. Our own method says a finding is a lead and not a fact, so I ran it. Same commit, minutes apart, browser launching cleanly both times: one run said FAILED with about 34 findings, two said PASSED with zero.

The findings it does produce flag a Mapbox canvas, a bare script tag, a Next.js streaming placeholder and plain layout divs, each as "mutated past the 5000ms budget". It is watching page hydration and map tiles, not animation. It also skips a route on timeout and does not count that as a failure.

Keep the gate, it does real work. Drop the word proven. A gate that disagrees with itself is the kind that ends up permanently skip-flagged.

KEEP

Motion durations, now with the citation they should have had

WCAG 2.2.2 fires at five seconds. Our slowest documented transition is 520ms and the shipped one is 280ms, so it binds none of them. What it does bind is infinite loops, and main carries 76 of those (44 animate-spin, 32 animate-pulse).

check-motion.mjs already knows this. Its code comment reads "the WCAG 2.2.2 criterion itself, not a tuning knob". But MOTION.md justifies the same rule on taste. Taste sits three precedence tiers below a legal floor, and only one of the two survives being overruled, so the justification should move.

OWNER DECISION

Password minimum: 8 or 15

We require 8. ASVS 5.0, 6.2.1 says at least 8, with 15 strongly recommended, so we pass. NIST 800-63B says SHALL be at least 15 without multi-factor, so we fail. Two standards, genuinely divergent, which makes it a decision rather than a fact. NIST is US federal and not law in Switzerland, so this is a quality bar and not a statutory floor.

My lean: stay at 8 and turn the breach check on instead. Raising the floor to 15 before launch costs signup completion, and the breach check removes far more real risk per unit of friction than length does.

KEEP, SHARPEN

The psychology laws hold, and this is the best-built file we own

PSYCHOLOGY.md already tiers every claim and already keeps a myth table. That is exactly the discipline the rest of the corpus is missing, and it is why this file needed the least work.

I re-sourced its two load-bearing numbers against the original papers instead of repeating them. Defaults, d = 0.68 is right: Jachimowicz, Duncan, Weber and Johnson 2019, 58 studies, 73,675 people, confidence interval 0.53 to 0.83. Choice overload is near zero is right: Scheibehenne, Greifeneder and Todd 2010, 63 conditions, 5,036 people. One caveat I am not glossing over: those sources say "virtually zero", and I never saw the specific 0.02 our file prints. Source the decimal or write "essentially zero".

Two rows added to the myth table, both debunked by the design pass: the "white space increases perceived value by up to 300%" claim, and the "5 to 10% of a page should be bold" rule. A debunk that lives only in a design document gets re-cited by a backend session.

DROP

A rule file tells new work to write code that a gate blocks

STRUCTURAL_RULES.md Rule 46 B is titled "Dark Mode Support" and tells you to write dark:text-s-dm-text and dark:bg-s-dm-surface. Web is one light theme, you rejected dark mode twice, and there is a gate that refuses it. A session obeying this rule writes code it cannot commit.

The scare I did not bank. Twelve dark: occurrences looked like a live leak, because Tailwind's own docs say an unset darkMode key still fires on the visitor's operating-system setting. So I checked each one. Eight sit in four components that nothing imports. Two are JavaScript object keys, not Tailwind variants at all. One is a prompt string. Zero render. The white-only law is holding in the code. Only the rule file is wrong.

Found by accident on the way: those four never-imported components are themselves a dead-code violation of our own Rule 26.

REVISE

Three more rules that are half fiction

"BANNED: text-black, raw bg-white." Half perfect, half nonsense. text-black appears 0 times. bg-white appears 905 times, and white is roughly 80 percent of the palette by design. A ban broken 905 times is not a ban.

"The design system is in flux, do not cite the locked palette as authoritative." This inverts three precedence tiers. The LOCKFILE outranks _rules/ by a wide margin and the whole taste apparatus depends on it being authoritative. Drop it.

Six files still point at _tasks/SOLEN_DESIGN.md as the current design source, weeks after CODE_SAFETY.md tombstoned it in its own header. The tombstone was written once and never propagated. Same wrong-tier failure the 2026-07-27 pass named.

"Return both keys for backwards compatibility." The incident behind it was real. The fix is not: duplicated response keys have no removal path, so they accumulate forever. Our own backend research already covers the right answer under API versioning.
