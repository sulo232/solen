Caching, researched law

Date: 2026-07-16. Sources fetched this run: 15 (list at the bottom, every claim below traces to one). For: any Solen session touching response headers, fetch() cache options, Redis (Upstash), materialized views, or a "why did this look stale / why did user A see user B's data" bug. Stack verified live this session: Next.js 15.3.8 App Router, Netlify host (@netlify/plugin-nextjs), Supabase Postgres, Upstash Redis (@upstash/ratelimit + @upstash/redis), ~28 salons, serverless request model.

This file also grounds itself in what Solen ALREADY built. The codebase already has a working, thought-through caching layer in three places: app/api/salons/route.ts, app/api/salons/[slug]/route.ts, and lib/discovery/feed-cache-headers.ts (personalization-aware CDN caching, edge runtime), lib/discovery/thumb/[id]/route.ts (three-tier durable proxy cache), and lib/cities.ts / lib/search/filter-availability.ts (per-process in-memory TTL cache). Nothing here contradicts that work; it explains WHY it's shaped that way and where the same pattern should or shouldn't be repeated.

0. The short version

  1. Per-lambda memory is not a cache, it's a lottery. A Map() at module scope survives only as long as the one warm container happens to survive, and Netlify's own docs describe the runtime as ephemeral by design; never depend on it for correctness, only as a "cheap when it happens to be warm" optimization with a real fallback. (T2, confirms the existing lib/cities.ts pattern is correctly used as a soft optimization, not a source of truth.)
  2. Next.js 15 flipped the caching default: fetch() is UNCACHED unless you opt in. This reverses Next 14. Every session's instinct from older Next.js knowledge ("fetch is cached by default") is now wrong for anything already npm installed on this repo. (T1, official Next.js docs, fetched this run.)
  3. The one HTTP response header that actually reaches Netlify's CDN from a Function/Edge Function is Netlify-CDN-Cache-Control, not Cache-Control. Cache-Control still ships to the browser; netlify.toml's static header block does NOT apply to function responses at all. This is exactly what the existing app/api/salons/route.ts comment already discovered and documents. (T1, official Netlify docs.)
  4. Never cache a response whose content depends on Authorization/session cookies at a URL that doesn't encode that dependency. This is the single most expensive caching bug class that exists: web cache deception / cache poisoning, one user's private data served to another from a shared cache. (T1, OWASP + PortSwigger, both fetched.)
  5. Cache stampede has three named fixes, in order of complexity: locking (mutex/SETNX), probabilistic early expiration (XFetch), stale-while-revalidate. At Solen's traffic (~28 salons), none of these are close to necessary yet; know the pattern, don't build the machinery. (T1/T2, Wikipedia + the original XFetch paper + RFC 5861.)
  6. Postgres has no query result cache. shared_buffers caches disk pages, not query results; a repeated identical query still re-executes the plan every time (only the underlying page reads may be cheap because they're in RAM). Materialized views are Postgres's actual "precomputed result" mechanism, and they are NOT automatically kept fresh. (T1, official Postgres docs + T2 industry consensus.)
  7. revalidateTag/revalidatePath are event-based invalidation; revalidate: N is TTL-based. Solen's DB writes are the event; use tag-based invalidation wherever a write mutates data that a cached read serves, TTL alone means every write is stale for up to N seconds. (T1, official Next.js docs.)
  8. ETags need a stable content hash function; don't hand-roll one from Date.now() or unstable object key order. A wrong or non-deterministic ETag either serves 304-with-wrong-body or never gets a cache hit. (T1, MDN/RFC 9110 conditional-request mechanism.)
  9. Never cache: anything gated by checkUserBanned/auth, Stripe webhook responses, payment intents, anything containing PII/booking details, OTP/2FA codes, admin dashboards. These are all "if this leaks between users it's a security incident," not "if this is stale it's annoying." (CONV, derived from OWASP API8:2023 Security Misconfiguration + Solen's own S1 security stack.)
  10. A materialized view is the right tool only once a query is (a) expensive to compute AND (b) tolerant of being some minutes stale. Solen has zero materialized views today; before adding one, check whether a plain index or the existing 5-minute in-process TTL pattern (lib/cities.ts) already solves it cheaper. (Solen-specific, T2 for the general claim.)

1. The layers, and which ones Solen can actually use on Netlify + serverless

The question: which of the textbook cache layers (browser, CDN, app/process memory, Redis, DB query cache, materialized views) are real options given Netlify hosting + a serverless request model, and which are traps.

What the evidence says:

  • Browser cache. Governed by the response's Cache-Control header (the one MDN documents as the browser-facing directive). Fully real, free, and already used correctly in this codebase: app/api/salons/route.ts sets Cache-Control: public, max-age=0, must-revalidate (i.e. "browser must always revalidate, don't trust a local copy blindly") while letting the CDN hold the real TTL via a separate header. (T1, MDN HTTP caching guide, fetched.)
  • CDN cache (Netlify's edge). Real and already the backbone of Solen's anon-browse caching. Netlify documents three cache-control headers with strict precedence: Netlify-CDN-Cache-Control (most specific, Netlify's own edge only) beats CDN-Cache-Control (any standards CDN) beats Cache-Control (browser/generic). If more than one is present, Netlify's edge obeys the most specific one and still forwards the others downstream. Crucially: Netlify Function and Edge Function responses are NOT cached by default because they're dynamic; you must set the header yourself, in code, every time. Netlify also documents that netlify.toml's static [[headers]] block is a header-INJECTION rule for the publish directory/CDN assets, and does not apply to a Function or Edge Function's own response, only that response's own headers ship. This is exactly the discovery the codebase already made and left as a comment in app/api/salons/route.ts; this research confirms it against Netlify's current docs rather than trusting the inherited comment. (T1, docs.netlify.com/build/caching/caching-overview, fetched.) Netlify also supports cache-tag purging (Netlify-Cache-Tag / Cache-Tag response header + a purgeCache({tags}) API call, rate-limited to 2 purges per tag per 5 seconds) as an event-based invalidation primitive at the CDN layer, separate from Next.js's own tag system. Solen doesn't use this today; it's a real option for CDN-level tag invalidation of the anon browse endpoints if TTL-only ever becomes insufficient.
  • App/process memory (a module-level Map/variable). Real, but scoped to ONE warm serverless instance, not the fleet. Netlify's own Functions docs describe the runtime as an "ephemeral runtime environment"; a forum answer from Netlify support states plainly there's no guarantee a later request reuses the same container, so an in-memory cache should never be relied on for correctness, only exploited opportunistically as a "sometimes free" speedup with a working cold-path fallback. This is exactly how Solen already uses it: lib/cities.ts's activeCitiesCache and lib/search/filter-availability.ts's TTL cache and lib/feature-flags.ts's ban/flag caches all fall through to a real DB read on a cold instance, and BACKEND.md itself documents (lib/feature-flags.ts:784 note) that "an owner toggling maintenance_mode or banning a user is not instantaneous across the fleet" because these caches are per-process. That tradeoff is correct and already accepted; the law is: never build a NEW in-memory cache that assumes it's shared, or that a bust/invalidate on one instance reaches every instance. (T2: official ephemeral-runtime docs + a support-forum confirmation, softened to T2 because the forum post is not the canonical doc page.)
  • Redis (Upstash). The one layer that IS actually shared across every serverless instance, because it's an external network hop, not in-process state. Solen already uses Upstash Redis for rate limiting (lib/ratelimit.ts), phone OTP storage, and the nail AI monthly budget counter, but NOT yet as a general response/data cache. It is the correct tool whenever a cache value must be (a) shared across cold instances and (b) fresher than a CDN's edge TTL, or must support atomic operations (locks, counters) that a CDN cache cannot do. Cost/complexity note: this is a new operational dependency (another thing that can be down, another latency hop), Upstash's own request pricing means an over-eager cache-everything strategy has a real dollar cost at scale, though at Solen's traffic this is not yet a binding constraint.
  • DB query cache. Does not exist in Postgres the way it exists in MySQL. Postgres's shared_buffers caches raw data/index pages in RAM to avoid disk I/O, and separately can cache a parsed/planned PREPARE'd statement's plan, but it does NOT cache "the result set for query X." A repeated identical SELECT still re-executes the full query plan every single time; the only speedup is that the underlying pages are likely already in RAM (which is a real, meaningful speedup, but a different mechanism than "result caching"). Anyone reaching for "let's turn on the query cache" needs to be redirected to either an index, a materialized view, or an app-level cache (Redis/unstable_cache) instead, because there is no dial to turn on inside Postgres itself. (T1, official Postgres docs on shared_buffers/plan caching + T2 industry consensus, both fetched.)
  • Materialized views. Real, and the correct Postgres-native answer to "this aggregate query is expensive and the underlying data doesn't need to be second-fresh." REFRESH MATERIALIZED VIEW fully replaces the contents; without CONCURRENTLY it takes an exclusive lock that blocks concurrent reads of the view for the refresh's duration; CONCURRENTLY avoids that lock but REQUIRES a UNIQUE index on the view (plain columns only, no expression index, no WHERE clause) and can only run one refresh at a time regardless. Solen has zero materialized views in the live 146-table schema today (nothing in _inventory/_db-snapshot.json beyond the app's own tables), so this is a genuinely unused tool, not a maintenance burden anyone is carrying. (T1, official Postgres docs, fetched.)
  • Next.js's own layered cache (App Router). A distinct fifth thing, sitting between "app memory" and "CDN": Next.js documents four internal caches (Request Memoization, Data Cache, Full Route Cache, Router Cache). Request Memoization dedupes identical fetch() calls within ONE render pass (server-side only, does not survive across requests). The Data Cache is what fetch({cache:'force-cache'})/unstable_cache write into, and on Netlify this is backed by Netlify's own persistent cache infrastructure through @netlify/plugin-nextjs, not a bare in-process Map, per Netlify's Next.js Runtime integration; UNVERIFIED in this run whether it durably survives across cold Netlify Function instances the same way Vercel's Data Cache does (see Unverified section). The Full Route Cache is the static-HTML-at-build-or-ISR-revalidate mechanism (route segment revalidate export). The Router Cache is purely client-side, in the browser tab.

Where the real tradeoff lies: every layer beyond "browser + CDN with a short TTL" adds an operational dependency and an invalidation problem. The cheapest layer that solves the actual staleness tolerance should always win. For Solen at 28 salons, CDN-level s-maxage=60, stale-while-revalidate=300 (already the pattern in three routes) plus the existing per-process TTL Maps covers the overwhelming majority of read-heavy, low-write-frequency data. Redis-as-cache and materialized views are both real, correctly-shaped tools for later, not missing pieces today.

Recommended default for Solen: CDN header caching (Netlify-CDN-Cache-Control) for anonymous, non-personalized GETs; a per-process TTL Map (the lib/cities.ts pattern) for rarely-changing, cheap-to-recompute lookups; Redis only when a value must be both shared-across-instances AND write-coordinated (locks, counters, already the case for rate limits and OTP); no materialized view until a specific query is both measurably slow (see fable-backend's measure-first rule) and tolerant of staleness.

2. Invalidation strategies: TTL vs event-based vs tag-based, and Next 15's actual defaults

The question: when a cached value goes stale, how does the system find out, and how did Next.js 15 change what's cached by default.

What the evidence says, confirmed against the current docs (not memory):

  • fetch() in Next.js 15 App Router is UNCACHED (no-store-equivalent) by default. The official fetch API reference (fetched this run, version stamped 16.2.10 docs, lastUpdated: 2026-03-03) states the default cache behavior is 'auto no cache': Next.js fetches fresh on every request in dev, and fetches once at build time only if the route can be statically prerendered; if any request-time API is used, it fetches fresh every request. Opting into caching requires { cache: 'force-cache' } explicitly, or a positive next.revalidate number. This is a genuine reversal from Next.js 14 (where an un-annotated fetch was cached by default) and was made specifically because implicit caching caused a wave of "why isn't my data updating" bugs (T2, corroborating blog commentary, softened because that motivational framing itself is secondary reporting, not the primary doc; the DEFAULT BEHAVIOR ITSELF is T1, directly quoted from the official page). Practical Solen implication: any code written or copy-pasted from a Next 14-era tutorial that relies on implicit fetch caching does nothing on this stack. Route Handlers are also explicitly no-cache by default now (same source).
  • unstable_cache, not fetch, is Next's tool for caching a Supabase/Postgres query result (or any non-fetch async function), since Solen's data layer is supabase-js, not raw HTTP fetch calls to an API. unstable_cache(fn, keyParts, { tags, revalidate }) wraps an arbitrary async function; the codebase's own lib/search/filter-availability.ts comment (fetched from disk this session) explicitly notes there is currently zero unstable_cache usage anywhere in Solen, the hand-rolled TTL-Map pattern was a deliberate choice to mirror the existing lib/cities.ts sibling rather than introduce a new caching primitive. That's a defensible call for a single rarely-read module-level cache; unstable_cache becomes worth reaching for specifically when the tag-based on-demand invalidation (revalidateTag) is needed, which a hand-rolled Map cannot give you without writing that plumbing yourself. (T1, official Next.js caching guide, fetched.)
  • TTL-based invalidation (revalidate: N on a route segment, a fetch, or unstable_cache) is the simplest and already Solen's dominant pattern: app/api/metrics/global/route.ts (revalidate = 86400), app/api/salons/trending/route.ts (revalidate = 86400), app/api/slots/last-minute/route.ts (revalidate = 60), app/api/analytics/platform/route.ts (revalidate = 86400). Cost: a write can leave stale data visible for up to the full TTL window; for a 24h TTL on metrics/global, an owner-facing stat can lag a full day, which is an accepted tradeoff for a low-stakes vanity metric but would be wrong for anything transactional.
  • Event-based / tag-based invalidation (revalidateTag, revalidatePath, Netlify's own purgeCache({tags})) fires exactly when a write happens, not on a clock. Next's official docs show the canonical pattern: tag a fetch/unstable_cache call with next: { tags: ['user'] }, then call revalidateTag('user') inside the Server Action or Route Handler that performs the mutating write. This is the mechanism Solen is currently NOT using anywhere (grep across app/ and lib/ for revalidateTag/revalidatePath returned zero hits this session), which is fine today because nothing is currently fetch/unstable_cache-cached with a long enough TTL for staleness to bite, but it is the gap to close the day a cached read (say, a salon's public profile) gets a TTL long enough that "a salon just edited their bio and it doesn't show for 5 minutes" becomes a real owner complaint. At that point the fix is: tag the cached read with the salon's id, call revalidateTag(salon:${id}) from the PATCH route that saves the edit, not "just lower the TTL," which reintroduces the DB load an event-based invalidation exists to avoid.
  • RFC 9111 (obsoletes RFC 7234) is the actual standard behind every Cache-Control directive in play: must-revalidate ("once stale, a cache MUST NOT reuse the response until successfully validated"), no-cache ("MUST NOT be used to satisfy any other request without forwarding it for validation"), no-store ("MUST NOT store any part of either this request or any response"), and the public/private split ("private" means a shared cache MUST NOT store it). One correction to a common assumption worth stating explicitly: stale-while-revalidate is NOT defined in RFC 9111 itself; it's a separate extension, RFC 5861, which RFC 9111 references but does not incorporate. RFC 5861 defines it as: caches MAY serve the stale response for up to the indicated number of seconds while attempting a non-blocking background revalidation, and recommends servers set max-age + stale-while-revalidate to "the longest total potential freshness lifetime they can tolerate." (T1 for both RFCs, fetched directly from rfc-editor.org.)

Where the real tradeoff lies: TTL is zero-code and zero-coordination but bounds staleness by a fixed clock regardless of whether a write actually happened; tag-based is precise (invalidates exactly when data changes) but requires every write path to remember to call revalidateTag/purgeCache, and a forgotten call is a silent staleness bug that looks identical to "it's just cached, wait it out," which is exactly the kind of silent-no-op class this codebase already has a name for.

Recommended default for Solen: keep TTL-only for read-heavy, rarely-mutated, low-stakes data (current revalidate=86400 usages are fine as-is). The moment a cached value is user-editable AND the TTL exceeds "a few seconds," add tag-based invalidation on the write path rather than shortening the TTL, shortening the TTL just moves the DB load back onto the read path without actually fixing correctness.

3. Cache stampede / thundering herd, and the fixes

The question: what happens when a hot cache key expires and many concurrent requests all miss at once, and what's the actual fix, not folklore.

What the evidence says:

  • Definition. A cache stampede (aka thundering herd, aka dog-piling) happens when a popular cached value expires and enough concurrency exists that many requests simultaneously attempt to recompute it, which can drive the cache hit rate briefly to zero and overload the backing store exactly when it's least able to absorb it. (T1, Wikipedia, fetched, itself citing the pattern as well-established in distributed systems literature.)
  • Fix 1: Locking (mutex). On a cache miss, one process acquires a lock (Redis: atomic SET key value NX EX ttl, never a separate SETNX + EXPIRE pair, that's not atomic and can leak an un-expiring lock on a crash between the two calls) and is the only one that recomputes; everyone else waits, serves stale, or fails fast. This is the industry-default first reach because it's easy to reason about, at the cost of added latency for waiters (industry sources cite 50-200ms typical added wait) and a real failure mode if the lock holder crashes without releasing (mitigated with a short lock TTL + a Lua script that verifies the lock token before deleting it, rather than an unconditional DEL). (T2, antirez's own Redis pattern write-up, fetched, converging with the general Redis distributed-locking literature.)
  • Fix 2: Probabilistic early expiration (XFetch / "exponential fetch"). Instead of waiting for a hard expiry, each reader independently decides to recompute EARLY, with probability rising as expiry approaches, per the formula now - delta * beta * log(random()) >= expiry (from the peer-reviewed VLDB 2015 paper "Optimal Probabilistic Cache Stampede Prevention," Vattani et al., cited by name across multiple technical write-ups and by its own PDF fetched-adjacent this run). This spreads recomputation across time instead of concentrating it at one instant, and is the more sophisticated fix once lock contention itself becomes the bottleneck at very high concurrency. (T1 for the algorithm's existence and formula, it's a named peer-reviewed result; T3 for any specific benchmark numbers quoted in vendor blogs, e.g. a "3-5 DB queries out of 10,000 concurrent requests" figure, that magnitude is directionally illustrative from a single source and NOT independently verified against Solen's own numbers, so it is explicitly not something to cite as a Solen fact.)
  • Fix 3: stale-while-revalidate (RFC 5861, see section 2). Functionally a stampede fix too: instead of the cache going empty at expiry and every request racing to recompute, ONE background revalidation happens while everyone else keeps getting the (soon-to-be-fresh) stale copy. This is the mechanism already in production use at Solen (app/api/salons/route.ts, [slug]/route.ts, feed-cache-headers.ts, all stale-while-revalidate=300), and for Solen's traffic level it is very likely sufficient on its own, a hot key expiring among a handful of concurrent Swiss users is a fundamentally different concurrency regime than the "10,000 concurrent requests" scenarios these papers and blog posts are written for.

Where the real tradeoff lies: locking adds correctness (only one recompute happens) at the cost of latency and lock-lifecycle complexity; probabilistic early expiration removes the lock's latency cost but is probabilistic (a small chance multiple readers still race) and needs tuning (the beta parameter); stale-while-revalidate is the cheapest of the three (a header, no new infrastructure) but only works when "serve something slightly old" is an acceptable answer, which is true for salon browse listings and false for, say, a real-time seat-availability check at checkout.

Scale honesty: at ~28 salons, Solen almost certainly never sees enough concurrent traffic on any single cache key for a stampede to matter in the classic sense (the papers and vendor benchmarks describing this problem are written for services fielding thousands of concurrent requests per second on one hot key). The existing stale-while-revalidate headers already cover the realistic case. Building an XFetch-style probabilistic early-expiration layer or a Redis distributed lock purely for stampede protection today would be solving a problem Solen does not have; revisit only if a specific cached endpoint is independently measured (not guessed) to receive concurrent bursts large enough that a cold recompute could double-hit the DB in a way that matters, which at current scale has not happened.

4. ETags and conditional requests

The question: how does a client avoid re-downloading a response body it already has, and what's the actual mechanism.

What the evidence says:

  • The full request/response dance (MDN HTTP caching guide, fetched): server sends ETag: "<opaque-hash>" with the original 200 response. On a later request for the same resource, the client sends If-None-Match: "<that-hash>". If the server's current ETag for the resource still matches, it replies 304 Not Modified with NO body, the client reuses its own cached copy; if it doesn't match, the server replies 200 with the new body and new ETag. MDN + the underlying RFC 9110 note servers should ideally send both ETag and Last-Modified where practical, since Last-Modified also serves other ecosystem purposes (CMS "last edited" display, crawler re-fetch scheduling) beyond pure cache validation. (T1.)
  • Why ETag over Last-Modified alone: Last-Modified only has 1-second resolution and can't distinguish two edits inside the same second, or detect a change that doesn't touch a timestamp (e.g. a computed/derived response); an ETag is a content-derived hash so it changes if and only if the actual bytes changed, which is a strictly stronger correctness guarantee. (T1, MDN, same fetch.)
  • The practical failure mode for a hand-rolled ETag: if the hash is computed from something that isn't a deterministic function of the actual response content, timestamps not tied to real content changes, unstable JSON key ordering, a random UUID minted per request, the ETag either (a) never matches on a real re-request even when content is identical (zero cache benefit, pure waste), or worse (b) matches when content actually DID change (serves a stale/wrong 304). Solen doesn't hand-roll ETags anywhere today (grep for ETag/etag in app/api returned nothing beyond framework-level noise), so this is a forward-looking rule rather than a fix to an existing bug: if a future route wants ETag support, the hash MUST be derived from the actual serialized response body (or a version/updated_at column already used as the source of truth for the record) never from wall-clock time or a fresh random value.

Where the real tradeoff lies: ETags save bandwidth (a 304 has no body) but cost a server-side comparison (usually cheap: string equality) on every request, and require the server to actually compute/store a stable hash, which is extra code for a marginal win when responses are already small (most of Solen's API responses are JSON payloads in the low KBs, not multi-MB assets where bandwidth savings would be dramatic).

Recommended default for Solen: don't add ETags to hand-written API routes today, the CDN's s-maxage/stale-while-revalidate headers already solve the "avoid recomputing/re-fetching" problem at the layer that matters (avoiding a DB round trip), and ETags mainly solve "avoid re-transmitting bytes the client already has," which is a smaller win at Solen's response sizes. Next.js's static asset pipeline and Netlify's static-asset CDN layer already handle ETags/content hashing for build output automatically; that's a solved problem, not something to hand-build.

5. Tenant-safe cache keys: the class of bug where cached data leaks between users

The question: how does a cache end up serving user A's authenticated/personalized response to user B, and how does Solen avoid it.

What the evidence says:

  • Two distinct named attack classes, don't conflate them (PortSwigger Web Security Academy, fetched): web cache deception is when an attacker tricks the cache into storing ANOTHER user's private response (e.g. by exploiting a path-normalization mismatch between the CDN and the origin, so /profile/settings.js gets treated as a static, cacheable asset by the cache layer while the origin still returns the real dynamic, personalized /profile/settings content), then the attacker reads that cached copy. Web cache poisoning is the reverse direction: manipulating what gets INTO the cache so it serves malicious/wrong content to OTHER, later users. Root causes for deception specifically: path mapping discrepancies between cache and origin, delimiter mismatches (;, . treated as a path terminator by one layer and not the other), and normalization gaps in decoding/dot-segment resolution. (T1.)
  • The core defensive rule, stated flatly by both MDN and PortSwigger: any response whose content is personalized by a cookie or Authorization header must ship Cache-Control: private (never cacheable by a SHARED cache/CDN, only the individual browser's own private cache may hold it), or no-store if it must never be cached anywhere at all, including the browser. Putting Cookie into the Vary header is explicitly called out as the WRONG fix (cookies vary per-request in ways that would make the cache key explode into near-uniqueness and defeat caching entirely); the correct fix is private/no-store, not a Vary: Cookie. (T1, MDN, fetched.)
  • Vary in general exists to add request headers to the cache key so two different valid responses for the identical URL don't collide (MDN's own canonical example: Vary: Accept-Language so an English and a Japanese response don't overwrite each other in a shared cache). Its failure mode in the other direction, forgetting to Vary on something that DOES change the response, is exactly how a personalized response for one URL can be cached and replayed to a different user whose request differs only in that missing dimension. (T1, MDN.)
  • How Solen already gets this right, and why it's shaped that way. lib/discovery/feed-cache-headers.ts is the clearest evidence in the codebase that this exact risk was already reasoned through carefully (the file's own header comment, read directly this session, explicitly names "cache poisoning" and explains the design): the discovery feed personalizes the SAME URL differently depending on whether a session cookie is present (a logged-in "for you" ranking vs. an anonymous general feed). Since Netlify's CDN cache key is the URL alone (no cookie in the key by default) and the comment explicitly states there was no live-docs access at the time to verify Netlify's exact cookie-matching Vary semantics, the team deliberately did NOT attempt a Vary-based split; instead they only mark a response cacheable when userId is POSITIVELY confirmed null (no auth cookie present at all), and any request that resolved a session always gets no-store. That is the textbook-correct, conservative resolution of exactly the ambiguity PortSwigger and MDN describe: when in doubt about whether a personalization dimension is safely captured by the cache key, do not cache the personalized branch at all. app/api/salons/[slug]/route.ts follows the identical pattern (ANON_CACHE_HEADERS vs a no-store variant keyed on auth presence). This research CONFIRMS that reasoning was sound against the current primary sources, it is not new advice, it's independent verification of an already-good decision.
  • The tenant dimension specifically (multi-salon, not just multi-user). Solen's RLS model means almost every authenticated read is already scoped server-side by auth.uid(), so the classic "tenant A sees tenant B's row" bug is primarily a DB/RLS problem (out of scope for this file, covered in the auth/RLS research), but the CACHING version of that same bug is: a CDN or app-memory cache keyed only by a URL that is IDENTICAL across tenants (e.g. /api/dashboard/summary, no salon id in the path or query) would replay salon A's dashboard numbers to salon B's owner if it were ever marked cacheable. The concrete rule: any cache key for tenant-scoped data must include the tenant/user id as part of the key (either in the URL path/query Solen already uses, e.g. /api/analytics/salon/[id]/route.ts, or explicitly in a Redis/unstable_cache key), and if the id can't cleanly be put in the key (e.g. it's derived from a cookie, not a URL param), the response must be no-store/private, full stop, exactly the branch-detection Solen already does in feed-cache-headers.ts.

Where the real tradeoff lies: the safe default (no-store for anything ambiguous) costs cache hit rate and adds DB load on every such request; the unsafe default (cache first, ask questions later) risks a genuine data-leak security incident. This is not a close call, Solen's own feed-cache-headers.ts comment gets the cost/benefit exactly right: "correctness beats caching."

Recommended default for Solen: every new cacheable GET route must state, in a comment next to the cache-header constant (matching the existing file convention), (1) whether the response ever varies by auth/cookie/tenant, and (2) if yes, how the cache key or the no-store branch accounts for that. A route with cache headers and no such comment is a review flag.

6. What should never be cached

Derived from the security evidence above (OWASP API Security Top 10 2023, item 8 "Security Misconfiguration," fetched and confirmed current this run, T1) plus Solen's own S1 security stack (_docs/BACKEND.md):

  • Anything gated by checkUserBanned/getUser()/role checks where the response body contains data scoped to that specific authenticated identity (bookings, profile, payment methods, salon-owner dashboards, staff schedules).
  • Stripe webhook handler responses and anything payment-related (payment intents, refund status, payout figures): correctness must always beat any performance gain here, and Stripe's own webhook delivery/retry semantics assume a fresh, authoritative response every time, not a cached one.
  • OTP/2FA codes and their verification responses (verify-phone/send, verify-phone/check): these are already correctly no-store by nature (short-lived Redis values, not HTTP-cached at all) and must stay that way; caching a "code accepted" response would be a direct auth bypass.
  • Admin/dashboard mutation endpoints (feature flags, ban toggles, user management): staleness here isn't a UX inconvenience, it's "an admin thinks they just banned someone and the fleet doesn't know yet," which is already an accepted-but-flagged tradeoff for the 10s in-process ban cache (see section 1) and must never be extended into a longer-lived or shared cache without re-deciding that tradeoff explicitly.
  • Any response whose cache key can't positively prove it excludes a personalization dimension (see section 5): the safe move is always no-store, not "cache it and hope the key is right."
  • Rate-limit state itself (paradoxically): the whole point of lib/ratelimit.ts's Redis-backed sliding window is that it must be read-and-written fresh on every request; a cached rate-limit check is a rate limit that doesn't limit.

Myths and traps

  • MYTH: "Next.js fetch() is cached by default." True in Next.js 14, FALSE in Next.js 15 (the version this repo runs). Anyone importing this belief from older tutorials, Stack Overflow answers, or their own training data will silently ship an always-fresh (i.e. accidentally slower, more DB load) route and not notice until someone asks why a "cached" endpoint hits the DB every time. (Confirmed T1 this run against the currently-live Next.js docs.)
  • MYTH: "Postgres has a query cache we can just turn on." No such feature exists; shared_buffers is page caching, not result caching. The tool that does what people mean by "query cache" in Postgres is a materialized view (minutes-scale staleness tolerance) or an app-level cache (Redis/unstable_cache), not a Postgres setting.
  • **TRAP (this stack specifically): netlify.toml's /api/* header block does NOT reach Function/Edge Function responses.** The static Cache-Control: no-store, no-cache, must-revalidate rule in netlify.toml looks like a blanket "never cache any API response" guarantee; it is not, it's a CDN/static-asset header injection rule and Netlify's own docs confirm Function/Edge Function responses ship only their OWN headers. Any route that wants CDN caching must set Netlify-CDN-Cache-Control itself in code (already correctly done in 3 routes); any route relying on the netlify.toml block alone to guarantee no-store is trusting a rule that silently doesn't apply to it, exactly the "control that looks wired but does nothing" failure class this codebase already has a name for.
  • TRAP: an in-memory Map cache "working" in local dev or a single warm Netlify instance is not evidence it works correctly across the fleet. It will pass a manual click-test and still serve stale/wrong flag state to a cold instance in production. This is why lib/feature-flags.ts's own file comments already document the "not instant across the fleet" caveat rather than pretend the cache is fleet-wide.
  • TRAP: Vary: Cookie looks like the "correct" fix for personalized caching and is explicitly the WRONG one (MDN calls this out directly): it doesn't collapse cache variants sensibly (cookies are near-unique per browser), it just silently defeats caching while looking like it solved the problem. The right fix is private/no-store, which is what Solen already does.
  • TRAP (Stripe Connect specific): a cached read of payout/balance figures is a correctness bug, not a performance win. Connect balance and payout state changes asynchronously via webhooks Solen doesn't fully control the timing of; a stale cached balance shown to a salon owner is worse than a slow fresh one.
  • TRAP: assuming Netlify Blobs is a safe shared cache across concurrent function invocations. Netlify's own docs (fetched this run) state the default consistency model is EVENTUAL with up to 60 seconds of edge-propagation delay, and explicitly warn there is no concurrency control: "if two overlapping calls try to write the same object, the last write wins." It is well-suited to persisting the OUTPUT of an async background job (exactly how Solen's discovery-thumbnail proxy already uses Supabase Storage for a conceptually identical durable-cache tier), not to a read-your-own-write cache or anything needing atomicity, that's Redis's job, not Blobs'.

Premature at our scale

  • Distributed cache locking (Redis SETNX mutex) for stampede protection. Correct at high concurrency on a single hot key; at ~28 salons and low traffic, no Solen endpoint has been measured to receive concurrent-enough traffic on one key for a stampede to be a real risk. Trigger to revisit: a specific cached endpoint independently measured (not guessed) to receive a burst of concurrent requests at the exact moment a cache entry expires, causing a measurable DB load spike.
  • Probabilistic early expiration (XFetch). Same trigger as above, one tier further out; this is the fix for when locking's own latency/contention becomes the new bottleneck, which requires stampede-scale traffic to even be relevant.
  • Materialized views. Correct once a specific aggregate query is provably slow (explain-analyze, not a guess) and tolerant of minutes-scale staleness. Zero exist today and none are currently justified; the "measure first" discipline from fable-backend applies directly, don't build one speculatively.
  • A general-purpose Redis response cache layer (cache-aside for arbitrary API responses). Upstash Redis is already a paid, monitored dependency for rate limiting/OTP/nail-budget; extending it to general response caching is reasonable once a SPECIFIC endpoint needs fleet-wide-consistent, sub-CDN-TTL freshness that a per-process Map can't give. No such endpoint has been identified yet.
  • Netlify's Durable Cache primitive (Netlify-CDN-Cache-Control: ...durable..., reduces cold function invocations by sharing cached responses across edge nodes): real and potentially useful once Solen's function invocation COUNT/cost becomes a measured concern; at current traffic this is solving a cost problem Solen doesn't have yet.
  • CDN cache-tag purging via Netlify's purgeCache({tags}) API. A genuinely useful event-based CDN invalidation primitive, but Solen's current TTL windows (60s CDN, up to 300s stale-while-revalidate) are already short enough that manual purging isn't buying much; worth adopting the day a CDN TTL gets pushed longer (e.g. to reduce DB load further) and a write-triggered purge becomes necessary to keep correctness.

Unverified

  • Whether Next.js's Data Cache (the unstable_cache/fetch({cache:'force-cache'}) backing store) is durably shared across separate Netlify Function cold starts, the way Vercel's own Data Cache is documented to be on Vercel's infrastructure. Netlify's @netlify/plugin-nextjs integration page was not fetched this run (out of scope budget); this matters because if Solen ever adopts unstable_cache at any real TTL, whether that cache is a real fleet-wide durable store on Netlify specifically, or effectively degrades to per-instance behavior, changes the entire recommendation. Needed: fetch Netlify's own Next.js Runtime / ISR documentation and confirm directly rather than assuming Vercel-equivalent behavior.
  • Netlify's exact Vary + cookie-name-matching semantics at the CDN edge (does it support cookie-value-aware variants at all, and if so by exact cookie name or pattern). This is the specific gap the codebase's own feed-cache-headers.ts comment already flags as unverified; this research run did not close it either (would need a dedicated Netlify docs page on Vary support specifically, not found in the caching-overview fetch). Current mitigation (binary no-store split) is safe regardless of the answer, so this is a "nice to resolve for future cache-hit-rate optimization," not a live risk.
  • Any specific numeric benchmark for XFetch's improvement magnitude (e.g. "3-5 DB queries out of 10,000 concurrent requests," "p99 latency 45ms") is a single vendor blog's illustrative figure, not independently reproduced or measured against Solen's own infrastructure; explicitly not to be cited as a Solen-applicable fact, only the ALGORITHM's existence and shape is T1.
  • Whether Upstash Redis (the specific managed Redis Solen already pays for) has any documented recommended pattern or SDK helper for cache-aside/stampede locking specifically, versus the generic Redis-the-protocol patterns cited here. Not fetched this run; if Solen ever adopts Redis-as-cache, Upstash's own docs should be checked directly rather than assuming generic Redis advice transfers 1:1 (Upstash is REST-based, not a persistent TCP connection, which changes some latency/locking assumptions).
