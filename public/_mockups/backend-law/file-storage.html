File & object storage , researched law

Date: 2026-07-16. Sources fetched this run: 17 (listed at the bottom with what each established). Audience: any Claude session or engineer touching Supabase Storage, upload routes, signed URLs, image serving, or bucket policies on Solen. Scale: ~28 salons, low traffic, serverless (Netlify Functions via @netlify/plugin-nextjs), Supabase Postgres + Storage, no separate CDN/S3/R2 in front of Storage today.

0. The short version

  1. Never proxy raw file bytes through your own server if you can avoid it. Direct-to-storage upload (presigned/signed URL) is the default; a server-mediated upload is the exception, justified only by a real ownership check that must happen before the write. T2/CONV, see section 2. Solen currently proxies every upload through a Next.js API route , this is the single biggest gap between current practice and the researched default, and it directly collides with a hard platform limit (section 2).
  2. Object storage, not database blobs, for anything user-facing (photos, documents, exports). Postgres CAN store binary via bytea/TOAST, and does so fine up to roughly 100 MB with no special tuning, but this is the narrow case, not the default. T2, section 1.
  3. Never trust a client-declared MIME type or file extension. It is trivial to spoof (OWASP, T1) and this codebase has already been bitten by it once (service-photos, section 6). Validate server-side against a real allowlist, and set the Storage-layer allowed_mime_types too so a client-supplied Content-Type can never become the object's serving header.
  4. Signed URLs are bearer tokens, not access control. Anyone holding the link can use it until it expires, full stop, no revocation. Short expiry (minutes, not days) is the only real defense once you accept that a link can leak. T1/T2, section 3.
  5. A public bucket bypasses RLS for reads entirely , anyone with the object's URL (guessed or leaked) gets the file, and depending on the Storage implementation, a public bucket can also make listing/enumeration possible. Only mark a bucket public when every object in it is meant to be public. T2, section 9.
  6. Content-addressed, immutable filenames get Cache-Control: immutable, max-age=31536000; anything mutable-at-the-same-URL gets short/no cache. Never immutable on a URL whose bytes can change under it. T1 (MDN), section 4.
  7. Malware/virus scanning of user uploads is real, well-documented practice at AWS scale (ClamAV Lambda), and is currently ABSENT from Solen. At 28 salons and low file-upload volume, full async AV scanning is premature machinery; the honest floor today is strict MIME/extension allowlisting + nosniff + private-by-default, with AV scanning flagged as the next step once upload volume or trust boundary (public submissions) changes. T2/T3, section 5, and "Premature at our scale."
  8. Orphan cleanup needs to run in both directions: rows without files (broken references) AND files without rows (storage leaks, cost + attack surface). Neither is automated in Solen today. T2/CONV, section 8.
  9. On-the-fly image transforms are the right default for a marketplace with unpredictable image sizes; pre-generation only pays off at a scale where transform cost/latency dominates, which Solen is nowhere near. T2, section 5.
  10. A TS type or a migration file is not proof of live bucket config. Only 5 of Solen's 14 live Storage buckets exist in a committed migration; bucket flags (public, file_size_limit, allowed_mime_types) and RLS policies on storage.objects must be checked against the live project, per this project's existing rule.

1. Object storage vs blobs in the database

The question. Where should a file's bytes live: an object store (Supabase Storage / S3 / R2), or a database column (bytea, or SQL's BLOB / Postgres large objects)?

What the evidence says.

Postgres has two ways to store binary data: bytea (a variable-length byte string column, T1, Postgres binary data types docs) and the separate Large Object facility. For bytea, any value over roughly 2 KB triggers TOAST (The Oversized-Attribute Storage Technique): Postgres compresses the value and/or moves it out of the main row into a side table once the row exceeds the ~2 KB TOAST_TUPLE_THRESHOLD, transparently to the query layer (T1, Postgres storage docs, TOAST). This means Postgres does not choke on a stored image or PDF: the row stays small, the blob lives in the TOAST table, and it is only paged in when actually selected. In one documented test case (HTML pages + URLs) the whole table including TOAST used about 50% of raw data size with no runtime penalty versus an untoasted comparison.

The genuine advantages of storing the blob in Postgres: it is transactionally consistent with the row that references it (no split-brain between "the DB says this exists" and "the file is actually there"), it is backed up and replicated by whatever already backs up the database, and there is exactly one source of truth. The genuine disadvantages: no CDN in front of a database column, no cheap range/streaming reads, DB storage costs and I/O are usually more expensive per GB than object storage, and every read of a large blob adds load to the database connection pool that a CDN-fronted object store would have absorbed for free.

Where the real tradeoff lies. The crossover is not "always object storage." It is: object storage wins once (a) the file needs to be served directly to a browser/CDN cheaply, (b) file sizes get into the video/large-media range, or (c) you want independent scaling of storage from the database. DB blobs win when the artifact is small (a signature, a small config blob, a thumbnail under a few hundred KB), needs to be transactionally atomic with a row update (e.g. "this row and its blob must appear together or not at all, no eventual consistency window"), or you specifically want one restorable unit with the rest of the data.

Recommended default for Solen: object storage (Supabase Storage) for every user-facing file (salon photos, client before/after photos, review photos, documents, exports). This matches what Solen already does, correctly, for every one of these. The one place Solen already stores something blob-like outside the DB that arguably could have been a DB blob: the nightly db-backups JSON exports (lib/backup/export.ts) are small per-table JSON files written to a private Storage bucket rather than another DB. That is the right call here specifically because Supabase PITR is off and the backup must survive a DB-level incident, so it must NOT live in the same database it is backing up.

Cost of getting this wrong at Solen's scale: low today (28 salons, modest photo volume), but a DB-blob mistake compounds because every added blob column makes routine table dumps/exports (the nightly backup, npm run smoke, any future migration) slower and heavier for no benefit, since Storage already gives cheap CDN-fronted delivery for free.

2. Presigned / direct uploads: never proxy bytes through your own server

The question. Should the client upload bytes to your own Next.js API route, which then re-uploads them to Storage, or should the client upload directly to Storage using a short-lived signed URL your server issued?

What the evidence says. Every major object-storage vendor's own recommended pattern is the same: server issues a signed URL scoped to a specific key (and, ideally, a size and content-type constraint), and the client PUTs/POSTs directly to the storage backend. AWS: "[presigned URLs] allow an upload without requiring another party to have AWS security credentials," generated with an expiry (max 7 days via SDK/CLI) (T1, AWS S3 presigned URL upload docs). Cloudflare R2 mirrors the same model with expiry from 1 second to 7 days and explicitly frames the URL as "a bearer token" (T1, R2 presigned URLs docs). Supabase Storage's own upload docs steer the same direction for anything non-trivial: standard multipart upload is fine under about 6 MB, but "we recommend using TUS Resumable Upload for uploading files greater than 6MB in size for better reliability" (T2, Supabase standard uploads docs), and Supabase separately exposes createSignedUploadUrl specifically so the client can upload directly without the file ever touching your server.

The reason this is not just a style preference: serverless functions have hard body-size and duration limits, and a proxy pays for bytes twice. Netlify Functions cap request payloads at 6 MB, and for base64-encoded binary payloads the effective usable size drops to about 4.5 MB once you account for base64's ~30% overhead (T2, Netlify functions configuration docs, corroborated by Netlify community threads on the same number). Next.js itself defaults its App Router body-size handling around 10 MB via the (currently experimental) proxyClientMaxBodySize config, and separately warns that API route responses over 4 MB are "not built to support the transmission of large amounts of data" in a serverless deploy (T2, Next.js proxyClientMaxBodySize docs, Next.js API routes response-size-limit message). Proxying also means your server pays for the read bandwidth AND the re-upload bandwidth, doubles the request's wall-clock time (download-then-upload instead of one direct upload), and ties up a serverless invocation (billed duration) for the whole transfer instead of for a microsecond URL-signing call.

Where the real tradeoff lies. A server-side proxy upload is still the right call when you need to do something to the bytes before they land that only the server can safely do: enforce an ownership check using data the client must not be trusted to assert (Solen's formula-photo route explicitly does this, checking the client belongs to the salon BEFORE the Storage write, after a prior finding where the write happened first and wasted a Storage write on an unauthorized request), or run synchronous virus scanning / image reprocessing that must complete before the object is considered "real." The cost of direct upload is that authorization now has to happen at signing time (before you've seen the bytes) rather than at write time, which means you cannot make the authorization decision depend on the file's actual content (its real dimensions, its real virus-scan verdict) unless you add a second, async "confirm" step after upload.

Solen's actual current state, and the concrete cost of it. Every upload route inspected in _docs/BACKEND.md section 3 (salon-gallery, client-photos, formula-photos, review-photos, salon-documents, service-photos, discovery admin uploads) proxies the file through a Next.js API route running as a Netlify Function: the browser sends multipart/form-data to the route, the route validates it, then re-uploads to Supabase Storage from server code. This is the pattern this section says to avoid, and it collides directly with the platform limits above: formula-photo validates files up to 10 MB and salon/documents validates PDFs up to 10 MB, both above Netlify's ~6 MB raw request-body ceiling. UNVERIFIED: whether Netlify's Next.js runtime (which may run some routes as Edge Functions or use a different body-handling path than a "classic" Netlify Function) actually enforces the 6 MB figure for these specific routes in production, or whether a larger file already fails today with a platform-level 413 before the app's own size check ever runs. This is worth a direct empirical test (upload an 8 MB file to /api/salon/documents against the live site) rather than continuing to trust either the docs number or the app's validation ceiling.

Recommended default for Solen going forward: new upload surfaces should use Supabase's createSignedUploadUrl (client uploads directly to Storage; server only signs the URL and validates the row-level ownership/metadata before signing) for anything that can plausibly exceed a couple of MB (formula photos, salon documents, gallery photos). Keep server-side proxying only for routes that must synchronously validate ownership against data the uploader must not see or control before the bytes are accepted, and where files are reliably small (well under the 4.5-6 MB ceiling). Cost of migrating: touches every upload route's client and server code, and moves the ownership check from "before I write the file" to "before I sign the URL," which is a real behavior change worth its own mockup/review, not a drive-by refactor.

3. Signed URLs, expiry, and the leak-by-sharing problem

The question. Once you generate a temporary signed URL for reading or writing an object, what security properties does it actually have, and how long should it live?

What the evidence says. A signed/presigned URL embeds the authorization directly in the URL string: whoever holds that string can perform the allowed action until it expires, with no way to check who is making the request. AWS's own prescriptive guidance is blunt about the consequence: "Presigned URLs cannot be revoked before expiry using standard mechanisms... expiration is the primary revocation mechanism" (T1, AWS presigned URL best practices). Community security writeups converge on the same framing from the reader's side: "If you grant read access to an object in a bucket for 1 day, anyone with the link can access that object for the whole day, multiple times" (T2, multiple independent security blogs on S3 presigned URLs, e.g. insecurity.blog, Advanced Web Machinery). This is the exact mechanism behind "leak by sharing": a signed URL pasted into a chat, forwarded in an email, or logged by an analytics tool remains fully valid for anyone who later reads that chat/email/log, for the whole expiry window.

Concrete expiry guidance converges around: downloads, minutes to at most an hour (the URL should be consumed almost immediately after signing, so 15 minutes is "more than enough" for a browser to fetch an image right after your page requests it); uploads, a wider window (up to a few hours) to tolerate a slow client connection, but bounded, and ideally paired with a content-length-range condition on the upload policy so a leaked upload URL cannot be used to write an arbitrarily large file (T1/T2, same AWS prescriptive-guidance source plus the S3 presigned-URL docs above). Cloudflare R2's presigned URLs support the same 1 second to 7 day expiry window and the same "treat it as a bearer token" framing (T1, R2 presigned URLs docs).

Where the real tradeoff lies. Shorter expiry is strictly safer but adds friction: a signed URL that expires in 60 seconds is useless if it's embedded in an email a user opens 10 minutes later, or cached in a service worker, or if the browser retries a slow request past the window. The practical compromise is to size expiry to the actual usage pattern (an inline <img> src needs only as long as the page stays open and the browser's first fetch; a "download my invoice" link a user might click from an email needs longer, maybe re-signed on each page load rather than emailed directly).

Recommended default for Solen: signed URLs for anything currently served as a raw public URL from a private bucket (see section 9's finding on client-photos/formula-photos) should be minted per page-load, short-lived (minutes), and never persisted anywhere durable (never store a signed URL string in a database column; store the object's storage path, and re-sign a fresh URL every time it needs to be served). Cost: an extra signing call on every page render that shows a private photo, which for 28 salons' worth of traffic is negligible. This also interacts with Supabase's Smart CDN: with Smart CDN enabled (Pro plan and above), a signed URL response is cached at the CDN edge keyed on the exact token in the URL, so re-signing on every request means every request is a fresh cache key (a cache miss) unless you deliberately reuse the same signed URL within its CDN cache window (T2, Supabase Storage CDN / Smart CDN docs). This is a real tension: short-lived, unique-per-request signed URLs are the safer security default but defeat edge caching; a slightly longer, deliberately-reused signed URL (re-signed every N minutes rather than every request) is often the better practical balance once traffic volume makes CDN cache-hit-rate matter. At Solen's current scale this tension is not yet worth engineering around; issue fresh short-lived URLs and revisit if Storage egress or CDN cost becomes visible.

4. CDN and cache headers: immutable + content-hashed names vs revalidation

The question. How long should a browser/CDN be allowed to cache a file, and how do you avoid serving a stale (or a too-fresh, always-refetched) asset?

What the evidence says. MDN's Cache-Control reference (T1, MDN Cache-Control docs) is the canonical source here: max-age sets a freshness window; immutable tells the cache the response will never change while it's fresh, which lets the browser skip the conditional revalidation request entirely on a hard refresh; no-cache allows storage but forces revalidation before every reuse (right for frequently-changing content, not the same as "don't cache"); no-store forbids caching outright (right for sensitive/private content). immutable is safe only when the filename or URL itself changes whenever the content changes (a content hash in the path, or a version segment) , because the browser will never re-check the origin for as long as the cache entry is fresh, an update served at the same URL under immutable will not reach users until the cache naturally expires or the user clears it.

Supabase Storage's own default is a 1-hour cache at both the CDN and the browser, with automatic invalidation on update/delete that can take up to 60 seconds to propagate across regions; this can be overridden per-object via the cacheControl option at upload time (T2, Supabase Storage CDN fundamentals, Smart CDN docs).

Where the real tradeoff lies. Aggressive caching (immutable, a year-long max-age) is free performance and free egress-cost savings, but only if the object at that URL genuinely never changes. Solen's upload routes write to paths like formula-photos/{salon.id}/{clientId}/{ts}-{type}.{ext} and salon-gallery/{slug}/{filename} , the timestamp in the formula-photo path already makes each upload a distinct, immutable key, which is the right shape for aggressive caching. Paths that instead reuse a stable name (anything that could later be overwritten via upsert: true, which Supabase's own upload docs warn "we caution against... due to CDN propagation delays") should NOT be marked immutable, because a real update at that same URL would be invisible to any client holding a cached copy until the cache naturally expires.

Recommended default for Solen: any Storage object whose path already encodes a timestamp or a content hash (most of Solen's current upload paths qualify) should be served Cache-Control: public, max-age=31536000, immutable. Anything that can be overwritten in place at a stable path (an upsert: true write to the same key, e.g. a salon's primary avatar if that pattern exists) should use a short max-age with revalidation, or better, be migrated to a hash/timestamp-suffixed path so it too can be immutable. Cost: none at Solen's traffic level; this is a pure win once the path scheme is verified per-bucket.

5. Image transforms: on-the-fly vs pre-generated

The question. Should thumbnails/resized variants be generated at upload time and stored (pre-generated), or generated on request and cached (on-the-fly)?

What the evidence says. Supabase Storage's built-in image transformation is on-the-fly: request ?width=..&height=..&resize=cover|contain|fill&quality=..&format=.. on a Storage URL and it resizes at request time, caching the result at the CDN edge afterward (T2, Supabase image transformations docs). It is gated to Pro plan and above, priced at $5 per 1,000 "origin images" beyond the plan's included quota (100/month on Pro/Team), capped at 2500px and 25 MB / 50 MP inputs, and cannot output HEIC. The alternative, pre-generation, means running a resize step (Solen already does this in one place: sharp-based WebP conversion in the discovery admin upload/staging routes) at upload time and storing each size variant as its own object.

Where the real tradeoff lies. On-the-fly transforms mean you never have to predict every size you'll ever need (a new card layout that wants a slightly different crop just works, no backfill), at the cost of a per-transform charge and a first-request latency hit (cache miss) for any size nobody has requested yet. Pre-generation means predictable, flat storage cost and zero request-time latency, at the cost of committing to a fixed set of sizes up front and having to re-run a batch job if you ever change them (or living with stale sizes forever).

Recommended default for Solen: on-the-fly transforms for anything served through Supabase Storage's own transform endpoint (salon gallery, client photos), because Solen does not yet know its final size matrix and the traffic volume (28 salons) means the $5/1,000-origin-image pricing is a rounding error. Keep the existing sharp-based pre-generation only where it already exists for a specific, narrow reason (the discovery pipeline's WebP conversion, which is about normalizing an unpredictable external format, not about producing multiple sizes). Cost of on-the-fly at scale: if Solen's origin-image count (unique width/height/quality/format combinations actually requested) grows past the low thousands per month, the $5/1,000 fee starts to matter and pre-generating a small fixed set of sizes (thumbnail, card, full) becomes the cheaper choice; that is a "revisit at X" item, not a current problem.

6. Virus/malware scanning

The question. Should uploaded files be scanned for malware before being stored or served?

What the evidence says. This is not scanning for a novel technique, it is a well-trodden AWS reference pattern: a Lambda function running ClamAV (either as a Lambda layer with virus definitions persisted to EFS, or as a containerized clamd daemon on ECS Fargate to avoid Lambda cold-start cost of loading the AV engine) triggered on object upload, tagging the object INFECTED/CLEAN in object metadata, often fronted by an S3 → EventBridge → SQS → Lambda pipeline for retry/backpressure control (T2, multiple sources: AWS CDK serverless ClamAV construct, Serverless Guru secure-upload writeup). The OWASP File Upload Cheat Sheet names the same principle at a higher level: "run the file through an antivirus or a sandbox if available to validate that it doesn't contain malicious data," alongside Content Disarm & Reconstruct (CDR) for document formats like PDF/DOCX where a "clean" file can still carry an embedded exploit in its structure (T1, OWASP File Upload Cheat Sheet).

Where the real tradeoff lies. AV scanning adds real infrastructure (a scanning service, definition updates, a queue, a way to hold the object "pending" until scanned or reject it after the fact) and real latency (the AWS pattern above scans asynchronously after upload, meaning the object briefly exists before its scan verdict is known, or the app must hold it in a staging area until cleared). It is unambiguously the right control once a product accepts uploads from untrusted or anonymous parties at meaningful volume, or once uploaded files are served to OTHER users (not just back to the uploader), because that is the scenario where a malicious file becomes a distribution vector rather than a self-inflicted risk.

Solen's actual exposure today. Every upload route requires an authenticated salon owner or a logged-in customer (reviews), and most served images are photos rendered through <Image>, not documents opened/executed by other users. salon-documents (PDFs, private bucket) is the one surface closest to "a file another human might open outside a browser's image renderer" (an owner viewing another user's uploaded verification document, if such a review flow exists). UNVERIFIED: whether any admin/reviewer flow actually opens a salon-documents PDF directly (as opposed to just checking metadata), which would be the concrete scenario where a malicious PDF matters.

Recommended default for Solen: do not build AV scanning infrastructure now. Current mitigations (server + Storage-layer MIME allowlists, nosniff, private buckets for documents) address the more likely and more automatable risk (arbitrary HTML/SVG execution via the trusted domain, section 7) more cheaply than AV scanning would. This is explicitly "premature at scale": the trigger to revisit is either (a) opening uploads to unauthenticated/public submission (a public review or contact form that accepts files with no login), or (b) salon-documents becoming something reviewers routinely open as a PDF rather than just storing.

7. Content-type sniffing and why you must not trust the client-declared type

The question. Can you trust the Content-Type a client sends with an upload, or the file extension, when deciding what MIME type to serve the object back as?

What the evidence says. OWASP is unambiguous: "The Content-Type for uploaded files is provided by the user, and as such cannot be trusted, as it is trivial to spoof" (T1, OWASP File Upload Cheat Sheet). The cheat sheet's recommended layered defense: an extension allowlist (not blocklist, and watch for double extensions like .jpg.php and null-byte tricks like .php%00.jpg), a real file-signature (magic-bytes) check server-side, generated (not user-supplied) filenames, and storage outside the web root or in dedicated object storage with tightly scoped permissions. Separately, on the SERVING side, MDN documents why browsers historically "sniff" a response's real content type regardless of the declared header (to gracefully handle misconfigured servers), and why X-Content-Type-Options: nosniff matters: without it, a browser can still execute an uploaded file as HTML/JS even if you declared it text/plain, which is exactly how a malicious upload becomes a stored XSS payload (T1, MDN X-Content-Type-Options docs).

Where the real tradeoff lies. There isn't much of one here, this is close to a pure-upside control: validating server-side and setting nosniff costs a few lines of code and has essentially no functional downside. The only real cost is remembering to do it consistently across every upload route AND every bucket, which is exactly where Solen has already slipped once.

Solen's own documented incident. service-photos had no Storage-layer MIME allowlist until a fix (supabase/migrations/20260710155420_...sql) closed it: the client-controlled file.type was being passed straight through as the object's served Content-Type on a PUBLIC bucket, meaning arbitrary HTML/SVG could be hosted and served from the trusted *.supabase.co domain (a same-origin-adjacent XSS/phishing vector). Per _docs/BACKEND.md's own finding, salon-gallery and salon-documents still have ONLY app-layer MIME checks with no Storage-layer allowed_mime_types set live, and client-photos's app route currently has no app-layer MIME/size validation at all (masked only by the bucket's own file_size_limit/allowed_mime_types happening to be set, which the same doc calls "bucket-level luck, not designed defense-in-depth").

Recommended default for Solen: every bucket that serves user-uploaded content needs BOTH an app-layer MIME allowlist (already true for most routes) AND a Storage-layer allowed_mime_types set on the bucket itself (true for only 2 of the buckets checked), so the control survives even if the app-layer check is ever bypassed, forgotten in a new route, or the bucket gets recreated without its config. This is cheap, has already caught one real incident on this exact codebase, and should be closed for the remaining buckets named in the existing audit, not treated as optional hardening.

8. Orphan cleanup: rows without files, files without rows

The question. How do you keep the database's references to files and the actual objects in Storage from drifting apart over time?

What the evidence says. This failure mode is well documented across every object-storage ecosystem under different names (S3 lifecycle + inventory reconciliation, Apache Iceberg's VACUUM/orphan-file-deletion for exactly this problem in a different data-lake context) but the underlying pattern is the same everywhere: (1) a periodic job compares the database's set of referenced storage keys against the actual object listing, (2) objects present in storage but referenced by no row are orphans (created by a failed transaction that wrote the file but never committed the row, or a row later deleted without cleaning its file) and are candidates for deletion after an age threshold, (3) rows that reference a storage key which no longer exists (a "broken image" in the product) are the mirror-image bug, usually caused by a file deleted directly against storage (or by a delete route that removed the DB row but the Storage delete call failed/was skipped) (T2/CONV, AWS Glue orphan-file-deletion docs, various S3 orphan-cleanup writeups). Supabase itself documents this exact class of bug on their own side: a fixed TUS-upload race condition "could leave orphaned locks," and separately a hardening change that blocks raw DELETE SQL against Storage tables specifically because "direct SQL DELETE commands on storage tables were the leading cause of orphaned objects" in their own system (T2, Supabase Storage performance/security/reliability blog post).

Where the real tradeoff lies. Building a full reconciliation job (list every object, diff against every referencing table, delete/report both directions) is real work and needs care: it must never delete something mid-upload (a file that exists in storage a few seconds before its DB row commits is not yet an orphan), and it must handle the many-tables-reference-one-bucket case correctly (Solen has 14 buckets referenced from at least 7+ different tables/columns, per _docs/BACKEND.md).

Solen's actual current state. No orphan-cleanup job exists today, in either direction. Concretely: salon_documents.file_url deletion (DELETE /api/salon/documents) re-fetches the row, checks ownership, then removes the Storage object using the same path , this is correct today, but if the Storage delete call ever silently fails (network blip, wrong path), the DB row's DELETE would still succeed independently unless it's inside a shared transaction (Storage and Postgres are not in the same transaction, so this genuinely can drift). On the other side, any upload route that writes to Storage and then fails the subsequent DB insert (e.g. a transient Postgres error after the Storage write succeeds) leaves an orphaned object with no referencing row, silently consuming storage forever.

Recommended default for Solen: given the current scale (28 salons, modest photo/document volume), a full automated reconciliation cron is premature; the cost of a stray orphaned photo or document is a few KB of wasted storage, not a functional bug. What is NOT premature: making delete routes defensive (log and alert, don't silently swallow, if the Storage-side delete fails after the DB row is gone, since that is the case that actually produces a broken/dangling reference visible to a user) and, when a reconciliation job eventually gets written, running it read-only/report-first (list mismatches, do not auto-delete) for at least one cycle before ever auto-deleting anything, given the codebase's own documented pattern of routes that build ad-hoc service-role clients and bypass the usual guardrails (salon-gallery, section 9).

9. Storage-level authorization: RLS policies, public vs private buckets, and the "public bucket allows listing" issue

The question. How does access control actually work on Supabase Storage, what does marking a bucket "public" really mean, and can a public bucket be enumerated/listed by an attacker?

What the evidence says. Supabase Storage layers Row Level Security policies on the storage.objects table exactly like any other Postgres table: "Storage does not allow any uploads to buckets without RLS policies" by default, and you write ordinary RLS policies (often keyed on storage.foldername(name)[1] to scope access to a folder matching the caller's identity) to control INSERT/SELECT/UPDATE/DELETE per bucket (T2, Supabase Storage access control docs). Marking a bucket public changes the read path entirely: "public buckets are already publicly accessible" and Supabase's own object-serving endpoint checks the bucket's public flag BEFORE anything else, meaning a public bucket's objects are reachable by anyone with the URL regardless of what RLS policies exist on storage.objects , RLS still governs write/delete/list on a public bucket, but not read-via-URL. Community security writeups on Supabase's public-bucket model converge on the same point: once a bucket is public, "anyone who possesses the asset URL can readily access the file," and this is a durable design choice, not a bug, so the real security boundary for a public bucket is "how guessable/leakable is the URL," not RLS.

Supabase's storage backend has also had real, fixed vulnerabilities in this exact area: a March 2026 update fixed a path-traversal bug that let "crafted paths escape the storage root directory," and separately fixed a bug where an "orphan object scanner" produced false-positive matches on bucket-name prefixes due to a missing trailing-slash boundary check (T2, Supabase Storage performance/security/reliability blog post). More broadly, the pattern of "a table exists but nobody enabled RLS on it, so the anon key reads/writes everything" is documented at real scale in the wild: CVE-2025-48757 (disclosed May 2025) found 303 endpoints across 170 Lovable-generated projects (about 10.3% of the sampled apps) exposing Supabase tables through the public anon key specifically because RLS was never turned on (T3, a single vendor-scanner source, vibeappscanner.com) , this CVE is about ordinary Postgres tables rather than storage.objects specifically, but it is the same class of failure (RLS-off-by-default) and the exact reason Solen's own audit treats "verify RLS live, not migration files" as standing law.

Where the real tradeoff lies. Public buckets are simpler (no signing, works with plain <img src>, cacheable by any CDN with no auth logic) and are the right choice for content that is genuinely meant to be public anyway (a salon's public gallery photos, published discovery images). Private buckets are the right choice the moment the content is meant to be seen only by specific people (a client's before/after photos, a salon's verification documents) , but "private" only actually protects the content if every code path serving it uses signed URLs; a private bucket whose app code calls .getPublicUrl() anyway gets you the WORST of both worlds (URL rejected outright at the Storage layer , see below , or, if it does resolve, effectively public reads with none of the operational simplicity of an intentionally public bucket).

Solen's actual current state, and a live, documented gap. Per _docs/BACKEND.md section 3's live bucket inventory: client-photos and formula-photos are both genuinely private (public: false, live-verified), yet both upload routes (app/api/clients/[id]/photos/route.ts:70, app/api/dashboard/coiffeur/formula-photo/route.ts:82-86) call .getPublicUrl() and persist that value, and the frontend renders it straight into <Image src>. Supabase's /object/public/... endpoint checks the bucket's public flag first and rejects the request for a private bucket independent of RLS, so as documented these URLs should currently be non-functional (broken images) rather than an active leak, unless something downstream (a caching proxy, a different endpoint) resolves them anyway , this needs empirical confirmation, not just the code-level read, since a silently-broken image and a silently-working insecure link look identical from a grep. The existing RLS SELECT policies on these two buckets (salon_owners_read_client_photos, salon_owners_read_formula_photos, both scoped to the owning salon) show the INTENDED model is authenticated/signed access; nobody finished the job by switching the app code to createSignedUrl(). Separately, salon-gallery's upload route builds its own service-role Postgres client instead of using the shared session-bound helper, so every Storage call for that bucket runs with the service role and RLS on storage.objects never applies at all for it; the only thing preventing a cross-salon gallery write today is the app-layer salon.owner_id !== user.id check, with no RLS second gate the way client-photos/formula-photos/salon-documents/service-photos all have.

Recommended default for Solen: (1) fix the client-photos/formula-photos mismatch by switching both routes to createSignedUrl() (short expiry, re-signed per page load per section 3) rather than flipping the buckets to public, since the existing RLS policies show private-with-signed-access was the intended model; (2) add a genuine storage_owners_upload_*-style RLS policy to salon-gallery so it has the same two-gate defense as its siblings, or explicitly document why the service-role bypass there is accepted (it currently is not documented as an accepted risk, just present); (3) treat "query pg_policies on storage.objects live" as the standing verification step before trusting any bucket's access model, exactly as the project's own rules already say, because this section shows two of the fourteen live buckets currently disagree with what their code assumes about them.

Myths and traps

  • MYTH: "The file's Content-Type header tells you what kind of file it is." It is entirely client-controlled and trivially spoofed (T1, OWASP). Trusting it to set the SERVED content-type on a public bucket is exactly the incident Solen already had on service-photos.
  • MYTH: "A signed URL is basically as safe as a login-gated page." It is a bearer token with no revocation and no per-request identity check (T1, AWS prescriptive guidance). Anyone who gets the string gets the access, for the whole window, as many times as they want.
  • MYTH: "Private bucket = safe, whatever the app code does." A private bucket only protects reads if every code path serving its contents uses signed URLs. .getPublicUrl() on a private bucket is not a smaller version of a public URL, it is a broken or misleading link, and the fact that it LOOKS like the same code as the public-bucket routes is exactly how this drifted unnoticed in Solen's own codebase (section 9).
  • MYTH: "RLS policies matter for reads on a public bucket." They don't, for reads. Supabase's public-object endpoint checks the public flag first and serves the bytes to anyone with the URL, RLS or not. RLS on a public bucket still governs write/delete/list.
  • MYTH: "Postgres can't handle binary data well, always use object storage." Overstated. TOAST makes bytea perform fine up to a fair size (well past 100 MB is documented as reasonable) with no special tuning; the real reason to prefer object storage is CDN/cost/streaming, not a Postgres limitation.
  • Serverless-specific trap (this stack): base64 JSON payloads roughly halve your effective body-size budget. A route that accepts a file as a base64 string inside a JSON body pays ~30% overhead before your platform's raw body-size cap even applies; multipart form-data avoids this specific tax but is still bounded by the same raw cap.
  • PostgREST-specific trap (this stack's documented #1 failure mode): a Storage RLS policy that references a phantom column or the wrong bucket_id silently fails closed (upload/read just doesn't happen) rather than erroring loudly. This is exactly what happened to review-photos: its INSERT policy was dropped at some point after the original migration, the upload route still calls the RLS-bound session client (not the admin client), the RLS violation is caught and swallowed (continue), and the route returns 200 { success: true, photos: [] } for every request. Prove behavior (upload a review photo, confirm the row + object both exist), never just that the route returns 200.
  • Netlify-specific trap: several of Solen's own upload routes validate file sizes (10 MB) above Netlify's documented raw function body cap (6 MB, ~4.5 MB effective for base64). This has not been empirically confirmed to fail in production this session (flagged UNVERIFIED above) but is exactly the kind of platform-limit-vs-app-assumption mismatch this stack has been bitten by before; test it directly rather than trusting either number.
  • Stripe Connect trap (adjacent, worth naming since this stack uses Connect): a connected account's uploaded verification documents (identity docs) should go through Stripe's own file upload API (https://uploads.stripe.com/v1/files), not through your own Storage buckets , mixing "documents Stripe needs for KYC" into your own bucket inventory is a common confusion in Connect integrations; UNVERIFIED for Solen specifically whether salon-documents ever holds Stripe-required KYC documents or is purely Solen's own verification flow (worth a direct check before assuming it's fine either way).

Premature at our scale

  • A full ClamAV/malware-scanning pipeline (Lambda + EFS + SQS + tagging). Correct once uploads come from untrusted/anonymous parties at volume, or served to other users at volume. Solen's uploads are all authenticated-user-gated today. Trigger to revisit: a public (no-login) upload surface ships, or salon-documents becomes something a human routinely opens as a rendered PDF rather than just storing.
  • Automated storage/DB reconciliation with auto-delete. Correct at a scale where orphan storage cost or orphan-caused bugs are actually visible in a bill or a support ticket. At 28 salons this is pennies. Trigger to revisit: Storage cost becomes a line item worth optimizing, or a support ticket traces back to a dangling reference.
  • Pre-generating a fixed image-size matrix instead of on-the-fly transforms. Correct once transform request volume/cost is material or request-time latency on a cache miss becomes a measured problem. Trigger to revisit: Supabase's $5/1,000-origin-image transform billing shows up as a non-trivial line item, or a specific page's image-load latency is measured and traced to a transform cache miss.
  • A dedicated CDN/S3/R2 layer in front of Supabase Storage. Supabase's built-in Smart CDN already covers the caching need at this traffic level; standing up a separate CDN is real added infrastructure (DNS, cache-invalidation logic, a second billing relationship) that buys nothing extra yet. Trigger to revisit: Storage egress cost or CDN cache-hit-rate becomes a measured, material problem, or a specific need arises that Supabase's CDN doesn't cover (e.g. edge compute on the image path).
  • S3 Inventory-style periodic full-bucket audits for orphan detection. This is the right heavyweight tool once bucket object counts get into the range where a manual/ad-hoc comparison stops being feasible. At Solen's per-bucket object counts, a simple scheduled query (compare table's referenced paths against a Storage list() call) is enough; the Inventory-report machinery is overkill.

The gaps in detail

1. review-photos has zero INSERT policy, every upload silently fails (STOR-12)

What is wrong: storage.objects RLS is enabled (relrowsecurity=true, live-confirmed) with no forced bypass. The only policy naming review-photos is public_read_review_photos (SELECT). No INSERT policy exists for this bucket in the live 19-row policy set.

The exact code (app/api/reviews/[id]/photos/route.ts:63-70):

const { error: uploadErr } = await supabase.storage
  .from("review-photos")
  .upload(path, file);

if (uploadErr) {
  console.error("Photo upload error:", uploadErr);
  continue;
}

The route uses the session (RLS-bound) client, not the admin client its five sibling upload routes could use.

What breaks in practice: A reviewer selects up to 3 photos, the request returns 200 { success: true, photos: [] }, the review submits fine, but no photo is ever attached. From the customer's side this looks like it worked; there is no error surfaced anywhere. Confirmed still live today, same as BACKEND.md's 2026-07-14 read (policy count unchanged).

The fix and its cost: Either (a) add CREATE POLICY "reviewers_upload_own_review_photos" ON storage.objects FOR INSERT WITH CHECK (bucket_id = 'review-photos' AND EXISTS (SELECT 1 FROM reviews WHERE id::text = (storage.foldername(name))[1] AND user_id = auth.uid())), matching the salon_owners_upload_* pattern already used for 5 other buckets, one migration, or (b) switch the route to createAdminSupabaseClient() like formula-photo/clients/[id]/photos do, one-line import + client swap. Option (a) keeps genuine defense-in-depth; option (b) is faster and matches the pattern most sibling routes already use for uploads that already have a solid app-layer ownership check (review.user_id !== user.id at :32). Either is a same-session fix.

2. Private-bucket getPublicUrl() mismatch renders broken images, confirmed empirically (STOR-05)

What is wrong: client-photos and formula-photos are both public:false live, but both upload routes call .getPublicUrl() and persist that URL, and the frontend renders it directly.

The exact code:

// app/api/clients/[id]/photos/route.ts:85
const { data: urlData } = supabase.storage.from("client-photos").getPublicUrl(path);
// ... photo_url: urlData.publicUrl  → stored, then rendered:
// components-legacy/dashboard/ClientPhotosTab.tsx:111
<Image src={p.photo_url} ... />

Same shape in formula-photo/route.ts:82-99 → FormulaBook.tsx:330-333.

What breaks in practice, proven not guessed: I ran the actual request this bug produces:

curl https://tocfnsmxmdxkrcmjzzdw.supabase.co/storage/v1/object/public/client-photos/nonexistent-path-test.jpg
→ HTTP 400  {"statusCode":"404","error":"Bucket not found","message":"Bucket not found"}

versus a real object in the genuinely public discovery-images bucket, which returns HTTP 200. Supabase's public-object endpoint checks the bucket's public flag before it even looks up the object, so this is a hard 400 for every single stored URL, not an occasional miss. Net effect: every client before/after and formula photo would render as a broken image in the dashboard, not a leak of any kind (no one can fetch these files this way; they just can't be viewed this way either, including by their rightful owner). client_photos has 0 rows in prod today, so no salon owner has actually hit this broken state yet, but it will fire the first time anyone uses the feature.

The fix and its cost: Replace .getPublicUrl() with .createSignedUrl(path, expirySeconds) at read time (list/GET endpoints), never at write time, and never persist the signed string, keep the DB column as a raw path (the way salon_documents.file_url already correctly does it). Requires a small migration script to convert existing photo_url/before_photo_url/after_photo_url values from full URL back to path (the pathFromPublicUrl() helper already exists in lib/gdpr/purge-client-photo-storage.ts:40-48, reusable), plus updating the two render call sites to fetch a fresh signed URL server-side before rendering. A few hours of work, no schema change needed if paths are stored going forward and legacy rows (there are none live) are backfilled.

3. Two upload routes bypass Storage RLS via service-role client (STOR-07)

What is wrong: salons/[slug]/gallery/route.ts and dashboard/coiffeur/formula-photo/route.ts both perform their Storage .upload() call using a service-role (RLS-bypassing) client rather than the session-bound client every other sibling upload route uses.

The exact code:

// app/api/salons/[slug]/gallery/route.ts:7-10
const getSupabase = () => createClient(
  getPublicEnv().NEXT_PUBLIC_SUPABASE_URL,
  getServerEnv().SUPABASE_SERVICE_ROLE_KEY
);

Live pg_policies confirms salon-gallery has no RLS policies of any kind (it does not appear anywhere in the 19-row live policy set), so even if this route used the session client, RLS would default-deny every request; the service-role bypass here is arguably load-bearing, not just convenience. formula-photos, by contrast, DOES have a live salon_owners_upload_formula_photos INSERT policy that mirrors every other bucket's pattern, it is simply never exercised because formula-photo/route.ts:23,71-76 also uses createAdminSupabaseClient().

What breaks in practice: For both buckets, the app-layer check (salon.owner_id !== user.id for gallery; getActiveSalon + clientBelongsToSalon for formula-photos) is the ONLY thing standing between a caller and a cross-salon write. Both checks currently look sound on read (no bug found), but there is no second gate if either check ever regresses. This is exactly the "one gate only" pattern the project's other 4 upload routes deliberately avoid.

The fix and its cost: For salon-gallery: add the matching salon_owners_upload_gallery / salon_owners_read_gallery policies (same shape as the other 5 buckets already have) and switch the route to the session client, this also closes STOR-04's gap on this bucket in the same migration since RLS forces MIME/size discipline to matter less. For formula-photos: simplest fix is switching the upload call from admin.storage to supabase.storage (the session client is already constructed at :13 for auth), the RLS policy is already live and ready, this is a one-line change. Neither fix is large; both are worth batching with the STOR-12 fix in one migration + one PR since they touch the same storage.objects policy surface.

4. salon-gallery and salon-documents have zero Storage-layer size/MIME enforcement (STOR-04)

What is wrong: Live storage.buckets shows file_size_limit: null, allowed_mime_types: null for both salon-gallery (public) and salon-documents (private), and also for formula-photos (private). Only client-photos and service-photos have the Storage-layer allowlist set.

What breaks in practice: For salon-gallery specifically (public bucket, no allowlist at either layer if the app-layer check were ever bypassed or a future route reused the bucket without copying the same validation), a client-controlled file.type could in principle get hosted as the object's real Content-Type on the trusted *.supabase.co domain, the exact class of bug that was already fixed for service-photos (migration 20260710155420_...) after a real finding. Today's app-layer check in gallery/route.ts:54-60 does correctly allowlist jpeg/png/webp, so this is defense-in-depth missing, not an active hole, but it is the single point of failure BACKEND.md already flagged and it remains true live as of this session.

The fix and its cost: UPDATE storage.buckets SET file_size_limit = 5242880, allowed_mime_types = ARRAY['image/jpeg','image/png','image/webp'] WHERE id = 'salon-gallery' and a parallel one for salon-documents with ['application/pdf','image/jpeg','image/png'] and a 10MB (10485760) cap to match the app-layer number (see gap 5 below for why that number itself needs re-checking). One migration, near-zero cost, matches what was already done for service-photos and client-photos.

5. Netlify function body-size limit vs the app's stated 10MB caps (STOR-02) , genuinely unverified

What is wrong: formula-photo (:53) and salon/documents (:51) both check file.size > 10 * 1024 * 1024 in app code, implying files up to 10MB are expected to work. Netlify's documented synchronous-function request body ceiling is materially smaller than that (around 6MB raw). No next.config.js or netlify.toml override for body size limits was found (grepped for proxyClientMaxBodySize, bodySizeLimit; zero hits in either file).

What I could not determine, and why: Whether an 8-10MB multipart upload to either live route actually succeeds or gets rejected upstream by Netlify's function runtime with a 413 before the app's own check runs requires an actual authenticated POST against the production route with a real file, i.e. a write operation. As a read-only auditor with no salon-owner test session, I did not perform this test; doing so would also create a real Storage object and DB row under a mandate that says never write.

The concrete test needed: With a seeded test-salon-owner session (GET /api/dev/login?to=<path> per project convention, dev/staging only, never prod), POST a real 8MB and a real 9.5MB image/PDF to both routes and record the actual HTTP status and where in the stack it fails. If it 413s below 10MB, either lower the app-layer cap to match reality (cheap, but silently shrinks the promised limit) or migrate both routes to a direct client-to-storage signed upload (createSignedUploadUrl) per STOR-02's own recommendation, which removes the proxy ceiling entirely, more work but the correct fix once files can plausibly approach the true limit. Severity is MEDIUM specifically because it is unverified, not because the current numbers are proven wrong.
