0. The short version

The rules a new session must obey before touching schema or a migration, each with its tier:

  1. Money is an integer in the currency's minor unit (Rappen for CHF), never a float, never the Postgres money type. (T1, Stripe's own convention; T2 general practice) Solen violates this on its oldest tables today, treat any new money column as integer-Rappen and flag the legacy numeric(x,2) columns rather than copying them.
  2. Every timestamp column is timestamptz, stored and reasoned about in UTC, converted to local time only at render/display time. (T1, Postgres official guidance)
  3. Primary keys stay UUID (v4, via gen_random_uuid()) at Solen's current scale; do not chase UUIDv7 or bigint identity yet. (T2/T3, tradeoff-dependent, see section 3) The random-insert cost UUIDv4 imposes only shows up once a table's *hot, randomly-inserted* index no longer fits in cache, our biggest table is ~9,400 rows.
  4. Status-like columns are text + a CHECK (col IN (...)) constraint, never a native Postgres ENUM. (Solen convention, backed by a real Postgres migration-cost tradeoff, T1 for the mechanic) This is already 100% consistent across 233 CHECK constraints in the codebase, keep it that way.
  5. Row Level Security is enabled on every table with no exceptions, and every RLS-bound (auth.uid()-filtered) policy wraps the auth function in a sub-select, (select auth.uid()), not a bare call. (T1 mechanic, Supabase-documented 94-99% latency difference at scale) Solen is compliant on the "every table" part; the sub-select wrapping needs a policy-by-policy audit (see auditQuestions).
  6. RLS returning zero matched rows and RLS raising an error look identical from the client: both come back as a 200 with an empty result. This is Solen's single most repeated backend bug class (see _docs/BACKEND.md section 2, the RLS-client trap on availability_slots and bookings). Never trust "no error" as proof a write happened, check the affected-row count.
  7. A JSONB column is for genuinely schema-less or vary-per-row data (an intake form's varying question set, a draft wizard's in-progress state), not a shortcut around designing three more tables. (T2, Postgres's own docs make this exact distinction) 92 files in Solen's migrations touch jsonb, that is not automatically wrong, but every new one should be asked "could this be columns instead."
  8. Multi-tenancy at Solen is shared-database, shared-schema, tenant column (salon_id or owner_id) plus RLS. (CONV, this is a named, well-understood pattern, not an empirical law) This is already the whole codebase's model and is the right one at 28 tenants; schema-per-tenant or database-per-tenant would be a regression, not an upgrade (see section 11).
  9. Soft delete via a status flag (what Solen actually does) is not the same thing as GDPR-compliant erasure. A banned_at or account_status='suspended' column is a *product* state, not a privacy control; a real erasure request needs its own anonymize-or-hard-delete path, which Solen has built separately (20260713150000_gdpr_deletion_completeness.sql and the financial-retention migration). Never assume flipping a flag satisfies Article 17. (T1, GDPR text itself)
  10. Constraints (NOT NULL, CHECK, UNIQUE, FK) are the actual source of truth for an invariant, application code that "also checks it" is a UX nicety, not the enforcement. (T1, this is simply what a constraint is for; T2 for why app-only validation fails under concurrency) Solen's own EXCLUDE-constraint fix for double-booking (section on constraints) is the textbook version of this rule already applied correctly.

1. Database choice: relational vs document vs key-value

The question. Given the freedom to pick again today, should Solen be on a relational database, a document store, or a key-value store (or some mix)?

What the evidence says. The mainstream framing (T2, converging across Microsoft's cloud-native architecture guide, Cockroach Labs, and multiple vendor comparisons) is that the three categories trade off differently on the CAP axis and on schema rigidity: relational databases prioritize consistency and enforce a schema up front, giving ACID transactional guarantees at the cost of that box you can't just add anywhere. Key-value stores trade query expressiveness for raw speed at very high frequency (session tokens, rate-limit counters, feature flags), Document stores trade schema enforcement for flexibility, letting each record's shape vary. None of this is a formal proof, it's a converged industry categorization (CONV, not an empirical law): "CAP theorem" itself is a distributed-systems constraint about partition tolerance, and applies most directly to distributed/multi-node databases, a single-region managed Postgres instance is not really making that tradeoff in the way a multi-region NoSQL cluster is.

Where the tradeoff actually lies for Solen. Solen's core data (salons, services, bookings, staff, payments, reviews) is deeply relational: a booking references a salon, a service, a staff member, and a slot, and the correctness of "this slot cannot be double-booked" or "this booking must reference a real, active service" is exactly what foreign keys and exclusion constraints exist to guarantee. A document database would either duplicate that relational structure inside each document (denormalize by hand, invite the drift bug class) or route back through in-application joins, which is strictly worse than what Postgres already does natively. Key-value stores are already IN the stack, correctly scoped: Upstash Redis backs the rate limiter (@upstash/ratelimit), not the primary data model.

Recommended default and cost. Stay on Postgres as the single system of record; use Upstash Redis (already present) only for ephemeral/high-frequency state (rate limits, short-lived locks, maybe a future cache), never for anything that needs a foreign key relationship or a transactional guarantee. Cost of this choice: none at Solen's scale, this is not a real open decision, it is confirming the existing correct choice. The only genuine trigger to revisit: a workload that is overwhelmingly read-only, extremely high QPS, and tolerant of staleness (e.g., a public leaderboard or trending feed with millions of reads/day), at which point a purpose-built cache layer in front of Postgres, not a database swap, is the correct next step.

Sources: Microsoft Learn, relational vs NoSQL data, Cockroach Labs, SQL vs NoSQL.

2. Schema design, normalization, and when to denormalize

The question. How normalized should Solen's schema be, and when is it correct to deliberately break normal form.

What the evidence says. The classical normal forms (T1/CONV, this is foundational relational-theory, Wikipedia is an acceptable tier for the definitions themselves): 1NF requires each column hold a single atomic value (no repeating groups packed into one field); 2NF removes partial dependency on part of a composite key; 3NF removes transitive dependency (a non-key column depending on another non-key column rather than directly on the key); BCNF tightens 3NF so every functional dependency's left side is a superkey. Normal forms beyond 4NF are explicitly noted as "mainly of academic interest" (Wikipedia, Database normalization), so nothing here argues for chasing 5NF. The practical tradeoff of denormalization is described consistently across several T3 sources converging on the same shape (T2 by convergence): normalized schemas are fast to write and safe against update anomalies but slow to read (joins); denormalized schemas are fast to read but pay write amplification (the same fact updated in more than one place) and risk silent drift between the copies. The rule of thumb given: denormalize when a table is read far more often than written and the join cost is the actual measured bottleneck, not a guess; the classic bad case is denormalizing a high-volatility field (something that changes every second), because every write then fans out to every denormalized copy (ClickHouse, when to denormalize, DataCamp, denormalization).

Where the tradeoff lies for Solen. Solen already has one clean example of correct, deliberate denormalization: salons.average_rating and salons.review_count are (per _rules/DB_SCHEMA.md) computed/cached fields rather than a COUNT()/AVG() over reviews on every card render, because the salon list is read on every homepage/search view and rating changes are comparatively rare (one write per review vs. thousands of list reads). That is exactly the "read >> write, and the volatile field is low-churn" case the sources describe as the correct time to denormalize. The wrong version of the same instinct would be caching something that changes on every booking (e.g., a salon's "next available slot", which needs to be live, not cached) into a column, that field's staleness cost would be immediate and visible.

Recommended default and cost. Model relationally to at least 3NF by default: every fact lives in exactly one place, keyed by its natural owner (a service's price lives on services, not copied onto every booking row, bookings.price_paid is a deliberate historical snapshot, not a denormalized live mirror, and that distinction, "this is a point-in-time record, not a cache," is the right reason to duplicate a value). Denormalize only a specific, named, read-hot, write-cold field, and only after the join cost is measured, not assumed. Cost of denormalizing: every future write path that touches the underlying fact must remember to also update the cached copy, or a cron/trigger must do it; forgetting is a silent, undetectable data-drift bug, exactly Solen's #1 documented failure class in a different guise (a stale cache doesn't throw an error, it just quietly shows the wrong number).

Sources: Wikipedia, Database normalization, ClickHouse engineering blog, when to denormalize.

3. Primary key strategy: UUIDv4 vs UUIDv7 vs ULID vs bigint identity

The question. What should a new table's primary key be: a random UUID (v4), a time-ordered UUID (v7), a ULID, or a plain auto-incrementing bigint.

What the evidence says, precisely.

  • UUIDv4 is defined by RFC 9562 (T1, published May 2024, explicitly obsoletes RFC 4122) as 122 bits of random data plus fixed version/variant bits. RFC 9562 itself states implementations "SHOULD NOT assume that UUIDs are hard to guess... MUST NOT be used as security capabilities," i.e. even the spec that defines UUIDs says don't rely on their unguessability for access control, that has to be enforced separately (authorization checks), a point OWASP's API Security Top 10 makes independently below.
  • UUIDv7 is defined in the same RFC: the top 48 bits are a Unix millisecond timestamp, followed by a version nibble, then pseudorandom bits, arranged so that "implementations that require sorting... sort as opaque raw bytes without the need for parsing" (T1). The RFC explicitly recommends: "Implementations SHOULD utilize UUIDv7 instead of UUIDv1 and UUIDv6 if possible."
  • ULID (the canonical spec, CONV, a community spec, not an RFC) is a 128-bit identifier: 48-bit millisecond timestamp + 80 bits of randomness, Crockford Base32-encoded to a 26-character string (vs UUID's 36-character hex-with-dashes form), same "sorts by creation time" property as UUIDv7, and is monotonic within the same millisecond. Functionally ULID and UUIDv7 are now near-equivalent (same information content, same sortability), the practical difference is encoding (Base32 26 chars vs UUID's hex format) and library maturity, not correctness.
  • Bigint identity (GENERATED ALWAYS AS IDENTITY, Postgres's modern replacement for SERIAL): 8 bytes, monotonically increasing per a database sequence, smallest and fastest to index, but only meaningful within a single database (it doesn't survive a merge of two systems without a remap) and directly exposes creation order and row count to anyone who can see one value.

The B-tree mechanic behind the performance claims (this is the actual "why", not folklore). A B-tree index physically stores its entries in key order. When new rows insert with a monotonically increasing key (bigint identity, or a time-ordered UUIDv7/ULID), each new entry appends to the rightmost edge of the tree, a cheap, cache-friendly operation. When new rows insert with a uniformly random key (UUIDv4), each insert lands at a random point in the tree's existing key range, which is very likely to be a full or nearly-full page, forcing a page split, this is the actual mechanical reason UUIDv4 costs more at scale, not a vague "UUIDs are bigger" complaint. Independent benchmarks converge on the direction and rough magnitude (T3, single-source numbers, verify on our own data before trusting the exact figure): one published benchmark reports a 50-million-row bulk insert completing in about 1.8 minutes with UUIDv7 vs about 20 minutes with UUIDv4, with the UUIDv7 index roughly 25% smaller; a separate source describes UUIDv4 index leaf pages as "approximately 40% larger... for the same logical number of rows" than bigint, due to worse data locality (QueryPlane, UUID vs Integer IDs in Postgres, Andy Atkinson, Avoid UUIDv4 Primary Keys). Storage itself is also just bigger: a UUID is 16 bytes vs bigint's 8 (Cybertec, int4 vs int8 vs uuid vs numeric).

Enumeration exposure. OWASP's API Security Top 10, API1:2023 (T1, the current, verified-current edition, not a stale memory of an older year) names "Broken Object Level Authorization" as the #1 API risk: an attacker manipulating an object ID in a request to reach a resource they don't own, and calls out sequential integer IDs by name as making that enumeration trivial ("If the userIds are sequential, the attacker can simply enumerate... /users/1001 exposes /users/1002"). OWASP's own listed mitigation is "prefer the use of random and unpredictable values as GUIDs," but OWASP is explicit this is a supplementary hardening, not a substitute for "implement a proper authorization mechanism... check if the logged-in user has access... in every function" (OWASP API1:2023). This matters directly for the UUIDv4-vs-v7 choice: a v7 UUID's leading 48 bits are a plaintext creation timestamp, so it leaks *when* a row was created (and lets an attacker infer roughly how many rows exist between two timestamps) even though the trailing random bits are still unguessable. A bigint identity leaks both count and order. A UUIDv4 leaks neither. None of the three replace an authorization check.

Solen's actual situation (verified this run). Solen runs Postgres 17.6.1 (confirmed via Supabase MCP), not 18, so Postgres's new built-in uuidv7() function (T1, shipped in PG18, not available to us) is not usable without either an extension (e.g. pg_uuidv7) or generating v7 UUIDs in application code before insert. Every existing table uses id uuid DEFAULT gen_random_uuid() PRIMARY KEY (UUIDv4). Our largest table, availability_slots, sits around 9,400 rows. At that row count, the entire index fits in a handful of database pages held in RAM; the "page split under a full page" cost the benchmarks above describe simply does not bite yet, that cost is a function of index size relative to cache, not of UUID version in isolation.

Recommended default and cost. Keep UUIDv4 (gen_random_uuid()) for new tables today; it is simpler (built into Postgres core since v13, no extension, no app-side generation code), avoids leaking creation time/order, and its downside (worse index locality) is invisible at our row counts. Cost of switching to v7/ULID now: added complexity (an extension or app-side generation, a library dependency, a second ID format to reason about) for a performance benefit that doesn't exist yet at 9,400 rows. The concrete trigger to revisit: any single table's row count crossing roughly the point where its primary-key index no longer comfortably fits in the Postgres shared-buffer cache (a few million rows for a typical small Supabase instance is a reasonable order-of-magnitude alarm, this should be measured against Solen's actual instance size when it becomes relevant, not assumed), or specifically availability_slots/bookings growing two to three orders of magnitude from where they are today.

4. Indexing: B-tree, GIN, GiST, BRIN, partial, composite, covering

The question. Which index type for which access pattern, and how to order/shape a composite index.

What the evidence says (all T1, official Postgres docs, indexes-types.html):

  • B-tree (the default) handles equality, ranges, BETWEEN, IN, IS NULL, and left-anchored LIKE 'foo%', and can also return rows in sorted order. This should be the default choice unless the access pattern is specifically one of the below.
  • GIN (Generalized Inverted Index) is for columns holding *multiple* component values per row: arrays, jsonb, full-text search vectors. It builds one index entry per component value, so @> (contains), ? (key exists), and array-overlap queries can use it directly.
  • GiST (Generalized Search Tree) is a general framework, most commonly used in Solen's stack for geometric/range types and, critically, as the backing index for exclusion constraints (see section 10, our own double-booking guard uses EXCLUDE USING gist).
  • BRIN (Block Range Index) stores only a min/max summary per physical block range, and is only effective when the indexed column's values correlate with the table's physical row order (the textbook case is a created_at column on an append-only, rarely-updated, very large table). It is dramatically smaller and cheaper to maintain than a B-tree, but only wins when that correlation holds.
  • Composite (multicolumn) index column order (indexes-multicolumn.html): "equality constraints on leading columns, plus any inequality constraint on the first column without an equality constraint, will always be used to limit the portion of the index scanned. Constraints on columns to the right... are checked in the index... but do not necessarily reduce the portion... scanned." In plain terms: put the column(s) you always filter on with = first; a query that only filters on a trailing column gets much less benefit (recent Postgres versions can sometimes "skip scan" here, but the docs are explicit this only helps when the leading column has few distinct values). Postgres's own docs also warn against multicolumn indexes wider than about three columns "unless usage is extremely stylized."
  • Partial indexes (indexes-partial.html) index only the rows matching a WHERE predicate, useful specifically to avoid indexing a common value a query would never need the index for anyway (e.g. indexing only WHERE status = 'pending' rows when 95% of rows are 'completed' and nobody queries those).
  • Covering indexes (INCLUDE), available since Postgres 11, add extra payload columns to an index without making them part of the sort key, letting a query be answered entirely from the index (an "index-only scan") without visiting the table. The docs' caveat, easy to get backwards: an INCLUDE column can never be used to filter or sort, only key columns can, so a column you filter or ORDER BY on must be a real key column, not an INCLUDE column.

Solen's actual index usage (verified this run): 3 GIN indexes (a jsonb preferences column, one tsvector full-text column, one text[] languages column), exactly one GiST (the double-booking exclusion constraint), zero BRIN, 16 partial indexes already in use. This shape is correct for our scale and access patterns: GIN is being reserved for genuinely multi-valued columns (right call), BRIN's absence is also correct (we have no huge append-only time-series table yet that would benefit).

Recommended default and cost. Default to a plain B-tree on any foreign key and any column used in a WHERE/JOIN/ORDER BY. Reach for GIN specifically when the column is an array, jsonb, or full-text search target, never as a general "make it fast" reflex, a GIN index is more expensive to maintain on write than a B-tree. Reach for a partial index when a status-like column has a small "active" subset and a large "resolved/dead" majority (Solen already has 16 of exactly this pattern, e.g. limiting a unique index to non-cancelled bookings). Do not reach for BRIN until there is an append-heavy, naturally-time-ordered table in the tens-of-millions-of-rows range, that trigger has not arrived. Cost of over-indexing: every index adds write overhead (every INSERT/UPDATE must maintain every index on the changed columns) and storage; the common mistake at Solen's scale is not too few indexes, it's not measuring which composite index's column order actually matches the query's WHERE clause.

5. Enums: native Postgres ENUM vs CHECK constraint vs lookup table

The question. How should a fixed, small set of allowed values (a booking's status, a review's severity) be represented and enforced.

What the evidence says (T1, Postgres enum docs): a native ENUM type is a static, ordered set of labels, 4 bytes on disk, comparable and sortable by declared order, type-safe (two different enum types cannot be compared without an explicit cast). Its documented, sharp limitation: "existing values cannot be removed from an enum type, nor can the sort ordering... be changed, short of dropping and re-creating the type," and the widely-hit operational gotcha (T1, confirmed independently across the Postgres mailing list and multiple ORM issue trackers, e.g. flyway#350, prisma#5290) is that ALTER TYPE ... ADD VALUE cannot run inside a transaction block, and even when run standalone, the new value cannot be used in the same transaction that added it. Most migration frameworks wrap every migration in a transaction by default, so adding one new enum value routinely breaks a migration tool unless that specific migration is special-cased to run non-transactionally. A CHECK (col IN (...)) constraint has none of this: adding a new allowed value is a normal ALTER TABLE ... DROP CONSTRAINT ... ADD CONSTRAINT (which can be done as NOT VALID then VALIDATE CONSTRAINT to avoid a long table lock), runs fine inside a transaction, and rolls back cleanly if the migration fails. A lookup table (a separate status_types table with a foreign key from the main table) adds the most flexibility (values can carry metadata: a display label, a sort order, a color) at the cost of a join for something that is usually static and small enough not to need one.

Where the tradeoff lies. Native ENUM wins on storage size (4 bytes flat) and on getting free ordering/comparison operators for cheap; it loses on migration friction the moment product requirements add a new status, which for a fast-moving product like Solen (new booking states, new dispute states, new moderation states have all shipped over the life of this codebase) is often, not rare. CHECK constraints give up almost nothing at Solen's data volumes (the storage difference between a text column with 10-20 distinct short values and a 4-byte enum is not a measurable cost at 146 tables' worth of data) and buy back the ability to add a value inside a normal, transactional, rollback-safe migration.

Solen's actual practice (verified this run): zero native Postgres ENUM types anywhere in 264 migration files, and 233 CHECK (col IN (...)) constraints. This is not an accidental gap, it is a completely consistent pattern across the entire codebase's life, and it is the right call given how often Solen's product surface adds a new status value. This is worth locking in as explicit law rather than leaving as an unstated habit: the next session that reaches for CREATE TYPE ... AS ENUM should be told no.

Recommended default and cost. text + CHECK (col IN (...)) for any fixed small set of values, matching the existing 233-instance convention. Reach for a lookup table only when a status genuinely needs to carry its own data (a color, a sort order, a longer description used in three places), not just an allowed-value list. Never reach for a native ENUM given how often Solen's statuses grow a new value and how badly that interacts with transactional migrations.

6. JSON/JSONB columns: when they're right, when they're a schema you refused to write

The question. When is a jsonb column the correct tool, and when is it hiding an under-designed schema.

What the evidence says (T1, Postgres JSON types docs): jsonb stores a decomposed binary representation (no whitespace, no preserved key order, duplicate keys collapse to the last value) that is slower to write but much faster to query than json (which stores an exact text copy and must be re-parsed on every access); the docs state plainly "most applications should prefer... jsonb, unless there are quite specialized needs, such as legacy assumptions about ordering of object keys." jsonb is fully indexable: the default GIN operator class (jsonb_ops) supports key-existence (?, ?|, ?&) and containment (@>) queries by indexing every key and value; the alternative jsonb_path_ops operator class indexes only values (not keys), producing a smaller, more specific index at the cost of losing key-existence queries. The docs are explicit about the actual scope question: "even for applications where maximal flexibility is desired, it is still recommended that JSON documents have a somewhat fixed structure," and that each JSON document should represent "an atomic datum" the business rules say cannot be usefully subdivided into independently-modifiable pieces. There is also a documented concurrency cost: "any update acquires a row-level lock on the whole row," so a large, frequently-updated JSON blob becomes a lock-contention hazard in a way that separate narrow columns would not.

Where the tradeoff actually lies. The Postgres docs' own "atomic datum" framing is the sharpest test available: if the pieces inside the JSON blob are ever going to be independently queried, filtered, foreign-keyed, or updated one at a time by different code paths, that is relational data wearing a JSON costume, and belongs in real columns/tables where constraints, indexes, and foreign keys can do their job. If the shape is genuinely one unit that only ever moves as a whole (a wizard's in-progress draft state, a third-party webhook payload kept for audit, a set of intake-form answers whose question set varies by service category), jsonb is the right, not lazy, choice.

Solen's actual usage. 92 migration files touch jsonb. Spot examples from _rules/DB_SCHEMA.md land on both sides of the line correctly: salons.opening_hours (a fixed small nested shape, {mon: {open, close}, ...}, queried as a whole by the "is this salon open now" logic, reasonable as JSON, though its own short-day-key convention mismatch is a separately-documented footgun); salon_drafts.draft_data (wizard-in-progress state, genuinely one atomic unit until it becomes a real salon row, textbook correct use); intake_forms.responses (question sets vary by category, genuinely schema-less per the product's own design, correct use). None of the found usages look like relational data hiding in JSON to avoid a migration, which is the failure mode this sub-topic exists to guard against; that discipline should be named explicitly so a future session doesn't quietly start reaching for jsonb as a way to skip writing a migration.

Recommended default and cost. Use jsonb (never plain json) when the data is genuinely one atomic, whole-unit blob that isn't independently queried piece-by-piece. Index it with GIN (jsonb_ops if key-existence queries matter, jsonb_path_ops if only containment queries do, for a smaller index). Cost of misusing jsonb for what should be columns: you lose NOT NULL/CHECK/FK enforcement on the individual fields (Postgres cannot enforce "this nested field is required" the way it enforces a real column), lose the ability to index or join on a specific nested field without an expression index, and every read of that field has to know and parse the JSON shape in application code instead of the database enforcing it.

7. Money storage: integer minor units, never float

The question. What column type and unit should a monetary amount be stored in.

What the evidence says. Stripe's own documentation (T1, this is the API contract our Stripe Connect integration is bound to, not an opinion) states all amounts are integers in "the smallest unit of the currency without decimals": for two-decimal currencies (CHF, EUR, USD), multiply the human amount by 100 (1000 = CHF 10.00, 1099 = CHF 10.99); zero-decimal currencies (JPY, KRW) use the value as-is (Stripe, Supported currencies). Postgres's own docs (T1, datatype-numeric.html) directly recommend: "for exact storage and calculations (such as for monetary amounts), use the numeric type instead" of floating point, because floating point is an approximate binary representation and cannot exactly represent most decimal fractions, silently losing or gaining fractions of a cent over repeated arithmetic. Postgres's money type exists but is not the recommended path: it is locale-dependent in its output formatting and rounding behavior, which makes it a portability and correctness hazard across environments, the practical community consensus (T2/T3, converging, no single canonical source directly warns against it as strongly as the framing here implies, softened accordingly) is to avoid it in favor of numeric(precision, scale) paired with an explicit currency column, or (the stricter version, matching Stripe's own convention) an integer column in minor units. Martin Fowler's Money pattern (T2, a named, long-standing design pattern, martinfowler.com/eaaCatalog/money.html) frames the underlying problem as a language-design gap: "none of the mainstream base class libraries provide native money types," so an amount and its currency need to travel together as one unit with currency-aware arithmetic (adding two Money values of different currencies should be a hard error, not a silent wrong number), whether that unit lives at the database row level (an amount_minor column plus a currency column) or the application object level.

Where the tradeoff actually lies. numeric(10,2) and "integer minor units" both avoid floating point's silent rounding error, so the sharper practical choice is integer-minor-units vs numeric with decimals, and the deciding factor is: does this amount ever have to round-trip through Stripe's API. Any amount that becomes a PaymentIntent, a Charge, a Connect transfer, or a refund has to be an integer in minor units at the API boundary regardless of how it's stored, so storing it as integer minor units in Postgres too means zero conversion code and zero chance of an off-by-a-factor-of-100 bug at the boundary. An amount that never touches Stripe directly (a display-only aggregate, a historical decimal price snapshot) can reasonably use numeric(10,2) if that is more convenient to read in SQL, but consistency across the codebase is worth more than either choice in isolation.

Solen's actual situation (verified this run, and this is a genuine finding, not a hypothetical). The codebase is currently split: services.price, bookings.price_paid, and salon_payouts.gross_amount/commission_amount/net_amount (the older, foundational tables, 014_new_schema.sql and 055_platform_commission.sql) are numeric(8,2)/numeric(10,2), decimal CHF amounts. Newer tables (tips.amount, and the refund-appeal event log added in 20260601_refund_appeal_foundation.sql, both with an explicit -- Rappen comment) are plain integer storing Swiss Rappen, matching Stripe's minor-unit convention directly. This means any code path that touches both an old-style and a new-style money column in the same calculation has to know which convention applies to which column, or it will be off by a factor of 100, exactly the kind of silent numeric bug this codebase's own "no fabricated data" and "silent no-op" failure modes warn about, except here the risk is a silent *wrong* number rather than a missing one.

Recommended default and cost. Every new money column is integer, storing the currency's minor unit, named with an explicit unit-bearing suffix or comment (the existing -- Rappen comment convention is good, keep it) rather than a bare amount. Never introduce another numeric(x,2) money column going forward. Do not attempt to silently migrate the legacy numeric(8,2) columns as a side effect of unrelated work, that is a real, scoped, single-purpose migration (touching every read site that assumes decimal CHF) and should be its own tracked task, not something a future session guesses is safe to do inline. Cost of leaving the split as-is: every new feature that reads both an old and new money column must be told, explicitly, which convention each one uses; this is exactly the kind of fact that belongs in _rules/DB_SCHEMA.md's per-table notes and should be added there if it isn't already.

8. Timestamps: timestamptz vs timestamp, always UTC, and the recurring-local-time nuance

The question. What timestamp type to use, and how to handle "this recurs at 9am local time" correctly across a DST transition.

What the evidence says (T1, Postgres datatype-datetime.html): timestamp (without time zone) stores exactly the value given, with no conversion, and carries no information about which zone it was meant in. timestamptz stores every value internally as UTC, converting from the session's TimeZone setting on input (if the input string doesn't specify one) and converting back to the session's TimeZone on output. The documentation is explicit about the deeper trap this creates for anything involving a timezone abbreviation rather than a full IANA name: "the difference between abbreviations and full names: abbreviations represent a specific offset from UTC, whereas many of the full names imply a local daylight-savings time rule, and so have two possible UTC offsets" (i.e. EST always means UTC-5, but America/New_York means UTC-5 or UTC-4 depending on the date). Critically, the docs do not provide any mechanism to store a timezone name alongside a single instant for future recurrence purposes, timestamptz fixes a moment in time (one absolute instant, unambiguous forever), it deliberately throws away "what wall-clock time did the person who created this mean." That means a *recurring* local event (a salon's Tuesday 9am slot, every week, forever) cannot be correctly represented as a single stored timestamptz plus "just add 7 days" arithmetic across a DST boundary, doing that silently shifts the wall-clock time by an hour twice a year. The correct pattern (T2, this is the well-understood general recurrence pattern, not something the Postgres docs themselves spell out) is to store the recurrence rule in local wall-clock terms plus an explicit IANA zone name (day_of_week, local_time, timezone: 'Europe/Zurich') and materialize each concrete occurrence into a timestamptz only when generating the actual bookable slot, at which point Postgres/the IANA database correctly resolves the local time to the right UTC instant for that specific date.

Solen's actual situation. services, staff_breaks, staff_time_off, recurring_rules, and off_peak_slots (per _rules/DB_SCHEMA.md) already store day_of_week + start_time/end_time as local wall-clock fields, not a timestamptz with naive weekly arithmetic, that is the correct pattern already in place. availability_slots.starts_at/ends_at (the materialized, concrete, bookable instant) is where the conversion to an absolute moment should happen, and per the migration grep, timestamptz is overwhelmingly the dominant type used (158 occurrences vs 3 for bare timestamp), which is the right ratio.

Recommended default and cost. timestamptz for every column that represents a specific instant (a booking's actual start time, a row's created_at/updated_at, a payment's processed time). Never bare timestamp. For anything that repeats on a local wall-clock schedule, store the recurrence as local time + an explicit zone name, and only produce a timestamptz at the point a concrete occurrence is generated (which Solen already does correctly for opening hours and staff schedules). Cost of getting this wrong: a bug that only manifests twice a year, at the DST transition, affecting exactly the bookings/slots near the boundary, which is close to the worst possible bug shape (rare, narrow window, easy to ship without noticing, expensive to diagnose after the fact because it "was fine yesterday").

9. Soft vs hard delete, and what it does to unique constraints, RLS, and GDPR erasure

The question. Should a "deleted" row actually be removed, or flagged and kept.

What the evidence says. The recurring, well-converged (T2/T3, several independent write-ups land on the identical failure mode) practical problem with the classic "soft delete = add a deleted_at column, filter it out everywhere" pattern is that a unique constraint doesn't know about the flag: if users.email has a plain UNIQUE constraint and a user "deletes" their account by setting deleted_at, the row still occupies that email in the unique index, so the same person can never sign up again with that email, a real, commonly-hit bug, not a hypothetical. The documented fix (T2) is a partial unique index scoped to only the live rows: CREATE UNIQUE INDEX ON users (email) WHERE deleted_at IS NULL, which is exactly the partial-index mechanism from section 4, applied to this specific problem. RLS interacts with soft delete the same way any other filter does: if "deleted" rows should become invisible, that has to be encoded as part of the RLS policy's USING clause (or a WHERE on every read), or a soft-deleted row is still fully visible to anyone the policy would otherwise allow, silently reintroducing exactly the "looks gone but isn't" bug this pattern is meant to avoid in the first place. On GDPR specifically: Article 17 (T1, official text, gdpr-info.eu/art-17-gdpr) requires erasure "without undue delay" once a qualifying ground applies (data no longer necessary, consent withdrawn, unlawful processing, etc.), but explicitly carves out exceptions where processing is necessary "for the establishment, exercise or defence of legal claims" or to comply with a separate legal obligation, this is exactly why a payments/booking history often has to be *anonymized* (identity stripped, financial facts kept) rather than *deleted outright*, satisfying both the erasure right and a retention obligation (in Solen's case, Swiss OR Art. 958f bookkeeping retention, referenced directly in the codebase's own migration comments). A flag like deleted_at or is_active = false is, on its own, neither of these things: it doesn't satisfy Article 17 (the data is still fully present and re-identifiable) and it isn't a bookkeeping-safe anonymization either, it's a *product* soft-delete (hide from the UI, allow undo), a different concern that happens to look similar.

Solen's actual situation (verified this run). Zero deleted_at columns exist anywhere in Solen's 264 migrations. What Solen actually has instead is a set of status/flag columns doing three genuinely different jobs that are easy to conflate: (1) visibility toggles (salons.is_active, services.is_active, staff_members.is_active) which are product soft-delete, hide without erasing, exactly the pattern above; (2) moderation state (profiles.account_status, profiles.banned_at) which is a trust-and-safety flag, not a delete of any kind; (3) a genuinely separate, purpose-built GDPR erasure pipeline (data_deletion_log, and the dedicated migrations 20260602083300_financial_retention_on_delete.sql and 20260713150000_gdpr_deletion_completeness.sql) which does the anonymize-not-delete dance specifically for the legally-retained financial rows. This is the right shape: Solen did not try to make one is_active-style flag do all three jobs, it built the erasure path as its own system. The auditable question is whether every table holding personal data is actually wired into that erasure pipeline, not whether a generic deleted_at pattern exists (it correctly doesn't need to).

Recommended default and cost. Use a purpose-named flag or status column for product-level soft delete (is_active, a status value), never a generic deleted_at that tries to also mean "gone for privacy purposes." If a table has a uniqueness requirement that a soft-deleted row would otherwise block, scope the unique constraint with a partial index (WHERE is_active/WHERE deleted_at IS NULL) rather than leaving it unscoped and hitting the "can't reuse this email" bug. Treat true GDPR/nFADP erasure as its own explicit, tested pipeline (as Solen already has), never as an accidental side effect of a product soft-delete flag. Cost: three different concepts (hide-from-UI, trust-and-safety strike, legal erasure) sharing a naming pattern (all look like "a column that means this row is kind of gone") is a real confusion risk for a future session, the fix is naming and documentation discipline, not a schema change, name each column for exactly what job it does.

10. Constraints as the source of truth

The question. Where should an invariant (uniqueness, a valid range, a required relationship) actually be enforced.

What the evidence says (T1, Postgres ddl-constraints.html): NOT NULL is documented as more efficient than the equivalent CHECK (col IS NOT NULL) and should always be the first choice for "this must be present." CHECK enforces a boolean expression per-row (and can span multiple columns in the same row, but explicitly "cannot reference table data other than the new/updated row", cross-row rules need something else). UNIQUE by default treats NULLs as distinct from each other (multiple NULLs are allowed unless NULLS NOT DISTINCT is specified), and automatically creates a backing B-tree index. PRIMARY KEY is UNIQUE + NOT NULL combined, at most one per table, and is the default target for foreign keys referencing that table. FOREIGN KEY enforces that a column's value must exist in the referenced table (with ON DELETE/ON UPDATE behaviors: CASCADE, RESTRICT, SET NULL, SET DEFAULT, NO ACTION), and by default a referencing row with any NULL column "escapes" the check entirely (unless MATCH FULL is used, in which case all-or-nothing). Exclusion constraints are the tool for the class of invariant a simple UNIQUE cannot express: "if any two rows are compared on these columns/expressions with these operators, at least one comparison must be false," which is exactly the shape of "no two bookings for the same staff member may have overlapping time ranges," a pairwise, range-based rule, not a flat equality rule.

Why this matters more than it sounds like: constraints are enforced under concurrency, application code is not. A CHECK or UNIQUE constraint is evaluated by Postgres at the moment of the write, atomically, regardless of how many concurrent requests are racing each other. An equivalent check written in application code ("first SELECT to see if a slot is free, then INSERT the booking if it is") has a race window between the SELECT and the INSERT where a second concurrent request can pass the same check before the first one commits, this is precisely a Time-of-Check-to-Time-of-Use (TOCTOU) bug, and it is exactly the class of bug Solen's own booking system has already hit and fixed at the database layer, not the application layer.

Solen's actual situation, and this is the single best worked example in the whole codebase for this rule. _docs/BACKEND.md documents the exact sequence: prevent_double_booking (20260328_prevent_double_booking_gist.sql) is a GiST exclusion constraint, EXCLUDE USING gist (staff_member_id WITH =, tstzrange(starts_at, ends_at) WITH &&) WHERE (status IN ('booked','blocked')), mathematically preventing two overlapping booked/blocked ranges for the same staff member, a case application-level "check then write" code cannot correctly guarantee under concurrency. Even that wasn't the whole story: a second gap remained (two different bookings could still both reference the same slot_id, since bookings.slot_id had no uniqueness constraint of its own), closed later by bookings_one_active_per_slot, a partial unique index on bookings(slot_id) scoped to only live, non-cancelled, non-group bookings. This is constraints-as-source-of-truth done correctly, twice, on the same feature: first the range-overlap invariant (exclusion constraint), then the same-slot-twice invariant (partial unique index), neither expressible or safely enforceable as an application-level "check first" pattern.

Recommended default and cost. Every invariant that must always hold gets a real constraint: NOT NULL for required fields, CHECK for a per-row rule, UNIQUE/partial-unique for a uniqueness rule (scoped with a WHERE clause whenever "unique among live rows only" is the actual intent, per section 9), FOREIGN KEY for every reference between tables, and an exclusion constraint for any pairwise/range-overlap rule a flat UNIQUE can't express. Application-level validation is a good UX nicety (fail fast with a friendly message before even hitting the database) but is never the enforcement, and should never be trusted as the only check. Cost: constraints do add a small amount of write-time overhead (checking NOT NULL/CHECK is cheap; enforcing UNIQUE/FOREIGN KEY/exclusion constraints costs an index lookup per write), which is a correct and necessary cost, the actual risk to watch for is the opposite direction, a missing constraint that lets a bad row exist for however long it takes someone to notice.

11. Multi-tenancy models: shared table + tenant_id vs schema-per-tenant vs database-per-tenant

The question. How should each salon's data be isolated from every other salon's data.

What the evidence says (T2/CONV, Wikipedia, Multitenancy, converged with Supabase's own multi-tenant guidance). Three named models, in increasing order of isolation and decreasing order of density/cost-efficiency: (1) shared database, shared schema, every tenant's rows live in the same tables, distinguished by a tenant-identifying column, isolation is enforced entirely at the application (or database policy) layer, cheapest and highest-density, but "most demanding to secure" because a single missing filter leaks across every tenant at once; (2) shared database, separate schemas, each tenant gets its own namespace of tables inside one database, moderate isolation, moderate cost, but the schema count grows linearly with tenant count, and cross-tenant queries (a platform-wide admin report) become harder, not easier; (3) separate databases per tenant, strongest isolation, simplest per-tenant backup/restore, but highest cost and lowest density, and now every schema migration has to run N times instead of once.

Where the tradeoff actually lies. The deciding factors are tenant count, per-tenant data volume, and how often the platform needs a cross-tenant query. At a handful of tenants each with enormous, sensitive, differently-shaped data (think: enterprise SaaS with a handful of Fortune 500 customers), schema-per-tenant or database-per-tenant earns its cost, because isolation and independent scaling matter more than density, and cross-tenant reporting is rare or nonexistent. At many small, structurally-identical tenants where the platform itself needs constant cross-tenant visibility (search, discovery, admin analytics, trending scores, exactly Solen's shape), shared-schema is not just cheaper, it is functionally necessary: v_trending_salons, the homepage search/discovery surface, and platform-wide admin dashboards all need to query across every salon in a single statement, which schema-per-tenant or database-per-tenant would turn into N separate queries fanned out and merged in application code, strictly worse, not better.

Solen's actual situation. Every one of Solen's 146 tables is a single shared table with a salon_id (or owner_id) column identifying the tenant, isolation enforced by RLS policies referencing that column (e.g. the slots_manage_owner policy: EXISTS (SELECT 1 FROM salons s WHERE s.id = salon_id AND s.owner_id = auth.uid())). This is the shared-database-shared-schema model, and given ~28 salons that need to appear together in search results, homepage rankings, and cross-salon discovery feeds, it is the correct model, not a shortcut. The real risk this model carries, named explicitly by the sources and directly true of Solen (per section 12 below): every single query and every single RLS policy is now a place a missing or wrong tenant filter can leak one salon's data into another's view, there is no structural database-level wall doing that job for free the way a separate schema or database would.

Recommended default and cost. Stay on shared-table + tenant column + RLS. This is not premature or a compromise at 28 tenants, it is the right architecture for a many-small-similar-tenants marketplace that needs cross-tenant queries as a core product feature (search, discovery, ranking). The cost is entirely pushed onto RLS policy correctness (section 12) and query discipline, there is no free isolation here, every table needs its own correct policy, and that surface only grows as tables are added. The trigger that would change this recommendation: a single tenant becoming so large, so differently-shaped, or so contractually isolated (a big enterprise chain wanting its own dedicated infrastructure, a legal requirement to physically segregate one customer's data) that it stops looking like "one more salon" and starts looking like its own dedicated deployment, at which point that one tenant, not the whole platform, would be the candidate for schema or database separation.

12. Row Level Security

The question. How RLS actually works, what it guarantees, and its concrete failure modes.

What the evidence says (T1, Postgres ddl-rowsecurity.html and sql-createpolicy.html): ALTER TABLE ... ENABLE ROW LEVEL SECURITY switches a table to default-deny, no policy means no rows visible or writable to a normal role. FORCE ROW LEVEL SECURITY additionally binds the table owner to the same policies (by default, a table's owner bypasses RLS entirely, a fact worth stating plainly because it's easy to assume RLS applies to everyone). Superusers and any role with the BYPASSRLS attribute always bypass RLS, this is exactly Supabase's service_role. A policy's USING clause governs which existing rows are visible/eligible for SELECT/UPDATE/DELETE; WITH CHECK governs which new/modified rows are allowed through INSERT/UPDATE; specifying only USING applies it to both. Multiple permissive policies (the default kind) combine with OR, any one of them granting access is enough; restrictive policies combine with AND, any one of them denying is enough, this distinction matters because stacking restrictive policies is how you build a hard, non-overridable floor (e.g. "admins may only act from a specific network"). The docs also flag a genuine, non-obvious hazard: unique/primary-key/foreign-key constraint checks bypass row security entirely to preserve referential integrity, which the docs warn "can leak information through constraint violations" (a user might learn a row exists, via a unique-constraint error, that RLS would otherwise have hidden from them). And a subtler one: a policy expression containing a sub-SELECT (checking a caller's privilege level via a join to another table) runs against that sub-SELECT's own transaction snapshot; under READ COMMITTED, a concurrent privilege change might not be seen consistently, the documented fixes are SELECT ... FOR SHARE in the sub-select, an ACCESS EXCLUSIVE lock on the referenced table, or wrapping the check in a SECURITY DEFINER function.

Supabase's own performance-specific guidance (T2, Supabase's official docs, one strong source, verified this run, supabase.com/docs/guides/database/postgres/row-level-security): wrap auth.uid() (and any other per-row function call) in a sub-select, (select auth.uid()) = user_id rather than a bare auth.uid() = user_id, so Postgres's query planner can run it once per statement as an initPlan instead of once per row; Supabase's own benchmark reports roughly a 95% improvement for a simple policy and over 99% for a complex one from this rewrite alone. Separately, indexing any column referenced in a policy's condition (the tenant/owner column, typically) produced a reported 99.94% improvement in their benchmark; and for policies whose logic requires a join to another table for an authorization check, wrapping that logic in a SECURITY DEFINER function (rather than embedding the join directly in the policy) reportedly recovers up to another 99.99%. These are single-source (Supabase's own) benchmark numbers, the direction (sub-select the function, index the filtered column, avoid inline joins in hot policies) is directionally trustworthy as it follows directly from how Postgres's planner works, but the exact percentages are Supabase's own measurement on their own test data and should be treated as a T3 magnitude, verify on Solen's own tables before quoting an exact number to the founder.

Solen's actual situation, verified this run and via _docs/BACKEND.md section 2. All 146/146 tables have RLS enabled (_inventory/_db-snapshot.json, rlsDisabled: []), so the "enable it everywhere, no exceptions" part of the law is already fully met. Where Solen genuinely struggles, and this is documented as the single most-repeated bug class in the whole backend (multiple audit files cite multiple instances), is exactly the "RLS silently matches zero rows and looks identical to success" failure mode: availability_slots has a write policy (slots_manage_owner) that only the salon owner satisfies, so a *customer's* own session client attempting to claim or free a slot matches zero rows under RLS and PostgREST returns a normal 200 with an empty result, not an error, code that only checks error (not the returned row count) believes the write succeeded when it silently did nothing. The documented, correct fix pattern already exists in the codebase (lib/bookings/claim-slot.ts's claimSlot() helper, which routes through the service-role client and checks the affected-row count), but per _docs/BACKEND.md's own audit, it is not yet wired into every call site that needs it (the main booking-creation route's inline slot claim and its own rollback deletes are named as still using the session client in at least three places as of this writing). Whether every RLS policy also uses the (select auth.uid()) sub-select wrapping Supabase recommends was not directly verified this run (see Unverified), it is worth a dedicated grep pass.

Recommended default and cost. Keep RLS enabled on every table with no exceptions (already true). Every policy that calls auth.uid() or any other per-row function should wrap it in a sub-select. Every column an RLS policy filters on (typically owner_id/salon_id) should be indexed. Any write that matters for correctness or money (a slot claim, a status transition, a refund) must check the actual affected-row count after the write, never just the absence of an error, and must use the service-role client with its own explicit application-level ownership check whenever the RLS-bound session client cannot satisfy the write policy by design (the owner-only slots_manage_owner case). Cost: this is not a "nice to have", it is closing Solen's single most expensive, most-repeated bug class; the cost of doing it right is a small amount of extra code (checking row counts, choosing the right client) at every write site, which is far cheaper than the cost already paid finding and fixing this same bug shape repeatedly across bookings, group bookings, and slot management.

Myths and traps

  • MYTH: "Using UUIDs instead of sequential IDs makes an endpoint secure against enumeration/IDOR." OWASP's own API1:2023 lists unpredictable IDs as one of four mitigations, alongside (not instead of) "implement a proper authorization mechanism... check access in every function." A UUID primary key with no ownership check on the route is exactly as exploitable as a sequential integer with no ownership check, the attacker just can't guess the next ID, they can still use one they already have or one leaked elsewhere.
  • MYTH: "UUIDv7 leaking a millisecond timestamp is a security problem the same way sequential IDs are." It's a smaller, real information leak (approximate creation time, and by extension a rough count of rows created between two known timestamps), but it does not hand an attacker a way to iterate every ID the way a plain sequential integer does. Don't conflate the two risks when deciding between UUIDv4 and v7.
  • TRAP, Solen's stack specifically: PostgREST returns 200 with an empty result for both "genuinely zero rows matched" and "RLS silently blocked the write." This is not a hypothetical for us, it is the documented, repeated root cause behind at least three separate audited bugs in _docs/BACKEND.md (availability_slots slot claims, bookings rollback deletes, and the earlier group_bookings incident it names as precedent). Every write that matters for money or availability must check the affected-row count, never just the absence of an error field.
  • TRAP, serverless + connection-per-invocation: a cold Netlify/Next.js lambda opening a fresh Postgres connection per request is a real cost, but it is Supabase's connection pooler's problem to solve (PgBouncer/Supavisor), not a reason to reach for a different database model. Not directly re-verified against current Supabase pooler docs this run (see Unverified), flagged here because it is a common but usually wrong instinct ("serverless means NoSQL"), the actual fix for connection exhaustion under serverless is pooling configuration, not abandoning the relational model.
  • TRAP: assuming a CHECK constraint change is always instant. Adding a brand-new CHECK to an existing populated table (as opposed to adding a value to an existing IN (...) list) validates every existing row by default and can take a full table lock while doing it; use NOT VALID followed by a separate VALIDATE CONSTRAINT to avoid a long lock on a live table. (This distinction, new-constraint vs new-allowed-value-in-an-existing-constraint, was not separately re-verified against the Postgres ALTER TABLE docs this run, flagged as a T2 general-practice claim, not re-fetched.)
  • TRAP, our stack specifically: two money conventions coexist right now (numeric(8,2) decimal CHF on the legacy tables vs integer Rappen on the newer ones). Any new feature that reads both in the same calculation without checking which convention applies will be off by a factor of 100. This is documented here explicitly so it stops being an implicit trap and becomes a named, flagged fact.
  • MYTH: "Soft delete (a flag) satisfies GDPR erasure requests." A flagged-but-present row is still fully re-identifiable personal data; Article 17 requires it actually be gone (or lawfully anonymized under a stated exception), a flag alone does neither.

Premature at our scale

  • BRIN indexes. Correct once a table is huge, append-only, and naturally time-ordered (think tens of millions of rows of event/audit log). Solen's biggest table today is ~9,400 rows. Trigger to revisit: any single table crossing roughly 10 million rows with a strongly time-correlated access pattern (an audit log, a raw event stream), not before.
  • UUIDv7/ULID migration for existing tables. The random-insert index-locality cost is real but invisible until a table's primary-key index stops fitting comfortably in cache, which requires a table far larger than anything Solen has. Trigger to revisit: a table's row count growing two to three orders of magnitude from today, or Solen upgrading to Postgres 18 (making uuidv7() free to call) combined with an actual measured insert-latency problem, whichever comes first, and even then this is a "new tables only" decision, not a retrofit of existing primary keys (changing an existing PK type is a much bigger, higher-risk migration than choosing one for a new table).
  • Schema-per-tenant or database-per-tenant multi-tenancy. Only earns its cost once a tenant is large/sensitive/contractually-isolated enough that dedicated infrastructure outweighs cross-tenant query convenience. At 28 broadly similar salons that all need to appear in the same search/discovery/ranking surfaces, this would be a straightforward regression, not an upgrade. Trigger to revisit: a single enterprise-scale tenant (a large chain) with its own compliance/isolation requirement, handled as a one-off exception for that tenant, not a platform-wide switch.
  • A dedicated caching layer (Redis-backed read cache) in front of Postgres for salon/search data. Upstash Redis is already present for rate limiting, but a general read-through cache for hot query results is premature until a specific, measured query is shown to be a bottleneck at real traffic, not assumed to be one. Trigger to revisit: a specific, profiled, frequently-hit query that remains slow after correct indexing.
  • Formally versioned/event-sourced money ledgers (append-only ledger tables with no UPDATE, ever). Correct at real financial-services scale and audit requirements; Solen already has the right instinct in places (the refund-appeal event log, the anonymize-not-delete financial retention migration) without needing to formalize a full event-sourcing architecture platform-wide yet. Trigger to revisit: a real external audit/compliance requirement naming this specifically, not a general "more rigor" impulse.
