Backend law layer 2026-07-16

How it was, what changed,
and why it is better.

Ten changes. Each shows the before, the after, and the plain reason it is an improvement.

The one sentence: the backend had rules, but they were suggestions. Now they are walls.
Sixteen backend hooks already existed when you said gates were missing. Ten of them only printed a warning. The audit proves warnings do not work: two separate bugs shipped again while their warning hook was live and watching.

The six gates

Three already existed but only whispered. Three did not exist at all. All six now stop the edit, and all six take an escape hatch (a comment like // cas-ok: reason) for when you genuinely mean it.

Change 1
Charging a card without re-checking the booking
BEFORE

A hook printed: "reminder, this update has no safety check." Then the edit went through anyway.

It did not work. This week's audit found a brand new case in cron/pre-charge: it charges a customer's card without first checking the booking is still valid. The hook warned. The code shipped.

AFTER

The edit is blocked. You cannot write a money update that forgets to confirm it actually changed a row.

If a case genuinely does not need it, you write // cas-ok: single row, no race and it lets you through.

WHY BETTER

The database lies here. If two people book the same slot, one update silently changes nothing and still reports success. Without the check, you charge someone for a booking that no longer exists.

Change 2
Asking the database for a column that does not exist
BEFORE

A warning. Again ignored: this exact mistake came back seven times, including after the warning shipped.

Once it blanked your entire homepage for weeks and nobody noticed, because it throws no error.

AFTER

Blocked, checked against the real live database, not against what the code thinks exists.

Escape: // phantom-ok: just migrated for the case where you added the column five minutes ago.

WHY BETTER

This is the quietest bug you have. Ask for a column that is not there and you get back nothing, not an error. The page just goes empty and everything looks fine.

Change 3
Putting someone's typed text straight into a database filter
BEFORE

A warning, and a badly aimed one. Tested against your real code it flagged 6 out of 6 files, and every one was innocent.

Including the exact file its own message pointed to as the correct way to fix the problem.

AFTER

Blocked, and rebuilt so it can tell cleaned text from raw text. It now fires on zero of those 6 innocent files and still catches the real thing.

WHY BETTER

A gate that keeps flagging correct work gets switched off in frustration, and then nothing is protected at all. Getting the false alarms to zero is what makes it survivable.

Change 4
Reading another salon's data (new gate)
BEFORE

Nothing watched this. Your code has a special database key that skips every security rule, used in 267 places.

Audits found this class of bug in three separate rounds, about 20 routes each time.

AFTER

Blocked on brand new routes: you cannot ship a new page that takes an ID from the visitor and looks it up with the skip-all-security key and no ownership check.

WHY BETTER

This is the most common real-world break-in on the web: change a number in the address bar, see someone else's data. It only guards new routes, deliberately, because guarding every edit wrongly flagged 80 of your 234 existing routes.

Change 5
Photo uploads and deletes across salons (new gate)
BEFORE

Nothing watched this. Four separate audit rounds found storage bugs, including one that let a photo be deleted from a salon that did not own it.

AFTER

Blocked on new routes that write or delete files using the skip-all-security key with no ownership check first.

WHY BETTER

Same break-in as change 4, but with files instead of rows. And storage fails silently too: review-photos returned "success" for months while saving nothing at all.

Change 6
Fake data written straight into the database (new gate)
BEFORE

You already had a gate that blocks made-up numbers, but it only reads page files.

It cannot see a database migration. Which is exactly how the fake wheelchair-access flags got onto your live site.

AFTER

Blocked: a migration cannot invent a value from a hash or a random number and write it into a column customers read.

Tested against all 264 of your real migrations: it fires on exactly one, the guilty one.

WHY BETTER

It closes the door the fake data walked through. It cannot un-write the rows already there, which is why that one is still your decision.

The change I like most, because it deleted a gate

Change 7
Crons reporting a good night when every payment failed
BEFORE

Your nightly jobs could report "all good" on a night every single Stripe charge failed, because they counted failures in a box the reporter never opens.

I built a hook for it. The reviewer then proved my hook was useless: it looked for a shape that never occurs in your code and missed the one that does.

AFTER

Hook deleted. Instead I removed one word from a type definition, so the bad shape is now impossible to even write.

Your build refuses it. Forever. No hook involved.

WHY BETTER

A type error can never misfire. A hook is a guard at a door, guessing. A type is a door that is the wrong shape. And it cost nothing: nothing in your code used the bad form, so removing it broke zero things.

Not knowing whether you follow your own rules
BEFORE

8 of your 15 topics had been checked against the real code. 7 had not, including security, authorization, and reliability.

What that actually turned up

Five things worth your attention, in the order I would fix them.

1. Seven salons claim wheelchair access based on a hash of their ID.
Also eight claiming LGBTQ+ welcome. Live right now, shown as badges and as search filters. Someone filtering for step-free access is getting a coin flip. My recommendation: null the columns today (one database update), add the questions to onboarding next. Do not wait for step two to do step one.
2. A customer can pay salon B's cheaper price at salon A.
The rebooking route never checks the chosen service belongs to that salon. Fix: about 6 lines, copying a pattern you already have working in two other files.
3. The confirmation email has no time limit, and it sits inside the booking.
If the email provider hangs, the customer's booking screen hangs with it, after the booking already saved. They see a failure for something that actually worked. Fix: one line, once we measure how slow the provider really gets.
4. Anyone can run up your AI bill.
The limit on the public AI feature is keyed on a value the visitor can simply make up, and there is no daily ceiling behind it.
5. Guest booking links hand a live 30-day key to PostHog.
The token stays in the address bar after use, and your analytics records full addresses by default.

The part that made all of it trustworthy

Every gate passed the test written by the thing that built it. Then the real code went through, and five of seven failed.
That is why a separate reviewer grades the work and never writes it. One gate wrongly denied 80 of your 234 real routes. One fired on the very file its own error message calls the correct fix. Both looked perfect until they met your actual codebase. The rule that came out of it is now written down: a gate is only finished when the whole real codebase runs through it clean.
