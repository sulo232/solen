Rate limiting & abuse , researched law

Date: 2026-07-16. Sources fetched this run: 20 (listed at the bottom, each with what it established). For: Solen.ch backend engineers (Next.js 15 App Router on Netlify, Supabase Postgres, Stripe Connect, @upstash/ratelimit 2.0.8 + @upstash/redis 1.37.0, ~28 salons, low traffic, serverless/cold-lambda request model).

This file also cross-checked against Solen's OWN live implementation (lib/ratelimit.ts, app/api/auth/signup/route.ts), not just outside docs, because a law file is useless if it contradicts what the codebase already does correctly. Where Solen already matches the researched law, that is stated explicitly so nobody "fixes" a thing that isn't broken.

0. The short version

  1. Sliding window (counter, not log) is the right default for almost every route. It gives smooth-enough burst behavior at roughly the memory cost of fixed window. Solen already does this everywhere via Ratelimit.slidingWindow(...). (T2, Upstash docs + Cloudflare engineering blog)
  2. IP address alone is not an identity. CGNAT, mobile carrier NAT, and corporate NAT put hundreds to thousands of real users behind one IP; Cloudflare measured CGNAT IPs getting rate limited 3x more often than non-CGNAT IPs despite equal bot rates. Key on userId wherever a session exists; IP is a fallback for anonymous/pre-auth routes only. (T2, Cloudflare)
  3. Never lock an account out on repeated failed logins. NIST SP 800-63B-4 (July 2025, current) requires *throttling* (a max of 100 consecutive failures, ideally far lower, with increasing delay) instead of a hard lockout, because a lockout is a denial-of-service an attacker can trigger against a victim they don't even control credentials for. (T1, NIST)
  4. CAPTCHA is a speed bump, not a wall. OWASP's credential-stuffing cheat sheet is explicit that CAPTCHA-solving services defeat it at reasonably high success rates; layer it with device/connection fingerprinting and rate limiting, never rely on it alone. (T1, OWASP)
  5. A rate-limited response is 429, not a bare error. Always include Retry-After (RFC 9110 / RFC 6585) so the client knows when to retry. The newer RateLimit / RateLimit-Policy header pair is still an active IETF draft (draft-ietf-httpapi-ratelimit-headers-11, expires Nov 2026), not an RFC yet, so treat it as forward-looking, not mandatory. (T1 for 429/Retry-After, T2 for the draft's direction)
  6. Fail-open vs fail-closed is a per-route decision, not a global one. Money-moving, brute-force-able, and enumeration-oracle routes must fail closed if the limiter backend is unreachable; everything else should fail open so a Redis outage doesn't take down browsing. Solen already implements exactly this split (ABUSE_PRONE_LIMITERS). (T2, Stripe engineering + Solen's own code)
  7. Quota and throttle are different controls answering different questions. A rate limit shapes traffic (how fast); a quota bounds total consumption (how much, over a day/month). Solen's getAiDailyLimiter() (100/day sliding window) is a quota, correctly kept separate from the per-minute throttles. (CONV, AWS API Gateway docs)
  8. A rate limit must be proven to discriminate, not just exist. This project's #1 failure mode (silent no-ops) applies here too: a limiter object that's never wired into a route, or one keyed on the wrong identifier, returns 200 forever while looking present in the code. Test it by actually tripping it.
  9. **Account lockout as a *concept* is not banned outright; hard permanent lockout is.** A short, escalating throttle plus optional step-up (CAPTCHA, notify the user) is what NIST actually recommends, not "3 strikes and the account is dead until support intervenes."
  10. Disposable-email blocklists are a leaky, decaying control, not a real defense. Treat them as one weak signal among several, never a claimed solution to signup abuse. (T3, vendor sources, explicitly softened below)

1. Algorithms: fixed window vs sliding window log vs sliding window counter vs token bucket vs leaky bucket

The question: which counting strategy decides "is this request allowed," and what does each cost in memory, computation, and burst-boundary correctness?

What the evidence says

  • Fixed window. Divide time into fixed-size buckets (e.g. every 60s), increment a counter, reset it to zero when the window rolls over. Upstash's own docs (T2) call this "very cheap in terms of data size and computation" but flag the classic flaw: a client can send its full quota in the last second of one window and its full quota again in the first second of the next, doubling the effective rate right at the boundary, what Upstash's docs describe as causing "request stampedes... whenever a new window begins." [upstash.com/docs/redis/sdks/ratelimit-ts/algorithms]
  • Sliding window log. Store a timestamp per request (e.g. a Redis sorted set), and count how many timestamps fall within the trailing window on every check. This is the *exact* version, no approximation, but it is O(requests-in-window) in both memory and computation: a busy key can accumulate thousands of stored timestamps. Upstash's public API does not expose a pure sliding-window-log implementation, only the more efficient approximation below, a design choice that trades perfect accuracy for boundedness. (T2, inferred directly from what Upstash's own algorithm page does and does not offer, plus the general CS description corroborated by the Cloudflare post below)
  • Sliding window counter (the "sliding window" most libraries actually ship). Keep only two integers per key: the previous window's count and the current window's count. Approximate the true count as previous_count × ((window_length − elapsed_time) / window_length) + current_count. This is exactly Cloudflare's published formula from "How we built rate limiting capable of scaling to millions of domains": with a 50 req/min limit and 42 requests counted in the previous minute, 18 so far in the current minute, 45 seconds elapsed, the estimate is 42 × (15/60) + 18 = 49.5 requests (T1: cited from Cloudflare's post, this is the origin engineering write-up for the pattern most rate-limit libraries now ship). Cloudflare validated it against 400 million real requests from 270,000 sources: 0.003% of requests were wrongly allowed or blocked, with an average 6% gap between the approximated and true rate, and zero false positives. It assumes uniform request flow within the previous window, which is "fine in most cases" per Upstash but is a real approximation, not exact math. Memory cost: two numbers per key, essentially the same as fixed window; computation cost: one extra read plus arithmetic, "more expensive... but only an approximation." [blog.cloudflare.com/counting-things-a-lot-of-different-things/, upstash.com/docs/redis/sdks/ratelimit-ts/algorithms]
  • Token bucket. A bucket holds up to maxTokens, refilling at refillRate per interval; each request removes one token, and an empty bucket rejects the request. Upstash: "expensive in terms of computation" relative to the others, but it is the only one of the four that natively supports a configurable burst allowance separate from the sustained rate (maxTokens set higher than refillRate). Stripe uses this exact algorithm in production: "We use the token bucket algorithm to do rate limiting... a centralized bucket host where you take tokens on each request, and slowly drip more tokens into the bucket," with every Stripe user getting their own bucket. [stripe.com/blog/rate-limiters, upstash.com/docs/redis/sdks/ratelimit-ts/algorithms]. AWS API Gateway also uses token bucket for its account/stage/method throttling, exposing "throttling rate" (tokens added per second) and "throttling burst" (bucket capacity) as the two knobs. [docs.aws.amazon.com/apigateway/.../api-gateway-request-throttling.html]
  • Leaky bucket. The mirror image of token bucket: water (requests) is added on arrival and drained at a fixed rate; if the bucket overflows, the request is discarded (policing) or delayed (shaping, the classic FIFO-queue variant used in traffic shaping and in tools like nginx's limit_req). Wikipedia (T2, standard CS reference, corroborated by the general networking literature it cites): "given equivalent parameters, the two algorithms will... determine exactly the same sequence of events" as token bucket, they are dual formulations of the same idea. The practical difference in this ecosystem: leaky bucket as a queue *smooths* traffic to a strictly constant output rate (good for shaping outbound calls to a downstream API with a hard rate cap, e.g. calling Stripe or Resend), while token bucket as a meter *permits bursts* up to the bucket size (good for admitting user-facing bursts without immediately rejecting).

Where the real tradeoff lies

Fixed window is cheapest but leaks bursts at the boundary. Sliding window log is exact but unbounded in memory under load, a genuine DoS surface of its own if an attacker can force a hot key to accumulate unbounded timestamps. Sliding window counter (the approximation) is the sweet spot most SaaS rate limiters (Cloudflare, Upstash, this project) actually ship: bounded memory, boundary-smoothing, small (~6% per Cloudflare's own measurement) inaccuracy that essentially never matters for abuse-prevention purposes. Token bucket costs a bit more per check but is the only one that cleanly expresses "allow bursts up to N, then throttle to steady rate," which is why Stripe and AWS both chose it for *outbound* capacity protection rather than simple abuse throttling.

Recommended default for Solen, and its cost: sliding window counter (Upstash's Ratelimit.slidingWindow) for essentially everything, which is what lib/ratelimit.ts already does for all 20+ limiters in the file. Cost: a small, bounded, and already-paid Redis command cost per check; the ~6% approximation error is irrelevant at Solen's request volume (a real attacker doesn't care if they get blocked at request 47 vs 50). Token bucket would be the better choice specifically if Solen ever needs to protect a fixed *downstream* budget with a hard, non-burstable ceiling (e.g. a paid third-party API with a literal per-second cap the vendor enforces), which is not the shape of any current abuse problem here.

2. Dimension choice: per-user vs per-IP vs per-API-key vs per-endpoint, and why IP alone is broken

The question: what identity do you attach the counter to?

What the evidence says

  • Per-user (session/JWT subject) is the strongest identity when a session exists: it survives IP rotation, VPNs, and shared networks, and it is what an attacker cannot cheaply multiply (creating N accounts is more expensive than rotating N IPs). Solen already keys authenticated routes on userId (see applyRateLimit(generalLimiter, { userId: user.id }) throughout app/api/**).
  • Per-IP is the only option pre-authentication (signup, login, guest lookup, password reset) and remains the standard secondary signal even post-auth. But IP is a leaky proxy for "one person":
  • CGNAT. Carrier-Grade NAT puts "hundreds or even thousands of clients... behind a single, shared IP address," entirely without the user's knowledge, an ISP-side capacity decision, not a voluntary proxy. Cloudflare's own measured data: CGNAT IPs get rate limited roughly 3x as often as non-CGNAT IPs, despite a nearly identical bot-traffic rate (4.8% vs 4.7%), meaning the extra blocking is pure collateral damage, not extra abuse. This concentrates disproportionately on users in regions where CGNAT is heaviest. (T1/T2, Cloudflare engineering blog, primary measurement) [blog.cloudflare.com/detecting-cgn-to-reduce-collateral-damage/]
  • IPv6 /64. RFC 6177 (March 2011, current standard for end-site IPv6 assignment) explicitly reasons that "although a /64 can (in theory) address an almost unlimited number of devices, sites should be given sufficient address space," and recommends end sites (including single homes) get *more* than one /64 rather than being pinned to it. The practical rate-limiting consequence: a single IPv6 /64 is the correct unit to key on for one "site" (a household, an office), not a single /128 address, because a device can rotate its /128 within its assigned /64 (privacy extensions, SLAAC) while remaining the same network. Rate limiting on the full /128 under-counts the same actor as many identities; rate limiting on /32-equivalent (the whole ISP) over-counts unrelated actors as one. (T1, RFC 6177) [rfc-editor.org/rfc/rfc6177.html]
  • Reverse proxies and load balancers. Any request behind Netlify's edge, a CDN, or a corporate proxy arrives at the origin with the proxy's IP unless a trusted forwarding header is read correctly.
  • Spoofable X-Forwarded-For. The XFF header's client-supplied leftmost entry can be set to anything by the caller; trusting it naively lets an attacker rotate through fake values and evade a per-IP limiter entirely with zero real IP changes. Solen's own code comment in lib/ratelimit.ts::getClientIp() states this precisely: "x-forwarded-for's leftmost entry is attacker-supplied (an attacker can prepend any value), so every auth/OTP limiter keyed on it alone is trivially bypassed by rotating the header," and correctly prefers Netlify's edge-set x-nf-client-connection-ip (unspoofable by the client, since Netlify's edge overwrites it) with XFF only as a local/dev fallback. This is Solen already applying this exact piece of researched law; nothing to change here.
  • Mobile carriers. Cellular networks are CGNAT's largest real-world deployment; a mobile ISP's entire regional user base can share a small IP pool, which is the same collateral-damage mechanism as CGNAT above, not a separate phenomenon.
  • Per-API-key. Standard for B2B/partner APIs (Stripe, AWS) because the key *is* the accountable identity and is provisioned, not squatted. Solen has no external partner API surface today (dashboard sessions and customer sessions are the only two identity classes), so this dimension doesn't currently apply, but it is the correct dimension the day Solen ships any salon-facing integration API.
  • Per-endpoint. Orthogonal to the identity dimension: the *same* user/IP should get a different budget on /api/auth/signup (5/min, expensive, abuse-prone) than on /api/salons/search (cheap, read-only, high legitimate volume). Solen already does this: lib/ratelimit.ts defines a distinct named limiter per route family (authLimiter, paymentLimiter, bookingLimiter, discoveryFeedLimiter, etc.) rather than one global limiter, which is the correct pattern.

The real tradeoff: per-user is strong but only exists after login; per-IP is universal but is a statistical proxy for identity, not identity itself, and its accuracy degrades unpredictably by network topology, not by attacker sophistication. The fix is never "a smarter IP heuristic," it's minimizing how much weight any single IP-based limiter carries (short windows, generous-but-not-infinite thresholds, combined with per-user limits the moment a session exists) and never treating an IP block as equivalent to blocking "a person."

Recommended default for Solen: userId first wherever a session exists (already the case); IP-keyed only for the genuinely pre-auth / enumeration-oracle surfaces (signup, login, guest lookup, referral validate), using the trusted-header-first getClientIp() Solen already has; keep per-endpoint granularity (already the case). Cost of this design: a shared IP (CGNAT, office, campus) can still trip a pre-auth limiter meant for one bad actor; the mitigation is keeping those specific windows short and the thresholds generous enough that a real burst of legitimate guest users (e.g. several people in one salon's waiting room using guest lookup on the same WiFi) doesn't get caught, which is a judgment call to periodically sanity-check against real usage, not a solved problem.

3. Brute-force protection

The question: how do you stop an attacker from guessing a password (or OTP, or reference code) by sheer repetition, without over-engineering for a threat model Solen doesn't have.

What the evidence says: this is really sections 1 and 2 applied to one dangerous class of endpoint, plus NIST's specific numeric guidance (next section). The concrete mechanism is: rate limit the endpoint (throttle), on both the account/identifier being guessed *and* the IP doing the guessing, with a short enough window that a scripted brute force can't get meaningful signal before being cut off. OWASP's credential-stuffing cheat sheet frames the *broader* category (of which classic password brute force is a subset): a single control never suffices, layer several, and IP-blocking specifically "should not be used as the sole or primary defense due to the ease in circumvention" because "sophisticated tools distribute requests across proxy networks, defeating per-IP rate limits." [cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html] The strongest single defense category-wide is MFA: OWASP cites Microsoft's analysis that MFA "would have stopped 99.9% of account compromises" (T2, OWASP citing a named vendor analysis, treat the specific 99.9% as a cited third-party figure, not independently re-derived here).

Solen's actual exposure today: guestLookupLimiter (10 attempts / 10 min per IP) protects the reference_code guest-booking lookup, explicitly documented in-code as an enumeration-oracle defense, additionally backstopped by the token space being 256-bit (making brute force computationally infeasible regardless of the rate limiter, per the code comment). authLimiter (5/min per IP) covers signup, login, and OTP/phone-verify routes. referralValidateLimiter (10 / 10 min per IP) protects a public code-validity oracle. This is a coherent, already-applied instance of "rate limit the guessing surface, key it on IP because there's no session yet, keep the window short."

Recommended default: keep the existing per-route IP-keyed sliding-window limiters on every guessing/enumeration surface; the pattern is right and doesn't need new machinery. The gap (if any) is coverage, not design: any *new* guessing-shaped endpoint (a new code-validation, lookup-by-token, or "check if X exists" route) needs the same treatment from day one, not bolted on after an incident.

4. Account lockout tradeoffs (lockout as a self-inflicted DoS; what NIST actually says)

The question: should N failed login attempts lock the account, and if not, what instead?

What the evidence says, directly quoted from the current, authoritative source: NIST SP 800-63B-4 ("Digital Identity Guidelines: Authentication and Authenticator Management," published July 2025, formally superseding the 2017/2020 SP 800-63B, confirmed via its own publication-history page: "Supersedes NIST SP 800-63B (June 2017; updated March 2, 2020)") states in section 3.2.2, "Rate Limiting (Throttling)" (T1, read directly from the PDF, this is the exact current normative text, not a paraphrase):

"the verifier SHALL limit consecutive failed authentication attempts using a specific authenticator on a single subscriber account to no more than 100 by disabling that authenticator... The limit of 100 attempts is an upper bound, and agencies MAY impose lower limits. The limit of 100 was chosen to balance the likelihood of a correct guess (e.g., 100 attempts against a six-digit decimal OTP authenticator output) versus the potential need for account recovery when the limit is exceeded."

Critically, this is framed as *disabling that specific authenticator* (temporary, self-healing on success), not "the account is locked, contact support." NIST explicitly lists the anti-lockout techniques agencies "MAY" use on top of the count ceiling:

"Requiring the claimant to complete a bot detection and mitigation challenge before attempting authentication [CAPTCHA]... Requiring the claimant to wait after a failed attempt for a period of time that increases as the subscriber account approaches its maximum allowance for consecutive failed attempts (e.g., 30 seconds up to an hour)... Leveraging other risk-based or adaptive authentication techniques to identify claimant behaviors that fall within or outside of typical norms (e.g., the use of the claimant's IP address, geolocation, timing of request patterns, or browser metadata)."

And on recovery: "When the subscriber successfully authenticates, the verifier SHOULD disregard any previous failed attempts for the authenticators used in the successful authentication," and "Following successful authentication... the verifier SHOULD reset the retry count." [nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-63B-4.pdf, section 3.2.2, pages 30-31 of the PDF]

Note on a wrong number that surfaced during this research and got corrected: an initial web search summary claimed NIST 800-63B-4 requires "no more than 10 failed attempts." That is false; the actual, directly-read PDF text says 100, described explicitly as an *upper bound* that implementers may tighten. This is exactly the kind of memory-poisoning error this research protocol exists to catch, flagging it here so it is never repeated. (MYTH: "NIST caps failed logins at 10", the real number is a 100-attempt ceiling, agencies may go lower)

Why permanent/hard lockout is actively harmful: if account state can be flipped to "locked" by anyone who knows (or can enumerate) a username/email, an attacker who has zero interest in actually breaking into the account can lock out every real user by intentionally failing logins against known usernames, a denial-of-service that costs the attacker nothing and costs the product a support ticket per victim. Progressive throttling (the NIST-recommended alternative) degrades the attacker's own attempt rate without ever fully denying the legitimate owner access once they arrive with the correct credential.

Recommended default for Solen: never implement account-level "N strikes and you're locked" logic. authLimiter (5 attempts/min per IP, sliding window) is already, functionally, a throttle in the NIST sense, not a lockout: the block is time-bounded and per-IP, and a real user who mistypes their password five times gets a short, self-clearing delay rather than a support-desk ticket. Confirmed by grep: there is no account_locked / failed_login_attempts column or lockout logic anywhere in the current codebase or migrations, this is a case of the codebase already avoiding a mistake the industry commonly makes, worth stating explicitly so nobody "fixes" it by adding lockout later without re-reading this section. Cost of the current approach: 5/min per IP is loose enough that a slow, patient, low-and-slow brute force spread across time could in theory make some headway against a weak password; the actual backstop against that is Supabase Auth's own password strength requirements (Solen's signup schema already requires 8+ chars, an uppercase letter, and a digit) plus the fact that Solen has no evidence today of targeted brute-force attempts at ~28-salon scale.

5. Bot and signup abuse (disposable email, credential stuffing, CAPTCHA tradeoffs)

The question: how do you stop scripted account creation and credential-stuffing attacks against login, without breaking the experience for the 99% of real users.

What the evidence says

  • Credential stuffing (reusing breached username/password pairs at scale against a different site) is architecturally different from brute force: the attacker already has *valid-looking* credentials and is testing which accounts they match, so a per-account attempt-count limit does little (each account only gets tried once or twice) while an IP or device-level velocity signal is what actually catches it. OWASP's cheat sheet (T1, canonical source for this specific attack class) lays out the full layered stack: MFA first (strongest single control), then, where MFA isn't feasible everywhere: CAPTCHA ("can help to identify automated/bot attacks," but breakable "with a reasonably high success rate" by paid solving services, so deploy it selectively on risk-flagged logins, not universally), breached-password screening at signup/reset (NIST 800-63B-4 itself now requires checking new passwords against known-breach corpora and rejecting matches outright), device and connection fingerprinting (JA3-style connection fingerprinting is noted as potentially "more accurate... than other defenses relying on IP addresses or user agents alone," but all client-supplied signals, including device fingerprints, are "provided by the client" and therefore spoofable in principle), unpredictable usernames, multi-step login flows, and user-visible "last login" notices. [cheatsheetseries.owasp.org/cheatsheets/Credential_Stuffing_Prevention_Cheat_Sheet.html]
  • Disposable/throwaway email at signup is a real but structurally losing arms race if fought with a static blocklist: vendor-reported figures (T3, treat softly, these are marketing-adjacent benchmarks, not peer-reviewed) describe blocklist accuracy decaying "from 100% to 43%" over time as new disposable domains launch continuously and existing ones rotate, and note that Gmail-based disposable-alias services (which piggyback on a real, non-blockable domain) are specifically hard to catch this way. Treat any specific percentage here (including the "up to 30% of free-tier signups" claim surfaced in this research) as an unverified vendor statistic, not a number to cite in a product doc. What *is* solid: a domain blocklist is a decaying signal that needs either a maintained third-party API or acceptance that it will always miss a meaningfully-sized set of throwaway domains, so it should never be the sole gate on signup abuse, same principle as CAPTCHA.
  • CAPTCHA tradeoffs, stated plainly: CAPTCHA adds real friction to every legitimate user who sees it, is bypassable by paid human-solving services and increasingly by AI vision models, and (per OWASP) is best used selectively, e.g. after N failed attempts or on a risk-flagged session, not as a blanket gate on every login or signup. Its actual job is raising the attacker's marginal cost, not making the endpoint unattackable.
  • Unrestricted resource consumption (OWASP API Security Top 10, API4:2023): the current (2023, confirmed as the live edition via OWASP's own site) API-specific top-10 entry that subsumes what used to be a standalone "lack of rate limiting" item. Its worked scenario is directly relevant to Solen's shape (a booking/marketplace product that calls paid third-party services): "An attacker repeatedly triggers a forgot-password endpoint that sends SMS verification codes via a third-party service... forces the company to incur significant charges." [owasp.org/API-Security/editions/2023/en/0xa4-unrestricted-resource-consumption/] This is structurally identical to Solen's own AI-generation cost-cap concern already addressed by getAiDailyLimiter() (a 100/day per-user quota specifically because "a cost cap that fails open on a misconfigured Upstash defeats the whole point of having one," per the in-code comment), which is exactly the right instinct: rate limiting alone (a per-minute request cap) doesn't bound a *cost*, only a *rate*; a separate quota is needed wherever a request has a real per-call dollar cost (SMS, AI generation, email sends).

Recommended default for Solen: keep the layered, not-single-point stack Solen already leans on (Supabase's own password strength + breach checks, per-route sliding-window IP limits on auth, no lockout, generic non-enumerating signup responses, per-user daily cost quota on paid AI calls). The concretely open gaps: no CAPTCHA anywhere (acceptable at 28-salon scale, revisit if scripted signup abuse is actually observed in PostHog/logs, not preemptively), no disposable-email check at signup (same: acceptable today, cheap to add later as one more weak signal, never a claimed solution), no device/connection fingerprinting (correctly not worth the engineering cost at this scale).

6. Quota vs throttle

The question: are "how fast" and "how much, total" the same control? They are not.

What the evidence says: AWS's own API Gateway documentation (T2, official vendor docs, describing a widely-adopted pattern) draws the line explicitly: a *throttle* is the token-bucket rate/burst pair ("the rate, in requests per second, that tokens are added to the token bucket" and "the capacity of the token bucket") that shapes the *speed* of a traffic stream and resets continuously, while a *quota* is "a total consumption limit (typically daily or monthly)" that bounds cumulative usage regardless of how slowly it's spread out. [docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-request-throttling.html] A user who stays exactly at the throttle ceiling all day can still exhaust a monthly quota; a throttle alone cannot express a budget.

Solen's own code makes this distinction correctly and explains why in a comment worth quoting directly, because it is exactly the right mental model: "The per-minute limiters below (generalLimiter, adminLimiter) only cap burst rate; a user sitting at the per-minute cap all day can still run up an unbounded bill... Apply THIS IN ADDITION to, never instead of, the existing per-minute limiter." (lib/ratelimit.ts, around getAiDailyLimiter)

Recommended default: every route that calls a metered, paid third-party service (Gemini/fal.ai generation today; would extend to any future SMS/email-per-send billing or a partner API with a metered contract) needs both a throttle (burst protection) and a quota (cost ceiling), never just one. Cost: a second Redis-backed counter and, in Solen's case, a DB-backed configurable cap (platform_settings.ai_daily_cap) with a 60s in-memory TTL cache, already built and already correctly labeled "in addition to, never instead of."

7. The correct response: 429 + Retry-After + RateLimit headers

The question: what should the server actually send back when it rejects a request for rate-limit reasons?

What the evidence says

  • Status code 429 "Too Many Requests" is defined by RFC 6585 ("Additional HTTP Status Codes," April 2012, confirmed current, not superseded for this specific status code): "The 429 status code indicates that the user has sent too many requests in a given amount of time ('rate limiting')," and the spec explicitly ties it to Retry-After: "The response representations SHOULD include details explaining the condition, and MAY include a Retry-After header indicating how long to wait before making a new request," with a worked example of Retry-After: 3600. [rfc-editor.org/rfc/rfc6585.html] (T1)
  • Retry-After itself is defined in RFC 9110 ("HTTP Semantics," June 2022, T1, confirmed as obsoleting RFC 7231 and folding the header's definition into the current core HTTP spec), and accepts either a delay in seconds or an absolute HTTP-date.
  • The RateLimit / RateLimit-Policy header pair (what many engineers loosely call "the rate limit headers RFC") is not an RFC. As of this research, the current document is draft-ietf-httpapi-ratelimit-headers-11, an active IETF HTTPAPI working-group Internet-Draft, published 2026-05-23, intended status "Standards Track," expiring 2026-11-24 (T2, directly read from the datatracker page, status confirmed live at time of writing, not assumed from memory). It defines a server-advertised quota policy (RateLimit-Policy, with parameters q = quota, qu = unit, w = window seconds, pk = partition key) and the current-state header (RateLimit, with r = remaining quota, t = window, pk = partition key), explicitly states it does "not mandate a specific throttling algorithm," and says that if both Retry-After and RateLimit appear in one response, "the Retry-After field value SHOULD NOT reference a point in time earlier than the end of the effective window." [datatracker.ietf.org/doc/html/draft-ietf-httpapi-ratelimit-headers] Because it is still a draft, do not cite it as "the standard," and do not assume the exact field names are frozen, draft-to-draft revisions have renamed fields before.
  • Solen's current implementation already returns 429 with Retry-After (correctly computed as seconds until reset) plus X-RateLimit-Limit / X-RateLimit-Remaining / X-RateLimit-Reset, the older, de-facto (never formally standardized) convention popularized by GitHub/Twitter-era APIs, not the new draft's field names or syntax.

The real tradeoff: the X-RateLimit-* convention Solen uses today is universally understood by every HTTP client and tooling library in practice (CONV, a coordination device, not a formal standard), while the IETF draft's RateLimit/RateLimit-Policy pair is the more "correct," standards-track-aiming replacement but is still moving and has essentially zero client-library adoption pressure forcing a switch today.

Recommended default for Solen: keep the current 429 + Retry-After + X-RateLimit-* pattern exactly as implemented; it satisfies the only hard-standard part (429 + Retry-After, both T1) and uses a well-understood, if informal, convention for the rest. Do not migrate to the IETF draft's header names while it's still a pre-RFC draft: cost of migrating now is churn for zero real client benefit (nothing consumes the new headers today) and a risk of migrating to field names that change again before the draft finalizes.

8. Fail-open vs fail-closed when the limiter backend is down

The question: if Redis (or whatever backs the limiter) is unreachable, do requests get blocked (fail closed) or let through (fail open)?

What the evidence says

  • Stripe's engineering post is explicit and unambiguous in one direction: "Make sure that if there were bugs in the rate limiting code (or if Redis were to go down), requests wouldn't be affected. This means catching exceptions at all levels so that any coding or operational errors would fail open." [stripe.com/blog/rate-limiters] Stripe's reasoning: a rate limiter existing to protect *availability* should never itself become the availability outage.
  • Upstash's own SDK bakes in the same default, but as a client-side safety net rather than a design mandate: a configurable timeout (5 seconds by default) on the Redis round trip, after which "the request will be allowed to pass regardless of what the current limit is," i.e. fail open on backend slowness/unavailability, unless the caller overrides it. [upstash.com/docs/redis/sdks/ratelimit-ts/features] Note this is a *separate* mechanism from whatever try/catch the calling application adds around .limit(), both layers can independently decide to fail open, and if the application's own catch block doesn't also fail closed for a specific route, the SDK's internal fail-open default silently governs that route too.
  • The disagreement this file must not paper over: fail-open is correct for the general case (Stripe's stated reasoning: don't let the limiter become the outage), but it is actively wrong for a narrow set of routes where the entire point of the limiter is a security or cost boundary, not an availability nicety, brute-force/enumeration endpoints, and anything with a real per-call dollar cost. A limiter that fails open there doesn't degrade gracefully, it silently switches off the exact protection it exists for, at precisely the moment (a Redis outage or misconfiguration) an attacker is most likely to be probing.
  • Solen's own code already resolves this correctly, per-route, not globally, which is worth stating as a positive finding rather than a gap: lib/ratelimit.ts defines ABUSE_PRONE_LIMITERS (auth, payment, booking, guest lookup, referral validate/complete, resend-access, and every AI-daily-cap instance) and fails closed (returns the same 429 a real limit-hit would, minus headers it has no real numbers for) specifically for those, *only* on a verified real-production boot (CONTEXT === "production" && NODE_ENV === "production", a deliberate double-check against Netlify's preview/branch deploys also setting CONTEXT), while every other limiter (browsing, discovery, messaging, admin) fails open exactly as Stripe recommends, so a Redis misconfiguration degrades the product instead of degrading its security boundary. On an actual Redis *error at runtime* (not just missing config), both code paths currently fail open (catch logs and lets the request through) for every limiter, including the abuse-prone ones, which is the one place this file flags a real inconsistency: the "fail closed" logic only fires on Redis being *unconfigured*, not on Redis *erroring mid-request* (timeout, connection reset). That gap is worth a deliberate owner decision (should a runtime error on paymentLimiter.limit() also fail closed, matching the unconfigured-Redis behavior, or is fail-open-on-runtime-error acceptable because Upstash's managed Redis has high uptime and an attacker can't trigger transient errors on demand). Flagging, not fixing, per this research task's scope.

Recommended default: keep the per-route split (already correct); treat the runtime-error-vs-unconfigured inconsistency above as an explicit open question for the owner, not a silent gap, since "fail open on every runtime error including for abuse-prone limiters" is a real, live security tradeoff, not an oversight to quietly patch inside a research file.

Myths and traps

  • MYTH: "NIST caps failed login attempts at 10." The current, directly-read NIST SP 800-63B-4 text says the verifier SHALL limit consecutive failures to *no more than 100* (an upper bound; agencies may go lower), not 10. This exact wrong number surfaced from an initial web search summary during this research run and was caught only by fetching and reading the actual PDF section. Treat any secondhand paraphrase of a NIST numeric requirement as unverified until the primary text is read.
  • MYTH/stale: citing the 2017/2020 SP 800-63B as current. As of August 2025, SP 800-63B-4 (July 2025) supersedes it. Any doc, blog post, or memory still citing "SP 800-63B, 2017" for authentication throttling guidance is citing a superseded document; the throttling numbers and the 100-attempt ceiling above are the current ones.
  • MYTH: "the RateLimit headers are an RFC now, use RateLimit-Policy / RateLimit." As of this research, they are still draft-ietf-httpapi-ratelimit-headers-11, an Internet-Draft, not a published RFC. Don't cite an RFC number for it because none exists yet.
  • MYTH: "blocking by IP stops credential stuffing / brute force." OWASP states plainly that IP blocking alone is trivially circumvented by distributing requests across proxy networks, and per this file's own research, CGNAT and mobile-carrier NAT make IP an unreliable proxy for identity even without any attacker evasion effort at all.
  • MYTH: "CAPTCHA solves bot signup abuse." Both OWASP and the general literature agree CAPTCHA-solving services defeat it "with a reasonably high success rate." It raises cost, it doesn't close the door.
  • TRAP, specific to Solen's serverless/Netlify stack: a rate limiter that lives in in-process memory (a plain JS Map or module-level counter) does not work correctly across serverless invocations. Each cold lambda gets a fresh process, so an in-memory counter resets constantly and undercounts badly; this is exactly why Solen's limiters are all backed by external Redis (Upstash) rather than local state, correctly avoiding this trap.
  • TRAP, specific to PostgREST/Supabase: a rate limit implemented as a check against a DB column (e.g. "count failed_attempts in the users table") is a query, not a rate limiter, subject to this project's own documented #1 failure mode: a silently-wrong .select() or a race condition between concurrent requests reading-then-writing the same counter (no atomic increment) can undercount under load, letting a burst through uncounted. A real limiter needs an atomic increment primitive (Redis INCR/Lua script, or Postgres UPDATE ... SET n = n + 1 RETURNING n inside one statement), never a read-then-write from application code.
  • TRAP, specific to Stripe Connect: Stripe itself rate limits the platform's API calls (per Stripe account, not per Solen's own users), so a burst of Solen-side activity (e.g. a batch payout job, or a traffic spike triggering many PaymentIntent creations) can hit *Stripe's* rate limit, a completely separate limiter Solen doesn't control and must handle with its own backoff/retry logic on Stripe API calls, not just worry about limiting inbound requests to Solen's own API.
  • TRAP: fail-open by omission. The most common way a rate limiter silently stops working isn't a design flaw, it's a limiter object defined in lib/ratelimit.ts but never actually imported and called (applyRateLimit) inside a specific route. That route returns 200 forever with zero protection while npm run exists ratelimit or a quick grep can make it look like the feature "exists." Every new abuse-prone route needs its limiter call verified by actually tripping it (send N+1 requests, confirm the 429), not just by seeing the import line.

Premature at our scale

  • Distributed / multi-region rate limiting (Upstash's multi-region feature, replicating counters across regions with CRDT-based async merge, accepting "no way to guarantee the set ratelimit is not exceeded by a small margin"): correct for a global, multi-region-deployed API serving latency-sensitive traffic from several continents. Solen is a single-region Netlify deployment serving a Swiss market; there is no latency problem this solves today. Revisit trigger: if Solen ever deploys origin infrastructure across multiple regions (not just Netlify's CDN edge, the actual compute), or if p95 latency to the Upstash region becomes measurably user-visible from a specific market.
  • Adaptive/ML-based bot scoring (Cloudflare's CatBoost bot-score model, described in their CGNAT post as informing per-request WAF rules): correct at Cloudflare's traffic volume (billions of requests, enough signal to train a model). At ~28 salons' worth of traffic, there is neither the request volume to train anything meaningful nor evidence of sophisticated bot traffic to justify it. Revisit trigger: documented, repeated scripted-abuse incidents that simple IP/user throttling and CAPTCHA-on-suspicion don't stop.
  • Device/connection fingerprinting (JA3, canvas fingerprinting, etc.): a real, OWASP-endorsed layer for high-value targets (banks, large-scale consumer platforms under active credential-stuffing attack). Solen has shown no evidence of being under such attack; adding fingerprinting now is speculative engineering against a threat that hasn't materialized, and it carries its own privacy/GDPR-surface cost that should be weighed only once there's a concrete incident to justify it. Revisit trigger: a real, observed credential-stuffing campaign (spike in failed logins across many distinct accounts from a shared pattern) that IP+user throttling alone doesn't stop.
  • CAPTCHA on every signup/login: premature; adds friction to 100% of legitimate users to defend against a threat not yet observed at Solen's scale. Revisit trigger: measurable scripted signup volume in PostHog/analytics, or a real spike in authLimiter 429s from a narrow set of IPs/patterns.
  • Disposable-email-domain API subscription (a paid, continuously-updated blocklist service): premature; today's signup volume (a marketplace with ~28 salons, presumably low absolute signup counts) doesn't justify a recurring vendor cost for a control that's a decaying signal at best. Revisit trigger: observed abuse pattern where fake/throwaway accounts are actually causing a concrete problem (spam reviews, farmed referral credits, promo-code abuse), not a hypothetical one.
  • A formal API-key-based partner-tier throttling system (AWS-usage-plan-style per-client quotas): correct the day Solen ships a partner-facing API (e.g. a salon POS integration, a third-party booking widget). No such surface exists today; building the machinery in advance is speculative. Revisit trigger: the first real external API consumer.

  • The specific claim "up to 30% of free-tier signups are generated by bots... or disposable email addresses" (surfaced in a vendor-blog search result) could not be traced to a primary, methodologically-described study; treat it as an unsupported marketing figure, not a number to cite anywhere in Solen product docs.
  • The "59% average detection rate across 17 disposable-email services in a 272-test benchmark" figure is from a vendor blog (prospeo.io), not a peer-reviewed or independently reproducible source; directionally plausible (blocklists do decay) but the specific percentage is unverified.
  • Whether Solen's authLimiter (5/min per IP) specifically has ever been tripped by a real attacker, versus being purely precautionary, was not checked in this research pass (would require reading PostHog/log data, out of scope for a research-only file). Stated here so a future session doesn't assume either way without checking.
