0. The short version

  1. Never call supabase.auth.getSession() server-side for an authorization decision. It trusts the client-supplied cookie without verifying the JWT signature; only getUser() round-trips to the Auth server and fails closed. (T2, Supabase docs + already hook-enforced in this repo: .claude/hooks/no-getsession-authz-gate.py.)
  2. Password length beats composition. Require length (8 minimum only if MFA is also required, 15 minimum for password-only), allow up to 64+ chars, allow ALL characters including spaces/unicode, never force periodic rotation, never require an uppercase+digit mix. (T1, NIST SP 800-63-4.) Solen's signup/reset schemas currently violate this (8-char + uppercase + digit rule) , flagged below, not yet fixed.
  3. Don't hand-roll password hashing. Supabase Auth (GoTrue) already hashes with bcrypt server-side; Solen never sees or stores a plaintext or self-hashed password. If Solen ever hashes anything itself (e.g. a bespoke API key), the order of preference is Argon2id > scrypt > bcrypt > PBKDF2, and bcrypt silently truncates any input past 72 bytes. (T1, OWASP Password Storage Cheat Sheet.)
  4. Password reset and forgot-password flows must return the identical response and timing whether or not the account exists, and must invalidate the reset token after one use with a short expiry. Solen's signup route already does this for enumeration; its reset-password page does NOT invalidate other active sessions after a successful reset, and should. (T1 OWASP; T0 = confirmed gap in our own code, see section 6.)
  5. The sessions-vs-JWT debate is real, not folklore, and the honest answer for a 28-salon marketplace is: keep what Supabase already gives you (short JWT + rotating refresh token, both revocable), don't hand-roll a stateless-forever JWT. Solen already has this by construction because it never issues its own long-lived signed tokens for auth. (See section 1.)
  6. OAuth: implicit flow is dead, PKCE is mandatory even for server-rendered apps. Solen's Supabase client stack (@supabase/ssr) defaults to PKCE-flow OAuth already, so this is compliant by default, not by anyone's deliberate choice, worth knowing so nobody "simplifies" it back to implicit or a bare authorization-code-without-PKCE flow. (T1, RFC 9700.)
  7. Cookie flags: session-carrying cookies need HttpOnly + Secure + SameSite=Lax (or Strict where it doesn't break a cross-site redirect flow) + narrow Path, and the __Host- prefix where the cookie doesn't need to span subdomains. Solen's own guest/session cookies already do httpOnly + sameSite=lax, but do not yet consistently use the __Host- prefix. (T1, OWASP Session Management Cheat Sheet.)
  8. MFA is the single highest-leverage authentication control available and Solen has none wired up, despite Supabase Auth shipping TOTP MFA free and enabled on every project by default. This is the biggest concrete gap this research surfaces. (T2, OWASP Authentication Cheat Sheet + Supabase docs.)
  9. Passkeys (WebAuthn) are the correct end-state for phishing resistance but are BETA on Supabase Auth as of May 2026 and not something to build a dependency on yet for a production consumer marketplace; TOTP is the pragmatic near-term MFA answer. (T2, Supabase changelog.)
  10. SSO/SAML is enterprise B2B machinery Solen does not need. Solen is B2C; if federated login is ever wanted, OIDC (which Solen partially already has via Google/Apple OAuth) is the right layer, SAML is not. (T2/CONV, several converging vendor sources.)

1. Sessions vs JWT: the real debate

The question. Should an authenticated user's identity be carried as a self-contained signed token (a JWT) that the server can verify without a database lookup (stateless), or as an opaque session identifier that the server looks up in a store on every request (stateful)?

The stateless case. A JWT signed with the server's key can be verified with pure cryptography (a signature check), no database round-trip, no shared session store. This is genuinely valuable when: verification has to happen on a machine that doesn't share a database connection with the issuer (a different microservice, a CDN edge function, a different company's server in federation). For serverless (Solen's Netlify/Lambda model), avoiding a synchronous DB hit on every request is real latency and cost savings, this is the honest strength of the JWT argument (T2, multiple sources including reptile.haus, "Stop Defaulting to JWTs").

The strongest case against. The exact same statelessness that makes a JWT fast to verify makes it impossible to revoke early. If a user logs out, changes their password, or their laptop is stolen, a plain JWT stays valid until it naturally expires, there is no way to invalidate it early without introducing a server-side revocation list, "and once you're maintaining a server-side blocklist checked on every request, you've reintroduced the stateful lookup you were trying to avoid, so you get all of the statelessness's downsides (no clean revocation) and none of its upside (no DB hit)" (T2, ianlondon.github.io, "Please Don't Use JSON Web Tokens for Browser Sessions"; converging summary via mojoauth CIAM Q&A). This is not a fringe opinion, it is the mainstream security-engineering position, and it is why RFC 9700 (the current OAuth 2.0 security BCP) spends real text on refresh-token rotation and sender-constraining rather than trusting bare stateless access tokens (see section 8).

The resolution the industry actually converged on (short access token + long revocable refresh token). Don't pick one pole. Issue a short-lived signed access token (JWT, stateless, cheap to verify, damage-limited by its own short expiry) and a separate long-lived, database-backed, single-use, rotating refresh token that CAN be revoked instantly (kill the row, and every future refresh attempt fails). This is exactly what Supabase Auth does: the access token JWT defaults to a 1-hour expiry ("most applications should use the default... 1 hour", Supabase Sessions docs), and the refresh token is stored server-side, rotates on every use, and is revoked by deleting the session row on sign-out. So the "JWT vs sessions" debate for Solen is already resolved by the platform choice: Solen gets stateless-fast reads for the 1-hour window and a real revocation point (the refresh token / session row) for everything else.

The actual tradeoff for a marketplace like Solen. A booking marketplace has three account tiers with very different blast radii if a stolen token stays valid: an anonymous browsing session (low stakes), a customer account (stored payment methods, booking history, PII), and a salon-owner/staff dashboard session (can move money via Stripe Connect payouts, can see other customers' PII). The 1-hour access-token window is an acceptable risk for the customer tier; for the owner/staff dashboard tier, it is the thing that makes "instant kick a compromised owner session" actually work, because revoking the refresh token (deleting the session) still leaves up to 1 hour of the already-issued access token's validity, since Solen's middleware calls getUser() (a live verify against the Auth server, not a local JWT decode) it actually re-checks aliveness on every protected request rather than trusting a cached JWT locally, so a session deletion (ban, force sign-out) takes effect on the NEXT request, not after up to an hour. This is a meaningfully better revocation story than pure client-side JWT verification would give, and it's already how Solen is built (middleware.ts:101-146, lib/supabase.ts:68-72).

Recommended default and its cost. Keep the current architecture (short JWT + Supabase-managed rotating refresh token + server-verified getUser() on every privileged check). The cost: every privileged request pays one network round-trip to the Supabase Auth server (this is why middleware.ts races it against a 4-second timeout, T2 already true in the codebase). At Solen's traffic (~28 salons, low request volume), this cost is negligible; it would start to matter at a scale where Auth-server round-trip latency shows up as a measurable page-load tax, which is not Solen's problem today.

2. Cookie flags

What the standard says. OWASP's Session Management Cheat Sheet (fetched, cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html) is explicit:

  • HttpOnly: blocks document.cookie JS access, the floor defense against session-token theft via XSS. Does not stop an XSS payload from making authenticated requests using the cookie (XSS+CSRF combo still works), it only stops the token from being read and exfiltrated.
  • Secure: cookie is sent only over HTTPS. Mandatory, full stop, to prevent a man-in-the-middle from reading the session ID on an unencrypted hop.
  • SameSite: "Session cookies must explicitly set SameSite=Strict (preferred) or SameSite=Lax. Never use SameSite=None without Secure." Strict blocks the cookie on ANY cross-site navigation including a user clicking a link from an external site into your app (they'd land logged-out and have to click again); Lax sends the cookie on top-level GET navigations (a normal link click) but blocks it on cross-site POSTs and subresource requests, which is why Lax is what most session cookies actually ship with, it is the practical CSRF-mitigating default that doesn't break "click a link from Google into your logged-in app."
  • __Host- prefix: browser-ENFORCED (not just documentation) guarantee that a cookie named __Host-xxx must be set with Secure, no Domain attribute, and Path=/, which prevents a sibling subdomain from setting or overriding your cookie (the "cookie tossing" attack class). Recommended specifically for session identifiers.
  • Domain / Path: narrowest possible. Omitting Domain restricts the cookie to the exact origin (safer than Domain=.solen.ch, which would let any subdomain, including a future lower-trust one, read and forge it).
  • Max-Age/Expires: session cookies should be non-persistent (no Max-Age, dies with the browser) unless a "remember me" is a deliberate product decision; persistent cookies widen the window an unattended device stays logged in.

Note the __Host-/__Secure- prefix mechanism itself is still formally an Internet-Draft, not a ratified RFC, as of this run: draft-ietf-httpbis-rfc6265bis-22, dated December 2025, still under IETF HTTP working group review, expiring 2027-01-07 (datatracker.ietf.org/doc/draft-ietf-httpbis-rfc6265bis). This does not mean it's unsafe to rely on: all major browsers already implement the prefix enforcement (it long predates formal ratification, the same way SameSite shipped in Chrome before its RFC was finalized), but it is honest to flag that "per RFC 6265bis" is citing a draft, not a final standard, tier this CONV/T2 rather than T1.

What Solen actually does (grep-verified this run). lib/bookings/guest-access.ts:112-121 sets the guest booking-access cookie with httpOnly: true, secure: (implied by env), sameSite: "lax"; app/api/admin/preview-salon/route.ts:43-62 and app/api/search/event/route.ts:100-102 and app/api/analytics/track-view/route.ts:52 follow the same httpOnly + sameSite: "lax" shape. app/api/salons/active/route.ts:36-37 sets httpOnly: false (a non-auth city/salon-switcher cookie, not a session credential, so this is an intentional and correct exception, not a bug). None of the grepped cookie-setting call sites in app/ use the __Host- prefix explicitly (Supabase's own session cookies, set internally by @supabase/ssr, are a separate matter, see below).

Where the real tradeoff lies. SameSite=Strict is marginally more CSRF-safe than Lax but breaks the "arrive via an external link and be already logged in" UX (the user has to re-navigate once). For a booking marketplace where a large share of traffic legitimately arrives via an external link (Google Maps listing, an Instagram bio link, a WhatsApp share of a salon page), Lax is the correct default: it still blocks the attack Strict exists to prevent (a forged cross-site POST) while not silently logging the user out of a link click. Strict is worth reserving for the highest-stakes cookie only, if Solen ever splits "browsing session" from "payment-authorization session."

Recommended default and cost. Keep httpOnly + secure + sameSite=lax, narrow Path per cookie's actual scope, and add the __Host- prefix to any custom-set auth-adjacent cookie (the guest booking-access cookie is the clearest candidate: it doesn't need to span subdomains and IS a bearer credential for a booking). Cost: near zero, this is a rename plus dropping any Domain attribute if one is set; do this as a small hardening pass, not a redesign.

3. Password hashing: argon2id vs bcrypt vs scrypt vs PBKDF2

Current OWASP recommendation (fetched, Password Storage Cheat Sheet, T1):

AlgorithmWhen to useCurrent parameters
Argon2idPrimary recommendation, use unless you have a specific reason not tom=19456 (19 MiB), t=2, p=1 (minimum config); alternates m=12288,t=3,p=1 or m=9216,t=4,p=1 trade memory for iterations
scryptFallback if Argon2id is unavailable in your stackN=2^17 (128 MiB), r=8, p=1 minimum
bcryptLegacy systems only, not a first choice for new systemswork factor minimum 10
PBKDF2Only when FIPS-140 compliance is a hard requirementPBKDF2-HMAC-SHA256: 600,000 iterations; PBKDF2-HMAC-SHA512: 220,000 iterations

The bcrypt 72-byte truncation trap. "bcrypt has a maximum input length of 72 bytes for most implementations" (T1, same source). Any password bytes past the 72nd are silently ignored, not rejected, so "correct-horse-battery-staple-plus-70-more-characters-that-do-nothing" and the same string with anything appended past byte 72 hash IDENTICALLY. If your own code enforces a max password length, cap it at or below 72 bytes AND actually enforce the cap (reject, don't silently truncate) so a user isn't misled into believing extra length adds entropy it doesn't. OWASP's own mitigation for cases where longer input matters is to pre-hash: bcrypt(base64(hmac-sha384(password, pepper)), salt, cost), using a separately-stored pepper, specifically to also defend against "password shucking" (an attacker who already has your hash DB pre-computing bcrypt hashes of known-breached passwords and matching without ever seeing the plaintext).

What Solen actually does. Solen never implements its own password hashing. Password storage is entirely inside Supabase Auth (GoTrue): "Supabase Auth uses bcrypt... to store hashes of users' passwords, stored in the encrypted_password column of auth.users" (T2, Supabase Password security docs via search, corroborated by supabase/auth GitHub issue #1750 confirming bcrypt as the write path and Argon2i/id + Firebase scrypt as read-compatible verify paths for migrated accounts). This means: Solen is currently on bcrypt, not Argon2id, for password hashing, but this is a GoTrue/Supabase platform decision, not something Solen's own code controls or should try to override (there is no supported "switch Supabase Auth to Argon2id" configuration as of this research). This is correct-but-out-of-Solen's-hands: if Argon2id-for-passwords ever becomes a hard requirement, it would mean leaving Supabase's managed Auth for password storage entirely, a large migration, not a config flag. Not recommended at Solen's scale; bcrypt at GoTrue's default work factor is still an acceptable T2-grade choice, just not the current T1 ideal.

Where this would matter for Solen's OWN code (not Supabase Auth). Any place Solen hashes a secret itself, an API key, a webhook shared-secret comparison, an invite-token hash, should follow the same order (Argon2id preferred; for something that's really a high-entropy random token rather than a human-chosen password, a plain HMAC-SHA256 comparison is fine and cheaper, since slow hashing exists specifically to blunt brute-forcing LOW-entropy human-chosen secrets, not high-entropy random tokens).

4. NIST SP 800-63B password policy

Current revision, verified. NIST published SP 800-63, Revision 4 in July 2025, which supersedes 800-63-3 (T1, confirmed via csrc.nist.gov and pages.nist.gov/800-63-4 both showing 800-63B-4 as current, 800-63B (rev 3) marked Withdrawn). Cite this as SP 800-63-4 (or "800-63B-4" for the authentication-specific volume), not "800-63-3", in any future Solen doc, the older number is now stale.

What it actually mandates (fetched, pages.nist.gov/800-63-4/sp800-63b.html, T1):

  • Length over composition. Minimum length 8 characters IF multi-factor authentication is also in use; minimum 15 characters for single-factor (password-only) authentication. Maximum length must be permitted to at least 64 characters (to not block passphrases).
  • No composition rules. Explicitly: verifiers "SHALL NOT" impose composition rules (forced mixes of uppercase/lowercase/digit/symbol).
  • No forced periodic rotation under normal conditions; a forced change is only required "if there is evidence the authenticator has been compromised."
  • Breached-password blocklist check is required. Verifiers must compare the prospective password against a blocklist of known breached/commonly-used/expected passwords (the practical implementation almost everyone uses is the "Pwned Passwords" k-anonymity API or a downloaded copy of the list).
  • Paste and password-manager support is explicitly endorsed, not merely tolerated: "SHOULD permit... the 'paste' function," and should not fight browser autofill.

Where Solen currently deviates (grep-verified this run). app/api/auth/signup/route.ts (signupSchema, per _docs/BACKEND.md section 1) and app/[locale]/auth/reset-password/page.tsx:52 both enforce "8+ characters, one uppercase, one digit", i.e. a composition rule NIST 800-63-4 explicitly says not to impose, and neither route checks the new password against a breached-password list. This is a real gap against the current T1 standard, not a stylistic quibble: composition rules are the exact anti-pattern 800-63-4 spent its revision cycle telling the industry to drop, because they push users toward predictable substitutions (Password1!) that are easier, not harder, to crack, while doing nothing to stop credential-stuffing with an already-breached password that happens to satisfy the composition rule.

Recommended default and its cost. Move Solen's password schema to: minimum 10-12 characters (Solen has no separate MFA requirement today, so treat it as single-factor and lean toward the 15-char NIST floor, though a pragmatic middle ground like 10 is a defensible product call given consumer drop-off at 15), no composition requirement, max length near bcrypt's 72-byte ceiling, and add a Pwned-Passwords check on both signup and password-change. Cost: this IS a user-facing change (existing users with an 8-char password aren't retroactively invalidated, only new/changed passwords get the new rule) and a Pwned-Passwords API call adds one external network hop to the signup/reset critical path, budget for that call failing open (don't block signup if the breach-check API times out) rather than failing closed. This is a small, well-scoped fix, not a redesign.

5. Email verification

What the standard says (OWASP Authentication Cheat Sheet, fetched, T1/T2). Changing a verified email address should require re-proving identity (current password for non-MFA accounts, MFA re-verification for MFA accounts) and should send a nonce/confirmation link to the proposed new address before it becomes active, with a notification-only email to the OLD address so the real owner is alerted even if they didn't initiate the change (catches session-hijack-then-change-email attacks).

What Solen does today. app/api/auth/signup/route.ts:52-59 sends emailRedirectTo via Supabase's built-in signUp() confirmation flow, landing on app/api/auth/callback/route.ts, and deliberately returns the same generic response for both new and already-registered emails (T2, anti-enumeration, matches OWASP guidance directly). There is no dedicated "change your email address on an existing account" flow visible in the grepped surface, this is a gap only if Solen actually offers users an email-change feature; if it does not yet, there's nothing to harden.

Recommended default. Keep the current signup-confirmation shape (it already matches the standard). If/when an email-change feature ships, require current-password re-entry, confirm via a link to the NEW address, and notify the OLD address, don't let a stolen session silently redirect all future login recovery to an attacker-controlled inbox.

6. Password reset

What the standard says (OWASP Forgot Password Cheat Sheet, fetched, T1). Reset tokens must be: cryptographically random and "sufficiently long to protect against brute-force" (no specific bit count given in the cheat sheet itself, use the same CSPRNG discipline as session IDs, effectively 128+ bits), single-use (invalidated the moment they're consumed), expiring "after an appropriate period" (industry practice converges on 15 minutes to 1 hour, though the cheat sheet itself doesn't pin a number), and the response for both the request-a-reset step and the actual reset-completion step must be enumeration-safe: identical message and identical response TIMING whether or not the account exists. Critically: "ask the user if they want to invalidate all of their existing sessions, or invalidate the sessions automatically" after a successful reset.

What Solen actually does (grep + read-verified this run). Password reset flows entirely through Supabase's built-in resetPasswordForEmail (app/api/auth/login/route.ts:50-56) and updateUser({password}) (app/[locale]/auth/reset-password/page.tsx:66). Supabase's own recovery link/token mechanics (entropy, single-use, expiry) are the platform's responsibility and are reasonable to trust (Supabase is a widely-audited Auth-as-a-service provider). The gap is specific and confirmed by reading the actual file: app/[locale]/auth/reset-password/page.tsx calls supabase.auth.updateUser({ password }) and, on success, simply shows a success toast and redirects to /auth/login after 2.5 seconds (page.tsx:63-71). There is no call to sign out other active sessions (Supabase exposes supabase.auth.signOut({ scope: "others" }) for exactly this) anywhere in that file or its API-route counterparts. Concretely: if an attacker has an active, still-valid session on a victim's account (say, from an earlier credential-stuffing hit before the victim notices and resets their password), the victim resetting their password today does NOT kick the attacker's existing session out. This is the single most concrete, fixable finding in this research file, small in scope (one added signOut({scope:"others"}) call, or a call to Supabase Admin's session-invalidation for the user), directly named by the current OWASP standard, and directly falsifiable against the code (page.tsx:66, no session-invalidation call anywhere nearby).

Recommended default and cost. Add await supabase.auth.signOut({ scope: "others" }) (or equivalent admin-side session revocation) immediately after a successful updateUser({password}) in the reset flow, and consider the same after a user-initiated password CHANGE (not just a forgot-password reset). Cost: near zero engineering effort, one line; the user-facing effect is that if they were logged in on another device before the reset, that device gets logged out, which is the CORRECT and expected behavior, not a regression to soften.

7. Magic links

The tradeoff. A magic link (click an emailed link, no password) trades "remembering a password" for "having access to your email inbox at the moment of login." This concentrates all authentication trust into the email provider: if the user's email account is compromised (a very common real-world compromise vector, email accounts are reused, phished, and SIM-swap-adjacent-recoverable far more than people expect), the attacker now controls login to every service using magic links tied to that inbox, with no separate secret to additionally compromise. Magic links also have UX friction (context-switch to an email client, possible delivery delay, easy to lose in spam) and a security nuance often missed: the link itself is a bearer credential, if it's not single-use and short-expiry it is exactly as dangerous as a leaked password, and if the email client prefetches links (some corporate security scanners auto-click every link in an inbox to scan it) the link can be consumed before the real user ever sees it.

What Solen does today. Magic links exist ONLY in the dev-only session-minting shortcut (app/api/dev/login/route.ts:18-60, hard-gated to NODE_ENV === "development", 404s in the real Netlify production build) via admin.auth.admin.generateLink(). There is no production-facing "log in via magic link, no password" feature for real users; Supabase's signInWithOtp capability exists on the platform but Solen doesn't call it for customer/owner login (grep-confirmed, zero hits for signInWithOtp outside the dev route).

Recommended default. Don't add production magic-link login for Solen unless there's a specific product reason (e.g. reducing signup friction for first-time salon-owner onboarding). If it's ever added, treat the link exactly like a password-reset token: single-use, short expiry (under 15 minutes), and don't rely on it as the ONLY factor for the salon-owner/staff dashboard tier where Stripe Connect payout access sits behind it, pair it with the same MFA push recommended in section 10.

8. OAuth2 / OIDC + PKCE

Why the implicit flow is dead. The OAuth 2.0 implicit grant returns the access token directly in the URL fragment after redirect, no code-exchange step. This means the token can leak via browser history, the Referer header on a subsequent navigation, or any JS on the page (including third-party scripts) that reads location.hash. RFC 9700, the current OAuth 2.0 security Best Current Practice (fetched, datatracker.ietf.org/doc/rfc9700, T1), states the implicit grant "SHOULD NOT" be used, full stop, in favor of the authorization-code flow.

PKCE is now mandatory, not optional, even for confidential (server-side) clients. RFC 7636 (fetched, datatracker.ietf.org/doc/html/rfc7636, T1) was written to close the "authorization code interception" attack against PUBLIC clients (mobile/SPA apps that can't hold a client secret): the client generates a random code_verifier, sends its SHA-256 hash as code_challenge in the authorization request, and must present the original code_verifier at the token-exchange step, so an intercepted authorization code is useless without the verifier that never left the legitimate client. RFC 9700 goes further and says authorization servers "MUST support PKCE" and it should be used by confidential clients too, not just public ones, as defense-in-depth against code injection.

Redirect URI validation must be exact-string-match. RFC 9700: servers "MUST utilize exact string matching" when validating redirect URIs (the one carved-out exception is variable localhost ports for native-app loopback redirects). A prefix-match or wildcard-match redirect validator is a known open-redirect-into-token-theft vector.

Refresh tokens for public clients need sender-constraining or rotation. RFC 9700: refresh tokens issued to public clients "MUST be sender-constrained or use refresh token rotation" specifically because a public client can't prove it's the same client that received the original token the way a confidential client's client-secret does.

What Solen actually does. Solen's Google/Apple OAuth (components-legacy/auth/SignIn.tsx:54-74, landing on app/api/auth/callback/route.ts:8-72) runs through @supabase/ssr's createBrowserClient/createServerClient, which default to PKCE flow for both browser and server clients (T2, confirmed via Supabase's own SSR advanced-guide and supabase/ssr source, "clients are initiated to use the PKCE flow by default... automatically configured to handle saving/retrieval of session information in cookies"). Solen's own OAuth callback route separately validates the redirect/next query param against startsWith("/") + no // prefix + no backslash (app/api/auth/callback/route.ts, per _docs/BACKEND.md), which is Solen's OWN open-redirect guard on top of Supabase's OAuth exchange, a reasonable belt-and-suspenders addition, not a replacement for redirect-URI exact-matching (which is enforced on the Supabase Auth provider side, in the Supabase dashboard's allowed-redirect-URLs config, not in this repo's code, worth confirming that config is a tight allowlist, not a wildcard).

Recommended default and cost. No code change needed here, Solen is compliant with RFC 9700's core recommendations (PKCE, no implicit flow) by virtue of the platform default, not a deliberate choice anyone made, which is exactly why this needs to be WRITTEN DOWN: if a future refactor ever sets flowType: "implicit" explicitly (there is no reason to, but it's a one-line regression risk) or someone builds a bespoke OAuth client outside @supabase/ssr, they'd silently walk this protection back. The action item is a one-time check of the Supabase project's "Redirect URLs" allowlist (dashboard config, not code) to confirm it's a tight exact-match list, not a wildcard domain.

9. SSO / SAML

What the current sources say. SAML moves signed XML assertions through browser redirects and POST bindings; it is overwhelmingly an enterprise B2B pattern (an IdP like Okta/Azure AD federating employee logins into many corporate SaaS tools). OIDC (JSON, built on OAuth2) is the modern, lighter-weight equivalent and is what nearly every source converges on for consumer-facing (B2C) apps: "if you're a consumer-facing application (B2C) you're just fine supporting OIDC alone" (T2/CONV, converging across Clerk, Stytch, and several other vendor comparisons found via search this run). None of these sources are a formal standards body ruling "never use SAML for B2C", so tier this CONV, a coordination convention the industry has converged on for good structural reasons (SAML's XML-signature complexity and enterprise IdP assumptions don't map to a consumer signup flow), not an empirical law.

Solen's actual position. Solen already has Google and Apple OAuth (OIDC-family, federated consumer login), which is exactly the right layer for a B2C marketplace. There is no SAML anywhere in the codebase (grep-confirmed no saml hits), and there should not be one, unless Solen ever needs to sell a white-label or franchise product INTO a business customer who mandates their own corporate IdP for their staff logins, a B2B use case Solen does not have today.

Premature-at-scale note. SAML/enterprise SSO is squarely in the "correct at scale, wrong for us now" bucket, see the dedicated section below.

10. MFA / TOTP (RFC 6238)

What TOTP is. RFC 6238 (fetched, datatracker.ietf.org/doc/html/rfc6238, T1) extends HOTP (event-counter-based one-time passwords, HMAC-based) by using TIME as the moving factor instead of a counter, so both sides (server and the authenticator app) derive the same 6-digit code from a shared secret and the current Unix time divided into 30-second steps, without needing to stay in sync on a counter. Default time step is 30 seconds ("a balance between security and usability"). The underlying HMAC can be SHA-1 (the near-universal default every authenticator app supports), SHA-256, or SHA-512; shared secret length should match the HMAC's output length (20 bytes for SHA-1, the practical minimum virtually every implementation uses).

Why MFA matters more than almost anything else in this file. OWASP's Authentication Cheat Sheet states MFA "would have stopped 99.9% of account compromises" (T2, this is Microsoft's own widely-cited internal telemetry claim as relayed by OWASP, tier it T2 rather than T1 since it's a single vendor's internal number relayed secondhand, but it converges with essentially every other industry source on MFA being the highest-leverage single control against credential-stuffing and phishing, which are the dominant real-world account-takeover vectors, not sophisticated cryptographic attacks).

TOTP's own weakness, honestly stated. TOTP is phishing-VULNERABLE: a real-time phishing proxy (an attacker's fake login page that relays the victim's password AND their live TOTP code to the real site within the 30-second window) defeats TOTP completely, it only stops REPLAY of a stolen code after the window expires, not a live man-in-the-middle at login time. This is exactly why WebAuthn/passkeys (section 11) are the phishing-resistant upgrade path, the private key never leaves the device and never transmits anything a phishing proxy could relay.

What Solen actually has. Nothing. Grep across app/ and lib/ for totp, mfa, webauthn, passkey returns zero hits outside unrelated string matches. Yet Supabase Auth ships TOTP MFA "free to use... enabled on all Supabase projects by default" (T2, Supabase MFA/TOTP docs via search) via a simple three-call flow (mfa.enroll() → show QR → mfa.verify()). This is a real, concrete, currently-unused capability sitting on the platform Solen already pays for and already uses, not a "go build a new system" ask.

Recommended default and cost. Do NOT force MFA on every customer account (friction that doesn't match Solen's B2C low-stakes-browsing majority use case). DO offer/require it for the highest-blast-radius account tier: salon owners and staff with dashboard access (they can see other customers' PII and, via Stripe Connect, are adjacent to real payout money movement, per _docs/BACKEND.md section 4). Cost: enrollment UX (QR code screen, recovery-code generation and secure display, a "lost my authenticator" recovery support flow) is real product work, budget a small dedicated build, not a footnote; the API cost itself is zero (Supabase includes it). This is the single highest-value NEW auth work this research surfaces for Solen, more valuable than any of the cookie/policy nudges above.

11. Passkeys / WebAuthn

Standard status. W3C published a Candidate Recommendation snapshot of WebAuthn Level 3 on 2026-01-13, open for implementation feedback until at least 2026-06-23 (T1, w3.org/TR/webauthn-3 via search). WebAuthn Level 2 (the prior, more stable level) is already supported by all major browsers (Chrome 120+, Firefox 118+, Safari 17+, Edge 120+). The core property that makes passkeys phishing-resistant: the private key is generated and stored on the authenticator (device secure enclave or hardware key) and NEVER transmitted; the browser cryptographically binds the credential to the exact origin it was created for, so a phishing site on a look-alike domain simply cannot obtain a valid signature, unlike a password or a TOTP code which a user CAN be tricked into typing into the wrong site.

Supabase's own support is beta, dated this year. Supabase announced beta Passkey support for Supabase Auth on 2026-05-28 (T2, Supabase changelog #46458 via search), requiring @supabase/supabase-js v2.105.0+ (Solen is on 2.110.2, so version-compatible) and explicit opt-in at client-creation time; the API is explicitly flagged as subject to change without notice.

Recommended default and cost. Track this, don't build on it yet. A beta auth primitive from any provider, even a trusted one, is the wrong foundation for a production payment-adjacent flow; "the API may change without notice" is not a hypothetical caveat for a marketplace that can't afford an auth outage. Revisit when Supabase marks passkey support generally available (not beta). Until then, TOTP (section 10) is the pragmatic phishing-reduction step available today without depending on a moving API.

12. Refresh token rotation + reuse detection

What Supabase actually implements (fetched + search-corroborated, T2, Supabase Sessions docs + DeepWiki/supabase/auth refresh-tokens page). Refresh token rotation is on by default for every Supabase project. Mechanically: each session tracks a monotonic counter; a normal refresh matches the presented token's counter to the session's counter and increments it, issuing a new ("child") refresh token and invalidating the old one. A short 10-second reuse interval tolerates the same (now-superseded) refresh token being presented again within that window without treating it as an attack, this exists purely to absorb legitimate races (a flaky network causing a client to retry a refresh call, or concurrent tabs/SSR requests refreshing near-simultaneously), not as a security weakening; Supabase's own docs say this interval is "not recommended to be changed." Outside that 10-second grace window, presenting an already-superseded (revoked) refresh token is treated as reuse detection firing: GoTrue immediately revokes the ENTIRE token family descended from the compromised token, which is the correct response to "someone has a stale copy of my refresh token", it kills not just that one token but every token chain descended from it, on the theory that if an old token shows up again, an attacker likely copied it at some point in the past and the whole lineage since is suspect.

Why this matters and what it defends against. Refresh-token rotation with reuse detection is specifically the mitigation for "an attacker stole a refresh token once (a leaked log line, a compromised backup, a MITM'd network) and is now replaying it alongside the legitimate user continuing to use their own, still-rotating token." Without rotation, a stolen refresh token is valid until its (very long, "never expires" per Supabase) natural end, silently, forever, with no signal to the legitimate user that anything is wrong. With rotation+reuse-detection, the MOMENT the attacker uses their stale copy, the real user's session gets forcibly logged out too (collateral, but a clear and honest signal something happened) and the attacker's access is killed at the same time.

What Solen actually does. Nothing to configure, this is a platform default already active on every Supabase project, Solen included, by virtue of using Supabase Auth for session management (lib/supabase.ts, @supabase/ssr). There is no code in Solen that opts out of it. This is worth stating plainly in this file specifically because it's easy for a future session to assume "we don't do refresh-token rotation" simply because there's no visible code implementing it, when in fact it's happening below the app layer, inside GoTrue, on every session.

Recommended default. Leave it exactly as-is; do not build a custom session/refresh layer to "add" rotation, it already exists. The only thing worth periodically checking is whether Solen's own session client-side handling (lib/supabase-browser.ts, lib/supabase.ts:90 disables autoRefreshToken on the ADMIN client specifically, which is correct, since the admin/service-role client isn't a user session) ever accidentally caches or persists a refresh token somewhere outside Supabase's own storage abstraction (localStorage exposure would defeat the whole point, see the Session Management Cheat Sheet's explicit warning against storing tokens in localStorage/sessionStorage, section 2).

13. Session revocation

What the standard says. OWASP's Session Management Cheat Sheet (fetched, T1) requires BOTH server-side invalidation (destroy the session server-side, e.g. delete the row/token) AND client-side cookie clearing (Set-Cookie with an expired date, plus optionally the Clear-Site-Data response header on logout to also purge cache/storage). A session ID must be treated as attacker-controllable input and validated, never trusted blindly. Re-authentication (not just "are you still logged in" but "prove your password again right now") should be required before sensitive actions: password change, email change, payment-method change, MFA enrollment change.

What Solen actually does. Sign-out flows through Supabase's own signOut(), which deletes the session server-side (the refresh-token row) and Solen's SSR cookie-writing wraps that into clearing the cookie on the response. The ban gate (checkUserBanned, lib/feature-flags.ts:149-183) is a SEPARATE, additional revocation-adjacent mechanism: even if a banned user's JWT/session is technically still valid, every request that calls checkUserBanned() after getUser() gets a 403 within a 10-second cache window (T0, confirmed by reading _docs/BACKEND.md section 1 grounding, which itself cites lib/feature-flags.ts:119 for the TTL). This is a reasonable belt-and-suspenders layer: it means "kill this account NOW" doesn't strictly require deleting every session row, flipping banned_at is enough, PROVIDED the calling route actually checks it (see the honest caveat below).

A real gap already documented in this codebase, worth repeating here because it's an AuthN-adjacent revocation gap. Per _docs/BACKEND.md section 1 (already-existing project documentation, corroborated, not re-derived here): three separate "is this account restricted" fields exist on profiles (banned_at/ban_reason, is_suspended, account_status), but only banned_at is actually read by the live enforcement gate, and banned_at currently has NO application-level write path (only a raw DB write can set it). is_suspended has an admin-UI write path but is never checked by anything. This means today, flipping "suspend user" in the admin panel does not actually revoke anything, a genuine silent no-op in exactly this project's documented failure-mode pattern. This is not new research, it's flagged here because it sits squarely inside "session revocation" and any future AuthN work should not assume the admin panel's suspend button does what its label says.

Recommended default and cost. Wire is_suspended (or consolidate onto one canonical field) into checkUserBanned()'s check, and add a write path for banned_at through the admin UI rather than requiring a raw SQL write. Small, scoped fix (one function edit + one route), already scoped and named in the existing backend doc, not new scope this file is inventing.

14. Admin impersonation and its audit trail

What the (T2/T3, no formal standard exists for this specific pattern) converging practitioner guidance says. Log at minimum: who initiated the impersonation session, whose identity was assumed, a reason/ticket reference, and every action taken while impersonating (T3, OneUpTime, "How to Build Impersonation Implementation"). Impersonation sessions should have a SHORTER token lifetime than a normal session (one hour is a commonly cited default), should require just-in-time approval or at minimum be bound to a reviewable reason code, and should have a role-hierarchy limit (support staff impersonate regular users only; only a higher tier can impersonate anyone, and even then typically excluding other admins). The audit log itself should be visible to any admin, not just the one who acted, specifically so impersonation is a WATCHED capability, not a private backdoor. None of this is a formal RFC/NIST-grade standard, it is converged practitioner consensus, tier CONV/T3, verify any specific number (the "one hour" impersonation-token lifetime, for instance) against your own risk tolerance rather than treating it as a law.

What Solen actually does. There is exactly one impersonation-shaped feature in the grepped codebase: app/api/admin/preview-salon/route.ts, which sets an httpOnly+sameSite=lax cookie (per the earlier cookie grep), almost certainly a "preview a salon's dashboard as an admin" feature. This file was not read in full this run (out of this research pass's scope to audit line-by-line), so whether it currently logs WHO previewed WHAT and WHEN is unverified by this research pass and should be confirmed by actually reading app/api/admin/preview-salon/route.ts before relying on any claim about its audit behavior. There is no grep hit for a dedicated "impersonate as this customer" admin feature (only the salon-preview cookie), so Solen's actual admin-impersonation surface appears to be narrow (salon-preview only) rather than a general "log in as any user" tool, which meaningfully lowers the risk here versus a support tool that can assume ANY user's identity.

Recommended default and cost. Before this feature grows (e.g. if a future "log in as this customer to debug their booking" support tool is proposed), require: an explicit audit-log INSERT at impersonation start and end (actor id, target id, reason, timestamp), a short session lifetime distinct from a normal login session, and restrict it to admin role only (never salon_owner). This is a "build it right when it's built," not a "go audit preview-salon today" ask, given Solen's current admin-impersonation surface is narrow.

Myths and traps

  • MYTH: "JWTs don't need a database, so they scale better, full stop." True only if you never need to revoke one early. The moment you add a revocation list, you've reintroduced the exact server-side state you were trying to avoid, so the "no DB" claim quietly becomes false in practice for any real app with a logout button. (T2, section 1.)
  • MYTH: "Password composition rules (require an uppercase + a digit + a symbol) make passwords stronger." NIST 800-63-4 explicitly rejects this; composition rules push users toward predictable, easily-guessed substitutions and don't meaningfully raise entropy against a real attacker who already has breached-password lists. Solen's own signup/reset schemas currently do this, it's a documented gap, not a myth Solen is immune to.
  • MYTH: "SameSite=Lax alone is full CSRF protection, no token needed." Lax blocks cross-site POSTs and most subresource requests, but state-changing GET endpoints (if you have any, which is itself an anti-pattern) and certain edge cases (top-level navigation with method GET carrying query-string side effects) can still leak through. SameSite is a strong layer, not a substitute for a CSRF token on money-moving or destructive actions.
  • MYTH: "SMS OTP is a fine MFA factor, it's what my bank uses." NIST classifies SMS OTP as a "restricted authenticator" specifically because of SS7 interception and SIM-swap attacks; it is tolerated, not recommended, and should not be Solen's first MFA choice if TOTP is available (T2, OWASP MFA cheat sheet).
  • OUR STACK'S TRAP #1 (serverless): the getUser() network round-trip on every privileged request is a REAL, not theoretical, cold-start/latency cost on Netlify's Lambda-backed Next.js runtime. This is why middleware.ts races it against a 4-second timeout, treat that timeout+reject-equivalence as load-bearing security code, not an incidental perf guard, per _docs/BACKEND.md's own documented history of a prior bypass bug here.
  • OUR STACK'S TRAP #2 (PostgREST/RLS): a session-scoped Supabase client silently matching ZERO rows on an owner-gated table update is NOT an authentication bug, it's an authorization/RLS interaction, but it is routinely MISDIAGNOSED as "the user's session must have expired" by whoever's debugging it. The actual fix in this codebase (lib/bookings/claim-slot.ts) is to use the service-role client for that specific write while still gating it in application code, this belongs in the reader's mental model of "what does an auth failure even look like here" even though it isn't strictly an AuthN bug.
  • OUR STACK'S TRAP #3 (Netlify, not Vercel): any copy-pasted auth/session guidance that assumes Vercel Edge Middleware's specific runtime constraints (e.g. certain Node API availability inside edge middleware) may not transfer cleanly to Netlify's Next.js runtime. Verify against Netlify's own @netlify/plugin-nextjs behavior before assuming a Vercel-authored blog post's middleware pattern applies as-is.
  • OUR STACK'S TRAP #4 (Stripe Connect adjacency): the salon-owner/staff dashboard session is not "just another logged-in user", it sits one hop from real payout money movement. Any AuthN hardening priority call (where to spend the MFA effort, where a shorter session timeout matters) should weight this tier higher than the customer-browsing tier, they are not equally risky sessions even though they run through the identical auth code path today.

Premature at our scale

  • SAML/enterprise SSO. Correct once Solen has a B2B customer (e.g. a franchise chain) whose IT department mandates federating their staff logins through a corporate IdP. Trigger to revisit: the first actual enterprise/franchise deal that names SAML as a contractual requirement. Building it speculatively now is pure unused surface area.
  • Sender-constrained tokens (DPoP / mutual TLS) for refresh tokens. RFC 9700 recommends these for PUBLIC clients as an even-stronger alternative to bare rotation. Supabase's built-in rotation+reuse-detection is already a reasonable T2-grade mitigation for Solen's actual threat model (a web + eventual mobile-app consumer marketplace, not a multi-tenant API platform issuing tokens to untrusted third-party public clients). Trigger to revisit: Solen ever issues API tokens to genuinely UNTRUSTED third-party integrators (a public developer API), which is not on the roadmap today.
  • A custom session store / bespoke JWT signing to "own" the session layer instead of Supabase Auth. This would trade a well-audited managed Auth provider (with rotation, reuse detection, and a maintained security-fix cadence) for homegrown code Solen would have to audit itself. There is no scale threshold that makes this a good idea for Solen; it would only become defensible if Solen needed an auth capability Supabase genuinely cannot provide (some very specific federation or compliance requirement), not as a general "more control" upgrade.
  • Full WebAuthn/passkey rollout as the PRIMARY login method. Correct end-state for phishing resistance industry-wide, but premature specifically because Supabase's own support is beta as of this research (May 2026). Trigger to revisit: Supabase marks passkey support generally available (not beta) and Solen has confirmed cross-browser/cross-device passkey UX doesn't strand a meaningful share of Solen's actual customer device mix (older Android/Safari versions still in real use in the Swiss market).
  • Real-time risk-based/adaptive authentication (behavioral biometrics, device-fingerprint risk scoring feeding a step-up MFA challenge). OWASP's Authentication Cheat Sheet gestures at "adaptive authentication models" for reauthentication triggers; this is genuinely valuable at a scale where anomaly detection has enough signal (traffic volume, a fraud team) to tune without drowning in false positives. At ~28 salons and Solen's current traffic, there isn't enough volume to responsibly build or tune this; a much simpler fixed rule set (require reauth on password/email change, on new-device login if that's ever tracked) covers the realistic near-term risk. Trigger to revisit: meaningful growth in transaction volume AND a first real fraud incident that a fixed rule set would have missed.

The gaps in detail

AUTHN-13: admin "Suspend" button is a silent no-op (HIGH)

What is wrong: three separate "is this account restricted" fields exist on profiles (confirmed live: banned_at/ban_reason, is_suspended, account_status), but the one live enforcement gate, checkUserBanned(), only ever reads banned_at:

lib/feature-flags.ts:158-159
  const { data: profile, error } = await admin
    .from("profiles").select("banned_at, ban_reason").eq("id", userId).single();
...
lib/feature-flags.ts:175
  const banned = !!profile?.banned_at;

Meanwhile is_suspended has a real, working write path:

app/api/admin/users/route.ts:61,66
  const { user_id, role, is_suspended } = validated;
  ...
  if (is_suspended !== undefined) updates.is_suspended = is_suspended;

and a real UI (app/[locale]/dashboard/all-users/page.tsx:120-128 toggles it via a "Suspend" confirm dialog that calls this route and updates the row in place). checkUserBanned() is called at the top of roughly 100 route handlers.

What breaks in practice: an admin opens the all-users dashboard, clicks Suspend on an abusive customer, sees the UI flip to "suspended", and believes the account is now blocked. It is not. Every route gated by checkUserBanned() still lets that user book, review, message, and transact normally, because the gate never looks at is_suspended. There is also no way to set the field the gate DOES check (banned_at) short of a raw SQL write in Supabase Studio, so the admin panel's suspend action and the code's actual ban check are two disconnected systems.

The fix and its cost: this is a one-function, one-route change. Either (a) extend checkUserBanned() to also read and OR-in is_suspended (cheapest, ~3 lines), or (b) go further and consolidate all three fields behind one check with account_status as the source of truth. Either way, also decide whether banned_at needs its own admin write path or should be retired in favor of is_suspended alone, since maintaining three parallel fields with only one enforced is exactly the kind of drift this project has been burned by before.

AUTHN-03: password reset does not invalidate other sessions (HIGH)

What is wrong: app/[locale]/auth/reset-password/page.tsx exchanges the recovery code for a session (:34-48), lets the user set a new password (:61, supabase.auth.updateUser({ password })), and on success just shows a confirmation and redirects to login (:67-68). Nothing in the file calls supabase.auth.signOut({ scope: "others" }) or any equivalent revocation.

What breaks in practice: a user resets their password specifically because they suspect their account was compromised (stolen laptop, leaked credential, a session that leaked via XSS elsewhere). Today, that reset changes the password but does nothing to the attacker's already-established session or refresh token; the attacker's session survives the very action meant to lock them out. This is precisely the scenario OWASP's Forgot Password Cheat Sheet calls out.

The fix and its cost: one line, right after the updateUser call succeeds: await supabase.auth.signOut({ scope: "others" }). Cheap, no schema change, no new route.

AUTHN-02: password policy is composition-based with no breach check (MEDIUM)

What is wrong: both the signup schema and the reset-password UI enforce "8+ chars, one uppercase, one digit" instead of a length floor with no composition rule:

app/api/auth/signup/route.ts:18-22
  password: z.string().min(8, "Mindestens 8 Zeichen")
    .regex(/[A-Z]/, "Mindestens ein Grossbuchstabe")
    .regex(/[0-9]/, "Mindestens eine Zahl"),

app/[locale]/auth/reset-password/page.tsx:53
  const passwordValid = password.length >= 8 && /[A-Z]/.test(password) && /[0-9]/.test(password);

There is no breach-list check anywhere in the codebase (zero grep hits for pwned/breach), and the platform-level equivalent, Supabase Auth's "leaked password protection" (HaveIBeenPwned check), is confirmed OFF per _plans/BACKEND_HEALTH_AUDIT_2026-07-14.md:48,134,146 (a Supabase dashboard toggle, an owner action, not app code).

What breaks in practice: composition rules push users toward predictable patterns (Password1!) that satisfy the regex but are weaker than a longer passphrase the rule would otherwise block, and without a breach check, a password already sitting in a public breach corpus is accepted without warning.

The fix and its cost: relax the zod schema and the UI validator to a length floor (NIST recommends 15+ for single-factor; Solen's current 8 is below even NIST's 8-with-MFA floor, and there is no MFA per AUTHN-09) with no forced uppercase/digit. The breach-check half is effectively free: flip Supabase's "leaked password protection" toggle (Auth > Providers > Password), which the health audit already queued as a 10-second owner action. Only the composition-rule removal needs a code change.

AUTHN-09: MFA does not exist (MEDIUM)

What is wrong: zero references to mfa, totp, webauthn, or passkey anywhere in app/ or lib/.

What breaks in practice: nothing breaks today, this is an absent control, not a bug. But it means the highest-blast-radius account tier (salon owner/staff dashboards, which sit next to Stripe Connect payout access) has exactly the same single-factor protection as a browsing customer account, and the composition-rule password policy above means a credential-stuffed or breached password is the only thing standing between an attacker and a salon's payout dashboard.

The fix and its cost: this is real product work, not a one-liner. Supabase's TOTP MFA API (auth.mfa.enroll/challenge/verify/listFactors) is free and already available on the project; the build is an enrollment UI, recovery-code flow, and a support/reset path, scoped to owner/staff roles rather than every customer.

AUTHN-12: salon-preview impersonation writes no audit trail (LOW)

What is wrong: app/api/admin/preview-salon/route.ts correctly gates on role === "admin" and restricts the target to [TEST]%-prefixed salons only, and its cookie expires in 1 hour, all good. But it never calls lib/audit.ts's logAuditEvent(), the audit-log helper 26 other admin routes (salon approve/reject/freeze/warn, commission changes, feature-flag toggles, discovery moderation) already use to write to the live audit_log table.

What breaks in practice: nothing today, because the route is scoped to test salons only, so there's no real customer/salon data exposure risk yet. But if this route is ever generalized to preview real salons (a natural next step for support tooling), there would be zero record of which admin previewed which salon, when, or why.

The fix and its cost: one extra call, await logAuditEvent(request, user.id, "preview_salon", "salon", salon_id), right before returning the response. Trivial, and worth doing before the route's scope is ever widened past test salons.

AUTHN-04: no __Host- cookie prefix (LOW)

What is wrong: none of the 4 sampled cookie sites use the __Host- name prefix. All correctly set httpOnly: true, sameSite: "lax", and secure conditional on NODE_ENV === "production" (deliberately, so local dev over plain HTTP still works, per the comment in lib/bookings/guest-access.ts:112-114).

What breaks in practice: nothing today; this is defense-in-depth against subdomain cookie-tossing, a threat that requires an attacker already controlling a sibling subdomain of solen.ch. Adopting __Host- also requires the cookie to be unconditionally Secure and Path=/, which conflicts with the deliberate prod-only Secure flag used for local dev.

The fix and its cost: low priority. If pursued, would need a dev-environment HTTPS setup first (so Secure can be unconditional), then a rename with a migration window for in-flight cookies.

What Solen already does RIGHT

  • getUser() discipline is real, not aspirational. Every server-side authorization decision in middleware.ts and the auth helpers uses getUser(). All 28 repo-wide getSession() calls were individually checked and are in "use client" files doing UI-only "already logged in, bounce away" checks, exactly the documented exception. The enforcement hook (no-getsession-authz-gate.py) is confirmed wired into .claude/settings.json in this worktree (a prior health audit flagged this as possibly missing; it is not missing here).
  • The backslash open-redirect bug found on 2026-07-09 is fixed. app/api/auth/callback/route.ts:18 now has all three guards (startsWith("/"), !startsWith("//"), !includes("\\")). Preserve all three if this line is ever touched again.
  • Signup's email-enumeration oracle is fixed and the fix is documented in the code. app/api/auth/signup/route.ts:70-74 returns the identical generic response whether the email is new or already registered, with an explicit SECURITY: comment explaining why. This closes the MEDIUM finding from the 2026-07-09 audit.
  • PKCE is the active OAuth flow by platform default and nothing overrides it. flowType is never set anywhere in the repo.
  • Rate-limiting's IP-spoofing hole is fixed. lib/ratelimit.ts:322-334's getClientIp() now prefers Netlify's trusted x-nf-client-connection-ip header (unspoofable at the edge) before falling back to the attacker-controllable x-forwarded-for, closing the HIGH finding from the 2026-07-09 audit that let an attacker bypass every auth-route rate limit by rotating a fake XFF header. Not one of this topic's 13 named principles, but directly load-bearing for auth-route abuse resistance, so worth recording here.
  • Solen never hand-rolls password hashing, and its own use of hashing (sha256 over 256-bit random tokens for booking-access and directory-claim codes) is the correct tool for that job, a slow KDF would be wasted effort on an already-infeasible-to-brute-force token.
  • No premature SAML or passkey dependency. Both correctly deferred per the research's own "correct at scale, not yet" framing, and nothing in the code contradicts that.

Would need the owner to open the dashboard or grant Management API access.
  • Refresh-token rotation and reuse-detection (AUTHN-07): entirely inside Supabase GoTrue; no app code implements, wraps, or could disable it, so there is nothing in this repo to point at as proof either way. Treated as "trust the platform" per the research's own framing, not independently verified here.
  • Whether preview-salon's 1-hour cookie is meaningfully shorter than "a normal session" in practice: a real logged-in user's session persists indefinitely via silent refresh-token rotation (also platform-internal, see above), so the comparison is against an unbounded baseline. The 1-hour absolute cap is a real, verifiable bound in the code; whether that counts as "shorter than normal" depends on how a normal Supabase access-token TTL is configured project-wide, which is also dashboard config, not code.
