The single most important fact for this file: Solen has almost none of the machinery this topic is usually written about. No Sentry, no OpenTelemetry, no structured logs, no request-id propagation, no SLOs, no paging system. What exists is a hand-built health probe (GET /api/health), 203 files calling console.error("[Component] ...", err), a daily founder-digest email, and Netlify's own function log viewer, whose retention window is measured in hours to days, not months. This file researches what the industry actually recommends, then draws the line, explicitly, between what is correct-at-scale and what Solen should adopt now.

0. The short version

  1. Structured (JSON) logs plus a request id on every line are what make "grep the logs" become "query the logs." This is a practice, not a formal standard: no RFC mandates it, but every major cloud logging backend (Google Cloud Logging, Datadog, Honeycomb) is built around parsing a JSON payload and indexing its fields, and the moment a log line is JSON, grep becomes an actual query language. T2 (Google Cloud Logging docs + OWASP Logging Cheat Sheet, converging).
  2. A request id (or W3C traceparent) generated at the edge and threaded through every log line and every downstream call is what turns "500 isolated console.error calls" into "the ten log lines that explain one failed booking." Solen currently has zero of this: not one file in app/ or lib/ generates or propagates a request/trace id. T1 (W3C Trace Context is a formal W3C Recommendation, the industry's actual interop format for this).
  3. RED (rate, errors, duration) is the right metric frame for Solen's request-driven API surface; USE (utilization, saturation, errors) is the right frame for its few managed resources (Postgres connections, Upstash Redis, function concurrency). They are not competing methods, they are for different things: RED was invented specifically because USE "doesn't really apply to services." T1/T2 (Tom Wilkie's own RED post, Brendan Gregg's own USE post).
  4. An SLO is a deliberately chosen, deliberately-not-100% target, and the honest way to pick one at Solen's size is to start from what a missed booking or a failed payment actually costs a salon, not from a benchmark number copied off a blog. Google's own SRE book states 100% availability is both impossible and the wrong goal to chase. T1 (Google SRE Book, Service Level Objectives chapter).
  5. Alert on symptoms (the SLO is burning) not on causes (CPU is at 80%), and use burn-rate math to decide page vs ticket vs email, not gut feel. This is the single highest-leverage fix available to a small team, because it is free (no new tooling) and it is the documented cure for alert fatigue. T1 (Google SRE Workbook, "Alerting on SLOs"; Rob Ewaschuk's "My Philosophy on Alerting," which the SRE book explicitly built on).
  6. "Liveness vs readiness" is a Kubernetes-specific pair of questions ("is the process alive" vs "should traffic be routed to it right now") that literally does not exist for Solen, because Netlify Functions have no long-lived process to restart or route around. The useful residue of the idea for Solen is a single dependency-health endpoint (which Solen already has), not two probes. T1 (Kubernetes docs) + T2 (serverless-health-check sources, directional).
  7. An audit trail is not "the logs, but kept longer." It is a specific, narrower thing: append-only, tamper-evident, retained on a defined schedule, and queryable well enough to answer "who did what, when" months later for a real legal or dispute reason. Solen's console.error output currently satisfies none of these four properties, and physically cannot, because Netlify's own function-log retention is measured in hours to days. T2 (audit-trail definition sources) + T1 (Netlify's own docs on function log retention).
  8. Never log a password, a session token, a full card number, or a Swiss AHV/social-insurance number; think hard before logging a name, phone number, or email at all. This is explicit in the OWASP Logging Cheat Sheet and it is also a GDPR/nFADP problem the moment a log line becomes "processing of personal data," which it legally is. T1 (OWASP Logging Cheat Sheet) + T1 (Swiss FADP Art. 5(h), Art. 8).
  9. OpenTelemetry is the right long-term interoperability layer for traces/metrics/logs, and it is real, non-trivial adoption cost (a collector to run, a semantic-convention vocabulary to learn, breaking-change churn the project's own governance committee has publicly admitted to). At 28 salons on one Next.js app, the entry cost buys almost nothing Solen doesn't already get more cheaply from a request-id convention plus PostHog/Sentry-class tooling. T1 (OpenTelemetry's own docs) + T2 (2026 adoption-cost reporting, directional).

1. Structured logs (JSON, not string soup) and request id / trace id propagation

The question. Solen's current logging convention (203 files) is console.error("[ComponentName] description:", err), a human-readable string with an ad hoc bracketed prefix. Is this good enough, and if not, what specifically should replace it, and why does a request id matter more than the JSON format itself.

What the evidence says. There is no RFC or formal standard mandating JSON logs; this is a converged industry practice, not a law. Google's own Cloud Logging docs describe the mechanism precisely: when a log payload is a JSON object, it is stored in a queryable jsonPayload field, "you can construct queries that search specific JSON paths and you can index specific fields," whereas a plain-text log line only supports substring search. Google also documents a small set of "special fields" a JSON log can set to get first-class treatment: severity, logging.googleapis.com/trace, logging.googleapis.com/spanId, and httpRequest, specifically so a single log line can be correlated with a distributed trace. T2 (cloud logging structured-logging docs). The OWASP Logging Cheat Sheet frames the same practice from the security-and-forensics angle rather than the cloud-vendor angle: it recommends capturing "when, where, who and what" for every event, and names an "interaction identifier" as "a method of linking all (relevant) events for a single user interaction," precisely so an investigator does not have to reconstruct a request's story from disconnected lines by timestamp-guessing. T1 (OWASP Logging Cheat Sheet). The 12-factor app methodology adds the deployment-shape argument: "a twelve-factor app never concerns itself with routing or storage of its own output stream," each process just writes its event stream unbuffered to stdout, and the execution environment (in Solen's case, Netlify's function runtime) is responsible for collating and routing it. T2 (12factor.net/logs). The request-id/trace-id propagation piece has an actual formal standard behind it: the W3C Trace Context specification defines the traceparent HTTP header as version-trace-id-parent-id-trace-flags (e.g. 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01), explicitly so that "the incoming request in a tracing system" has "a common format, understood by all vendors," and OpenTelemetry adopted it as its default propagation format. T1 (W3C trace-context spec, HTTP header format).

Where the real tradeoff lies. JSON logging costs almost nothing: it is a formatting choice at the call site, not new infrastructure. The actual cost is discipline (every call site has to remember the shape) and a slightly worse experience reading raw logs in a terminal by eye (a human parses [bookings] slot claim failed: err faster than {"component":"bookings","msg":"slot claim failed","err":"..."}, until there is tooling that pretty-prints it). Request-id propagation costs a little more: it needs to be generated once per request (at the edge, in middleware.ts, or at the top of each route handler if middleware doesn't run for API routes) and threaded into every log call and every outbound call (the Supabase client's error path, the Stripe SDK's error path, an email send failure) for the rest of that request's lifetime. Skipping propagation is what makes today's 203 independent console.error calls impossible to correlate: when a booking fails, the six log lines it produced across bookings/route.ts, email.ts, and a webhook handler have no shared key, so reconstructing "what actually happened to this one booking" means grepping by approximate timestamp and hoping nothing else happened in the same second.

Recommended default for Solen. Two independent, additive changes, in priority order: (1) generate ONE request id per inbound request (a crypto.randomUUID() is sufficient, a real traceparent header is nicer if a future tracing backend is added) and thread it through every console.error/console.log call for that request, cheapest to bolt onto the existing [Component] description string convention as a fourth field rather than a rewrite; (2) migrate the log payload itself to a JSON object ({ requestId, component, level, message, err }) opportunistically, file by file, not as a stop-the-world rewrite of 203 call sites. Cost: the request-id thread is the valuable 20%, the JSON-format switch is nice-to-have and can lag. Do NOT adopt a full structured-logging library (pino/winston) yet, see "Premature at our scale."

2. Metrics: RED for request-driven services, USE for resources

The question. What should Solen actually watch as its standing metrics, given it is mostly a request-driven API surface (354 routes) sitting on top of a small number of managed resources (Postgres via Supabase, Redis via Upstash, Netlify function concurrency)?

What the evidence says. These are two different, complementary methods invented for two different kinds of thing, not competing philosophies. RED (Rate, Errors, Duration) was created by Tom Wilkie in 2015, specifically because he found the existing USE method didn't fit services: "The USE Method doesn't really apply to services; it applies to hardware, network disks, things like this... We really wanted a microservices-oriented monitoring philosophy." Rate is "the number of requests per second," Errors is "the number of those requests that are failing," Duration is "the amount of time those requests take," and Wilkie's stated reason these three matter is that they are "a good proxy to how happy your customers will be." T1/T2 (Grafana Labs' own writeup of Wilkie's talk, grafana.com/blog/the-red-method-how-to-instrument-your-services). Google's SRE book generalizes this to the Four Golden Signals (latency, traffic, errors, saturation), the same idea with "saturation" folded in and latency explicitly split by outcome: "distinguish between the latency of successful and failed requests... a slow error is even worse than a fast error." T1 (sre.google/sre-book/monitoring-distributed-systems). USE (Utilization, Saturation, Errors) is Brendan Gregg's method, and by his own definition it is a resource-analysis checklist: "for every resource, check utilization, saturation, and errors," where utilization is "the average time that the resource was busy servicing work," saturation is "the degree to which the resource has extra work which it can't service, often queued," and errors are simple counts. Gregg's own stated scope-limit: it "solves about 80% of server issues with 5% of the effort" but "will, however, only find certain types of issues," it's "one tool in a larger toolbox," not a complete methodology. T1 (brendangregg.com/usemethod.html).

Where the real tradeoff lies. Applying USE to a request-driven API (asking "what's the utilization of the POST /api/bookings route") is a category error, there's no meaningful "percent busy" for a stateless serverless function; that's exactly the gap RED fills. Applying RED to a shared resource (asking "what's the error rate of Postgres") loses the actual bottleneck signal, which is about capacity being exhausted (connection pool saturation, disk IOPS, Redis eviction), not about a rate/error/duration triplet. Using only one method leaves a blind spot: RED alone tells you customers are unhappy but not why (could be app-code, could be the DB connection pool exhausted); USE alone tells you a resource is maxed but not whether users actually felt it.

Recommended default for Solen. Track RED at the API-route level (or at least route-group level: bookings, payments, search, auth) as the customer-facing signal, and USE at the level of Solen's three actual shared, capacity-bounded resources: Supabase Postgres (connection count against the plan's connection limit, query duration percentiles, error rate on 5xx/PGRST codes), Upstash Redis (command rate against the plan's rate limit, latency, error rate), and Netlify function concurrency/duration (relevant because Netlify functions have hard execution-time limits, a function timing out IS a saturation event, not just an error). Cost: today Solen collects almost none of this in any structured, queryable form. The realistic first step is not a metrics backend, it's making sure Supabase's own dashboard (already paid for) and Upstash's own dashboard (already paid for) are actually looked at, before building custom RED/USE dashboards. See "Premature at our scale."

3. SLI / SLO / error budgets, and picking an SLO honestly at small scale

The question. Should Solen define formal SLOs (e.g. "99.9% of bookings succeed") and, if so, how does a 28-salon marketplace pick a number that isn't either fake-precise or meaninglessly loose?

What the evidence says. Google's SRE book's own vocabulary, verified directly from the source: an SLI is "a carefully defined quantitative measure of some aspect of the level of service that is provided" (latency, error rate, throughput, availability are the common ones); an SLO is "a target value or range of values for a service level that is measured by an SLI," typically expressed as SLI ≤ target or within bounds; an SLA is "an explicit or implicit contract with your users that includes consequences of meeting (or missing) the SLOs," the defining feature being that a SLA has consequences and an SLO by itself does not. T1 (sre.google/sre-book/service-level-objectives). On picking one honestly, the book states its own principles directly: "start with user needs, not what's measurable," "keep it simple," "avoid absolutes" (100% availability "is impossible... can reduce the rate of innovation and deployment, require expensive, overly conservative solutions, or both"), and "base targets on desired performance, not current behavior" (locking in today's accidental performance as a permanent target creates an unsustainable "heroic effort" trap). The book's own error-budget framing: the gap between 100% and the chosen SLO is "the budget of how much unreliability is remaining," which functions as "an SLO for meeting other SLOs," and its stated payoff is political, not technical: it "removes the politics from negotiations between the SREs and the product developers when deciding how much risk to allow," because as long as budget remains, releases can keep shipping; once it's spent, the team's priority shifts to reliability work, by agreement, not by argument. T1 (same source, plus sre.google/workbook/error-budget-policy corroborating the same mechanic).

Where the real tradeoff lies. A number with no user-facing meaning ("99.95% uptime" copied off a SaaS status-page benchmark) is worse than no SLO at all, because it invites cargo-cult decisions (chasing the fourth nine when nobody, including the founder, actually knows what a missed nine costs a salon). A number that is too loose (a 95% SLO on booking success) is equally dishonest if the real failure mode, a booking silently not going through, costs a salon a walked-in customer and costs Solen trust; the SLO should reflect that specific cost, not an industry-average target. The Google framing assumes an organization big enough to have separate "SRE" and "product" teams whose negotiation the error budget is meant to depoliticize; Solen has no such split.

Recommended default for Solen. Pick one or two SLIs that map directly to money or trust, not a broad availability number: (1) booking-creation success rate (a booking request that starts but doesn't complete is the single worst failure Solen can have, directly costing a salon a customer), (2) payment-capture success rate. Set the SLO from a plain question, "how many failed bookings per week would make the founder personally intervene," not from an industry benchmark; that number, converted to a percentage of Solen's actual weekly booking volume, IS the honest SLO. Skip formal error-budget POLICY machinery (release freezes, budget-burn dashboards) at this size, see "Premature at our scale," but do track the raw SLI (bookings created vs bookings that error out) somewhere queryable, because right now Solen cannot answer "how often does a booking actually fail" with a number at all.

4. OpenTelemetry: what it is, the semantic conventions, and what adoption actually costs

The question. OpenTelemetry (OTel) is the industry's vendor-neutral instrumentation standard for traces, metrics, and logs. Should Solen adopt it now, and if not, what specifically is it buying that Solen would be giving up.

What the evidence says. OTel's own docs define semantic conventions as "common names for different kinds of operations and data," covering traces, metrics, logs, profiles, and resources, whose stated purpose is standardization: "by following a unified naming convention, teams avoid fragmentation" across codebases and vendors. T2 (opentelemetry.io/docs/concepts/semantic-conventions). On logs specifically, OTel's own docs are precise about the mechanism, and this is more nuanced than "OTel doesn't do logs": "OpenTelemetry provides a Logs API and SDK for producing log records" and that API "is public and can be used directly by application code," but in practice "as an application developer, the Logs Bridge API should not be called by you directly... instead, you just use your preferred logging library" with a configured bridge, so OTel's real value-add for logs is enrichment: "OpenTelemetry will automatically correlate your existing logs with any active trace and span, wrapping the log body with their IDs." T1 (opentelemetry.io/docs/concepts/signals/logs). Distributed tracing itself rides on the W3C Trace Context standard from section 1; OTel adopted traceparent/tracestate as its default propagation format, which is the actual interoperability win, any two OTel-instrumented services, regardless of vendor, agree on the wire format for "which trace and span is this."

On cost, directly from 2026 reporting. OTel's own Governance Committee has publicly acknowledged the adoption friction: "complexity and lack of stability" have created "impediments to production deployments," citing "breaking configuration changes, performance regressions at large deployments, and the difficulty of coordinating upgrades across hundreds or thousands of services." The project's own response, a 2026 "Blueprints" initiative, exists specifically "to reduce the growing complexity of deploying and operating observability systems at scale." T3 (2026 tech press, directional, not a formal OTel spec claim, but corroborated by the project's own governance committee admission cited within it). One further concrete operational detail worth flagging for any future adoption: running the OTel Collector (the piece that receives, batches, and exports telemetry) is commonly described as needing a minimum ~4GB memory footprint for graceful-shutdown behavior, i.e. it is not a lightweight sidecar to bolt onto a handful of serverless functions. T3, single-source, unverified against an official OTel resource-sizing doc, treat directionally only.

Where the real tradeoff lies. OpenTelemetry's entire value proposition is portability across MANY services and MANY backend vendors: instrument once, swap Datadog for Honeycomb for Grafana without re-instrumenting. Solen is one Next.js app, one deploy target (Netlify), and no plan to run multiple independently-deployed backends. The portability OTel sells is a solution to a problem Solen does not have. What OTel would cost: standing up and paying for (or self-hosting) a Collector, learning the semantic-convention vocabulary, and absorbing the project's own admitted churn, none of which Netlify's serverless function model makes any easier (a Collector wants to be a long-lived process; Netlify Functions are explicitly the opposite).

Recommended default for Solen. Do not adopt OpenTelemetry now (see "Premature at our scale"). Take the ONE piece of it that is genuinely cheap and portable regardless of backend: the traceparent request-id format from section 1, so that if Solen ever does add a tracing backend, the wire format is already right. Everything else (the SDK, the Collector, the semantic-convention vocabulary) waits for a trigger named below.

5. Error tracking

The question. Solen has no dedicated error-tracking tool (no Sentry, no Bugsnag); errors surface only as console.error lines that vanish from Netlify's log viewer within hours to days (see section 8). Is a dedicated error tracker warranted, and what does it actually add over logs.

What the evidence says. The practical distinction, stated directly by a vendor in this space but matching the shape of the problem regardless of which tool is chosen: "logging includes everything, not just information related to errors... when the same error fires 1,000 times across 1,000 users, your log aggregator shows 1,000 lines. [An error tracker] shows you one issue with a count of 1,000... full stack trace, affected users, browser/OS details, and the breadcrumb trail of what happened right before the crash." T3 (Sentry's own comparison page, vendor-sourced, but the underlying mechanic, deduplication/grouping of repeated errors into one issue with full context, is the generic value proposition of this whole tool category, not a Sentry-specific claim). Solen's own stack already includes PostHog (posthog-js/posthog-node, per package.json), and PostHog ships a genuine error-tracking feature: automatic or manual exception capture (posthog.captureException()), grouping into issues, and linking an exception to the same session recording and product-analytics context PostHog already collects for the user who hit it. T2 (PostHog's own error-tracking docs, posthog.com/docs/error-tracking).

Where the real tradeoff lies. A dedicated error tracker's whole value is automatic grouping (a spike in one root cause reads as "1 issue, 47 occurrences," not 47 log lines to eyeball) and rich per-error context (stack trace, breadcrumbs, affected user) that a console.error line will never have without deliberate work to attach it. The cost of NOT having one, concretely for Solen: 203 files call console.error, and the only place those lines are currently visible is Netlify's function log viewer, whose retention (24 hours to 7 days depending on plan, section 8) means an error from last week is already gone by the time anyone thinks to look, and there is no dedup at all, the same underlying bug logged 40 times across 40 bookings reads as 40 disconnected lines, not "1 bug."

Recommended default for Solen. Turn on PostHog's error tracking (posthog.captureException() in the existing server/client catch blocks, or its automatic-capture mode). Cost: near zero, PostHog is already a paid dependency and already wired client- and server-side; this is a config/adoption change, not new infrastructure. This closes the single biggest and cheapest gap in Solen's observability stack today. Do NOT additionally stand up Sentry: it would duplicate a capability Solen is already paying for and not using.

6. Alerting: page vs ticket vs email, and alert fatigue as the actual failure mode

The question. Solen's only standing "alert" today is a daily 05:15 UTC founder-ops email (app/api/cron/daily-digest/route.ts, reporting bookings created/completed, cron-run failures in the last 24h, and the pending-reviews backlog). Is this the right shape, and what should trigger something more urgent than an email.

What the evidence says. The foundational source here is Rob Ewaschuk's "My Philosophy on Alerting," written as a Google SRE and later folded directly into the Google SRE book's own alerting chapter. His stated criteria for a page: "urgent, important, actionable, and real," representing "either ongoing or imminent problems with your service," because a human can only sustain that level of urgent response "a few times daily before exhaustion sets in." Below that: tickets/bugs, sub-critical issues needing timely-but-not-immediate attention, which "fail without a responsible triage system" (an unowned ticket queue is where alerts go to die); and email/reports, periodic low-priority summaries, which need a designated person reviewing them, not an ignored mailing list. T2 (Ewaschuk's original doc). Google's own SRE book restates the same three-tier structure (pages, "lower-priority" notifications that "tend to easily become overrun with noise," and dashboards for subcritical conditions with no direct notification at all) and gives a concrete checklist for any alert rule: does it detect "an otherwise undetected condition that is urgent, actionable, and actively or imminently user-visible," can it be safely ignored, does it definitively indicate real user impact, does it enable swift action rather than a purely robotic response. T1 (sre.google/sre-book/monitoring-distributed-systems). On WHAT to alert on: both sources are explicit that symptom-based alerting beats cause-based alerting, "users care about unavailable data, not unavailable database servers," and cause-based signals should appear as supporting CONTEXT on a symptom-based page or on a dashboard, not fire their own page. The SRE Workbook's follow-on chapter operationalizes this for SLOs specifically: alert on burn rate (how fast the error budget is being consumed relative to the SLO), not on the underlying cause, using a tiered scheme (a fast-burn, short-window alert that pages, e.g. a rate that would exhaust 2% of a month's budget in an hour; a slow-burn, long-window alert that tickets, e.g. sustained 1x burn over 3 days) and recommending multi-window, multi-burn-rate alerts (require BOTH a long window and a short window to exceed threshold together) as "the most viable and most highly recommended option," because it gives fast reset-time on recovery while still catching slow degradation. T1 (sre.google/workbook/alerting-on-slos). Both sources converge, independently, on the actual alert-fatigue cure: "err on the side of removing noisy alerts, over-monitoring is a harder problem to solve than under-monitoring," because false positives erode trust in the whole alerting system in a way that is much harder to repair than adding a missing rule later.

Where the real tradeoff lies. A page for everything is exhausting and gets ignored or muted, which is worse than no alert at all (a muted pager is silent exactly when something real happens). An alert on every possible cause (CPU high, one slow query, one failed webhook retry) generates noise that trains the on-call person (at Solen's size, the founder) to stop looking, which is the textbook alert-fatigue failure mode both sources name directly. Symptom/burn-rate alerting costs more up-front thinking (you need an SLI to burn against) but pays for itself immediately in signal-to-noise.

Recommended default for Solen. Keep the daily-digest email as the "report" tier, it already matches Ewaschuk's own third tier correctly. Add exactly one page-tier alert, wired to something Solen doesn't have any real-time signal on today: a booking-creation or payment-capture failure RATE crossing a threshold in a short window (the symptom, not "Stripe webhook returned non-200," which is the cause). A single Resend/email or a Slack-webhook ping triggered from the existing booking/payment code paths is enough at this volume, no PagerDuty-class tool needed. Do not add cause-based alerts (a single failed cron run, a single 500) as pages; those belong in the digest or a dashboard, per the symptom-over-cause rule, unless they sustain long enough to threaten the SLI itself.

7. Health checks: liveness vs readiness, and what they mean with no long-lived process

The question. Kubernetes draws a sharp line between "liveness" (should this process be killed and restarted) and "readiness" (should traffic be routed to this instance right now). Does that distinction mean anything for Solen, which runs on Netlify Functions with no long-lived process at all.

What the evidence says. Kubernetes's own docs define the three probe types precisely: a liveness probe "determines when to restart a container," catching a case like deadlock "where an application is running, but unable to make progress"; a readiness probe "determines when a container is ready to accept traffic"; a startup probe gates both of the others until "the application within a container is started," specifically for slow-booting apps. The two run in parallel once startup succeeds: "using both can ensure that traffic does not reach a container that is not ready for it, and that containers are restarted when they fail." T1 (kubernetes.io/docs/concepts/workloads/pods/probes). This entire model presupposes a long-lived process instance that can be in a "not ready yet" state (still loading config, warming a cache) distinct from a "definitely broken, kill it" state, and that a scheduler (kubelet) is continuously polling it to make a routing/restart decision. On the serverless side, the concept genuinely does not transfer: "AWS Lambda operates at a regional level, not within specific Availability Zones... Lambda health checks aren't explicitly designed for pre-warming in the traditional sense, making the readiness probe concept less applicable in its traditional form," and the practical replacement pattern is CloudWatch alarms plus scheduled synthetic health-check invocations, not a continuously-polled in-process probe. T2/T3, directional secondary sourcing (no single official AWS page states this as cleanly as the search synthesis implies; treat the mechanism, not the exact wording, as verified). Netlify Functions are documented (Netlify's own materials, corroborated by third-party writeups) as having "no shared memory between calls, no state that persists between requests," each invocation is a fresh, isolated execution, which is the same shape as Lambda (Netlify Functions run on AWS Lambda under the hood) and rules out an in-process "not ready yet" state entirely: a Netlify Function is either invoked successfully or it isn't, there is no warm instance sitting in a "still starting up" phase that a probe could catch mid-flight.

Where the real tradeoff lies. Building a fake liveness/readiness split for a system with no long-lived process to distinguish is cargo-culting a Kubernetes idiom onto an architecture where the underlying question ("is THIS instance, which will exist for milliseconds, ready") doesn't parse. What DOES transfer, and what Solen already has, is the DEPENDENCY-health idea underneath both probes: "can this deployment currently do its job," answered by checking the things a request actually needs (DB reachable, Redis reachable, required env vars present), which is precisely what GET /api/health already does.

Solen's actual implementation, verified this session. lib/health.ts runs three probes in parallel with a 2-second timeout each via Promise.race: probeDb does a HEAD count against the tiny cities table via the service-role client (deliberately chosen so a .select("*", {count:"exact", head:true}) cannot silently no-op on a renamed column, this project's own documented failure class); probeRedis PINGs Upstash if configured, reporting "unconfigured" (not a failure) if the env vars are absent; probeEnv checks PROD_REQUIRED_VARS are present, but only during a real production boot (CONTEXT=production && NODE_ENV=production), so dev/preview never trips it. The route returns 200 if every probe is ok/unconfigured, 503 if any hard-fails, and .github/workflows/cron-jobs.yml piggybacks a curl-and-retry-once check onto the existing every-15-minute Actions job, so a down site fails that job red, which triggers GitHub's default failed-workflow email, zero extra infrastructure. This is, in substance, exactly the single "dependency health" endpoint the analysis above says is the right shape for a system with no long-lived process; it should be named and kept as that, not apologized for as "not real liveness/readiness."

Recommended default for Solen. Keep the single /api/health dependency probe as-is; do not build a separate "readiness" endpoint, there is no separate readiness question to ask in this architecture. If a genuine gap shows up later (e.g. Solen adds a real long-lived worker process, not a serverless function, for a queue consumer), THAT component is the one that would get an actual liveness/readiness pair, because it would be the first thing in the stack with an in-process "starting up" state to distinguish.

8. An audit trail is not logs

The question. Solen has console.error output and a handful of _audit/history-style DB tables (not inventoried in this pass). Does either of these constitute an "audit trail" in the sense GDPR accountability, a payment dispute, or a Swiss data-breach investigation would actually need.

What the evidence says. An audit trail is defined, across the sources checked, as narrower and more demanding than a log: "a chronological, tamper-evident record of every action taken on a system or transaction, capturing who did what, when, from where, and on what version," distinct from a generic application log by four properties: append-only/tamper-evident (write-once or WORM storage, cryptographic hashing, or hash-chaining, so "any unauthorized modification, deletion, or insertion can be detected"), retained on a defined schedule (not "however long the hosting platform happens to keep console output"), queryable (able to answer a specific question about a specific actor/object/time later, not just "search the last few days"), and legally meaningful (built to support "non-repudiation, compliance, and forensic analysis," the exact opposite of a debug log a developer can quietly edit or delete). T2 (multiple converging secondary sources on the audit-trail definition; no single official standards body defines "audit trail" as crisply as these define an SLO, so this is T2 not T1). GDPR's own accountability principle gives the legal teeth to this distinction for Solen specifically: Article 5(2) makes the controller "responsible for, and able to demonstrate compliance with" the data-protection principles, and Article 30's Records of Processing Activities requirement is explicitly one of the concrete mechanisms by which that demonstration happens, "regulators often request first during an audit." T1 (GDPR Art. 5(2)/Art. 30, per converged legal-guidance sources). The concrete, Solen-specific fact that makes this section load-bearing rather than theoretical: Netlify's own docs state function logs are "retained for at least 24 hours" of activity, extending "to 7 days for certain pricing plans," and the only way to keep logs beyond that window is Log Drains, which is an Enterprise-plan-only feature. T1 (docs.netlify.com/build/functions/logs). This means Solen's console.error output, whatever else it is, is NOT an audit trail today: it fails retained (gone within a week), fails queryable-long-term (there's nothing left to query), and fails tamper-evident (nobody has claimed any integrity property over ephemeral function-log output). It also was never designed to be one: it's debug output for a developer looking at a live incident, not a compliance record.

Where the real tradeoff lies. Building a genuine audit trail (an append-only audit_log table, INSERT-only RLS policy, hash-chained or at minimum immutable rows, a defined retention schedule) is real, standing engineering work: a new table, a discipline about what writes to it and when, and a decision about retention length tied to an actual legal requirement, not a guess. Treating console.error as "good enough" is free but false, and the falseness only surfaces at the worst possible moment: a payment dispute, a data-subject access request, or an actual FDPIC (Swiss data-protection authority) inquiry, when "we have logs" turns out to mean "we had logs, for about a week, and then Netlify deleted them."

Recommended default for Solen. Do not conflate the two. Keep console.error/structured logs as the fast, ephemeral, developer-facing debugging signal (section 1). Separately, identify the SPECIFIC events that need a real audit trail, almost certainly: booking status changes (created, cancelled, completed, no-show), payment/refund actions, and role/permission changes on profiles (already partially covered by the guard_profile_privilege_columns() trigger per _docs/BACKEND.md, though that trigger prevents unauthorized change, it does not itself create a queryable history of legitimate changes). For those, an append-only DB table (which Postgres/Supabase already gives Solen for free, no new infrastructure) that records actor, action, target, timestamp is the right, proportionate answer, not a generic "log everything forever" policy. Cost: schema design + write discipline at every mutation site that matters, bounded and doable at 28 salons; NOT a new logging platform.

9. PII scrubbing in logs and error reports, and the GDPR/nFADP implications for a Swiss company

The question. Solen is a Swiss company processing Swiss (and some EU) customers' personal data: names, emails, phone numbers, booking history, payment metadata. What must NEVER appear in a log or an error report, and what is the actual legal exposure if it does.

What the evidence says. The OWASP Logging Cheat Sheet is explicit and absolute on the hard-never category: "session identification values, access tokens, authentication passwords, database connection strings, encryption keys and other primary secrets," "bank account or payment card holder data," and application source code must never appear in logs, full stop, "never log data unless it is legally sanctioned." For personal data that falls short of that hard-never bar (names, phone numbers, emails, the ordinary PII Solen collects for every booking) the same source recommends "personal data de-identification techniques such as deletion, scrambling, or pseudonymization" rather than an outright ban, because the tradeoff there is investigability (a developer debugging a real customer's failed booking legitimately needs SOME way to identify which booking) versus exposure (that same data sitting in a log line is now a second, unmanaged copy of personal data outside Solen's actual customer database, with none of the RLS/access controls that database has). T1 (OWASP Logging Cheat Sheet). OWASP's Top 10:2025 (confirmed current, category A09, renamed from the 2021 edition's "Security Logging and Monitoring Failures" to "Security Logging and Alerting Failures," reflecting an added emphasis on alerting/response, not just log capture) names "sensitive information exposure through logging" and unprotected/unmonitored log integrity as concrete instances of this failure class, at the #9 rank in a community-voted top ten of the whole industry's web-application risk. T1 (owasp.org/Top10/2025). Legally, the moment a log line contains a name, email, or any identifier tied to a real person, it IS "processing of personal data" under both GDPR and the Swiss nFADP (the revised Federal Act on Data Protection, in force since 1 September 2023 with no transition period), which means it inherits the same obligations as the rest of Solen's data: a lawful basis, data-minimisation (Art. 6 GDPR's six lawful bases; the FADP's equivalent framing), a defined retention period that must be justified, not indefinite (GDPR Art. 5(1)(e) storage limitation; the EDPB has stated explicitly that "blanket indefinite retention is not acceptable even where a legal basis exists"), and a security-breach notification duty if it leaks: FADP Art. 24 requires the controller to notify the FDPIC "as quickly as possible" of a breach "likely to lead to a high risk," a duty described as "worded more softly than the 72-hour deadline of the GDPR" but real nonetheless, and FADP Art. 8 requires "appropriate technical and organisational measures with reference to risk" for data security generally, a standard that substantially overlaps ISO 27001's own control catalogue. T1/T2 (converged legal-guidance sources on FADP Art. 8/24, GDPR Art. 5(1)(e)/EDPB retention guidance).

Where the real tradeoff lies. Scrubbing everything (hashing or redacting every user-identifying field before it can ever reach a log line) is the safest posture but makes debugging a specific customer's specific problem materially harder; "user_id: [REDACTED]" is useless when the actual support question is "why did booking X fail for this exact customer." Logging freely is the opposite failure: every log line becomes a second, ungoverned copy of personal data, subject to the same retention/breach obligations as the primary database but with none of its access controls (RLS doesn't apply to a Netlify function's stdout), and Solen's OWN documented incident-history precedent (the "silent no-ops" class, section 7 crossover) shows Solen already treats "the log line is the only record we have" as an acceptable-in-practice debugging pattern, which is exactly where a PII leak into logs would most likely happen unnoticed.

Recommended default for Solen. Never log: passwords, session/auth tokens, Stripe secret keys or full card numbers (Stripe's own tokenization already means Solen's code should never see a raw PAN, so this should already be moot, but it's the absolute floor either way), and any Swiss AHV/social-insurance-style government identifier if one is ever collected. For ordinary customer PII (name, email, phone), prefer logging the internal ID (booking id, user id, both already UUIDs per Solen's schema) over the raw name/email/phone in a log line; the ID is enough to look the record up in the actual, access-controlled database when investigating, and doesn't create a second copy of the PII itself sitting in ephemeral function-log storage. Cost: a one-time pass over the highest-risk log call sites (payment, auth, booking-confirmation email paths) to confirm nothing raw is being interpolated into a console.error string, not a systemic rewrite.

Myths and traps

  • MYTH: "console.error with a bracketed prefix is basically structured logging." It is a human-readable convention, not a structured, queryable format, and it carries no request/trace id, so two log lines from the same failed request cannot be joined without guessing by timestamp. This is Solen's literal current state (203 files, verified this session), not a hypothetical.
  • MYTH: "our logs are our audit trail." See section 8: Netlify's own docs put function-log retention at 24 hours to 7 days depending on plan, and Log Drains (the only export path) is Enterprise-only. Whatever console.error output is, it is not append-only, not long-retained, and not designed for "who did what, when" months later.
  • MYTH: "100% uptime/availability is the right target to aim for." Google's own SRE book states this directly: it's not just unrealistic, chasing it "can reduce the rate of innovation and deployment, require expensive, overly conservative solutions, or both." A deliberately-imperfect SLO with a spendable error budget is the documented alternative, not a consolation prize.
  • MYTH: "liveness/readiness probes are just good practice everywhere, we should add them." They answer a question ("is this long-lived instance alive, and is it ready for traffic") that does not exist for a Netlify Function, which has no persistent instance to be "not ready yet." Copying the Kubernetes idiom onto a serverless architecture is cargo-culting, not hardening; the single dependency-health check Solen already has (/api/health) is the right-sized equivalent.
  • TRAP (Solen-specific, PostHog): error tracking is a config change away, not a new vendor decision. posthog-js/posthog-node are already dependencies (package.json) and PostHog's error-tracking feature (captureException) is part of the same product Solen already pays for. The gap is adoption, not tooling.
  • TRAP (Solen-specific, Netlify): "we'll just look at the Netlify function logs if something breaks" only works within the retention window. If an incident is reported by a salon owner a week after it happened (a very plausible support-ticket timeline), the underlying log line is very likely already gone on most plans.
  • TRAP (Solen-specific, GitHub Actions cron): the daily-digest email is doing real alerting work already and should be named as such, not treated as "just a nice-to-have email." It matches Ewaschuk's own "report" tier precisely (periodic, low-urgency, reviewed by one accountable person). The gap is the missing PAGE tier above it, not a replacement for the digest.
  • CONV, not an empirical truth: "OpenTelemetry is simply the modern default, every serious backend should be on it." OTel's own governance committee has publicly named "complexity and lack of stability" as real production impediments even at large scale; treating adoption as a default rather than a cost/benefit decision ignores the project's own admitted friction.

Premature at our scale

  • A dedicated metrics/dashboards platform (Prometheus/Grafana, Datadog, etc.) implementing full RED+USE dashboards. Correct once there are enough services and enough traffic that a human can no longer just check the Supabase and Upstash dashboards directly. At 28 salons, both of those vendor dashboards, already paid for, already cover the USE side; the RED side (per-route rate/error/duration) has no home yet, but a purpose-built platform is overkill before there's meaningful traffic to look at. Revisit trigger: enough concurrent traffic, or enough distinct services, that "just check the two vendor dashboards" stops being sufficient to spot a problem.
  • Formal error-budget POLICY machinery (automated release freezes on budget exhaustion, a budget-burn dashboard, a documented error-budget policy doc). The underlying idea (an SLO with an accepted failure rate) is right-sized for Solen now (section 3); the release-gating bureaucracy around it is not, because Solen has no separate SRE-vs-product organizational split for the error budget to depoliticize. Revisit trigger: more than one person shipping to production regularly enough that "should we ship today" becomes a real, recurring disagreement.
  • OpenTelemetry SDK + Collector + semantic-convention adoption. Correct once Solen runs more than one independently-deployed service that needs to share one instrumentation vocabulary and one exportable trace format across vendors. Today it is one Next.js app on one deploy target. Revisit trigger: a second independently-deployed backend service (a separate mobile API, a separate admin service) that needs to share traces with the main app; until then, the request-id/traceparent wire-format-only adoption (section 4) captures nearly all the realistic benefit at close to zero cost.
  • A dedicated append-only audit-log PLATFORM (a compliance-grade immutable ledger service, cryptographic hash-chaining infrastructure). The underlying need (an append-only table for booking/payment/role-change history) is real and cheap now (section 8); a dedicated tamper-proof ledger PRODUCT is not, because Postgres's own INSERT-only RLS policy plus ordinary access controls already gets Solen most of the real-world protection at 28 salons. Revisit trigger: a specific compliance regime (a payment processor's audit requirement, an enterprise salon partner's security questionnaire, an actual FDPIC inquiry) that names cryptographic tamper-evidence as a hard requirement, not an assumption.
  • Multi-window, multi-burn-rate alerting with several distinct SLO-burn alert rules. The underlying principle (alert on symptoms, not causes) is adoptable today at near-zero cost (section 6); the full multi-window apparatus Google's workbook describes is built for a team fielding pages around the clock across many services. Revisit trigger: more than one on-call person, or SLO coverage broad enough that a single fast-burn/slow-burn pair per SLI stops being sufficient signal.
