Background jobs and async, researched law

Date: 2026-07-16. Sources fetched this run: 21 (list at bottom, each with what it established). For: any session touching app/api/cron/*, .github/workflows/cron-jobs.yml, lib/cron-run.ts, pg_cron migrations, the Stripe webhook handler, or any new async/queue-shaped work at Solen.

Stack facts used throughout (verified live this session, not from memory): Next.js 15.3.8 App Router on Netlify (@netlify/plugin-nextjs), 354 API routes, 26 of them under app/api/cron/*, pinged by GitHub Actions (.github/workflows/cron-jobs.yml) on 14 UTC cron expressions with a shared-secret bearer token. A separate, smaller layer of 3 native pg_cron jobs runs pure-SQL maintenance inside Supabase Postgres. There is no message broker anywhere in the stack today. Scale: about 28 salons live, low traffic, pre-revenue-scale, serverless request model (every request may be a cold lambda).

0. The short version

  1. At ~28 salons, "a cron pings an HTTP endpoint that does a bounded SQL scan" is not a compromise, it is the correct architecture. A real broker is premature. (T2, reasoned from scale; see §1.)
  2. Every consumer of a repeatable trigger (cron retry, Stripe webhook retry, GitHub Actions overlap) must be idempotent. Exactly-once delivery does not exist across a network; only exactly-once-effect via an idempotent consumer does. (T1, FLP + Two Generals impossibility results.) Solen already does this correctly in app/api/stripe/webhook/route.ts via a processed_webhook_events claim-then-process pattern; that pattern is the house style, copy it.
  3. Any retry loop you write must use jittered exponential backoff, never fixed-interval retry and never bare exponential backoff without jitter. Un-jittered backoff still synchronizes retries into thundering-herd waves. (T1, AWS Architecture Blog.) Solen currently has zero backoff-with-jitter implementation anywhere in the codebase, it should be added the next time a retry loop is written against Resend, seven.io, or Gemini.
  4. A dead letter queue is a concept ("what happens after N failures"), not necessarily a piece of infrastructure. At Solen's scale the DLQ is legitimately "an admin email plus a DB row that stays in a failed state for a human to look at," not a second queue. (T1 pattern, T2/scale-honesty on implementation.)
  5. GitHub Actions' schedule trigger is explicitly "best effort": it can be delayed or silently dropped under platform-wide load, with no SLA. (T1, GitHub's own docs.) Never build logic that assumes a cron fired at its exact scheduled minute.
  6. Overlap protection needs a lock, not a schedule assumption. Solen's cron-jobs.yml has no concurrency: group and no advisory lock inside any cron route, so two overlapping invocations of the same cron are possible in principle today. The current safety net is per-row idempotency (status-column CAS, Stripe idempotency keys), which is good defense but is not the same thing as mutual exclusion. (T1 mechanic, reasoned application to our code.)
  7. "Write to our DB, then call Stripe" (or Resend, or any external system) in that order without a recovery path is a dual-write bug. The fix is the transactional outbox pattern: only ever write local state transactionally, and let a separate relay step do the external call, tolerant of being retried. (T2, microservices.io.) Most of Solen's money code already does the equivalent by hand (deterministic idempotency keys, CAS status columns) rather than a literal outbox table, this is a fine substitute at our scale, see §6.
  8. Every job needs an explicit timeout budget, because your platform will impose one whether you plan for it or not. Netlify serverless functions have a hard, non-configurable execution ceiling (double-digit seconds range, exact current number disputed between Netlify's own docs pages, see §5 and Unverified). discovery-ai-backfill already sets maxDuration = 300; every long-running cron should do the same deliberately rather than discovering the ceiling in production.
  9. An idempotency key for a job execution is not the same thing as a Stripe idempotency key, though the mechanism (a stable string, a uniqueness constraint, a claim-before-work insert) is identical. Every cron/job that mutates money or sends a message exactly-once-in-effect needs one; Solen already has good examples (pre-charge:<bookingId>:<amountRappen>, the processed_webhook_events claim row).
  10. pg_cron and GitHub-Actions-triggered HTTP cron are different tools for different jobs, don't conflate them: pg_cron for pure-SQL maintenance that needs no external API/service-role logic (it already prevents overlapping runs of the *same* job natively); the GitHub Actions HTTP pattern for anything that needs Node, Stripe, email, or an admin Supabase client. (T1, mechanic verified from the pg_cron source repo.)

1. Queue choice: real broker vs Postgres-as-a-queue vs pg_cron vs cron HTTP endpoint

The question. When work needs to happen "later" or "in the background," there are at least four honest architectures, and picking the wrong one for your scale is either premature complexity or a silent reliability gap.

What the evidence says.

  • A real broker (Amazon SQS, Upstash QStash, RabbitMQ, a hosted Kafka) is built for the case where you have many producers and many concurrent consumers competing for work, need strict per-message retry policies, and want a dead letter queue and redrive as first-class infrastructure features rather than something you hand-roll. Upstash QStash in particular is HTTP-based, "100% built on stateless HTTP requests," delivers with automatic retries and an explicit dead letter queue, and durably stores messages before delivering to the destination via HTTP (T2, Upstash's own getting-started docs, upstash.com/docs/qstash/overall/getstarted). It fits Solen's stack particularly well because Solen already depends on Upstash for rate limiting (@upstash/ratelimit + @upstash/redis), so there is zero new vendor relationship to add if this is ever adopted.
  • Postgres-as-a-queue (a table + SELECT ... FOR UPDATE SKIP LOCKED) turns a plain table into "a high-throughput job queue" by letting multiple concurrent workers each grab a disjoint batch of rows without blocking each other: "With SKIP LOCKED, any selected rows that cannot be immediately locked are skipped... Skipping locked rows provides an inconsistent view of the data, so this is not suitable for general purpose work, but can be used to avoid lock contention with multiple consumers accessing a queue-like table" (T1, official Postgres docs, postgresql.org/docs/current/sql-select.html). The entire value of this pattern is concurrent consumers. If you only ever have one consumer running at a time (one cron invocation processing a batch, sequentially), SKIP LOCKED buys you nothing over a plain WHERE status = 'pending' LIMIT 50.
  • pg_cron runs scheduling and execution entirely inside Postgres as a Postgres extension: "pg_cron can run multiple jobs in parallel, but only one instance of each specific job at a time. If a second instance is triggered before the first finishes, it's queued and starts as soon as the first one completes" (T1, primary source, github.com/citusdata/pg_cron). This native overlap protection is a real advantage over the GitHub Actions pattern below, but pg_cron jobs can only run SQL, an Edge Function, or a webhook call, they cannot hold a Stripe SDK client, a typed admin Supabase client, or arbitrary Node logic. Supabase's own docs cap this at "max 8 concurrent jobs, 10-minute limit per job" (T1, supabase.com/docs/guides/cron).
  • A cron pinging an HTTP endpoint (Solen's actual pattern: GitHub Actions on a UTC schedule, bearer-secret-authed POST/GET to a Next.js route) is the least "infrastructure-y" option. It has no native overlap protection (see §3) and GitHub's own schedule trigger is best-effort (see §3), but it can run arbitrary Node/TypeScript with full library access, which is exactly what Solen's crons need (Stripe SDK, Resend, seven.io, Gemini vision, typed Supabase clients).

Where the real tradeoff lies. A real broker buys you delivery guarantees, backpressure, and DLQ tooling you don't have to build, at the cost of a new vendor dependency, new auth/network surface, and (for QStash specifically) per-message pricing once volume grows. Postgres-as-a-queue buys you "no new infrastructure" at the cost of having to hand-roll everything a broker gives you for free (visibility timeout, redrive, backpressure) the moment you actually need concurrent consumers. pg_cron buys you native overlap protection for pure-SQL work but can't touch Stripe or Resend. The HTTP-cron pattern buys you full language/library access at the cost of owning overlap protection, timeout budgeting, and retry logic yourself.

Recommended default for Solen, with cost. Keep the current three-tier split (pg_cron for pure-SQL maintenance, GitHub-Actions-HTTP-cron for anything needing Node/Stripe/email, zero broker) exactly as-is. Cost of this choice: no native overlap protection on the HTTP-cron tier (§3 fix: add advisory locks), no first-class DLQ (§4: the DLQ is an admin email + a stuck-row state), and if volume ever needs multiple *concurrent* workers processing the same table, Postgres-as-a-queue with SKIP LOCKED becomes the next honest step before reaching for a broker. Reaching for a real broker today, at 28 salons and one consumer per cron, would be solving a concurrency problem Solen does not have.

2. At-least-once delivery and idempotent consumers (exactly-once is a marketing claim)

The question. Can a system guarantee a message/job/webhook is processed exactly once?

What the evidence says. No, not across an unreliable network, and this is a formal result, not an engineering shortfall. "Exactly-once delivery at the network layer is impossible. The Two Generals Problem proves that an unreliable network cannot guarantee coordinated exactly-once semantics with finite messages" and "FLP and the Two Generals Problem are not design complexities, they are impossibility results" (T1 impossibility results, argued in a widely-cited T2 engineering post, bravenewgeek.com/you-cannot-have-exactly-once-delivery). The reason is structural: a sender cannot distinguish "my message was lost" from "my message arrived but the acknowledgment was lost," so it must either risk never redelivering (at-most-once, silent data loss) or risk redelivering a message that already landed (at-least-once, duplicates). Every "exactly-once" marketing claim from a vendor is really at-least-once delivery plus idempotent processing on the consumer side: "what vendors call 'exactly-once' is actually at-least-once delivery combined with idempotent processing on the consumer side... The practical answer is at-least-once delivery with idempotent consumers. Design every consumer so that processing the same message twice has no additional effect" (T2, converges with the T1 impossibility results above).

Idempotence itself has a precise, older, and broader definition: "an operation can be repeated or retried as often as necessary without causing unintended effects" (T1, en.wikipedia.org/wiki/Idempotence), and in HTTP terms GET/PUT/DELETE are meant to be idempotent by spec while POST is not, which is exactly why webhook and job-trigger endpoints (which are POSTs by nature) need an explicit, hand-built idempotency mechanism rather than getting it for free from the HTTP method.

Where the real tradeoff lies. Building an idempotent consumer costs a persistence layer (a claim table, a CAS column, a unique index) and a little more code at every call site. Skipping it costs you double-charges, double-emails, and double-side-effects the first time a retry, a network blip, or an overlapping cron run actually happens, which given Stripe's own retry window (see §3, up to three days) is not an edge case, it is a certainty over the app's lifetime.

Recommended default for Solen, with cost. Solen already has the right pattern in production and should keep using it verbatim: app/api/stripe/webhook/route.ts does an atomic claim-before-process insert into processed_webhook_events keyed on event.id (primary key, so a duplicate insert reliably 23505s), releases the claim on a thrown error so a legitimate retry can re-run, and only 200s once the handler actually completed. This is the textbook idempotent-consumer pattern and it is worth naming as the template new job/webhook code should copy. Cost: it requires one extra committed row per event and a deliberate "release the claim on failure" step, which is easy to forget when writing a new handler; the file's own comment documents a real prior bug where the claim was committed *before* the handler ran, silently marking failed events as done.

3. Retries with exponential backoff and jitter (full vs equal vs decorrelated)

The question. When a call to an external system (Stripe, Resend, seven.io, Gemini, TikTok's oEmbed endpoint) fails transiently, how should a retry be spaced?

What the evidence says. Fixed-interval retry synchronizes clients into repeated collision waves under contention. Exponential backoff alone is not sufficient: "while exponential backoff makes calls happen less frequently, clusters of calls still occur, and contention hasn't been significantly reduced... The solution isn't to remove backoff, it's to add jitter. Adding jitter spreads out spikes to an approximately constant rate" (T1, aws.amazon.com/blogs/architecture/exponential-backoff-and-jitter). The same source gives three concrete formulas:

  • Full Jitter: sleep = random(0, min(cap, base * 2^attempt)), i.e. the entire backoff window is randomized from zero.
  • Equal Jitter: sleep = base*2^attempt/2 + random(0, base*2^attempt/2), keeping half the backoff fixed and jittering only the other half, to avoid very short sleeps.
  • Decorrelated Jitter: sleep = min(cap, random(0, 3 * last_sleep)), growing the jitter window off the *previous* random value rather than a clean exponential curve.

AWS's own stated tradeoff: "The decision between 'Decorrelated Jitter' and 'Full Jitter' is less clear. The 'Full Jitter' approach uses less work, but slightly more time. Both approaches present a substantial decrease in client work and server load" versus un-jittered exponential backoff (T1, same source). The article frames jittered backoff as "a standard approach for remote clients," not an edge-case optimization.

Where the real tradeoff lies. Full Jitter is simplest to implement and reason about (one call to random(), no extra state) but a small fraction of retries will fire almost immediately (sleep can be 0), which is fine for most failures but wrong for something you know needs at least N seconds (e.g. respecting a Retry-After header). Decorrelated Jitter avoids ever collapsing to near-zero sleep but needs you to carry the previous sleep value across attempts, which is awkward in a stateless serverless function unless you're looping within one invocation.

Recommended default for Solen, with cost. Solen currently has zero backoff-with-jitter implementation anywhere in the codebase (confirmed by grep across lib/ and app/api/: existing "retry" comments describe unique-constraint collision retries and CAS-conflict retries, both of which are correctly immediate, not backed-off, because they're contending for a DB row, not a rate-limited external API). The gap that matters: cron routes that call Resend, seven.io, or Gemini today either succeed, fail and get caught by the per-item try/catch (logged, not retried until the next scheduled cron run hours later), or in pre-charge's case rely on Stripe's own idempotency key to make a same-day re-run cheap. For any *new* code that needs an in-process retry loop against a flaky external API (not "wait for the next cron run" but "retry within this invocation"), use Full Jitter as the default: it's the AWS-recommended baseline, cheapest to implement, and Solen's job runtimes are short-lived serverless invocations where "slightly more time" (Full Jitter's stated cost versus Decorrelated) is irrelevant, but carrying state across attempts (Decorrelated Jitter's requirement) is annoying inside a single function call. Cap total retry time well under whatever the job's own timeout budget is (§8), a 3-attempt Full Jitter loop with a 2 second base and an 8 second cap costs at most seconds, not minutes.

4. Dead letter queues

The question. What happens to a job/message after it has failed enough times that retrying it again is pointless?

What the evidence says. A dead-letter queue "is a special type of message queue that temporarily stores messages that a software system cannot process due to errors," used so a team can "examine logs for exceptions that might have caused messages to be moved to a dead-letter queue... analyze the contents of messages... determine whether you have given your consumer sufficient time to process messages... move messages out using dead-letter queue redrive" (T1, docs.aws.amazon.com, SQS dead-letter queues). The mechanism in SQS specifically: a redrive policy sets maxReceiveCount, the number of times a consumer can receive a message before it's moved off to the DLQ, and AWS's own guidance is "set the maxReceiveCount high enough to allow for sufficient retries" rather than moving to the DLQ on the first failure. AWS also flags a retention-period trap worth knowing even if you never touch SQS: DLQ retention should always exceed the source queue's retention, because the message's expiry clock started when it first entered the *original* queue, not when it moved to the DLQ, so a DLQ with too-short a retention can silently drop a message that just arrived there.

Where the real tradeoff lies. A DLQ's entire value is a durable, inspectable place for "gave up on this" state plus a human alerting hook. What it costs is infrastructure: a second queue, a redrive policy, and (usually) a dashboard or alert wired to "the DLQ is non-empty." At 28 salons, standing up a literal second queue for this is disproportionate to the volume of jobs that would ever land there.

Recommended default for Solen, with cost. The DLQ *concept* still applies, implemented as: a status column the job flips to a terminal failed state (not silently dropped, not infinitely retried) plus an admin-visible signal. Solen already has the pieces: withCronRun's errors[] array (when a cron populates it) flips cron_runs.ok to false, which fails the GitHub Actions run (the de facto alert) and shows up in daily-digest's "cron failures" section; reportError/alertAdmin sends a direct email on a thrown exception. The gap documented in _docs/BACKEND.md §6 (several money-adjacent crons, e.g. no-show, release-payments, pre-charge, reconcile, track per-item failures under a different field name that never gets copied into errors[], so a night where every single charge fails still reports cron_runs.ok:true) is functionally "the dead letter queue exists but nothing is watching it." Fixing that wiring (deciding per-cron whether item-level failures should flip ok:false) is the cheap, correct DLQ investment here, not standing up a second queue. Cost: touching money-adjacent cron code carries real risk, changes there should go through the money-code review discipline already in place (deterministic idempotency keys, CAS columns), not be done as a drive-by.

5. Cron correctness: overlapping runs, missed runs, distributed locks, HTTP-cron auth + timeout budgets

The question. Four separate failure modes hide under "cron correctness": (a) the same job running twice concurrently, (b) a scheduled run never firing at all, (c) needing a lock to prevent (a) across processes/instances, and (d) an HTTP-triggered cron being callable by anyone or running past its platform's time budget.

What the evidence says, per failure mode.

  • (a) Overlapping runs. GitHub Actions does not natively prevent two runs of the same scheduled workflow from executing concurrently unless you add a concurrency: group to the workflow YAML, a concurrency: key exists specifically for this purpose in Actions but Solen's cron-jobs.yml has none (confirmed: grep -n "concurrency" .github/workflows/cron-jobs.yml returns nothing). Contrast with pg_cron, which natively serializes: "pg_cron can run multiple jobs in parallel, but only one instance of each specific job at a time. If a second instance is triggered before the first finishes, it's queued and starts as soon as the first one completes" (T1, github.com/citusdata/pg_cron).
  • (b) Missed runs. GitHub's own docs state the schedule trigger is best-effort: "The schedule event can be delayed during periods of high loads of GitHub Actions workflow runs. High load times include the start of every hour... If the load is sufficiently high enough, some queued jobs may be dropped" and "the shortest interval you can run scheduled workflows is once every 5 minutes" (T1, docs.github.com, events-that-trigger-workflows#schedule). There is no documented catch-up/backfill behavior, a dropped run is simply gone; the next scheduled run is your only recovery, which is exactly why Solen's crons all use bounded, re-runnable batch queries (.limit(50), status-column filters) rather than "process only what changed since the last run" logic that a missed run would silently corrupt.
  • (c) Distributed locks. Postgres advisory locks are the standard primitive for "only one process should do X right now," and Solen already uses them correctly for row-level critical sections: pg_advisory_xact_lock(hashtext(...)) guards the staff-daily-limit trigger, the member-discount reservation, and the credit/voucher redemption RPCs (all found live in supabase/migrations/). The official semantics: transaction-level advisory locks (pg_advisory_xact_lock) are "automatically released at the end of the transaction," need no explicit unlock, and behave like a normal lock request; session-level locks (pg_advisory_lock) are "held until explicitly released or the session ends" and critically "do NOT honor transaction semantics: a lock acquired during a transaction that is later rolled back will still be held following the rollback" (T1, postgresql.org/docs/current/explicit-locking.html). What Solen does not yet have is the same primitive applied at the *cron-job* level (one lock per cron *name*, held for the duration of the whole HTTP request, to physically prevent two overlapping invocations of e.g. pre-charge from both racing the same batch), it only has row-level locks inside specific write paths. This matters less today because every cron's row-level idempotency (status filters, Stripe idempotency keys) already absorbs most of the damage an overlap would cause, but it is not the same guarantee as "only one invocation runs at a time," and a cron doing non-idempotent side effects (e.g., appending to a log, incrementing a counter without a WHERE guard) would not be protected.
  • (d) HTTP-triggered cron auth + timeout. Every one of Solen's 26 cron routes checks Authorization: Bearer <CRON_SECRET> before doing anything (_docs/BACKEND.md §6, verified against several route files this session), which is the correct minimum bar for an HTTP endpoint that runs privileged, service-role logic on a public URL. On timeout: Netlify enforces a hard execution ceiling on every function regardless of whether you plan for it, discovery-ai-backfill already declares export const maxDuration = 300 explicitly because AI-vision analysis across a batch can run long; every cron whose batch size or downstream API latency could plausibly approach the platform ceiling should set maxDuration deliberately rather than discover the limit via a truncated production run. Netlify's own documentation is not internally consistent on the exact default number, see §8 and Unverified below, but the actionable point does not depend on the exact figure: the ceiling is real, non-configurable beyond maxDuration (where Next.js exposes it), and every cron should be sized to its batch limit (.limit(50)) with that ceiling in mind.

Where the real tradeoff lies. Adding a per-cron advisory lock costs a few lines (pg_try_advisory_lock, bail out cleanly with a 200 "already running" response if not acquired, this must be a *try* variant, not a blocking one, or a genuinely-slow first run would make the second invocation hang instead of skip) and one more thing to reason about when debugging a cron. Not adding it costs nothing today (row-level idempotency covers the money-critical paths) but is a real gap the moment a new cron is written whose side effects aren't naturally idempotent per row.

Recommended default for Solen, with cost. Keep the current per-row idempotency discipline for all money-adjacent crons (it works, it's proven). Add a pg_try_advisory_lock (keyed by a stable hash of the cron's own name, transaction-scoped is wrong here since the "transaction" is the whole HTTP request, so this should be the session-level pg_advisory_lock/pg_try_advisory_lock pair with an explicit unlock in a finally, not the _xact variant) as a second, cheap layer of defense specifically for any *new* cron whose logic is not naturally row-idempotent, and consider retrofitting it onto the handful of crons that do non-idempotent counting or logging. Cost: one more migration, one more thing every future cron author needs to know about; worth it only for crons where "ran twice" would actually do something wrong beyond wasted work.

6. The transactional outbox pattern (why "write DB then call Stripe" is a dual-write bug)

The question. If a request needs to both commit a local database write and call an external system (Stripe, Resend, a webhook), and those two things cannot be wrapped in one atomic transaction, what happens when the process dies, throws, or times out between the two steps?

What the evidence says. This is "the dual-write problem: it occurs whenever we need to update two separate systems... because these two systems aren't linked and can't be updated in a transactional fashion" (T2, microservices.io/patterns/data/transactional-outbox.html). The named fix: "when a business transaction occurs... it makes the necessary changes to a database transaction and stores all events in the outbox table in the same database... A message relay then sends the messages stored in the outbox to the message broker," so "the state and the outbox table will always be updated in a transactional fashion, and if the state fails to update, the event won't be written to the outbox, guaranteeing that the data in the outbox is completely in sync with the database." Two implementation strategies for the relay step exist: transaction log tailing (watch the DB's write-ahead log for new outbox rows, push them out) and polling publisher (a periodic job selects unpublished outbox rows and sends them). The pattern's own stated weaknesses: developers can simply forget to write to the outbox alongside the business write (a discipline problem, not solved by the pattern itself), and the relay itself can crash after sending but before marking a row published, causing a duplicate send, "however... this is typically manageable since message consumers usually need to be idempotent anyway" (ties directly back to §2).

Where the real tradeoff lies. A literal outbox table plus a relay job is the textbook implementation, and it is the right call when the "external system" is genuinely a message broker or another service you don't control the retry semantics of. It costs a new table, a relay job, and one more moving part to keep in sync. Solen's actual external calls (Stripe, Resend, seven.io) are all themselves either idempotent-by-key APIs (Stripe) or fire-and-log calls where a failed send just needs a retry path, not a durable queue, so a literal outbox table is more machinery than the problem needs.

Recommended default for Solen, with cost. Solen's money code already implements the *spirit* of the outbox pattern without a literal outbox table, by making the local write and the external call each individually safe to retry: a deterministic Stripe idempotency key is computed *before* the Stripe call (pre-charge:<bookingId>:<amountRappen> in app/api/cron/pre-charge/route.ts, refund:<source>:<id>:<staleRefunded>:<amountCents> in lib/purchases/issue-purchase-refund.ts), so a crash between "we decided to charge" and "Stripe confirmed the charge" is recoverable: the next attempt (whether a cron re-run or a manual retry) reuses the same key and Stripe collapses it to the original result rather than double-charging. This is the correct substitute at Solen's scale: the important discipline is "compute the idempotency key before the external call, and make the local write re-derivable from state rather than only from a one-shot event," not literally building an outbox table. The trap to avoid, and the one the outbox pattern exists to name, is writing the local row as "done" *before* confirming the external call succeeded (a webhook handler doing UPDATE bookings SET status='paid' before the Stripe charge is confirmed, for instance), or the reverse (calling Stripe first, writing the DB row after, with no idempotency key, so a retry after a DB write failure double-charges). Cost of getting this wrong is exactly a double-charge or a silently-never-happened charge, which is why every money-adjacent write in this codebase should be reviewed against "is the external call keyed, and is the local write ordered so a crash between the two steps is recoverable, not double-counted."

7. Timeouts on every job

The question. What happens if a job (a cron invocation, a webhook handler, a retry loop) simply never returns?

What the evidence says. Every platform in this stack imposes a hard ceiling whether or not you plan for it. Netlify enforces execution timeouts per function type (see §8 for the exact, disputed number), and Next.js exposes a maxDuration route-segment config specifically so you can *declare* your intended ceiling rather than be surprised by the platform's default: "after will run for the platform's default or configured max duration of your route. If your platform supports it, you can configure the timeout limit using the maxDuration route segment config" (T1, nextjs.org/docs/app/api-reference/functions/after). Stripe's own guidance for webhook handlers specifically: "your endpoint must return a successful status code (2xx) quickly, before applying any complex logic that could cause a timeout... you must return a 200 response before updating a customer invoice as paid in your accounting system" (T1, translated from docs.stripe.com/webhooks), which is the general principle: acknowledge fast, do the slow work after or separately, don't let the caller's own retry-on-timeout logic become your load multiplier.

Where the real tradeoff lies. Setting an explicit, conservative maxDuration costs nothing to write and forces you to think about batch sizing up front. Not setting one costs you a silent truncation the first time a batch grows past what fit comfortably during testing, at 28 salons that headroom is currently large, but it will not stay large forever, and a cron that silently stops partway through a batch (no explicit timeout handling) can leave a job half-processed with no signal that it was truncated rather than completed.

Recommended default for Solen, with cost. Every cron or job that could plausibly run long (a per-item external API call inside a loop, e.g. discovery-ai-backfill's Gemini vision calls, or discovery-deadcheck's TikTok oEmbed probes) should declare maxDuration explicitly and keep its batch size (.limit(N)) calibrated to comfortably finish inside that budget, not right up against it. Cost: this is a one-line addition per route, the real cost is doing the arithmetic once (roughly: maxDuration ÷ worst-case-per-item-latency = safe batch size) rather than guessing.

8. Idempotency keys for job execution

The question. How do you make "run this job" itself safe to trigger twice, as distinct from making the job's *external* side effects (a Stripe charge) idempotent?

What the evidence says. The mechanism is identical to any other idempotency key: a stable, deterministic string plus a uniqueness constraint the first writer wins and every subsequent writer loses gracefully. Stripe's own implementation of this exact mechanism for its API is instructive because it's fully documented: "idempotency keys are retained for at least 24 hours... the idempotency layer compares incoming parameters to those of the original request and errors if they're not the same to prevent accidental misuse" and, for true concurrent races, "if the request conflicts with another request that's executing concurrently, we don't save the idempotent result" (T1, docs.stripe.com/api/idempotent_requests). The generalizable lesson for *our own* job-execution idempotency keys (not calls to Stripe, but our own cron/job triggers): a key needs (1) enough entropy or determinism to uniquely identify "this exact unit of work," (2) a durable claim (an insert with a unique/primary key, not a check-then-write, exactly as processed_webhook_events does), and (3) a defined behavior on parameter mismatch or concurrent collision, don't silently accept a same-key-different-params retry as if it were identical.

Where the real tradeoff lies. A per-job idempotency key costs one more DB write (the claim) and a decision about what "identical" means for that job (is pre-charge on the same booking but at a different amount the *same* job or a *different* one, worth being deliberate about, as Solen's key pre-charge:<bookingId>:<amountRappen> already is: same booking, same amount collapses; same booking, different amount is intentionally a distinct key). Skipping it costs you exactly the double-processing bugs at-least-once delivery guarantees you will eventually see (§2).

Recommended default for Solen, with cost. Every job (cron route or webhook handler) that has an externally-visible, non-trivially-repeatable effect (charges money, sends a message, mutates a counter) needs an idempotency key at the job-execution level, following the two house patterns already in this codebase: (a) a durable claim-before-work row with a unique constraint when the "job" is a discrete external event (processed_webhook_events, keyed on Stripe's own event.id), or (b) a deterministic string passed as the Stripe idempotency key itself when the job's job *is* the Stripe call (pre-charge:<bookingId>:<amountRappen>, refund:<source>:<id>:<staleRefunded>:<amountCents>). Cost: deciding what belongs in the key (which parameters make two executions "the same job" versus "a different job") is a real design decision each time, not boilerplate, get it wrong (too narrow a key) and legitimate different work collapses together; get it wrong (too broad) and duplicate work slips through.

Myths and traps

  • MYTH: "Exactly-once delivery" is an achievable engineering goal. It is a marketing simplification for "at-least-once delivery plus an idempotent consumer." Grounded in the Two Generals Problem and the FLP impossibility result, both formal, not opinions (T1/T2, bravenewgeek.com). Never let a design doc say "we guarantee exactly-once" without meaning "at-least-once + idempotent."
  • MYTH (partially): "SKIP LOCKED turns any table into a queue for free." It only helps with concurrent-consumer lock contention; Postgres's own docs call the resulting view "inconsistent... not suitable for general purpose work" outside that specific use case (T1). If you only ever have one consumer at a time, plain WHERE status='pending' does the same job with none of the caveat.
  • Trap specific to our stack: GitHub Actions' schedule trigger is not a clock. It's explicitly best-effort and can silently drop a run under platform-wide load (T1, GitHub's own docs). Any logic that assumes "this runs every 15 minutes, guaranteed" is wrong; Solen's crons are correctly built to tolerate a missed run (bounded, re-runnable batch queries) but new crons must keep that discipline.
  • Trap specific to our stack: no concurrency: group in cron-jobs.yml means two runs of the same schedule really can overlap. Confirmed by reading the file (no concurrency: key present). The current safety net is row-level idempotency, which is good but is not the same guarantee as mutual exclusion; a future cron with non-per-row side effects would not be protected.
  • Trap specific to our stack: Netlify's own docs disagree with each other on the exact default synchronous function timeout (one current page states 60 seconds non-configurable, another current page, for the separate "Async Workloads" product, states 30 seconds for "standard serverless functions"). Treat the exact number as unresolved (see Unverified) but the actionable fact, a hard non-configurable ceiling exists, as certain. Don't cite either specific number as gospel in code comments without re-checking Netlify's docs at the time.
  • Trap specific to our stack: withCronRun's ok flag only reflects a thrown exception or a populated errors[] array, not any per-item failure the handler tracks under a different field name. Several money-adjacent crons (no-show, release-payments, pre-charge, reconcile) currently do exactly this, meaning a night where every single Stripe call in that cron fails can still report cron_runs.ok:true and a green GitHub Actions run. This is a real, present gap, not a hypothetical, documented independently in _docs/BACKEND.md §6.
  • Trap specific to our stack: barber_walkin_queue is a customer-facing physical queue table (walk-ins waiting for a haircut), not a job queue. Don't confuse it with a background-jobs mechanism when searching the DB snapshot for "queue"-named tables.
  • Trap specific to Stripe Connect + webhooks: a webhook handler that writes local "done" state before the external call is confirmed is a dual-write bug waiting to happen, and the fix isn't "add more error handling" but "reorder so the local write is only ever derived from a confirmed external state, or key the external call so a retry after a partial local write is safe" (§6).
  • Trap in PostgREST/Supabase specifically (this codebase's #1 general failure mode, restated for jobs): a job that does .select() on a column that doesn't exist returns null, not an error, so a "job" that looks like it ran and returned 200 may have silently done nothing. Every new cron needs to prove it discriminates (actually picks up the rows it's supposed to, actually applies its filter), not merely that it returns {ok: true}.

Premature at our scale

  • A real message broker (SQS, QStash, Kafka, RabbitMQ). Correct once Solen has genuinely concurrent consumers competing for the same work, or needs cross-service fan-out that a DB table can't express cleanly. Trigger to revisit: multiple background workers needing to process the same table concurrently (not just sequential cron runs), or a job type whose retry/DLQ semantics get too complex to hand-roll safely.
  • Postgres-as-a-queue with SELECT FOR UPDATE SKIP LOCKED. Correct once there are multiple concurrent consumers reading the same job table. Today every cron is a single sequential consumer per invocation; SKIP LOCKED would add complexity with no corresponding benefit. Trigger to revisit: introducing a worker pool or parallel job processing against one table.
  • A literal transactional outbox table + relay job. Correct when the "external system" is a broker/queue you don't control the retry semantics of, or when you have many different event types fanning out to many different consumers. Today Solen's two external dependencies that matter for this (Stripe, email/SMS) both have workable substitutes (deterministic idempotency keys, best-effort send + cron-level retry) that achieve the same safety without the extra table. Trigger to revisit: adding a second downstream consumer of the same "booking confirmed" event that needs independent retry/ordering guarantees from the email send.
  • Per-cron distributed locking via a dedicated lock-service or Redis-based mutex (Upstash Redis is already in the stack for rate limiting, so this would be "free" in one sense). Correct once cron overlap has caused an actual incident. Today a Postgres advisory lock (already the house pattern for row-level critical sections) is enough, and cheaper: no new service, same DB connection already in use.
  • A formal DLQ queue/topic as infrastructure, versus the current status-column + admin-email approach. Correct once failure volume is high enough that a human reading email digests can't keep up, or once retries need programmatic redrive rather than a person deciding what to do. At 28 salons' worth of cron volume this is not the bottleneck.
  • OpenTelemetry-style distributed tracing across job executions. Correct at a scale where cron failures are hard to correlate across services. Today cron_runs + Netlify function logs + the daily digest email are enough to debug any single failing cron by hand.

Unverified

  • The exact default Netlify synchronous function execution timeout is genuinely unresolved from official sources fetched this session. docs.netlify.com/build/functions/configuration/ states a table of "Synchronous: 60 seconds (not configurable), Scheduled: 30 seconds, Background: 15 minutes." docs.netlify.com/build/async-workloads/optional-configuration/ separately states "the default deployment options for standard serverless functions includes a 30 second timeout," referencing the *same* functions/overview anchor. Does Solen actually do this?

Background jobs & async , Solen audit 2026-07-16

Verdict

Solen's cron fleet does the hard parts right and the easy part wrong. The at-least-once / idempotent-consumer discipline (JOBS-01) and the deterministic pre-Stripe-call idempotency key (JOBS-03) are both genuinely well implemented, not just in the one webhook route the research names but copied correctly into most of the newer crons too. Bounded .limit() batches and re-runnable status-column filters (JOBS-04's mitigation for GitHub Actions' best-effort schedule) are the house style and are followed in the majority of routes. But the observability wrapper withCronRun has a real, currently-live wiring gap: at least 6 of 26 crons, including every money-adjacent one the research named by name (no-show, release-payments, pre-charge, reconcile) plus discovery-ai-backfill and process-deletions, report their per-item failures under a differently-named field (declined, failed, mismatches, results) that withCronRun does not read, so cron_runs.ok stays true and the GitHub Actions run stays green even on a night where every single Stripe call in that cron failed. This is exactly the dead-DLQ failure mode JOBS-08 describes, and it is not hypothetical, it is the current, unfixed shape of the code. Retry-with-jitter (JOBS-02) is a total, confirmed gap exactly as the research states: there is no retry loop against an external API anywhere in this codebase, jittered or not, so there is nothing to fix there yet, only something to build correctly the first time it is needed. Per-cron advisory locks (JOBS-05) do not exist for any of the 26 crons, but every cron sampled is either naturally row-idempotent (status-column re-asserts, unique DB indexes) or writes to a fully-recomputed target, so the absence is a real but currently low-risk gap, matching the research's own framing.

The gaps in detail

1. withCronRun's errors[] contract is silently violated by 6+ crons (JOBS-08)

What is wrong. lib/cron-run.ts only flips cron_runs.ok to false (and the HTTP status to 500, which is what ping-cron's jq -e '.ok == true' hard-assert checks) when the handler either throws, explicitly returns ok: false, or returns an errors field that is an ARRAY. Several crons, including every one of the four money-adjacent crons the research asked to re-check by name, count their per-item failures into a differently-named field instead:

// app/api/cron/release-payments/route.ts:64
return { released, failed, processed: released + failed };
// app/api/cron/pre-charge/route.ts:123
return { charged, declined, processed: charged + declined };
// app/api/cron/no-show/route.ts:147
return { processed, charged };  // failures aren't even counted
// app/api/cron/reconcile/route.ts:424-430
return { checked, checkedPurchases, skipped, mismatches, processed: checked + checkedPurchases };
// app/api/cron/discovery-ai-backfill/route.ts:74
return { ok: true, analyzed, failed, picked: items?.length ?? 0, processed: analyzed };
// app/api/cron/process-deletions/route.ts:246
return { message: `Processed ${dueUsers.length} users`, results, processed: dueUsers.length };

What breaks in practice. Picture a night where seven.io/Stripe has an outage window and every release-payments capture call throws, or every pre-charge card is declined because the chargeOffSession primitive has a bug. failed/declined climbs to the full batch size, but withCronRun still computes ok: true (no throw, result.ok !== false, errors.length === 0 because errors was never populated). The GitHub Actions run stays green (ping-cron/action.yml's jq -e '.ok == true' passes), no email fires, and cron_runs shows a row that LOOKS like a clean run. The founder's own daily-digest cron reads exactly this table (cron_runs.eq("ok", false), daily-digest/route.ts:95-98) to build its "cron failures" section, so this isn't just a GitHub Actions blind spot, it is also a blind spot in the one human-facing ops summary that exists. reconcile's case is slightly better in that a real mismatches array DOES trigger a separate admin email (reconcile/route.ts:397-421), but that email path itself silently no-ops when ADMIN_EMAIL is unset (console.warn only, :420), so reconcile has two independent ways to go quiet, not one.

The concrete fix and its cost. Rename the local counters into the errors: string[] shape withCronRun already reads, or (cheaper, no behavior change to the counter names other code may depend on) add one line before each return that maps the existing failure signal into an errors array, e.g. for release-payments:

const errorMsgs: string[] = [];
// inside the catch block that currently does failed++:
errorMsgs.push(`booking ${booking.id}: capture failed: ${err.message}`);
// at the return:
return { released, failed, errors: errorMsgs, processed: released + failed };

This is a same-shape change already proven correct in 12+ other crons in this same fleet (abandon-sweep, welcome-series, rebooking-nudge, sms-reminders, salon-onboarding, birthday-messages, review-prompt, release-deposits, discovery-deadcheck all already do exactly this, several behind a shared capErrors() helper). Cost: roughly 6 small diffs, each touching only the return statement and adding one errorMsgs.push() per existing catch block. No schema change, no migration, no behavior change to the actual money/booking logic. discovery-ai-backfill's fix is the smallest: replace the hardcoded ok: true with nothing (let withCronRun derive it) and add errors: capErrors(...) from the existing failed accounting.

2. Three-plus crons loop an external API call per item with no bound and no declared maxDuration (JOBS-04 + JOBS-06)

What is wrong. sms-reminders runs two fully-sequential loops (no runWithConcurrency, unlike its sibling notification crons) of up to 100 bookings each, calling sendSMS (seven.io) once per booking, awaited in series:

// app/api/cron/sms-reminders/route.ts:91-105 (24h loop), :147-161 (1h loop, same shape)
const ok = await sendSMS(phone, `Erinnerung: ...`);

barber-smart-reminders has no .limit() at all on either its salons query or its per-salon unique-customer list, and also sends SMS sequentially. discovery-deadcheck has no .limit() on its published-items-with-a-tiktok_url query and calls TikTok's oEmbed endpoint (12s timeout) once per item, sequentially, weekly. None of these three (nor welcome-series/rebooking-nudge, which ARE concurrency-capped at 5 but still pull an unbounded candidate list) declare a maxDuration.

What breaks in practice. At 28 salons this is currently safe: seven.io calls are typically sub-second, TikTok's oEmbed likewise, and daily/weekly customer volumes are small. But the design has no ceiling: if the discovery library grows to a few thousand published TikTok-sourced looks (a stated product direction), discovery-deadcheck's single weekly run would attempt that many sequential 12s-capable oEmbed calls with no cap, run long past any Netlify sync-function ceiling (disputed exact number per JOBS-10, but a hard ceiling exists on every plan), and truncate mid-batch with the tail of items never checked, silently, since a truncated serverless invocation does not even reach the withCronRun catch block to log the partial state.

The concrete fix and its cost. Add .limit(N) to the three unbounded queries (bound to whatever maxDuration divided by worst-observed per-item latency yields, following the same math discovery-ai-backfill's own comment already documents: "10 looks x ~10s AI ~= under the function limit"), and add an explicit export const maxDuration = <N> to each of the four routes named above. Cost: a one-line .limit() addition to 3 queries plus a one-line maxDuration export to 4 route files; no logic change, since all four already resume correctly next run via their existing sent-once / claim-before-send / is_active guards, an unprocessed tail just waits for the next scheduled tick.

What Solen already does RIGHT (name it; a new session needs to know what NOT to "fix")

  • The processed_webhook_events claim-then-process pattern (`app/api/stripe/webhook/route.ts:51-63,

903-907`) is exactly right: atomic PK insert as the claim, release-on-throw, and it is the ONLY inbound webhook route in the codebase, so there is no drift to fix elsewhere yet.

  • The deterministic idempotency-key-before-Stripe-call pattern is correctly propagated well

beyond the original webhook, into pre-charge, charge-fee.ts, off-session-charge.ts, issue-refund.ts, and issue-purchase-refund.ts. Do not "refactor" these into a shared key-builder unless a real duplication bug shows up; the shape is already consistent.

  • Bounded, re-runnable batch queries with status-column filters are the default style, not the

exception: no-show, abandon-sweep, pending-timeout, release-deposits, discovery-ai-backfill, review-prompt all .limit() and filter on a status/flag column so a late or doubled GitHub Actions tick is safe. This is the correct mitigation for JOBS-04 and should be the template for any new cron, not something to "harden" further with extra locking.

  • runWithConcurrency (lib/concurrency.ts) is a small, correct, deliberately-simple bounded

worker pool used by 5 notification crons to cap concurrent email sends. It is NOT a retry/backoff mechanism and should not be mistaken for one; it solves a different problem (flooding the email provider) and solves it well.

  • capErrors() (duplicated verbatim across ~9 crons, each with a "RING 3a" comment) correctly

caps a per-item failure array at 20 entries plus a "...and N more" tail, so a systemic failure never floods the cron_runs.errors column. This is the right pattern; the fix for gap #1 above is to make the 6 non-conforming crons ALSO use it, not to change it.

  • availability_slots_dedup_uniq (a live unique index, NULLS NOT DISTINCT, on

(salon_id, service_id, staff_member_id, starts_at)) is a real DB-level backstop that makes generate-slots naturally safe under an overlapping run, exactly the kind of row-idempotency substitute for an advisory lock that JOBS-05 endorses as sufficient at this scale.

  • The slot-purge pg_cron job (purge_past_available_slots, scheduled weekly via

supabase/migrations/20260711161352_backend_loop_schedule_slot_purge.sql) confirms the team DOES act on a "needs scheduling" follow-up once flagged; cron_runs's own missing purge (Unknowns below) is the same class of item, not yet urgent.

  • The no-show re-assert guard (2026-07-14 HIGH finding) is verified FIXED in current code

(app/api/cron/no-show/route.ts:48-58, re-asserts status=confirmed in the WHERE clause and checks updatedRows.length before proceeding). Do not re-flag this; it is closed.
