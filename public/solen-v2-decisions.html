ISSUE 5 · iOS ZOOM

When the user taps an input on iPhone, does the page zoom in?

iOS Safari auto-zooms any <input> with font-size < 16px when focused — to make it readable. The zoom doesn't return until the user manually pinches out. This is real and affects every login / signup / booking screen on iPhone. The locked §13.4 search bar uses 14px, so it currently zooms.

What I know for sure: the 16px iOS Safari zoom threshold is a real, documented WebKit behavior — anything below 16px triggers focus-zoom. What I don't know without checking: what specific booking competitors use. I won't claim "Fresha uses X" without verifying. If you want me to actually inspect Fresha / Treatwell / Booking.com inputs, I can do that — say the word.
OPTION A
All text-input font-size = 16px

Override the size table for text inputs specifically. md height stays 56px. Only the rendered TEXT inside the input goes from 14 → 16px. Affects §13.4 (locked) — the search-row value would re-lock at 16px.

font-size: 16px · iOS will not zoom

Pros: No zoom anywhere. Matches Fresha/Treatwell/Booking. Universally accessible.

Cons: Slightly larger text than current locked §13.4 (14px → 16px). All search-row labels/values rerender.

OPTION B
Keep 14px, accept the zoom

14px stays in the size table for visual density. iPhone users see one zoom-in on focus; zoom-out requires manual pinch.

font-size: 14px · iOS WILL zoom on focus

Pros: No spec changes. Visual density preserved.

Cons: Real UX harm on the booking funnel — users land on iPhone, tap email field, page zooms, they fight it back. Booking abandonment risk.

OPTION C
15px compromise

15px also avoids zoom on iOS Safari (the threshold is exactly 16px on most iOS, but 15px works on iOS 14+ in practice). Smaller than 16, larger than 14.

font-size: 15px · iOS will not zoom on most versions, but not officially documented

Pros: Tighter than 16. Also avoids zoom in practice.

Cons: Not officially documented. Apple could change the threshold in a future iOS. Riskier than 16.

Decision needed: A, B, or C? My read: probably A (matches industry, zero risk) but you decide.

ISSUE 7 · TERMINOLOGY

Circle elements — fix the loose phrasing.

My §F.1.5 said "circle radius: pill (50%)" but §7 distinguishes --radius-pill (99px, for pill shapes) from --radius-full (50% / 9999px, for actual circles). Loose phrasing in §F.1 should reference the right token. This is just a doc edit, not a visual decision — sample below confirms which is which.

VAR
--radius-pill (99px)

For pill shapes (rectangles with very-rounded ends). Used by buttons, chips, badges, the "Aktuell" tag, the search CTA.

Pill: rectangle with 99px radius
VAR
--radius-full (50%)

For actual circles (square aspect-ratio elements). Used by avatars, switch knobs, radio circles, heart buttons, status dots.

S
Circle: square with 50% radius (avatar / radio / heart button)

ISSUE 8 · FOCUS + ACTIVE

When a field is keyboard-focused AND being typed in — does the focus ring stack on top of the active border?

Both states are brand-orange (per §1). When they co-occur, you get TWO concentric brand-orange treatments around the field. Below: each state in isolation, then "stacked" (option A) vs "focus replaces active" (option B).

REFERENCE
Default (no state)
state =default
1px ink-1 .10 border. No focus, no active.
REFERENCE
Active only (mouse click + typing)
state =active
2px brand-orange border + #FFF4E8 bg. No outline.
REFERENCE
Focus only (keyboard tab in)
state =focus
2px brand-orange outline, 2px offset. No border change, no bg change.
OPTION A
Stacked (current draft)

Focus ring + active state co-occur — both render. User sees outer outline + inner border. Two concentric brand-orange treatments.

state =focus + active stacked
Both effects render simultaneously.

Pros: Both signals visible — keyboard nav AND typing both read clearly.

Cons: Visually busy. 2 brand-orange rings around one field. Real-world: rare to be in both states (active + keyboard-focus) at the same time.

OPTION B
Focus replaces active

When focus-visible is on, the active border doesn't render (or the active border IS the focus indicator). Single brand-orange treatment, not stacked.

state =focus + active (single)
Outline only — bg tint persists, border stays default 1px.

Pros: Cleaner. One brand-orange signal at a time.

Cons: Subtler. Mouse-click (no focus-visible) shows active state w 2px border; keyboard-tab (focus-visible) shows outline ring only — two different visuals for "I'm using this field."

Decision needed: A (stack both) or B (focus replaces active border)? Compare the two demos above side by side. My non-recommendation: I have NO opinion on this without seeing the actual booking-wizard layout — your call.
