## Verdict

Better than the research could confirm on one axis, because it flagged a question it could not check: **does a dedicated audit-shaped table already exist? It does.** `audit_log` (migration `031_audit_log.sql`) is properly shaped (`actor_id`, `action`, `target_type`, `target_id`, `metadata`, `ip_address`, `created_at`), RLS-enabled, admin-only SELECT, already wired into **30+ call sites** across bookings/disputes/refunds/no-show fees/salon moderation/account deletion, with **59 live rows**. That is a far better starting point than "console.error is the audit trail." But the one category the law names explicitly, **role/permission changes**, is exactly the one it does not cover.

The research's headline claim is **CONFIRMED, not merely repeated**: zero request-id propagation. No request-id, trace-id, or correlation-id is generated anywhere.

> **CORRECTED 2026-07-17 (live re-audit):** this is wrong. Request-id propagation is live end to end: it ships on the crash path, is reused when the caller supplies one, and is set on the 400 branch and the Stripe webhook. Evidence: POST /api/bookings with no body -> status 500, `x-request-id: 8dd8ed55-e78d-46a3-8c62-ef76810e0c9f`; same call with header `x-request-id: my-own-id-12345` -> reused; POST /api/bookings {} -> 400 + `x-request-id: 10284a20-...`; POST /api/stripe/webhook no body -> 400 + fresh id, with header `x-request-id: trace-abc-999` -> reused.

## The gaps

**OBS-01, no request id (HIGH).** A customer messages support three days after a failed booking. That flow touched booking creation, an email failure path, and possibly the Stripe webhook, each with independent `console.error` lines and **no shared key**. Reconstructing it means grepping Netlify's log viewer by approximate timestamp and hoping nothing else happened that second. This is the law's "highest-leverage missing piece" and the codebase confirms it.

**OBS-03, role changes leave no trace (MEDIUM).** `app/api/admin/users/route.ts` is the only route writing `profiles.role`/`is_suspended`. An admin promoting a user to `admin`, demoting a `salon_owner`, or suspending an account leaves **zero queryable record** of who did it, when, or from where, beyond a few days of Netlify logs. Concrete: two months on, a salon owner disputes a suspension, or a compromised admin session silently self-elevates. `logAuditEvent` is already imported in a dozen adjacent admin routes, one import away.

> **CORRECTED 2026-07-17 (live re-audit):** the "one import away" fix has ALREADY BEEN MADE in source (three actions wired, before/after values captured). Do not re-do it. But the live `audit_log` table proves it has never actually fired: 0 of 61 rows are `user.*` actions, and the newest row predates the wiring commit. This is now a "does the wiring actually run" bug (dead code path, wrong guard, or route never hit in practice), not a "wire it in" task. Evidence: SQL on `audit_log`, total_rows 61, role_change_rows 0, suspend_rows 0, newest row 2026-07-12 21:57:17.

**OBS-04, the safety net has a confirmed hole (MEDIUM).** The daily digest is correctly a report tier and should NOT be escalated on its own. But its "cron failures" section reads `cron_runs.ok = false`, and `jobs-async.md`'s JOBS-08 shows `release-payments`, `pre-charge`, `no-show`, `reconcile` can report `ok: true` on a night every Stripe call failed. Layered on top, `_docs/BACKEND.md:847` documents a second hole: the `daily-03-utc` job hard-fails on `solen-score/recalculate`'s missing `ok` field with no `continue-on-error`, blocking `process-deletions`/`reconcile`/`style-affinity-recompute` from running most nights. Two independent bugs point the same way: **the founder's one alerting surface is quietest on the nights that matter most.**

**OBS-06, `captureException` never called (MEDIUM).** One production bug firing across 40 bookings = 40 disconnected log lines, not "one issue affecting 40 users." `app/error.tsx` and `app/global-error.tsx` already call `console.error(error)` in a `useEffect`; adding `posthog.captureException(error)` beside it needs no new dependency.

## What Solen already does RIGHT

- **Sentry correctly avoided, not merely absent.** `lib/error-report.ts:3-4` documents it was added once and deliberately removed for PostHog. A fresh session's "add error tracking" instinct must not mean "add Sentry."
- **PostHog's consent gate is genuinely careful**: fails closed on a missing/error consent lookup, caches only clean reads, and both client and server gate on the same `profiles.analytics_consent`. Real GDPR/nFADP discipline, not a checkbox.
- **`audit_log` is well-designed and load-bearing**, not a gap to build from scratch: indexed, RLS-enabled, admin-only read, 30+ write sites, and `lib/audit.ts` correctly never blocks the main operation on an audit-write failure while still alerting if the audit write itself fails.
- **The `reportError`/`alertAdmin` internal-ID discipline is real project-wide**: all 12 sites checked pass only internal IDs.
- **`/api/health` is exactly right**: one dependency probe, no K8s cargo-cult, wired into the existing 15-min cron at zero marginal cost.
- **The daily digest omits a section on query failure rather than fabricating a zero**, consistent with the no-fabrication rule.
