# Webhooks , Solen audit 2026-07-16

## Verdict

Solen's ONE live webhook (`app/api/stripe/webhook/route.ts`, the only `constructEvent` call site in the whole repo) gets the T1 fundamentals right: raw-text signature verification, default 5-minute tolerance, a PRIMARY-KEY-backed atomic idempotency claim, claim-release-on-throw, and advance-only CAS guards on the two branches most exposed to Stripe's out-of-order delivery (`payment_intent.payment_failed`, `setup_intent.succeeded`, and now the `charge.dispute.closed` decrement). The one previously-documented state-corruption bug (pre-charged bookings getting silently downgraded from `paid` back to `deposit_held`) was fixed on 2026-07-14, though the fix is a type-string exclusion, not the state-based CAS the law actually asks for, so the class of bug it closes is narrower than it looks. There is no default-case log line for unrecognized event types (a real, still-open observability gap, T2). Outbound webhooks (principles WEBHOOK-09 through WEBHOOK-13) do not exist anywhere in the codebase, confirmed by exhaustive grep this session, so those five principles are legitimately not-yet-applicable forward design law, not gaps.

## The gaps in detail

### WEBHOOK-05, the generic booking else-branch still has no state guard (the real fix so far is narrower than the law asks for)

What is wrong: `route.ts:212-222` reads:

```ts
} else if (pi.metadata?.type !== "pre_charge") {
  await admin.from("bookings").update({
    payment_status: "deposit_held",
  }).eq("payment_intent_id", pi.id);
}
```

This is the only branch left in the file that writes a `payment_status` with no `.in(...)` / `.is(...)` prior-state guard. The 2026-07-14 fix (`_plans/BACKEND_HEALTH_AUDIT_2026-07-14.md:65,110`, item F1) closed the one case that was PROVEN to be live-corrupting: `app/api/cron/pre-charge/route.ts:92-100` synchronously sets `payment_status:"paid"` AND overwrites `bookings.payment_intent_id` with the new pre-charge PI's id, so the async webhook for that same PI, arriving later with `metadata.type === "pre_charge"`, would otherwise match that exact row and downgrade it back to `deposit_held`. Excluding `type === "pre_charge"` genuinely closes that hole.

But I traced every other place in the codebase that could feed this WHERE clause a matching row, specifically every write of a PaymentIntent id onto `bookings.payment_intent_id` (18 grep hits across `app/` and `lib/`, each opened and checked): `lib/bookings/charge-fee.ts` (cancellation/no-show fees) writes `fee_charge_intent_id`, a SEPARATE column, never `payment_intent_id`. `lib/bookings/dispute-engine.ts`'s `chargeUpcharge` (upcharge) writes to `booking_disputes`, never touches `bookings.payment_intent_id`. `app/api/cron/no-show/route.ts:98` and `app/api/bookings/[id]/cancel/route.ts:232` both use the string `payment_intent_id` only as an `audit_log.metadata` JSON key, not a `bookings` column write. So today, `cancellation_fee`/`no_show_fee`/`upcharge` PaymentIntents can NEVER match this WHERE clause (their own PI id is never written to `bookings.payment_intent_id` anywhere), meaning the else-branch is currently a no-op for those three event types, not the active regression `_docs/BACKEND.md:335` still describes.

What breaks in practice, if this ever changes: the safety here is an UNSTATED, untested cross-file invariant ("no code ever attaches a non-'booking'/non-'pre_charge' PaymentIntent id to `bookings.payment_intent_id`"), not an enforced guard. If a future refactor ever consolidates `fee_charge_intent_id` into `payment_intent_id`, or a new charge type reuses that column, the exact corruption `_docs/BACKEND.md:335` describes reappears silently, with no test or CAS to catch it: an already-`paid`/`refunded`/`partially_refunded` booking gets its `payment_status` reset to `deposit_held`, and `app/api/cron/release-payments/route.ts:24-32` (still live, runs every 6h, still queries `payment_status = 'deposit_held'` for capture) would then call `paymentIntents.capture()` on an already-fully-captured PI, which Stripe rejects, logged as a cron failure rather than a double-charge, per `_docs/BACKEND.md:335`'s own prior analysis of the failure mode.

The concrete fix: replace the type-exclusion with the same shape already used three other places in this exact file (`payment_failed`, `setup_intent.succeeded`, `charge.dispute.closed`): `.eq("payment_intent_id", pi.id).in("payment_status", ["pending", "none", "card_saved"])` (or equivalent), so the write is self-defending regardless of what future code ever populates that column, not just today. Cost: one line changed, no new table, no migration, same shape the file already uses elsewhere, this is a same-file consistency fix, not new architecture.

### WEBHOOK-06, no default: case in the switch

What is wrong: `route.ts:69-900`'s `switch (event.type)` has no `default:` branch. What breaks in practice: nothing errors (correct half), but if a new event type is ever enabled in the Stripe Dashboard and no matching `case` is added (the file's own header comment at lines 17-20 only lists 7 event types, while the switch actually implements 12, `setup_intent.succeeded`, `account.application.deauthorized`, `charge.refunded`, `payout.paid`, `payout.failed` are all handled in code but absent from that comment, so the comment itself is already stale and cannot be trusted as the enabled-events list), the event silently 200s forever with zero trace in logs. The concrete fix: add `default: console.log("[stripe/webhook] unhandled event type:", event.type);` before the closing brace of the switch, no throw, no status change, exactly as the principle asks. Cost: one line.

## What Solen already does RIGHT (do not "fix" these)

- Raw-body signature verification (`req.text()`, no `req.json()` anywhere near this route, no middleware body-consumption) is correct and must stay that way for any future webhook route added to this codebase.
- The `processed_webhook_events` idempotency claim (INSERT-first, 23505-as-no-op, PRIMARY KEY-backed) is correct, atomic, and the file's own comments (`route.ts:41-50`) document the exact production incident it replaced (a check-then-insert race). Do not revert to a read-then-write shape.
- The claim-release-on-throw pattern (`route.ts:901-909`) correctly covers every current branch because the whole switch lives inside one try block. Any new case added to the switch inherits this automatically; do not wrap a new case in its own try/catch that swallows the error before it reaches the outer catch.
- `payment_intent.payment_failed`'s advance-only guard (`route.ts:485-490`, `.in("payment_status", [...])`) and the slot-free gated on `cancelledRows?.length` (`route.ts:495`) correctly stop a late/out-of-order failure event from freeing an already-paid booking's slot. This was a previously-flagged CRITICAL (`_plans/BACKEND_AUDIT_INDEX.md:54`) that is confirmed fixed and still present.
- `charge.dispute.closed`'s ledger decrement (`route.ts:683-730`) uses a CAS on `lost_dispute_id IS NULL`, correctly making a Stripe redelivery of the same dispute a no-op instead of double-decrementing the salon's payout. This closes a previously-flagged non-atomic read-then-write (`_plans/BACKEND_AUDIT_INDEX.md:87`).
- `account.updated` now correctly flips `accepts_online_payment` both ON and OFF (`route.ts:805-821`), closing a previously-flagged one-directional bug (`_plans/BACKEND_HEALTH_AUDIT_2026-07-14.md:110`, F2). (Note: `payouts_enabled` is still never checked anywhere in the codebase, per `_docs/BACKEND.md:336` and `_plans/BACKEND_AUDIT_INDEX.md:92`, this is a genuinely still-open finding, but it belongs to Stripe Connect account-state correctness, not to any of this topic's 14 webhook principles, so it is named here for completeness and not scored above.)
- The one `stripe.paymentIntents.retrieve()` call in the file exists for a real reason (an expanded field the bare event omits), not defensive over-fetching. Do not add more retrieve calls "to be safe" on branches that already have what they need in `event.data.object`.
- Every Connect-scoped branch (`payout.paid`, `payout.failed`) correctly keys off `event.account`, and the two Account-object branches correctly key off the object's own `.id` (an equally valid variant since the object IS the account for those types). Any new Connect-scoped case must follow the same pattern.
