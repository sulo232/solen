# AuthZ (authorization)

Solen audit 2026-07-27

## Verdict

The live database is meaningfully safer than a static read of `supabase/migrations/*.sql` suggests. Two findings from this pass's own research (an orphaned `USING(true)` UPDATE policy on `reviews`, and several unscoped `WITH CHECK(true)` INSERT policies on `inventory`/`staff_calendars`/`addons`/`salon_photos`) were built by grepping migration files in isolation; the live `pg_policies` table shows neither exists today. `supabase/migrations/014_new_schema.sql` recreated the affected tables from scratch after those early policies were written, wiping them along with whatever they granted. **Migration-file history is not proof of live database state on this project**, and this audit's own method (query `pg_policies` directly) should be the default going forward, not a fallback.

What is real: the `staff` role is genuinely unmodeled (confirmed: `profiles_role_check` doesn't even allow `'staff'` as a value, so staff identity lives entirely in `staff_salon_id`), and `middleware.ts` locks every staff account out of `/dashboard` while at least one client surface (`MobileMenu.tsx`, fixed this pass) was promising them a working link there. The 270+ service-role call sites remain a real, unaudited surface in principle, though a 7-file spot-check this pass (weighted toward the ones a naive grep flags as riskiest) found all seven correctly designed, mostly via a cryptographic-proof shape (HMAC token, payment intent, email verification code) that a text-signal heuristic cannot recognize as an ownership check. `FORCE ROW LEVEL SECURITY` is confirmed absent everywhere, and this pass closes the open question research/authz.md left hanging: it does not matter for app traffic, because `anon`/`authenticated` both have `rolbypassrls = false` live; only `postgres`/`service_role` bypass, and app sessions never connect as either.

## Coverage + method

Read in full: `research/authz.md`, `LAW.md` section 6 (Authorization, frozen 2026-07-27), `audit/authn.md` (for AUTHN-12, which duplicates this file's preview-salon finding), `middleware.ts:140-230`, `app/api/staff/accept-invite/route.ts`, `app/[locale]/_components/layout/MobileMenu.tsx`, `app/api/profile/route.ts`, `app/api/admin/preview-salon/route.ts`, `lib/audit.ts`.

Live database queried directly via the Supabase MCP (`execute_sql`, read-only), project `tocfnsmxmdxkrcmjzzdw`:
- `pg_policies` for `reviews`, `bookings`, `salon_photos`, `addons`, `inventory`, `sms_reminders`, `staff_calendars`, `loyalty_stamps`, `quartier_subscriptions` (full policy set per table, not just a count).
- `pg_policies` grouped by `(tablename, cmd)` having more than one PERMISSIVE policy, across the whole `public` schema.
- `pg_policies` filtered to any write command (`INSERT`/`UPDATE`/`DELETE`/`ALL`) with `qual = 'true'` or `with_check = 'true'`, across the whole `public` schema.
- `pg_class.relrowsecurity` / `relforcerowsecurity` and `pg_tables.tableowner` for the same table list plus `reviews`/`bookings`.
- `pg_roles.rolbypassrls` for `anon`, `authenticated`, `service_role`, `postgres`.
- `pg_constraint` for `profiles_role_check`'s exact definition.

Grepped repo-wide: `createAdminSupabaseClient` across `app`/`lib` (271 files, up from research's 267/270 counts, confirming the surface is not shrinking); a refined heuristic (auth/ownership signal absent AND no `resolve*(`/`require*(` call anywhere in the file) narrowed that to 52 candidates (down from the research session's 71, by recognizing resolver-style helper calls generically instead of by exact name). Of those 52, 7 were read in full this pass: `app/api/quartier/subscribe/route.ts`, `app/api/bookings/guest-lookup/route.ts`, `app/api/directory/[id]/claim/route.ts`, `app/api/walkin/confirm/route.ts`, `app/api/walkin/queue/remote-join/route.ts`. This is a sample, not a completed audit; 45+ of the 52 flagged files remain unread, and the other ~219 admin-client files were never flagged by the heuristic in the first place (the heuristic can only prove "no textual signal in this file", not "this file is safe").

## The gaps in detail

### AUTHZ-03: staff role has no authorization invariant, and one live surface was promising it one (HIGH)

See `LAW.md`'s new authz section 6 addendum (authz-rls-02, 2026-07-27) for the full writeup. Summary: `profiles.role` cannot legally hold `'staff'` (live CHECK constraint), so staff identity is `staff_salon_id` presence only. `middleware.ts` never grants that identity any dashboard route. `MobileMenu.tsx` was the one place that disagreed, showing a "Dashboard" nav entry to `staff_salon_id`-only accounts that led straight into the middleware bounce. Fixed this pass (removed the false affordance). Not fixed, and explicitly not attempted without an owner decision: which dashboard subpaths a staff account should actually reach, and what RLS predicate backs each one. That is real, unscoped feature work, not a bug fix.

### AUTHZ-04 / AUTHZ-05: the object-level and service-role audits are real but not completable by grep alone

Both principles are correctly stated in `LAW.md` section 6 already. What blocks closing either is that the actual verification requires reading each file and understanding whether its check is a genuine ownership predicate, a cryptographic proof, or nothing at all, exactly the kind of judgment a text-pattern hook can flag but not resolve. Two new hooks ship this pass (`idor-object-check-reminder.py`, `admin-client-check-reminder.py`) that put the reminder in front of whoever adds file #272 or the next `params.id`-reading route, which is the cheapest point to catch a real miss. They do not, and cannot, retroactively audit the other ~264 files. That remains open work; this file's per-principle table above states the true remaining count so a future session does not have to re-derive it.

## What Solen already does RIGHT

- **Migration file history is stale where it looks stalest.** The `014_new_schema.sql` full-table-recreation event, undocumented as such anywhere in `_backend-system/`, quietly closed two real-looking vulnerabilities (AUTHZ-01, AUTHZ-02) years before this audit went looking for them. Worth naming explicitly so a future static-analysis pass doesn't re-flag the same false positive.
- **The cryptographic-proof pattern is used correctly and consistently** for account-less/pre-account flows: HMAC-signed tokens with `timingSafeEqual` (`walkin/confirm`), SHA-256 hashed access tokens (`bookings/guest-lookup`), and hashed email verification codes with a Redis attempt cap (`directory/[id]/claim`). Each of these substitutes for a database ownership column in a case where no `user_id` exists yet, and each does so without a timing oracle.
- **`anon`/`authenticated` never carry `BYPASSRLS`.** The one role that does (`service_role`) is exactly the one the code explicitly opts into via `createAdminSupabaseClient()`, never a silent default.
- **The 26-site `logAuditEvent()` convention is real and consistently used** for admin actions of comparable sensitivity; the one gap found (`preview-salon`) is now closed.

## Unknowns

- **The true violation rate among the ~264 `createAdminSupabaseClient()` call sites this audit did not read.** The 7-file sample (0/7 violations) is too small to extrapolate from in either direction; it demonstrates the pattern exists and is followed where checked, not that it holds everywhere.
- **The 45 of 52 heuristic-flagged object-level-check candidates not read this pass.** Given the 7/7 clean rate on the files that were read, a reasonable prior is that most of the remainder are also legitimate public-by-design or crypto-proof routes, but that is an extrapolation, not a finding.
- **Whether the owner wants `'staff'` added as a legal `profiles.role` value, or wants staff identity to stay `staff_salon_id`-only.** This is the actual fork behind AUTHZ-03 and needs an explicit product decision, not a schema change guessed into existence.
