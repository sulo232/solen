# Migrations, Solen audit 2026-07-16

## Verdict

Solen follows the forward-only migration law it wrote for itself (`_rules/DB_SCHEMA.md` section 7): zero down migrations, zero rollback tooling, and zero renames or type changes in 264 migration files across the project's whole history, structural change has always been additive. The one genuinely new, live finding is not a migration-mechanics problem: a 2026-05-30 seed migration fabricates nine salon amenity flags (wheelchair access, kid-friendly, LGBTQ+ welcome, etc.) with a hash function and that fabricated data is rendered to real customers today, a direct hit on the project's own no-fabrication law. On pure migration mechanics, the two real process gaps are consistent but low-current-risk: `NOT VALID` + `VALIDATE CONSTRAINT` is used correctly in only 2 of the ~9 populated-table constraint additions I found, and `CREATE INDEX CONCURRENTLY` is used 0 times in 161 index creations. Neither has caused an incident because every table involved is small (largest is 9,365 rows), but the pattern isn't followed. `lock_timeout` is unset everywhere, a real and cheap-to-close gap, with zero recorded incidents. The PostgREST schema-cache concern (MIG-09) is actually in good shape: I confirmed live that Supabase's own `pgrst_ddl_watch`/`pgrst_drop_watch` event triggers are installed and enabled on the project, so `apply_migration` auto-notifies PostgREST on every DDL statement without any extra step.

## Coverage and sampling method

- Read all 264 files under `supabase/migrations/*.sql` via targeted `grep` passes (not individually opened one by one); every grep pattern below ran against the full set, so counts are exhaustive for that pattern, not a sample.
- Read the full content of every file a grep pattern flagged as a candidate violation (not just the matching line), to confirm table/context (new table vs. populated table, drop vs. re-add, comment vs. executed statement).
- Queried the LIVE DB directly (not migration files) for two things where the migration files cannot answer the question: (a) `pg_event_trigger` catalog, to prove/disprove the PostgREST auto-reload mechanism (MIG-09); (b) `_inventory/_db-snapshot.json` (captured 2026-07-12, live `pg_class`/`pg_stat_user_tables`) for the row counts that determine lock-duration severity (MIG-04/05/06/11).
- Used the Supabase MCP `list_projects`/`get_project`/`list_migrations` tools for project metadata and drift-check context; both are read-only calls, no migration was applied and no data was written.
- Read `_rules/DB_SCHEMA.md` section 7 (the existing migration law), `_plans/BACKEND_HEALTH_AUDIT_2026-07-14.md`, `_plans/BACKEND_AUDIT_INDEX.md`, `_rules/LESSONS_LEARNED.md`, and `.github/workflows/db-migrate.yml` to avoid re-reporting known/fixed findings and to find any rollback-instruction text.
- Did not read all 264 files end to end line by line; relied on exhaustive grep + full-file reads only for flagged candidates. Did not apply a test migration or curl an endpoint (explicitly out of scope for a read-only auditor); the PostgREST reload question was answered instead by reading the live event-trigger catalog, which is stronger evidence than a single empirical test would have been.

## The gaps in detail

### 1. Fabricated salon amenity data, live and rendered to customers (MIG-07, HIGH, new finding)

`supabase/migrations/20260530_seed_salon_amenities.sql` runs this against the real, live `salons` table:

```sql
update salons set
  wheelchair_accessible = abs(hashtext(id::text || 'wheel'))   % 100 < 45,
  near_public_transport = abs(hashtext(id::text || 'transit')) % 100 < 70,
  kid_friendly          = abs(hashtext(id::text || 'kid'))     % 100 < 40,
  pet_friendly          = abs(hashtext(id::text || 'pet'))     % 100 < 30,
  wifi_friendly         = abs(hashtext(id::text || 'wifi'))    % 100 < 78,
  lgbtq_friendly        = abs(hashtext(id::text || 'lgbtq'))   % 100 < 45,
  woman_owned           = abs(hashtext(id::text || 'woman'))   % 100 < 42,
  family_owned          = abs(hashtext(id::text || 'family'))  % 100 < 38,
  student_discount      = abs(hashtext(id::text || 'student')) % 100 < 50
where is_active;
```

The migration's own header comment states the intent plainly: "seed descriptive salon amenities so the filter facets return varied, meaningful results" because the real columns were "unpopulated (~1 salon each)". This is not a demo/test table, it is the production `salons` table, and it is not gated behind `is_test`. The values were never entered by a salon owner and never verified against reality, they are the output of a hash function.

What breaks in practice: this fabricated data is live and user-facing today. `app/[locale]/_components/salon/SalonAdditionalInfo.tsx:54-62` renders "Rollstuhlgerecht" (wheelchair accessible), "Kinderfreundlich" (kid friendly), "LGBTQ+ willkommen" and 6 other badges directly from these columns on the salon detail page, and `app/[locale]/_components/search/SearchTemplate.tsx:232-234` exposes several of the same columns as live search filter facets, so a customer can filter for "wheelchair accessible" salons and get a result set that is, per-salon, a coin flip weighted by a hash of the salon's UUID. This is exactly the class of harm the project's own taste rule 1 exists to prevent ("no fabricated data... a fake value is worse than a dot, it's a lie the user trusts"), made worse here because these are accessibility and identity-adjacent claims (wheelchair access, LGBTQ+ welcome) a real customer could reasonably rely on for a real-world decision.

Concrete fix and cost: this needs an owner call, not a mechanical fix, because the honest options trade off differently: (a) null out all 9 columns again and hide the badges/filters until salons self-report real values (cheap, immediate, loses the "varied facets" UX the migration was chasing), (b) add a real onboarding/dashboard field so salons enter their own amenities and re-run a real backfill from actual answers (the correct long-term fix, costs a small onboarding-form addition), (c) restrict the fabricated flags to `is_test = true` salons only, if the intent was ever meant to be demo-only, and null them out for the 28 real live salons. This was not found in `_design-system/REMOVED.md`, `_plans/BACKEND_AUDIT_INDEX.md`, or any other prior audit I checked, it appears to be a genuinely new finding, not a re-flag of something already fixed.

### 2. NOT VALID + VALIDATE CONSTRAINT used inconsistently (MIG-04, MEDIUM)

The pattern is known and used correctly twice (`20260602120000_walkin_foundations.sql`, `20260614010000_solen_plus_phase1_perks.sql`), so this isn't a knowledge gap, it just isn't applied every time. Example of the gap, `supabase/migrations/075_compliance_roles_schema.sql:8-17`:

```sql
ALTER TABLE public.profiles DROP CONSTRAINT IF EXISTS profiles_role_check;
ALTER TABLE public.profiles ADD CONSTRAINT profiles_role_check
  CHECK (role IN ('customer','salon_owner','staff','admin'));
...
ALTER TABLE public.profiles DROP CONSTRAINT IF EXISTS profiles_account_status_check;
ALTER TABLE public.profiles ADD CONSTRAINT profiles_account_status_check
  CHECK (account_status IN ('active','warned','suspended','banned'));
```

`profiles` currently has 49 live rows (`_inventory/_db-snapshot.json`); the largest table this pattern hit historically is `bookings` (`068_megabuild_foundation.sql`, `075_booking_confirmation_mode.sql`, `20260601_refund_appeal_foundation.sql`), now at 956 rows. At these sizes the `ACCESS EXCLUSIVE` scan-and-lock this causes is sub-second and has caused no recorded incident. What breaks in practice, only at future scale: as `bookings` grows past tens of thousands of rows, the same bare `ADD CONSTRAINT` pattern would hold a full-table write lock for the scan duration, and Solen's traffic is real-money booking writes, so any multi-second lock there is a customer-visible outage window, not a cosmetic slowdown. Concrete fix and cost: adopt the already-proven two-line pattern (`... NOT VALID; ALTER TABLE ... VALIDATE CONSTRAINT ...;`) as the default for every future `ADD CONSTRAINT ... CHECK` on a table that isn't brand new in the same migration. Zero cost beyond writing one extra line; no rework needed on the historical instances since they already ran without incident.

### 3. CREATE INDEX CONCURRENTLY never used (MIG-05, MEDIUM, bounded today)

0 of 161 `CREATE INDEX` statements use `CONCURRENTLY`. Representative example, `supabase/migrations/20260625104237_discovery_items_tags_gin_index.sql` and the 142 FK indexes from the 2026-06-24 perf-hardening pass (`_plans` reference `perf_add_missing_fk_indexes`) all ran as plain `CREATE INDEX IF NOT EXISTS`. What breaks in practice, again only at future scale: a plain `CREATE INDEX` takes a `SHARE` lock that blocks all writes to that table until the build finishes; on `availability_slots` (9,365 rows, the busiest write table via the booking flow) this is currently a sub-second block, not a customer-visible outage. It becomes a real risk once that table is large enough that an index build takes more than a few seconds, at which point every booking write queues behind it. Concrete fix and cost: switch to `CREATE INDEX CONCURRENTLY` for any future index on `bookings`, `availability_slots`, or any other table taking live write traffic; the cost is a slower (double-scan), non-transactional build that can leave an `INVALID` index behind on failure (documented recovery: drop and retry), which is why it's a deliberate choice per-index rather than a blanket default for tiny reference tables.

### 4. lock_timeout never set (MIG-10, MEDIUM, cheap, zero incidents)

Confirmed 0 of 264 files, and no CI/runner path sets it either (the only automated push path, `.github/workflows/db-migrate.yml`, is dormant, `workflow_dispatch`-only, explicitly disabled per its own header comment pending a migration-history rebaseline). What breaks in practice: without `lock_timeout`, an `ACCESS EXCLUSIVE`-requiring statement that happens to queue behind a long-running query on the same table doesn't fail fast, it waits, and every subsequent query against that table queues behind IT, turning a brief lock into a full outage for that table. This has not happened yet (no incident in `_rules/LESSONS_LEARNED.md` or the audit trackers). Concrete fix and cost: one line at the top of DDL-carrying migrations, e.g. `SET LOCAL lock_timeout = '5s';` before the `ALTER TABLE`/`CREATE INDEX` statements, so a colliding migration aborts loudly instead of queueing silently. Trivial to add going forward; no need to retrofit the 264 existing files.

## What Solen already does RIGHT (do not "fix" these)

- **Forward-only migration law is real and followed.** `_rules/DB_SCHEMA.md` section 7 states it explicitly and the evidence backs it: zero down-migration files, zero rollback tooling, in 264 files.
- **No renames, no type changes, ever.** Every structural change in the project's history has been additive (new column added, old column left in place or, twice, explicitly dropped only after being unused). This is more conservative than the textbook expand/contract pattern, not less, there is no "single combined step" risk to find because the risky step (contract) has essentially never been taken.
- **Backfills are idempotent by construction.** Every backfill I found (loyalty A-to-B migration, promo/discovery seeds) uses a `NOT EXISTS`/`ON CONFLICT`/deterministic-hash guard. Nobody needs to build batching machinery, GitLab-style, at 28 salons and a 9.4K-row max table, and nobody has.
- **PostgREST auto-reload is actually wired up.** `pgrst_ddl_watch`/`pgrst_drop_watch` event triggers are live and enabled on the project; this is Supabase's own mechanism working as documented, not a gap Solen needs to build tooling around.
- **The additive-idempotent `apply_migration` discipline (`IF NOT EXISTS`/`CREATE OR REPLACE`/`DROP POLICY IF EXISTS` guards) is followed pervasively** across the sampled files, this is the load-bearing convention that makes re-running or backfilling a migration file safe, and it shows up correctly in essentially every file I opened.
- **Drift between live schema and local files is a known, already-documented, already-tooled problem**, not a surprise: `_rules/DB_SCHEMA.md` section 7 gives the exact backfill recipe, and `.github/workflows/db-migrate.yml`'s own header names the 42-version drift and keeps the auto-push path deliberately disabled until a rebaseline, rather than risking a `db push` conflict against production.
