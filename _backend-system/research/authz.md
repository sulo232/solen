# AuthZ (authorization) , researched law

Status: researched 2026-07-16. 15 external pages fetched (URLs and what each established are listed in Sources). Written for Solen.ch: Next.js 15.3.8 App Router, Supabase Postgres (RLS + two-client model), Stripe Connect, Netlify serverless, ~28 salons live, 354 API routes, 264 migrations, 146 tables. Every claim below is tagged T1/T2/T3/CONV/MYTH. Grounding against Solen's own code is cited by file:line, taken from `_docs/BACKEND.md` (mapped 2026-07-14) and direct greps this session.

Authentication (who you are) is a different topic; this file is about authorization (what you, once known, are allowed to touch). The single most important fact for this codebase: **Solen already has one authorization bug class documented as its number one failure mode** (RLS silently matching zero rows and PostgREST reporting that as success), and that failure mode is the generic industry problem this file researches, not a Solen-only quirk. Sections below connect the two.

## 0. The short version

1. **Object-level authorization (IDOR/BOLA) is not optional and is not covered by a role check.** Every read or write that takes a client-supplied ID must independently verify the caller owns or is scoped to that specific row, on every single call, even if the caller's role would generally be allowed to touch that table. T1 (OWASP API1:2023, is the #1-ranked API vulnerability in both the 2019 and 2023 editions).
2. **RBAC is the correct default model for Solen's four roles (customer / salon_owner / staff / admin).** Solen does not need ABAC or a graph-based policy engine (Zanzibar/OpenFGA/SpiceDB) at 28 salons; those solve problems Solen does not have yet (cross-org sharing, deeply nested resource hierarchies, millions of relationship tuples). T2/CONV, with the scale caveat spelled out in section 1.
3. **RLS is Solen's real authorization enforcement layer, not a decoration on top of app-code checks.** Every table in the live snapshot has RLS enabled (146/146, `rlsDisabled: []`) and 326 `CREATE POLICY` statements exist across migrations. Treat a missing or wrong policy as a live vulnerability, not a style nit. T1 (Postgres RLS is the actual SQL-level enforcement, applied as an implicit `WHERE`; Supabase docs).
4. **The service-role client is a live authorization bypass, not a client library quirk.** `SUPABASE_SERVICE_ROLE_KEY` maps to a Postgres role with the `BYPASSRLS` attribute; it "skips any and all Row Level Security policies," full stop. 267 files in Solen's `app/`+`lib/` call `createAdminSupabaseClient()`. Every one of those call sites is now a hand-written authorization check with zero backstop from the database. T1 (Supabase official docs, quoting Postgres's own `BYPASSRLS` semantics).
5. **Defense in depth means checking authorization in at least two independent layers that fail differently, not the same check copy-pasted twice.** Solen's actual second layer is Postgres RLS underneath the app-code check, which is the right pairing because RLS fails differently (silently, at the SQL level) than an app-code `if` (which throws or 403s). Middleware alone is not a security boundary: Next.js middleware itself had a full authorization-bypass CVE in 2025 (CVE-2025-29927, header-based, fixed in 15.2.3; Solen is on 15.3.8, patched, but the pattern it exposed, "the edge layer can be tricked into skipping itself," is the argument for never trusting middleware as the only gate). T1 (NVD CVE) + T2 (multiple independent vendor writeups).
6. **Tenant isolation ("forgot the WHERE clause") is a special case of object-level authorization, and RLS's fail-silent behavior makes it worse, not better, if nobody checks the affected-row count.** Solen's own audits already document this exact class three times (bookings, group_bookings, availability_slots). AWS's own tenant-isolation guidance says the same thing: a missing `WHERE tenant_id = ...` without RLS just leaks data across tenants; the same missing clause WITH RLS returns an empty result set instead of an error, which is safe for reads but means a write silently no-ops and callers MUST check row counts. T2 (AWS Database Blog + Solen's own three documented incidents).
7. **Policy-as-code (OPA/Rego, Cedar) is correct in principle and premature for Solen today.** It solves "authorization logic is scattered across 300+ files and nobody can audit it centrally," which IS a real Solen problem (see section 2), but the fix at 28 salons is a shared helper library + a lint/grep-able convention, not a standalone policy engine with its own deploy and latency budget. T2, scale-gated, revisit trigger given in "Premature at our scale."
8. **A role check answers "can users with this role ever do this kind of thing." An object check answers "can THIS user do it to THIS row, right now."** Confusing the two is how BOLA happens: code that correctly gates a route to `role === 'salon_owner'` but then trusts a client-supplied `salonId` without checking `salons.owner_id === user.id` is vulnerable even though the role check "worked." T1 (OWASP API1 vs API5 distinction, both fetched this session).
9. **Function-level authorization (vertical, "can this role hit this endpoint at all") and object-level authorization (horizontal, "can this identity touch this row") are two different checks and Solen needs both on every privileged route**, not one standing in for the other. T1 (OWASP API5:2023).

## 1. RBAC vs ABAC vs ReBAC (Zanzibar/OpenFGA/SpiceDB): which fits Solen

**The question.** Solen has four roles (`profiles.role`: `customer`, `salon_owner`, `staff`, `admin`, `_docs/BACKEND.md:43`) plus a resource-scoping dimension (which salon does a given owner/staff member belong to) and a per-object ownership dimension (does this specific booking/review/photo belong to this specific user). Which authorization model should express this: role-based (RBAC), attribute-based (ABAC), or relationship-based (ReBAC, the Zanzibar/OpenFGA/SpiceDB family)?

**What each model actually is, from primary sources.**

- **RBAC**: "an approach to restricting system access to authorized users," built on users to roles to permissions, with sessions as the runtime binding. The NIST/ANSI/INCITS RBAC standard (2004) defines three levels: Core RBAC, Hierarchical RBAC (role inheritance), Constrained RBAC (separation of duties). Its own documented weakness is "role explosion": once you need access control finer than a role can express, you either multiply roles combinatorially or bolt something else on. T1 (Wikipedia RBAC, summarizing the NIST/ANSI/INCITS standard; [en.wikipedia.org/wiki/Role-based_access_control](https://en.wikipedia.org/wiki/Role-based_access_control)).
- **ABAC**: per NIST SP 800-162 (the actual federal guide, published January 2014, updated 2019), "a logical access control methodology where authorization to perform a set of operations is determined by evaluating attributes associated with the subject, object, requested operations, and, in some cases, environment conditions against policy, rules, or relationships." Its architecture separates four functional points: Policy Enforcement Point (PEP, where the check happens), Policy Decision Point (PDP, where the decision is computed), Policy Information Point (PIP, where attribute values come from), Policy Administration Point (PAP, where rules are authored). T1 ([csrc.nist.gov/pubs/sp/800/162/upd2/final](https://csrc.nist.gov/pubs/sp/800/162/upd2/final); PEP/PDP/PIP/PAP breakdown corroborated by NIST's ABAC framing summarized in Wikipedia's ABAC article, [en.wikipedia.org/wiki/Attribute-based_access_control](https://en.wikipedia.org/wiki/Attribute-based_access_control)). ABAC's stated cost: "the more granular the controls, the higher the [performance] overhead," and policy-combination complexity grows with the number of attributes in play.
- **ReBAC (Zanzibar/OpenFGA/SpiceDB)**: Google's Zanzibar (USENIX ATC 2019) is "a global system for storing and evaluating access control lists" unifying authorization across Calendar, Drive, Maps, Photos, YouTube and hundreds of other Google services, on a relationship-tuple data model, `namespace:object#relation@user`, plus a consistency token ("Zookie") so a permission change is guaranteed to be visible before the object change it protects becomes visible (external consistency). Its published production numbers: trillions of ACLs, millions of authorization requests/second, 95th-percentile latency under 10ms, >99.999% availability, sustained 3+ years. T1/T2 (Google Research's own paper summary page, [research.google/pubs/zanzibar-googles-consistent-global-authorization-system](https://research.google/pubs/zanzibar-googles-consistent-global-authorization-system/)). **OpenFGA** and **SpiceDB** are the two production-grade open-source implementations of the Zanzibar model; OpenFGA's own docs describe ReBAC as directly modeling "relationships between specific users and resources, enabling dynamic permission patterns like shared team access, hierarchical object relationships, and contextual conditions without rigid role categories," and state their tuple syntax "closely follows the original syntax in the Zanzibar Paper." T2 ([openfga.dev/docs/concepts](https://openfga.dev/docs/concepts)).

**Where the real tradeoff lies.** RBAC is cheap to reason about and cheap to audit ("what can a `salon_owner` do" is one grep) but cannot express "this specific staff member can see this specific salon's bookings" without either a role per salon (explosion) or bolting ownership checks on in app code anyway. ABAC is maximally expressive but every policy decision now depends on which attributes were actually loaded at decision time, which is exactly the kind of thing that goes silently wrong in a codebase that already has a silent-no-op problem: a policy that says "if attribute X" quietly evaluates false, not "policy X does not exist," when X is missing or misnamed. ReBAC (Zanzibar/OpenFGA/SpiceDB) is built for graphs of nested relationships at Google-scale traffic (millions of QPS, sub-10ms P95) and its cost is running and operating a whole separate authorization service with its own consistency model, on top of what you already have in Postgres.

**Recommended default for Solen, and why it is NOT ABAC or ReBAC today.** Solen's actual shape is: a small number of flat roles, plus ownership that is always exactly one hop away (a booking belongs to one customer and one salon; a salon belongs to one owner; a staff member belongs to one salon). That is RBAC (for "what can this role generally do") **plus per-row ownership checks** (for "can this identity touch this row"), which is precisely what Postgres RLS already gives you for free when the policy is written as `owner_id = auth.uid()`. Reaching for Zanzibar/OpenFGA/SpiceDB at 28 salons would mean running and paying for a second stateful service, replicating a consistency model Postgres already gives you as a side effect of being one database, and re-deriving "salon owner can manage their own staff" as a graph query instead of a one-line RLS `EXISTS`. Cost: an entirely new piece of infrastructure, a new failure mode (tuple/DB consistency drift), and a team that now has to reason about authorization in two systems. **Recommended: RBAC (role column + route-level role gate) as the outer check, RLS ownership predicates as the inner, per-row check, nothing more, for the current shape of the product.** T2/CONV, see "Premature at our scale" for the one real gap this leaves open (staff-to-salon access, which genuinely IS a relationship the current model does not express anywhere, RLS or app-code, see section 5).

## 2. Where authorization should live: edge middleware vs route handler vs service layer vs database RLS vs a policy engine, and the case for more than one

**The question.** Solen has (at least) four candidate places to put an authorization check: `middleware.ts` (Next.js edge middleware, runs before the route), the route handler itself (`app/api/**/route.ts`), a shared service/lib layer (`lib/auth/require.ts`, `lib/bookings/claim-slot.ts`), and the database (Postgres RLS policies). Which one is authoritative, and is putting a check in more than one place redundant waste or real defense in depth?

**What the evidence says.**

- **Middleware is not, and cannot be, the sole authorization boundary.** Next.js middleware had a full authorization-bypass vulnerability, CVE-2025-29927: a crafted `x-middleware-subrequest` header made Next.js treat an external request as an internal subrequest and skip the middleware entirely, so any route gated only by middleware (e.g. an admin path) became reachable with one extra header. Affected: all Next.js releases before 12.3.5, 13.5.9, 14.2.25, and 15.2.3. T1 ([nvd.nist.gov/vuln/detail/CVE-2025-29927](https://nvd.nist.gov/vuln/detail/CVE-2025-29927)), corroborated independently by Datadog Security Labs, JFrog, and Zscaler ThreatLabz writeups (T2, multiple independent vendor confirmations converging on the same mechanism). **Solen fact-check: package.json pins Next.js 15.3.8, which is past the 15.2.3 fix line, so Solen is not vulnerable to this specific CVE.** But the CVE is the concrete proof of the abstract argument: the edge layer is reachable and spoofable in ways a route handler running your own code is not, so it must never be the only check.
- **The route handler is where the actual per-request identity and per-object check has to live**, because it is the layer that both knows the specific object ID being requested and can call out to the database to verify ownership before acting. This is a restatement, not a new claim, of OWASP's own prevention guidance for both BOLA and Broken Function Level Authorization: "check authorization in every function that uses an input from the client to access a record" (API1) and "make sure all administrative controllers inherit from an administrative abstract controller that implements authorization checks" (API5), i.e. the check belongs at the function/handler level, every time, not once upstream. T1 (OWASP API1:2023 and API5:2023, both fetched this session).
- **The database (RLS) is the layer that fails differently from all the others, which is exactly why it is worth having as a second, independent check rather than a duplicate of the first.** Supabase's own RLS docs describe policies as an implicit `WHERE` clause Postgres itself enforces on every query issued through a non-service-role client, and explicitly frame it as defense in depth: it holds even if the request comes from "third-party tools" that never went through your app code at all (a Supabase Studio query, a leaked anon key hitting PostgREST directly, a future code path nobody remembered to add a check to). T1 ([supabase.com/docs/guides/database/postgres/row-level-security](https://supabase.com/docs/guides/database/postgres/row-level-security)).
- **A dedicated policy engine (OPA/Rego, Cedar) is a fifth candidate layer**, whose actual pitch is centralizing and versioning policy so it can be "read, write, analyze, version, distribute, and enforce... separate from the service itself," decoupling the policy DECISION from its enforcement point. T2 ([openpolicyagent.org/docs/latest/philosophy](https://www.openpolicyagent.org/docs/latest/philosophy)). This is the right answer to "authorization logic is scattered across 300+ files," which is Solen's actual documented state (see the "Myths and traps" section), but it is a heavyweight answer.

**The real tradeoff.** Putting a check in exactly one place is efficient but single-point-of-failure: if that one place has a bug (a stale role check, a forgotten `.eq("owner_id", ...)`, a middleware CVE), there is nothing behind it. Putting the identical check in every layer is wasted latency and a maintenance burden (four places to update when the rule changes) without actually adding protection, because a bug in the shared logic is copy-pasted everywhere it was duplicated. The valuable form of defense in depth is layers that are **independently implemented and fail differently**: an app-code `if` fails by 403/throw (loud), RLS fails by returning zero rows (silent but provably absent from the result), middleware fails by redirect (can be routed around). Two of these catching the same bug independently is real depth; the same one-liner pasted twice is not.

**Recommended default for Solen.** Keep the two layers Solen already has by construction: (1) the route handler does the identity check (`getUser()`) and the coarse role/feature gate, then issues the actual query; (2) RLS enforces the fine-grained per-row ownership predicate underneath it, for every table, all the time, whether or not the app-code check was written correctly. Middleware stays a UX-and-perimeter convenience (redirect unauthenticated users to login, gate `/dashboard` from anonymous traffic) and must never be the only place a sensitive check lives, which the CVE above already proves for Next.js specifically. Do not add a fifth policy-engine layer yet (see "Premature at our scale"). Cost of this recommendation: none beyond what Solen is already paying, since both layers already exist; the actual work is closing gaps where one layer is missing (see section 5's staff-access gap and section 4's service-role gap).

## 3. Object-level authorization: IDOR/BOLA is #1 and cannot be replaced by a role check

**The question.** Is a correct role check ("is this user a `salon_owner`") sufficient to protect a route that also takes a client-supplied object ID ("update booking `{id}`")?

**What the evidence says.** No, and this is not a minor nuance, it is the #1-ranked API vulnerability in the current OWASP list. **API1:2023, Broken Object Level Authorization**, is defined as occurring when "the server component usually does not fully track the client's state, and instead, relies more on parameters like object IDs... sent within the request to decide which objects to access," without validating "that a user can only access the objects that they should have permissions to access." OWASP rates its exploitability as "Easy": attackers manipulate object identifiers (sequential integers, UUIDs, strings) via path params, query strings, headers, or payloads. Impact: "moderate" technical severity to confidentiality/integrity but the business impact reaches "data disclosure to unauthorized parties, data loss, or data manipulation" up to "full account takeover." T1 (OWASP API1:2023, [owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization](https://owasp.org/API-Security/editions/2023/en/0xa1-broken-object-level-authorization/)). BOLA held the #1 spot in BOTH the 2019 and the current 2023 edition of the OWASP API Security Top 10, and is reported to appear in around 40% of real-world API attacks (T2, directional industry figure from vendor analysis, not an OWASP-published number, treat the "40%" as qualitative "very common" rather than load-bearing precision).

**Why a role check cannot substitute.** A role check answers a coarse question: "can a `salon_owner`, in general, update a booking." An object check answers a specific one: "can THIS `salon_owner` update THIS booking, which belongs to THAT salon." Code can pass the first check while failing the second: `role === 'salon_owner'` is true, and the code still updates `bookings` where `id = req.body.bookingId` without ever checking that booking's `salon_id` belongs to this owner. OWASP's own prevention list is explicitly about this gap: deploy authorization that "relies on the user policies and hierarchy" (not just role), and "check authorization in every function that uses an input from the client to access a record," plus using unpredictable IDs (GUIDs, which Solen already does via `gen_random_uuid()` on every primary key, e.g. `supabase/migrations/014_new_schema.sql`) as a mitigation for ID-guessing but never a substitute for the check itself.

**Solen's own version of this, already documented.** `_docs/BACKEND.md` names the exact mechanism by which Solen's RLS is supposed to provide this check and where it currently does not: `availability_slots` has exactly one write-capable policy (`slots_manage_owner`, owner-only), so a logged-in customer's session client silently matches zero rows on a slot claim, and the main `bookings/route.ts` creation path's own inline slot claim (`app/api/bookings/route.ts:531`) and rollback deletes (`:541,549,554`) route through the session client for a logged-in user rather than the documented `claimSlot()` admin-client helper, an unresolved contradiction between the documented invariant and the live code at those exact lines (flagged, not verified live, in `_docs/BACKEND.md` section 2). This is a live candidate for the row-level side of the object-level-authorization gap: not that the wrong user can claim someone else's slot (RLS still blocks that), but that a legitimate own-slot claim can silently no-op and leave a corrupted booking state, which is the "prove behavior, not existence" failure mode from Solen's own CLAUDE.md, applied to authorization specifically.

**Recommended default for Solen.** Every route that accepts a client-supplied object ID (booking ID, salon ID, review ID, client/customer ID, staff ID) must load that specific row and assert ownership/scope before acting on it, in addition to any role check, and that assertion must check the actual affected-row count on writes, not just the absence of a Postgres error (per the RLS-silent-zero-rows trap already documented project-wide). Cost: one extra `SELECT`/`.eq()` per privileged route; this is not optional plumbing, it is the check.

## 4. Tenant isolation enforcement: the "forgot the tenant_id WHERE clause" class

**The question.** Solen is a multi-tenant marketplace (each salon is a tenant of sorts, sharing one Postgres database with every other salon). What is the standard failure mode here, and what does the standard fix look like?

**What the evidence says.** This is a named, well-documented pattern in multi-tenant SaaS architecture, not a Solen-specific worry. AWS's own guidance (SaaS Tenant Isolation Strategies whitepaper, and the AWS Database Blog's worked Postgres example) states the pooled/shared-database multi-tenant model "can be more difficult to enforce your data access policies, and is commonly implemented by hoping the correct WHERE clause is implemented in every SQL statement," i.e. without a database-enforced backstop, tenant isolation is exactly as strong as every single query's hand-written filter, forever, across every future code change. The documented fix is Postgres RLS with a tenant-scoped policy, e.g. `CREATE POLICY tenant_isolation_policy ON tenant USING (tenant_id = current_setting('app.current_tenant')::UUID)`, plus `FORCE ROW LEVEL SECURITY` on the table (because by default, the table OWNER role still bypasses its own RLS policies, so forgetting `FORCE` silently reopens the hole for exactly the role most likely to run migrations/queries in production). T2 (AWS Database Blog, [aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security](https://aws.amazon.com/blogs/database/multi-tenant-data-isolation-with-postgresql-row-level-security/)).

**The sharp edge that matters for Solen specifically.** The same AWS source states plainly what RLS does when the WHERE clause is missing and RLS IS enabled: "rows that don't match the policy's USING statement simply do not exist in the result set," i.e. RLS converts a would-be data leak into a silent empty result, which is good for reads (nothing leaks) but dangerous for writes (an UPDATE/DELETE that should have hit one row hits zero, with no error, and the caller has to explicitly check the row count to notice). This is the exact same shape as Solen's own documented "silent no-op" incidents. `_docs/BACKEND.md` names three concrete occurrences of this precise class inside Solen already: (1) `availability_slots` writes from a non-owner session client (`slots_manage_owner` policy), (2) `bookings` having NO delete policy for anyone but `service_role`, so a session-client rollback delete after a failed slot claim silently no-ops and leaves an orphaned row (flagged as unresolved at `app/api/bookings/route.ts:541,549,554`), and (3) a prior, already-fixed instance on `group_bookings` (`_plans/BOOKING_BACKEND_AUDIT.md:187`, closed by two migrations, verified per `_plans/BACKEND_FIX_TRACKER.md:27`). This is not a hypothetical pattern description, it is Solen's own incident history matching the textbook failure mode exactly.

**Recommended default for Solen.** Solen's tenant boundary is `salon_id`/`owner_id`, not a literal multi-tenant SaaS "tenant" column, but the mechanism is identical: (1) every table scoped to a salon needs an RLS policy that checks `salons.owner_id = auth.uid()` (or the salon's staff relationship, once that's modeled, see section 5) for writes, which 326 `CREATE POLICY` statements across Solen's migrations already attempt; (2) every write issued against such a table, from EITHER the session client or (especially) the service-role client, must check the affected-row count and treat zero as a failure, not a no-op success; (3) `FORCE ROW LEVEL SECURITY` is a genuine gap-check worth running against Solen's live schema (not verified in this research pass, flagged in Unverified) since Postgres's default (table owner still bypasses its own policies) is exactly the kind of silent hole this whole file is about.

## 5. Policy-as-code

**The question.** Should Solen's authorization rules live as data/config in a dedicated policy engine (OPA/Rego, AWS Cedar, or similar) instead of scattered as `if` statements across route handlers?

**What the evidence says.** The stated purpose of policy-as-code, per OPA's own philosophy docs, is decoupling: "software services should allow policies to be specified declaratively, updated at any time without recompiling or redeploying, and enforced automatically," with authorization DECISIONS made by a separate engine (the PDP) that the application (the PEP) simply queries, rather than every service re-implementing its own authorization logic from scratch. T2 ([openpolicyagent.org/docs/latest/philosophy](https://www.openpolicyagent.org/docs/latest/philosophy)). This maps directly onto NIST 800-162's PEP/PDP/PIP/PAP architecture from section 1: policy-as-code is one concrete way to build a PDP that many PEPs can share.

**Where the real tradeoff lies.** A policy engine is the correct fix for "authorization logic is duplicated and drifting across dozens of services with no single source of truth to audit," which is a real, large-company problem. It costs: a new service to run (or an embedded WASM/Rego evaluator to maintain), a new language for whoever writes policy (Rego has its own learning curve), a new place authorization bugs can now hide (a Rego policy bug is just as capable of silently evaluating to `allow: false` for everyone or `allow: true` for nobody as an app-code bug is), and a new latency hop on every authorization-sensitive request unless the policy is evaluated in-process.

**Solen's actual version of the underlying problem, which policy-as-code would nominally fix.** `_docs/BACKEND.md` documents this exists today, at a smaller scale than "policy as code" is built for: `lib/auth/require.ts` defines "canonical" `requireAuth`/`requireAdmin`/`requireSalonOwner`/`requireRole` helpers, but **zero files under `app/` or `lib/` actually import them** (grepped across the whole tree, per `_docs/BACKEND.md:41`). Instead, 244 files inline their own `getUser()` + `.from("profiles").select("role")` check, 84 files inline an admin check shaped like `profile?.role !== "admin"`, 50 files inline an owner check shaped like `salon.owner_id !== user.id`, and one route (`app/api/admin/seed-test-salons/route.ts:18-30`) defines its OWN locally-scoped function literally named `requireAdmin()` that duplicates the shared helper's logic instead of importing it. This is exactly the "scattered, undauditable, drifting" state policy-as-code exists to solve, just at a scale (a few hundred inline checks in one codebase, not thousands of policies across many services) where the fix is a shared TypeScript helper actually being adopted, not a new runtime.

**Recommended default for Solen.** Do not adopt OPA/Cedar/a policy engine now (see "Premature at our scale"). DO treat this finding as the actionable version of "policy as code" for Solen's current size: make `lib/auth/require.ts`'s helpers the ONE place role/ownership logic lives, actually import them everywhere, and delete the 244+ inline re-implementations over time (or, at minimum, stop writing new inline copies; a grep-based lint rule catching a new inline `profile?.role !==` pattern outside `lib/auth/` would give most of policy-as-code's audit benefit at zero infrastructure cost). Cost: a refactor across ~300 call sites, which is real but bounded, versus running a new stateful service.

## 6. The Supabase trap: service-role bypasses RLS entirely, so every service-role read/write is a hand-rolled check

**The question.** What exactly does the Supabase/Postgres `service_role` key do to authorization, and what does that mean for every route in Solen that uses it?

**What the evidence says, precisely.** Supabase's own API-keys documentation states plainly: the service_role key "by design... has full access to your project's data. It also uses the BYPASSRLS attribute, skipping any and all Row Level Security policies you attach." T1 ([supabase.com/docs/guides/api/api-keys](https://supabase.com/docs/guides/api/api-keys), directly quoting Postgres's own `BYPASSRLS` role attribute semantics, [postgresql.org/docs/current/ddl-rowsecurity.html](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)). This is not a client-library setting that can be worked around with a header; `BYPASSRLS` is a Postgres role attribute evaluated by the database itself, independent of which client library or which headers are attached to the connection. The RLS overview docs add the operational warning directly: "these should never be used in the browser or exposed to customers," server-side-only, by design. T1 ([supabase.com/docs/guides/database/postgres/row-level-security](https://supabase.com/docs/guides/database/postgres/row-level-security)).

**What this means concretely.** Once a route calls `createAdminSupabaseClient()`, Postgres does not check ANY policy for that connection, for ANY table, for the rest of that request. Every ownership/scope/role check that would otherwise have been RLS's job is now 100% the responsibility of the application code that called the admin client, with zero backstop. Solen's own `_docs/BACKEND.md` states this as an explicit invariant: "the admin client does no authorization by itself. Every route using `createAdminSupabaseClient()` must independently verify the caller owns the resource... before issuing the write; RLS provides zero protection once you're on the service-role client" (`_docs/BACKEND.md:153`).

**Solen's actual exposure, measured this session.** `grep -rl "createAdminSupabaseClient" app/ lib/` returns **267 files**. Every one of those 267 files is, by definition, a place where RLS is providing zero protection and the entire authorization decision rests on whatever `if` statements that specific file's author remembered to write. This is by far the largest attack surface for BOLA (section 3) and tenant-isolation gaps (section 4) in the whole codebase, larger than every RLS policy gap combined, precisely because it is 267 independent, hand-written, unaudited copies of "did this developer remember to check ownership before this specific admin-client call."

**The reason this specific client exists at all, and why it can't just be removed.** Solen's own documented "RLS-client trap" (`_docs/BACKEND.md:119-121`) is that some legitimate operations (claiming an availability slot on behalf of a customer, who is never the salon owner and thus never satisfies `slots_manage_owner`) cannot be done through the session client at all under the current policy shape, so the admin client is the only way to make the write succeed. The admin client is not a mistake, it is the necessary escape hatch for exactly the cases RLS's simple ownership model can't express (a customer legitimately modifying a slot they don't "own" under the salon-owner-only policy). The bug is not that the escape hatch exists, it's that using it removes ALL protection, not just the one policy that was in the way, so every escape-hatch call site needs to reconstruct the FULL authorization decision by hand, and 267 call sites is a lot of places for that reconstruction to have a gap.

**Recommended default for Solen.** Treat every new `createAdminSupabaseClient()` call site as requiring an explicit, visible ownership/role check immediately adjacent to it in the same function, the same discipline the S1 security work already applies elsewhere. A worthwhile follow-up audit (not scoped to this research file, flagged for a future backend audit pass): sample a meaningful fraction of the 267 call sites and verify each one actually performs the check `_docs/BACKEND.md` says it must, rather than assuming "it's an admin-client call, so it must have been reviewed." Cost: this is audit effort, not a design change, since the two-client model itself is the right shape; the risk is purely in unaudited drift across 267 sites over time.

## Myths and traps

- **MYTH: "a passed role check means the request is authorized."** It means the request passed a VERTICAL check (can this role class hit this endpoint at all). It says nothing about the HORIZONTAL check (can this specific identity touch this specific row). OWASP splits these into two separate, separately-ranked vulnerabilities (API1 BOLA vs API5 Broken Function Level Authorization) for exactly this reason; conflating them is the single most common real-world API authorization bug. T1.
- **MYTH: "RLS protects me even through the admin client."** False by design; `BYPASSRLS` is a Postgres role attribute, not a client-library convenience that can be reasoned around. Once a query runs on the service-role connection, Postgres evaluates zero policies for it. T1. This is Solen's single biggest live authorization surface (267 call sites).
- **TRAP (generic, not Solen-specific): "middleware/edge auth is enough."** CVE-2025-29927 is the concrete, dated proof that an edge-layer-only check can be bypassed by a crafted request that never reaches the "real" check at all. Solen's Next.js 15.3.8 is patched against this specific CVE, but the argument (never make the edge layer your only gate) outlives the specific CVE number. T1.
- **TRAP (Solen-specific, PostgREST): a filtered write that matches zero rows returns `error: null`, not a failure.** This is not unique to authorization, it's Solen's documented #1 general silent-no-op class, but it is MOST dangerous specifically in authorization code, because "the write silently didn't happen" and "the write correctly refused an unauthorized caller" look byte-for-byte identical from the response alone. Every authorization-sensitive write (a slot claim, a status transition, a booking cancellation) must check the actual affected-row count, never just the absence of an `error` field. Documented three times already in Solen's own audits (`availability_slots`, `bookings` DELETE, the now-fixed `group_bookings`).
- **TRAP (Solen-specific, Stripe Connect): destination-charge transfers still need an app-level ownership check on which salon's connected account gets the money.** Solen routes tips/payouts via `transfer_data: { destination: stripeAccountId }` (`app/api/tips/route.ts:142`, `app/api/walkin/tip/route.ts:160`), reading `stripe_account_id` off the `salons` row associated with the booking. Stripe's own Connect authentication docs describe account-scoping (the `Stripe-Account` header or the `stripeAccount` client param) as a MECHANISM for directing a call at a specific connected account; Stripe's docs do not themselves enforce that YOUR code picked the right account for the right customer's booking, that check is entirely Solen's to make, the same shape as the service-role trap: the platform gives you power to act as/for an account, it does not verify you were authorized to act for THIS one. T2 (Stripe Connect docs, fetched this session).
- **CONV, not an empirical truth: "REST verb maps to CRUD permission."** Treating `DELETE /bookings/:id` as automatically requiring "delete" permission and nothing else is a convention, not a law; Solen's own `bookings` table has NO delete policy for anyone but service_role by design (deletions are meant to be an admin/service operation, not a customer self-service one), so a naive REST-verb-to-permission mapping would be actively wrong here. Don't assume the HTTP verb tells you the authorization rule.

## Premature at our scale

- **Zanzibar-style ReBAC (OpenFGA or SpiceDB) as a standalone authorization service.** Correct at Google's/large-marketplace scale (trillions of tuples, millions of QPS, deep sharing graphs). Solen has ~28 salons, a handful of roles, and ownership that is always one hop deep. Running a second stateful service to answer questions Postgres RLS already answers in a single `EXISTS` clause is pure overhead today. **Revisit trigger:** if Solen ever needs to express relationships RLS genuinely cannot (a staff member belonging to MULTIPLE salons with different permissions per salon, salon-to-salon delegated management, a partner/agency layer managing several salons' dashboards on their behalf), that is the first real ReBAC-shaped requirement, and it is also exactly the gap already visible today in section 5 (staff access is currently unmodeled in RLS at all).
- **A dedicated policy engine (OPA/Rego, AWS Cedar).** Correct once authorization logic needs to be authored, reviewed, and versioned by non-engineers, or needs to be shared identically across many independently-deployed services. Solen is one Next.js app on Netlify with ~300 inline checks in one repo; the actual fix (see section 5) is making everyone import the ONE existing `lib/auth/require.ts` helper instead of re-inlining the pattern, which is a refactor, not new infrastructure. **Revisit trigger:** if Solen ever splits into multiple independently-deployed services (a separate mobile backend, a separate admin service) that each need to make the same authorization decisions consistently without importing each other's code.
- **ABAC with a full PEP/PDP/PIP/PAP architecture.** Correct when authorization genuinely depends on many cross-cutting, situational attributes evaluated together (time of day, device trust score, geolocation, real-time risk signals) the way NIST 800-162 was written for (federal information-sharing environments). Solen's actual authorization inputs today are: role, salon ownership, staff-salon linkage (partially unmodeled), booking ownership. That's RBAC-plus-ownership, not ABAC. **Revisit trigger:** a genuine cross-cutting policy need shows up (e.g. "block bookings from this device fingerprint" or "require step-up verification if risk score exceeds threshold"), which is a fraud/trust-and-safety feature, not a routine authorization rule, and would likely be better served by a small number of explicit checks than a general ABAC engine even then.
- **`FORCE ROW LEVEL SECURITY` audited/enforced everywhere as a formal, tracked control.** The concept matters now (see section 4, it's the difference between "the table owner role also bypasses RLS by accident" and not), but formalizing it as a tracked compliance control with its own dashboard/reporting is premature; at 28 salons, a one-time grep/audit pass against the live schema is proportionate. **Revisit trigger:** a compliance requirement (SOC2, an enterprise salon customer's security questionnaire) that demands a documented, continuously-monitored control here.
