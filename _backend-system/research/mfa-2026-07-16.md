# MFA for the salon-owner/staff dashboard, research pass (2026-07-16)

Research only. No code touched. This answers `_backend-system/QUESTIONS.md` Q4 / audit finding AUTHN-09.

---

## Recommendation, in plain English

**Build it, but scope it down from what the question assumes, and build the recovery path in the same PR as the enrollment flow, not after.**

Three corrections to the original framing, all backed by evidence below:

1. **There is no "staff" dashboard login today.** I read the code: only two roles can reach `/dashboard` at all (`salon_owner`, `admin`), enforced in `middleware.ts`. The `staff_members` table is just a list of barbers you can book with, not a login account (its `access_role` column is explicitly commented in the code as "unused elsewhere in the codebase" (see file:line below)). So this is really "MFA for salon owners and platform admins," not "owners and staff." Nobody else needs to be touched.
2. **Use the App Authenticator (TOTP) factor only, never the Phone/SMS factor.** TOTP is free and on by default. Phone MFA costs real money ($75/month, see below) AND Solen's own security law doc already flags SMS-as-MFA as a myth to avoid (SIM-swap risk). So the "is it free" question has one clean answer only if you pick TOTP.
3. **The lost-phone problem is worse than a generic "support burden."** Supabase does not hand you backup codes. If an owner enrolls one TOTP factor and loses the phone with no second factor registered, the only way back in is someone with your Supabase service-role key manually deleting their MFA factor. That "someone" has to be Solen, not Supabase support, because Solen owns the project. This is a concrete on-call task you're signing up for, not paperwork. Details and the exact API call below.

Net: yes, do it. It is free, real, and closes the highest-leverage gap on the account tier that sits next to payouts. But the honest scope is a slightly smaller build (2 roles, 1 factor type, 1 dashboard settings page) plus a recovery runbook you must write before turning it on for anyone, because there is no vendor safety net once an owner is locked out.

## 1. What Supabase Auth MFA ships today

**Verified** against the live Supabase docs (fetched this session via the Supabase MCP `search_docs` tool) and cross-checked against the code actually installed in this repo (`node_modules/@supabase/auth-js@2.110.2`, pinned via `@supabase/supabase-js: ^2.110.2` in `package.json`).

- **Factor types Supabase Auth supports:** App Authenticator (TOTP) and Phone (SMS-based OTP as a second factor). Source: [supabase.com/docs/guides/auth/auth-mfa](https://supabase.com/docs/guides/auth/auth-mfa), [supabase.com/docs/guides/auth/auth-mfa/totp](https://supabase.com/docs/guides/auth/auth-mfa/totp).
- **TOTP is GA and free, on by default on every Supabase project.** Verified quote from the docs: *"TOTP MFA API is free to use and is enabled on all Supabase projects by default."*
- **The client API is exactly what the docs describe, verified in the installed code, not just read from docs.** I grepped `node_modules/@supabase/auth-js/dist/main/GoTrueClient.js:209-218` directly and found:
  ```
  this.mfa = {
    verify, enroll, unenroll, challenge, listFactors,
    challengeAndVerify, getAuthenticatorAssuranceLevel,
    webauthn: new WebAuthnApi(this),
  }
  ```
  and confirmed `factorType` accepts `'totp'` and `'phone'` at `GoTrueClient.js:4749-4751`. So every method named in the docs (`enroll`, `challenge`, `verify`, `unenroll`, `listFactors`, `getAuthenticatorAssuranceLevel`) is really shipped in the version this repo has installed, this is not a stale doc describing a newer SDK than we have.
- **A third factor type, WebAuthn-as-MFA, is present in the installed client code** (`this.mfa.webauthn`, a 706-line `WebAuthnApi` class at `node_modules/@supabase/auth-js/dist/main/lib/webauthn.js:424`) but I could **not** confirm it is GA-documented as an MFA factor: the main MFA guide only documents TOTP and Phone with full enroll/challenge/verify flows, and the self-hosted config guide says "the Auth service supports three MFA factor types" but only lists env-var toggles for two (`MFA_TOTP_*`, `MFA_PHONE_*`). **Tiering this "assume": the SDK ships WebAuthn MFA code, but I did not find a documented, stable enroll/challenge flow for it distinct from the separately-documented Passkey feature below.** Not needed for the recommendation either way, TOTP covers the ask.
- **Passkeys are a separate, different feature** (a primary sign-in replacement, not a second factor): sign in with a device passkey instead of password. Verified as **explicitly Experimental**: the docs literally head the feature "Experimental" and require `@supabase/supabase-js` v2.105.0+ (source: [supabase.com/docs/guides/auth/passkeys](https://supabase.com/docs/guides/auth/passkeys)). We're on 2.110.2 so the version floor is met, but "Experimental" from Supabase itself is reason enough to not build on it for a payout-adjacent tier. Not part of the recommendation.

## 2. Cost

**Verified** by fetching the live Supabase pricing page this session (not recalled from training):

- TOTP (App Authenticator) MFA: **free on every plan tier**, Free/Pro/Team/Enterprise all included.
- Phone-based MFA is a **paid add-on**: **$75/month for the first project, then $10/month per additional project** on Pro and Team plans.
- Plan tiers for reference: Free $0/mo, Pro $25/mo, Team $599/mo, Enterprise custom.

**Conclusion: this only stays free if you build on TOTP and never turn on Phone MFA.** That lines up with the security recommendation anyway (see the SMS/SIM-swap point below), so there's no tension between "cheap" and "secure" here, TOTP is both.

## 3. The AAL model, and whether RLS can read it

**Verified** from the live MFA guide (same URL as above), plus reasoned application to this repo's architecture (tiered "expect" where noted).

- Two levels: **`aal1`** (single factor, e.g. password/magic-link/OAuth login) and **`aal2`** (also passed an MFA challenge). Encoded as an `aal` claim directly inside the JWT.
- **Yes, RLS can read it, without any new plumbing.** Postgres RLS policies can do:
  ```sql
  create policy "require mfa"
    on some_table
    as restrictive
    to authenticated
    using ((select auth.jwt()->>'aal') = 'aal2');
  ```
  The `as restrictive` keyword is load-bearing: a restrictive policy narrows access regardless of what any permissive policy on the same table already allows, so this can be layered on top of Solen's existing owner-scoped policies without rewriting them.
- Supabase's own docs give three ready-made policy templates: enforce for **all** users, enforce for **new** users only (by `created_at` cutoff), or enforce **only for users who opted in** (checked by querying `auth.mfa_factors` for a `status = 'verified'` row). The third template is the natural rollout shape for Solen: it degrades to aal1-or-aal2 automatically for anyone who hasn't enrolled yet, so it can be turned on immediately without locking out the 28 existing owners (more in section 6).
- **The real nuance for Solen, reasoned from this repo's own architecture, not from the docs:** RLS is not the only gate here. `lib/auth/require.ts`'s `requireAdmin()` explicitly hands back a **service-role client** (`createAdminSupabaseClient()`, which bypasses RLS entirely) once the role check passes, and the codebase's own security notes (`fable-backend` skill, section 1) say outright: "a route using the service role bypasses RLS entirely, so it must do ownership checks itself." That means an `aal2`-only RLS policy protects direct client/anon-key reads and writes, but any API route that escalates to the admin client after `requireSalonOwner()`/`requireAdmin()` would need its **own** explicit `aal2` check in app code (reading the claim off `supabase.auth.getUser()`'s JWT, or calling `getAuthenticatorAssuranceLevel()`), because the DB-level policy never runs for that code path. **Expect, not verified by testing:** I did not find an existing helper in `lib/auth/require.ts` that reads `aal` today (grepped, zero hits for `aal`, `mfa`, `totp`, confirming AUTHN-09's "zero grep hits" claim independently). Any real implementation has to add this check to `requireSalonOwner`/`requireAdmin`, not just to RLS, or admin-client routes stay aal1-only despite the DB policy.

## 4. The lost-phone story, concretely

This is the part that turns "flip a free switch" into a real support commitment. Verified from three separate Supabase doc pages fetched this session:

- **Supabase does not issue backup/recovery codes.** Verified quote (from the Supabase-account-level MFA guide, which uses the identical underlying mechanism as project end-user MFA): *"Supabase does not return recovery codes. Instead, we recommend that you register a backup TOTP factor to use in an event that you lose access to your primary TOTP factor."*
- **If a user loses every enrolled factor, official guidance is blunt:** *"For security reasons, we will not be able to restore access to your account if you lose all your two-factor authentication credentials."* The dedicated troubleshooting page ([Lost access/Forgot the MFA device](https://supabase.com/docs/guides/troubleshooting/lost-accessforgot-the-mfa-device-nAPT-7)) says the only recourse at that level is to contact Supabase support, but that page is written for people locked out of their **own Supabase dashboard account**, not for end users of a project built on Supabase Auth. Supabase support cannot and will not reset an individual end-user's MFA factor inside your project on your behalf, this has to be a Solen-owned action.
- **The concrete, verified mechanism Solen would use:** `supabase.auth.admin.mfa.listFactors({ userId })` and `supabase.auth.admin.mfa.deleteFactor({ id: factorId, userId })`. I confirmed both methods exist in the installed `auth-js` package (`node_modules/@supabase/auth-js/dist/main/GoTrueAdminApi.js:36-37`, bound as `this.mfa = { listFactors, deleteFactor }`) and are documented at [auth-admin-listfactors](https://supabase.com/docs/reference/javascript/auth-admin-listfactors) and [auth-admin-deletefactor](https://supabase.com/docs/reference/javascript/auth-admin-deletefactor). Both run on the **service-role** client, which `lib/supabase.ts`'s `createAdminSupabaseClient()` already provides, so no new SDK, dependency, or infra is needed to build this, it's a ~10-line internal script or admin-dashboard button.
- **What "22:00 on a Saturday" actually looks like in practice, reasoned from the above (expect, not tested):** an owner with a pending payout calls or messages support, cannot get past the MFA challenge screen, and has no backup factor. Someone with access to the Supabase service-role key (today: whoever can run scripts against prod, i.e. the founder or whoever has the key) must identify the user, run `deleteFactor`, and tell the owner to log in again and immediately re-enroll. There is no self-service "I lost my phone" flow anywhere in Supabase Auth for this, Solen has to build even the minimal version: a support runbook (who has the key, what they run) at a minimum, an internal admin-dashboard button at best.
- **Mitigation that Supabase itself recommends and that costs nothing extra:** let users enroll a **second, backup TOTP factor** (a different device/app) at enrollment time, not as an afterthought. `MFA_MAX_ENROLLED_FACTORS` defaults to 10 per user (**assume**: verified only in the self-hosted Docker config docs, not explicitly confirmed for hosted projects, but there's no reason to expect hosted behaves differently since it's the same GoTrue server). Prompting "add a second device now" during enrollment is the single highest-leverage thing to build against the lost-phone story, and it's a UI decision, not an API limitation.

## 5. What this would touch in this repo, and the honest effort

Read directly, not guessed, before estimating:

- **`lib/auth/require.ts`** (`requireAuth`, `requireAdmin`, `requireSalonOwner`, `requireRole`, all four exported from `lib/auth/index.ts`): none of them check `aal` today. Each of the four would need an `aal2` branch if MFA is to be enforced at the app-code layer (needed per section 3's nuance, since service-role routes bypass RLS). Realistically this means one new shared helper (e.g. `requireAal2()` or a parameter on the existing helpers) plus updating call sites that guard payout-adjacent routes specifically, not all ~230 call sites the file's own comment says exist repo-wide.
- **`middleware.ts`** (lines 148-224 today gate `/dashboard` on `user` existing + `profile.role in (salon_owner, admin)`): this is the natural place to add the AAL redirect-to-MFA-challenge step, mirroring the existing pattern (it already redirects to `/auth/login` on no-user and to `/` on wrong-role). Supabase's own guidance here is explicit: don't hard 401/403 on an aal1 session, redirect to a challenge screen instead, because a mismatched AAL is very often just "still has the tab open from before enrolling," not an attack.
- **New surface, does not exist today:** an MFA enrollment/challenge UI. The natural home is `app/[locale]/dashboard/settings/page.tsx` (confirmed this is the only file in that folder today, a single settings page, good place for a "Security" section) for enrollment/unenrollment, plus a new challenge screen somewhere in the `/auth/login` flow (today `app/[locale]/auth/login/page.tsx` renders `components-legacy/auth/SignIn.tsx`, a 282-line client component that currently does email/password + Google OAuth + reset-password, with **zero** MFA branching) for the post-password TOTP code prompt.
- **`app/api/auth/login/route.ts`:** currently returns the session directly after `signInWithPassword`. Would need to branch on the response's AAL (check `getAuthenticatorAssuranceLevel()` after sign-in) and, if a challenge is pending, return a state the frontend uses to show the challenge screen instead of completing login.
- **New RLS migration:** at least one `as restrictive` policy (the "opted-in" template from section 3) on the tables that gate Stripe Connect payout data (`app/api/salon/invoices/[payoutId]/route.ts`, `app/api/stripe/connect/*` are the read paths I found; the exact tables need a look at what `invoices`/payout queries actually touch, not fully enumerated in this research pass).
- **A recovery/support tool:** the `deleteFactor` script or admin-dashboard button from section 4. Small in code, but it is a new operational responsibility (someone has to be reachable to run it), which is the real cost, not the code.

**Honest effort estimate (assume, this is a scope-and-judgment call, not a measured number):** this is a genuine multi-day feature, not a one-liner, in line with the audit's own framing ("real product work, not a one-liner"). Rough shape: 1-2 days for enrollment + challenge UI and the login-flow branching, half a day for the `aal2` check in `lib/auth/require.ts` and the RLS policy, half a day for the recovery tooling and runbook, plus QA time walking through "what happens when I lose my phone" end to end before it ever reaches a real owner. Call it a week of focused work including testing, not a sprint-filler.

## 6. Scope: who should get it

**Recommendation: salon owners and platform admins only (`profiles.role IN ('salon_owner', 'admin')`). Not customers. There is no separate "staff" tier to scope in or out, because it doesn't exist as a login concept yet.**

Reasoning, grounded in what the code actually does (verified, not assumed):

- `profiles.role` is a Postgres `CHECK` constraint with exactly three values: `'customer', 'salon_owner', 'admin'` (verified: `supabase/migrations/014_new_schema.sql:29`). There is no `'staff'` role.
- `staff_members` is a table of bookable people (barbers/stylists customers pick when booking), not an authentication concept. Its `access_role` column is explicitly dead: the code comment at `app/api/salons/route.ts:799-802` states *"'role' ... is a phantom column here: staff_members never had a 'role' column ... only 'access_role' (a permission level, unused elsewhere in the codebase)."* I independently grepped the whole `app/` and `lib/` tree for `access_role` usage and found only type-definition hits and that one comment, confirming "unused" is accurate today.
- `middleware.ts`'s dashboard gate (lines 148-224) checks only `profile.role` and, as a fallback, `salons.owner_id === user.id`. It never looks at `staff_members` or `staff_invites`. So today, a barber cannot independently log into the dashboard as themselves, only the salon owner account (or an admin) can.
- Forcing MFA on customers would be the wrong call: customers are booking haircuts, the blast radius of a compromised customer account is "someone can see or cancel your own appointment," nowhere near the payout access an owner account has. This matches the question's own framing and I found nothing in the code that changes that calculus.

If Solen later builds real per-staff dashboard logins (a `staff_invites`-backed login, distinct from the owner account), that new tier should get the same MFA requirement at build time, not retrofitted later, but that is a separate, currently-nonexistent feature and out of scope for this question.

## 7. Enforcement posture and the migration path for the 28 existing owners

**Recommendation: mandatory for the owner/admin tier, but rolled out via the "opted-in" RLS template plus a grace-period nudge, not a hard cutover that locks anyone out on day one.**

- Supabase's three enforcement templates (verified, section 3) map directly onto a safe rollout:
  1. Ship the enrollment UI and make it **encouraged but not required** at first (the "opted-in" RLS template: `aal2` required only for users who already have a verified factor, everyone else stays at whatever they have). Nobody is locked out on ship day, because nobody is forced into aal2 they didn't opt into.
  2. Nudge existing owners (banner in the dashboard, maybe an email) for a grace period.
  3. Flip to "enforce for all" (the first RLS template, unconditional `aal2` requirement) only once you've confirmed, per owner, that they've completed enrollment, or accept that a straggler gets locked out and needs the recovery runbook from section 4 to get back in.
- **Concretely for the 28 live salons:** none of them get force-enrolled the moment this ships. The rollout order should be: ship opt-in, grade owners into "enrolled" vs "not yet," follow up individually with the stragglers (this is a founder-scale operation at 28 salons, a phone call or WhatsApp per straggler is realistic), then flip enforcement once the list is short enough that a phone call, not a lockout, is the fallback.
- Doing a hard mandatory cutover on day one, given there is **no backup-code system** (section 4), would mean handing yourself a support ticket per unresponsive owner with a real chance some don't see the notice in time. The gradual path costs a little more calendar time and gets you to the same enforced end-state without that risk.

## 8. The strongest counter-argument, and whether it survives

**The case against building this now:** "Solen is 28 salons. MFA fixes a stolen-password scenario, but the actual measured incidents on this project (per the audit itself) are things like the fabricated-accessibility-flags bug, the dead CHF budget gate, and the NIST-violating password policy, none of which are 'someone logged into an owner account with a stolen password.' At this scale, the operational cost (support burden, a whole new UI surface, a recovery runbook someone has to actually staff) plausibly outweighs a risk that hasn't manifested yet. 'Premature at our scale' is a legitimate reason not to build something new."

**Does it survive? Partially, and it changes the recommendation's timing, not its yes/no.**

- It survives as a reason to **not treat this as the week's top priority.** The owner's own QUESTIONS.md draft already ranked it "after Q1 and the express-rebook fix," and nothing in this research changes that ordering, MFA is real work with no burning incident behind it.
- It does **not** survive as a reason to leave it undone indefinitely, for a reason specific to this codebase, not a generic "always add more security" argument: the account tier in question sits **directly next to Stripe Connect payout access** (verified: `app/api/stripe/connect/*`, `app/api/salon/invoices/[payoutId]/route.ts` are real, live routes gated only by `requireSalonOwner`/`requireAdmin`, single-factor). Combined with the fact that Q5 in the same audit found the current password policy is **below even NIST's floor for single-factor auth without MFA** (an 8-character floor with composition rules NIST calls counterproductive), the actual live posture today is: a payout-adjacent account can be reached by a single weak, possibly-reused password, with a policy that pushes users toward predictable patterns. That is a materially higher risk than "MFA in the abstract," and it is free to close with TOTP.
- The house framing itself draws this line explicitly: "premature at our scale" is legitimate for choosing not to *build* something new, but "never a reason to leave something broken." AUTHN-09 is filed as a **gap**, not a bug, so read narrowly this house rule doesn't strictly bind here, a missing control isn't the same as a broken one. But the Q5 password-policy finding (same audit, same tier of accounts) arguably tips this from "an absent nice-to-have" into "the two gaps compound into an actually weak floor for a payout-adjacent account today," which is closer to "broken" than "merely missing." That's a judgment call, not a fact I can verify further, flagged as such rather than asserted as settled.
