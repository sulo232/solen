# API design , researched law

Date: 2026-07-16. Sources fetched this run: 15 (listed at the bottom with what each established). For: any session building or reviewing a Solen `app/api/**/route.ts` file, or writing the mobile app's API contract.

Scale reminder used throughout: ~28 salons live, low traffic, serverless (Netlify functions, cold starts common), Postgres via Supabase/PostgREST plus hand-written route handlers, Stripe Connect for money. Solen has exactly one first-party web client (the Next.js app calling its own routes) plus one first-party mobile client (Expo/React Native) starting to consume the same routes. There is no public third-party API today.

## 0. The short version

The rules a new session must obey before touching an API route. Tier in brackets.

1. **Keep REST/JSON over Next.js Route Handlers as the one API style.** Do not introduce GraphQL, tRPC, or gRPC for the web+mobile surface. [T2, reasoned from our two-client shape, see section 1]
2. **201 responses that create a resource carry a `Location` header pointing at the new resource; 204 responses carry no body.** [T1, RFC 9110]
3. **409 = the state conflicts with the world (a slot got taken, a status changed under you). 422 = the request itself is well-formed but semantically wrong (a date in the past, a missing required combination).** Don't use 409 for validation errors or 422 for race losses. [T1, RFC 9110 + WebDAV RFC 4918 origin of 422]
4. **Every 429 response sets `Retry-After`.** Ours already does this on the normal path (`lib/ratelimit.ts:283-288`) but NOT on the fail-closed early return (`lib/ratelimit.ts:272`). That is a real gap, fix it. [T1, RFC 9110 section 10.2.3, verified against our own code]
5. **Any endpoint that spends money or has a side effect a client might retry must accept (or synthesize) an idempotency key, store it, and replay the ORIGINAL response on a repeat.** We already do this correctly for Stripe-facing writes (`lib/bookings/issue-refund.ts`, `booking-pay-intent`, cron `pre-charge`). Extend the same discipline to any new mutating endpoint that a flaky mobile network could double-fire. [T1, this is literally how Stripe's own API behaves, see section 3]
6. **Never use OFFSET pagination on a table that changes while the user scrolls, or past a few thousand rows.** Keyset (cursor: last-seen id/timestamp) pagination is the default for feeds and lists that grow; OFFSET is fine only for small, mostly-static, page-jump UIs (e.g. an admin table under ~2,000 rows). [T2, converging sources, section 4]
7. **Don't build a versioning scheme we don't need.** With one first-party client we own, "ship the route and the client together" beats any of URL-path, header, or Stripe-style date versioning. The single case that changes this is opening a public/partner API. [reasoned, section 5]
8. **Error responses should converge on ONE shape.** Ours today is an ad hoc `{ error: string }` (415 files use this pattern), which is fine for size but is not RFC 9457. Adopt the shape now for new/touched routes rather than inventing a second one; full backfill is not worth doing today (see Premature section). [T1 for the standard existing, T3 for how urgent adopting it is at our size]
9. **Validate at the trust boundary, not in the middle of business logic.** We already do this well: 137 route files import shared zod schemas from `lib/validations.ts` before touching the DB. Keep new routes on this pattern; never trust a client-supplied field (ownership, price, ids) without re-deriving it server-side. [T1, OWASP API Security Top 10, section 7]
10. **A long operation (AI generation, big export, Stripe payout batch) gets a job row plus polling, or a webhook it already fires into (Stripe), never a route that blocks the Lambda for 30+ seconds.** [T2, section 9, and this is a genuine Netlify function timeout risk, not just style]

## 1. REST vs GraphQL vs tRPC vs gRPC

**The question.** Solen's API is consumed by exactly two first-party clients we control (the Next.js web app calling its own route handlers, and the Expo mobile app calling the same routes over HTTPS/JSON) plus Stripe/cron webhooks calling in. There is no public third-party API. Given that shape, is REST/JSON the right choice, or should we move to GraphQL, tRPC, or gRPC?

**What the evidence says.**

- **tRPC** removes the schema/boilerplate layer entirely by sharing TypeScript types between server and client end to end: "tRPC allows you to create type-safe APIs without the need for schemas or boilerplate... When you make an API change, TypeScript immediately tells you which client call sites are affected" [T3, dev.to/pockit_tools "REST vs GraphQL vs tRPC vs gRPC in 2026", directional vendor-blog-style source, https://dev.to/pockit_tools/rest-vs-graphql-vs-trpc-vs-grpc-in-2026-the-definitive-guide-to-choosing-your-api-layer-1j8m]. The catch for Solen specifically: tRPC's type-sharing magic requires the client to import the server's TypeScript router types directly, which is trivial in a monorepo where the client is also TypeScript (our Next.js app) but does NOT work the same way for a React Native/Expo app unless it is in the same monorepo/workspace and stays perfectly in sync on every deploy. Our mobile app is a separate repo (`~/Documents/solen-mobile`). That kills the core value proposition of tRPC for us: half our client surface can't get the compile-time link.
- **GraphQL** solves over-fetching/under-fetching by letting the client shape the query: "GraphQL allows clients to specify exactly what data they need... eliminating over-fetching or under-fetching" [T3, same source]. This is a genuine advantage for apps with deeply nested, client-varying data needs (e.g. a social feed with wildly different views). It costs a schema layer, a resolver layer, N+1 query discipline, and caching complexity (GraphQL responses are hard to cache at the HTTP/CDN layer the way a REST GET is). For a booking marketplace with a fixed, small number of well-known screens (salon list, salon detail, booking flow, dashboard), the query-shaping benefit is marginal, we already know exactly what each screen needs.
- **gRPC** trades JSON/HTTP1.1 for Protobuf/HTTP2: "gRPC runs over HTTP/2 with Protobuf serialization and a required .proto contract. Protobuf payloads run 3 to 10x smaller... gRPC benchmarks consistently show lower p99 latency under high call volumes" but critically "It's impossible to directly call a gRPC service from a browser today... no browser provides the level of control required over web requests to support a gRPC client" [T2, two converging sources: graftcode.com/blog/grpc-vs-rest and last9.io/blog/grpc-vs-http-vs-rest]. gRPC's sweet spot is internal service-to-service calls at real scale (microservices, ML inference pipelines). Solen has a browser client and a mobile client, both of which would need a gRPC-Web shim or a REST/JSON translation layer just to talk to a native-gRPC backend, adding a whole compatibility layer for zero present benefit (we have no internal service mesh; Next.js API routes call Postgres/Stripe directly).
- **REST's own theoretical purity is mostly aspirational anyway.** Roy Fielding's REST requires the server to drive client navigation via embedded hyperlinks (HATEOAS): "a REST client should then be able to use server-provided links dynamically to discover all the available resources it needs" and Fielding himself has said "REST APIs must be hypertext driven", a requirement "frequently violated in practice-oriented implementations" [T1 for what Fielding's dissertation actually requires, T2 for how universally it's ignored, https://en.wikipedia.org/wiki/Representational_state_transfer]. Practically nobody's JSON API is "RESTful" by Fielding's original definition, including Stripe's. What the industry actually means by "REST" today is "resource-shaped URLs, HTTP verbs, JSON bodies", which is what Solen already does. Naming this precisely matters so nobody chases HATEOAS compliance as if it were a real requirement, it is CONV (a convention people call REST, not the thing Fielding described).

**Where the real tradeoff lies.** The performance argument for gRPC and the type-safety argument for tRPC both only pay off when you have MANY internal services calling each other (gRPC) or ONE shared TypeScript boundary across every client (tRPC). Solen has neither: one monolith-style Next.js backend, and two clients where only one is TypeScript-and-same-repo. GraphQL's flexibility argument pays off when client data shapes are unpredictable and vary a lot per screen or per client; ours don't, both clients want essentially the same salon/booking/dashboard shapes.

**Recommended default for Solen.** Stay on REST/JSON over Next.js Route Handlers. Cost of NOT switching: no compile-time client/server type link (mitigated already by hand-shared zod schemas + generated Supabase types), no query-shaping (mitigated by the fact each screen's data need is already known and stable), no HTTP/2 multiplexing win (irrelevant at 28 salons' traffic). Cost of switching to any of the three alternatives: real engineering time to migrate 354 existing route files, a second contract language to keep in sync with mobile, and for gRPC specifically an entire translation layer just to remain browser-reachable. This is not close.

**When this recommendation would flip.** If Solen ever exposes a genuine public/partner API (other businesses integrating against Solen bookings) GraphQL's flexible querying or a proper OpenAPI-described REST surface becomes worth evaluating fresh (see section 10). If the mobile app and web app ever move into one monorepo sharing a single TypeScript workspace, tRPC's tradeoff changes materially, revisit then, not before.

## 2. HTTP verbs and status codes

**The question.** Are we using status codes for what they actually mean, not just "200 if it worked, 400/500 if it didn't"?

**What the evidence says (RFC 9110, the current HTTP semantics RFC, June 2022, obsoletes the old RFC 7231).**

- **201 Created**: "The server has fulfilled the request by creating a new resource" [T1, https://datatracker.ietf.org/doc/html/rfc9110, section 15.3.2]. The convention (not literally mandated by 9110's text but universally paired) is that a 201 response includes a `Location` header pointing at the new resource's URL, per MDN and the wider HTTP status registry. Our codebase returns 201 in 45 places; whether each of those sets `Location` is worth an audit pass (see Audit Questions), it is not proven by grep alone.
- **204 No Content**: "The server has successfully fulfilled the request and there is no content to send in the response payload" [T1, same RFC, section 15.3.5]. Correct use: a DELETE or a PUT/PATCH that doesn't need to echo the updated resource back. Our codebase uses 204 only twice, which is plausible for a JSON API that tends to return the created/updated row (a defensible choice, not wrong, just worth naming: we generally prefer 200-with-body over 204 for updates, so the client doesn't have to re-fetch).
- **409 Conflict**: "The request conflicts with the current state of the server" [T1, same RFC, section 15.5.10]. This is the code for "someone else got there first": the slot you're booking was just taken, the refund CAS lost the race, a unique constraint would be violated. Our codebase already does this correctly and extensively (72 uses), e.g. the CAS-guarded refund and cancel flows documented in `_docs/BACKEND.md` sections on payments.
- **422 Unprocessable Content**: "The server understands the content type of the request entity and the syntax of the request entity is correct, but it was unable to process the contained instructions" [T1, same RFC, section 15.5.21, though the code number itself originates in RFC 4918/WebDAV and RFC 9110 folds it into mainline HTTP]. This is the code for "your JSON parsed fine and passed basic shape validation, but the values are business-logic-invalid" (e.g. a booking date in the past, an end time before a start time). Our codebase uses 422 exactly ONCE across 354 route files, and 400 fifteen times more often than 422 combined with 409. That strongly suggests 400 is doing double duty for both "malformed request" and "semantically invalid request", which blurs a distinction RFC 9110 draws on purpose (400 = "the server cannot or will not process the request due to something that is perceived to be a client error", a broader bucket; 422 narrows to "syntax is fine, semantics aren't"). This is not a crisis (both are 4xx, clients that just check `>= 400` behave identically), but it is real drift from the spec and worth naming rather than smoothing over.
- **429 Too Many Requests** plus **Retry-After**: RFC 9110 defines Retry-After as a response header telling the client when to retry, usable with 429 (rate limiting), 503 (temporary unavailability), and some 3xx redirects, with the value either a delay in seconds or an HTTP-date [T1, https://datatracker.ietf.org/doc/html/rfc9110, section 10.2.3]. **Verified directly against our own code**: `lib/ratelimit.ts` line 283-288 sets `Retry-After` correctly on the standard rate-limit-exceeded path (computed from the Redis-reported reset time). But the fail-closed branch at line 272 (`no Redis to ask, so this is the same 429 a real limit hit`) returns 429 WITHOUT a Retry-After header. That is a genuine, small, fixable gap: a client hitting the fail-closed path gets a 429 with no guidance on when to retry.

**The real tradeoff.** Being pedantic about 400 vs 422 costs nothing at read time (both are "client error, don't retry blindly") but pays off when a client wants to distinguish "my JSON was malformed, that's a client bug" from "my JSON was fine but this specific booking can't happen today", which matters for building good client-side error messages (mobile app especially: "check your input" vs "that date isn't available" are different UI treatments).

**Recommended default.** Use 422 for semantic/business-rule validation failures (a zod-shape pass but a business rule fail: booking in the past, invalid state transition attempted with valid-looking data) and reserve 400 for genuinely malformed requests (unparseable JSON, wrong content-type, missing required fields entirely). This is a naming/discipline change, not a breaking one, since both remain 4xx. Fix the fail-closed 429 gap in `lib/ratelimit.ts` regardless, it is a two-line fix with no tradeoff.

## 3. Idempotency keys (the Stripe pattern)

**The question.** How does Stripe's idempotency system actually work end to end (key scope, storage, replay, concurrency, expiry), and where does Solen already implement this correctly vs where should it extend?

**What the evidence says**, fetched directly from Stripe's own idempotency docs [T1, primary source, https://docs.stripe.com/api/idempotent_requests] plus Stripe's engineering blog post on the design rationale [T2, https://stripe.com/blog/idempotency]:

- **Mechanism**: the client generates a unique key (Stripe recommends "V4 UUIDs, or another random string with enough entropy to avoid collisions", explicitly warning against using anything containing sensitive data like an email) and sends it as the `Idempotency-Key` HTTP header on a POST. All POST requests accept idempotency keys; GET and DELETE are idempotent by definition and Stripe explicitly says not to send a key on those.
- **Storage and replay**: "Stripe saves results only after the execution of an endpoint begins", meaning if incoming parameters fail validation before any side effect starts, no result is cached and a retry with the same key is a fresh attempt, not a replay. Once execution begins, "the resulting status code and body of the first request" is saved and "subsequent requests with the same key return the same result, including 500 errors" [T1]. This is important: even a failed attempt gets replayed verbatim, the guarantee is "you got exactly one logical attempt", not "you get success eventually".
- **Expiry**: results are stored for at least 24 hours; after that, the same key starts a brand-new request rather than replaying [T1].
- **Concurrency**: "If... the request conflicts with another request that's executing concurrently, we don't save the idempotent result" [T1]. In practice Stripe returns an error for the second of two truly simultaneous requests sharing a key rather than letting both execute the side effect; the exact error shape wasn't spelled out in the fetched page, flagged in Unverified below.
- **Scope**: the fetched docs did not explicitly state whether a key is scoped per API key (per Stripe account) or globally; this is a real gap in what I could verify from the page content returned, flagged in Unverified.

**How Solen already applies this (verified directly from `_docs/BACKEND.md`, which is itself file:line grounded in the live codebase).** Solen's own money code already implements the Stripe pattern correctly and in more than one place:

- `lib/bookings/issue-refund.ts`: claims the accounting via a compare-and-set on `refunded_amount` BEFORE calling Stripe, then calls `refunds.create` with a deterministic idempotency key; on a Stripe throw it rolls the CAS back. This is the textbook pattern: reserve the intent locally first, then make the idempotent external call, so a retry after a partial failure can't double-refund.
- `booking-pay-intent` route: creates the PaymentIntent with "a deterministic idempotency key keyed on `(booking_id, baseAmountRappen)`", the PRE-discount amount specifically so a retry after a discount change replays the ORIGINAL PaymentIntent instead of silently forking a second one. This is a sharper application of the pattern than most tutorials show: the key is deliberately built from the invariant part of the request, not the whole payload, so business logic changes that shouldn't create a new side effect don't.
- Cron `pre-charge`: uses a deterministic key `pre-charge:<bookingId>:<amountRappen>` so an overlapping cron retry (two GitHub Actions runs racing) collapses into one charge.
- The webhook handler uses a DIFFERENT but related idempotency mechanism: an atomic unique-constraint INSERT into `processed_webhook_events` (insert-not-check-then-insert specifically to close a race where a mid-handler throw could mark an event processed without finishing it). This is Stripe-side idempotency (their event delivery can redeliver) handled with a database constraint rather than the `Idempotency-Key` header, which is the correct tool for THAT specific problem (an inbound webhook, not an outbound API call Solen controls).

**The real tradeoff.** Idempotency keys cost you: a place to store the key-to-response mapping (a table row, a Redis key, or in Stripe's case their own infra), a decision about key derivation (random per-attempt vs deterministic-from-content, Solen correctly uses deterministic-from-content for money paths so retries collapse), and a TTL policy. They are not free to add to every endpoint. The places they earn their cost are exactly the places Solen already put them: money-moving calls, and any call a flaky network (mobile customer on bad Swiss train wifi, or a cron overlapping itself) might genuinely fire twice.

**Recommended default.** Keep the existing money-path discipline. Extend the same pattern (a deterministic key built from the invariant business identifiers, not the whole request body) to any NEW mutating endpoint where a client retry is plausible and a double side effect would be bad: booking creation itself, voucher/credit redemption, any future partner-facing write. Do not add idempotency keys to routes with no side effect worth protecting (a GET, a read-only search) or where the operation is naturally idempotent already (an UPSERT keyed on a natural unique column).

**Cost of NOT doing this on a new endpoint**: a double-tap on a slow mobile connection double-books, double-charges, or double-redeems. This is exactly the failure class Solen's own `_rules/LESSONS_LEARNED.md` "silent no-op" culture already watches for, the idempotency-key gap is the retry-side mirror image of that same failure family.

## 4. Pagination: offset vs keyset/cursor

**The question.** Solen has 13 uses of PostgREST `.range()` (offset-style pagination) across `app/api`. Is that the right default, and where does it start to hurt?

**What the evidence says**, converging from Use The Index Luke (a well-established, widely cited SQL performance reference maintained by Markus Winand) and multiple 2026 engineering posts on Postgres pagination specifically [T2, https://use-the-index-luke.com/no-offset plus https://blog.sequinstream.com/keyset-cursors-not-offsets-for-postgres-pagination/ and https://www.stacksync.com/blog/keyset-cursors-postgres-pagination-fast-accurate-scalable, three converging sources]:

- **Why OFFSET degrades**: "Offset pagination degrades to O(n) at depth, keyset pagination maintains O(1) regardless of table size... When you request rows with an offset of 1000, Postgres must still traverse those first 1000 rows in the index, even though they'll be discarded." An index helps Postgres find a starting point but it still has to walk and discard every skipped row. Deep pages get linearly slower as the offset grows, this is a mechanical property of how the database executes the query (scan-then-skip), not a tuning problem you can index your way out of.
- **Why OFFSET breaks under concurrent inserts**: "Offset can miss or duplicate rows when data changes during traversal, keyset cursors are immune to this." If a new row is inserted into the sort order ahead of the user's current page while they're paging through, everything shifts by one and the next `OFFSET N` either re-shows a row they already saw or skips one they hadn't seen yet. This is a correctness bug, not just a speed one, and it shows up exactly in the shape of workload Solen has: a discovery feed or a booking list that keeps getting new rows while a user scrolls.
- **What keyset/cursor pagination is**: instead of "skip N, take M", the client sends the last-seen sort key (an id, a timestamp, or a composite of both for a stable tiebreak) and the query becomes `WHERE (created_at, id) < (last_created_at, last_id) ORDER BY created_at DESC, id DESC LIMIT M`. This requires a composite index matching the exact columns and sort order of the keyset, "the index must match both the columns and the sort order of your keyset" [T2]. Done right, cursor pagination stays fast at any depth because Postgres can seek directly to the boundary via the index rather than counting rows.
- **When OFFSET is still fine**: "Offset pagination is the right choice only when users need to jump to a specific numbered page" [T2]. A UI with page numbers (1, 2, 3... 47) genuinely needs offset semantics; keyset pagination can't jump to "page 47" without walking there, only forward/back from a known cursor. For a small, mostly-static admin table (a few hundred to low thousands of rows) the O(n) cost at realistic depths is trivial and not worth the added client complexity of cursor state.

**The real tradeoff.** Keyset pagination is genuinely more complex to implement correctly: you need a stable, unique-enough sort key (a timestamp alone can collide, hence the common id-tiebreak pattern), the client has to carry an opaque cursor forward instead of a page number, and "jump to page 6" style UIs don't map onto it cleanly. It is worth that complexity exactly where two things are both true: the table grows without bound, and/or rows are inserted concurrently with users paging. It is NOT worth it where the list is small and basically static.

**Recommended default for Solen.** Audit the 13 `.range()` call sites and classify each: (a) admin/dashboard tables under roughly 2,000 rows with no concurrent-insert pressure during a paging session, keep OFFSET, it's the simpler and cheaper-to-build option and the O(n) cost is invisible at this size; (b) anything customer-facing that scrolls (a salon list, a discovery feed, a booking history that keeps growing) or anything with real concurrent inserts during the scroll session, move to keyset. `_docs/BACKEND.md`'s note on computed filters already establishes the discipline of "resolve ids before `.range()`, never filter client-side over one page" for correctness on filtered searches; the keyset question is the depth/growth half of the same pagination-correctness concern, not a separate one.

**Cost of the status quo.** At ~28 salons and low traffic, none of Solen's tables are anywhere near the row counts (tens of thousands+) where OFFSET's O(n) walk becomes a measurable latency problem. This is explicitly a "correct eventually, premature to fully migrate today" item, flagged again in the Premature section, with the trigger being either (a) any single paginated table crossing roughly 10k-50k rows, or (b) a user-visible complaint about pages getting slower or showing duplicate/missing rows while scrolling a growing list.

## 5. Versioning: Stripe date-based vs URL path vs header

**The question.** Solen's API has zero versioning today (`app/api` has no `v1`/`v2` directories, confirmed by a direct filesystem check). Should it adopt one, and which style?

**What the evidence says.**

- **Stripe's model**: "Stripe implements versioning with rolling versions that are named with the date they're released (for example, 2017-05-24)... The first time a user makes an API request, their account is automatically pinned to the most recent version available, and from then on, every API call they make is assigned that version implicitly... New accounts default to the latest date. Existing accounts keep working until they explicitly upgrade" [T2, converging summary from multiple sources against the primary docs page, https://docs.stripe.com/api/versioning]. Per-request overrides exist via the `Stripe-Version` header. As of a 2024 process change, versions also carry a codename and are grouped into biannual releases (`2025-04-30.basil` etc). This model exists because Stripe has THOUSANDS of independent third-party integrators who cannot all upgrade in lockstep, and breaking any of them is existentially costly (real money moving). The date-pin is a promise: "your integration keeps working exactly as it did the day you wrote it, forever, until you choose to move."
- **URL path versioning** (`/v1/customers`, `/v2/customers`): the most common pattern in public APIs generally, simple to reason about, but Zalando's engineering guidelines explicitly reject it for their own APIs: "URL versioning... must not be used, as it creates tighter coupling and complicates release management" [T2, https://github.com/zalando/restful-api-guidelines/blob/main/chapters/compatibility.adoc], preferring media-type/header versioning (`Content-Type: application/x.zalando.cart+json;version=2`) instead, on the reasoning that it decouples the URL (a resource identity) from a representation choice (a format/version), and plays better with HTTP content negotiation. This is a real disagreement in the industry: URL-path versioning is far more common in practice (it's visible, debuggable, cacheable per-version) even though several style guides argue it's architecturally impure.
- **The actual precondition for any of these mattering**: all three schemes exist to solve ONE problem, letting a client that can't or won't upgrade immediately keep working while the server evolves. That precondition is a client Solen doesn't control upgrading on its own schedule. Solen controls both its web client and, practically, its mobile client's release cadence (an internal team ships both). There is no third party pinned to an old contract.

**The real tradeoff.** Any versioning scheme (date-based, URL-path, or header) is pure overhead if you don't have the problem it solves: you now maintain N behaviors instead of one, you need a deprecation/sunset process (section 11) to ever retire an old version, and you need version-routing logic in every handler or a gateway that does it for you. Stripe pays this cost because the alternative (breaking arbitrary third-party integrations) is far worse. Solen, with zero third parties, would be paying Stripe's cost structure for a problem it doesn't have.

**Recommended default for Solen.** No formal versioning scheme today. Ship route changes as: update the route handler and the one client that calls it (web or mobile) in the same deploy/PR wherever possible; for a genuinely breaking change to a route BOTH clients hit (rare, since the mobile app mostly calls the same endpoints as web), coordinate the mobile app release rather than standing up version infrastructure, mobile release cadence is the real constraint, not a versioning header. Where the mobile app must tolerate a short window of an old-vs-new server behavior (app store review lag is real and can be days), a targeted, narrow shim (an optional field, an additive change, a feature-flagged behavior) is cheaper than any of the three formal schemes.

**When this flips.** The day Solen opens a partner/public API (a salon POS integration, a third-party booking widget) is the day a real versioning scheme becomes necessary, and at that point Stripe's date-based model is the strongest reference: it is explicitly designed for "many independent integrators, unknown upgrade timelines", which is exactly the shape a public API creates. Revisit then, not before.

## 6. Error format: RFC 9457 Problem Details

**The question.** RFC 9457 defines a standard JSON error shape. Does it obsolete RFC 7807 (the owner's brief asked this to be confirmed), and should Solen adopt it?

**Confirmed**: yes, RFC 9457 explicitly obsoletes RFC 7807 [T1, primary source, https://www.rfc-editor.org/rfc/rfc9457.html, and confirmed independently by https://blog.frankel.ch/problem-details-http-apis/ whose title states it plainly: "RFC 7807 is dead, long live RFC 9457"]. The core structure carries over almost unchanged: five members, `type` (a URI identifying the problem category, defaults to `about:blank` if unspecified), `title` (a short human-readable summary of the TYPE, not the instance), `status` (the HTTP status code, duplicated in the body so a body-only consumer, e.g. a message queue, still has it), `detail` (an explanation specific to THIS occurrence), `instance` (a URI identifying this specific occurrence, useful for support/log correlation). The media type is `application/problem+json`. RFC 9457's actual additions over 7807 are narrower than the marketing implies: mainly an IANA registry for common problem `type` URIs so ecosystems can share well-known problem types instead of everyone inventing their own, plus clearer guidance that extension members are allowed and unrecognized ones MUST be ignored by clients (so a producer can add domain-specific fields, e.g. an array of per-field validation errors, without breaking generic consumers) [T1, same primary source]. There is no "errors array" standardized in the base spec, that would be an extension a given API defines itself, not something 9457 mandates.

**What Solen has today (verified by direct grep)**: an ad hoc `{ error: string }` shape, used in the overwhelming majority of the 415 status-setting responses found across `app/api`. This is NOT RFC 9457 shaped (no `type`, `title`, `instance`; `error` roughly maps to `detail`). It is also not wrong for what it's used for today: internal error messages consumed by Solen's own web and mobile clients, which know the shape because Solen wrote both ends.

**The real tradeoff.** RFC 9457's value is INTEROPERABILITY: a generic HTTP client, API gateway, or monitoring tool can parse any RFC-9457-shaped error without knowing Solen's specific error vocabulary, and a `type` URI gives a stable machine-readable category independent of the (possibly localized, possibly changed-for-copy-reasons) human message. That value is highest when: (a) third parties consume your errors, (b) you want tooling (Sentry-style aggregation, API gateways, OpenAPI-generated clients) to automatically understand error shapes, or (c) you have many services each inventing their own error shape and want one contract across them. Solen today has one backend, two first-party clients that already know the ad hoc shape, and no third-party consumers. Adopting the full RFC 9457 shape everywhere right now would mean touching some large fraction of 354 route files for a benefit (interop with nobody) that doesn't exist yet.

**Recommended default.** Do not do a mass migration of all 415 existing error responses today, that is real, disruptive engineering effort against near-zero present payoff (see Premature section). DO adopt the RFC 9457 shape (or at minimum its `type`/`title`/`detail` subset, since `instance` needs a URI scheme decision) for any brand-NEW route written from here forward, and for any route being substantially rewritten anyway. This gets Solen incrementally onto the standard at zero extra migration cost, riding normal feature work, and means the day a partner API or gateway tooling shows up, most new surface is already compliant.

**Cost of adopting it selectively rather than uniformly.** Two error shapes coexist in the codebase for a while. That's a real but bounded cost (a client has to handle both `{error: string}` and `{type, title, status, detail}` during the transition), acceptable because Solen's clients are first-party and can be updated in lockstep with the routes they call.

## 7. Validation at the trust boundary

**The question.** Is untrusted input (from the customer's browser, the mobile app, or any external caller) validated before it reaches business logic and the database?

**What the evidence says.** OWASP's API Security Top 10 (2023 edition, the current one) puts authorization and input-trust failures at the very top of the list. Specifically **API3:2023 Broken Object Property Level Authorization** "combines API3:2019 Excessive Data Exposure and API6:2019 Mass Assignment, focusing on the root cause: the lack of or improper authorization validation at the object property level," meaning an endpoint that blindly accepts and writes whatever fields a client sends (mass assignment) or blindly returns whatever fields exist on a row (excessive data exposure) is a top-tier, industry-wide vulnerability class, not a theoretical one [T1, https://owasp.org/API-Security/editions/2023/en/0x11-t10/, the official OWASP page]. **Broken Object Level Authorization (API1)** has held the number-one spot since 2019 and again in 2023 [T1, same source family], the class of bug where an endpoint checks that a caller is authenticated but not that they own the SPECIFIC object id in the URL/body.

The generic engineering discipline these map to: never trust a client-supplied value for anything that determines money, ownership, or access, always re-derive it server-side from what the authenticated session actually owns; validate the SHAPE of input (types, ranges, required fields) at the boundary before any of it reaches a query or a Stripe call; and never let a client-supplied object be spread directly into an UPDATE/INSERT (the mass-assignment failure mode) without an explicit allowlist of writable fields.

**How Solen already does this (verified directly).** 137 route files import shared zod schemas (`lib/validations.ts`), meaning shape validation at the boundary is already the norm, not an exception, across a large majority of mutating endpoints. `_rules/SECURITY_RULES.md`'s documented layer order (feature flag then auth then ban check then rate limit then zod validation then business logic) puts validation explicitly in the request pipeline before business logic runs, which is the textbook trust-boundary placement. The money-path code already re-derives amounts server-side rather than trusting a client-sent price (per `_docs/BACKEND.md`'s description of the discount/PaymentIntent flow reading back from the actually-returned PaymentIntent, not the client's in-memory calculation).

**The real tradeoff.** Validating everything at the boundary costs a bit of boilerplate per route (a schema definition, a parse call) and occasionally friction when a genuinely optional field needs careful `.optional()`/`.nullable()` schema design. The alternative, validating loosely or trusting a TypeScript type alone (which vanishes at runtime and proves nothing about what the network actually sent), is how mass-assignment and type-confusion bugs get into production; this project's own `_rules/LESSONS_LEARNED.md` culture around "silent no-ops" is the same failure family one layer downstream of a validation gap.

**Recommended default.** Keep the current zod-at-the-boundary discipline as the mandatory pattern for every new route. Where a route is found NOT using it (a genuine minority, since 137 of what is likely 200+ mutating routes use it, exact denominator not established from a grep alone), that is a finding worth flagging per-route, not a systemic redesign.

## 8. Batch operations

**The question.** How should an endpoint that operates on many resources at once be shaped?

**What the evidence says**, from Google's API Improvement Proposals (AIP), a widely used and carefully reasoned reference for resource-oriented API design even outside Google itself [T2, https://google.aip.dev/ and specifically the batch operations guidance surfaced via https://deepwiki.com/aip-dev/google.aip.dev/3.3-batch-operations]: batch method names follow a `Batch` + standard-verb pattern (`BatchCreate`, `BatchGet`), and "documentation should specify the maximum number of resources in a batch (typically 1000)." The core design questions a batch endpoint has to answer explicitly: is the operation atomic (all-or-nothing) or best-effort (partial success, with a per-item result array telling the caller which ones failed and why)? What is the hard cap on batch size (unbounded batch size is both a DoS vector and a timeout risk, doubly so on a serverless Lambda with a wall-clock limit)? And does the response echo back a per-item status, or just an aggregate success/fail?

**How Solen already does this (verified directly).** Batch-shaped endpoints already exist: `app/api/slots/bulk`, `app/api/dashboard/batch`, `app/api/admin/discovery/bulk-import`. Whether each of these declares an explicit item cap and an explicit atomic-vs-partial-success contract is a per-file question this research pass didn't verify (see Audit Questions); the existence of the pattern is confirmed, its rigor is not.

**The real tradeoff.** An atomic batch (all rows succeed or none do, typically one DB transaction) is simpler to reason about but means one bad row in a 500-row import blocks the other 499. A partial-success batch is more forgiving to the caller but pushes complexity onto them (they must read a per-item result array and handle a mixed outcome) and onto the server (the failure of item 37 must not corrupt the state of items 1-36 that already committed). At Solen's real batch use cases (bulk slot creation, discovery bulk-import, dashboard multi-select actions) partial success is usually the right call, a salon owner bulk-creating 200 slots would rather get 198 created and 2 flagged than have one bad slot definition silently void the whole batch. This should be a stated, deliberate choice per endpoint, not an accident of whichever came naturally out of a loop.

**Recommended default.** Any batch endpoint should explicitly document (in a code comment at minimum) its item cap, and whether it's atomic or partial-success, and if partial-success, return a per-item result array (not just a total count) so the caller can retry only the failed subset, which composes naturally with the idempotency-key discipline in section 3 (retry the failed items with the same deterministic key derivation, the succeeded ones replay harmlessly).

## 9. Long-running operations: 202 + poll vs webhook callback

**The question.** How should an operation that can't complete within a single request/response cycle (an AI image generation, a large export, a batch payout run) be exposed?

**What the evidence says**, converging across several practitioner sources plus Microsoft's documented Azure pattern (a widely cited reference architecture for this exact problem) [T2, https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply and https://restfulapi.net/rest-api-design-for-long-running-tasks/]: the standard shape is `POST /jobs` returns `202 Accepted` immediately with a `Location` (or a job id in the body) pointing at a status resource, then the client either polls `GET /jobs/{id}` until it reaches a terminal state, or the server calls back to a client-supplied webhook URL when done. "202 Accepted... signaling successful receipt of a request without guaranteeing its immediate completion... specifically designed for asynchronous operations where processing may take significant time." Polling is simpler to implement (no need for the caller to expose a reachable endpoint) but uses more bandwidth/requests and adds latency (bounded by poll interval) to when the caller learns of completion; webhooks are lower-latency and lower-bandwidth but require the caller to run something reachable and to handle retries/ordering/security (signature verification) on the receiving end. Google's AIP takes essentially the same position for its ecosystem: "individual API methods that might take a significant amount of time to complete should return a `google.longrunning.Operation` object instead of the ultimate response message" and mandates that all such APIs implement ONE shared Operations service rather than each inventing its own polling contract [T2, https://google.aip.dev/151].

**Why this specifically matters for Solen's infrastructure.** Netlify functions (the actual host, verified from `netlify.toml`/`@netlify/plugin-nextjs`) run as serverless functions with a wall-clock execution limit; a route handler that tries to synchronously wait out a slow Gemini/fal image generation or a large export risks hitting that ceiling and failing the whole request with no partial progress saved. This isn't a style preference, it's a hard platform constraint. Solen ALREADY has the webhook side of this pattern working correctly for Stripe (the webhook handler with its idempotent event-claim table); the polling side (a job-status resource for slow internal operations like AI generation) is the piece worth checking for consistent presence.

**The real tradeoff.** Building the 202+poll pattern properly needs: a persisted job row (status, progress, result, error), a status endpoint, and a decision on how long completed job rows are kept before cleanup. That's real infra for what might be a small number of genuinely slow operations. The cheap alternative, just letting the request run long and hoping the platform timeout doesn't hit, is exactly the kind of thing that works fine in dev and fails silently or loudly in production under real latency (a slow AI provider day, a large export).

**Recommended default for Solen.** Any endpoint that calls out to Gemini/fal for generation, or that could plausibly produce a large export, should be checked against: does it return promptly (202-style) with a pollable status, or does it block the Lambda? Where it blocks and the operation is reliably fast (sub-few-seconds), that's fine as is, adding job-polling machinery to something reliably fast is unneeded complexity. Where it can genuinely run long (AI image generation is the obvious candidate given the existing daily-cap/budget code in `lib/ratelimit.ts` treats it as expensive), it should move to the job-row-plus-poll shape if it hasn't already. This is a per-route audit, not a blanket rewrite (see Audit Questions).

## 10. OpenAPI

**The question.** Should Solen maintain an OpenAPI spec for its API surface?

**What the evidence says.** The current OpenAPI Specification version is 3.2.0, released September 2025, building on 3.1 (Feb 2021) with additions like structured tag nesting and native streaming media type support; "OpenAPI 4.0 does not exist" as of the search date, mentions of it or "Moonwalk" refer to a still-in-development future major version [T2, converging from https://apiscout.dev/guides/openapi-4-whats-new-migration-guide-2026 and the OpenAPI Initiative's own site https://www.openapis.org/, plus the spec repo https://spec.openapis.org/oas/v3.2.0.html]. OpenAPI's value proposition is: a single machine-readable contract that generates client SDKs, interactive docs (Swagger UI/Redoc), server-side request validation, and contract tests, all from one source of truth. Confirmed by direct filesystem search: Solen's own repo has zero OpenAPI files (the only `openapi` hits are inside `node_modules` for the Stripe and Svix SDKs, which ship their OWN OpenAPI specs describing THEIR APIs, not Solen's).

**The real tradeoff.** OpenAPI's biggest wins (generated client SDKs for external consumers, interactive API docs for partners, contract-testing a public surface) all assume there's an audience beyond the team that already knows the code. Solen's two clients are both written by the same team that writes the routes; they don't need generated SDKs, they read `lib/validations.ts` and the route file directly. Writing and maintaining an OpenAPI spec for 354 route files by hand would be a very large one-time cost plus an ongoing maintenance tax (every route change needs a matching spec change, and a spec that drifts from the actual code is worse than no spec because it actively misleads). Auto-generating one FROM the existing zod schemas is possible (there are zod-to-OpenAPI tooling options) and would lower that cost substantially, but this pass did not verify any specific tool's fit for Next.js Route Handlers + zod 4.3.6, so a concrete recommendation on tooling is UNVERIFIED here.

**Recommended default.** Do not hand-write a full OpenAPI spec today, the cost is large and the present audience (internal only) doesn't need it. If a public/partner API ever ships (the same trigger as the versioning section), that is the point to generate an OpenAPI spec FROM the existing zod validation schemas rather than writing one from scratch, since 137 route files already have the shape information a generator needs.

## 11. Deprecation policy: Sunset header (RFC 8594)

**The question.** How should Solen retire an old endpoint or field, and does the Sunset header (RFC 8594) apply?

**What the evidence says**, from the RFC itself and Zalando's widely cited engineering guidelines [T1 for the RFC, T2 for the practitioner pattern of pairing it with a Deprecation header]: RFC 8594 "defines the Sunset HTTP response header field, which indicates that a URI is likely to become unresponsive at a specified point in the future," carrying a single HTTP-date timestamp for when the resource is EXPECTED to stop responding [T1, https://datatracker.ietf.org/doc/html/rfc8594]. It is explicitly a two-stage story: "deprecation happens in two stages: the first stage being that the API is not the preferred or recommended version anymore and the second stage being that the API or a specific version of the API gets decommissioned. The Sunset header field is appropriate for the second stage." In practice, teams pair it with a separate (still-draft, not yet an RFC) `Deprecation` header marking the START of the deprecation window, with `Sunset` marking its END, "the window between them is when clients can still use the endpoint but should be migrating off it" [T2, https://zuplo.com/learning-center/http-deprecation-header]. Zalando's own guidelines operationalize this: "producers setting `deprecated: true`... and adding further explanation," requiring migration documentation, and requiring EXTERNAL partner consent to the sunset timeline before they're even allowed onto the deprecated version in the first place [T2, https://github.com/zalando/restful-api-guidelines/blob/main/chapters/deprecation.adoc].

**The real tradeoff.** This entire mechanism exists to coordinate a deprecation with clients you don't control the release cadence of. Solen has exactly that situation in ONE place today: the mobile app, whose users can sit on an old App Store build for a while after a server change ships (unlike the web app, which every visitor gets fresh on next page load). For any route ONLY the web app calls, there's no one to send a Sunset header to, remove it when the code removes it. For any route the MOBILE app calls, an old app build could still be hitting a route the server team wants to retire; that is the one real internal case where a deprecation window (even an informal one: "keep the old route alive and working for N weeks past the app store release before removing it") matters, though a machine-readable Sunset header specifically is more valuable when an automated OTHER SYSTEM (a partner's server, a monitoring tool) needs to react to the date programmatically rather than a human developer just remembering to check.

**Recommended default.** Don't build the formal Sunset/Deprecation header machinery today, there's no automated third-party consumer that would parse it. DO keep the underlying discipline it encodes: before removing or breaking a route the mobile app calls, keep the old route alive and working for a real window (long enough to cover reasonable adoption of the new mobile build, informed by actual app-store release-to-adoption lag, not a guessed number) rather than deleting it the moment the new client ships. `_design-system/REMOVED.md`'s existing graveyard discipline (log what was removed and why) is the right adjacent pattern to extend to API removals specifically, so a removed route's history is traceable the same way a removed UI feature's is.

## Myths and traps

- **MYTH: "REST means resources and verbs, that's the whole standard."** Fielding's actual REST requires HATEOAS (server-driven hypermedia navigation); almost nothing anyone calls a "REST API" today, including Stripe's, implements that. What the industry means by REST is a convention (CONV), not a formal standard being followed. Naming this precisely matters so nobody chases HATEOAS compliance as a real requirement for Solen.
- **MYTH/STALE: citing Vercel-specific caching or deployment behavior as if it applies to Solen.** Solen is hosted on Netlify (`@netlify/plugin-nextjs`), confirmed live in this project's own stack notes. Any Next.js caching/ISR/edge-function advice sourced from a Vercel-authored blog post needs re-verification against Netlify's actual adapter behavior before being treated as fact for this codebase; this file did not independently re-verify Netlify's Next.js plugin caching semantics (flagged in Unverified).
- **Trap specific to our stack: PostgREST silently returns null on a nonexistent column, not an error.** This is the project's own documented #1 failure mode (`_rules/LESSONS_LEARNED.md`, `_docs/BACKEND.md`), and it interacts directly with API design: a validation layer that only checks the SHAPE of a zod schema, not that the schema's field names actually exist as live DB columns (per `_inventory/_db-snapshot.json`, not a TS type), can pass validation cleanly while silently no-op-ing the underlying write or filter. Any new endpoint's zod schema should be checked against the live DB snapshot, not just against a `Database` TypeScript type that could itself be stale.
- **Trap specific to serverless/Netlify: a synchronous long-running-operation route is a timeout waiting to happen, not just a style violation.** On a traditional always-on server, blocking a request thread for a slow AI call is wasteful but survivable. On a serverless function with a hard wall-clock limit, it's a hard failure with no partial state saved unless you've built the 202+poll job-row pattern (section 9).
- **Trap specific to Stripe Connect specifically: an idempotency key must be deterministic from BUSINESS-INVARIANT fields, not the whole request body, or a legitimate retry after a mid-flight state change (e.g. a discount recalculated) silently forks a second real-money side effect instead of replaying the first.** This is exactly why `booking-pay-intent`'s key is built from `(booking_id, baseAmountRappen)`, the PRE-discount amount, not the full computed charge, per `_docs/BACKEND.md`. A naive "hash the whole JSON body" key generation strategy would NOT have this property and is a real anti-pattern for this specific stack.
- **Trap: treating a 200 with `{success: false}` in the body as acceptable API design.** Every fetched source on status codes agrees the HTTP status line itself should carry the outcome so that generic infrastructure (caches, proxies, monitoring, retry logic) that only looks at the status code behaves correctly without parsing the body. This wasn't directly evidenced as a Solen-specific problem in this pass (not systematically checked across all 354 routes), flagged as an audit question below rather than asserted as a finding.

## Premature at our scale

- **Full OpenAPI spec for the whole API surface.** Correct once there's a partner/public API or once client SDK generation actually saves real engineering time across multiple consuming teams. Premature now: 354 routes, two first-party clients written by the same team, zero external consumers. Trigger to revisit: first partner/public API integration request, or the mobile team repeatedly hand-writing request/response types that drift from the server (a sign a generated contract would pay for itself).
- **A formal versioning scheme (date-based, URL-path, or header).** Correct once a third party is pinned to a contract on a schedule Solen doesn't control. Premature now: coordinate the one internal mobile release instead. Trigger: first public/partner API.
- **Mass migration of all existing `{error: string}` responses to full RFC 9457 Problem Details.** Correct value materializes with generic tooling or third-party consumers. Premature now as a blanket rewrite (real engineering cost, near-zero present payoff); adopt incrementally on new/touched routes instead (already the recommendation above, not a contradiction, the premature part is specifically the BULK BACKFILL, not the standard itself).
- **Full keyset-pagination migration of every `.range()` call site.** Correct for tables that grow into the tens of thousands of rows or see heavy concurrent inserts during paging sessions. Premature as a blanket sweep today given Solen's actual row counts at 28 salons; do it per-table as each one's growth or concurrency profile actually warrants it (see section 4's audit split).
- **A formal Sunset/Deprecation HTTP header pipeline with machine-readable timestamps.** Correct once an automated external system (a partner's integration, a public API consumer) needs to programmatically react to an announced retirement date. Premature now: the one internal case (mobile app version lag) is better served by a human-managed "keep the old route alive for N weeks" discipline than by header infrastructure nobody automated is reading.
- **gRPC or a service-mesh-style internal RPC layer.** Correct once Solen has multiple genuinely separate backend services calling each other at real scale. Premature now: one Next.js monolith-style backend talking directly to Postgres and Stripe, no internal service-to-service traffic to optimize.
